# ADR-0017: User documentation site

Status: Accepted · Based on: D-067, N-081 · SRs: SR-139, SR-140, SR-141 · Issue #344

## Context

D-067: ReqSeq has documentation for its users, in Get started, How-to, Reference and Concepts; what can be generated from the tool's sources is generated, never written by hand; online is only the version of the latest release, and each delivery brings its own version. SR-139 asks for a reference generated from the descriptions the tool itself uses, SR-140 for examples that run against the version, SR-141 for documentation that is readable and searchable without network and opens from the app. Architecture and developer docs stay in the repository.

## Decision

**Generator.** Astro with Starlight: Markdown pages, sidebar, light and dark mode, and a local search that needs no server (Ctrl K). The search is our own, not Starlight's Pagefind (product owner decision, 2026-11-09, #1220: Pagefind's WebAssembly holds crates outside the licence allowlist of ADR-0015): after the build, `writeSearchIndex` of `packages/docs/src/search-index.ts` (an Astro integration in `astro.config.mjs`) reads every built page and writes `search-index.json`, a MiniSearch index of title, headings and text with the URL, title and an excerpt stored, and the options it was built with. `site/src/components/Search.astro` replaces Starlight's search component (`pagefind: false`, `components.Search`): a button and a dialog with a search box, opened with Ctrl K (⌘ K), whose script fetches the index from the site on the first search and searches it with MiniSearch, the same version as the generator, the hits written as text. Arrow keys move between box and hits. It needs only `connect-src 'self'` and no `eval` or WebAssembly, online and offline. The same integration writes `llms.txt` (an index with one line per page, by sidebar section) and `llms-full.txt` (every page as Markdown under its title and address) from the content folder (`packages/docs/src/llms.ts`, #1260), so AI assistants read the documentation as plain text, offline too.

**Sources and layout.**

- Hand-written pages: `docs/guide/` (Markdown, English, SR-074).
- `packages/docs` (`@reqseq/docs`, private, never shipped): the generator in `src/` (TypeScript, 100 % coverage, ADR-0016). It depends on `core`, `cli`, `app`, `api` and `mcp`, whose exports it reads. `pnpm docs:generate` copies `docs/guide/` into the one content folder Starlight reads, `packages/docs/site/src/content/docs/` (git-ignored, a copy rather than a link so every system reads the same files), and writes the generated reference next to it. Hand-written pages live in `index.md` or the section folders `start/`, `how-to/` and `concepts/`, which the sidebar lists; the generator refuses a page elsewhere.
- `packages/docs/site/`: the Starlight site, `.mjs` config and CSS only. It is not a workspace member (`packages/*` matches direct children only) and has its own lockfile, installed with `--ignore-workspace --ignore-scripts` only by the docs steps of CI and by `docs-pages.yml` (precedent: `toolchain/packaging/`, ADR-0014). So the about 290 packages of Astro never reach other jobs or agent installs.
- `pnpm docs:build` generates, installs the site and builds it into `packages/docs/site/dist/`.

**Generated.** The reference of SR-139, plain Markdown (no MDX), never written by hand. Commands (in place): `reference/commands/`, an index by catalog group and one page per catalog command with title, summary, effect, inputs and outputs from its schemas (a `$ref` named by its definition, with its description), and its call in each access, each taken from the adapter itself: the app's command prompt entry (`appCommandEntry` of `@reqseq/app`: the covering action or the catalog title, with its key), the exact `--help` of the CLI (`runCli` in-process), the API path and the MCP tool, both checked against `schemas/generated/`; after them a page `servers` with the `--help` of `serve api`, `serve docs` and `mcp`, the commands outside the catalog. Internal references in the texts (SR, D, ADR, #nnn) stay as the tool shows them. Codes: `reference/problem-codes/`, cause and remedy of every problem and error code from `schemas/problem-codes.yaml`, with an anchor per code (`#relation-outdated`, errors `#error-input-invalid`). Formats: `reference/formats/`, one page per schema of a file users read or write, with its fields, its definitions (an anchor each) and its examples from `schemas/examples/<format>/` (also SR-009 AK1), and `reference/common-types/` from `common.schema.json`; a `$ref` in a command or format page links there. `activity` and `recent-workspaces` are internal cache files and only listed; the generator fails on a schema that is neither documented nor listed. Standard model: `reference/standard-model/`, every type, property, relation kind and status of `schemas/examples/metamodel/standard-model.yaml` (the metamodel `workspace.init` writes) with its `description` from that file and an anchor each (`#type-need`, `#property-title`, `#relation-refines`, `#status-draft`). Keyboard shortcuts: `reference/keyboard-shortcuts/`, every key of the app with what it does on Windows and Linux and on macOS (SR-139 AK5), from `shortcutReference` of `@reqseq/app`, which reads the app's own tables: the actions with their shortcuts, the letters after the prefix key, and the tables next to the handlers of the application menu, prompts, lists, graphs, the element buffer and the editor (slash menu, `[[`, the Markdown keymap); CodeMirror's own text editing keys get one sentence, not a list. Links between pages carry the base path, so the generator reads `REQSEQ_DOCS_BASE` too. What's new: `whats-new/`, every release tag in the history of the build, newest first, with the summary of its version from `docs/releases/` as on the GitHub release, and the commits since the last release tag; a tag without a summary and the unreleased commits get the sections New, Fixes and Specification of the GitHub release notes (`releaseNotes`, #346), without the other changes and the compare link (#1259). `pnpm docs:generate` writes it after the generator with `scripts/package/stage.mjs --whats-new`, from Git (`git tag`, `git log`), so a delivery's offline site carries the notes of its own and every earlier version. The published builds check out the whole history and set `REQSEQ_DOCS_RELEASES=1`, which fails a build in a shallow clone or without a release tag; a shallow checkout, as in the CI of pull requests, gives a page without releases.

**Tested examples (SR-140).** Every `reqseq` command in a ```` ```sh ```` block (or `bash`, `shell`, `zsh`, also indented in a list item) of a guide page is an example; a block that mixes it with other commands, and a `reqseq` command in any other block (also after a prompt such as `$`), are refused, so no example is skipped silently. `docs:generate` and the `[SR-140/AK2]` test run the examples of each page in order, in a fresh empty folder, with `runCli` of this build in-process (no shell: the words are split by the generator, quotes only, and shell syntax is refused). A ```` ```text title="Output" ```` block right after a block is the expected output of its last command: a line `...` stands for any lines, `...` in a line for any text, and a short or file ID (`N-7fe707`, `N-d0e44b7fe707`) for the ID the run creates, which later commands of the page then get in its place. Any other block with a title (```` ```xml title="evidence/ci/results-build-1.xml" ````) is a file the page writes at that point, with the same IDs in place of the samples, at a relative path inside the folder (refused otherwise), so a page can show a workspace file or a test tool's JUnit file and the commands that read it. A non-zero exit code, a differing output, or a command still running after 60 s (it is then stopped through its signal) stops the build. Hand pages above 600 words of prose get a warning.

**How-to pages (SR-140 AK3).** Each page in `how-to/` has the sections `## App`, `## CLI`, `## API` and `## MCP`; where the task is not possible in an access, its section says so in one line. The CLI section holds the tested examples. The API section shows each request as an ```` ```http ```` block, `POST /v1/commands/<command>` and after a blank line the JSON input; the MCP section each tool call as a ```` ```json ```` block `{ "name": "<tool>", "arguments": {...} }` (a JSON block without `name`, such as a client configuration, is no call). `docs:generate` and the `[SR-140/AK3]` test refuse a how-to without one of the four sections, a bold name in `## App` that is no command prompt entry (`appCommandEntry`), and a command, tool or input field that `schemas/generated/` does not have. Options are not repeated: the pages link to the command reference. The user content of `docs/delivery/` is the how-to "Install ReqSeq"; its two files stay as pointers, since the release workflow links them. Connecting a test tool (SR-063) is the how-to "Record test evidence from JUnit XML" with "Name the requirement in a test" and "Record test results in CI", whose CI snippets the end-to-end test of SR-063 reads (#1255); `toolchain/junit/README.md` keeps only a pointer to them and the example with its tested blocks "Try it here".

**Screenshots.** The app's pictures on the guide pages come from the Electron spec `packages/app/test/guide-screenshots.spec.ts`: it opens the fixed workspace `fixtures/SR-140/get-started` (exactly the elements the steps of Get started create) for the pictures of Get started and the slash menu, and `fixtures/enabler-344/weather-station` (more elements, the standard model) for the traceability matrix and the metamodel graph, in light mode at 1024×576 (the metamodel graph at 1600×1000, cut to its boxes), waits for each view to be complete, and writes `app-<view>.png` to the CI artifact (`test-results/electron/guide-images/`). Only `pnpm docs:screenshots` (Linux, under `xvfb-run` without a display) sets `REQSEQ_GUIDE_IMAGES`, so that the spec also writes `docs/guide/images/`; a normal test run changes no tracked file. It runs on Linux only, because fonts and anti-aliasing differ between systems; a run on the same system writes the same bytes. `docs-pages.yml` runs `pnpm docs:screenshots` before every build of the published site, so the site always shows the app of its release. The committed copies serve the README (which shows the animation below), GitHub's view of the pages and the site build of pull requests; after a change to the app that the pictures show, the author runs `pnpm docs:screenshots` and commits them. Both fixtures have the IDs Get started prints. The README's animation (SR-140 AK4) comes from `guide-animation.spec.ts` the same way: it does the steps of Get started in the app on an empty folder and ends in the graph of the need, one frame per step and every few typed letters, and with `REQSEQ_GUIDE_IMAGES` ffmpeg (one palette, no dithering) makes `app-get-started.gif` of them, with a grey frame and round corners that are transparent outside, so that it reads as a screen on light and dark pages; ImageMagick (`convert -layers Optimize`) then stores only the changed rectangle per frame, which ffmpeg does not once a frame has transparent pixels. A module loaded into the core process only by this spec gives the two new elements the UUIDs of the fixture, so the animation shows the README's IDs. A generated page may show an image of the guide too (the standard model page does), under the same check. Nothing compares pixels, so CI never fails on a rendering detail. What CI enforces is that a page never shows a picture that is gone: `docs:generate` refuses an image (`![alt](path)`) without alt text or whose relative path names no file of the guide, and `images/` is the one folder outside the sections, for images only. Astro serves the files as they are (`passthroughImageService`), since its default service needs the native package Sharp.

**No network.** No web fonts, CDN or analytics; system font stacks. `packages/docs/site/run.mjs` starts Astro with telemetry and the update check off (`ASTRO_TELEMETRY_DISABLED`, `ASTRO_DISABLE_UPDATE_CHECK`). CI builds the site under `unshare -rn`, so a download during the build fails it.

**Base path.** `site` is `https://thomasbirkmaier.github.io`, `base` comes from `REQSEQ_DOCS_BASE` (default `/ReqSeq` for Pages, `/` for the offline build). Hand-written pages link without the base (`[Get started](/start/get-started/)`); `docs:generate` adds it when it copies them, so the same pages build for both.

**Offline build (SR-141).** The delivery ships the site built with `REQSEQ_DOCS_OFFLINE=1` (#1205): base `/` for the site and the generator, no link to the repository, which leads nowhere without network, and no `site`, so no page names an address the delivery does not have (no canonical link, no sitemap). It writes hidden source maps, from which the staging tells the packages of its scripts (ADR-0015) before it leaves them out. Every page title names the version, `<page> | ReqSeq <version>`, online too. The release job `docs-site` builds it once on Linux with the steps it shares with `docs-pages.yml` (`.github/actions/docs-site`), and `scripts/package/stage.mjs` puts it into the staged CLI as `docs/` (ADR-0014), after checking that it is the offline build of the root version and the licences of what it ships (ADR-0015). It is served over HTTP, not opened through `file://`: the search loads its index with `fetch`, which `file://` blocks, and Starlight's links point to folders. CLI-only users, such as those on a stock Ubuntu 24.04 where the app needs the admin step (ADR-0014), open it with `reqseq serve docs [--port <n>]`, which serves the site on `127.0.0.1` only and prints its address (product owner decision, 2026-11-08: the bundled docs open through a CLI command that serves them on loopback). The block `@reqseq/core/docs-site` (only `node:*`, reads only) holds the request-to-file rule, the media types, the headers with the CSP and `commandPagePath`, and `startDocsServer` of `@reqseq/api` serves it with the Host rule of the API, GET and HEAD only, without token and without writing anything; there is no option for another address or folder (`packages/core/docs/docs-site.md`). How the app opens the site is decided with #1192.

This is no catalog command, an assumption without a question issue: SR-141 names the accesses itself („mit jeder Auslieferung mitliefern“, „aus der App heraus öffnen“), and SR-080 AK1 asks for every function in every access, where „reine Darstellung“ is excluded and „Werte aus den Dateien des Arbeitsbereichs“ are not; the documentation is neither a workspace value nor a function on one, but fixed files of the delivery. Like `serve api` and `mcp`, `serve docs` is a transport, and one module of core decides what every way in serves.

**Pages.** `.github/workflows/docs-pages.yml` builds the docs of a tag with `.github/actions/docs-site` (also without network now) and deploys them with `actions/upload-pages-artifact` and `actions/deploy-pages`. `release.yml` calls it after its `release` job published a release; a run by hand takes a tag. Only the deploy job has `pages: write`, `id-token: write` and the environment `github-pages`, and it deploys only when the tag is the latest release. `main` is built only as a check of pull requests, in both variants: CI builds the Pages one and then the offline one with `stage.mjs --docs-site`. Once, the product owner sets the Pages source to "GitHub Actions" and allows the tags `v*` in the environment `github-pages`.

**Checks.** Linux-only steps of the required job `checks` generate the content, install the site, audit it (`pnpm audit --audit-level high` on the site lockfile; `pnpm audit --prod` and `licenses:check` of the workspace do not see it) and build it offline. `starlight-links-validator` fails the build on a dead internal link. `tests-needed.sh` counts `docs/guide/` as a change that needs these steps.

## Consequences

- A docs change runs the full `checks` job. The site adds about a minute to it.
- The site's packages are dev tools in their own lockfile; the audit step blocks a pull request on a high finding.

## Rejected

- The site as a workspace package: about 290 packages in every install and job on three systems, and Astro's `.ts` and `.astro` files under the coverage and lint gates.
- A separate CI job with a path filter: the required checks would not gate it, and the pages depend on core and the CLI too.
- `on: release: published` for Pages: a release published with `github.token` starts no workflow.
- Docusaurus, VitePress, MkDocs: heavier (React), no plain-Markdown sidebar with built-in offline search, or a Python toolchain.

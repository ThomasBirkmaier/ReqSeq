# ADR-0008: In-memory model, search index, cache and file watching

Status: Proposed · Based on: D-002, D-014 · SRs: SR-003, SR-007, SR-015, SR-020, SR-068, SR-081, SR-082

## Context

Targets at 50,000 elements and 200,000 relations on 4 cores and 16 GB: start ≤ 3 s with cache, ≤ 30 s without; open element ≤ 200 ms; filter or chain ≤ 500 ms; search ≤ 300 ms; full check ≤ 60 s; external change visible ≤ 2 s; pull with 1,000 files ≤ 10 s.

## Decision

- **The files are the database.** `core` keeps an in-memory model per workspace: per element the parsed frontmatter, version, file location and outgoing relations (also the targets of the inline references in its text: UUID, version, repository and line, `ElementRecord.references`, #240); an inverted relation index (incoming), indexes by type, status, package and validity. Text bodies are loaded lazily and kept in an LRU.
- **Search:** MiniSearch (in-memory full-text index, fuzzy and prefix search, case-insensitive) over title, text, property values and IDs (SR-068 AK1, AK2). Search within a view or filter intersects with the selection (SR-068 AK3).
  - Index (`query/search-index.ts`, #323): MiniSearch 7.2.0 (MIT, no dependencies, no network access; ADR-0015), one document per element record, keyed by repository and file (files may share a UUID, SR-088). Fields: `title` (the property with the meaning `title`, D-059), `text` (the Markdown below the frontmatter without the destinations of links and images: the reader sees the label, and the `logreq:` destinations of inline references would add four times the words of the texts at N-036) and `properties` (the values of every other key except `id`, `type`, `status` and the keys that hold relations, also inside lists and mappings, dates as ISO text, and for a choice also its name). IDs are not indexed (150,000 random tokens would cost about 110 MB and 1 s at N-036); a query word in the form of a short ID (`SR-46fb54`, also with 12 digits) is compared with the records (type prefix and the end of the UUID), and a word of at least 6 hex digits finds the UUIDs that begin or end with it; exactly, in any case, never fuzzy, and independent of how many digits the shown short ID has (SR-084). Words are split at every character that is not a letter, mark or digit and compared in NFC and lower case; fuzzy search tolerates one edit in a word of 4 to 7 letters, two from 8 (MiniSearch's fraction 0.2), none below 4; prefix search from 2 letters; a title match counts twice (BM25).
  - `searchElements(index, query, options)` (consumed by `element.search`, #80, and the `[[` link search, SR-066): `fields`, `within` (the records of the selection of an active view or filter, `Selected.elements`, SR-068 AK3, compared by repository and file, so of two files with one UUID only the selected one counts, SR-088; `total` counts only hits inside it), `combineWith` (`and` by default), `fuzzy`, `prefix`, `offset` and `limit`. The words without an ID form go to MiniSearch as one query; ID matches come first, then score, then store order. Only the page is described (fields and matched terms of each hit), for SR-098.
  - Built per store and metamodel (`searchIndexState`, `query/search-state.ts`): the store keeps no text, so the build reads every element file again (`readElementBodySync`), in the calling thread, in slices of 5 ms with a turn of the event loop between them (as the current versions). A file changed since the store read it is indexed as it is now when it still holds the same UUID, else without text, and such a build is not cached. A change of the metamodel or layout resets it. A build or carry stops (`SearchBuildCancelled`) when its workspace is closed or its value is no longer the state, so a reset or the exit of a process never waits for a whole build. One that no search waits for pauses while a command runs on the workspace (`Workspace.busy`, counted by `invoke`; asked at every turn, then every 10 ms), so a command waits for at most the slice that runs; `searchIndex(workspace)`, which a search calls, lets it go on (the state itself is not exported from the block, since a command that awaited it directly would pause its own build). A search whose build stops because the state was reset meanwhile (a watcher batch that changes the metamodel or layout) waits for the next build, up to 5 times, while the workspace is open. A server starts the build only after its warm-up and one more second (`warmSearchIndex`, `SEARCH_WARM_DELAY_MS`), so nothing of the index lies on the way to its first answer (SR-082 AK1); it counts as a server from the start of the warm-up, so a search during it (`logreq mcp` and the app do not wait for the warm-up) also builds without the cache.
  - Carried over a store change (`carrySearchIndex`, #184; SR-007 AK2): the documents of the changed files are removed and the files that hold an element now are read again and added. Unlike every other carried state, the MiniSearch object is changed in place, not copied (a copy costs about as much as a build): the documents are read first and the object is changed in one synchronous step, so a search sees it before or after the change; the index of the previous store shares the object and filters its hits to its own records. A change of more than `SEARCH_CARRY_LIMIT` (10,000) UUIDs builds the index again. The engine keeps every document it added (`SearchEngine.documents`), so a carry removes the old ones exactly (`MiniSearch.remove`) and the carried index equals a fresh build, scores included. MiniSearch's vacuum is never started (auto vacuum off): it walks the term tree in batches with pauses, and a document added or a search made in a pause (a search drops the words of discarded documents it meets) changes nodes the walk stands on, and MiniSearch 7.2.0 then throws in its timer (found by the SR-007 AK2 test and in review). An index loaded from the cache has no documents: its carries discard them, and searches drop their words as they meet them, which is safe without a vacuum; scores may differ a little from a fresh build until then.
  - Measured on the generated workspace (50,000 elements, 200,000 relations, quiet local runs; `test/perf/search-index.test.ts`): build about 7 s with no turn of the event loop blocked longer than about 35 ms; heap about 200 MB with the documents kept for carries (about 30 MB of them), about 355 MB for a synthetic index of 50,000 texts of 150 words with its documents (about 310 MB without); `element.get` while a server builds the index 8 to 35 ms (paused, against 220 to 265 ms before the build paused for commands); typical queries 20 to 240 ms, very common words, two-letter prefixes and whole titles as one query up to 400 to 500 ms (a risk for SR-098, #110); a carry of one saved file about 150 to 170 ms, of 1,000 files about 2.2 to 3 s with the store update (SR-007 AK2: 10 s).
- **Queries** (filters, chains, coverage) run on the in-memory indexes; no SQL engine. Chains and coverage are graph walks with cycle detection (SR-022 AK4).
  - Incoming relation index (`model/incoming.ts`, #258): `buildIncomingIndex(store, metamodel)` collects, in one pass over the store and each element's own frontmatter keys, every relation item with a text `id` under a key that holds relations (`relationKey`: relation kinds and properties of kind `relation`, so validity and packages too) and every inline reference, by the UUID it names. A relation link holds its source, key, position in the list (`relationPath` makes the path when it is reported), the item object as parsed and the repository it points into (the item's `repository`, else the source's own; an item whose `repository` is not text is left out). `incomingTo(index, repository, id)` gives the links into one repository and UUID: relations first, then references, whose repository is decided as `resolveReference` resolves them (#250), a reference that is `ambiguous` among other repositories counting for each of them. The index is raw: relations of an element to itself and to a UUID that several files share are kept. `incomingFor(workspace, store, metamodel)` keeps one index per store (`incomingState`, a `WeakMap`, built again for another metamodel), carried over a change of the store (below, #267). Each list (the links into one UUID) is in store order of the sources, then frontmatter key order and items, or text order; the order of the UUIDs in the maps is not defined (a carried index adds new ones last), so `derivationEdges` gives its edges in no defined order (the cycles of `cyclesOf` and their elements are in store order whatever the edge order). Three readers that scanned the store before the index existed read it when the workspace holds the index of their store (#272): the SR-086 carry (below), the hints that `element.setStatus` and `element.supersede` return for the relations to the elements they superseded (`supersededTargetProblems`, SR-072 AK2: the sources of the relations of relation kinds to their UUIDs, then the same rules as the scan on just those sources, about 7 ms instead of about 75 ms) and the successors of a superseded element in its view (`successionsFor`, SR-072 AK3: the `replacement` links into its repository and UUID, ordered as the succession index orders them, well under 1 ms instead of building the succession index of a new store, about 22 ms). They never build it: a build costs 0.3 to 0.5 s, more than each scan. A server (`logreq serve api`, `logreq serve mcp`, later the app) holds the index from its start (warm-up, below), so there they always read it; a one-shot CLI command where no chain has run scans as before, and so does a reader whose metamodel would let a key of a relation kind hold something the index leaves out (a property with the same key, which the loader refuses). Measured on the generated workspace (50,000 elements, 200,000 relations) in a shared, loaded container: old and new path alternately in one process, 15 rounds, medians; without the index both paths are the same code.
  - Trace walk (`trace/`, #258): breadth first from one element or a set over a function that gives the steps of an element (`walk`); each element once at its shortest depth with the edge it was first reached through (`via`, `pathTo`; a start stays at depth 0 also when another start leads to it), every step an edge (also into an element reached before), `maxDepth` (elements at that depth are reached, not expanded: `expanded` on each node), unresolved targets and `incomplete`, and leaves for the evidence of stage 4. Cycles are the strongly connected components of the walked subgraph with more than one element or an edge to itself, not back edges on the breadth-first tree path, which miss cycles entered through a diamond: first the vertices without an edge in are peeled off (Kahn; in a chain most of them), then Tarjan's algorithm (iterative) runs on the rest. A cycle that closes only beyond `maxDepth` is not seen. `cyclesOf(elements, edges)` gives the cycles of any graph, `derivationEdges(graph)` every derivation edge of the store with an available parent, from the index without a `targetState` each (SR-090); `derivationCycleProblemsState` (`trace/cycles.ts`, #102) reports them in `workspace.check`, without a carry hook. The derivation graph (`derivationGraph`) takes its relation kinds from the meaning `derivation` (SR-013); parents are the element's own items looked up with `targetState`, children the index's derivation relations into the element's repository and UUID, unresolved as `ambiguous` while several files there share the UUID (SR-088). Measured on the generated workspace (50,000 elements, 200,000 relations; a cloud container with 4 cores, noisy): building the index 0.3 to 0.5 s once per store, the chain from the first need (about 42,000 elements, 112,000 edges) 0.25 to 0.38 s, of which the cycle search 8 to 25 ms, an upward chain a few ms, the cycles of the whole store about 0.3 s.
  - Warm-up of the incoming index (#227): a server builds the incoming relation index right after the load (`warmWorkspace`, before `logreq serve api` listens; in the background for `logreq serve mcp`), so the first chain after a start does not pay for the build (0.25 to 0.45 s at N-036; SR-082 AK4). This adds the build to the start that SR-082 AK1 measures (3 s with the cache; about 1.3 s on CI before). Building it in the background after the API listens was considered and not chosen: the build is synchronous and blocks the event loop for the same time right after listening, so the first `workspace.status` would answer that much later anyway. A larger change (a pull, more than `CARRY_LIMIT` UUIDs) still leaves the next store without an index until the next chain builds it. `trace.chain` pages its output (`limit`, `offset`, `total`, spec-frage #290): the walks stay complete, only one page of nodes and their edges, gaps and unresolved relations is built, since the whole chain of the largest need (about 42,000 nodes, 36 MB of JSON) takes about 0.2 s to serialise alone.
  - Filter and selection (`query/`, #81, SR-069, SR-101): a condition (`filter.schema.json#/$defs/condition`) is compiled once into a predicate on element records (`compileWhere`): references (`resolveRef`, any case), views (`resolveView`), type sets with their subtypes, choice names (`findNamed`), regular expressions and meanings are resolved while compiling, and errors name the input field (`selection.where.all[1].op`). The selection (`resolveSelection`) is the conjunction of `ids`, `where`, `package` and `view` (validity only until stage 5) in store order, one pass over the store; `incomplete` while a listed repository is not here. Semantics: property conditions work on the values of a key (absent, `null` and `[]` are none, a list gives its items); `eq`, `ne` (not `eq`), `in` compare with `===`, `contains` is a text part ignoring case, `lt` to `ge` compare numbers with numbers and texts with texts (ISO dates as text), `matches` is a JavaScript regular expression with flag `u`; a choice may be given by its display name; a key that holds relations takes element references (`eq`, `ne`, `in`, `exists`, `missing`). Relation conditions take `kind` (a relation kind or a relation property), `meaning` or neither (every relation kind); `up` reads the element's items (`to` through `targetState`), `down` the incoming index (built only when a condition needs it), no direction either; `evidence` asks the evidence provider (`evidenceStatusState`), which also gives the verification status per view and the validation status; stage 3 has no records, so its default gives `open` to requirements and needs and no evidence, and stage 4 replaces it (#127, option 1). Relation conditions with `exists`: without `to`, every item that names a target counts, also one whose target is missing or not available (the relation is there; the check reports the target, SR-089); with `to`, only an available other end that meets it, so `up` with `to: {all: []}` counts the available targets only (#336). `text` (#80), `emergent` (SR-035) and baselines are refused with `input.invalid` until they come; a schema operator without a branch in `compileLeaf` does not compile (`never` check). A compiled condition is for one run: it holds the states it was compiled against (store, short IDs, incoming index, evidence provider, views) and its `notes` only gain `incomplete`, so a saved filter or a bulk update (#83) compiles its condition again per run and never keeps a compiled one. A saved filter (`selection.filter`, SR-070) is read from its file on every call (a handful of small files) and joins the selection with its `where` and `view`; `element.list` without `sort` takes its sort. Measured by name through the catalog on the generated workspace (system requirements in draft, sorted by title, first page; `[SR-082/AK4]` in `test/perf/open-filter-chain.test.ts`, #228): about 185 ms in a local run (4 cores), the file read and the compile included. The short semantics of each operator are also in the descriptions of `filter.schema.json`, because agents read them there (in the MCP tool schemas); the selection part of an MCP tool has its own size bound for them (ADR-0009, #336). Measured with `element.list` on the generated workspace (50,000 elements, 200,000 relations, the index warmed): every element 25 ms, a type 35 to 40 ms, requirements without child 60 ms, with a parent of type need (a `targetState` per item) 160 to 200 ms, a regular expression on titles about 50 ms (first page of 200 built each time).
- **Cache** per path of a working copy in the OS cache folder (`<cache>/logreq/<sha256 of the canonical workspace path>/`; canonical: absolute, symbolic links resolved with `realpath`, and lower case on Windows, so two names of one folder share a cache), never in the repository; copies at different paths never share a cache folder (SR-081 AK2, "je Kopie" read as "je Pfad der Kopie"). On macOS `realpath` also gives the name as stored, so another case or Unicode normal form of the name (APFS ignores both by default) leads to the same folder; on Linux these are other folders. Because the cache belongs to the path, a copy moved elsewhere gets a new cache folder, and a new copy at the old path (a fresh clone) inherits whatever the old copy left there. Such leftovers are harmless only because every entry is checked against the files before it is used: a stale `api.json` is replaced (ADR-0009), and the model cache (SR-082) checks each file entry against its file and must check the serialised search index as a whole (for example against the set of file entries it was built from), never trust it per file. An old copy's API that still runs makes a `logreq serve api` of the new clone at its old path refuse until it stops (ADR-0009). Cache folders of moved or deleted copies are not collected (stage 1). The model cache (`model.json`, `model/model-cache.ts`, SR-082) holds, per repository (name and canonical folder), what each file that parsed contributed to the store (frontmatter, classification, warnings) with its snapshot (size, mtime, content hash), plus the inode and change time of the file when the cache was written (as Git's index does: a file rewritten with the same size and mtime, by `cp -p` or a restore, gets another change time or inode; from `lstat` with `bigint`, as decimal strings, so a 64-bit file ID on Windows, often above 2 ** 53 where a JS number loses its low bits, stays exact: the inode unsigned, since Node gives one of 2 ** 63 or more as a negative bigint, and the change time in nanoseconds, a file changed before 1970 left out; the mtime is compared as `mtimeNs` turned into ms the way Node computes `mtimeMs`, so the snapshot keeps the number form; format 3, #232). Versions are not part of the store and are not cached (#259: the current versions are computed on first use instead, below). Should they ever be cached, this rule applies: A cached version is valid only while the element file and every image it embeds (ADR-0005 "Files") still have the size and mtime it was computed with, and every missing image is still missing; the entry therefore records them too. Presence is checked with the lookup of ADR-0005 (name by name, spelled as on disk), not with a plain `stat`: a rename to another case, a new `.git` entry in a folder above an image or a twin name in the other normal form changes what counts. A change of the `ignore` globs of the workspace file invalidates every cached version. The cached entry would also have to name the definitions of the properties that counted, since the metamodel decides which do. The cold load reads files in worker threads (below); computing versions there needs a synchronous variant of the image lookup (`embeddedImages` is asynchronous). Its header names the format, a fingerprint of core's code and the canonical root. The fingerprint is a SHA-256 over the product version, the exact dependency versions of core (YAML parser, schema validator) and core's code files; core's build writes it to `dist/code-fingerprint.json` with the hash of `dist/.tsbuildinfo`, so a packaged or bundled build (ADR-0014) never walks its own files, and a `tsc -b` after the build (newer build information) or a run from the sources computes it from the files. Start: list all files, `lstat` each one with an entry (blocking calls: 0.2 s for 50,000 files, through the libuv thread pool 1.5 s), reuse the entry when size, mtime, inode and change time match and the mtime lies more than 2 s before the start of the load that wrote the cache (a file changed again within the resolution of its time stamp keeps size and time: such "racy" entries are read again), read the rest as on a cold start (worker pool from 1,000 files). The racy rule compares file times with the clock of the machine; on a network share whose clock runs ahead, files look racy and are read again (slower, never wrong); one whose clock runs behind by more than 2 s can let a change within the same second go unseen, as for Git. Inode and change time are taken when the cache is written, so a file whose change time lies less than 2 s before the start of the load is not written to the cache at all: a change between the read and the write that keeps size and mtime (`cp -p`) would otherwise go unseen. A cache that is not JSON, has another format, code or root, or an entry of the wrong shape (every field of every kind of entry is checked) is discarded whole; entries of a repository count only while its name and canonical folder match the layout. Only values JSON gives back exactly are cached: plain objects, arrays, strings, booleans, `null` and finite numbers other than `-0`; an entry with anything else (`!!timestamp`, `!!binary`, `!!set`, `!!omap`, `.inf`, `.nan`, `-0`, an alias that contains itself) is left out and its file read on every start. Markdown files without frontmatter and faulty files have no snapshot and are read on every start too. The cache is written again in the background (atomic private write through the files block; one save after the other per workspace; closing the workspace waits; a failed write is ignored) after a load with 1,000 or more out-of-date files or at least 1 % of them (an entry gone, or a file read that the cache can hold: new, changed, racy); fewer are read again at the next start instead, since writing the cache costs about 1.4 s at 50,000 files (75 MB). Changes the watcher or LogReq's own writes apply are not written to the cache; the next start reads those files again. A cache folder inside a repository folder of the layout is never used; a cache folder that does not exist yet is named by its nearest existing parent folder (`realpath`) and the rest of its path, so one that lies inside a repository through a symbolic link is recognised on the first run too. The cache is opt-in per `Workspace` (`new Workspace(root, { cacheFolder })`): the CLI passes `cacheFolder(root)` for every command and server, tests leave it out. A server loads the workspace before it serves (`warmWorkspace`: `warmModel` loads metamodel, store, short IDs and the incoming relation index; the search index is built in the background, below), after its watcher is ready, so no change during the load is missed (SR-007): `logreq serve api` first refuses a port that is not one and an API for the copy that runs or starts (`checkPort`, `refuseRunningApi`, ADR-0009), prints "Loading the workspace..." to stderr and listens only once the workspace is loaded; stopped meanwhile (Ctrl-C), it never listens, and it exits once the running load has finished, since a load is not aborted, so its first answer means "usable" (SR-082 AK1, AK2); `logreq mcp` starts the load without waiting, so a cold load does not hold up the protocol handshake. The search index (`search.json`, `query/search-cache.ts`, #323) is stored with a header (format, fingerprint of core's code, canonical root and a SHA-256 digest over the repository, path and content hash of every element record in store order and the part of the metamodel that decides the documents: title key, relation keys, choice names) and used only when the store loaded from the files has the same digest and the index holds exactly one document per record, never per file. Only a one-shot process uses it: a command that needs the index loads it (about 1.4 s at N-036, of which about 1 s blocks the thread, since MiniSearch rebuilds its maps in one call; its asynchronous loader took about 7 s) and writes it after an exact build (about 1.4 s for 27 MB, through the save queue of the model cache, skipped once the index was carried). A server neither reads nor writes it: `warmWorkspace` starts the build in the background a second after the model is loaded (`warmSearchIndex`), in slices that pause while a command runs, so the server answers meanwhile as without it and a search waits for it; blocking for a second right after listening would delay the answers SR-082 AK1 and AK3 measure, and a server keeps the index current by carrying it. Measured on the generated workspace (4 cores): a start of `logreq serve api` until `workspace.status` answers takes about 1.8 s with the cache and about 12 s without it (a cloud container, files in the page cache of the OS). The search index does not change it (#323): it starts a second after the warm-up; on one generated workspace, five starts with the cache alternating between this change and the code before it took 2.92 s and 2.81 s on average at a load average of 12 to 15, a difference within the spread of single starts (±0.3 s), of which loading the MiniSearch module is about 8 ms. The OS cache folder is `%LOCALAPPDATA%` on Windows, `~/Library/Caches` on macOS and `$XDG_CACHE_HOME` or `~/.cache` elsewhere (`cacheFolder(root)` in core's workspace block); the folder of a copy also holds `api.json` of its local API (ADR-0009).
- **Cold start:** files are parsed by a pool of worker threads (`node:worker_threads`, one per core minus one, at least one; `model/read-pool.ts`, #148). `loadElements` walks every repository first; when the files of all repositories together are 1,000 or more, they go in one queue, in chunks of 250, to one pool, else they are read in the calling thread as before. A watcher batch (`updateElements`) counts per repository: a repository with 1,000 or more files to read again (a checkout, a pull) gets a pool, which also keeps that parsing off the thread that serves the API, MCP or app. The threshold is the measured break-even: in a fresh process on 4 cores (3 workers) both ways take about 1.0 s for 1,000 files (starting the workers, which load the YAML parser and compile the schemas, costs about 0.5 s); from 2,000 files the pool is ahead (4,000 files: 2.3 s against 3.2 s; 50,000: about 10 s against 41-43 s, of which about 17 s are YAML parsing and about 10 s file calls). Each worker (`model/read-worker.ts`, started with `workerData` marking it, so the module serves nothing in any other thread) reads, parses and classifies its files with blocking calls (`readElementFileSync`, `contributionSync`: the same checks and results as `readElementFile`; calls through the libuv thread pool cost more than they save there) and sends back the contributions as plain data, tagged with the id of the job, so calls on one pool may overlap; the calling thread freezes the snapshots again (a structured clone drops `Object.freeze`) and assembles the store. An abort is checked before the workers start and before each chunk; the workers are stopped with `terminate` when the read ends, also on an abort or a failure; a worker that fails or stops rejects the read. Tests run the TypeScript sources in the workers: `scripts/test-support/worker-preload.mjs` (passed with `--experimental-strip-types --import <URL>` in `execArgv` of the Vitest configs) maps the `.js` specifiers to the `.ts` files and blocks the network in the workers too; coverage of the worker code comes from in-thread tests of the same functions, and a CLI e2e test runs the pool from `dist`.
- **Current versions** (#259; `model/current-versions.ts`): the current version of every element (ADR-0005: from its file and the images its text embeds), which SR-025 compares the stored versions of relations and inline references with (later also SR-026, SR-092, SR-031). A workspace state (`currentVersionsState`, read through `currentVersions(workspace)`), built on first use, once per element store, in the calling thread: each element file is read again with blocking calls (`readElementBodySync`, with the same checks as the full read; while the bytes still have the SHA-256 of the store's snapshot only the frontmatter split runs, no YAML parse), the images are looked up only for a text that embeds one (one `ImageMemo` per run), in slices of at most 20 ms (and 500 files) with a turn of the event loop between them, so a server keeps answering (SR-082, N-036). A file changed since the store read it counts as it is now, as for `currentTarget`; its entry also holds the element as the file holds it now (`element`, optional), so a list shows data and version that agree (SR-023). An element gets no version (`unknown` with its reason) and nothing fails when its file no longer holds it (`not-in-file`), an image cannot be read (`image-unreadable`) or a value that counts has no normal form (`not-computable`: `.inf`, `.nan`, ADR-0005); every other error is a bug and is passed on. Measured at N-036 (50,000 elements, 200,000 relations, files in the page cache): 4 to 5 s in local runs of the performance suite (4 cores, 16 GB: 3.9 s with the whole suite, 5.0 s with the core suite alone); about half of it is reading the files again (of that, `lstat` and the link checks about a third), most of the rest computing the versions. The same with `fs.promises` reads (the libuv thread pool) took about 11 s. A pool of worker threads would save about 1.5 s on 4 cores and nothing on 2, for a second worker protocol and the synchronous image lookup; rejected for now. Not cached (above): the cached start (SR-082) needs no version, and a check pays the build once against the 60 s of SR-020. The state depends on the store and on the metamodel (which properties count): a change of the metamodel, or of the layout with its `ignore` globs, resets it. A change of the store through `applyStoreChange` (watcher batches, `recordWrites` of every writing command) is carried (`carryStoreUpdate`): each record that is another object in the new store gets its version again, every other entry is kept (a few ms at N-036 after a save).
  - Images are no Markdown files and the watcher drops their events (below); a version kept across its batches is therefore checked on use, not reported by the watcher. Each version keeps what the lookup of each image found (`ImageSeen`: size and mtime of the file, missing, or in a nested repository), and `currentVersions` checks a kept state before it returns it (`checkImages`, `imagesUnchanged`): the lookup of ADR-0005 again, name by name with a fresh memo, so a rename to another case, a new `.git` entry above an image or a twin name in the other normal form counts, and an `lstat` of each file found, nothing hashed; the elements with images are checked 32 at a time. The entries of elements whose images changed, and every entry without a version (its file or images may be readable again), are computed again; when one comes out different, the state is replaced (compare and set), which resets the states built on it, else it is kept. A state built by the same call is not checked again, and callers that come while a check runs share it. The check costs one listing per folder on an image path and one `lstat` per image, nothing for elements without images: a later use at N-036, where the generated workspace embeds no image, takes well under 0.1 s; a workspace where many elements embed images pays about one `lstat` per image on each use (not measured yet). Reporting image files from the watcher was rejected: it would pass every event of a file that is not Markdown (build output inside a repository) to the store's queue, need an index from image paths in every spelling to the elements that embed them, and still miss a new `.git` entry above an image, whose events the watcher drops.
  - Sort and derivation tree (`query/sort.ts`, #87, SR-075, D-031): `element.list` sorts the whole selection by its `sort` keys, then builds the page; nothing about the order is ever written (AK3). Keys apply in order, ties go to the next key and then to the store order. `id` is the short ID, `type` and `status` follow the metamodel order of the types and statuses, `title` is the property with the meaning `title` (`metamodel.meaning-unassigned` without it), any other key sorts by its first value (choices of a `choice` property in metamodel order, then numbers, texts ignoring case by code units after NFC and lower case, booleans); no value (absent, `null`, `[]`, a mapping, NaN) is last in both orders, `desc` reverses the rest; a key that holds relations is `input.invalid`. `hierarchy` may only be the first key and only ascending; the keys after it order the roots and the elements below each parent. The tree holds each element of the selection once (spec-frage #354, option 1): parents are its own derivation items whose target is available and in the selection, as the chain goes up; breadth first from the elements without such a parent, each element hangs below the parent that reaches it first (shortest depth, then sort order); the cycles that no root reaches and nothing else left over leads into (`cyclesOf`) become roots at their first element in sort order, and the rest hangs below them; the list is the tree depth first, and the output's `tree` gives depth and parent for each element of the page. The parents of every element of a store are read once per store as store positions (`parentPositions`, `trace/graph.ts`, in a `WeakMap` by store, with the metamodel they were read with; a change of the files makes a new store, so nothing is carried), without the incoming index, so a one-shot CLI call does not build it; a tree call then walks the store and the selection side by side and links the elements by array positions. Looking up the 128,000 parents of N-036 as records on every call cost several times as much (0.4 to 0.75 s against 0.08 to 0.16 s for the tree in a loaded container). Measured with `element.list` on the generated workspace (50,000 elements, 200,000 relations, a loaded container with 4 cores at load 7 to 12; `test/perf/element-list-sort.test.ts`): sorted by title 0.11 to 0.25 s, as a tree 0.08 to 0.16 s, as a tree with siblings by title 0.17 to 0.27 s, the first tree of a store (reading its parents) 0.33 to 0.39 s, first page of 200 each.
  - Lists (`trace.related`, SR-023; later `element.list` and the data export): `currentVersionsOf(workspace, records)` gives the versions of one page only. With a kept state it takes that state's entries of the page and checks only their images (`stale`, as `checkImages` does for the store), computing the stale ones again without changing the state; without one it reads only the page's files and builds no state, unless the page is at least a quarter of the store, which builds and keeps it (`currentVersions`). An element without a version is listed without `version` and with one `file.faulty` warning in its `problems` (`listElements`); it never fails the list.
  - Single-element paths (`element.get`, the element hints of SR-026) never wait for the whole build: they use the state only when its build has ended (`currentVersionsIfBuilt`, `settledValue`: never waiting for a running build) and otherwise read the versions of the targets they need from their files (`currentVersionsOf`; SR-026, #38: `element.get` shows the element's outdated relations and evidence this way). `currentVersionsOf` looks up only the records it is given in the kept state (one map lookup each, not a walk over its 50,000 entries) and checks only their images; a list or view of K elements costs O(K) when the state is built, and K file reads when it is not, unless K is a quarter of the store, which builds the state. A page of at least a quarter of the store that is asked for while a build is running goes through `currentVersions` and so waits for that build and its `checkImages` over the whole store. The cycle hint of one element (SR-026 AK3) likewise comes from the kept cycle state when it is built, and otherwise from a walk up from the element through its own relations (`elementCycleFindings`, as `upwardGraph` for SR-067): it never builds the incoming index (0.3 to 0.5 s) or the cycles of the store. Starting the build in the background right after a server has loaded (`warmWorkspace`) was considered and left to SR-025 (#37) and SR-026 (#38), and is not done by either (open): the build runs in this thread, so until it ends every open of an element waits up to one slice per await, which the tagged SR-082 AK3 tests (open within 200 ms after the load) would have to show is acceptable.
- **Outdated relations** (SR-025, #37; `hints/outdated.ts`): a workspace state over the current versions (above) and the incoming index: one pass over the relation items and inline references of the store in slices of 20 ms (SR-082), a map lookup per target. Lines of items come from a scan of the frontmatter text (`model/item-lines.ts`: LogReq writes one flow mapping per relation item under a top-level key), read again only for sources with a finding and only while the file still has the SHA-256 of the store's snapshot (a changed file gives no line); the YAML is parsed only for another layout. Parsing the YAML of every source again cost about 28 s in the worst case below; the scan brought the findings with lines to 9.3 s. Carried over a store change (`carryStoreUpdate`): the changed files and the sources of relations and links to a changed UUID (from the incoming index of the store before the change, which the state depends on so that it is carried first) are looked at again, the rest is kept; a new or deleted element or a missing index builds it again. The dates of the versions (D-013, ADR-0005) are not kept: `datedProblems` asks `versionDates` on every check. Worst case at N-036 (every relation and link outdated, 300,009 findings, local runs on a shared 4-core container): the CLI check without Git 36.6 s (SR-020 AK1: 60 s, asserted); with Git the dates add about 32 s (one walk per target file, every element a target), which puts a CLI check above 60 s. Capping the dates (at 10,000 targets) is spec question #287; the usual case (500 changed targets) takes 8.7 s in process with dates.
- **File watching** (SR-007; `model/watch.ts`, `model/watch-tree.ts`): no dependency (`chokidar` was planned) and no process; the watcher writes nothing. It runs only where a workspace stays open: `watchWorkspace(workspace)` is a workspace state that the CLI starts for `logreq serve api` and `logreq mcp` (later the app), and closing the workspace stops it; a one-shot CLI command reads a fresh workspace and needs none.
  - macOS and Windows: `node:fs` `watch` with `recursive: true` on every available repository folder (FSEvents, ReadDirectoryChangesW; a repository nested in another is seen through the outer one).
  - Linux: one plain `fs.watch` per folder (`FolderTree`), not `recursive`. Node emulates `recursive` on Linux with one inotify watch per file and folder; a file replaced by a rename (an atomic save by vim, JetBrains IDEs or LogReq's own `writeFileAtomic`, a delete and re-create, a checkout) is then never reported again, and at 50,000 files the watch costs about 0.6 s of blocked event loop, about 100 MB and 50,000 inotify watches. A folder's watch reports every name in it however the file was written, so one watch per folder is enough: about one inotify watch per folder. Left out are `.git`, `node_modules`, folders of the `ignore` globs (unless the metamodel lies in them), folders of other repositories of the workspace (they have their own tree) and folders with a `.git` entry; a new folder named by an event is watched with its subfolders, and the watches of a folder that is gone are dropped. A folder that vanishes during the walk is skipped; a broken folder watch is dropped and its folder checked and watched again, without reading the layout again. A watch belongs to one folder: each watch keeps the `dev:ino` of its folder from a stat right after it attached, and a walk that finds the path gone, no longer a folder or with another inode drops the watch and watches it anew (a folder deleted and created again, replaced by a move, or emptied and filled by a checkout). Linux names the watched folder itself when it is deleted or moved away (`IN_DELETE_SELF`, `IN_MOVE_SELF`); a new folder in its place can get the same inode, so such an event drops the watch at once and walks the folder again. A repository folder that is gone reads the layout again, as a broken recursive watch does on macOS and Windows; the repository is then not available, and a clone in its place is seen after the next layout change or restart. All walks of a tree run one after the other; a folder that got a new watch is reported once more, for files created before the watch attached. A start that a newer layout overtook stops after its next step and its watches are closed; events of a layout that is no longer watched are dropped. Own code instead of chokidar v4 (ADR-0015): the per-folder tree is about 240 lines, chokidar would add a dependency and its own Linux emulation with the same replaced-file questions.
  - A folder that cannot be watched (`ENOSPC`: the inotify limit, raise `fs.inotify.max_user_watches`; or a refusal) is reported as a `workspace.not-watched` warning in `workspace.status` (`watcherProblems`); its changes are not seen until LogReq restarts or the layout changes. Commands still work. Only a process with a watcher (API, MCP server, app) reports it; a one-shot CLI command has no watcher and reads the files anew.
  - Events under `.git` and `node_modules` and LogReq's temporary files are dropped; so are other files than `*.md` unless the path is a folder or gone (images too: the current versions check them on use, above). Events are debounced (100 ms after the last, at most 1 s after the first) and processed in batches, one after the other, so a pull with 1,000 changed files is one or a few updates.
  - The workspace file or `.logreq/local.yaml` changed: the old watches are closed, the layout is reset (and with it everything built on it) and the new repositories are watched; events sorted with an older layout are dropped. A path in the metamodel folder: the metamodel and the state built on it are reset, without rewriting any element (SR-015). The layout gives an existing metamodel folder as its real path (the name as stored, as for the repositories); events are compared with it in NFC and lower case, so a spelling other than `realpath`'s still counts (a twin folder on Linux costs an extra reset). An event at the folder or a folder above it (renamed, moved, deleted, created), or in a missing folder, reads the layout once and compares it, so its real path and existence stay current (#231). A metamodel folder reached through a link out of its repository, or missing below a linked folder, is not watched. A broken recursive watch (macOS, Windows) reads the layout again and watches anew. An event without a file name (the OS dropped the names of a burst: ReadDirectoryChangesW overflows its small buffer, 4 KB in libuv, on a pull of a few hundred files, about 20 times for 1,000 files on windows-2025, and libuv then reports one change without a name; #226) checks every repository below the watched folder file by file, reads the metamodel again when its folder lies there, and, when the main repository lies there, reads the layout once and compares it with the watched one, so a workspace file changed by the same pull is not missed (and a repository that appeared or disappeared is noticed with it).
  - Element paths: the store is updated, not read again (`updateElements`). Per repository with changes, the Markdown files are listed again (one walk, no reads; it applies the ignore globs, nested repositories and links like the full read), files that are gone are dropped (also one deleted between the walk and its read), new files are read, files named by an event are read again, files below a changed folder (or all, when the OS gives no file name) are read again when size or mtime differ. A file read again with the same snapshot (SHA-256, size, mtime) keeps its record; the result equals a full read. The change goes through `applyStoreChange(workspace, change)`: one queue per workspace, `Workspace.replace` (compare and set) to install the new store, and a retry on the newer store when the store was replaced meanwhile. Replacing carries the states built on the store over the change or resets them (below); with nothing changed the old store and those states are kept. A store nobody has read yet is left alone. A failed update resets the store, so the next command reads it in full. A repository that is missing at start is watched only after the layout changes.
  - LogReq's own writes (`element.create`, `element.update` and later writing commands, #166) update the store the same way, without reading any file: `recordWrites(workspace, layout, files)` takes every file a command wrote, `withWrittenFiles` builds each file's record from the bytes just written and the snapshot of the write, swaps them in (new files in path order), assembles the store once and installs it through `applyStoreChange`, so a save waits behind a watcher batch that is running. The states built on the store are carried over or reset as for the watcher (below). When the watcher then sees a file, it reads it again and finds the same snapshot, so nothing is applied twice; a write the watcher saw first changes nothing. Whenever the result could differ from a full read (`StoreFallback`: the store holds a file in another state than the one replaced, a new file that the walk would not list under its repository, a repository with folders that cannot be listed, or a layout read again since the write), the store is reset instead; any other error is passed on.
  - The watcher tells who listens what a batch changed (#331; `WorkspaceWatcher.onChange`, `model/watch-change.ts`), so the app shows external changes (SR-007) and can show live which elements changed outside it (the requirement for that is still to be exported from the spec graph, #326): once per batch that changed the model, after the change is in place (the store installed through `applyStoreChange`, or the states reset and the new repositories watched), on the chain of batches, so calls come in order and a listener that reads the workspace sees the new model. A `WorkspaceChange` is plain frozen data that the app's core process posts to its windows as it is: `scope` `elements` (the store was updated), `metamodel` (the metamodel is read again on its next use, so every element may show differently) or `workspace` (the layout is read again, the store was read in full, `readsInFull`, or it was reset after a failed update: everything is read again), and `elements`, the UUIDs whose record came (`added`), went (`removed`: a deleted file, one that is no longer an element, a changed UUID; SR-007 AK3) or is another record (`changed`: content, a move, a copy), each sorted; empty for `workspace`, and for a batch that changed only files that are no elements (the findings may differ). The UUIDs are those of the records that are other objects (`storeUpdate`), each looked up in `byId` before and after, which is one pass over the files of each changed repository, as for the carry of the states built on the store, plus one lookup per changed record (an estimate: a few ms at N-036, not measured yet); a pull is one or a few calls, as it is one or a few batches (SR-007 AK2). A file read while it is being written (a pull still running when the 1 s of a batch are up) can count as no element in one batch, its UUID `removed`, and be `added` again in a later one: a consumer must not drop or close an element for a single `removed`; the last list a UUID appears in, or the workspace as it reads, counts. A batch that replaced nothing (`.git`, other files, the same snapshot, a store nobody read) calls nobody, nor does a closed watcher (`close` drops the listeners, so a listener that closes it stops the ones after it). The watcher does not wait for a listener; one that throws or whose Promise rejects stops neither the others nor the watcher. LogReq's own writes (`recordWrites`) are not reported: the command that wrote knows it (the app sends `written` to its windows itself), and the watcher then finds the same snapshot; writes of another process (the API server in Electron's main process, a CLI command) reach the watcher as file changes and are reported. It is no catalog command (ADR-0002): the catalog holds functions a caller asks for with an input and gets an output from, on every access; this is a push from a process that keeps a workspace open. A one-shot CLI command has no watcher, the API and the MCP server answer requests and their clients ask again (each command reads the current model), and the event carries nothing a command does not return (UUIDs), so every access still gives the same result (D-029, SR-080). Should an API or MCP client ever need to be told, a server-sent event of the API or an MCP notification would forward this event, not a new function.
  - States built on the store are carried over a change instead of being built again (#184): `Workspace.replace` is still compare and set; after it installed the new store it gives every dependent with a `carry` hook, dependencies first, its next value, provided every dependency of it that depends on the store was carried too, and resets every other dependent. `applyStoreChange` knows what changed: a `StoreUpdate` names the files whose record is another object in the new store and the UUIDs of those records (`updateElements` and `withWrittenFiles` keep every other record the same object), and `carryStoreUpdate` hands it to the hooks; a store replaced any other way, or one without `repositories`, resets the dependents. The short IDs build again only the groups (last 6 digits) of the changed UUIDs (`updateShortIds`); the findings of SR-015, SR-016 and SR-085 find and locate the changed files only and keep the located problems of every other file, merged in store order without a walk over all elements (`carryProblems`); SR-088 looks again at the files of the changed UUIDs; SR-086, when a changed UUID came, went, or changed the repository or type of a record, also at every element whose own UUID or a target under a key with a rule lies in the short-ID group of a changed UUID (its target or a short ID in its message may have changed): with the incoming relation index of the store before the change in the memo (#272; it holds every relation of an unchanged file as it is now), the records whose UUID lies in such a group and the sources of the relations under a key with a rule to a UUID that does, found by a scan of the index's keys and the store's UUIDs (a short ID depends on every UUID of its group, also one no element has, so this part stays a scan, of about 100,000 strings), and merged as a list without a walk over all elements, about 22 ms with the findings; without the index a scan of the frontmatter in memory and a walk over all elements (about 40 ms for 200,000 relations in quiet runs, about 110 ms in the same loaded runs), and otherwise (the usual save of a title, text or property) at the written files only. Missing targets (SR-089, which also depend on unreadable files; a carry hook added later must also look again at every source whose relations or inline references point at a UUID of a changed file), superseded targets (SR-072, successors across elements) and superseded validity (SR-040) are reset as before; only `workspace.check` reads them. The succession index of the element view (SR-072 AK3, `successors.ts`) is kept per store and not carried: the first view of a superseded element after a change of the store builds it again (about 23 ms at 50,000 elements and 200,000 relations), then each such view is a lookup; while the workspace holds the incoming relation index of the store (carried over the change), the view reads that instead and builds nothing (#272). The incoming relation index is carried (#267; `carryIncomingIndex`): when the store that is replaced has an index in the memo, the hook adds the index of the new store, built from the old one: the links whose source lies in a changed file are dropped, the links of the records in those files now (the records of the update's UUIDs that lie there, before and after) are merged into each list of a UUID they name, in store order (repository order of the workspace file, then file path), every other list and link object is kept; a store without an index gets none. A server holds the index from its start (warm-up, above), so in `logreq serve api` and `logreq serve mcp` every save pays the carry (about 30 to 50 ms at N-036); a one-shot CLI command pays nothing extra until a chain has run. At N-036 the carry costs a fixed 30 to 50 ms (copying the two maps of up to 50,000 UUIDs) plus about 0.1 ms per changed record (0.13 to 0.25 s for 1,000), against 0.3 to 0.5 s for a build. It runs inside `Workspace.replace`, in the thread that serves commands, so it is done only while the update names at most `CARRY_LIMIT` (1,000, the read pool's threshold for a watcher batch) UUIDs; after a larger change (a pull, a checkout: 5,000 records cost about as much as a build, all 50,000 about 1 s) the new store gets no index and the next chain builds it (#273). A chain right after a save (trace context and walk) took 0.11 to 0.17 s in local runs, after the first chain of the process (0.30 to 0.41 s, before the walk is optimised by the engine) (SR-082 AK4, `test/perf/open-filter-chain.test.ts`). Building it in the background after a store change instead was rejected: it would block the thread of a server for the whole build after every save. A carried value is derived from the old one, which is not disposed and not changed, so a command that still holds the old one keeps a consistent view. Each carried state equals what a fresh build gives (tests compare them after saves, creates, status changes and watcher batches). Measured on the generated workspace (50,000 elements, 200,000 relations), with every finding state built before (an API server after `workspace.check`): a save of a title takes about 90 ms (about 80 ms when the states are reset instead), opening an element right after it about 4 ms instead of about 100 ms (the short IDs built again), and the next `workspace.check` about 0.9 s instead of about 1.5 s.
  - The store and the states built on it may be swapped while a command runs. A command that needs one consistent view reads the store once and derives what it needs from that object (`buildShortIds(store.byId, metamodel)`, `duplicateIdFindings(store)`) rather than reading several states one after the other.
- **Performance tests** (ADR-0011) with generated workspaces of 50,000 elements run nightly and on PRs labelled `perf`, against the thresholds above.

## Consequences

- Memory: roughly 1–2 KB per element without text, so well under 500 MB at 50,000 elements; the current versions add one small entry per element (the version and what the lookup of each embedded image found, and for a file changed since the store read it the element it holds now until the store is updated).
- Memory of the search index: about 200 MB at N-036 for the generated workspace and about 355 MB for texts of 150 words, each with the indexed text of every document, which the engine keeps so that a carry can remove it exactly (about 30 and 45 MB of it); held by a server from about a second after its start; a one-shot command builds or loads it only when it searches. Disk: `search.json` takes about 27 MB per copy and holds the words of every title, text and property, so the privacy note on the model cache applies to the texts too.
- Several instances on separate copies never share state (SR-081 AK1).
- Disk: the model cache takes about 75 MB per copy at 50,000 elements, in the OS cache folder of the user. Folders of moved or deleted copies are not collected in stage 1; removing `<cache>/logreq/` is always safe.
- Privacy: the model cache holds a copy of every element's frontmatter (titles, properties, relations; not the text, only the UUID, version, repository and line of each inline reference in it) in the user's cache folder, readable only by that user (mode 0600, folder 0700). Backups or roaming profiles that include the cache folder take that copy along.
- The watcher and file listings ignore LogReq's own temporary files `.<file name>.<8 hex>.logreq-tmp` (`isTempFile` in `files`, ADR-0007). Parsed files carry plain, frozen snapshots (path, size, mtime, SHA-256), so they can be cached and sent to worker threads; the kept YAML `Document` is for the write path only and the model may drop it to save memory.

## Rejected

- SQLite as primary store: a second source of truth next to the files; native module per Electron version.
- An external search engine: network service, violates N-047.

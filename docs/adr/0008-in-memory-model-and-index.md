# ADR-0008: In-memory model, search index, cache and file watching

Status: Proposed · Based on: D-002, D-014 · SRs: SR-003, SR-007, SR-015, SR-020, SR-068, SR-081, SR-082

## Context

Targets at 50,000 elements and 200,000 relations on 4 cores and 16 GB: start ≤ 3 s with cache, ≤ 30 s without; open element ≤ 200 ms; filter or chain ≤ 500 ms; search ≤ 300 ms; full check ≤ 60 s; external change visible ≤ 2 s; pull with 1,000 files ≤ 10 s.

## Decision

- **The files are the database.** `core` keeps an in-memory model per workspace: per element the parsed frontmatter, version, file location and outgoing relations; an inverted relation index (incoming), indexes by type, status, package and validity. Text bodies are loaded lazily and kept in an LRU.
- **Search:** MiniSearch (in-memory full-text index, fuzzy and prefix search, case-insensitive) over title, text, property values and IDs (SR-068 AK1, AK2). Search within a view or filter intersects with the selection (SR-068 AK3).
- **Queries** (filters, chains, coverage) run on the in-memory indexes; no SQL engine. Chains and coverage are graph walks with cycle detection (SR-022 AK4).
- **Cache** per working copy in the OS cache folder (`<cache>/logreq/<sha256 of the canonical workspace path>/`; canonical: absolute, symbolic links resolved with `realpath`, and lower case on Windows, so two names of one folder share a cache), never in the repository and never shared between copies (SR-081 AK2). It holds, per file, size, mtime, content hash, parsed frontmatter and version, plus the serialised search index. Start: list and `stat` all files, reuse cache entries whose size and mtime match, parse the rest. A corrupt or old-format cache is discarded. The OS cache folder is `%LOCALAPPDATA%` on Windows, `~/Library/Caches` on macOS and `$XDG_CACHE_HOME` or `~/.cache` elsewhere (`cacheFolder(root)` in core's workspace block); the folder of a copy also holds `api.json` of its local API (ADR-0009).
- **Cold start:** files are parsed by a pool of worker threads (`node:worker_threads`, one per core minus one).
- **File watching** (SR-007; `model/watch.ts`, `model/watch-tree.ts`): no dependency (`chokidar` was planned) and no process; the watcher writes nothing. It runs only where a workspace stays open: `watchWorkspace(workspace)` is a workspace state that the CLI starts for `logreq serve api` and `logreq mcp` (later the app), and closing the workspace stops it; a one-shot CLI command reads a fresh workspace and needs none.
  - macOS and Windows: `node:fs` `watch` with `recursive: true` on every available repository folder (FSEvents, ReadDirectoryChangesW; a repository nested in another is seen through the outer one).
  - Linux: one plain `fs.watch` per folder (`FolderTree`), not `recursive`. Node emulates `recursive` on Linux with one inotify watch per file and folder; a file replaced by a rename (an atomic save by vim, JetBrains IDEs or LogReq's own `writeFileAtomic`, a delete and re-create, a checkout) is then never reported again, and at 50,000 files the watch costs about 0.6 s of blocked event loop, about 100 MB and 50,000 inotify watches. A folder's watch reports every name in it however the file was written, so one watch per folder is enough: about one inotify watch per folder. Left out are `.git`, `node_modules`, folders of the `ignore` globs (unless the metamodel lies in them), folders of other repositories of the workspace (they have their own tree) and folders with a `.git` entry; a new folder named by an event is watched with its subfolders, and the watches of a folder that is gone are dropped. A folder that vanishes during the walk is skipped; a broken folder watch is dropped and its folder checked and watched again, without reading the layout again. A watch belongs to one folder: each watch keeps the `dev:ino` of its folder from a stat right after it attached, and a walk that finds the path gone, no longer a folder or with another inode drops the watch and watches it anew (a folder deleted and created again, replaced by a move, or emptied and filled by a checkout). Linux names the watched folder itself when it is deleted or moved away (`IN_DELETE_SELF`, `IN_MOVE_SELF`); a new folder in its place can get the same inode, so such an event drops the watch at once and walks the folder again. A repository folder that is gone reads the layout again, as a broken recursive watch does on macOS and Windows; the repository is then not available, and a clone in its place is seen after the next layout change or restart. All walks of a tree run one after the other; a folder that got a new watch is reported once more, for files created before the watch attached. A start that a newer layout overtook stops after its next step and its watches are closed; events of a layout that is no longer watched are dropped. Own code instead of chokidar v4 (ADR-0015): the per-folder tree is about 240 lines, chokidar would add a dependency and its own Linux emulation with the same replaced-file questions.
  - A folder that cannot be watched (`ENOSPC`: the inotify limit, raise `fs.inotify.max_user_watches`; or a refusal) is reported as a `workspace.not-watched` warning in `workspace.status` (`watcherProblems`); its changes are not seen until LogReq restarts or the layout changes. Commands still work. Only a process with a watcher (API, MCP server, app) reports it; a one-shot CLI command has no watcher and reads the files anew.
  - Events under `.git` and `node_modules` and LogReq's temporary files are dropped; so are other files than `*.md` unless the path is a folder or gone. Events are debounced (100 ms after the last, at most 1 s after the first) and processed in batches, one after the other, so a pull with 1,000 changed files is one or a few updates.
  - The workspace file or `.logreq/local.yaml` changed: the old watches are closed, the layout is reset (and with it everything built on it) and the new repositories are watched; events sorted with an older layout are dropped. A path in the metamodel folder: the metamodel and the state built on it are reset, without rewriting any element (SR-015). A broken recursive watch (macOS, Windows) reads the layout again and watches anew.
  - Element paths: the store is updated, not read again (`updateElements`). Per repository with changes, the Markdown files are listed again (one walk, no reads; it applies the ignore globs, nested repositories and links like the full read), files that are gone are dropped (also one deleted between the walk and its read), new files are read, files named by an event are read again, files below a changed folder (or all, when the OS gives no file name) are read again when size or mtime differ. A file read again with the same snapshot (SHA-256, size, mtime) keeps its record; the result equals a full read. The change goes through `applyStoreChange(workspace, change)`: one queue per workspace, `Workspace.replace` (compare and set) to install the new store, and a retry on the newer store when the store was replaced meanwhile. Replacing resets the states built on the store (short IDs, findings); with nothing changed the old store and those states are kept. A store nobody has read yet is left alone. A failed update resets the store, so the next command reads it in full. A repository that is missing at start is watched only after the layout changes.
  - The store and the states built on it may be swapped while a command runs. A command that needs one consistent view reads the store once and derives what it needs from that object (`buildShortIds(store.byId, metamodel)`, `duplicateIdFindings(store)`) rather than reading several states one after the other.
- **Performance tests** (ADR-0011) with generated workspaces of 50,000 elements run nightly and on PRs labelled `perf`, against the thresholds above.

## Consequences

- Memory: roughly 1–2 KB per element without text, so well under 500 MB at 50,000 elements.
- Several instances on separate copies never share state (SR-081 AK1).
- The watcher and file listings ignore LogReq's own temporary files `.<file name>.<8 hex>.logreq-tmp` (`isTempFile` in `files`, ADR-0007). Parsed files carry plain, frozen snapshots (path, size, mtime, SHA-256), so they can be cached and sent to worker threads; the kept YAML `Document` is for the write path only and the model may drop it to save memory.

## Rejected

- SQLite as primary store: a second source of truth next to the files; native module per Electron version.
- An external search engine: network service, violates N-047.

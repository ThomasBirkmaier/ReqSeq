# ADR-0019: One display model per display, shared by the app and the HTML export

Status: Accepted · Based on: D-029, D-078, D-080, N-036, ADR-0002, ADR-0010 · SRs: SR-011, SR-075, SR-080, SR-082, SR-084, SR-107, SR-137, SR-149, SR-224, SR-231 to SR-234 · The Electron app (`packages/app`) named here, with its React renderer, was removed (#2310); the pages of the web UI (`packages/web`, ADR-0020) import `@reqseq/core/displays` in its place, and where this ADR names the app's renderer or IPC, it describes the Electron app

"Display" is the glossary term for a way the tool presents data; "view" stays the set of requirements of the core or a variant (#1428).

## Context

The app renderer (`packages/app/src/renderer`, React) and the HTML export (`packages/core/src/html-export`, HTML strings) present the same displays of a workspace: element page, list, package page, overview or start page, neighbourhood, hints. D-080 says the export's pages are displays of the tool that show what its commands return, so that readers see the same terms, identifiers, relations and verification status as in the app.

The data is shared, but what each side builds from it is not. Both sides group, order, label, cap and word the same data in their own code:

- Relation groups: kind key, in order of appearance, incoming included (app, `element-view.ts:252`) against kind name, in metamodel order, outgoing only (export, `section-relations.ts:9`).
- The criteria count of the verification status in five forms: "verified 2 of 3 criteria (AK1 …)" (CLI), "open (2 of 3 criteria, AK3 not verified)" (app element), "open · 2 of 3" (app matrix), "open, 2 of 3 criteria" (export element), "open 2/3" (export list).
- Neighbourhood caps: 200 parents and 5000 nodes in the app against 100 each in the export. Empty group: "(no value)" against "–".
- Package members by `element.list where.package` (app) against the export's own walk over property relations (`export.ts:395`). Type counts with every status (app) against only elements with a page (export).
- List grouping and ordering in three places: `element.list`, `list-page.ts`, and `list-script.ts` in the browser.
- Hint group titles kept in the renderer (`hint-list.ts`, `LABELS`), next to the titles per problem code in `problem-codes.yaml` (SR-224 AK6), against D-078.

Each fix to one side leaves the other behind. The v0.13 milestone aims at visible navigation in the app, which needs a change of D-062 first; this ADR does not presuppose it.

## Decision

1. **A display model per display, in core.** `packages/core/src/displays/<display>.ts` holds one pure builder per shared display: `elementPageDisplay`, `neighbourhoodDisplay`, `listDisplay`, `packageDisplay`, `overviewDisplay`, `hintListDisplay`. It is exported as the core subpath `@reqseq/core/displays`, like `problem-titles`. This extends ADR-0002 rule 3: display rules that the app and the export share live in core `displays/`, outside the catalog; they compute no value (point 2). Baseline pages, the variant comparison and the export menu (SR-231 AK4, SR-234) have no app side and stay modules of `html-export` until an SR asks for an app display.

2. **Builders take command-output-shaped data, never the store.** A builder's input is typed with the generated output types of the catalog (`element.get`, the `$defs` of `data-export.schema.json`, `trace.neighbourhood` `nodes`/`edges`, `hint.list` `hints[]`, `evidence.list` `display`, `element.facets`, `metamodel.get`, `workspace.status`), plus pure display options (limit, chosen variant, page). In the web UI these are the outputs of the catalog commands through the UI server (ADR-0020); in the Electron app they came from `invoke` over IPC (ADR-0010). The export calls no commands: its batch produces the same shapes with the functions the commands' `run` uses (`listElements` with `withEvidenceStatus`, `neighbourhoodOutput` over a walk bounded with `maxNodes`, the item mapping of `hint.list`), unpaged. A test runs both on one fixture and checks that the export's input for an element equals what the command returns for it (D-080). A value the export needs in another form than a command gives it (status per criterion in each view, package members, type counts) is derived only from that command's output and checked by the same fixture test; a value no command gives at all is first added to a command output (catalog PR, ADR-0002). The change since a baseline has the shape of the `baseline.compare` difference (`fieldDifference`, D-080), computed in one pass per baseline and repository (N-036) and checked against that command by a fixture test (`commands/html/export-baselines.test.ts`); its word-level rendering stays in `word-diff.ts`.

3. **Import rule.** `displays/` modules import only types, other `displays/` modules and the import-free modules (`graph/words`, `model/criterion-items`, `query/fold`, `problem-titles`, `hint-order`, `type-order`), so the browser bundle never pulls in `node:*`. An ESLint `no-restricted-imports` block on `packages/core/src/displays/**` enforces it; since a flat-config block replaces the options of the core block, it repeats that block's patterns (`testkitInProduct`, `testCommandInProduct`). A rule a builder needs that lives in a module with model imports (the hint order `CHECK_ORDER`, the value order of SR-075 AK1 for values already in an output) first moves into an import-free module, which the old module re-exports. Ordering that needs the store (`element.list` `sort`/`group`) stays in the command; the builder takes the order the output gives. The export computes the facet index and ranks of its lists (SR-233 AK1, AK5) in `html-export` and passes them in.

4. **One wording per thing.** `ElementRef` (UUID, repository, short ID, identifier, title, status, invalid, verification cell, hint count) and `VerificationCell` (the view it is for, status or absent, criteria counts) are shared by every display. Words come from one function each: `verificationLabel(cell, "long" | "short")` (long: "open, 2 of 3 criteria, AK3 (k7f3) not verified"; short, for cells and badges: "open · 2 of 3"), `relationGroupLabel`, `emptyValueLabel`, `boundNote`. Hint groups are headed by the title of the problem kind from `problem-codes.yaml` (`@reqseq/core/problem-titles`); where a group needs a plural heading, it becomes a second field of the same entry (schema PR), and `hint-list.ts` `LABELS` is removed. The CLI's text output uses the same label functions.

5. **Targets, not links.** A display model names where a row leads as a target: an element, package or variant by UUID and repository, a list by type key. The app maps it to a buffer, the export to its stable page path (SR-231 AK3). No builder writes a URL.

6. **Write facts only from commands.** A display model passes on only the write facts a command output gives (`element.get` `readOnly`, the read-only flag of `workspace.status`). No builder derives an editing rule; SR-011 AK3 stays in core's command layer. The export ignores them (D-080: nothing can be edited in it).

7. **Two thin renderers.** The app renders a display model with React in its own look, the export with HTML strings and the docs stylesheet (D-080, SR-231 AK4). Rows, groups, order, caps and words are the same unless an SR says otherwise (point 9). App only: perspectives and recently opened on the overview, matrix and graph (D-063, D-080), editing data, paging. Export only: the change since a baseline, the missing-repository lines (SR-232 AK8), the start-page rows of SR-233 AK3 beyond the type lines (commit, export date, tool version, verification degree with counts, requirements not verified, elements with hints, changes since the newest baseline, the incomplete note), and the precomputed facet index and ranks. `list-script.ts` keeps the filter combination, hit counts and search that SR-233 AK1 and SR-231 AK7 prescribe for the browser; groups and ranks come from the display model. Perspectives are not shown in the export; showing one later needs a decision first.

8. **Batch and page (N-036, SR-082).** A builder works on one page and takes precomputed inputs. The export builds each page's display model just before rendering it and keeps none after writing it, so its peak memory is today's batch plus one page. Builders do no scan of the whole input per row; the list builder sorts at most once per sortable column. The app calls a builder once per shown page and adds no command call to the path that opens an element or a list unless the app performance rows of SR-082 AK3/AK4 still pass. Each migration PR compares the `html.export` rows of the nightly run with the last main run and states the difference under Verification; more than 10 % in time or memory is a review finding.

9. **Differences between app and export.**
   (a) Where an SR prescribes different content per side, the builder takes a named, permanent option that cites it: ID form (SR-084 AK4 against SR-233 AK1, SR-232 AK5), neighbourhood bound (SR-232 AK5; the app's caps are its `limit`), outgoing relations only on the export page (SR-232 AK1), the incoming group of package membership left out of the neighbourhood of a package page in the export (`withoutPackageMembers`, SR-232 AK9; the app's neighbourhood buffer keeps it, SR-107 AK2, and the app's package page drops the same group at the element, SR-107, #2174), invalid statuses in lists (SR-231 AK1), groupable keys (SR-233 AK1 against SR-149), type counts that follow each side's list (the export's lists hold no element with an invalid status, SR-231 AK1). In a list without a chosen variant, which every export list is, a requirement outside the core shows no verification status (SR-137 AK4, SR-233 AK1 and AK4); with a chosen variant the status is the one in that variant's view.
   (b) Where the spec names no wording, there is one (empty group value).
   (c) The open hints of an element come from `hint.list` on both sides (SR-232 AK4); the app's status line counts the same set. If the step that moves the element page finds that `element.get` `problems` and `hint.list` give different sets, that difference becomes a `question` issue before the step continues.
   (d) A side that breaks its SR is a `bug`: relation kinds unknown to the metamodel are dropped on the export page (SR-232 AK1, #2205).
   No difference is settled silently in code.

## Consequences

- One rule per wording, order and cap: a fix lands in both renderers at once.
- The move is an epic with one sub-issue per display, each one PR. The element page and the neighbourhood go first, before #2174, #2178 and #2184 are built, so their new rows go into the display model. A display moves only when no open PR changes its renderer.
- Builder tests need 100 % per file (ADR-0016). Tests named `[SR-xxx/AK-…]` stay where the AK is observed (app display or Playwright, export HTML); builder tests come in addition. A PR that moves code out of `packages/app` checks that the app's `.ts` coverage stays at 80 % or more, and adds app tests where it would not.
- One test per moved display builds the display model once from a fixture and checks that both renderers show each of its rows, groups and labels, so drift shows as a failing test.
- `packages/core/src/html-export` shrinks to the HTML renderer, the site frame, search, baselines, variants and the baseline diff. The app renderer loses the grouping of `element-view.ts`, the labels of `rows.ts`, `list-groups.ts`, the tree building of `neighbourhood.ts` and `hint-list.ts` `LABELS`.
- Docs: `packages/core/README.md` (subpaths), a block file `packages/core/docs/displays.md`, the renderer part of ADR-0010, `packages/core/docs/html-export.md`, the ADR index.

## Rejected alternatives

- **New catalog commands `display.*`.** They would make every wording an API for agents and grow the catalog by presentation; the values behind the words are already queryable (SR-080 AK4). The export would run one command per page with input and output checks and an answer each, and the catalog's paging (`limit` ≤ 5000) and complete walks do not fit a batch of 50,000 pages.
- **The export as a static build of the app.** SR-233 AK5 (a list without JavaScript) and SR-231 AK3 (a stable page per element) rule out a single-page build, and the app's React tree carries editing data the export must not have (D-080).
- **Keep two renderers and align them by tests only.** The same data would still be shaped twice, and the drift listed in Context shows where that leads.

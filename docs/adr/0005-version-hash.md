# ADR-0005: Version (Fassung) as content hash

Status: Proposed · Based on: D-013, D-027, D-036, D-042, D-057, D-060 · SRs: SR-021, SR-025, SR-031, SR-065, SR-091, SR-097 · Schema: `common.schema.json#/$defs/version`

## Context

Relations and references store the version of their target as a hash over its content (D-013). Only line endings, trailing spaces and blank lines are normalised (D-027); the normal form has a version number stored with every hash.

## Decision

**Version string:** `n<normal-form>:<16 hex>`, e.g. `n1:9f86d081884c7d65` — the first 64 bits of SHA-256. The prefix is the normal-form version (D-027). 64 bits are enough because versions are only ever compared for one element.

**Content of normal form 1:**

1. Text: the Markdown body, everything after the line that closes the frontmatter.
2. Every property whose definition has `content: true` (D-013, D-057: the flag "counts to the version" per property; in the standard model text, acceptance criteria, requirement type, verification method, emergent and validity count; title, status, packages, rationale, topic, statement and origin do not). Title, status and properties without the flag are not content (SR-021 AK3). Relation kinds are not content, so a new child does not change the parent. Unknown properties are not content.
3. Embedded images (D-057: "eingebettete Bilder zählen immer mit"): every image the text embeds with a relative link that resolves inside the same repository, with its SHA-256 (see **Files**). Where the editor puts new images (next to the element file) is SR-097 AK1; any image in the repository counts.

**Canonical form (n1):** UTF-8 bytes of

```
reqseq-version n1\n
text\n<normalised text as one JSON string>\n
prop <key>\n<canonical JSON of the value>\n      (keys sorted by code point)
file <path>\n<sha256 hex | missing>\n         (paths sorted by code point)
```

- Text normalisation: CRLF and CR to LF; trailing spaces and tabs removed from every line; runs of blank lines collapsed to one; leading and trailing blank lines removed (D-027). Nothing else, also not Unicode normalisation.
- The text is written as one JSON string (escaped like every canonical JSON string), so no text can produce lines that look like a `prop` or `file` section.
- Property values: as parsed by the YAML 1.2 core schema. The same whitespace rules apply to every string; lists keep their order. A relation-valued property contributes the target `id` as a JSON string, and a list of them when the value is a list; nothing else of the target counts, so the version of a validity target does not cascade. A malformed relation entry (no string `id`) is passed through unchanged; the element check reports it.
- Canonical JSON: no whitespace; object keys sorted by code point; strings escaped as `JSON.stringify` does (only `"`, `\`, and control characters, the latter as `\b \f \n \r \t` or lower-case `\u00xx`; every other character as UTF-8, also U+2028); numbers as ECMAScript `Number::toString` (`JSON.stringify`, RFC 8785), e.g. `1`, `0.1`, `1e+21`, and `-0` as `0`. Non-finite numbers (`.inf`, `.nan`) are invalid: computing the version throws.
- Sorting by code point equals the byte order of UTF-8.

**Markdown properties (SR-127):** the metamodel flag `markdown` does not enter normal form 1: the version reads the values and the `content` flag only, so the same file has the same version with and without the flag. Images in a Markdown property are no embedded images and do not count; only the text embeds images.

**Files (n1):** which images count, and how, is part of normal form 1. The result must be the same on every operating system and file system, so these rules are normative; another tool that reimplements n1 must follow them, also where they differ from CommonMark.

*Markdown subset.* The text is read line by line; a line ends at LF, CRLF or CR. Each line is classified on its own, with only the state below carried over from the lines before it. Where these rules differ from CommonMark, they win.

- Block quotes: up to 3 spaces, `>` and an optional space, repeated, are removed before a line is classified. A line with more `>` markers than the last one starts a new block (paragraph text ends). A line with fewer markers that continues paragraph text keeps the paragraph and the depth (lazy continuation).
- List items: a line that starts with up to 3 spaces, then `-`, `+`, `*` or 1 to 9 digits followed by `.` or `)`, then a space, a tab or the line end, is a list item; it starts a new block and the list. Any of these markers, also an ordered one other than `1.`, interrupts paragraph text. A list ends at an unindented, non-blank line outside a fence that is not a list item and does not continue paragraph text (a fence, a thematic break or an ATX heading interrupts it; with no paragraph open, any such line ends the list). In a block quote, a list item line is never a lazy continuation: it takes the quote depth of its own markers. List indentation is not tracked.
- "Indented" means starting with 4 spaces or a tab; tabs are not expanded.
- Fenced code: a line that starts with up to 3 spaces (after one list item marker, if any; a second marker on the same line is text) and 3 or more backticks or tildes opens a fence, except a backtick fence whose rest of the line holds a backtick. Everything is code until a line (after block quote markers) that holds only a run of the same character at least as long, with up to 3 spaces before it and white space around it, closes the fence. The fence state ignores block quotes: an unclosed fence, also one opened in a block quote, runs to the end of the text.
- Indented code: an indented line is code unless it continues paragraph text, is inside a list, or follows a definition line. An indented line right after an ATX heading (up to 3 spaces, 1 to 6 `#`, then a space, a tab or the line end), after a setext underline (up to 3 spaces, a run of `=` or of `-`, trailing spaces, after paragraph text) or after a thematic break (up to 3 spaces, three or more `-`, `*` or `_` with spaces or tabs between) is code. A blank line ends paragraph text.
- Code spans: a run of backticks opens a code span only when a run of the same length closes it on the same line; otherwise the backticks are text.
- Only image syntax counts: inline `![alt](destination "title")` on one line, and reference-style `![alt][ref]`, `![alt][]` and `![alt]` whose label a link reference definition defines. Only `[]` (nothing between the brackets) is collapsed: after `![alt][ ]`, or a label longer than 999 characters, the image is a shortcut `![alt]` and the brackets after it are text. Plain links `[text](path)` do not count.
- HTML is not recognised: images inside HTML blocks and HTML comments count. Entity references are not decoded (`&amp;` stays as written).
- Inline images and links are read with a stack of open brackets as in CommonMark: links do not nest, images and links in the alt text of an inline image do not count, and images and links in the alt text of a reference image do count. Parentheses nest at most 32 deep in a destination.
- A definition is one line `[label]: destination` with an optional title (`"…"`, `'…'` or `(…)`). The destination is in `<…>`, or has no spaces, does not start with `<` and has balanced unescaped parentheses. The label has at least one character that is not white space, no unescaped brackets, and at most 999 UTF-16 code units as written (an escape counts as two). A definition may start after a list item marker, also right after paragraph text. Otherwise it must not continue paragraph text, so a definition right after paragraph text is paragraph text; inside a list it may follow any indentation. The line after a definition is paragraph text, also when indented. Definitions spanning several lines are not recognised. Definition lines hold no images.
- Labels match after this normalisation: the characters ECMAScript `String.prototype.trim` removes are removed at both ends, each run of spaces and tabs becomes one space, then ECMAScript `toLowerCase` and then `toUpperCase` are applied (locale independent). The first definition of a label wins. A reference image whose label no definition has does not count.

*Path rules.* For each image destination, in this order:

1. Drop an optional `<…>` wrapper and the title. Remove backslash escapes of ASCII punctuation. Drop a query (`?…`) or fragment (`#…`).
2. Does not count: an empty destination, an absolute URL (any scheme, also `file:`, `data:` and a drive letter `C:`), an absolute path (`/…`).
3. Percent-decode. A destination that is not valid percent-encoded UTF-8 stays as written. Does not count: a decoded path with a C0 control character or DEL.
4. Resolve against the folder of the element file, removing `./` and resolving `..`. Does not count: a path that ends outside the repository, or at the repository folder, the folder of the element file or the element file itself (compared after NFC, so the folder or file in the other normal form is still itself). Also not counted: a path through a name the element walk skips (`.git` or `node_modules` in any case, with trailing dots or spaces), or one an `ignore` glob of the workspace file matches (the path or a folder above it, as the text spells it after decoding, compared in NFC (`ignoreMatcher`)).
5. Missing on every OS, whatever is on disk: a decoded path that holds `\` (also from `%5C`; escapes are gone after step 1), a destination that ends with `/`, or a name that Windows changes or refuses (a trailing dot or space, one of `<>:"|?*`, a control character, a device name such as `NUL` or `com1.png`).
6. Otherwise look the path up name by name from the repository folder, listing each folder. Each name must equal a name on disk: exactly, or else the only one equal to it after NFC. Case is never ignored. A name that matches no entry, or two entries equal after NFC, is missing. Every folder above the file must be a real folder; below a link to a folder, every file is missing. Does not count: a file inside a nested repository, that is below a folder (not the repository folder) that holds a `.git` entry or is the folder of another repository of the workspace.
7. The file itself: a regular file counts with the SHA-256 of its bytes. A symbolic link is not followed and counts with the SHA-256 of its link text, which is its Git blob and what a checkout without links (`core.symlinks=false`) holds. Windows gives a link text with `\` as separator; there every `\` of it becomes `/`, as Git stores it. Anything else (a folder, a device) is missing.

*Canonical form.* The path is relative to the folder of the element file, with `/`, after normalisation (it may start with `../` while it stays inside the repository). The path keeps the spelling of the text, not the one on disk. A destination ending with `/` keeps the `/`. Each path is written once, however often the text embeds it; `version.ts` rejects a duplicate path, so the caller dedupes. A missing file counts with the marker `missing` instead of a hash, so adding the file later changes the version. `<sha256 hex>` is lower case. Reading errors other than "not there" (`ENOENT`, `ENOTDIR`) are not missing: computing the version fails with `file.faulty`.

*Implementation.* The model module extracts the images (`model/images.ts`, with the shared Markdown scanner `markdownImages` in `model/markdown-links.ts`). It walks the folders itself and reads the hashes through the `files` block (`readFileSha256`, streamed, at most 32 files at a time). `version.ts` takes the normalised paths and hashes. A command or run passes one memo of folder listings (with an NFC index built on the first name not found exactly) and image hashes to all its lookups (`TargetContext.images`). The rule is option 1 of spec question #131, decided on 2026-10-24, implemented by enabler #178. The test vectors in `schemas/examples/version/` pin these rules (vector `SR-7a8b9c0d1e2f`).

**Changing the normal form** means a new prefix `n2`. Stored `n1` versions are then compared by recomputing `n1` for the current content, so nothing becomes outdated silently (D-027).

**Version date (D-013 display):** the committer date of the newest commit that started this version: the element file has the version there, and no parent of the commit has it. Read via Git (ADR-0006), lazily and cached. The date is in UTC as `YYYY-MM-DDTHH:MM:SSZ` (whole seconds), the same string on every platform and Git version. Uncommitted content has no date (`null`, shown as "uncommitted").

*Where the date is shown* (D-013; decided on PR #266, review round 1). The hints on outdated relations (SR-025, SR-026) show the dates of the stored and the current version (`versionDates`). The element view shows the date on request: `element.get` and `element.resolve` give `versionDate` only with the input `versionDate: true`. By default it runs no git and leaves the field out, so opening an element stays within SR-082 AK3 (200 ms) however long the history is; the app asks for the date in a second call (stage 3). At an outdated reference the app shows the date of the version the reference stores (SR-110 AK2, #702): `element.get` with `hintDates: true` dates only the `relation.outdated` hints (walks of their target files, none for an element without such hints), not the element's own version, and the app asks for it only after the element is shown and only when the element has such hints. Both calls give the same result through app, CLI, API and MCP (D-029).

*Which commits.* The commits reachable from HEAD that changed the element file or an image one of its texts embeds (`git log` with these paths, renames not followed: the history of the path the file has now), and every merge, each with its parents among them (`--full-history --parents`: no history simplification, so what counts for one file never depends on the other files a call reads with it). A commit that is not listed changed none of these paths and is no merge, so it has the version of its parent; so has a merge whose sides all lead to the same evaluated commit (the newest one before it that changed these paths or is itself an evaluated merge), which is therefore skipped. When a text at an older commit embeds an image no newer text embeds, the history is read again with that path too, so a commit that changed only that image counts. At each listed commit, the element file must hold the element (same UUID, frontmatter that parses, a type); its version there is computed by normal form 1 with today's metamodel, as any stored `n1` version is compared (above).

*Start of a version* (decided with enabler #260, review round 1). A commit starts a version when the file has that version there and none of the commit's parents has it. The date of a version is the committer date of its newest start. Therefore:

- A commit that changed only something outside the version (the status, the title) starts nothing; the date stays.
- A version that comes back (a revert) starts again; its date is the date of the revert.
- A merge that resolves a conflict starts its version. So does a merge that joins the file of one side with an image of the other: that version exists only from the merge on.
- A merge that takes the version of one of its parents starts nothing.

*Lazy evaluation.* A version is computed only where an answer needs it: from the newest listed commit back, in rounds of 2, 4, 8 … commits, until the newest start of the asked version is certain (the versions of its parents are known and no newer commit is still open). Each text blob is read and parsed once, each image blob hashed once, and versions are kept by text blob and image hashes. An element whose current version started recently needs one or two rounds whatever the length of its history.

*Embedded images at an old commit* (decided with enabler #260). The links are those of the text at that commit, by the Markdown subset and path rules 1 to 5 above, with today's `ignore` globs. Then:

1. Rule 6 is done in the commit's tree instead of the folder walk: the path as the text spells it, else the only one of its NFC and NFD forms the commit has (both there: missing). Git compares names exactly, so this looks at the whole path: a path whose folder and file names Git stores in different normal forms is not found and counts as missing, while the working copy (rule 6, name by name) finds it; such a version has no date. Such trees come only from tools that disagree about one name; matching name by name would need a tree listing per folder and commit, which is not worth it.
2. Rule 7: a blob entry (a file or a symbolic link) counts with the SHA-256 of the blob as Git stores it: no checkout filters, so no other program runs and Git LFS never goes to the network. A symbolic link is its link text, as in the working copy. A folder, a submodule entry or no entry is `missing`.
3. A path that the working copy finds inside a nested repository now (rule 6) does not count at any commit: Git does not store a nested repository's files in this repository.

*No date (`null`).* No walked commit starts the version: uncommitted content, a version from before a rename, or a version whose image the checkout changed (line-ending conversion of an SVG, a Git LFS pointer: the working copy then differs from the blob, so the recomputed version differs; marking SVG images `-text` in `.gitattributes` keeps their dates, an element with an image in Git LFS has none). Also no date when the version is not `n1`, or when Git cannot tell: git missing or refusing the repository, no `.git` entry in the repository folder (then no process starts), no commit, a shallow clone (its oldest commit would look as if it made every file), an image blob Git no longer has, or a git call that fails or times out. The answer always waits for its walk: there is no time limit of its own besides the limits of the git calls (ADR-0006), so the same request gives the same date through every access (D-029). A walk that failed because git timed out, was stopped or is missing is not kept and is tried again by the next call; one that failed for another reason (Git refuses the repository or reports a broken object) keeps `null` until HEAD moves.

*Cost.* One walk per element file and HEAD gives the dates of all versions the file had, so many relations to one target cost one walk. The walks of one call share the git processes of their repository: one `log` over the folders of the walked paths (literal pathspecs ending in `/`: one per file would cost time per commit, folder entry and path, minutes in a deep history with large folders; the paths of each walk are picked from the answer), which walks the whole history reachable from HEAD and lists every merge (once more when an old text embeds an image the current one does not; `element.get` passes the current text, so its images are in the first `log`), and one `cat-file --batch-command` process for all object rounds of the call (git 2.36 and newer; an older git gets one `cat-file --batch-check` or `--batch` process per round). HEAD is read from the files of the Git folder (ADR-0006, `headFiles`); `rev-parse` runs only where they cannot tell. The walks are kept per workspace while these files are unchanged, and while HEAD names the same commit (packing refs keeps them), until the metamodel or the workspace file is read again (`model/version-date.ts`). `element.get` with `versionDate` starts the walk before it builds the view, so Git reads the history meanwhile. The performance suite (`packages/core/test/perf/open-filter-chain.test.ts`) records such an open at N-036 size with 1,002 commits per repository, without a threshold; the tagged SR-082 AK3 tests measure the open without the date. `packages/core/test/perf/version-date-merges.test.ts` records the first walk of 300 files over 3,001 commits with 1,000 merges.

- An absent property, `null` and an empty list are the same and are left out. Numbers are written as JSON numbers, dates as `YYYY-MM-DD` strings, choice values as their key. A property flagged `content` counts only if the element's type has it; unknown keys never count.

**One implementation** in `core` (`packages/core/src/version/version.ts`, pure: the model module passes text, property values, the property definitions of the element's type, and the normalised embedded images with their SHA-256, or `null` when missing). Before any version is stored, stage 1 adds test vectors in `schemas/examples/version/` (input file, canonical bytes, hash) so other tools can reimplement it (N-048, D-013 "also by other tools"). `vectors.yaml` there describes the format; `pnpm schemas:check` checks hash and element schema, a core test recomputes the canonical bytes.

## Consequences

- A status change, a renamed title or a new child relation never makes evidence outdated.
- Reformatting a table makes evidence outdated, as D-027 wants.
- The date lookup needs Git history; in a shallow clone the date is unknown (`null`), like uncommitted content. The schema has one `null` for both.
- The cache (ADR-0008) must key a cached version on the embedded files too (size and mtime, or their hash), not only on the element file; otherwise a changed image keeps a stale version.
- The version is no write precondition, since a change of the title, the status or a property that does not count leaves it as it is; `element.get` and `element.update` give the SHA-256 of the element file (`fileSha256`) for that, and `element.update` refuses a write when `expectedFileSha256` differs from it (SR-106); that hash is never stored in a relation, so the rejection of a whole-file hash as version below stands.

## Rejected

- Commit hashes or counters as version: lost on rebase, collide on parallel branches (D-013).
- Hash over the whole file: would include title and status.

# ADR-0011: Test tools, evidence and quality gates

Status: Proposed · Based on: D-026, D-050, D-051, D-054, D-055 · SRs: SR-019, SR-020, SR-068, SR-076..SR-083

## Decision

**Tools**
- Unit and integration tests: **Vitest**, one root config (`vitest.config.ts`), test files `packages/*/src/**/*.test.ts` and `packages/*/test/**/*.test.ts`.
- CLI end-to-end: Vitest tests that spawn the built `logreq` binary on fixture workspaces (`packages/cli/test/e2e/`).
- App: **Playwright** with its Electron support (`_electron.launch`), under `xvfb-run` on Linux (`packages/app/test/`), from stage 3.
- Delivery (ADR-0014): Vitest tests in `packages/*/test/delivery/` (`pnpm test:delivery`, own config) unpack and inspect the built artifacts and start their launcher, MCP server and app. They run only in the release workflow, never on pull requests. On Linux they run in a network namespace with loopback only, created by root, as a non-root user with Chromium's sandbox on (never `--no-sandbox`); `unshare -rn` is not used for them, because Chromium refuses to run as the mapped root. Every release run builds and tests each system on GitHub's `macos-14`, `ubuntu-24.04` and `windows-2025`: SR-076's macOS 14 and Ubuntu 24.04 evidence, and Windows evidence from Windows Server 2025 (not Windows 11 itself).
- Test names start with `[SR-xxx/AKn]` for every acceptance criterion with method Test (D-050). JUnit XML (`test-results/junit.xml`) is the evidence record; from stage 4 LogReq reads it itself.

**Fixtures and data**
- Small fixtures per SR in `fixtures/<sr-id>/`, built as temporary Git repositories by a helper (`fixtures/README.md`).
- Generator for large workspaces (50,000 elements, 200,000 relations, mixed types and repositories) with a fixed seed, in `packages/testkit` from stage 1 (D-055); from stage 4 with evidence records of that workspace (`withEvidenceRecords`: JUnit files of CI runs, Markdown verification and validation records, #583).
- Realistic multi-repository scenarios come from `logreq-testdata` (D-055), checked out in CI.

**Product rules as tests**
- *Offline:* every Vitest run loads `scripts/test-support/block-network.mjs`, which fails any connection that is not loopback (SR-077, SR-078). The Electron tests additionally assert that the session blocked all non-local requests. On Linux CI the CLI e2e suite also runs inside `unshare -rn` (no network namespace).
- *Loopback only:* API test asserts the listening address (SR-079).
- *Read-only Git:* `.git` snapshot before and after (ADR-0006, SR-083).
- *Status untouched:* every write command except setStatus/supersede leaves status unchanged (SR-087).
- *Cross-access:* the same scenario through core, CLI, API and MCP gives equal output (SR-080).
- *Performance:* generated 50,000-element workspace; thresholds from SR-007, SR-015, SR-020, SR-068, SR-082. Runs nightly and on PRs labelled `perf`; the perf job is not a required check. Every time is recorded in `verification/performance.md` as analysis, and a time over its threshold opens or updates an issue. A test tagged `[SR-xxx/AKn]` for an acceptance criterion with method Test asserts its threshold, so the perf job fails when it is exceeded. The reference machine of the performance SRs has 4 cores and 16 GB; the job prints the cores and memory of its runner. A pass on a runner at or below the reference machine is evidence for the criterion; a failure on a weaker runner is measured again on the reference machine before code changes (#215, SR-020). Untagged measurements (component times, such as the cold load inside one process) only record. Implementation (#126): tests in `packages/*/test/perf/` (`pnpm test:perf`, `vitest.perf.config.ts`, excluded from the required run) record times with `measure` of the testkit (`measureMedian` records the median of several runs, for a latency such as SR-098 AK1, #110), and tagged tests assert with `thresholdMessage`; `scripts/perf/report.mjs` writes `verification/performance.md`; `.github/workflows/perf.yml` runs the suite inside `unshare -rn` at 02:30 UTC and with label `perf`. It commits the record on the nightly run when the record is complete (no failure except threshold assertions, `report.mjs --junit`) and opens or updates one issue labelled `perf` when a threshold is exceeded. Correctness assertions in perf tests fail the run as usual.

**Quality gates (required checks)**
`checks (ubuntu-24.04 | macos-14 | windows-2025)`: on Linux the static checks (typecheck, lint, format, schemas, generated contracts, licenses, the Python unit tests of `scripts/sr-issues`, audit), then build, unit tests with the coverage thresholds of ADR-0016, `spec:check`, the CLI e2e suite and `trace-check`, in one job with one install and one build; on macOS and Windows build, unit tests, `spec:check` and e2e (#566; until then the separate jobs `static`, `test`, `e2e` and `trace-check`). A step after the install runs even when an earlier check failed, so one red step never hides another result. A change to a pull request's title or body, or of its label `enabler` or `spec-export`, runs only `trace-check (PR text)`; other labels start no job, and a change of the base branch is a full run. If `checks` failed only in its trace-check step, fixing the text is not enough: re-run the failed jobs of that run (`lead-run` skill, `merge.md`). Every run (pull requests, nightly at 02:00 UTC and manual) runs `checks` and `electron` on all three systems in parallel, and a push to `main` runs nothing: each pull request is fully checked before its merge, the nightly and manual runs check `main`, a red nightly run is fixed on `main` the next morning, and closing or merging a pull request cancels its run (product owner decision, 2026-10-28), on GitHub's hosted runners; no job runs on a self-hosted runner, because a public repository must not run code from pull requests on a machine of its own (until the move to a public repository, pull requests ran on Linux only, on self-hosted runners, and Windows only on manual dispatch, #365, #566). The performance suite runs on GitHub's hosted Ubuntu runner, which has the size of the reference machine. The Electron tests run in the job `electron` (#322): `pnpm --filter @logreq/app test:electron` downloads the Electron binary, builds the app and runs Playwright, under `xvfb-run` on Linux, on all three systems. Their JUnit file is `test-results/junit-electron.xml`. A pull request that changes only files no test or build reads (`docs/**`, `.claude/**`, `verification/**`, `toolchain/**/*.md` except anything below `toolchain/junit/`, and Markdown at the root; `.github/scripts/tests-needed.sh`) skips build, unit tests, `spec:check` and e2e in `checks`, the Electron tests in `electron` (both jobs pass with those steps skipped) and `perf` (skipped); the static checks and `trace-check` always run, and `spec/`, `fixtures/`, `packages/`, `toolchain/junit/**` (read by the e2e test `toolchain-junit.test.ts`: the guide and the element files of the example workspace, SR-063) and every other path, nightly and manual runs run everything (#520).

**Verification records** for Analyse, Inspektion, Demonstration in `verification/SR-xxx.md` (D-050), confirmed by a person at stage acceptance.

## Rejected

- Jest: slower, weaker ESM support.
- Separate test runners per package: harder to produce one JUnit file per run.

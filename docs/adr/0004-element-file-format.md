# ADR-0004: Element file format

Status: Proposed · Based on: D-012, D-015, D-017, D-020, D-040, D-041, D-042, D-043, D-045, D-056, D-057, D-058, D-059 · SRs: SR-001..SR-005, SR-010, SR-016, SR-021, SR-042, SR-048, SR-057, SR-066, SR-072, SR-089, SR-102 · Schema: `schemas/element.schema.json`

## Context

D-015 and D-056 fix "one Markdown file per element, YAML frontmatter, then text". Everything that touches the file format belongs in stage 1 even if the function comes later (D-035). This ADR fixes the remaining details so that no agent invents its own.

## Decision

### Frontmatter

```yaml
---
id: 102ee39b-773f-4cd0-b414-825b7146fb54     # UUID v4, never changes (D-017)
type: system-requirement                      # type key (D-043)
status: draft                                 # status key (D-030)
title: Show wind speed in large digits        # property with meaning `title`
requirement-type: functional
acceptance-criteria:
  - Given ..., when ..., then ...
validity:                                     # meaning `validity` (D-020); absent or empty = all
  - { id: ca0dd4a9-…, version: n1:2c26b46b68ffc68f, title: Pro }
packages:                                     # meaning `packages` (D-040)
  - { id: 19fd3f5e-…, version: n1:4be0643f1d98573b, title: Release 1.0 }
derives-from:                                 # relation kind key
  - { id: 878e339e-…, version: n1:7d865e959b2466f0, title: Wind speed visible at a glance }
  - { id: fe5fce30-…, version: n1:e3b0c44298fc1c14, repository: subsystem-sensor }
customer-id: WS-0815                          # external ID: a property, here with the meaning `identifier` (D-017, #305)
---
```

- Structural keys: `id`, `type`, `status`. `status` is one of the statuses of the element's type: a type may restrict the metamodel's statuses with `statuses`, inherited like properties, and an element of a type without status has no `status` key (#306). A status outside the type is the hint `element.status-not-allowed`, a missing one on a type with a status that is not marked invalid `element.missing-status`. A type whose statuses are all marked invalid (e.g. `statuses: [retired]`) has an optional status: its elements without `status` are current, and `element.supersede` retires them (#344, option 1). Every other key is a property key or relation kind key of the metamodel. Keys are unique across properties and relation kinds. The origin of imported elements is stored in ordinary properties with the meanings `source`, `source-identifier`, `import-date`, `delivery` and `import-version` (the Importfassung, which never counts to the version; D-059, SR-057); only ReqIF import writes them. The standard model gives them to every type (#357).
- Identifiers (#305, decision of 2026-10-26 on that issue): an ID from another source (D-017), such as the spec ID `SR-036` or a customer ID, is an ordinary property; the metamodel may give one property the meaning `identifier` (kind `text` without `many`, else `metamodel.invalid`). Its value is the element's identifier, unique per type: elements of one type that share one (compared in any case) each get the hint `element.duplicate-identifier`. The standard model has no such property; a workspace adds one. Every command that takes an element reference (`common.schema.json#/$defs/elementRef`, resolved in one place, `resolveRef` in `packages/core/src/model/resolve.ts`) accepts the identifier besides the UUID and short ID, in any case: a reference of the UUID form names only the element with that UUID (identifiers are never compared with it); any other names every element whose short ID or identifier it is, and when that is more than one element (a short ID of one that is the identifier of another, an identifier shared by two types) it is `ref.ambiguous` with them as candidates, never a guess. A reference of the short-ID form that names no element by short ID but is an identifier also takes the elements whose UUID ends with its tail as candidates (the prefix may have changed since it was stored, SR-015, #275), so it never silently names the element with the identifier. A reference has at most 256 characters, no control characters and no spaces at either end; `ref.unknown` quotes it. Outputs show it as `identifier` next to `shortId` (elements, their relations, chain, related and affected elements) and as `elementIdentifier` next to `elementShortId` on problems; messages name elements by short ID only, since a message kept in a state must not depend on another element's identifier.
- Values are text, number, date (`YYYY-MM-DD`), choice key, or lists of these. Relation-valued properties and relation kinds hold **relation targets**: `{ id, version }` plus `title` when the target is in the same repository, or `repository` (its workspace name) when it is in another one (D-058). A target across repositories never carries title or text (SR-005 AK1); the tool looks it up in the repository it names and shows its title when it is available locally (SR-005 AK2).
- Validity and packages are relation-valued properties, so they carry a version like any relation and become outdated when the variant or package changes.
- Unknown keys are kept byte for byte and reported as hint `element.unknown-property` (D-012, SR-016). An unknown `type` makes the element read-only (SR-016 AK3).
- A Markdown file counts as an element when its frontmatter has `id` and `type`. Files without frontmatter, or with frontmatter lacking these keys, are ignored and never changed (SR-003 AK2). A file whose frontmatter cannot be parsed is reported (SR-008) and never written.

### Text and inline references

- Below the frontmatter, after one blank line: the text, CommonMark with GitHub extensions (tables, task lists, strikethrough, autolinks), math as `$…$`/`$$…$$` (LaTeX), diagrams as fenced ` ```mermaid ` blocks (SR-065).
- An inline reference to another element (SR-066) is a normal Markdown link with the scheme `reqseq:`:
  `[<label>](reqseq:<uuid>?version=<version>)` within the same repository, and
  `[<label>](reqseq:<uuid>?version=<version>&repository=<name>)` when the target lies in another repository, with `<name>` the target repository's name from the workspace file (D-041). D-058 applies to inline references too (decision on spec question #177 (c), option 1, product owner decision, 2026-10-25): only with the repository name can ReqSeq tell a target in a repository that is not on this machine (N-041) from a missing one (N-065). The label is the title within the same repository and the short ID otherwise (D-058); ReqSeq never writes a title into a link across repositories. A link without `repository` points into the source's own repository, like a relation target without `repository` (D-058). So that links to another repository written before this decision keep working, a target that is not in the source's own repository but in exactly one other repository on this machine counts as that one (`resolveReference` in `packages/core/src/model/references.ts`). It renders as a plain link on GitHub and in any editor. Inline references count as relations with the internal meaning `reference` (not a metamodel meaning; it appears only in command output) for outdated checks (SR-066 AK3) and the affected-elements query (SR-024), but not for the chain.
- Properties marked Markdown (SR-127, #444): the metamodel marks a property of kind `text` with `markdown: true` (never one with the meaning `title` or `identifier`: `metamodel.invalid`), and its values are Markdown like the text: emphasis, code and inline references. In the standard model these are `acceptance-criteria` and `rationale`. The file stays valid YAML and readable: a value is a YAML string, plain where YAML allows it, else quoted (`**Gegeben** …` starts with `*`, so it is double-quoted), one line per value. A reference in such a value is the same link as in the text and counts as an inline reference for the missing-target check (SR-089), the outdated check (SR-025), the affected elements (SR-024) and the neighbourhood (SR-107). A link in the title, in an identifier or in a property that is not marked is plain text. The store records the links of every string value of the frontmatter (`ElementRecord.propertyReferences`, read only when the frontmatter holds `reqseq:`) and `referencesOf` selects those of the marked properties under the metamodel, so a change of the flag needs no new read. Messages name the place ("Reference in acceptance-criteria (item 2) of …"). Images in a Markdown property are no embedded images: they do not count to the version (ADR-0005) and the app does not show them.
  - Hint ID: `relation.outdated/<repository>/<file>/<source>/@text:<key>/<target>?version=<stored>` with `&repository=<name>` as for the text and `&n=<k>`, counted over all values of that property (a list is one text). The key follows a colon, since a key can be `text` and `@<key>` would clash with `@text`.
  - Setting: `element.create`, `element.update` and `element.bulkUpdate` give a reference in a value they set the version of its target, exactly as for the text, and refuse an unknown or ambiguous target with `ref.unknown` or `ref.ambiguous` naming the property (`details.key`). Only the properties the input sets are handled: a save that sets something else never adds a version to a link written by hand.
  - Confirming: `hint.confirm` replaces the version inside the scalar's own source text (`set-scalar` with `source`), so plain stays plain, quotes stay as they are and no other byte changes (SR-027 AK1). Only a block scalar (`|`, `>`) is rewritten, as one line with the same value. A link in a property that counts to the version (`content: true`, as `acceptance-criteria`) changes the version of the element when it is set or confirmed, as one in the text does; in `rationale` it does not.
- Images live next to the element file in a folder named like the file without `.md` (`SR-825b7146fb54/layout.png`) and are linked relatively; their bytes count to the version (ADR-0005, SR-065 AK2). Where they go is SR-097 AK1; the reading of "neben der Element-Datei" is asked in spec question #334 (option 1, this folder, until answered). `element.addAttachment` (`model/attachment.ts`) copies an image there and gives the Markdown; the caller inserts it and saves the text with `element.update`, so the command changes no element file and never the version by itself.
  - Name: the source name made portable: NFKD with the combining marks dropped (`Ä` is `A`), every run of other characters than ASCII letters, digits, `_` and `-` one `-`, no `-` at either end, at most 64 characters, `image` when nothing is left, `-image` after a Windows device name (`CON-image.png`); the extension in lower case, one of `.avif .bmp .gif .jpeg .jpg .png .svg .webp`. So the name is the same on every OS, Git server and text editor and needs no escaping; a folder name ReqSeq did not choose (an element file `Wind (gusts).md`) is percent-encoded in the link (`Wind%20%28gusts%29/layout.png`).
  - Never replaced, never deleted (D-045): a name the folder has in any case or Unicode normal form gets `-2`, `-3`, ...; a file with exactly that name and the same bytes is reused; a name the text already embeds (a missing image) is skipped. The path must pass the rules of the element walk before anything is written (`newFileTarget`: never below `.git`, D-036; no `ignore` glob; no nested repository; portable folder names).

### File name and location

- File name: type prefix, dash, the last 12 hex characters of the UUID, `.md` (D-056), e.g. `SR-825b7146fb54.md`. The displayed short ID is separate: at least 6 characters, longer when needed to be unique (SR-002 AK3). Code gets file names only from one function `fileNameFor(element)` in `core`.
- A clash of two 12-character stems in one folder (about 1 in 10^9 at 50,000 elements) is reported by the check as `element.file-name-clash` and resolved by hand; ReqSeq never renames.
- The file name never changes after creation, also not on rename or type change (SR-001 AK2).
- Folders are free; ReqSeq finds elements by frontmatter (SR-003). New elements go to a folder given by the caller, else the type key as folder name.

### Relations

- A relation is stored only in the file of its source. Adding a relation never changes the target file (D-040, N-039: two people adding children to the same parent change different files).
- Direction by meaning (`schemas/metamodel.schema.json`): `derivation` source = child, target = parent; `replacement` source variant requirement replaces target core requirement in the variants of the source's validity (D-020); `succession` source (successor, new) supersedes target (old) (D-045, SR-072); `exclusion` source variant excludes target core requirement (SR-042: written into the variant file).
- `exclusion` is decided by D-059 (relation kind Excludes on the variant).
- Superseding (D-045, SR-072) uses the meaning `succession` ("Ablösen"), and only a variant replacement uses `replacement` ("Ersetzt", D-020): D-059 makes them two separate meanings, so no reader guesses one from the source's validity or the target's status (#356). `element.supersede` with a successor writes the status into the old file and the relation into the successor's file. The standard model offers `supersedes` (any types, `succession`) and `replaces` (system requirements in variants, `replacement`); when more than one relation kind with the meaning `succession` fits, the caller names it, unless the successor already has the relation to the element under exactly one of them, which is then reused (nothing new is written, #196).
- Setting a target (SR-021, spec question #177): a relation or inline reference stores the target's UUID and its version at the moment it is set (plus the same-repository `title`, or `repository` across repositories, D-058). In a relation-valued property a target is the pair of UUID and repository, and a list names each target once (a target given twice is written once). A target the property already stores with a valid `version` keeps its stored entry unchanged (also any other keys in it; only its `title` follows the target, see "Stored titles"), whatever version the caller sends, so saving never confirms an outdated relation; only confirming a hint changes a stored version (D-042, SR-027). A stored entry without a valid version gets the current version, or stays as it is when its target cannot be found. Every new target gets its current version; callers give only `id` (and `repository`), the input schema makes `version` optional (`common.schema.json#/$defs/relationTargetInput`). In the text, a reference whose UUID and version the stored text already has is kept; every other one (new, without version, or with a version changed by hand) gets the current version, with other query parameters kept (empty ones, as in `reqseq:<uuid>?`, are dropped). A stored reference without version whose target cannot be found is kept as it is, so it never blocks other edits; a new one refuses the write (`ref.unknown`, `ref.ambiguous`). A `reqseq:` link that names its target by short ID, identifier or a UUID in upper case (`[D-031](reqseq:D-031)`) is resolved like any element reference (`resolveRef`, within the repository the link names, if any) and written as `reqseq:<uuid>` with the rest of its destination kept, then set like a new reference; one that does not resolve refuses the write (`ref.unknown`, `ref.ambiguous`, with the link in `details.link`), unless the stored text has it as written: then it stays, and `workspace.check` reports it as `relation.unresolved-link` (warning), since such a link counts for nothing (#176). A reference that is kept is compared by UUID, version and repository as written, so a stored link to another repository without `repository` stays as it is on save (it keeps working), also when it is copied with that UUID and version into another place of the text; one whose repository was changed by hand is set anew. A reference that is set looks its target up in the repository it names (refused with `ref.unknown`, reason `repository-not-available`, when that repository is not on this machine, as for relation targets), or, when it names none, in the source's own repository and else in the one other repository that has the UUID (`ref.ambiguous` when several do). When the target lies in another repository than the source and the link names none, `repository=<name>` is written right after `version` (D-058); a `repository` that names another repository stays as written, one that names the source's own is dropped, as a relation target within the repository stores none. A relation or reference from an element to itself stores the element's version from before the write; when the write changes what counts to the version (always for a reference in the text, since the text counts), the relation is outdated as soon as it is written. ReqSeq does not treat this case specially. Links are found by one scanner, `packages/core/src/model/markdown-links.ts`: inline links and images on one line, outside fenced code blocks (also in block quotes), indented code blocks and code spans; code spans take precedence over the brackets of a label, and links do not nest (CommonMark); images and escaped brackets are no references; reference-style links, links across lines and HTML are not handled, and a fence indented by 4 or more spaces in a nested list item is not recognised (the file comment lists the cases); each line is read in one pass from left to right with a stack of open brackets (CommonMark), without recursion, and parentheses nest at most 32 deep in a destination, so a line costs about linear time whatever its nesting. Implementation: `packages/core/src/model/targets.ts`.
- Missing targets (SR-089): a relation target and an inline reference are checked alike (`packages/core/src/model/missing-targets.ts`). A link without `repository` points into the source's own repository, which is always on this machine: it is missing when neither that repository nor another one here has the UUID (the one-other-repository rule above), also while some repository of the workspace is not on this machine. The trade-off (D-058): an old link to another repository written without `repository`, whose repository is not on this machine, is reported as missing too. Its message then names the repositories that are not here and says to add `repository=<name>` to the link; `element.create` and `element.update` say the same when such a new link finds no target, and suggest `repository=<name>` when copies of the UUID lie in several other repositories. An empty `repository=` names no repository. A link naming a repository that is not on this machine, or one the workspace file does not list, is no finding (SR-089 AK2, #193).
- Confirming a hint (D-042) rewrites only the `version` (and the same-repository `title`) of that one relation target (SR-027 AK1), besides the stored titles below.
- Stored titles (decision on spec question #307, product owner decision, 2026-10-26): the `title` of a same-repository target does not count to any version (ADR-0005), so a rename alone gives no hint. Whenever ReqSeq writes a source file through a write command (`element.update`, `element.setStatus`, `element.supersede`, `element.bulkUpdate`, `relation.add`, `relation.remove`, `hint.confirm`), it sets the stored `title` of each same-repository target of that file to the target's current title: only the text of that scalar changes, in its own quoting; never a version, never a target in another repository (or an entry that names one), never an entry without `title` (none is added) and never the label of an inline reference (text counts to the version). An entry the same call sets (a new target, or one set anew, whose title was just read from the target's file) is left as set; only entries the file held before (`version` aside) are refreshed. A missing, ambiguous or untitled target and a title the writer cannot change in place (alias, anchored scalar, block scalar) are left as they are; all titles of a file go in one pass of the writer (`set-scalar` with `ifPlain`). Only files a command writes anyway are refreshed; a command that changes nothing writes nothing. The title comes from the element store the command read (passed to `writeElementFiles`), through its UUID index (O(relations of the written file), N-036). The `element.bulkUpdate` preview does not show the refresh. Implementation: `packages/core/src/model/relation-titles.ts`. The SR-027 AK1 wording („ändert sonst nichts an der Datei“) gets a new decision version with the migration (#326).

### Stable writing

- ReqSeq changes only the lines of the keys it changes (ADR-0007, writing frontmatter): existing key order, comments and formatting of untouched keys are kept byte for byte; new keys are appended in the order of the type's properties in the metamodel.
- Lists of relation targets are written as one flow mapping per line, so a Git diff shows one changed line per changed relation (SR-102).
- Line endings: LF on write; existing CRLF files keep CRLF. UTF-8; new files without BOM, an existing BOM is kept like CRLF (so line 1 stays unchanged, SR-102). A final newline.
- Text layout (#308): a new file is `---`, the frontmatter, `---`, one blank line, the text, a final newline; a file without text ends with the closing `---` line. The blank line separates and is not part of the text: commands show the text without it (`element.get`) and take it without it (`element.create`, `element.update`). A text equal to the stored one (line endings aside) changes no byte, so the text `element.get` gives can be passed back unchanged. Any other text is written with LF (then the file's line ending) and a final newline, in the layout the file has: with the blank line, or without it in a file written so by hand (unless the text itself starts with a blank line); a file without text gets it. One implementation: `bodyForText` and `elementText` in `packages/core/src/files/text.ts`. The version reads the whole body after the closing line (ADR-0005), and its normal form drops leading and trailing blank lines, so neither the blank line nor the final newline changes a version.
- Nothing about display order is stored (D-031, SR-075 AK3).

## Consequences

- Files stay readable in any editor and on any Git server (SR-010).
- Merges of different elements never conflict (SR-001 AK3); merges of the same element conflict only on the changed lines.
- The spec itself is a workspace in this format (`spec/`, #326): the Logseq UUIDs are the element IDs and the SR ID is the property `spec-id` with the meaning `identifier`, so `SR-036` stays a valid reference (#305).

## Rejected

- Relations in a separate index file: every new relation would touch one shared file (conflicts, N-039).
- Block-style lists of mappings for relations: three to four lines per relation, noisy diffs.
- Wiki links `[[…]]` for inline references: not CommonMark, not rendered by Git servers.

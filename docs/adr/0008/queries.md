# ADR-0008, part: Queries: incoming index, trace walk, filter

Part of [ADR-0008](../0008-in-memory-model-and-index.md). Read this part when you work on `model/incoming.ts`, `trace/`, `query/`; the decision itself is in the ADR.

- Incoming relation index (`model/incoming.ts`, #258): `buildIncomingIndex(store, metamodel)` collects, in one pass over the store and each element's own frontmatter keys, every relation item with a text `id` under a key that holds relations (`relationKey`: relation kinds and properties of kind `relation`, so validity and packages too) and every inline reference, by the UUID it names. A relation link holds its source, key, position in the list (`relationPath` makes the path when it is reported), the item object as parsed and the repository it points into (the item's `repository`, else the source's own; an item whose `repository` is not text is left out). `incomingTo(index, repository, id)` gives the links into one repository and UUID: relations first, then references, whose repository is decided as `resolveReference` resolves them (#250), a reference that is `ambiguous` among other repositories counting for each of them. The index is raw: relations of an element to itself and to a UUID that several files share are kept. `incomingFor(workspace, store, metamodel)` keeps one index per store (`incomingState`, a `WeakMap`, built again for another metamodel), carried over a change of the store ([file watching](file-watching.md), #267). Each list (the links into one UUID) is in store order of the sources, then frontmatter key order and items, or text order; the order of the UUIDs in the maps is not defined (a carried index adds new ones last), so `derivationEdges` gives its edges in no defined order (the cycles of `cyclesOf` and their elements are in store order whatever the edge order). Three readers that scanned the store before the index existed read it when the workspace holds the index of their store (#272): the SR-086 carry ([file watching](file-watching.md)), the hints that `element.setStatus` and `element.supersede` return for the relations to the elements they superseded (`supersededTargetProblems`, SR-072 AK2: the sources of the relations of relation kinds to their UUIDs, then the same rules as the scan on just those sources, about 7 ms instead of about 75 ms) and the successors of a superseded element in its view (`successionsFor`, SR-072 AK3: the `succession` links into its repository and UUID, ordered as the succession index orders them, well under 1 ms instead of building the succession index of a new store, about 22 ms). They never build it: a build costs 0.3 to 0.5 s, more than each scan. A server (`reqseq serve api`, `reqseq serve mcp`, later the app) holds the index from its start (warm-up, below), so there they always read it; a one-shot CLI command where no chain has run scans as before, and so does a reader whose metamodel would let a key of a relation kind hold something the index leaves out (a property with the same key, which the loader refuses). Measured on the generated workspace (50,000 elements, 200,000 relations) in a shared, loaded container: old and new path alternately in one process, 15 rounds, medians; without the index both paths are the same code.
- Trace walk (`trace/`, #258): breadth first from one element or a set over a function that gives the steps of an element (`walk`); each element once at its shortest depth with the edge it was first reached through (`via`, `pathTo`; a start stays at depth 0 also when another start leads to it), every step an edge (also into an element reached before), `maxDepth` (elements at that depth are reached, not expanded: `expanded` on each node), unresolved targets and `incomplete`, and leaves for the evidence of stage 4. Cycles are the strongly connected components of the walked subgraph with more than one element or an edge to itself, not back edges on the breadth-first tree path, which miss cycles entered through a diamond: first the vertices without an edge in are peeled off (Kahn; in a chain most of them), then Tarjan's algorithm (iterative) runs on the rest. A cycle that closes only beyond `maxDepth` is not seen. `cyclesOf(elements, edges)` gives the cycles of any graph, `derivationEdges(graph)` every derivation edge of the store with an available parent, from the index without a `targetState` each (SR-090); `derivationCycleProblemsState` (`trace/cycles.ts`, #102) reports them in `workspace.check`, without a carry hook. The derivation graph (`derivationGraph`) takes its relation kinds from the meaning `derivation` (SR-013); parents are the element's own items looked up with `targetState`, children the index's derivation relations into the element's repository and UUID, unresolved as `ambiguous` while several files there share the UUID (SR-088). Measured on the generated workspace (50,000 elements, 200,000 relations; a cloud container with 4 cores, noisy): building the index 0.3 to 0.5 s once per store, the chain from the first need (about 42,000 elements, 112,000 edges) 0.25 to 0.38 s, of which the cycle search 8 to 25 ms, an upward chain a few ms, the cycles of the whole store about 0.3 s.
- Warm-up of the incoming index (#227): a server builds the incoming relation index right after the load (`warmWorkspace`, before `reqseq serve api` listens; in the background for `reqseq serve mcp`), so the first chain after a start does not pay for the build (0.25 to 0.45 s at N-036; SR-082 AK4). This adds the build to the start that SR-082 AK1 measures (3 s with the cache; about 1.3 s on CI before). Building it in the background after the API listens was considered and not chosen: the build is synchronous and blocks the event loop for the same time right after listening, so the first `workspace.status` would answer that much later anyway. A larger change (a pull, more than `CARRY_LIMIT` UUIDs) still leaves the next store without an index until the next chain builds it. `trace.chain` pages its output (`limit`, `offset`, `total`, spec-frage #290): the walks stay complete, only one page of nodes and their edges, gaps and unresolved relations is built, since the whole chain of the largest need (about 42,000 nodes, 36 MB of JSON) takes about 0.2 s to serialise alone.
- Filter and selection (`query/`, #81, SR-069, SR-101): a condition (`filter.schema.json#/$defs/condition`) is compiled once into a predicate on element records (`compileWhere`): references (`resolveRef`, any case), views (`resolveView`), type sets with their subtypes, choice names (`findNamed`), regular expressions and meanings are resolved while compiling, and errors name the input field (`selection.where.all[1].op`). The selection (`resolveSelection`) is the conjunction of `ids`, `where`, `package` and `view` (the view rule, `variants/view-rule.ts`: the validity less what a variant excludes or replaces, SR-041, SR-043) in store order, one pass over the store; the rule's index of replacement and exclusion items is one pass per store and metamodel, kept with the store (no file read), and the rule of a variant is built from it once, O(replacements + exclusions), so a view test is a set lookup beyond the validity; `incomplete` while a listed repository is not here. Semantics: property conditions work on the values of a key (absent, `null` and `[]` are none, a list gives its items); `eq`, `ne` (not `eq`), `in` compare with `===`, `contains` is a text part ignoring case, `lt` to `ge` compare numbers with numbers and texts with texts (ISO dates as text), `matches` is a JavaScript regular expression with flag `u`; a choice may be given by its display name; a key that holds relations takes element references (`eq`, `ne`, `in`, `exists`, `missing`). Relation conditions take `kind` (a relation kind or a relation property), `meaning` or neither (every relation kind); `up` reads the element's items (`to` through `targetState`), `down` the incoming index (built only when a condition needs it), no direction either; `evidence` asks the evidence provider (`evidenceStatusState`), which also gives the verification status per view and the validation status; stage 3 has no records, so its default gives `open` to requirements and needs and no evidence, and stage 4 replaces it (#127, option 1). Relation conditions with `exists`: without `to`, every item that names a target counts, also one whose target is missing or not available (the relation is there; the check reports the target, SR-089); with `to`, only an available other end that meets it, so `up` with `to: {all: []}` counts the available targets only (#336). `text` (#80) selects what `element.search` finds for its query (from `searchIndex`, by repository and file); `emergent` (SR-035) asks `isEmergent` (`model/emergent.ts`: the property with the meaning `emergent` holds `yes`; `false` holds for every element that is not marked; no property with the meaning is `metamodel.meaning-unassigned`), the predicate the output and the verification status use; baselines are refused with `input.invalid` until they come; a schema operator without a branch in `compileLeaf` does not compile (`never` check). A compiled condition is for one run: it holds the states it was compiled against (store, short IDs, incoming index, evidence provider, views) and its `notes` only gain `incomplete`, so a saved filter or a bulk update (#83) compiles its condition again per run and never keeps a compiled one. A saved filter (`selection.filter`, SR-070) is read from its file on every call (a handful of small files) and joins the selection with its `where` and `view`; `element.list` without `sort` takes its sort. Measured by name through the catalog on the generated workspace (system requirements in draft, sorted by title, first page; `[SR-082/AK4]` in `test/perf/open-filter-chain.test.ts`, #228): about 185 ms in a local run (4 cores), the file read and the compile included. The short semantics of each operator are also in the descriptions of `filter.schema.json`, because agents read them there (in the MCP tool schemas); the selection part of an MCP tool has its own size bound for them (ADR-0009, #336), so they carry the semantics and leave out SR and decision references and notes for maintainers (SR-035). Such a note: `subtypes` has no `default` keyword, because defaults inside `oneOf` are not applied; absent means true. Measured with `element.list` on the generated workspace (50,000 elements, 200,000 relations, the index warmed): every element 25 ms, a type 35 to 40 ms, requirements without child 60 ms, with a parent of type need (a `targetState` per item) 160 to 200 ms, a regular expression on titles about 50 ms (first page of 200 built each time). `element.facets` (#425) counts the statuses and the property values of a selection in one pass over it and one over the store for its free-text rule (a text, number or date property gives its values only when it has at most `maxValues`, default 30, distinct values in the workspace and one is shared), so the app offers filter values without counting itself; relation and choice properties always give theirs. Measured on the same workspace, warm: all elements and the system requirements about 0.2 s (median of 5, load 5 to 6 on a shared machine; bound 500 ms). Counting the distinct values of free text stops after `maxValues + 1` (`distinctCapped`): keeping every title of 50,000 elements had cost more than the rest. The app asks `element.facets` with `selection.ids` of the shown element to know which of its values open a list (SR-132): the pass over the store for the free-text rule remains for every few-valued or absent text property of its type, so one element costs about 75 ms (median of 5, one system requirement, the same loaded machine as the 0.28 s of all elements; bound 200 ms, the opening budget of SR-082).

# ADR-0008, part: Search index

Part of [ADR-0008](../0008-in-memory-model-and-index.md). Read this part when you work on `query/search-index.ts`, `query/search-state.ts`, `commands/element/search.ts`; the decision itself is in the ADR.

- Index (`query/search-index.ts`, #323): MiniSearch 7.2.0 (MIT, no dependencies, no network access; ADR-0015), one document per element record, keyed by repository and file (files may share a UUID, SR-088). Fields: `title` (the property with the meaning `title`, D-059), `text` (the Markdown below the frontmatter without the destinations of links and images: the reader sees the label, and the `reqseq:` destinations of inline references would add four times the words of the texts at N-036) and `properties` (the values of every other key except `id` and the keys that hold relations, also inside lists and mappings, dates as ISO text, and for a choice also its name; type and status by the name the metamodel gives them, else by the key as written, #80: SR-068 searches "Properties", and the tool shows those names; not also by the key, which mostly holds the same words and cost the build about a fifth more time). IDs are not indexed (150,000 random tokens would cost about 110 MB and 1 s at N-036); a query word in the form of a short ID (`SR-46fb54`, also with 12 digits) is compared with the records (type prefix and the end of the UUID), a word of at least 6 hex digits finds the UUIDs that begin or end with it, and a word that is the whole identifier of an element (the property with the meaning `identifier`, `SR-036`, #305; per index, a map built on first use) finds it; exactly, in any case, never fuzzy, and independent of how many digits the shown short ID has (SR-084). The identifier is a property value too, so its words match as words as well. Words are split at every character that is not a letter, mark or digit and compared in NFC and lower case; fuzzy search tolerates one edit in a word of 4 to 7 letters, two from 8 (MiniSearch's fraction 0.2), none below 4 and none for a query word with a digit (a number, a version or a part of an ID: `0000b3` would find `0000b1`; a word of the index with a digit can still be the typo of a query word without one, `sensorx` finds `Sensor1`); prefix search from 2 letters; a title match counts twice (BM25).
- `searchElements(index, query, options)` (consumed by `element.search`, #80, and the `[[` link search, SR-066): `fields`, `within` (the records of the selection of an active view or filter, `Selected.elements`, SR-068 AK3, compared by repository and file, so of two files with one UUID only the selected one counts, SR-088; `total` counts only hits inside it), `combineWith` (`and` by default), `fuzzy`, `prefix`, `offset` and `limit`. The words without an ID form are one query whose words must all match; it is scored by `scoreWords` (`query/search-scoring.ts`, #110, SR-098), which scores as MiniSearch 7.2.0's `search` does on the same index (the same terms: exact, prefix and fuzzy in MiniSearch's order and weights; the same BM25 expression and order of additions; the same `quality`; the matched words and fields of a page's hits as MiniSearch merges them), but in typed arrays per short ID instead of a result object per document and word, and describes only the page; it reads MiniSearch's protected index members, so the version stays pinned and `search-scoring.test.ts` compares it bit for bit with `search`; `combineWith: "or"` and an engine with discarded documents (a cache-loaded index after a carry, whose words MiniSearch drops while it searches) go to MiniSearch itself. The record, key and store position of each short ID are kept in arrays per index and engine change, and the first page is found without sorting all hits (pages up to 1,000; the order is strict, so the page is the same). ID matches come first, then score rounded to 6 significant digits (MiniSearch's scores of equal documents may differ in the last bits between a fresh, a cached and a long-carried index, whose average field lengths are kept incrementally; the rounded score is also what hits give, so every access orders alike, SR-080), then store order. Only the page is described (fields and matched terms of each hit), for SR-098. `matchingKeys(index, query)` gives the keys of every hit without sorting or describing them, for the filter condition `text`.
- `element.search` (`commands/element/search.ts`, #80, SR-068): resolves the selection (SR-068 AK3: a view, `where`, a package, IDs, later a saved filter), then awaits `searchIndex` and searches in the same turn, `within` the selection when it is narrower than the store or the index's store is another (swapped meanwhile: a new file the selection never saw is no hit); the hits are records of the index's store (a store swapped meanwhile is newer; the selection restricts it by repository and file), named with the short IDs of the selection's store. Output: one page (`limit` default 50, at most 500, `offset`; ADR-0009) of hits with UUID, repository, short ID, identifier, type, status, title, score, fields and matched terms, `total` and `incomplete`; no version or text, so a page reads no file. `fields` restricts the search (the `[[` search of SR-066 asks for `title` and `id`). Before the index is ready a search waits for its build (about 7 to 10 s at N-036, longer under load): every access gives the same result, never a partial one; SR-098 AK1 is taken to hold once the index is ready (warm server); the window after a start is spec question #388 (#110). The filter condition `text` (`condition.ts`) selects what `element.search` finds for its query, compared by repository and file.
- Built per store and metamodel (`searchIndexState`, `query/search-state.ts`): the store keeps no text, so the build reads every element file again (`readElementBodySync`), in the calling thread, in slices of 5 ms with a turn of the event loop between them (as the current versions). A file changed since the store read it is indexed as it is now when it still holds the same UUID, else without text, and such a build is not cached. A change of the metamodel or layout resets it. A build or carry stops (`SearchBuildCancelled`) when its workspace is closed or its value is no longer the state, so a reset or the exit of a process never waits for a whole build. One that no search waits for pauses while a command runs on the workspace (`Workspace.busy`, counted by `invoke`; asked at every turn, then every 10 ms), so a command waits for at most the slice that runs; `searchIndex(workspace)`, which a search calls, lets it go on (the state itself is not exported from the block, since a command that awaited it directly would pause its own build). A search whose build stops because the state was reset meanwhile (a watcher batch that changes the metamodel or layout) waits for the next build, up to 5 times, while the workspace is open. A server starts the build only after its warm-up and one more second (`warmSearchIndex`, `SEARCH_WARM_DELAY_MS`), so nothing of the index lies on the way to its first answer (SR-082 AK1); it counts as a server from the start of the warm-up, so a search during it (`reqseq mcp` and the app do not wait for the warm-up) also builds without the cache.
- Carried over a store change (`carrySearchIndex`, #184; SR-007 AK2): the documents of the changed files are removed and the files that hold an element now are read again and added. Unlike every other carried state, the MiniSearch object is changed in place, not copied (a copy costs about as much as a build): the documents are read first and the object is changed in one synchronous step, so a search sees it before or after the change; the index of the previous store shares the object and filters its hits to its own records. A change of more than `SEARCH_CARRY_LIMIT` (10,000) UUIDs builds the index again. The engine keeps every document it added (`SearchEngine.documents`), so a carry removes the old ones exactly (`MiniSearch.remove`) and the carried index equals a fresh build, scores included. MiniSearch's vacuum is never started (auto vacuum off): it walks the term tree in batches with pauses, and a document added or a search made in a pause (a search drops the words of discarded documents it meets) changes nodes the walk stands on, and MiniSearch 7.2.0 then throws in its timer (found by the SR-007 AK2 test and in review). An index loaded from the cache has no documents: its carries discard them, and searches drop their words as they meet them, which is safe without a vacuum; scores may differ a little from a fresh build until then.
- Measured on the generated workspace (50,000 elements, 200,000 relations, quiet local runs; `test/perf/search-index.test.ts`): build about 7 s with no turn of the event loop blocked longer than about 35 ms; heap about 200 MB with the documents kept for carries (about 30 MB of them), about 355 MB for a synthetic index of 50,000 texts of 150 words with its documents (about 310 MB without); `element.get` while a server builds the index 8 to 35 ms (paused, against 220 to 265 ms before the build paused for commands); with MiniSearch's `search` typical queries took 20 to 240 ms and very common words, two-letter prefixes and whole titles up to 400 to 500 ms; with `scoreWords` (#110) every term of the `[SR-098/AK1]` test is below 60 ms; a carry of one saved file about 150 to 170 ms, of 1,000 files about 2.2 to 3 s with the store update (SR-007 AK2: 10 s). `element.search` through `invoke` (the first 50 hits, medians of 7 runs on a shared container with 4 cores, 15 GB; `[SR-098/AK1]` in `test/perf/search-speed.test.ts`, #110): before `scoreWords` two letters 264 to 337 ms, a word of every text 290 ms, a whole title 277 ms, three words of every text about 470 ms (single runs up to 860 ms); after it 15 to 60 ms for every term (two letters and words of every element 25 to 45 ms, three words of every text about 55 ms, typos and topic words 15 to 25 ms, IDs 4 to 14 ms), with single runs up to about 330 ms under garbage collection; all 638 outputs of `element.search` and the condition `text` for 51 terms in 9 variants (pages, fields, selections) were the same before and after.

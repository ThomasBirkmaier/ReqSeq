# ADR-0008, part: File watching

Part of [ADR-0008](../0008-in-memory-model-and-index.md). Read this part when you work on `model/watch.ts`, `model/watch-tree.ts`, `model/watch-change.ts`; the decision itself is in the ADR.

- macOS and Windows: `node:fs` `watch` with `recursive: true` on every available repository folder (FSEvents, ReadDirectoryChangesW; a repository nested in another is seen through the outer one).
- Linux: one plain `fs.watch` per folder (`FolderTree`), not `recursive`. Node emulates `recursive` on Linux with one inotify watch per file and folder; a file replaced by a rename (an atomic save by vim, JetBrains IDEs or ReqSeq's own `writeFileAtomic`, a delete and re-create, a checkout) is then never reported again, and at 50,000 files the watch costs about 0.6 s of blocked event loop, about 100 MB and 50,000 inotify watches. A folder's watch reports every name in it however the file was written, so one watch per folder is enough: about one inotify watch per folder. Left out are `.git`, `node_modules`, folders of the `ignore` globs (unless the metamodel lies in them), folders of other repositories of the workspace (they have their own tree) and folders with a `.git` entry; a new folder named by an event is watched with its subfolders, and the watches of a folder that is gone are dropped. A folder that vanishes during the walk is skipped; a broken folder watch is dropped and its folder checked and watched again, without reading the layout again. A watch belongs to one folder: each watch keeps the `dev:ino` of its folder from a stat right after it attached, and a walk that finds the path gone, no longer a folder or with another inode drops the watch and watches it anew (a folder deleted and created again, replaced by a move, or emptied and filled by a checkout). Linux names the watched folder itself when it is deleted or moved away (`IN_DELETE_SELF`, `IN_MOVE_SELF`); a new folder in its place can get the same inode, so such an event drops the watch at once and walks the folder again. A repository folder that is gone reads the layout again, as a broken recursive watch does on macOS and Windows; the repository is then not available, and a clone in its place is seen after the next layout change or restart. All walks of a tree run one after the other; a folder that got a new watch is reported once more, for files created before the watch attached. A start that a newer layout overtook stops after its next step and its watches are closed; events of a layout that is no longer watched are dropped. Own code instead of chokidar v4 (ADR-0015): the per-folder tree is about 240 lines, chokidar would add a dependency and its own Linux emulation with the same replaced-file questions.
- A folder that cannot be watched (`ENOSPC`: the inotify limit, raise `fs.inotify.max_user_watches`; or a refusal) is reported as a `workspace.not-watched` warning in `workspace.status` (`watcherProblems`); its changes are not seen until ReqSeq restarts or the layout changes. Commands still work. Only a process with a watcher (API, MCP server, app) reports it; a one-shot CLI command has no watcher and reads the files anew.
- Events under `.git` and `node_modules` and ReqSeq's temporary files are dropped; so are other files than `*.md` unless the path is a folder or gone (images too: the current versions check them on use, see [current versions](current-versions.md)), or lies at, below or above an evidence location. A path there (a record, a JUnit file, a folder) resets the evidence read and with it the index and the status, unless every such path of the batch is a file this process wrote (`evidence.record`, `evidence.enrichJunit`) and still holds the bytes it wrote (SHA-256); a nameless event in a repository that holds an evidence location resets it too. A batch that changed only evidence files is told as an `elements` change with empty lists (#785). Events are debounced (100 ms after the last, at most 1 s after the first) and processed in batches, one after the other, so a pull with 1,000 changed files is one or a few updates.
- The workspace file or `.reqseq/local.yaml` changed: the old watches are closed, the layout is reset (and with it everything built on it) and the new repositories are watched; events sorted with an older layout are dropped. A path in the metamodel folder: the metamodel and the state built on it are reset, without rewriting any element (SR-015). The layout gives an existing metamodel folder as its real path (the name as stored, as for the repositories); events are compared with it in NFC and lower case, so a spelling other than `realpath`'s still counts (a twin folder on Linux costs an extra reset). An event at the folder or a folder above it (renamed, moved, deleted, created), or in a missing folder, reads the layout once and compares it, so its real path and existence stay current (#231). A metamodel folder reached through a link out of its repository, or missing below a linked folder, is not watched. A broken recursive watch (macOS, Windows) reads the layout again and watches anew. An event without a file name (the OS dropped the names of a burst: ReadDirectoryChangesW overflows its small buffer, 4 KB in libuv, on a pull of a few hundred files, about 20 times for 1,000 files on windows-2025, and libuv then reports one change without a name; #226) checks every repository below the watched folder file by file, reads the metamodel again when its folder lies there, and, when the main repository lies there, reads the layout once and compares it with the watched one, so a workspace file changed by the same pull is not missed (and a repository that appeared or disappeared is noticed with it).
- Element paths: the store is updated, not read again (`updateElements`). Per repository with changes, the Markdown files are listed again (one walk, no reads; it applies the ignore globs, nested repositories and links like the full read), unless the changed paths alone tell what the walk would list (#215; `listedWithoutWalk`, `pathState`): the OS named the paths (not all), at most `WALK_SKIP_LIMIT` (64) of them, the repository had no listing problem before, and each path is a file of the store that the walk still lists (checked along its path with `listsFile`: every folder above a real folder without a `.git` entry, not ignored or nested, spelled as on disk), a file of the store that is gone from a folder the walk goes into, a new `*.md` file the walk lists below which no file of the store lies, or a gone path that is no file of the store and no folder above one (an editor's temporary file; compared ignoring case and normal form) and has no name Windows abbreviates or changes (`REQUIR~1`, a trailing dot). Anything else (a folder, a link, another spelling, `.MD`, an error such as `ENOTDIR` or `EACCES`) walks. The watcher names the folder of a `.git` entry created or removed below the root, and keeps a link that replaces a folder, so both walk; a `file.stale-temp` warning is found only by a walk, so it may appear one walk later than before. Files that are gone are dropped (also one deleted between the walk and its read), new files are read, files named by an event are read again, files below a changed folder (or all, when the OS gives no file name) are read again when size or mtime differ. A file read again with the same snapshot (SHA-256, size, mtime) keeps its record; the result equals a full read. The store is then patched, not assembled anew (`patchStore`, #215): the `files` of a changed repository become a `PatchedMap` in path order over the files before (`model/patched-map.ts`: an immutable overlay over a shared base, never changed; from `max(1,024, size / 16)` overlay entries a patch builds a new base), `elements` is copied once (50,000 pointers, below 0.5 ms) and patched at the places of the records that went and came (binary search by repository index and path), `byId` is a `PatchedMap` in which each touched UUID's list is built again in store order (a new array); a hot read loop (a lookup per relation or per element: `resolveTarget`, `resolveId`, the identifier index, the derivation edges and walks, the neighbourhood, the matrix) reads it through `recordsById` (`model/by-id.ts`), which from `plainAt` lookups (`max(1,024, size / 8)`) on reads a plain view of it, a new `Map` with a copy of each list, built once (about 25 ms at N-036) and kept, so a carry over one changed file never builds it; a store patched from one with a view takes that view over and changes it in place (`handOverView`, O(changed)), and the store before builds a new one only if it is read hot again. Read directly, a patched `byId` made `workspace.check` 10 to 30 % slower: the call site saw two map classes and paid two lookups, and the lists of a store read long before lay far apart in memory (a full read allocates them anew); `problems` and `nonElements` are kept when every repository has the same `listing` object (a walk that finds the same problems keeps it) and every touched file contributes nothing or an element without warnings before and after, else they are collected again from the contents. From `PATCH_LIMIT` (1,000, `model/patch-limits.ts`) touched files (a pull, a bulk write) the store is assembled as a full read does. The change goes through `applyStoreChange(workspace, change)`: one queue per workspace, `Workspace.replace` (compare and set) to install the new store, and a retry on the newer store when the store was replaced meanwhile. Replacing carries the states built on the store over the change or resets them (below); with nothing changed the old store and those states are kept. A store nobody has read yet is left alone. A failed update resets the store, so the next command reads it in full. A repository that is missing at start is watched only after the layout changes.
- ReqSeq's own writes (`element.create`, `element.update` and later writing commands, #166) update the store the same way, without reading any file: `recordWrites(workspace, layout, files)` takes every file a command wrote, `withWrittenFiles` builds each file's record from the bytes just written and the snapshot of the write, patches them into the repository's files (a `PatchedMap` in path order: new files are sorted once, #729), patches the store once (`patchStore`, as above) and installs it through `applyStoreChange`, so a save waits behind a watcher batch that is running. The states built on the store are carried over or reset as for the watcher (below). When the watcher then sees a file, it reads it again and finds the same snapshot, so nothing is applied twice; a write the watcher saw first changes nothing. Whenever the result could differ from a full read (`StoreFallback`: the store holds a file in another state than the one replaced, a new file that the walk would not list under its repository, a repository with folders that cannot be listed, or a layout read again since the write), the store is reset instead; any other error is passed on.
- The watcher tells who listens what a batch changed (#331; `WorkspaceWatcher.onChange`, `model/watch-change.ts`), so the app shows external changes (SR-007) and can show live which elements changed outside it (the requirement for that is still to be exported from the spec graph, #326): once per batch that changed the model, after the change is in place (the store installed through `applyStoreChange`, or the states reset and the new repositories watched), on the chain of batches, so calls come in order and a listener that reads the workspace sees the new model. A `WorkspaceChange` is plain frozen data that the app's core process posts to its windows as it is: `scope` `elements` (the store was updated), `metamodel` (the metamodel is read again on its next use, so every element may show differently) or `workspace` (the layout is read again, the store was read in full, `readsInFull`, or it was reset after a failed update: everything is read again), and `elements`, the UUIDs whose record came (`added`), went (`removed`: a deleted file, one that is no longer an element, a changed UUID; SR-007 AK3) or is another record (`changed`: content, a move, a copy), each sorted; empty for `workspace`, and for a batch that changed only files that are no elements (the findings may differ). The UUIDs are those of the records that are other objects (`storeUpdate`), each looked up in `byId` before and after: from the touched files of a patched store (#215), else one pass over the files of each changed repository, as for the carry of the states built on the store, plus one lookup per changed record; a pull is one or a few calls, as it is one or a few batches (SR-007 AK2). A file read while it is being written (a pull still running when the 1 s of a batch are up) can count as no element in one batch, its UUID `removed`, and be `added` again in a later one: a consumer must not drop or close an element for a single `removed`; the last list a UUID appears in, or the workspace as it reads, counts. A batch that replaced nothing (`.git`, other files, the same snapshot, a store nobody read) calls nobody, nor does a closed watcher (`close` drops the listeners, so a listener that closes it stops the ones after it). The watcher does not wait for a listener; one that throws or whose Promise rejects stops neither the others nor the watcher. ReqSeq's own writes (`recordWrites`) are not reported: the command that wrote knows it (the app sends `written` to its windows itself), and the watcher then finds the same snapshot; writes of another process (the API server in Electron's main process, a CLI command) reach the watcher as file changes and are reported. It is no catalog command (ADR-0002): the catalog holds functions a caller asks for with an input and gets an output from, on every access; this is a push from a process that keeps a workspace open. A one-shot CLI command has no watcher, the API and the MCP server answer requests and their clients ask again (each command reads the current model), and the event carries nothing a command does not return (UUIDs), so every access still gives the same result (D-029, SR-080). Should an API or MCP client ever need to be told, a server-sent event of the API or an MCP notification would forward this event, not a new function.
- States built on the store are carried over a change instead of being built again (#184). The store's maps (`files`, `byId`) and the maps carried over a change may be a `PatchedMap` (#215); a hot read loop over one of them reads a plain view (as `recordsById` for `byId`): code reads them as `ReadonlyMap` only, never tests `instanceof Map`, never clones them or posts them to a worker, and copies none in full on a carry path; the order of the UUIDs in `byId` (and in the maps keyed by UUID built from it) is not defined after a change, so code that needs an order sorts or merges by file. `Workspace.replace` is still compare and set; after it installed the new store it gives every dependent with a `carry` hook, dependencies first, its next value, provided every dependency of it that depends on the store was carried too, and resets every other dependent. `applyStoreChange` knows what changed: a `StoreUpdate` names the files whose record is another object in the new store and the UUIDs of those records (`updateElements` and `withWrittenFiles` keep every other record the same object); for a store `patchStore` made from the store it replaces, the update comes from the touched files alone (#215, O(changed)), else from a diff of each repository whose contents are another object. `carryStoreUpdate` hands it to the hooks; a store replaced any other way, or one without `repositories`, resets the dependents. The short IDs build again only the groups (last 6 digits) of the changed UUIDs (`updateShortIds`); the findings of SR-015, SR-016, SR-085, SR-152 and SR-171 find and locate the changed files only and keep the located problems of every other file, merged in store order without a walk over all elements (`carryProblems`); SR-088 looks again at the files of the changed UUIDs; SR-086, when a changed UUID came, went, or changed the repository or type of a record, also at every element whose own UUID or a target under a key with a rule lies in the short-ID group of a changed UUID (its target or a short ID in its message may have changed): with the incoming relation index of the store before the change in the memo (#272; it holds every relation of an unchanged file as it is now), the records whose UUID lies in such a group and the sources of the relations under a key with a rule to a UUID that does, found by a scan of the index's keys and the store's UUIDs (a short ID depends on every UUID of its group, also one no element has, so this part stays a scan, of about 100,000 strings), and merged as a list without a walk over all elements, about 22 ms with the findings; without the index a scan of the frontmatter in memory and a walk over all elements (about 40 ms for 200,000 relations in quiet runs, about 110 ms in the same loaded runs), and otherwise (the usual save of a title, text or property) at the written files only. Missing targets (SR-089, which also depend on unreadable files; a carry hook added later must also look again at every source whose relations or inline references point at a UUID of a changed file), superseded targets (SR-072, successors across elements) and superseded validity (SR-040) are reset as before; only `workspace.check` reads them. The succession index of the element view (SR-072 AK3, `successors.ts`) is kept per store and not carried: the first view of a superseded element after a change of the store builds it again (about 23 ms at 50,000 elements and 200,000 relations), then each such view is a lookup; while the workspace holds the incoming relation index of the store (carried over the change), the view reads that instead and builds nothing (#272). The incoming relation index is carried (#267; `carryIncomingIndex`): when the store that is replaced has an index in the memo, the hook adds the index of the new store, built from the old one: the links whose source lies in a changed file are dropped, the links of the records in those files now (the records of the update's UUIDs that lie there, before and after) are merged into each list of a UUID they name, in store order (repository order of the workspace file, then file path), every other list and link object is kept; a store without an index gets none. A server holds the index from its start (warm-up, see [queries](queries.md)), so in `reqseq serve api` and `reqseq serve mcp` every save pays the carry (about 30 to 50 ms at N-036); a one-shot CLI command pays nothing extra until a chain has run. At N-036 the carry costs a fixed 30 to 50 ms (copying the two maps of up to 50,000 UUIDs) plus about 0.1 ms per changed record (0.13 to 0.25 s for 1,000), against 0.3 to 0.5 s for a build. It runs inside `Workspace.replace`, in the thread that serves commands, so it is done only while the update names at most `CARRY_LIMIT` (1,000, the read pool's threshold for a watcher batch) UUIDs; after a larger change (a pull, a checkout: 5,000 records cost about as much as a build, all 50,000 about 1 s) the new store gets no index and the next chain builds it (#273). A chain right after a save (trace context and walk) took 0.11 to 0.17 s in local runs, after the first chain of the process (0.30 to 0.41 s, before the walk is optimised by the engine) (SR-082 AK4, `test/perf/open-filter-chain.test.ts`). Building it in the background after a store change instead was rejected: it would block the thread of a server for the whole build after every save. The verification status state (`verificationState`, SR-031, SR-034; #698) is carried while the incoming relation index was carried with the change (so not after a change of more than `CARRY_LIMIT` UUIDs): the hook takes the new store and the memo of the index inside `Workspace.replace`, never later, so two changes in a row each pair their own store and index; it keeps the current versions it has read, the walks below the elements shown and the results of the evaluator, without those of the records of the changed UUIDs (before and after, twins included), of the records that embed images or had no version (the watcher does not report images, so these are read again at every change), and of all their ancestors before and after the change; when the variants change, or the state has no children (a metamodel that is not valid or has no derivation), it is built afresh from the change. Opening the top of the tree after a change of one file then computes again only the changed element, the records that embed images or had no version, and their ancestors, instead of the whole walk below it (about 8 ms instead of about 480 ms at N-036; the image path is not measured there, the generated workspace has none); the carry adds about 35 to 45 ms to the store update, above the 30 ms the #698 plan set, accepted by the lead for this change since no requirement limits the time of the store update, with a cheaper copy as follow-up issue #733 (`packages/core/docs/evidence-status.md`, rows of `test/perf/evidence.test.ts`). A carried value is derived from the old one, which is not disposed and not changed, so a command that still holds the old one keeps a consistent view. Each carried state equals what a fresh build gives (tests compare them after saves, creates, status changes and watcher batches). Measured on the generated workspace (50,000 elements, 200,000 relations), with every finding state built before (an API server after `workspace.check`): a save of a title takes about 90 ms (about 80 ms when the states are reset instead), opening an element right after it about 4 ms instead of about 100 ms (the short IDs built again), and the next `workspace.check` about 0.9 s instead of about 1.5 s.
- The store and the states built on it may be swapped while a command runs. A command that needs one consistent view reads the store once and derives what it needs from that object (`buildShortIds(store.byId, metamodel)`, `duplicateIdFindings(store)`) rather than reading several states one after the other.

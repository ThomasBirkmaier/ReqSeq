# ADR-0008, part: Current versions, sort, single-element paths

Part of [ADR-0008](../0008-in-memory-model-and-index.md). Read this part when you work on `model/current-versions.ts`, `query/sort.ts`; the decision itself is in the ADR.

- **Current versions** (#259; `model/current-versions.ts`): the current version of every element (ADR-0005: from its file and the images its text embeds), which SR-025 compares the stored versions of relations and inline references with (later also SR-026, SR-092, SR-031). A workspace state (`currentVersionsState`, read through `currentVersions(workspace)`), built on first use, once per element store, in the calling thread: each element file is read again with blocking calls (`readElementBodySync`, with the same checks as the full read; while the bytes still have the SHA-256 of the store's snapshot only the frontmatter split runs, no YAML parse), the images are looked up only for a text that embeds one (one `ImageMemo` per run), in slices of at most 20 ms (and 500 files) with a turn of the event loop between them, so a server keeps answering (SR-082, N-036). A file changed since the store read it counts as it is now, as for `currentTarget`; its entry also holds the element as the file holds it now (`element`, optional), so a list shows data and version that agree (SR-023). An element gets no version (`unknown` with its reason) and nothing fails when its file no longer holds it (`not-in-file`), an image cannot be read (`image-unreadable`) or a value that counts has no normal form (`not-computable`: `.inf`, `.nan`, ADR-0005); every other error is a bug and is passed on. Measured at N-036 (50,000 elements, 200,000 relations, files in the page cache): 4 to 5 s in local runs of the performance suite (4 cores, 16 GB: 3.9 s with the whole suite, 5.0 s with the core suite alone); about half of it is reading the files again (of that, `lstat` and the link checks about a third), most of the rest computing the versions. The same with `fs.promises` reads (the libuv thread pool) took about 11 s. A pool of worker threads would save about 1.5 s on 4 cores and nothing on 2, for a second worker protocol and the synchronous image lookup; rejected for now. Not cached ([cache](cache.md)): the cached start (SR-082) needs no version, and a check pays the build once against the 60 s of SR-020. The state depends on the store and on the metamodel (which properties count): a change of the metamodel, or of the layout with its `ignore` globs, resets it. A change of the store through `applyStoreChange` (watcher batches, `recordWrites` of every writing command) is carried (`carryStoreUpdate`): each record that is another object in the new store gets its version again, every other entry is kept (a few ms at N-036 after a save).
  - Images are no Markdown files and the watcher drops their events ([file watching](file-watching.md)); a version kept across its batches is therefore checked on use, not reported by the watcher. Each version keeps what the lookup of each image found (`ImageSeen`: size and mtime of the file, missing, or in a nested repository), and `currentVersions` checks a kept state before it returns it (`checkImages`, `imagesUnchanged`): the lookup of ADR-0005 again, name by name with a fresh memo, so a rename to another case, a new `.git` entry above an image or a twin name in the other normal form counts, and an `lstat` of each file found, nothing hashed; the elements with images are checked 32 at a time. The entries of elements whose images changed, and every entry without a version (its file or images may be readable again), are computed again; when one comes out different, the state is replaced (compare and set), which resets the states built on it, else it is kept. A state built by the same call is not checked again, and callers that come while a check runs share it. The check costs one listing per folder on an image path and one `lstat` per image, nothing for elements without images: a later use at N-036, where the generated workspace embeds no image, takes well under 0.1 s; a workspace where many elements embed images pays about one `lstat` per image on each use (not measured yet). Reporting image files from the watcher was rejected: it would pass every event of a file that is not Markdown (build output inside a repository) to the store's queue, need an index from image paths in every spelling to the elements that embed them, and still miss a new `.git` entry above an image, whose events the watcher drops.
  - Sort and derivation tree (`query/sort.ts`, #87, SR-075, D-031): `element.list` sorts the whole selection by its `sort` keys, then builds the page; nothing about the order is ever written (AK3). Keys apply in order, ties go to the next key and then to the store order. `id` is the short ID (text order: SR-10 before SR-9), `identifier` (#418) is the property with the meaning `identifier` in natural order (`compareNatural`: digit runs by number, SR-9 before SR-10 before SR-100; numbers equal, then the folded text, then the text as written; no `Number` or `BigInt`, so a run of any length is exact; no `Intl.Collator`, whose result depends on the ICU data of Node and Electron and on the locale, D-029) and an element without one (or a metamodel without the meaning, no error) follows ascending by its short ID as `id` orders it, `desc` reverses both groups; the reserved name shadows a property with the key `identifier` (a workspace that sorted by such a property changes order, as for `title`), non-ASCII digits count as text; only `fold` (NFC, lower case) depends on the Unicode data of the runtime, as the text sorts do; `type` and `status` follow the metamodel order of the types and statuses, `title` is the property with the meaning `title` (`metamodel.meaning-unassigned` without it), any other key sorts by its first value (choices of a `choice` property in metamodel order, then numbers, texts ignoring case by code units after NFC and lower case, booleans); no value (absent, `null`, `[]`, a mapping, NaN) is last in both orders, `desc` reverses the rest; a key that holds relations is `input.invalid`. `hierarchy` may only be the first key and only ascending; the keys after it order the roots and the elements below each parent. The tree holds each element of the selection once (spec-frage #354, option 1): parents are its own derivation items whose target is available and in the selection, as the chain goes up; breadth first from the elements without such a parent, each element hangs below the parent that reaches it first (shortest depth, then sort order); the cycles that no root reaches and nothing else left over leads into (`cyclesOf`) become roots at their first element in sort order, and the rest hangs below them; the list is the tree depth first, and the output's `tree` gives depth and parent for each element of the page. The parents of every element of a store are read once per store as store positions (`parentPositions`, `trace/graph.ts`, in a `WeakMap` by store, with the metamodel they were read with; a change of the files makes a new store, so nothing is carried), without the incoming index, so a one-shot CLI call does not build it; a tree call then walks the store and the selection side by side and links the elements by array positions. Looking up the 128,000 parents of N-036 as records on every call cost several times as much (0.4 to 0.75 s against 0.08 to 0.16 s for the tree in a loaded container). Measured with `element.list` on the generated workspace (50,000 elements, 200,000 relations, a loaded container with 4 cores at load 7 to 12; `test/perf/element-list-sort.test.ts`): sorted by title 0.11 to 0.25 s, by type and then identifier 0.16 to 0.18 s (asserted at 500 ms, SR-082 AK4; identifiers of 3 to 5 digits), as a tree 0.08 to 0.16 s, as a tree with siblings by title 0.17 to 0.27 s, the first tree of a store (reading its parents) 0.33 to 0.39 s, first page of 200 each.
  - Lists (`trace.related`, SR-023; later `element.list` and the data export): `currentVersionsOf(workspace, records)` gives the versions of one page only. With a kept state it takes that state's entries of the page and checks only their images (`stale`, as `checkImages` does for the store), computing the stale ones again without changing the state; without one it reads only the page's files and builds no state, unless the page is at least a quarter of the store, which builds and keeps it (`currentVersions`). An element without a version is listed without `version` and with one `file.faulty` warning in its `problems` (`listElements`); it never fails the list.
  - Single-element paths (`element.get`, the element hints of SR-026) never wait for the whole build: they use the state only when its build has ended (`currentVersionsIfBuilt`, `settledValue`: never waiting for a running build) and otherwise read the versions of the targets they need from their files (`currentVersionsOf`; SR-026, #38: `element.get` shows the element's outdated relations and evidence this way). `currentVersionsOf` looks up only the records it is given in the kept state (one map lookup each, not a walk over its 50,000 entries) and checks only their images; a list or view of K elements costs O(K) when the state is built, and K file reads when it is not, unless K is a quarter of the store, which builds the state. A page of at least a quarter of the store that is asked for while a build is running goes through `currentVersions` and so waits for that build and its `checkImages` over the whole store. The cycle hint of one element (SR-026 AK3) likewise comes from the kept cycle state when it is built, and otherwise from a walk up from the element through its own relations (`elementCycleFindings`, as `upwardGraph` for SR-067): it never builds the incoming index (0.3 to 0.5 s) or the cycles of the store. Starting the build in the background right after a server has loaded (`warmWorkspace`) was considered and left to SR-025 (#37) and SR-026 (#38), and is not done by either (open): the build runs in this thread, so until it ends every open of an element waits up to one slice per await, which the tagged SR-082 AK3 tests (open within 200 ms after the load) would have to show is acceptable.

# ADR-0008, part: Model cache

Part of [ADR-0008](../0008-in-memory-model-and-index.md). Read this part when you work on `model/model-cache.ts`; the decision itself is in the ADR.

- **Cache** per path of a working copy in the OS cache folder (`<cache>/reqseq/<sha256 of the canonical workspace path>/`; canonical: absolute, symbolic links resolved with `realpath`, and lower case on Windows, so two names of one folder share a cache), never in the repository; copies at different paths never share a cache folder (SR-081 AK2, "je Kopie" read as "je Pfad der Kopie"). On macOS `realpath` also gives the name as stored, so another case or Unicode normal form of the name (APFS ignores both by default) leads to the same folder; on Linux these are other folders. Because the cache belongs to the path, a copy moved elsewhere gets a new cache folder, and a new copy at the old path (a fresh clone) inherits whatever the old copy left there. Such leftovers are harmless only because every entry is checked against the files before it is used: a stale `api.json` is replaced (ADR-0009), and the model cache (SR-082) checks each file entry against its file and must check the serialised search index as a whole (for example against the set of file entries it was built from), never trust it per file. An old copy's API that still runs makes a `reqseq serve api` of the new clone at its old path refuse until it stops (ADR-0009). Cache folders of moved or deleted copies are not collected (stage 1). The model cache (`model.json`, `model/model-cache.ts`, SR-082) holds, per repository (name and canonical folder), what each file that parsed contributed to the store (frontmatter, classification, warnings) with its snapshot (size, mtime, content hash), plus the inode and change time of the file when the cache was written (as Git's index does: a file rewritten with the same size and mtime, by `cp -p` or a restore, gets another change time or inode; from `lstat` with `bigint`, as decimal strings, so a 64-bit file ID on Windows, often above 2 ** 53 where a JS number loses its low bits, stays exact: the inode unsigned, since Node gives one of 2 ** 63 or more as a negative bigint, and the change time in nanoseconds, a file changed before 1970 left out; the mtime is compared as `mtimeNs` turned into ms the way Node computes `mtimeMs`, so the snapshot keeps the number form; format 3, #232). Versions are not part of the store and are not cached (#259: the current versions are computed on first use instead, see [current versions](current-versions.md)). Should they ever be cached, this rule applies: A cached version is valid only while the element file and every image it embeds (ADR-0005 "Files") still have the size and mtime it was computed with, and every missing image is still missing; the entry therefore records them too. Presence is checked with the lookup of ADR-0005 (name by name, spelled as on disk), not with a plain `stat`: a rename to another case, a new `.git` entry in a folder above an image or a twin name in the other normal form changes what counts. A change of the `ignore` globs of the workspace file invalidates every cached version. The cached entry would also have to name the definitions of the properties that counted, since the metamodel decides which do. The cold load reads files in worker threads ([cold start](cold-start.md)); computing versions there needs a synchronous variant of the image lookup (`embeddedImages` is asynchronous). Its header names the format, a fingerprint of core's code and the canonical root. The fingerprint is a SHA-256 over the product version, the exact dependency versions of core (YAML parser, schema validator) and core's code files; core's build writes it to `dist/code-fingerprint.json` with the hash of `dist/.tsbuildinfo`, so a packaged or bundled build (ADR-0014) never walks its own files, and a `tsc -b` after the build (newer build information) or a run from the sources computes it from the files. Start: list all files, `lstat` each one with an entry (blocking calls: 0.2 s for 50,000 files, through the libuv thread pool 1.5 s), reuse the entry when size, mtime, inode and change time match and the mtime lies more than 2 s before the start of the load that wrote the cache (a file changed again within the resolution of its time stamp keeps size and time: such "racy" entries are read again), read the rest as on a cold start (worker pool from 1,000 files). The racy rule compares file times with the clock of the machine; on a network share whose clock runs ahead, files look racy and are read again (slower, never wrong); one whose clock runs behind by more than 2 s can let a change within the same second go unseen, as for Git. Inode and change time are taken when the cache is written, so a file whose change time lies less than 2 s before the start of the load is not written to the cache at all: a change between the read and the write that keeps size and mtime (`cp -p`) would otherwise go unseen. A cache that is not JSON, has another format, code or root, or an entry of the wrong shape (every field of every kind of entry is checked) is discarded whole; entries of a repository count only while its name and canonical folder match the layout. Only values JSON gives back exactly are cached: plain objects, arrays, strings, booleans, `null` and finite numbers other than `-0`; an entry with anything else (`!!timestamp`, `!!binary`, `!!set`, `!!omap`, `.inf`, `.nan`, `-0`, an alias that contains itself) is left out and its file read on every start. Markdown files without frontmatter and faulty files have no snapshot and are read on every start too. The cache is written again in the background (atomic private write through the files block; one save after the other per workspace; closing the workspace waits; a failed write is ignored) after a load with 1,000 or more out-of-date files or at least 1 % of them (an entry gone, or a file read that the cache can hold: new, changed, racy); fewer are read again at the next start instead, since writing the cache costs about 1.4 s at 50,000 files (75 MB). Changes the watcher or ReqSeq's own writes apply are not written to the cache; the next start reads those files again. A cache folder inside a repository folder of the layout is never used; a cache folder that does not exist yet is named by its nearest existing parent folder (`realpath`) and the rest of its path, so one that lies inside a repository through a symbolic link is recognised on the first run too. The cache is opt-in per `Workspace` (`new Workspace(root, { cacheFolder })`): the CLI passes `cacheFolder(root)` for every command and server, tests leave it out. A server loads the workspace before it serves (`warmWorkspace`: `warmModel` loads metamodel, store, short IDs and the incoming relation index; the search index is built in the background, see [search](search.md)), after its watcher is ready, so no change during the load is missed (SR-007): `reqseq serve api` first refuses a port that is not one and an API for the copy that runs or starts (`checkPort`, `refuseRunningApi`, ADR-0009), prints "Loading the workspace..." to stderr and listens only once the workspace is loaded; stopped meanwhile (Ctrl-C), it never listens, and it exits once the running load has finished, since a load is not aborted, so its first answer means "usable" (SR-082 AK1, AK2); `reqseq mcp` starts the load without waiting, so a cold load does not hold up the protocol handshake. The search index (`search.json`, `query/search-cache.ts`, #323) is stored with a header (format, fingerprint of core's code, canonical root and a SHA-256 digest over the repository, path and content hash of every element record in store order and the part of the metamodel that decides the documents: title key, relation keys, choice names) and used only when the store loaded from the files has the same digest and the index holds exactly one document per record, never per file. Only a one-shot process uses it: a command that needs the index loads it (about 1.4 s at N-036, of which about 1 s blocks the thread, since MiniSearch rebuilds its maps in one call; its asynchronous loader took about 7 s) and writes it after an exact build (about 1.4 s for 27 MB, through the save queue of the model cache, skipped once the index was carried). A server neither reads nor writes it: `warmWorkspace` starts the build in the background a second after the model is loaded (`warmSearchIndex`), in slices that pause while a command runs, so the server answers meanwhile as without it and a search waits for it; blocking for a second right after listening would delay the answers SR-082 AK1 and AK3 measure, and a server keeps the index current by carrying it. Measured on the generated workspace (4 cores): a start of `reqseq serve api` until `workspace.status` answers takes about 1.8 s with the cache and about 12 s without it (a cloud container, files in the page cache of the OS). The search index does not change it (#323): it starts a second after the warm-up; on one generated workspace, five starts with the cache alternating between this change and the code before it took 2.92 s and 2.81 s on average at a load average of 12 to 15, a difference within the spread of single starts (±0.3 s), of which loading the MiniSearch module is about 8 ms. The OS cache folder is `%LOCALAPPDATA%` on Windows, `~/Library/Caches` on macOS and `$XDG_CACHE_HOME` or `~/.cache` elsewhere (`cacheFolder(root)` in core's workspace block); the folder of a copy also holds `api.json` of its local API (ADR-0009) and `activity.json`, the last API or MCP access of the copy (SR-117; `schemas/activity.schema.json`: UUID and repository of the element, access, command, time, the SHA-256 of the element's file and the writer's process token and sequence number; written by every API and MCP process of the copy, the last writer wins, only into a cache folder outside every repository; removing it is safe). Next to the folders of the copies, `<cache>/reqseq/recent-workspaces.json` is the list of the workspaces the app opened last (SR-131; `schemas/recent-workspaces.schema.json`, `workspace/recent.ts`): `format` 1 and up to 20 entries, the most recent first, each the absolute root as opened, its canonical key (computed once when it was opened, so reading the list never resolves a path again) and the time; one entry per key. Only the app's core process writes it, after it opened a workspace (read, change and write under `lockCacheFile`; a lock another process holds is waited for once, then the record is skipped; a failed write is a log line), and only when `<cache>/reqseq` lies outside every repository of that workspace, the rule of the cache folder above, so it never becomes part of a working tree (D-036). The app's main process reads it, and so does the read command `workspace.recent` on every access (a file larger than 64 KiB, not JSON or of another shape is the empty list, which the next record replaces). It is private (mode 0600 in a 0700 folder, like `api.json`) and holds absolute paths of the user's workspaces, and with them the user name, and nothing else; `workspace.recent` gives the list to the command line, the API and the MCP server (SR-080 AK4, spec question #522), so every API caller and MCP client of the user sees the absolute paths of the user's other workspaces too, not only the root of the workspace it was started on. Each call checks each stored root again (`<root>/reqseq-workspace.yaml`, the root itself) with at most 2 `stat`s at once and 1 s per call: a root on a share (a UNC path opened through File > Open Workspace, or one under an automounter) then reaches the network through the OS, as the app's prompt does, and a share that hangs keeps its `stat`s, and so the 2 slots of the process, for as long as it hangs, so that in a long-running API or MCP server every root may count as missing (`exists: false`) from then on, local ones too. A one-shot `reqseq workspace recent` prints its answer after at most 1 s, but its process ends only once such a `stat` returns, which on a hard NFS mount that is down can be never: Node's `process.exit` waits for the threads of libuv too, so an exit timer does not help (#616: a `stat` in an unref'd child process for the one-shot CLI). Removing it, or all of `<cache>/reqseq/`, is safe and only forgets the list, as macOS may do when it purges `~/Library/Caches` under disk pressure.

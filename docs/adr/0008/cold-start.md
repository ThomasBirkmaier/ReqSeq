# ADR-0008, part: Cold start

Part of [ADR-0008](../0008-in-memory-model-and-index.md). Read this part when you work on `model/read-pool.ts`, `model/read-worker.ts`; the decision itself is in the ADR.

- **Cold start:** files are parsed by a pool of worker threads (`node:worker_threads`, one per core minus one, at least one; `model/read-pool.ts`, #148). `loadElements` walks every repository first; when the files of all repositories together are 1,000 or more, they go in one queue, in chunks of 250, to one pool, else they are read in the calling thread as before. A watcher batch (`updateElements`) counts per repository: a repository with 1,000 or more files to read again (a checkout, a pull) gets a pool, which also keeps that parsing off the thread that serves the API, MCP or app. The threshold is the measured break-even: in a fresh process on 4 cores (3 workers) both ways take about 1.0 s for 1,000 files (starting the workers, which load the YAML parser and compile the schemas, costs about 0.5 s); from 2,000 files the pool is ahead (4,000 files: 2.3 s against 3.2 s; 50,000: about 10 s against 41-43 s, of which about 17 s are YAML parsing and about 10 s file calls). Each worker (`model/read-worker.ts`, started with `workerData` marking it, so the module serves nothing in any other thread) reads, parses and classifies its files with blocking calls (`readElementFileSync`, `contributionSync`: the same checks and results as `readElementFile`; calls through the libuv thread pool cost more than they save there) and sends back the contributions as plain data, tagged with the id of the job, so calls on one pool may overlap; the calling thread freezes the snapshots again (a structured clone drops `Object.freeze`) and assembles the store. With the metamodel's `Versioning` (`model/loaded-version.ts`, #439: the definitions `versionDefinitions` gives per type and the SHA-256 of their JSON), each element also gets its version from the bytes just read (`parsedContribution`, so a worker, this thread, a watcher batch and a write give the same): only for a text that links no image (images are checked on use, [current versions](current-versions.md)), and none when computing fails (`.inf`, `.nan`, a bug), so a version never fails the load. Each version holds one value per normal form (`n1` today) and the fingerprint of its type's definitions; the calling thread interns the fingerprints. The store does not depend on the metamodel and builds no metamodel state: only when it reads a file it takes the metamodel state's value if there is one, else reads the metamodel itself (`workspaceVersioning`); none, or none valid, or a failure means no versions, never a failed read. Watcher batches and writes take the metamodel as it is then, so a file read after a change of the metamodel gets the new fingerprint and the others keep theirs; the store keeps the last `Versioning` (`ElementStore.versioning`, `loadedVersionsOf`). The model cache does not hold them yet (format 8). At N-036 hashing them adds about 0.83 s of CPU spread over the workers; reading every file again for them took 3.5 s in one thread (`realpath`, `lstat` and `open` about 1.5 s of it). An abort is checked before the workers start and before each chunk; the workers are stopped with `terminate` when the read ends, also on an abort or a failure; a worker that fails or stops rejects the read. Tests run the TypeScript sources in the workers: `scripts/test-support/worker-preload.mjs` (passed with `--experimental-strip-types --import <URL>` in `execArgv` of the Vitest configs) maps the `.js` specifiers to the `.ts` files and blocks the network in the workers too; coverage of the worker code comes from in-thread tests of the same functions, and a CLI e2e test runs the pool from `dist`.

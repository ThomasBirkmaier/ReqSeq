# ADR-0012: Evidence records and the JUnit convention

Status: Proposed · Based on: D-007, D-008, D-026, D-056 · SRs: SR-028..SR-034, SR-047, SR-093 · Schema: `schemas/evidence-record.schema.json`

## Decision

**Manual record (Markdown)**: frontmatter per `evidence-record.schema.json`: `logreq-record: 1`, `kind` (verification | validation), `element` (UUID), `version`, `method` (test | analysis | inspection | demonstration), `variant` (absent = core), `item` (Prüfling), `result` (passed | failed), `date`, `evidence` (where the Beleg is), `test-case`. Free text below. Written by `evidence.record` (SR-030) or by hand or by any tool. File name: `<date>-<short id>-<method>.md`, with `validation` in place of the method for validation records, in an evidence folder from the workspace file. A relative `evidence` path is relative to the record file.

**Automatic record (JUnit XML)**: each `<testcase>` names its requirement by one of
- a property `<property name="logreq:element" value="SR-46fb54"/>` (short ID or UUID), or
- a token `[SR-46fb54]` or `[SR-46fb54/AK2]` in the test case name.

After a run, `logreq evidence enrich-junit --item <build> results.xml` (SR-029) adds per test case `logreq:element` (UUID), `logreq:version`, `logreq:item`, `logreq:date` and optionally `logreq:variant`. Result: passed unless the test case has `<failure>` or `<error>`; `<skipped>` gives no record. Method is `test`, kind is `verification`. Unknown IDs: exit code 1 and a list (SR-029 AK2). Several IDs on one test case count for each (SR-033 AK2). Each `logreq:element` property gets one `logreq:version`, in the same order: the n-th version is the n-th element's, and a repeated element property gets its own version too (the reader, SR-093, rejects a test case whose counts differ, and one that gives the same element two different versions). Test case name and class name give the test case; each file is one execution (Durchführung).

**Reading**: all records in the evidence folders of the workspace file, recursively, `*.md` with `logreq-record` and `*.xml` with a JUnit root (SR-028). Records are never modified except by `enrich-junit`, and Belege are never written (D-007).

**Status** (SR-031): per element and view the newest record for the current version decides (verified or failed); records only for older versions give outdated; none gives open. Indirect verification (SR-034): a parent without own record is indirectly verified when all its valid children (status not invalid, valid for the view) are verified or indirectly verified; not when it is flagged emergent (SR-035). Validation status the same way with `kind: validation` only, one value per element from the records of the core (SR-038).

## Consequences

- Any test tool that writes JUnit works without code (SR-063 AK1); pytest and Vitest examples come in `toolchain/` (D-054).

## Block and state

The records live in the core block `evidence` (`packages/core/src/evidence/`, block doc `packages/core/docs/evidence-records.md`), built in stage 4 enabler #535:

- **Folders**: every `*.md` and `*.xml` file below each `evidence` location of the workspace file, walked by the rules of the element store (no `.git` or `node_modules`, no nested repository, the `ignore` globs, links never followed), the location folder itself included. An `ignore` glob that keeps the element store out of an evidence folder therefore hides its records too. A location in a repository that is not on this machine makes every result built on the records `incomplete`; a missing folder in an available repository is `evidence.folder-missing` (info).
- **Readers**: one per extension (`md`, `xml`), each given one file and its bytes; it reads nothing else. A Markdown file without `logreq-record` and XML without a JUnit root give nothing.
- **State**: `evidenceReadState` holds what the readers found (`records`, `skipped`, `problems`, `incomplete`); `evidenceRecordsState` is its records as an array. Commands and tests get records through that array, so a consumer is built and tested with records it injects, without files.
- **Record**: `data-export.schema.json#/$defs/evidenceRecord`, from a Markdown record or from one element of a JUnit test case alike, with its location (`source`, `repository`, `file`, `line`) and the JUnit `className`.
- **Test case**: identified by JUnit `classname` + `name`, or by the `test-case` of a Markdown record alone; records with the same identity are one test case across files. Each `<testcase>` is one execution, so a JUnit file normally gives one execution of a test case and one that holds it twice (a rerun such as `pytest-rerunfailures`) gives two (the JUnit reader, SR-093, keeps this). A `<skipped>` test case gives no record but is kept as a test case without execution. A test case is always shown from one element (`$defs/testCase`): its executions are that element's records, since version and outdatedness belong to the element; `elements` lists every element it names.
- **Index**: records by element, newest first (date as an instant, then repository, file, line), and the test cases. "Has evidence" is one function for filter, chain and coverage: a verification record in the view (core: no variant; a variant: for that variant). Validation records never count as Nachweis (D-007).

## JUnit XML

How LogReq reads JUnit files (stage 4 enabler E2, #536; plan review B3, S2, S3).

**Own scanner, no XML library.** `packages/core/src/files/xml-scan.ts` (`scanXml`) is a small XML scanner of our own instead of pulling `fast-xml-parser` (ADR-0015, stage 6) forward: the enrich of SR-029 must change a file without rewriting it, so it needs the byte offsets of every element and attribute, which that library does not give, and one parser is less to review. It reads start, end and empty tags with attributes, text, CDATA, comments, processing instructions, the five predefined entities and numeric character references. Every offset is a byte offset into the original bytes (not an index into a decoded string), so splicing at them keeps every other byte: BOM, CRLF, non-ASCII text and formatting. Lines count CRLF and a lone CR as one break. Attribute values come decoded (references resolved, for matching) and raw (with the offsets of the text between the quotes). The scan is iterative with an explicit stack, so deep nesting cannot overflow the call stack. It is linear in the size of the file, also for hostile input (many attributes in one tag, long texts). Consumers of the element tree walk it iteratively too. It never writes. ADR-0015 is unchanged; stage 6 (ReqIF) decides whether it reuses this scanner, so that the product does not end up with two XML parsers by accident.

**Offline and XXE safe.** Only UTF-8 is read (with or without BOM; an XML declaration that names another encoding is refused). A `<!DOCTYPE` and any entity other than the predefined ones are refused: no entity is expanded and no external reference is followed, so a file can never make LogReq open a network connection or read another file. A refused or not well-formed file in an evidence folder is `evidence.invalid-record` with the line the scanner gives. Refusal messages quote at most 40 characters of the file, with control characters, bidirectional controls and line separators escaped, so a crafted file cannot flood the output or send escape sequences to a terminal. The scanner is lenient where it costs nothing: it accepts literal control characters in text and values, `]]>` in text, `--` in a comment and any non-ASCII character in a name, none of which leads to expansion or I/O. Well-formed XML whose root is neither `testsuites` nor `testsuite` is not a JUnit file and is skipped silently.

**Test-case model.** `packages/core/src/evidence/junit-model.ts`: `junitTestCases(bytes)` gives every `<testsuite>` (nested ones included) and every `<testcase>` of a `<testsuite>`, in file order, with `name`, `className` (`classname`), `line`, the `timestamp` of the nearest enclosing suite that has one, its `<property>` elements (name, value, line, offsets), its outcome (`error` before `failed` before `skipped`, else `passed`) and `propertiesAt`, where a lossless enrich writes: `append` into an existing `<properties>` block (pytest's `record_property` writes one), `open-properties` for an empty `<properties/>`, `new-block` right after the start tag of `<testcase>`, `open-testcase` for a `<testcase …/>` that closes itself. An existing `logreq:item`, `logreq:date` or `logreq:variant` is replaced in place, never written twice; the n-th existing `logreq:version` is replaced in place for the n-th `logreq:element`, and the element and version of an added element are appended, so the order never changes. Replacing in place is at `valueAt`, the text between the quotes of its `value` attribute (escaped for its `quote`) or its element text when it has no `value` attribute (escaped for `<` and `&`), or as a whole (`start`..`end`) for `<property name="…"/>` without a value.

**Element references in a test case.** `elementRefsOf(testCase)` gives the values of the `logreq:element` properties (`source: "property"`) and the `<ref>` of every `[<ref>]` or `[<ref>/<anything>]` token in the test case name (`source: "name"`), each text once per source, classified by syntax (`common.schema.json` patterns): `shortId` (`SR-46fb54`), `uuid` (version 4, any case, as `uuidRef`) or `other` (an identifier such as `SR-036`, #305, or any other text). The callers (SR-029, SR-093) resolve with these rules:
- A property is an explicit statement: a property value that does not name exactly one element is reported (SR-029 AK2: listed, exit code 1), whatever its kind, so a typo such as `SR-0366` is never lost.
- Test tools put brackets in names on their own (pytest parameter lists such as `test_add[1-2]`, Vitest `each` titles). So a name token of kind `shortId` or `uuid` that names no element is unknown, and a name token of kind `other` counts only when it names exactly one element and is otherwise ignored silently. A parametrised test never makes enrich fail, with one rare exception: a pytest ID that happens to look like a short ID (a capital letter, a dash and six or more hex digits, such as `A-123456`) is reported as unknown.
- Two texts can name the same element (after enrich the property holds the UUID while the name still has the short ID): the callers deduplicate after resolving, so each element counts once (SR-033 AK2). Spec question #529 (Q4) may refine this.

**Reading enriched files (SR-093).** The JUnit reader (`packages/core/src/evidence/junit.ts`) reads the bytes only, without the element store, so it reads what enrich wrote and nothing else. A test case is enriched when it has a `logreq:version` property; then its `logreq:element` properties must be UUIDs, and the n-th `logreq:version` belongs to the n-th `logreq:element` (the convention in "Decision"; enrich writes them in that order, so a test case that names several requirements carries each one's own version; a repeated element with the same version counts once, with two different versions it is `evidence.invalid-record`); `logreq:item` and `logreq:date` are required once, `logreq:variant` at most once. Such a test case gives one record per element, a `<skipped>` one a skipped test case; one whose properties do not fit gives `evidence.invalid-record` with its line. A test case that names a requirement (a `logreq:element` property, or a short ID or UUID token in its name) without `logreq:version` gives no record; the file gets one `evidence.not-enriched` warning (spec question #529 Q3). Name tokens of kind `other` are not looked at, since only the store could tell whether they name an element. Each `<testcase>` stays one execution.

## Status rules

Nachweisstatus and Validierungsstatus are derived views; they never change the element's `status` (D-030).

- **Which records count** (SR-031, SR-047): per element and view the records of one kind (`verification` for the Nachweisstatus; `validation`, SR-038, for the Validierungsstatus; D-007 keeps them apart). In the core a record without `variant` counts, in a variant a record for that variant; a record for a variant the element does not apply in (SR-040) counts nowhere. The Validierungsstatus is one value per element, the core's: only validation records without `variant` count, one with a `variant` counts nowhere (spec question #534 Q2; the hint `evidence.outdated` still names it).
- **Which record decides** (SR-031 AK2, AK3): of the counted records of the element's current version, the newest by `date` (compared as an instant; a date that cannot be read is the oldest). Passed gives verified, failed gives failed. **Ties:** when several records of the current version share the newest date and one of them failed, the status is failed: two runs of one pipeline on two platforms are not verified when one failed (spec question #525 Q2, assumption until answered).
- **Outdated and open** (AK4, AK1): counted records only of other versions give outdated, none gives open. An element without a current version (a counted value without a normal form, #276) has no record of it: outdated with records, open without.
- **Which elements**: only elements whose type has the meaning `requirement` have a Nachweisstatus (D-012), in the core and in each variant they apply in (`$defs/element` `verification`). While the metamodel is not valid, the records are not compared (the versions follow the metamodel): every requirement is open.
- **Indirect verification** (SR-034, #46): a requirement with a verification record that holds in the view (any version, any result) keeps its status from the records and names no children (spec question #526 Q1, Q4). One without such a record takes its status from its counted children: the derivation children (relation kinds with the meaning `derivation`; one named only by an ambiguous relation is none, SR-088) whose type has the meaning `requirement`, whose status the metamodel does not mark invalid (D-044, AK3) and that apply in the view (SR-040), each once (#526 Q2). All of them verified or indirect, each in the same view against its own current version: `indirect` (AK1). Otherwise `open` with `missingChildren`, the counted children that are open, failed or outdated, direct children only, in child order (AK2; #526 Q4). No counted child: `open` without `missingChildren` (#526 Q3). An element on a derivation cycle of elements without own record is not indirect (#526 Q5). Without a relation kind with the meaning `derivation` nothing is indirect and nothing fails. Children in a repository that is not on this machine are not seen; `evidence.status` says `incomplete` (SR-006; #526 Q6). An element flagged emergent can still be indirect until SR-035 adds that condition. "Has evidence" (the filter's „ohne Nachweis“, SR-069 AK3), the coverage's `withEvidence` (SR-036) and the chain's `no-evidence` gap keep their rule, a verification record in the view: an indirectly verified parent has no Nachweis of its own there (spec question #527).
- **Validation status** (SR-038, #50): the validation records of the core, measured against the element's current version by the same rule as the Nachweisstatus (newest record of the current version decides, ties with one failed give failed, only older versions give outdated, none gives open); passed is named `validated`. Every element whose type has the meaning `need` has one (`open` without record); every other element has one only when a validation record names it, so requirement lines are not filled with `open` (assumption, spec question #534; SR-110). Verification records never count for it and validation records never for the Nachweisstatus, the indirect verification or "has evidence" (D-007). It is not inherited from children. While the metamodel is not valid every need is `open` and no other element has one.
- **The hint "Nachweis veraltet"** (SR-025 AK4) still takes the newest record of all versions per element, kind and variant, so a requirement can be verified and carry the hint when a newer record belongs to an older version (#43). Whether the hint follows the status is spec question #525 Q1; until it is answered, SR-025's tested rule stays.

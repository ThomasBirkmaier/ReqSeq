# ADR-0012: Evidence records and the JUnit convention

Status: Proposed · Based on: D-007, D-008, D-026, D-056 · SRs: SR-028..SR-034, SR-047, SR-093 · Schema: `schemas/evidence-record.schema.json`

## Decision

**Manual record (Markdown)**: frontmatter per `evidence-record.schema.json`: `reqseq-record: 1`, `kind` (verification | validation), `element` (UUID), `version`, `method` (test | analysis | inspection | demonstration), `variant` (absent = core; verification only, SR-038 AK4), `item` (Prüfling), `result` (passed | failed), `date`, `evidence` (where the Beleg is), `test-case`. Free text below. Written by `evidence.record` (SR-030) or by hand or by any tool. File name: `<date>-<short id>-<method>.md`, with `validation` in place of the method for validation records, in an evidence folder from the workspace file. A relative `evidence` path is relative to the record file.

**Recording in the tool** (`evidence.record`, SR-030): ID and version are never inputs: the tool writes the element's UUID and its current version (D-026: „Bei der Erfassung im Tool sind ID und aktuelle Fassung vorbelegt.“). `<date>` in the file name is the first ten characters of `date` as given (its own offset, so the same on every machine); `date` defaults to the time of the call, UTC, whole seconds. A record file is only ever created, never replaced: a name that is taken (in any case or Unicode normal form) gets `-2`, `-3`, ... before `.md`, also when the file appears between the check and the write. The folder is an evidence location of the workspace file or a folder below one (default: the first location whose repository is on this machine), so the record counts at once (spec question #589 Q1, assumption); missing folders below the location are created, after the full path passed the rules of every new ReqSeq file (no `.git`, `node_modules`, ignored or linked folder, portable names), and every refusal comes before anything is created. The bytes are read back with the Markdown reader before the write (as ADR-0007 does for elements); the body stays empty. A verification names a requirement, a validation a need or a requirement (D-012); a variant must be one the element applies in.

**Automatic record (JUnit XML)**: each `<testcase>` names its requirement by one of
- a property `<property name="reqseq:element" value="SR-46fb54"/>` (short ID or UUID), or
- a token `[SR-46fb54]` or `[SR-46fb54/AK2]` in the test case name.

After a run, `reqseq evidence enrich-junit results.xml <build>` (SR-029) adds per test case `reqseq:element` (UUID), `reqseq:version`, `reqseq:item` and `reqseq:date`. It writes no `reqseq:variant` yet (the catalog has no input for it) and keeps an existing one. An enriched test case (one with a `reqseq:version`) is never enriched again: its version stays the one it was tested against (D-026; spec question #529 Q5, assumption). Result: passed unless the test case has `<failure>` or `<error>`; `<skipped>` gives no record. Method is `test`, kind is `verification`. Unknown IDs: exit code 1 and a list (SR-029 AK2). Several IDs on one test case count for each (SR-033 AK2). Each `reqseq:element` property gets one `reqseq:version`, in the same order: the n-th version is the n-th element's, and a repeated element property gets its own version too (the reader, SR-093, rejects a test case whose counts differ, and one that gives the same element two different versions). Test case name and class name give the test case; each file is one execution (Durchführung).

**Reading**: all records in the evidence folders of the workspace file, recursively, `*.md` with `reqseq-record` and `*.xml` with a JUnit root (SR-028). Records are never modified except by `enrich-junit`; `evidence.record` only creates new ones; Belege are never written (D-007).

**Status** (SR-031): per element and view the newest record for the current version decides (verified or failed); records only for older versions give outdated; none gives open. Indirect verification (SR-034): a parent without own record is indirectly verified when all its valid children (status not invalid, valid for the view) are verified or indirectly verified; not when it is flagged emergent (SR-035). Validation status the same way with `kind: validation` only, one value per element from the records of the core (SR-038).

## Consequences

- Any test tool that writes JUnit works without code (SR-063 AK1). The guide for connecting one and its examples (an example workspace, Vitest, pytest) are in `toolchain/junit/` (SR-063, D-054), tested by `packages/cli/test/e2e/toolchain-junit.test.ts`, which runs the guide's command blocks as written.

## Block and state

The records live in the core block `evidence` (`packages/core/src/evidence/`, block doc `packages/core/docs/evidence-records.md`), built in stage 4 enabler #535:

- **Folders**: every `*.md` and `*.xml` file below each `evidence` location of the workspace file, walked by the rules of the element store (no `.git` or `node_modules`, no nested repository, the `ignore` globs, links never followed), the location folder itself included. An `ignore` glob that keeps the element store out of an evidence folder therefore hides its records too. A location in a repository that is not on this machine makes every result built on the records `incomplete`; a missing folder in an available repository is `evidence.folder-missing` (info).
- **Readers**: one per extension (`md`, `xml`), each given one file and its bytes; it reads nothing else. A Markdown file without `reqseq-record` and XML without a JUnit root give nothing.
- **State**: `evidenceReadState` holds what the readers found (`records`, `skipped`, `problems`, `incomplete`); `evidenceRecordsState` is its records as an array. Commands and tests get records through that array, so a consumer is built and tested with records it injects, without files.
- **Record**: `data-export.schema.json#/$defs/evidenceRecord`, from a Markdown record or from one element of a JUnit test case alike, with its location (`source`, `repository`, `file`, `line`) and the JUnit `className`.
- **Test case**: identified by JUnit `classname` + `name`, or by the `test-case` of a Markdown record alone; records with the same identity are one test case across files. Each `<testcase>` is one execution, so a JUnit file normally gives one execution of a test case and one that holds it twice (a rerun such as `pytest-rerunfailures`) gives two (the JUnit reader, SR-093, keeps this). A `<skipped>` test case gives no record but is kept as a test case without execution. A test case is always shown from one element (`$defs/testCase`): its executions are that element's records, since version and outdatedness belong to the element; `elements` lists every element it names.
- **Index**: records by element, newest first (date as an instant, then repository, file, line), and the test cases. "Has evidence" is one function for filter, chain and coverage: a verification record in the view (core: no variant; a variant: for that variant). Validation records never count as Nachweis (D-007).

## JUnit XML

How ReqSeq reads JUnit files (stage 4 enabler E2, #536; plan review B3, S2, S3).

**Own scanner, no XML library.** `packages/core/src/files/xml-scan.ts` (`scanXml`) is a small XML scanner of our own instead of pulling `fast-xml-parser` (ADR-0015, stage 6) forward: the enrich of SR-029 must change a file without rewriting it, so it needs the byte offsets of every element and attribute, which that library does not give, and one parser is less to review. It reads start, end and empty tags with attributes, text, CDATA, comments, processing instructions, the five predefined entities and numeric character references. Every offset is a byte offset into the original bytes (not an index into a decoded string), so splicing at them keeps every other byte: BOM, CRLF, non-ASCII text and formatting. Lines count CRLF and a lone CR as one break. Attribute values come decoded (references resolved, for matching) and raw (with the offsets of the text between the quotes). The scan is iterative with an explicit stack, so deep nesting cannot overflow the call stack. It is linear in the size of the file, also for hostile input (many attributes in one tag, long texts). Consumers of the element tree walk it iteratively too. It never writes. ADR-0015 is unchanged; stage 6 (ReqIF) decides whether it reuses this scanner, so that the product does not end up with two XML parsers by accident.

**Offline and XXE safe.** Only UTF-8 is read (with or without BOM; an XML declaration that names another encoding is refused). A `<!DOCTYPE` and any entity other than the predefined ones are refused: no entity is expanded and no external reference is followed, so a file can never make ReqSeq open a network connection or read another file. A refused or not well-formed file in an evidence folder is `evidence.invalid-record` with the line the scanner gives. Refusal messages quote at most 40 characters of the file, with control characters, bidirectional controls and line separators escaped, so a crafted file cannot flood the output or send escape sequences to a terminal. The scanner is lenient where it costs nothing: it accepts literal control characters in text and values, `]]>` in text, `--` in a comment and any non-ASCII character in a name, none of which leads to expansion or I/O. Well-formed XML whose root is neither `testsuites` nor `testsuite` is not a JUnit file and is skipped silently.

**Test-case model.** `packages/core/src/evidence/junit-model.ts`: `junitTestCases(bytes)` gives every `<testsuite>` (nested ones included) and every `<testcase>` of a `<testsuite>`, in file order, with `name`, `className` (`classname`), `line`, the `timestamp` of the nearest enclosing suite that has one, its `<property>` elements (name, value, line, offsets), its outcome (`error` before `failed` before `skipped`, else `passed`) and `propertiesAt`, where a lossless enrich writes: `append` into an existing `<properties>` block (pytest's `record_property` writes one), `open-properties` for an empty `<properties/>`, `new-block` right after the start tag of `<testcase>`, `open-testcase` for a `<testcase …/>` that closes itself. An enriched test case is never enriched again; the version stays the one it was tested against (D-026). In a test case that is not enriched yet, an existing `reqseq:element`, `reqseq:item` or `reqseq:date` is replaced in place, never written twice, and an existing `reqseq:variant` is kept; one `reqseq:version` per `reqseq:element` is added in the same order, and the element of an added element is appended after the last `reqseq:element`, so the order never changes. Replacing in place is at `valueAt`, the text between the quotes of its `value` attribute (escaped for its `quote`) or its element text when it has no `value` attribute (escaped for `<` and `&`), or as a whole (`start`..`end`) for `<property name="…"/>` without a value.

**Element references in a test case.** `elementRefsOf(testCase)` gives the values of the `reqseq:element` properties (`source: "property"`) and the `<ref>` of every `[<ref>]` or `[<ref>/<anything>]` token in the test case name (`source: "name"`), each text once per source, classified by syntax (`common.schema.json` patterns): `shortId` (`SR-46fb54`), `uuid` (version 4, any case, as `uuidRef`) or `other` (an identifier such as `SR-036`, #305, or any other text). The callers (SR-029, SR-093) resolve with these rules:
- A property is an explicit statement: a property value that does not name exactly one element is reported (SR-029 AK2: listed, exit code 1), whatever its kind, so a typo such as `SR-0366` is never lost.
- Test tools put brackets in names on their own (pytest parameter lists such as `test_add[1-2]`, Vitest `each` titles). So a name token of kind `shortId` or `uuid` that names no element is unknown, and a name token of kind `other` counts only when it names exactly one element and is otherwise ignored silently. A parametrised test never makes enrich fail, with one rare exception: a pytest ID that happens to look like a short ID (a capital letter, a dash and six or more hex digits, such as `A-123456`) is reported as unknown.
- Two texts can name the same element (after enrich the property holds the UUID while the name still has the short ID): the callers deduplicate after resolving, so each element counts once (SR-033 AK2). Spec question #529 (Q4) may refine this.

**Reading enriched files (SR-093).** The JUnit reader (`packages/core/src/evidence/junit.ts`) reads the bytes only, without the element store, so it reads what enrich wrote and nothing else. A test case is enriched when it has a `reqseq:version` property; then its `reqseq:element` properties must be UUIDs, and the n-th `reqseq:version` belongs to the n-th `reqseq:element` (the convention in "Decision"; enrich writes them in that order, so a test case that names several requirements carries each one's own version; a repeated element with the same version counts once, with two different versions it is `evidence.invalid-record`); `reqseq:item` and `reqseq:date` are required once, `reqseq:variant` at most once. Such a test case gives one record per element, a `<skipped>` one a skipped test case; one whose properties do not fit gives `evidence.invalid-record` with its line. A test case that names a requirement (a `reqseq:element` property, or a short ID or UUID token in its name) without `reqseq:version` gives no record; the file gets one `evidence.not-enriched` warning (spec question #529 Q3). Name tokens of kind `other` are not looked at, since only the store could tell whether they name an element. Each `<testcase>` stays one execution.

**Enriching (SR-029).** `evidence.enrichJunit` (`packages/core/src/evidence/enrich.ts`, block doc `evidence-records.md` "Enriching JUnit XML"):
- A test case with a reference that names no element or more than one (by the rules above) stays unchanged and is listed with its line as an error (`evidence.unknown-element`, `evidence.ambiguous-element`), so the CLI exits with 1; the others are enriched and the file is written (spec question #529 Q1, assumption). An enriched test case is kept as it is and counts; a kept version that is no longer current gives an `evidence.outdated` warning (spec question #529 Q5), and a UUID in it that names no element or several gives `evidence.unknown-element` or `evidence.ambiguous-element` as a warning (as `workspace.check` reports it), not an error (AK2 is about short IDs that are to be enriched).
- Date: the given one, else a valid `reqseq:date` of the test case, else the suite `timestamp` when it has a time zone (Surefire writes none), else the time of the call (spec question #529 Q2, assumption).
- Layout: a new `<properties>` block goes on the line of the `<testcase>` start tag; in a block on lines each new property gets a line of its own with the indentation and line ending of the property before it. Attribute values escape `& < >`, the quote, tab, line feed and carriage return (as character references, so they survive attribute normalisation).
- The spliced bytes are read back before anything is written: the bytes outside the enriched test cases must be those read, and each enriched test case must give exactly the intended values by the reader's checks; a difference is `internal` and nothing is written (the pattern of ADR-0007).
- The file is written in place or to `output` (ADR-0002 rule 5); `files` gives it relative to the workspace root (the folder of the main repository) when it lies in a repository of the workspace, else as an absolute path. With nothing to change the input is not rewritten; a given `output` is still written, unless it holds these bytes already.

## Status rules

Nachweisstatus and Validierungsstatus are derived views; they never change the element's `status` (D-030).

- **Which records count** (SR-031, SR-047): per element and view the records of one kind (`verification` for the Nachweisstatus; `validation`, SR-038, for the Validierungsstatus; D-007 keeps them apart). In the core a record without `variant` counts, in a variant a record for that variant; a record for a variant the element does not apply in (SR-040) counts nowhere. The Validierungsstatus is one value per element, the core's: only validation records without `variant` count, one with a `variant` counts nowhere (spec question #534 Q2; `evidence.list` lists it, and the hint `evidence.outdated` names it when it is of an older version).
- **Which record decides** (SR-031 AK2, AK3): of the counted records of the element's current version, the newest by `date` (compared as an instant; a date that cannot be read is the oldest). Passed gives verified, failed gives failed. **Ties:** when several records of the current version share the newest date and one of them failed, the status is failed: two runs of one pipeline on two platforms are not verified when one failed (spec question #525 Q2, assumption until answered).
- **Outdated and open** (AK4, AK1): counted records only of other versions give outdated, none gives open. An element without a current version (a counted value without a normal form, #276) has no record of it: outdated with records, open without.
- **Which elements**: only elements whose type has the meaning `requirement` have a Nachweisstatus (D-012), in the core and in each variant whose view holds them (the view rule, SR-043: none for a variant that excludes or replaces them, SR-047 AK3; `$defs/element` `verification`). While the metamodel is not valid, the records are not compared (the versions follow the metamodel): every requirement is open.
- **Indirect verification** (SR-034, #46): a requirement with a verification record that holds in the view (any version, any result) keeps its status from the records and names no children (spec question #526 Q1, Q4). One without such a record takes its status from its counted children: the derivation children (relation kinds with the meaning `derivation`; one named only by an ambiguous relation is none, SR-088) whose type has the meaning `requirement`, whose status the metamodel does not mark invalid (D-044, AK3) and that the view holds (SR-040, view rule SR-043 AK7: no core requirement the variant excludes or replaces, and its children only where their own validity puts them, SR-041 AK5), each once (#526 Q2). All of them verified or indirect, each in the same view against its own current version: `indirect` (AK1). Otherwise `open` with `missingChildren`, the counted children that are open, failed or outdated, direct children only, in child order (AK2; #526 Q4). No counted child: `open` without `missingChildren` (#526 Q3). An element on a derivation cycle of elements without own record is not indirect (#526 Q5). Without a relation kind with the meaning `derivation` nothing is indirect and nothing fails. Children in a repository that is not on this machine are not seen; `evidence.status` says `incomplete` (SR-006; #526 Q6). An element marked emergent is never indirect (SR-035). "Has evidence" (the filter's „ohne Nachweis“, SR-069 AK3), the coverage's `withEvidence` (SR-036) and the chain's `no-evidence` gap keep their rule, a verification record in the view: an indirectly verified parent has no Nachweis of its own there (spec question #527).
- **Emergent** (SR-035, #47): (1) an element is marked emergent when its property with the meaning `emergent` holds the choice key `yes` (D-043: files hold keys); `no`, no value, a display name, a list or any other value is no mark, and without a property with the meaning no element is emergent; the filter condition `emergent` is then `metamodel.meaning-unassigned` (SR-013 AK3; assumption, spec question #591 Q1). A person sets the mark (`element.update`, the property box of the app, the file); the tool never sets or computes it (D-030). (2) A property with the meaning `emergent` that is not of kind `choice` without `many` with a choice `yes` gives a `metamodel.invalid` **warning** at the line of `kind`, `many` or `choices` ("…; no element is marked emergent"): the metamodel stays valid and the workspace writable, every status is computed, and no element is emergent (D-012: „Das Tool zeigt sie als Hinweis an, blockiert aber nichts.“; #591 Q1). (3) An emergent requirement with a verification record that holds in the view keeps its status from the records (any version, any result; the own record is enough also when a child failed, #591 Q2). Without one it is `open` in that view, never `indirect`, with no `missingChildren`: its children are not walked (#591 Q3; `prepare` reads no version below it). (4) As a child without own record it is `open`, so its parent is not indirect and names it in `missingChildren` (SR-034 AK2). (5) The mark is per element; the own record must hold in the view (SR-047), so a core record does not verify it in a variant. (6) While the metamodel is not valid every requirement is `open` as before; the output field `emergent` and the filter still read the property. (7) The standard model counts Emergent to the version (`content: true`, ADR-0005), although D-057 lists it neither as counting nor as not counting (spec question #591 Q4, assumption: it stays). So changing the mark (a) makes the element's own records of the old version outdated, (b) gives each child whose derivation relation pins the old version the hint `relation.outdated` (SR-025), and (c) gives `element.update` an `affected` count above 0 (SR-024). Every element output carries `emergent: true` when the element is marked (left out otherwise); the property itself stays in `properties`.
- **Validation status** (SR-038, #50): the validation records of the core, measured against the element's current version by the same rule as the Nachweisstatus (newest record of the current version decides, ties with one failed give failed, only older versions give outdated, none gives open); passed is named `validated`. Every element whose type has the meaning `need` has one (`open` without record); every other element has one only when a validation record names it, so requirement lines are not filled with `open` (assumption, spec question #534; SR-110). Verification records never count for it and validation records never for the Nachweisstatus, the indirect verification or "has evidence" (D-007). It is not inherited from children. While the metamodel is not valid every need is `open` and no other element has one.
- **The hint "Nachweis veraltet"** (SR-025 AK4) still takes the newest record of all versions per element, kind and variant, so a requirement can be verified and carry the hint when a newer record belongs to an older version (#43). Whether the hint follows the status is spec question #525 Q1; until it is answered, SR-025's tested rule stays.
- **Verification degree** (SR-037, #49; `evidence.degree`, `$defs/verificationDegree`): the Nachweisgrad of a selection in one view, the selection's own, else its saved filter's, else the core (spec question #592 Q1). Counted are the elements of the selection whose type has the meaning `requirement`, whose status the metamodel does not mark invalid (AK3, D-044) and that have a Nachweisstatus in the view (they apply in it); needs and other types count nowhere, and without a view a requirement valid only in a variant is not counted (#592 Q1, Q2). The status of each is the one of the shared state, so the degree, `evidence.status` and the filter agree by construction. The output gives one count per Nachweisstatus, all five, `indirect` apart from `verified` (AK2), adding up to `total`, and `share = (verified + indirect) / total` (AK1: failed, outdated and open are in the denominator), left out when nothing is counted (#592 Q3) and never rounded in the data. While the metamodel is not valid every counted requirement is open, so the share is 0. **Display:** every access shows the share as a percentage rounded down to one decimal (`60 %`, `66.6 %`, `64.2 %`), so 100 % only when every counted requirement is verified or indirect (#592 Q3). The rule is written once, `degreePercent` in core (`@reqseq/core`, and `@reqseq/core/verification-degree` for the app's renderer, a module without imports); the CLI's readable output, the app's result buffer and every later view of a degree (the matrix, SR-126; the package page, SR-112) use it, not a rule of their own.
- **Requirements without passed test** (SR-120, #431; `evidence.withoutPassedTest`; spec question #532): a requirement is listed when its type has the meaning `requirement`, its status is not marked invalid (D-044), it applies in the view (the core unless a variant is given) and no verification record with method `test` and result `passed` holds for it there, of any version and also when a later run failed (AK2). Inspection, analysis, demonstration and validation records are no test execution (D-007). It is a derived list, not a status: no output field, no filter operator, and it never sets a status (D-030); „ohne Nachweis“ (any verification record) stays the rule of the filter, the chain and the coverage.

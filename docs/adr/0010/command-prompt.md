# ADR-0010, part: Command prompt and minibuffer

Part of [ADR-0010](../0010-electron-app.md). Read this part when you work on `catalog-commands.ts`, `create-element.ts`, `workspaces.ts`, `usage.ts`, the minibuffer; the decision itself is in the ADR.

- "Open workspace" (SR-131, `workspaces.ts`): an action of the command prompt, no shortcut (File > Open Workspace and Ctrl/Cmd+O keep the native folder dialog). It asks in the minibuffer for one of the workspaces opened last (`recentWorkspaces()`), by full path, in main's order, the most recent first; the prompt opens at once and fills when the list arrives, and typing narrows it with the ranking of the command prompt (`fuzzy.ts`, equal matches keep the order). The hints are muted words, no colour (D-062): "open" for the workspace of the window, "not found" for one whose workspace file is gone (it stays in the list until newer ones push it out; there is no remove action). Choosing another found one calls `openWorkspace`; the window then starts again with the overview of the new workspace (same window, no reload, no restart). Choosing the open one, or one not found, opens nothing and says so in the minibuffer ("… is not found; <name> stays open"). A typed text that starts with `/` or `~`, and on Windows also one that starts with `\` or a drive letter with `:` and a separator, is a folder path (AK5, spec question #524): its choice "Open <path>" (hint "folder") comes first (`Prompt.literal`), so Enter opens the workspace found from it upwards, which is then first in the list; a path without a workspace, or one main refuses, opens nothing and says so (a refused one "<path> could not be opened": main also refuses when it cannot load core's module of the list, so the window cannot tell the two apart). Before every switch, also from File > Open Workspace, the unsaved input of every buffer is saved (AK3, `onSave` above); input that cannot be saved keeps the open workspace and the minibuffer says "<element> could not be saved (<reason>); the workspace was not changed". Without an open workspace the command prompt still opens (Ctrl/Cmd+Shift+P, or a click on the idle minibuffer) and offers only the actions that apply then, "Open workspace", and, when core opened a folder without a workspace, the catalog command "Initialise workspace" (SR-073 AK2); no other shortcut works without a workspace. The catalog is asked for again when a workspace opens after a start without one.
- "Create element" (SR-064, `catalog-commands.ts`, `create-element.ts`): the catalog command `element.create` in the command prompt by its title, no action of its own; its key is Ctrl/Cmd+K E (below). It asks its arguments like any catalog command, and between the required arguments and the optional ones the required properties of the type (product owner decision, 2026-10-28: they are asked one after the other in the command line, no form, D-062). The type is one of the types of `metamodel.get` that are not abstract, by name, in the order of the metamodel; the title is typed text, also empty (core saves it with its hint). Then each required property of the type but the title, in the order of `required`: a choice among the choices of the metamodel (a list: those not taken yet), a relation target among the elements `element.search` finds among its target types, a text kind as typed text; a list takes one value per Enter. An empty input skips the property, or ends the values of a list. Backspace in an empty input goes back one answer; Ctrl/Cmd+Enter offers the optional arguments `text`, `repository` and `folder` once the required properties are answered, never `properties` (the other properties are added in the element buffer, "Add property"). The values go into `properties` as the box of the property would save them (`inputValueOf`), so the app decides nothing about them; core validates, and a refused input asks the property core names again with core's message (the rule of the catalog commands below). Nothing is written before the last answer; then one `element.create`, and the new element opens in its element buffer with its title, its text and the boxes of the properties given (an empty required property shows no box, D-062). The minibuffer says "Created <ID> <title> · <n> hints"; the modeline counts the hints while the properties are empty, and "Add property" offers them with every optional property of the type (SR-064 AK3).
- Command prompt ranking (SR-108 AK3, SR-121 AK2, SR-133, `usage.ts`): what was chosen is display state of the app, like the elements opened last: kept in the app's local storage under `logreq.usage.v1`, not per workspace (the commands are the same in every workspace) and never in the workspace or through a catalog command (SR-080 AK1: "außer reiner Darstellung der App"). Only the command ID and the text typed in the command prompt are recorded, with the count and the time of the last use (at most 500 commands and 500 texts); nothing for "Go to", argument steps or elements. Order: the match comes first (initials, letters in order, one slip per word); equally good matches, and every command when nothing is typed, go first by fit to the shown view (SR-133: every action shown, since it is shown only where it applies, and a catalog command whose argument the view gives: a list its selection, an element or a neighbourhood its element to a required element argument), then by use (uses divided by one plus the days since the last one); the command chosen the last time for exactly this text (lower case, spaces collapsed) comes first, when it is offered and matches now. A storage that is missing or throws gives the plain order.
- Minibuffer: the only control, apart from two exceptions: the copy symbols of the fields (SR-128, below; seen only on hover or focus) and the editor's transient `/` menu at the caret (SR-129, below; whether D-062 allows it is the spec question #453, until it is answered the menu only inserts formatting). Ctrl/Cmd+Shift+P opens the command prompt, Ctrl/Cmd+P jumps to an open buffer or to an element, Ctrl/Cmd+Shift+F searches; each entry shows its shortcut. The prefix key is Ctrl+K (Cmd+K on macOS; SR-109 AK3, SR-121 AK3; the set and the letters are the assumption of the open spec question #472, one table in `bindings.ts`): Ctrl/Cmd+K, then one letter runs one of the most frequent commands (E "Create element", R "Create relation", T "Set status", H "Confirm hints", L "List all elements", O "Show overview", F "Filter list by type", S "Sort list", B "Close buffer"; the write commands not in a read-only workspace, where the prompt does not offer them), and the command prompt shows that key next to the command („Ctrl+K L“, „⌘K L“). The window's key handler arms the prefix in the same event as Ctrl/Cmd+K (not while a prompt is open, whose input takes the keys), and the echo says „Ctrl+K-“. The next key is taken in the capture phase by listeners that live as long as the window (`use-prefix.ts`), so it never reaches the editor or a box: a Latin letter, bare or with the prefix modifier held (Emacs „C-k C-l“; on macOS Cmd only, the physical Ctrl with a letter is not bound; by its place `KeyL` on a non-Latin layout), runs the command bound to it where it applies (the rows are the entries of the command prompt, so SR-133 holds); a bound letter whose command does not apply says „<command> is not available here“; any other key says „Ctrl+K X is not bound“; Escape ends it quietly; a modifier alone, a composing input method and a held K are ignored; a second Ctrl/Cmd+K shows the next keys at once. When no key follows within 500 ms, the minibuffer shows the possible next keys with their commands above the echo line, in the order of the table, without an input and without moving the focus (a mode of the minibuffer, no dialog, D-062). A mouse press, leaving the window, another buffer shown (also by „Agent folgen“) and another workspace opening end the prefix. Ctrl+X and Ctrl+C are not used (cut and copy in every field), Ctrl+G stays free. In a prompt, Down/Up, Tab and Ctrl+N/Ctrl+P (the physical Ctrl key on every platform, also macOS) move the selection (SR-122); the prompt stops these keys, so they never reach the global shortcuts (Ctrl+P is "Go to" otherwise), and a key that a control handled is no shortcut (the window handler ignores a prevented key). In the text editor on macOS, CodeMirror binds the Emacs keys Ctrl+N/Ctrl+P to the caret, so there they move the caret and do not open "Go to" (at the first line of the text Ctrl+P goes into the title, as Up does, #621); Cmd+P does. The same holds for Ctrl+T (the traceability matrix, below): the physical Ctrl+T in the text editor on macOS stays the Emacs "transpose" of CodeMirror and shows no matrix; Cmd+T does. Every action has a keyboard path (SR-073 AK1). The prompt finds every function by its name (SR-073 AK2). It lists the actions of the app that apply to the shown buffer and the catalog's implemented read commands by their `title`, and the write commands listed below; a command an action does (its title, or the action's `covers`) is listed once. A catalog command asks its arguments one by one in the minibuffer in the order of its catalog `arguments`, each source answered by one read command (ADR-0002 rule 1); Backspace in an empty input goes back, Ctrl/Cmd+Enter offers the optional arguments, and the output opens the result buffer. The app builds the input only; core validates it. A refused input (`input.invalid`) asks again, with core's message, the value the details of the error name: the field of the first schema violation (`errors[0].field`: `ref`, `refs[0]`, `properties.<key>`, the property of a new element), else the property core names in `key` (for example an unknown or ambiguous choice it refused while writing the value). The answer takes the place of the refused value, in the prompt's line, in the name of the result buffer and in a list (`refs[0]` stays first). The other values given stay, except those read from it: the properties a type asks, and the arguments whose offer reads it (`of` or the nearest earlier field, also through another one: `target` ← `kind` ← `source`), which are asked or offered again after it. A refusal that names nothing asked in this run (another refusal, a field the prompt does not ask) asks the value given last, and one before the first argument goes to the minibuffer. The renderer's `call` keeps the `details` of the error for this. Write commands (SR-073 AK2, #85) are listed like read commands: every implemented one but `element.update` (the element buffer's: "Save element" covers it, with "Edit title", "Add property" and "Clear property"); "Save filter" takes its condition `where` as typed JSON (a "Save list filter" action from the shown list is a follow-up), and "Initialise workspace" is also the only catalog command offered while a folder without a workspace is open (core opens such a folder for it); while the workspace is read-only (`workspace.status`, as the modeline shows it) none that core refuses then (`whileReadOnly: refuse`). Two rules more than for a read command: one without a required argument asks its first argument (`hint.confirm`: `ref`, the shown element first), and an optional argument whose explicit `of` names a field given in this run is asked right after the required ones, in catalog order (`hint.confirm hintIds` of `ref`, `element.bulkUpdate value` of `property`); Enter on an empty input skips it, or ends its values, and Ctrl/Cmd+Enter offers a skipped one again. So "Confirm hints" on a shown element is Enter, Enter, Enter (the command, the element, no hint IDs: every hint of the element). Before a write command runs, the input of every open buffer is saved (`saveDraft`, as "Close buffer" saves), the shown one last as a workspace switch saves; the first that cannot be saved stops it, nothing is sent, and the minibuffer names the buffer. Its output opens a result buffer that is never asked again when the workspace changes, since that would write again. `element.bulkUpdate` writes only with `confirm` yes, an optional argument given with Ctrl/Cmd+Enter; without it, it shows what it would change (also in a result buffer that is not asked again). The arguments a command expects are completed with the values the metamodel allows (SR-108 AK4), ranked like the commands (`fuzzy.ts`) or found by `element.search`, each source answered by one read command: `status` the statuses of the element's type (`element.get` and `metamodel.get`; for the list `refs` those of its first element, core checks the others) and `invalidStatus` only the invalid ones; `property` the properties of the element's type, without an element (`element.bulkUpdate`) every property of the metamodel, never the one with the meaning title (the commands refuse it); `value` the choices of the property, a property of kind `relation` the elements of its target types, any other kind typed text; `relationTarget` the elements of the target types of the kind, from `relation.options` of the element the kind was offered for (the field two steps back, `target` ← `kind` ← `source`), else from the metamodel; `relation` (`relation.remove`) the kinds of the element's outgoing relations (relation kinds, not the properties of kind `relation`), then the targets of that kind; `hint` the hints of the element that can be confirmed (`hint.list`, those with a `hintId`, by their message). An element offer among target types does not put the shown element first. `filter`, the problem codes of `hint.list`/`hint.confirm kind` (#738) and `view` (variants, stage 5, #737) stay typed text. Names of actions and open buffers are ranked with uFuzzy in the renderer (UI only), and a query of one word that gives the beginnings of the words of a name finds it first (`flp` for "Filter list by property", SR-121 AK1); elements are found by `element.search` in core (ADR-0002). Lists come from `element.list` (filter, sort, derivation tree) in pages of 200, search results in pages of 50. A list starts sorted by type, then ID (#418): the app sends `sort: [{"by":"type","order":"asc"},{"by":"identifier","order":"asc"}]` (`DEFAULT_SORT`; digit runs by number, SR-9 before SR-10), which a CLI user reproduces with that input; `element.list` without `sort` stays the workspace order for every other access, and the modeline says nothing about the default (D-062). "Sort list" offers "Type and ID" (the default, sent explicitly), "Workspace order" (`sort: []`, named in the modeline) and the other keys; a list with a saved filter and no chosen sort keeps the filter's own sort (SR-070 AK3). Assumption: no SR sets a default order, so it is the app's choice of the input (ADR-0002). List filters cascade (SR-124): a list keeps its filter steps, each adds a condition (or the one saved filter) to the selection it sends to `element.list`, and the values "Filter list by property" offers come from `element.facets`, so the app counts and filters nothing itself.

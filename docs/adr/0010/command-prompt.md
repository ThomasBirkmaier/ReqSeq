# ADR-0010, part: Command prompt and minibuffer

Part of [ADR-0010](../0010-electron-app.md). Read this part when you work on `catalog-commands.ts`, `create-element.ts`, `workspaces.ts`, `usage.ts`, the minibuffer; the decision itself is in the ADR.

- "Open workspace" (SR-131, `workspaces.ts`): an action of the command prompt, no shortcut (File > Open Workspace and Ctrl/Cmd+O keep the native folder dialog). It asks in the minibuffer for one of the workspaces opened last (`recentWorkspaces()`), by full path, in main's order, the most recent first; the prompt opens at once and fills when the list arrives, and typing narrows it with the ranking of the command prompt (`fuzzy.ts`, equal matches keep the order). The hints are muted words, no colour (D-062): "open" for the workspace of the window, "not found" for one whose workspace file is gone (it stays in the list until newer ones push it out; there is no remove action). Choosing another found one calls `openWorkspace`; the window then starts again with the overview of the new workspace (same window, no reload, no restart). Choosing the open one, or one not found, opens nothing and says so in the minibuffer ("… is not found; <name> stays open"). A typed text that starts with `/` or `~`, and on Windows also one that starts with `\` or a drive letter with `:` and a separator, is a folder path (AK5, spec question ThomasBirkmaier/ReqSeq-archive#524): its choice "Open <path>" (hint "folder") comes first (`Prompt.literal`), so Enter opens the workspace found from it upwards, which is then first in the list; a path without a workspace, or one main refuses, opens nothing and says so (a refused one "<path> could not be opened": main also refuses when it cannot load core's module of the list, so the window cannot tell the two apart). Before every switch, also from File > Open Workspace, the unsaved input of every buffer is saved (AK3, `onSave` above); input that cannot be saved keeps the open workspace and the minibuffer says "<element> could not be saved (<reason>); the workspace was not changed". Without an open workspace the command prompt still opens (Ctrl/Cmd+Shift+P, or a click on the idle minibuffer) and offers only the actions that apply then, "Open workspace", and, when core opened a folder without a workspace, the catalog command "Initialise workspace" (SR-073 AK2); no other shortcut works without a workspace. The catalog is asked for again when a workspace opens after a start without one.
- Path completion (SR-143, `path-completion.ts`): a path argument (`complete: folder|file`, ADR-0002 rule 1) and a folder path in "Open workspace" are completed from core's `workspace.listFolder` (for "Open workspace" through main, `listFolder`), the folder of the text up to its last separator; the renderer only narrows by the typed name with `fuzzy.ts` (UI only, as for statuses), on NFC names, and partitions folders and links before files after ranking; core decides which entries exist (dot rule, files). A new kind of choice, `Choice.complete`, replaces the input and keeps the prompt open (the other kinds still close it); `Prompt.seek` is `find` with a note for the label and `alone` (the found choices take the place of the prompt's own items). The typed text stays the first row ("Open <path>", "Use <path>"), so Enter takes a path that names nothing yet (a new export file) and Down reaches the entries. Listings are cached per folder and dot rule for the life of the prompt and stale answers are dropped by the question number of `search`; at most 200 rows are rendered ("… n more"), so 10,000 entries stay within 100 ms (AK5). In the app `~` is the home folder in every path argument (core's local path rule of the app, ADR-0002 rule 4), so a suggestion and the file written agree; a `\` starts no completion in "Open workspace".
- "Create element" (SR-064, `catalog-commands.ts`, `create-element.ts`): the catalog command `element.create` in the command prompt by its title, no action of its own; its key is Ctrl/Cmd+K E (below). It asks its arguments like any catalog command, and between the required arguments and the optional ones the required properties of the type (they are asked one after the other in the command line, no form, D-062). The type is one of the types of `metamodel.get` that are not abstract, by name, in the order of the metamodel; the title is typed text, also empty (core saves it with its hint). Then each required property of the type but the title, in the order of `required`: a choice among the choices of the metamodel (a list: those not taken yet), a relation target among the elements `element.search` finds among its target types, a text kind as typed text; a list takes one value per Enter. An empty input skips the property, or ends the values of a list. Backspace in an empty input goes back one answer; Ctrl/Cmd+Enter offers the optional arguments `text`, `repository` and `folder` once the required properties are answered, never `properties` (the other properties are added in the element buffer, "Add property"). The values go into `properties` as the box of the property would save them (`inputValueOf`), so the app decides nothing about them; core validates, and a refused input asks the property core names again with core's message (the rule of the catalog commands below). Nothing is written before the last answer; then one `element.create`, and the new element opens in its element buffer with its title, its text and the boxes of the properties given (an empty required property shows no box, D-062). The minibuffer says "Created <ID> <title> · <n> hints"; the modeline counts the hints while the properties are empty, and "Add property" offers them with every optional property of the type (SR-064 AK3).
- Command prompt ranking (SR-108 AK3, SR-121 AK2, SR-133, `usage.ts`): what was chosen is display state of the app, like the elements opened last: kept in the app's local storage under `reqseq.usage.v1`, not per workspace (the commands are the same in every workspace) and never in the workspace or through a catalog command (SR-080 AK1: "außer reiner Darstellung der App"). Only the command ID and the text typed in the command prompt are recorded, with the count and the time of the last use (at most 500 commands and 500 texts); nothing for "Go to", argument steps or elements. Order: the match comes first (initials, letters in order, one slip per word); equally good matches go first by fit to the shown view (SR-133 AK2: every action shown, since it is shown only where it applies, a catalog command whose argument the view gives: a list its selection, an element or a neighbourhood its element to a required element argument, and in the overview every command), then by use (uses divided by one plus the days since the last one); without use the window's order (`unusedOrder`) holds: the entries with a letter after the prefix key in the order of the next keys, then the actions with a shortcut of their own in the order of `ACTIONS`, then the others by name. An empty input shows the first nine fitting commands in this order and a last row "All commands…" (`Prompt.opening`, SR-133 AK1), and, where at most ten commands can run, all of them without that row; the row opens the same commands alphabetically under the label "All commands" (`allCommandsPrompt`, AK3), records no use, has no key and no command help; the command chosen the last time for exactly this text (lower case, spaces collapsed) comes first, when it is offered and matches now. A storage that is missing or throws gives the plain order.
- Minibuffer: the only control, apart from two exceptions: the copy symbols of the fields (SR-128, below; seen only on hover or focus) and the editor's transient `/` menu at the caret (SR-129, below; whether D-062 allows it is the spec question ThomasBirkmaier/ReqSeq-archive#453, until it is answered the menu only inserts formatting). The × of a mark in the input (SR-215 AK9: a part of a value built from hits, #1645) is part of the minibuffer, as its hits are, and goes with the prompt. Ctrl/Cmd+Shift+P opens the command prompt, Ctrl/Cmd+P jumps to an open buffer or to an element, Ctrl/Cmd+Shift+F searches; each entry shows its shortcut. The prefix key is Ctrl+K (Cmd+K on macOS; SR-109 AK3, SR-121 AK3; the set and the letters are the assumption of the open spec question ThomasBirkmaier/ReqSeq-archive#472, one table in `bindings.ts`): Ctrl/Cmd+K, then one letter runs one of the most frequent commands (E "Create element", R "Create relation", T "Set status", H "Confirm hints", L "List all elements", O "Show overview", F "Filter list by type", S "Sort list", B "Close buffer"; the write commands not in a read-only workspace, where the prompt does not offer them), and the command prompt shows that key next to the command („Ctrl+K L“, „⌘K L“). The window's key handler arms the prefix in the same event as Ctrl/Cmd+K (not while a prompt is open, whose input takes the keys), and the echo says „Ctrl+K-“. The next key is taken in the capture phase by listeners that live as long as the window (`use-prefix.ts`), so it never reaches the editor or a box: a Latin letter, bare or with the prefix modifier held (Emacs „C-k C-l“; on macOS Cmd only, the physical Ctrl with a letter is not bound; by its place `KeyL` on a non-Latin layout), runs the command bound to it where it applies (the rows are the entries of the command prompt, so SR-133 holds); a bound letter whose command does not apply says „<command> is not available here“; any other key says „Ctrl+K X is not bound“; Escape ends it quietly; a modifier alone, a composing input method and a held K are ignored; a second Ctrl/Cmd+K shows the next keys at once; Ctrl+N/Ctrl+P (the physical Ctrl key, also on macOS) and Down/Up show them at once and move a selection through them, the first row first, and Enter runs the selected one (without one, „Ctrl+K Enter is not bound“; SR-122 AK6, SR-145 AK3); the list shown after the delay has none selected. So Ctrl+N and Ctrl+P are never letters after the prefix. When no key follows within 500 ms, the minibuffer shows the possible next keys with their commands above the echo line, in the order of the table, without an input and without moving the focus (a mode of the minibuffer, no dialog, D-062). A mouse press, leaving the window, another buffer shown (also by „Agent folgen“) and another workspace opening end the prefix. Ctrl+X and Ctrl+C are not used (cut and copy in every field), Ctrl+G stays free. In a prompt, Down/Up, Tab and Ctrl+N/Ctrl+P (the physical Ctrl key on every platform, also macOS) move the selection (SR-122); the prompt stops these keys, so they never reach the global shortcuts (Ctrl+P is "Go to" otherwise), and a key that a control handled is no shortcut (the window handler ignores a prevented key). In the text editor on macOS, CodeMirror binds the Emacs keys Ctrl+N/Ctrl+P to the caret, so there they move the caret and do not open "Go to" (at the first line of the text Ctrl+P goes into the title, as Up does, ThomasBirkmaier/ReqSeq-archive#621); Cmd+P does. The same holds for Ctrl+T (the traceability matrix, below): the physical Ctrl+T in the text editor on macOS stays the Emacs "transpose" of CodeMirror and shows no matrix; Cmd+T does. Every action has a keyboard path (SR-073 AK1). The prompt finds every function by its name (SR-073 AK2), except the seven read commands whose output the app shows only in other commands (SR-133 AK4, `SHOWN_IN` in `command-entry.ts`), which it neither lists nor finds. It lists the actions of the app that apply to the shown buffer and the catalog's other implemented read commands by their `title`, and the write commands listed below; a command an action does (its title, or the action's `covers`) is listed once. A catalog command asks its arguments one by one in the minibuffer in the order of its catalog `arguments`, each source answered by one read command (ADR-0002 rule 1); Backspace in an empty input goes back, Ctrl/Cmd+Enter offers the optional arguments, and the output opens the result buffer. The app builds the input only; core validates it. A refused input (`input.invalid`) asks again, with core's message, the value the details of the error name: the field of the first schema violation (`errors[0].field`: `ref`, `refs[0]`, `properties.<key>`, the property of a new element), else the property core names in `key` (for example an unknown or ambiguous choice it refused while writing the value). The answer takes the place of the refused value, in the prompt's line, in the name of the result buffer and in a list (`refs[0]` stays first). The other values given stay, except those read from it: the properties a type asks, and the arguments whose offer reads it (`of` or the nearest earlier field, also through another one: `target` ← `kind` ← `source`), which are asked or offered again after it, and a `group` reads the fields its selection comes from. So a refused `where` or `filter` drops a given `group`, a refused `ref` drops a given `criteria` or `file`, a refused `type` of "Create element" a given `properties` or `relations`, and a refused `path` of "Initialise workspace" a given `metamodel` (the sources of SR-215, #1643); a given `variant` stays with a refused `ref`, since it reads nothing, and no argument reads it (an element argument with a `meaning`). A refusal that names nothing asked in this run (another refusal, a field the prompt does not ask) asks the value given last, and one before the first argument goes to the minibuffer. The renderer's `call` keeps the `details` of the error for this. Write commands (SR-073 AK2, ThomasBirkmaier/ReqSeq-archive#85) are listed like read commands: every implemented one but `element.update` (the element buffer's: "Save element" covers it, with "Edit title", "Add property" and "Clear property") and `element.addAttachment` (the element buffer's "Insert image" covers it, SR-097); "Save filter" and "Save perspective" build their condition `where` from hits (below), and "Initialise workspace" is also the only catalog command offered while a folder without a workspace is open (core opens such a folder for it); while the workspace is read-only (`workspace.status`, as the modeline shows it) none that core refuses then (`whileReadOnly: refuse`). Two rules more than for a read command: one without a required argument asks its first argument (`hint.confirm`: `ref`, the shown element first), and an optional argument whose explicit `of` names a field given in this run is asked right after the required ones, in catalog order (`hint.confirm hintIds` of `ref`, `element.bulkUpdate value` of `property`); Enter on an empty input skips it, or ends its values, and Ctrl/Cmd+Enter offers a skipped one again. So "Confirm hints" on a shown element is Enter, Enter, Enter (the command, the element, no hint IDs: every hint of the element). Ctrl/Cmd+Enter then offers `all`: yes takes the place of the shown element (`replaces`; no takes no place), and with `kind` and `expected` (the total of "List hints" of that kind) it confirms the hints of that kind in the whole workspace (#644). Before a write command runs, the input of every open buffer is saved (`saveDraft`, as "Close buffer" saves), the shown one last as a workspace switch saves; the first that cannot be saved stops it, nothing is sent, and the minibuffer names the buffer. Its output opens a result buffer that is never asked again when the workspace changes, since that would write again. `element.bulkUpdate` writes only with `confirm` yes, an optional argument given with Ctrl/Cmd+Enter; without it, it shows what it would change (also in a result buffer that is not asked again). The arguments a command expects are completed with the values the metamodel allows (SR-108 AK4), ranked like the commands (`fuzzy.ts`) or found by `element.search`, each source answered by one read command: `status` the statuses of the element's type (`element.get` and `metamodel.get`; for the list `refs` those of its first element, core checks the others) and `invalidStatus` only the invalid ones; `property` the properties of the element's type, without an element (`element.bulkUpdate`) every property of the metamodel, never the one with the meaning title (the commands refuse it); `value` the choices of the property, a property of kind `relation` the elements of its target types, any other kind typed text; `relationTarget` the elements of the target types of the kind, from `relation.options` of the element the kind was offered for (the field two steps back, `target` ← `kind` ← `source`), else from the metamodel; `relation` (`relation.remove`) the kinds of the element's outgoing relations (relation kinds, not the properties of kind `relation`), then the targets of that kind; `hint` the hints of the element that can be confirmed (`hint.list`, those with a `hintId`, by their message). An element offer among target types does not put the shown element first. `view` offers `core` and the variants of the workspace (`metamodel.get` for the types with the meaning `variant`, then `element.list` of them; #285), as "Choose view" does. A value the metamodel names (a type, a status, a property, a relation kind, a choice) shows its key beside its name, right-aligned and muted like a shortcut, unless the two are the same; the ranking reads the name (SR-215 AK1, #1644). The other fixed values of SR-215 AK1 (#1644), each from one read command: `filter` the saved filters by name (`filter.list`); an `element` argument with a `meaning` (variant, package) the elements of the types with that meaning as hits (`metamodel.get`, then `element.list`, as `view` without `core`), not an element search; `criterion` (`evidence.record criteria`) the acceptance criteria of the element of `ref` that have a criterion key, by "AK<n> <text>" with the key beside, one per Enter, the key inserted (evidence.record refuses a criterion without a key, so such a criterion is not offered); `evidenceLocation` the `folder` of each evidence location of `workspace.status` whose repository is on this machine, the repository beside, and typed text too: Enter with no hit takes it, and a text below a location ("evidence/manual") stands first as "Use <text>"; `elementFile` the file of the element of `ref` (`element.get`), or, when `ref` is ambiguous, the files of `details.candidates` of `ref.ambiguous` with their repository beside (a reference element.get does not read, such as a criterion reference of "Resolve reference", is typed); `searchField` (`element.search fields`, SR-216 AK3): the fields `element.searchFields` lists, by name with the key beside, those taken left out, and after `properties` no single property (AK6); `metamodelLocation` (`workspace.init metamodel`) in two steps, the repository ("Main repository", the default, or "Repository <name>" for a typed name), then the path: in the main repository completed with the folders below the new workspace's `path` (`workspace.listFolder`, typed text taken), in another one typed; Backspace in its empty input goes back to the repository, and the value is `{ path }` or `{ repository, path }`. A `condition` (the `where` of "Save filter" and "Save perspective", SR-215 AK3 to AK10 as #1645 lists them, `condition-prompt.ts`) is built from hits: the first step offers the finishing hit ("No condition: all elements" without a mark, else "Take <n> conditions", first and so marked) and the kinds type, status, property, verification status, validation status, validity, relation and text search; a kind asks its values, and each value chosen is a mark in the input with the label of the same list filter step ("type: <key>", "status: <key>", "<property>: <value>", "text: <words>"), the others "verification: <status>", "validation: <status>", "validity: <view>" and "relation: without child". Types and relation kinds come from `metamodel.get`; statuses (by their name in `metamodel.get`), properties (as "Filter list by property" offers them, SR-124 AK2, AK3) and their values from `element.facets` over the marks so far, without a mark of the workspace; verification and validation statuses from the condition's schema in the catalog, the views of validity as "Choose view" lists them; a relation is with or without a child, a parent (the ends of a derivation), evidence, or a relation of a kind or a relation property. Without a mark on a shown list whose filter steps give a condition or a saved filter (not the matrix, the search hits or a package page), "Conditions of the shown list" comes first (SR-215 AK5): Enter adds each filter step as its mark and each condition of a perspective's selection as a mark with the label of its list filter step, else in JSON, gives its saved filter to `filter` of "Save perspective" (shown as "filter: <name>"), and goes on without the hit; "Save filter" has no such hit on a list with a saved filter, and the explanation line says why. "Save list as perspective" writes the same `where` under one `all`, so both ways write the same file (SR-214 AK5); only a perspective's selection with no further condition stays as stored (SR-213 AK3), which selects the same elements as its marks under `all`. Text that starts with "{" is one mark in JSON, as the command line takes it (or, not). The value is `{ all: [<the marks in their order>] }`, without a mark `{ all: [] }`. Backspace on an empty input removes the last mark where the kind is chosen, else it goes back a step, as Escape does (SR-134 AK4); a value step goes back to the kinds, a property's values to the properties; Escape keeps the marks, and they stand again when the prompt returns to the argument, also after core refused the condition with its message. A `sort` (SR-215 AK4, AK5, AK7, AK9, AK10 as #1646 lists them, `sort-prompt.ts`) is built the same way: the finishing hit ("No sort" without a mark, which skips the argument, else "Take <n> sort keys"), "Hierarchy (tree)" only without a mark (ascending), the keys "ID" (`identifier`), "Short ID" (`id`), "Title", "Type", "Status" and the properties of `metamodel.get` that hold no relations, and "Workspace order" (`sort: []`); a key asks "Order" as "Sort list" does and is then a mark "<key> <order>", a key chosen again replaces its mark in its place, and the value is the keys of the marks in their order. Without a mark, "Sort of the shown list" comes first on a list, not the matrix, the search hits or a package page (SR-215 AK5): the sort it is shown in (`listSort`), the default "Type and ID" too, which "Save list as perspective" writes, none while a saved filter's own sort holds; "Save filter" has none on a list with a saved filter, and the explanation line says why. A `group` (SR-215 AK1, AK5, #1647) offers the groupings "Group list" offers (`list-groups.ts`: "Type", "Status", "Package" with a property of the packages, and each property with values to choose, by name with the key beside) of the elements the call's earlier `where`, `filter`, `perspective` and shown selection select together, from one `element.facets` that the typed text then narrows (SR-108 AK5); a perspective's selection comes from `perspective.list`, its saved filter only where no other is given. On a grouped list, not the matrix, the search hits or a package page, "Grouping of the shown list" comes first for "Save perspective", as "Save list as perspective" saves it. Names of actions and open buffers are ranked with uFuzzy in the renderer (UI only), and a query of one word that gives the beginnings of the words of a name finds it first (`flp` for "Filter list by property", SR-121 AK1); elements are found by `element.search` in core (ADR-0002). The search of Ctrl/Cmd+Shift+F, an action and not the catalog command, chooses its fields in a prompt of its own (SR-216 AK6 to AK10, `search-fields.ts`): Ctrl/Cmd+Enter at the search words, or a click on that key in the explanation line, lists "Search all fields" or "Search in <n> fields" (back to the words, which stay) and the fields of `element.searchFields` not yet marked, each a mark before the words; the hits while typing and the list of search hits send the same `fields`, and the list names them under its heading, keeps them through "Clear all list filters" and a restart, and is another buffer than the same words in other fields. Lists come from `element.list` (filter, sort, derivation tree) in pages of 200, search results in pages of 50. A list starts sorted by type, then ID (ThomasBirkmaier/ReqSeq-archive#418): the app sends `sort: [{"by":"type","order":"asc"},{"by":"identifier","order":"asc"}]` (`DEFAULT_SORT`; digit runs by number, SR-9 before SR-10), which a CLI user reproduces with that input; `element.list` without `sort` stays the workspace order for every other access, and the modeline says nothing about the default (D-062). "Sort list" offers "Type and ID" (the default, sent explicitly), "Workspace order" (`sort: []`, named in the modeline) and the other keys; a list with a saved filter and no chosen sort keeps the filter's own sort (SR-070 AK3). Assumption: no SR sets a default order, so it is the app's choice of the input (ADR-0002). List filters cascade (SR-124): a list keeps its filter steps, each adds a condition (or the one saved filter) to the selection it sends to `element.list`, and the values "Filter list by property" offers come from `element.facets`, so the app counts and filters nothing itself.

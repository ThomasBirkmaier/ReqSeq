# ADR-0010, part: Lists, buffers and the views of an element

Part of [ADR-0010](../0010-electron-app.md). Read this part when you work on the lists, the buffer order, the neighbourhood, the matrix, the package page, follow agent; the decision itself is in the ADR.

- Open buffers after a restart (SR-115 AK4, `buffer-session.ts`): the buffers open when the window closed, or when the workspace was left for another, are display state like the elements opened last: kept per workspace in the app's local storage (`logreq.buffers.v1` with the name and repositories of the workspace, a literal like `logreq.recent.v1` and `logreq.usage.v1`, so a rename renames the three together), never in the workspace (SR-118 AK5) and through no catalog command (SR-080 AK1). When the workspace opens, the overview shows first (SR-118 AK1) and the stored buffers come back behind it, in their order of use and their order of opening (SR-115 AK5). Stored is what rebuilds a buffer, never a title, a text, an output or a selected row; the names of elements are read with one `element.list` by their UUIDs after the overview shows (`element.get` per element only when that call fails, because one is gone or a UUID is in two repositories), and an element that is gone (`ref.unknown`, `ref.ambiguous`) is left out; when a name cannot be read for another reason (core restarting), the stored buffers stay as they are and nothing is stored until the workspace opens again. A result buffer comes back only when the catalog lists its command as an implemented read command and runs it again when shown, so a restore never writes. The app stores the buffers on every change of them, but only once the buffers of that workspace are restored, so the reset of a start or a switch never overwrites them. When the name or the repositories of the open workspace change, the buffers move to the new key. Buffers the mode „Agent folgen“ opened are open buffers and come back too; the mode does not (SR-117). After "Close all buffers" only the overview comes back.
- Elements with a value (SR-132, `value-list.ts`): from a value of the shown element, the list of every element of the workspace with that value, a list buffer with one filter step, the step "Filter list by property", "Filter list by status" or the overview's type line adds (SR-124, SR-118), so it narrows further like any list. Which values qualify is `element.facets` for the element (`selection.ids`: its short ID), the rule of filtering: the status, the type, the values of choice and relation properties, and free text with few shared values; long free text (title, rationale, acceptance criteria) never. It is asked when the element is shown and again only when the element's type, status or properties change or something changes outside, not after a save of the text. "List elements with this value" (Ctrl/Cmd+Shift+Enter; on macOS only Cmd) takes the value at the cursor: the line with the caret in a text box, the focused target of a relation box, the box of a choice; a box with several values, a free-text box and every place outside a box ask in the minibuffer "Elements with" among the listable values (status first, then type, then the boxes in their order). From the command prompt it takes what the cursor was on before the prompt opened. Input is saved first, so the value typed is the one listed. Ctrl/Cmd+Enter stays "Follow reference" (spec question #610 F1); a target link (of a relation box or a relation group) opens itself only on Enter without Ctrl, Cmd or Alt, so both keys reach the window there, and "Follow reference" on a focused target link, in a box or a group, opens that target. Side effects: Alt+Enter on a link opens nothing, and on macOS the physical Ctrl+Enter on a link opens nothing (Cmd+Enter does); Shift+Enter still opens it. Pure display and input building (ADR-0002 rule 3), no catalog entry.
- Neighbourhood (SR-107): a buffer of its own, opened from an element with Ctrl/Cmd+J and left the same way. It shows the children as a tree and the incoming relations and references by kind. Both are `trace.neighbourhood`: the tree with `meanings: ["derivation"]` from the element and a growing `maxDepth` (the deepest open row plus two, so every shown row knows whether it has children; Up/Down select a row, the first Down the first row, SR-122; Right and Left open and close a row), the groups from one unfiltered call of depth 1. The element is named by UUID and repository (`repository` input, as `element.get`). The parents line above the title of every element page is `trace.neighbourhood` with `direction: "up"`. The app builds the inputs and shows the output in the order of the walk (ADR-0002).
- Traceability matrix (SR-125): a mode of the list buffer (`ListBuffer.matrix`, D-062), not a buffer of its own: Ctrl/Cmd+T ("Show traceability matrix") shows the list as a table and Ctrl/Cmd+T ("Show as list") brings the rows back, the selected row kept. The matrix has the key of the list, so it replaces the list in place and "Filter list by ...", "Clear list filter" and "Sort list" keep the mode (they rebuild the list from its steps and carry the flag). A package page offers the same shortcut and opens the list of its members (`where.package`, its sort) in matrix mode. The table is `trace.matrix` for the selection and sort of the list (the same input as `element.list`, so rows, columns, cells, counts and shares are what CLI, API and MCP give, ADR-0002, SR-080): one row per element, one column per relation kind and direction that occurs, each cell the elements at the other end as "<identifier or short ID> <title>", a "—" in the accent colour for a gap, "outdated" and the state of an end that is not there ("missing") marked as in the element view, and above each column "<count> · <share> %" over the whole selection. The app computes nothing: it formats the share as a whole percent and lays the answer out. Up/Down select a row (the first Down selects the first row, SR-122), Right/Left step through the row element and the relations of its cells, Enter or a click opens the element (an end that is not there opens nothing and the modeline says why). Rows come in pages of 200 as in the list. Search results and the neighbourhood have no entry yet.
- Lists of the main window (SR-122 AK4, AK5, `keys.ts` `rowTarget`): the overview, a list (also filtered and as a tree), a search result, the matrix, the elements of a package page, the neighbourhood (tree and incoming groups), the result buffer of a catalog command (SR-073) and the metamodel as text (SR-130, which always has a row selected: the type selected in the graph). A fresh list has no row selected (`NO_ROW` in `buffers.ts`). Down and Ctrl+N go one row down (with no row selected, to the first), Up and Ctrl+P one row up, Page Down/Up, Home and End as before. Ctrl+N and Ctrl+P are the physical Ctrl key alone (also on macOS; Cmd, Shift and Ctrl+Alt, which is AltGr on Windows, do not count). With a row selected the list takes the physical Ctrl+P, also on its first row, so it only moves the selection there on every platform (AK5); Cmd+P on macOS always jumps. With no row selected, and in a list without rows, the list does not take Ctrl+P: it stays "Go to" (SR-118 AK3 and SR-115 AK1 right after the start). A key that acts on "the row" selects the first row first when none is selected and acts on it in the same handler: Enter opens it, Right and Left in the neighbourhood open, close or select it, Right and Left in the matrix select it on its element (the next Right steps). A click and Enter keep the opened row as the cursor, as before. On a package page Ctrl+N on the page (the article or a field that has the focus itself, never from an editor or the list) selects the first element and enters the list; Ctrl+P on its first row leaves it like Up; Ctrl+P on the page outside the list is "Go to". The list prevents the keys it takes, so the window skips them. Pure display (ADR-0002 rule 3), no catalog entry.
- Split window (SR-115 AK3, `window-layout.ts`, `BufferArea.tsx`, actions "Split window", "Other window" and "Unsplit window"): commands of the prompt, no keys (#472), no catalog entry (pure display, ADR-0002 rule 3, like Follow agent). The sheet holds one area, or two of equal width side by side, parted by a quiet rule; an area has no heading, label or tab (AK2), and nothing marks the active one: the modeline names its buffer (D-062). The buffers stay one list in the order of use; the first is shown in the active area, and the layout (`{ active, other }`, `other` the key of the inactive area's buffer) is settled in the same reducer step as every buffer action, so the two never disagree. Rules: "Split window" keeps the shown buffer on its side and puts the buffer used before beside it, beside a single buffer the overview; with only the overview it is not offered. Of the actions that keep both areas, only `open` and `switch` change the active area (closing the active buffer and another workspace change it as below): choosing the inactive area's buffer (Go to, Next buffer, "Other window", a row that opens it) makes that area active and the other one shows what was active, so a buffer is never in both areas; a press or a focus in the inactive area does the same (an open prompt is cancelled then). `cursor`, `select`, `restore` and `update` (a view that read its data again replaces its buffer in place, so a result in the inactive area never becomes active) leave the areas as they are. "Close buffer" on the active area leaves one area, the other one; when the inactive area's buffer goes otherwise (Follow agent closes the buffer it opened, "Close all buffers", the 30 kept push one out) the area shows the next buffer in the order of use, and with none the window has one area. So with Follow agent on in a split, after the user makes their own buffer's area active, the next access opens the agent's element there and the user's buffer moves to the other area, which is mounted again (#744 asks the product owner whether an access should instead replace the mode's buffer in the inactive area); "Unsplit window" keeps the active area; another workspace starts with one area. The split is display state: it is not stored and not restored (AK4). Commands, Ctrl/Cmd+P, Alt+N/P and Follow agent act on the active area; only its element view gives the app its controls, and an element whose area becomes inactive saves its input at once (SR-105 AK1). The views of the right area prefix their DOM ids (`area-scope.ts`), so two lists side by side share no id. A graph or the metamodel opens on its selected node again when a split or unsplit changes its width. Working flow for the AK3 example: an element, Ctrl/Cmd+Shift+G for its graph, then "Split window" ("Split window" first and Ctrl/Cmd+Shift+G after it replaces the element in the active area by its graph).
- Next and previous buffer (SR-115 AK5, `opening-order.ts`, actions "Next buffer" and "Previous buffer"): Alt+N and Alt+P, Option+N and Option+P on macOS, show the buffer opened after or before the shown one, after the last the first. The order is the order of opening, not of use: App keeps it in a ref next to the buffers (`openingOrder`), so the `Buffers` type and the order of use (Ctrl/Cmd+P, the shown buffer) stay as they are. A buffer replaced in place (a list filtered, sorted or shown as matrix, a neighbourhood with a row opened) keeps its key and so its place; a closed buffer leaves the order and comes last when opened again; a buffer the 30 kept push out leaves it; opening a workspace starts again with the overview, and the buffers restored behind it (SR-115 AK4) take their stored order, before those opened while they were read. Switching moves the shown buffer to the front of the order of use, so it also counts as used (the candidates of Ctrl/Cmd+P, and an element as a recent element of the overview). The actions are offered and take the key only while more than one buffer is open. The keys are Alt alone: `matches` counts the letter (Linux and Windows; with Dvorak there the letter, not its place) or, when the key is no Latin letter, the physical key (`event.code`), since on macOS Option+N is a dead key ("Dead", the "~") and Option+P is "π"; so on macOS the place counts, also with Dvorak, and a non-Latin layout (Russian Alt+N "т") matches by the place. Not while an input method composes (`isComposing`, key "Process"), and not with Ctrl+Alt (AltGr) or Cmd+Option. The keys work everywhere, also in the text editor and a property box (product owner decision on a decision card, 2026-10-27: Alt+N and Alt+P switch the buffer in every context): CodeMirror binds no Alt-N or Alt-P, so the window's listener takes the key and prevents it. On a German Mac "~" is then typed only through the slash menu or by pasting. How no character comes into the editor on macOS: Chromium hands the dead key to the input method before the page sees the keydown, so `preventDefault` alone is not proof. The action first takes the focus out of a focused editor (`leaveEditor`, synchronously in the keydown), then switches: React shows the other buffer in a microtask after the listener, which unmounts the editor, the App's focus effect puts the focus on the new buffer, which cannot be edited, and a composition aimed at a focus that is no text input inserts nothing. Taking the focus out first also covers a later layout where the editor stays shown (a split window, SR-115 AK3). Playwright and happy-dom cannot type a real dead key; tests send the keydown macOS sends, and a manual check on a Mac confirms it. In an open prompt Alt+N and Alt+P are the prompt's: they type what the layout gives and switch nothing (an assumption, PR of SR-115 AK5). Pure display (ADR-0002 rule 3), no catalog entry. A restore of the buffers (SR-115 AK4) keeps this order.
- Package page (SR-112): an element whose type has the meaning `package` shows below its title, text, properties and relations the elements that name it (`element.list` with `where.package`, read-only like any list). They sort and show as a tree with "Sort list" like any list; Down on the page goes into them, Escape and Up on the first row come back. The page stays the element buffer, so the editor, saving and the draft are unchanged; the list is a part of it, not a buffer of its own. The modeline names the page by its type and the number of its elements, as the list reports it (SR-114 AK3).
- Follow agent (SR-117, `follow.ts`, `use-follow.ts`): the mode „Agent folgen“ is display state of the renderer (ADR-0002 rule 3, SR-080 AK1): off at the start, never stored, switched only by the actions "Follow agent" and "Stop following agent" (one key, Ctrl/Cmd+Shift+O, with availability that excludes each other; in the command prompt too), never by a catalog command, an app argument or the bridge (AK4). While it is on, each `agent-activity` shows the element of the access: its open buffer, else its buffer after one `element.get` (also after a change, since the name may have changed; a change of the shown element asks it again). Turning it on shows the access `workspace.activity` gives, and so does a restart of the core process while it is on; an access that is not newer than the one shown or held is dropped, and a lookup a newer access replaced is dropped. Unsaved input holds an access back (AK5): a draft in any buffer or an open prompt, in one function (`holdOf`); the latest held access is shown once neither is there, unless only the prompt held it and the user chose something in it (a buffer, a command, a filter or sort in place, also an action that does not navigate; the minibuffer tells a choice from Escape): his choice is newer, and the next access moves the view again (A3). Escape shows the held access. A dropped access counts as shown, so a pull after a restart does not bring it back. The mode closes the buffer it opened for the access before, in the same batch, never one with a draft and never the target, and only while it is the mode's (the user showing it himself or typing in it makes it his); what the mode shows is no recent element of the overview (SR-118). The modeline mark, after the workspace marks and before `stopped`, is `following agent`, or `following agent: waits for save` while a draft holds an access back (greys only, D-062). Opening another workspace ends the mode.

# ADR-0010, part: Bridge and channels

Part of [ADR-0010](../0010-electron-app.md). Read this part when you work on `src/preload/bridge.ts`, `src/main/` (the channels from the renderer to main); the decision itself is in the ADR.

- *Bridge (#322):* it is generic over the catalog and offers only seven functions:
  - `invoke` resolves to `{ ok: true, output }` or `{ ok: false, error }` with the error object of every access. It never rejects, because the context bridge keeps only an error's message.
  - `commands()` gives the catalog entries with `implemented`, as `GET /v1/commands` of the API does.
  - `copyText(text)` (SR-128) puts a text on the system clipboard and resolves `true`, or `false` when it could not. It never rejects. It is a facility of the window like the theme, so it is no catalog command (ADR-0002): it computes nothing, and CLI, API and MCP already give every value of a field with `element get` (SR-080). It is one of the four channels from the renderer to the main process, `ipcRenderer.invoke("reqseq:copy", text)` answered by `ipcMain.handle`; the renderer's own clipboard API is not used, because the session refuses every permission. The renderer is not trusted, so main writes the clipboard with `clipboard.writeText` only for a string of at most 16 Mi characters, from `event.senderFrame` that is the main frame of the web contents of the ReqSeq window, whose URL has the protocol `app:` and the host `reqseq` (`main/sender.ts`, the check of every channel from the renderer); anything else, and a clipboard that cannot be written, resolves `false` and writes nothing. Nothing is ever read from the clipboard.
  - `recentWorkspaces()` (SR-131) resolves the workspaces opened last, the most recent first, each `{ root, state }` with `state` `open` (the workspace of this window), `found` or `missing` (its workspace file is gone, AK4); `openWorkspace(root)` opens a root of that list in this window in place of the open workspace, and `openWorkspace(path, { typed: true })` the workspace found from a typed folder path upwards (AK5); it resolves `{ ok: true }` or `{ ok: false, reason }` with `missing`, `refused`, `unsaved` (the window could not save its input, AK3), `timeout` (the window did not answer in time), `busy` (another switch is running) or `no-workspace` (no folder from the typed one upwards holds a workspace), and the window learns the switch as `workspace-changed` with `opened`. They are two more channels to main (`reqseq:recent-workspaces`, `reqseq:open-workspace`), with the sender check of `copyText`; the preload checks main's answers, and anything of another shape is the empty list or a refusal, so neither rejects. They cannot go over the port: no core process, and so no port, exists while no workspace is open, and switching the workspace of the window is main's job. Switching is no catalog command: it is a function of the window (D-062, one workspace per window), and CLI, API and MCP choose their workspace with `--workspace` (ADR-0009). The list itself is a value CLI, API and MCP give too (SR-080 AK4; spec question #522, whose assumption is yes): the read command `workspace.recent` over the same core function (`recentWorkspaceStates`), with `exists` in place of the window's `state`, since only the window has an open workspace to mark. The app keeps reading the list through main, because without a workspace it has no port.
  - `onSave(save)` (SR-131 AK3) sets the function that saves the unsaved input of the window when main asks before a switch or before the window closes (`save({ closing })`), and returns the function that unsets it. Main asks on `reqseq:save` (`{ id }`) before every switch, from "Open workspace" and from File > Open Workspace, while a workspace is open and the page has loaded; the preload calls the function and answers on `reqseq:saved` (`{ id, saved }`, the fourth channel to main, with the sender check), `saved` only for `true` (a rejection, or anything else, is not saved; without a function nothing is unsaved). Main opens the other workspace only on `saved`; `false` keeps the open workspace (`unsaved`), and so does no answer within 30 s (`timeout`): main then sends `{ id, expired: true }`, which the preload passes on as the event `save-expired`, so the window says why nothing opened. A switch never carries on without the window's answer. Main runs one switch at a time: another one while it waits for the answer or for the core process answers `busy` and asks for no second save (File > Open Workspace then opens nothing and logs a line; the window says "Opening another workspace…"). The folder chosen in the dialog stays in main: the window only saves. Saving is the window's (`switch.ts`): each element buffer with a draft, the shown one last, is read with `element.get` and saved with `element.update` as "Save element" saves it; the first that cannot be saved (a value core refuses, an element that cannot be read, a file changed outside since the draft was typed on) stops, keeps its draft and is named in the minibuffer (spec question #523). A draft is dropped only when it is still the one that was saved; input typed meanwhile stops the switch and is kept, on the file as that save left it (its text, its boxes and its bytes), so the next switch or the view of that buffer does not take the app's own write for a change on disk. The editor of the shown buffer compares with a base of its own: when it reads the file again after such a save, it shows the app's write as a change on disk, which "Resolve change on disk" settles; both need input typed after `save-expired` released the window while its save still ran. From main's request until the other workspace is open (`workspace-changed: opened`), or the switch fails, the window takes no input: the sheet is `inert`, keys and commands are ignored, and the minibuffer says "Opening another workspace…" until the new workspace answers. At `opened` the old buffers, drafts and undo histories are reset at once, before the new workspace has loaded, so nothing of the old one can take input or be saved over the new port, and the window takes input again at once: a load that hangs never keeps it locked, and "Open workspace" or File > Open Workspace can choose another one. The overview of the new workspace comes with its `workspace.status`. It is no catalog command: it saves with catalog commands, and the request is the window's. Closing the window is leaving the element (SR-105 AK1), also on a quit, since Electron closes the window first: main prevents the first `close` (`main/close.ts`) and sends `{ id, closing: true }` on the same channel; the window saves in the same way, without the switching state, and main closes it on `saved`. `false` keeps the window open, and the window says why in the minibuffer and lets the next close discard its input (no dialog, AK3); no answer within 2 s keeps it open too: main sends `{ id, expired: true, closing: true }` (the event `save-expired` with `{ closing: true }`, so the window says it stays open and does not leave a switching state), and a close within 10 s goes through without asking, so a hung window can always be closed; a later close asks the window again. A close while a switch saves waits for that save. No new channel.
  - `on(event, listener)` subscribes to one of the events of the window and returns the function that unsubscribes; any other name subscribes nothing. All events share one channel (`BridgeEvents` in `shared/protocol.ts`, `{ event, data }` on the port): a new event is one entry there with the check of its data (`EVENT_DATA`), or, for an event that only main sends, its name in `WINDOW_EVENTS`, which the port never carries, and the bridge keeps its seven functions. Changes from outside the app (SR-116, SR-106) are no new event: they come as `workspace-changed` with the reason `external`. A window checks the data of every event as its schema does and passes on only those fields.
    - `workspace-changed` gets `{ reason }`: `opened`, `restarted`, `stopped`, `written` (a write command of the app) or `external`. Changes from outside the app (CLI, API, MCP, another editor, Git; SR-116, SR-106) are the batches of core's watcher (`watchWorkspace(...).onChange`, #331), which never reports the app's own writes: the core process passes each to the host, which sends it to every window as `{ reason: "external", scope, elements: { added, changed, removed } }` (UUIDs) and finds the repository folders again on the scopes `metamodel` and `workspace`. More than 1,000 UUIDs in all go as `scope: "workspace"` with empty lists (N-036). The preload checks the shape (the reason and scope enums, three lists of strings, at most 1,000) and passes only these fields. Transport only (ADR-0002): the renderer decides what to read again. An `external` change of scope `elements` reads neither the metamodel nor the status: an element buffer asks `element.get` again only when a change since the one it saw last names its element as changed or added (the app keeps, per UUID, the last change that named it, so two batches that arrive before a render are not lost; a `removed` that names it asks `element.get` too, see below), every other view (lists, the matrix, the neighbourhood, the overview, a result, the graph) asks again on each; the other scopes refresh everything as `restarted` does. An element changed or added outside is highlighted where a view shows it within 2 s of the change (SR-116 AK1): in the element buffer the fields whose shown value differs between the answer before and the new one (the title when none does, or when the buffer opened just then), and never one with input, and only when the `fileSha256` of the new answer differs from the one the buffer showed (so the app's own save, whose answer gives the hash it wrote, never flashes); in a list, the package page, the neighbourhood and the overview the row, in the matrix the row element. The mark is the class `outside-change`, a grey inset tint (token `--outside-change`, greys only) that fades in 2.5 s and is removed by one timer when the fade ends, 2.5 s after it was set, so a late timer still keeps AK2's 3 s, static with `prefers-reduced-motion`; no text, no control, the minibuffer stays silent (D-062). A list asked again for a change keeps its rows, selection and scroll until the answer is there, and Enter opens a kept row (its UUID stays valid), as a click does; a part (the package page) still waits for the answer, as before. An outside change of an element with input in its buffer (SR-106, SR-116 AK3; `renderer/outside-change.ts`, pure, the buffer only wires it) is decided per field from the outputs of `element.get`, on every read of the element (a targeted change, a full refresh, `written`, a buffer shown again with its draft), never from the event: the draft keeps the `fileSha256` its input was typed on, a field without input follows the file, a field whose input the file now holds has none any more, and when the bytes differ from those the input was typed on and input is left, nothing is saved (assumption, spec question #488 (1): any change of the file, not only one of a field with input). Then a read-only block "On disk" under every field with input shows the file's value (greys, the lines the input lacks in heavier weight by a line LCS, plain above 2,000 lines; the names of a choice, the labels of a relation), the modeline says `changed on disk`, the minibuffer says once how to resolve, and "Save element" says "Resolve the change on disk first". The action "Resolve change on disk" (command prompt, or Enter on a block; no key) asks "Keep my input" (one `element.update` with the fields with input and `expectedFileSha256` of the file now, so the outside change of every other field stays) or "Take the file" (the file's values into the editors as an edit, which Ctrl/Cmd+Z takes back; a choice or relation box drops its value). A later change that brings the file to the input or to the bytes it was typed on ends the conflict without asking. Every save sends `expectedFileSha256`; when core refuses it with `file.changed-on-disk`, one `element.get` decides: the same bytes (core's store lagged) save again once, silently; other bytes are the rule above. A read that fails with `ref.unknown` after the element was shown may still be a file being written (a pull): core's watcher reports it as removed in one batch and added in the next, and its store does not know the element in between. So the buffer stays as it is and editable, and asks once more after 2 s, longer than one batch (at most 1 s) and the time core takes to apply a large one; an `added` that names the element asks at once. Only a read that still fails then means the file is gone (SR-106 AK3): the editors keep their content read-only (Copy field works), the modeline says `deleted on disk`, the minibuffer names the deletion once, nothing is written or created; a later successful read (also on `added`) makes the buffer editable again and applies the rule above. The draft keeps the element its buffer showed (`Draft.shown`), so a buffer that was not shown when its file was deleted shows its input again in the same way, not an error. Any other failed read keeps the buffer and only echoes the error.
    - `save-expired` (SR-131 AK3) gets `{}`: main gave up waiting for the window's save, and the open workspace stays. Before a close it gets `{ closing: true }` (SR-105 AK1): the window stays open, and a close within 10 s closes it without waiting. It comes from main only (`reqseq:save` with `expired`): the preload emits it itself, and a `save-expired` on the port is dropped, so a core process cannot release a window that saves.
    - `agent-activity` (SR-117) gets an access an agent made through the API or the MCP server of this copy, as `workspace.activity` gives it (`access`, `command`, `effect`, `at`, `element: { id, repository }`; no content). The core process watches `activity.json` in the cache folder of the copy with core's `watchActivity` (ADR-0008, ADR-0009; one folder watch, no socket), and the host sends each new access to every window once the app's store holds the state the access saw, at the latest after 1 s. Nothing is sent when a window connects: the renderer asks `workspace.activity` for the last one. A port that is gone does not stop the others. The app's own calls pass the access `app` (ADR-0002 rule 4), which core does not record, so the app never follows itself. Why accesses cannot be seen (no cache folder outside the repositories, no watch) is a log line of the core process.
- Channels from the renderer to main (`copyText`, `recentWorkspaces`, `openWorkspace`, and the answer of `onSave`): each takes only messages of the main frame of the ReqSeq window (`main/sender.ts`). That shuts out other frames and contents, not a compromised renderer, which is bounded by the input checks: `reqseq:open-workspace` checks the type, the length (at most 4096 characters) and NUL before it reads anything, then opens only a root that is, character for character, a root of the stored list, read again for each request (no other folder, no other spelling, no `canonicalRoot` in main), or, for a typed path (`typed`), a path that core's lexical check takes before any file-system call (absolute or `~`, never relative, and on Windows only a path on a drive, `C:\…`, after `~` is expanded and the path normalised: no UNC, device or NT path such as `\\host\share`, `\\?\…` or `\??\UNC\…`, also written `/??/…`, and no `\foo` on the current drive) and from which upwards a folder holds a workspace file. So a compromised renderer can switch among the user's recent workspaces and open any workspace whose local path it can name: it can never open a folder without a workspace, and it can never make main touch a UNC path (`\\host\share`, which would make Windows open an SMB connection, SR-078). An answer on `reqseq:saved` only lets main go on with a switch the renderer could ask for anyway. Main makes no synchronous file-system call for these channels (a hung share would freeze the window): the canonical keys are stored, and the existence check is core's asynchronous one, with 1 s per request and at most 4 `stat`s at once, each kind with slots of its own (`WorkspaceChecks`: 2 for the roots of the list, 1 for the chosen root of the list, 1 for the folders of a typed path), so roots of the list on a dead share take at most 2 of the 4 threads of the thread pool that also serves `app://`; all 4 only when a chosen root and a typed path hang too (one slot each, the price of keeping a typed path from blocking a chosen root, #574); then main's other asynchronous file calls (the read of the list itself, `app://`) wait as well until a `stat` returns, and File > Open Workspace still opens. The only file-system calls that reach a share are the `stat`s of roots the user opened before (unless someone else changed the file of the list) and of local paths the user typed. A typed path under an automounter (`/net/<host>/…` with autofs `/net -hosts` on Linux, or `/net` in `auto_master` on macOS), or on a mapped network drive on Windows (`Z:\…`, also a `subst` of a UNC path), is local by its text, and its `stat` makes the OS mount or connect to that host's share: that is the user's choice (or a compromised renderer's), and it reaches the network as File > Open Workspace on that folder would. A root of the list that was chosen is checked again with a slot of its own, so roots on a dead share cannot keep a local workspace from opening, and the folders of a typed path have one of their own, so a typed path on a dead mount blocks only further typed paths; the walk upwards from a typed folder stops at a folder whose check timed out (`no-workspace`), so a slow folder never opens a workspace above the one that was meant; reading the list never waits on a FIFO or a device in its place (`O_NONBLOCK`, files only).

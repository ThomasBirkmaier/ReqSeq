# ADR-0010: Electron app: process model and security

Status: Proposed · Based on: D-003, D-004, D-019, D-029, D-061, D-062, D-063 · SRs: SR-065, SR-066, SR-073, SR-074, SR-076, SR-077, SR-078, SR-082, SR-100, SR-104, SR-106, SR-111, SR-113, SR-115, SR-116, SR-117, SR-125, SR-127, SR-128, SR-129, SR-130, SR-131, SR-132

## Decision

**Processes**
- *Main process:* windows, menus, file dialogs, the API server when enabled, and the switch to a recent workspace or to the workspace of a typed folder that the window asks for (SR-131). No program logic: the list of recent workspaces, its existence checks and the check of a typed path are core's (`@logreq/core/recent-workspaces`, a module of its own that loads no schema validator and no command, imported on the first request, so the start of main loads no part of core).
- *Core process:* `core` runs in an Electron `utilityProcess` (plain Node), so long commands never block the window. Main passes a `MessagePort` between renderer and core process, a new one on every page load. There is one core process per open workspace, opened as `logreq serve api` opens it: the root is found upwards from the chosen folder (else the folder itself), the model cache lies in the cache folder of the copy, and the watcher starts before the load. Opening another workspace (File > Open Workspace, or "Open workspace" in the window, SR-131) first has the window save its unsaved input (SR-131 AK3, `onSave` below) and goes on only when the window answers that it is saved; then it stops the core process: running reads are aborted, running writes finish, then the workspace closes; the process is killed after 5 s. A root of the list of recent workspaces is opened exactly (`exact`): the folder itself is the root, and a folder without its workspace file fails, never opening a workspace above it. Once a workspace with a workspace file is open, the core process records its root in core's list of recent workspaces (`<OS cache>/logreq/recent-workspaces.json`, ADR-0008, `recordOpenedWorkspace`; not when that folder lies inside a repository of the workspace) and sends main its key with `ready`, so main can mark the open one; stopping waits for that write, and a failed write is a log line. The app stops it the same way before it quits. A write also finishes when its window goes away. A core process that cannot open its workspace ends with exit code 1.
- *Renderer:* UI only. It calls `window.logreq.invoke(name, input)` and subscribes to `window.logreq.on("workspace-changed", …)`, `on("agent-activity", …)` and `on("save-expired", …)` via a minimal preload bridge (`contextBridge`; the preload is one CommonJS bundle, as the sandbox requires). It cannot reach Node, the file system or the network.
- *Bridge (#322):* it is generic over the catalog and offers only seven functions:
  - `invoke` resolves to `{ ok: true, output }` or `{ ok: false, error }` with the error object of every access. It never rejects, because the context bridge keeps only an error's message.
  - `commands()` gives the catalog entries with `implemented`, as `GET /v1/commands` of the API does.
  - `copyText(text)` (SR-128) puts a text on the system clipboard and resolves `true`, or `false` when it could not. It never rejects. It is a facility of the window like the theme, so it is no catalog command (ADR-0002): it computes nothing, and CLI, API and MCP already give every value of a field with `element get` (SR-080). It is one of the four channels from the renderer to the main process, `ipcRenderer.invoke("logreq:copy", text)` answered by `ipcMain.handle`; the renderer's own clipboard API is not used, because the session refuses every permission. The renderer is not trusted, so main writes the clipboard with `clipboard.writeText` only for a string of at most 16 Mi characters, from `event.senderFrame` that is the main frame of the web contents of the LogReq window, whose URL has the protocol `app:` and the host `logreq` (`main/sender.ts`, the check of every channel from the renderer); anything else, and a clipboard that cannot be written, resolves `false` and writes nothing. Nothing is ever read from the clipboard.
  - `recentWorkspaces()` (SR-131) resolves the workspaces opened last, the most recent first, each `{ root, state }` with `state` `open` (the workspace of this window), `found` or `missing` (its workspace file is gone, AK4); `openWorkspace(root)` opens a root of that list in this window in place of the open workspace, and `openWorkspace(path, { typed: true })` the workspace found from a typed folder path upwards (AK5); it resolves `{ ok: true }` or `{ ok: false, reason }` with `missing`, `refused`, `unsaved` (the window could not save its input, AK3), `timeout` (the window did not answer in time), `busy` (another switch is running) or `no-workspace` (no folder from the typed one upwards holds a workspace), and the window learns the switch as `workspace-changed` with `opened`. They are two more channels to main (`logreq:recent-workspaces`, `logreq:open-workspace`), with the sender check of `copyText`; the preload checks main's answers, and anything of another shape is the empty list or a refusal, so neither rejects. They cannot go over the port: no core process, and so no port, exists while no workspace is open, and switching the workspace of the window is main's job. Switching is no catalog command: it is a function of the window (D-062, one workspace per window), and CLI, API and MCP choose their workspace with `--workspace` (ADR-0009). The list itself is a value CLI, API and MCP give too (SR-080 AK4; spec question #522, whose assumption is yes): the read command `workspace.recent` over the same core function (`recentWorkspaceStates`), with `exists` in place of the window's `state`, since only the window has an open workspace to mark. The app keeps reading the list through main, because without a workspace it has no port.
  - `onSave(save)` (SR-131 AK3) sets the function that saves the unsaved input of the window when main asks before a switch or before the window closes (`save({ closing })`), and returns the function that unsets it. Main asks on `logreq:save` (`{ id }`) before every switch, from "Open workspace" and from File > Open Workspace, while a workspace is open and the page has loaded; the preload calls the function and answers on `logreq:saved` (`{ id, saved }`, the fourth channel to main, with the sender check), `saved` only for `true` (a rejection, or anything else, is not saved; without a function nothing is unsaved). Main opens the other workspace only on `saved`; `false` keeps the open workspace (`unsaved`), and so does no answer within 30 s (`timeout`): main then sends `{ id, expired: true }`, which the preload passes on as the event `save-expired`, so the window says why nothing opened. A switch never carries on without the window's answer. Main runs one switch at a time: another one while it waits for the answer or for the core process answers `busy` and asks for no second save (File > Open Workspace then opens nothing and logs a line; the window says "Opening another workspace…"). The folder chosen in the dialog stays in main: the window only saves. Saving is the window's (`switch.ts`): each element buffer with a draft, the shown one last, is read with `element.get` and saved with `element.update` as "Save element" saves it; the first that cannot be saved (a value core refuses, an element that cannot be read, a file changed outside since the draft was typed on) stops, keeps its draft and is named in the minibuffer (spec question #523). A draft is dropped only when it is still the one that was saved; input typed meanwhile stops the switch and is kept, on the file as that save left it (its text, its boxes and its bytes), so the next switch or the view of that buffer does not take the app's own write for a change on disk. The editor of the shown buffer compares with a base of its own: when it reads the file again after such a save, it shows the app's write as a change on disk, which "Resolve change on disk" settles; both need input typed after `save-expired` released the window while its save still ran. From main's request until the other workspace is open (`workspace-changed: opened`), or the switch fails, the window takes no input: the sheet is `inert`, keys and commands are ignored, and the minibuffer says "Opening another workspace…" until the new workspace answers. At `opened` the old buffers, drafts and undo histories are reset at once, before the new workspace has loaded, so nothing of the old one can take input or be saved over the new port, and the window takes input again at once: a load that hangs never keeps it locked, and "Open workspace" or File > Open Workspace can choose another one. The overview of the new workspace comes with its `workspace.status`. It is no catalog command: it saves with catalog commands, and the request is the window's. Closing the window is leaving the element (SR-105 AK1), also on a quit, since Electron closes the window first: main prevents the first `close` (`main/close.ts`) and sends `{ id, closing: true }` on the same channel; the window saves in the same way, without the switching state, and main closes it on `saved`. `false` keeps the window open, and the window says why in the minibuffer and lets the next close discard its input (no dialog, AK3); no answer within 2 s keeps it open too: main sends `{ id, expired: true, closing: true }` (the event `save-expired` with `{ closing: true }`, so the window says it stays open and does not leave a switching state), and a close within 10 s goes through without asking, so a hung window can always be closed; a later close asks the window again. A close while a switch saves waits for that save. No new channel.
  - `on(event, listener)` subscribes to one of the events of the window and returns the function that unsubscribes; any other name subscribes nothing. All events share one channel (`BridgeEvents` in `shared/protocol.ts`, `{ event, data }` on the port): a new event is one entry there with the check of its data (`EVENT_DATA`), or, for an event that only main sends, its name in `WINDOW_EVENTS`, which the port never carries, and the bridge keeps its seven functions. Changes from outside the app (SR-116, SR-106) are no new event: they come as `workspace-changed` with the reason `external`. A window checks the data of every event as its schema does and passes on only those fields.
    - `workspace-changed` gets `{ reason }`: `opened`, `restarted`, `stopped`, `written` (a write command of the app) or `external`. Changes from outside the app (CLI, API, MCP, another editor, Git; SR-116, SR-106) are the batches of core's watcher (`watchWorkspace(...).onChange`, #331), which never reports the app's own writes: the core process passes each to the host, which sends it to every window as `{ reason: "external", scope, elements: { added, changed, removed } }` (UUIDs) and finds the repository folders again on the scopes `metamodel` and `workspace`. More than 1,000 UUIDs in all go as `scope: "workspace"` with empty lists (N-036). The preload checks the shape (the reason and scope enums, three lists of strings, at most 1,000) and passes only these fields. Transport only (ADR-0002): the renderer decides what to read again. An `external` change of scope `elements` reads neither the metamodel nor the status: an element buffer asks `element.get` again only when a change since the one it saw last names its element as changed or added (the app keeps, per UUID, the last change that named it, so two batches that arrive before a render are not lost; a `removed` that names it asks `element.get` too, see below), every other view (lists, the matrix, the neighbourhood, the overview, a result, the graph) asks again on each; the other scopes refresh everything as `restarted` does. An element changed or added outside is highlighted where a view shows it within 2 s of the change (SR-116 AK1): in the element buffer the fields whose shown value differs between the answer before and the new one (the title when none does, or when the buffer opened just then), and never one with input, and only when the `fileSha256` of the new answer differs from the one the buffer showed (so the app's own save, whose answer gives the hash it wrote, never flashes); in a list, the package page, the neighbourhood and the overview the row, in the matrix the row element. The mark is the class `outside-change`, a grey inset tint (token `--outside-change`, greys only) that fades in 2.5 s and is removed by one timer when the fade ends, 2.5 s after it was set, so a late timer still keeps AK2's 3 s, static with `prefers-reduced-motion`; no text, no control, the minibuffer stays silent (D-062). A list asked again for a change keeps its rows, selection and scroll until the answer is there, and Enter opens a kept row (its UUID stays valid), as a click does; a part (the package page) still waits for the answer, as before. An outside change of an element with input in its buffer (SR-106, SR-116 AK3; `renderer/outside-change.ts`, pure, the buffer only wires it) is decided per field from the outputs of `element.get`, on every read of the element (a targeted change, a full refresh, `written`, a buffer shown again with its draft), never from the event: the draft keeps the `fileSha256` its input was typed on, a field without input follows the file, a field whose input the file now holds has none any more, and when the bytes differ from those the input was typed on and input is left, nothing is saved (assumption, spec question #488 (1): any change of the file, not only one of a field with input). Then a read-only block "On disk" under every field with input shows the file's value (greys, the lines the input lacks in heavier weight by a line LCS, plain above 2,000 lines; the names of a choice, the labels of a relation), the modeline says `changed on disk`, the minibuffer says once how to resolve, and "Save element" says "Resolve the change on disk first". The action "Resolve change on disk" (command prompt, or Enter on a block; no key) asks "Keep my input" (one `element.update` with the fields with input and `expectedFileSha256` of the file now, so the outside change of every other field stays) or "Take the file" (the file's values into the editors as an edit, which Ctrl/Cmd+Z takes back; a choice or relation box drops its value). A later change that brings the file to the input or to the bytes it was typed on ends the conflict without asking. Every save sends `expectedFileSha256`; when core refuses it with `file.changed-on-disk`, one `element.get` decides: the same bytes (core's store lagged) save again once, silently; other bytes are the rule above. A read that fails with `ref.unknown` after the element was shown may still be a file being written (a pull): core's watcher reports it as removed in one batch and added in the next, and its store does not know the element in between. So the buffer stays as it is and editable, and asks once more after 2 s, longer than one batch (at most 1 s) and the time core takes to apply a large one; an `added` that names the element asks at once. Only a read that still fails then means the file is gone (SR-106 AK3): the editors keep their content read-only (Copy field works), the modeline says `deleted on disk`, the minibuffer names the deletion once, nothing is written or created; a later successful read (also on `added`) makes the buffer editable again and applies the rule above. The draft keeps the element its buffer showed (`Draft.shown`), so a buffer that was not shown when its file was deleted shows its input again in the same way, not an error. Any other failed read keeps the buffer and only echoes the error.
    - `save-expired` (SR-131 AK3) gets `{}`: main gave up waiting for the window's save, and the open workspace stays. Before a close it gets `{ closing: true }` (SR-105 AK1): the window stays open, and a close within 10 s closes it without waiting. It comes from main only (`logreq:save` with `expired`): the preload emits it itself, and a `save-expired` on the port is dropped, so a core process cannot release a window that saves.
    - `agent-activity` (SR-117) gets an access an agent made through the API or the MCP server of this copy, as `workspace.activity` gives it (`access`, `command`, `effect`, `at`, `element: { id, repository }`; no content). The core process watches `activity.json` in the cache folder of the copy with core's `watchActivity` (ADR-0008, ADR-0009; one folder watch, no socket), and the host sends each new access to every window once the app's store holds the state the access saw, at the latest after 1 s. Nothing is sent when a window connects: the renderer asks `workspace.activity` for the last one. A port that is gone does not stop the others. The app's own calls pass the access `app` (ADR-0002 rule 4), which core does not record, so the app never follows itself. Why accesses cannot be seen (no cache folder outside the repositories, no watch) is a log line of the core process.

**Security settings (all windows)**
- `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `webSecurity: true`, no `webview`, no `remote`.
- Content Security Policy, sent as a response header with every page: `default-src 'self'; img-src 'self' data: logreq-file:; style-src 'self' 'unsafe-inline'; script-src 'self'; connect-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; frame-src 'none'`.
- The renderer is loaded from a custom `app://` protocol serving the bundled files (`app://logreq/index.html`; no development server). Images of elements are served by a `logreq-file:` protocol, `logreq-file://workspace/<repository>/<path>`, that only serves image files inside an available repository of the workspace. The repository is in the path because Chromium canonicalises hosts like `1.2` into IPv4 addresses. The path is checked lexically first (no `\`, `:` or NUL, inside the repository folder), so no UNC share or automount is touched; then links are resolved and checked again. The core process reads the files, and main relays them.
- All navigation, `window.open` and webviews are denied. External links open in the system browser only after the user clicks them; that arrives with the first screen that shows links. Redirects and the navigation of every frame are denied too. Every permission request (camera, notifications, ...) and every device chooser (HID, serial, USB, Bluetooth) is refused. The spell checker is off, because it downloads dictionaries, and its download URL points at a local URL that serves nothing. The CSP adds `frame-src 'none'`.
- Menu: minimal, so the keys stay free for the minibuffer and buffers (D-061..D-063): File > Open Workspace (Ctrl/Cmd+O), Quit (Close on macOS), Edit. Reload (F5) and the developer tools (F12) only in unpackaged builds.
- Channels from the renderer to main (`copyText`, `recentWorkspaces`, `openWorkspace`, and the answer of `onSave`): each takes only messages of the main frame of the LogReq window (`main/sender.ts`). That shuts out other frames and contents, not a compromised renderer, which is bounded by the input checks: `logreq:open-workspace` checks the type, the length (at most 4096 characters) and NUL before it reads anything, then opens only a root that is, character for character, a root of the stored list, read again for each request (no other folder, no other spelling, no `canonicalRoot` in main), or, for a typed path (`typed`), a path that core's lexical check takes before any file-system call (absolute or `~`, never relative, and on Windows only a path on a drive, `C:\…`, after `~` is expanded and the path normalised: no UNC, device or NT path such as `\\host\share`, `\\?\…` or `\??\UNC\…`, also written `/??/…`, and no `\foo` on the current drive) and from which upwards a folder holds a workspace file. So a compromised renderer can switch among the user's recent workspaces and open any workspace whose local path it can name: it can never open a folder without a workspace, and it can never make main touch a UNC path (`\\host\share`, which would make Windows open an SMB connection, SR-078). An answer on `logreq:saved` only lets main go on with a switch the renderer could ask for anyway. Main makes no synchronous file-system call for these channels (a hung share would freeze the window): the canonical keys are stored, and the existence check is core's asynchronous one, with 1 s per request and at most 4 `stat`s at once, each kind with slots of its own (`WorkspaceChecks`: 2 for the roots of the list, 1 for the chosen root of the list, 1 for the folders of a typed path), so roots of the list on a dead share take at most 2 of the 4 threads of the thread pool that also serves `app://`; all 4 only when a chosen root and a typed path hang too (one slot each, the price of keeping a typed path from blocking a chosen root, #574); then main's other asynchronous file calls (the read of the list itself, `app://`) wait as well until a `stat` returns, and File > Open Workspace still opens. The only file-system calls that reach a share are the `stat`s of roots the user opened before (unless someone else changed the file of the list) and of local paths the user typed. A typed path under an automounter (`/net/<host>/…` with autofs `/net -hosts` on Linux, or `/net` in `auto_master` on macOS), or on a mapped network drive on Windows (`Z:\…`, also a `subst` of a UNC path), is local by its text, and its `stat` makes the OS mount or connect to that host's share: that is the user's choice (or a compromised renderer's), and it reaches the network as File > Open Workspace on that folder would. A root of the list that was chosen is checked again with a slot of its own, so roots on a dead share cannot keep a local workspace from opening, and the folders of a typed path have one of their own, so a typed path on a dead mount blocks only further typed paths; the walk upwards from a typed folder stops at a folder whose check timed out (`no-workspace`), so a slow folder never opens a workspace above the one that was meant; reading the list never waits on a FIFO or a device in its place (`O_NONBLOCK`, files only).
- `session.webRequest.onBeforeRequest` cancels every request that is not `app:`, `logreq-file:` or `devtools:` (SR-078).
- No auto-updater, no crash reporter upload, no telemetry (SR-078). Electron fuses (ADR-0014): `RunAsNode` on for the CLI launcher (a fuse applies to the whole binary), `EnableNodeCliInspectArguments` and `EnableNodeOptionsEnvironmentVariable` off, `OnlyLoadAppFromAsar` on.

**UI** (D-061..D-063)
- React with TypeScript, bundled with `electron-vite`. A white sheet (D-062): the window shows one buffer, or two side by side after "Split window" (SR-115 AK3, below) (a list, a search result, an element, a neighbourhood, a graph (D-063), the metamodel (SR-130) or the result of a catalog command laid out by its shape), a quiet modeline (a display, not a control, with one exception: the ID of an element carries the copy symbol of a field, below) and the minibuffer. There is no tab bar, no permanent sidebar or tree, no form and no modal dialog (SR-100 AK1). Colour only for meaning: greys, and one accent colour for "outdated" and for a gap in the traceability chain ("—" in a cell of the matrix, D-062: „Farbe trägt nur Bedeutung, zum Beispiel veraltet oder Lücke in der Kette“; the token `--accent-gap` has the value of `--accent-outdated`).
- The first buffer of a workspace is the overview: one line per element type with its count (`element.facets`) and the five elements opened last; the full list opens only with "List all elements" (SR-118). Closing the last buffer shows the overview. The elements opened last are display state of the app (UUID and repository, per workspace) in the app's local storage, not in the workspace.
- Open buffers after a restart (SR-115 AK4, `buffer-session.ts`): the buffers open when the window closed, or when the workspace was left for another, are display state like the elements opened last: kept per workspace in the app's local storage (`logreq.buffers.v1` with the name and repositories of the workspace, a literal like `logreq.recent.v1` and `logreq.usage.v1`, so a rename renames the three together), never in the workspace (SR-118 AK5) and through no catalog command (SR-080 AK1). When the workspace opens, the overview shows first (SR-118 AK1) and the stored buffers come back behind it, in their order of use and their order of opening (SR-115 AK5). Stored is what rebuilds a buffer, never a title, a text, an output or a selected row; the names of elements are read with one `element.list` by their UUIDs after the overview shows (`element.get` per element only when that call fails, because one is gone or a UUID is in two repositories), and an element that is gone (`ref.unknown`, `ref.ambiguous`) is left out; when a name cannot be read for another reason (core restarting), the stored buffers stay as they are and nothing is stored until the workspace opens again. A result buffer comes back only when the catalog lists its command as an implemented read command and runs it again when shown, so a restore never writes. The app stores the buffers on every change of them, but only once the buffers of that workspace are restored, so the reset of a start or a switch never overwrites them. When the name or the repositories of the open workspace change, the buffers move to the new key. Buffers the mode „Agent folgen“ opened are open buffers and come back too; the mode does not (SR-117). After "Close all buffers" only the overview comes back.
- "Open workspace" (SR-131, `workspaces.ts`): an action of the command prompt, no shortcut (File > Open Workspace and Ctrl/Cmd+O keep the native folder dialog). It asks in the minibuffer for one of the workspaces opened last (`recentWorkspaces()`), by full path, in main's order, the most recent first; the prompt opens at once and fills when the list arrives, and typing narrows it with the ranking of the command prompt (`fuzzy.ts`, equal matches keep the order). The hints are muted words, no colour (D-062): "open" for the workspace of the window, "not found" for one whose workspace file is gone (it stays in the list until newer ones push it out; there is no remove action). Choosing another found one calls `openWorkspace`; the window then starts again with the overview of the new workspace (same window, no reload, no restart). Choosing the open one, or one not found, opens nothing and says so in the minibuffer ("… is not found; <name> stays open"). A typed text that starts with `/` or `~`, and on Windows also one that starts with `\` or a drive letter with `:` and a separator, is a folder path (AK5, spec question #524): its choice "Open <path>" (hint "folder") comes first (`Prompt.literal`), so Enter opens the workspace found from it upwards, which is then first in the list; a path without a workspace, or one main refuses, opens nothing and says so (a refused one "<path> could not be opened": main also refuses when it cannot load core's module of the list, so the window cannot tell the two apart). Before every switch, also from File > Open Workspace, the unsaved input of every buffer is saved (AK3, `onSave` above); input that cannot be saved keeps the open workspace and the minibuffer says "<element> could not be saved (<reason>); the workspace was not changed". Without an open workspace the command prompt still opens (Ctrl/Cmd+Shift+P, or a click on the idle minibuffer) and offers only the actions that apply then, "Open workspace"; no other shortcut works without a workspace. The catalog is asked for again when a workspace opens after a start without one.
- "Create element" (SR-064, `catalog-commands.ts`, `create-element.ts`): the catalog command `element.create` in the command prompt by its title, no action of its own and no shortcut. It asks its arguments like any catalog command, and between the required arguments and the optional ones the required properties of the type (product owner decision, 2026-10-28: they are asked one after the other in the command line, no form, D-062). The type is one of the types of `metamodel.get` that are not abstract, by name, in the order of the metamodel; the title is typed text, also empty (core saves it with its hint). Then each required property of the type but the title, in the order of `required`: a choice among the choices of the metamodel (a list: those not taken yet), a relation target among the elements `element.search` finds among its target types, a text kind as typed text; a list takes one value per Enter. An empty input skips the property, or ends the values of a list. Backspace in an empty input goes back one answer; Ctrl/Cmd+Enter offers the optional arguments `text`, `repository` and `folder` once the required properties are answered, never `properties` (the other properties are added in the element buffer, "Add property"). The values go into `properties` as the box of the property would save them (`inputValueOf`), so the app decides nothing about them; core validates, and a refused input asks the property core names again with core's message (the rule of the catalog commands below). Nothing is written before the last answer; then one `element.create`, and the new element opens in its element buffer with its title, its text and the boxes of the properties given (an empty required property shows no box, D-062). The minibuffer says "Created <ID> <title> · <n> hints"; the modeline counts the hints while the properties are empty, and "Add property" offers them with every optional property of the type (SR-064 AK3).
- Command prompt ranking (SR-108 AK3, SR-121 AK2, SR-133, `usage.ts`): what was chosen is display state of the app, like the elements opened last: kept in the app's local storage under `logreq.usage.v1`, not per workspace (the commands are the same in every workspace) and never in the workspace or through a catalog command (SR-080 AK1: "außer reiner Darstellung der App"). Only the command ID and the text typed in the command prompt are recorded, with the count and the time of the last use (at most 500 commands and 500 texts); nothing for "Go to", argument steps or elements. Order: the match comes first (initials, letters in order, one slip per word); equally good matches, and every command when nothing is typed, go first by fit to the shown view (SR-133: every action shown, since it is shown only where it applies, and a catalog command whose argument the view gives: a list its selection, an element or a neighbourhood its element to a required element argument), then by use (uses divided by one plus the days since the last one); the command chosen the last time for exactly this text (lower case, spaces collapsed) comes first, when it is offered and matches now. A storage that is missing or throws gives the plain order.
- Minibuffer: the only control, apart from two exceptions: the copy symbols of the fields (SR-128, below; seen only on hover or focus) and the editor's transient `/` menu at the caret (SR-129, below; whether D-062 allows it is the spec question #453, until it is answered the menu only inserts formatting). Ctrl/Cmd+Shift+P opens the command prompt, Ctrl/Cmd+P jumps to an open buffer or to an element, Ctrl/Cmd+Shift+F searches; each entry shows its shortcut. Commands, Ctrl/Cmd+P, Alt+N/P and Follow agent act on the active area; only its element view gives the app its controls, and an element whose area becomes inactive saves its input at once (SR-105 AK1). The views of the right area prefix their DOM ids (`area-scope.ts`), so two lists side by side share no id. A graph or the metamodel opens on its selected node again when a split or unsplit changes its width. Working flow for the AK3 example: an element, Ctrl/Cmd+Shift+G for its graph, then "Split window" ("Split window" first and Ctrl/Cmd+Shift+G after it replaces the element in the active area by its graph).
- Next and previous buffer (SR-115 AK5, `opening-order.ts`, actions "Next buffer" and "Previous buffer"): Alt+N and Alt+P, Option+N and Option+P on macOS, show the buffer opened after or before the shown one, after the last the first. The order is the order of opening, not of use: App keeps it in a ref next to the buffers (`openingOrder`), so the `Buffers` type and the order of use (Ctrl/Cmd+P, the shown buffer) stay as they are. A buffer replaced in place (a list filtered, sorted or shown as matrix, a neighbourhood with a row opened) keeps its key and so its place; a closed buffer leaves the order and comes last when opened again; a buffer the 30 kept push out leaves it; opening a workspace starts again with the overview, and the buffers restored behind it (SR-115 AK4) take their stored order, before those opened while they were read. Switching moves the shown buffer to the front of the order of use, so it also counts as used (the candidates of Ctrl/Cmd+P, and an element as a recent element of the overview). The actions are offered and take the key only while more than one buffer is open. The keys are Alt alone: `matches` counts the letter (Linux and Windows; with Dvorak there the letter, not its place) or, when the key is no Latin letter, the physical key (`event.code`), since on macOS Option+N is a dead key ("Dead", the "~") and Option+P is "π"; so on macOS the place counts, also with Dvorak, and a non-Latin layout (Russian Alt+N "т") matches by the place. Not while an input method composes (`isComposing`, key "Process"), and not with Ctrl+Alt (AltGr) or Cmd+Option. The keys work everywhere, also in the text editor and a property box (product owner decision on a decision card, 2026-10-27: Alt+N and Alt+P switch the buffer in every context): CodeMirror binds no Alt-N or Alt-P, so the window's listener takes the key and prevents it. On a German Mac "~" is then typed only through the slash menu or by pasting. How no character comes into the editor on macOS: Chromium hands the dead key to the input method before the page sees the keydown, so `preventDefault` alone is not proof. The action first takes the focus out of a focused editor (`leaveEditor`, synchronously in the keydown), then switches: React shows the other buffer in a microtask after the listener, which unmounts the editor, the App's focus effect puts the focus on the new buffer, which cannot be edited, and a composition aimed at a focus that is no text input inserts nothing. Taking the focus out first also covers a later layout where the editor stays shown (a split window, SR-115 AK3). Playwright and happy-dom cannot type a real dead key; tests send the keydown macOS sends, and a manual check on a Mac confirms it. In an open prompt Alt+N and Alt+P are the prompt's: they type what the layout gives and switch nothing (an assumption, PR of SR-115 AK5). Pure display (ADR-0002 rule 3), no catalog entry. A restore of the buffers (SR-115 AK4) keeps this order.
- Package page (SR-112): an element whose type has the meaning `package` shows below its title, text, properties and relations the elements that name it (`element.list` with `where.package`, read-only like any list). They sort and show as a tree with "Sort list" like any list; Down on the page goes into them, Escape and Up on the first row come back. The page stays the element buffer, so the editor, saving and the draft are unchanged; the list is a part of it, not a buffer of its own. The modeline names the page by its type and the number of its elements, as the list reports it (SR-114 AK3).
- Graph (SR-111, D-063): a buffer of its own. One topic per line:
  - Open and keys: opened from an element or its neighbourhood with Ctrl/Cmd+Shift+G ("Show graph", the title of `trace.graph`, which the action `covers`, so the prompt never opens it as a result buffer) and left the same way ("Show element"). Not Ctrl/Cmd+G: Ctrl+G is the Emacs keyboard-quit (SR-121) and stays free (#472). The graph is one tab stop with `aria-activedescendant`: arrows along links and layers, Page Up/Down by layer, Home, Enter or a click opens a node as the current element.
  - Data: the buffer holds the input of `trace.graph` (element, depth, kinds, meanings, view; the app adds `limit: 500`, the size of AK6), and every value it shows is in that output (nodes, levels, edges, marks, `truncated`) or the type name of `metamodel.get` (ADR-0002, SR-080 AK4).
  - Layout: where the nodes stand is display (ADR-0002 rule 3, SR-080 AK1): the renderer lays them out with `@dagrejs/dagre` (ADR-0015; the layout of Mermaid's flowcharts, ranker `tight-tree`, top-down, one layout edge per ordered pair of nodes, no link to itself), because the pixels depend on its font and zoom, so CLI and MCP get no coordinates. A link that runs against the levels (target farther down than source; it exists because core lists every link between two nodes and an element reached both ways keeps its smaller distance) is left out of the ranking and drawn afterwards between the placed nodes, so the element is never drawn below one of its parents, also when it is in a cycle with it; dagre's own cycle breaking would reverse a walk link instead (its `greedy` acyclicer throws or misplaces such graphs in 3.1.1). The layout runs on the main thread; SR-111 AK6 (500 nodes laid out within 1 s from the key press) is timed end to end in `test/graph-performance.spec.ts`, on a package graph of 500 nodes at depth 1 and on a whole chain of 500 nodes.
  - Up to 200 nodes: every other link's target stands above its source (ADR-0004), whatever its kind: the parents above the element, the children below (SR-111 AK1); for links that are not derivations (a package above its members, a decision above what is based on it, an element whose text references the element below it) this is the assumption of spec question #478. The drawn layers are dagre's ranks, not core's `level` (a diamond puts a node one layer under each parent), and a cycle among nodes of one level is broken by dagre.
  - Above 200 nodes (`output.nodes.length > 200`, #500): links within a level are left out of the ranking and drawn afterwards too; the layers then follow the levels (every node of a level in one layer, in the order of the levels) when every node links to a node one level nearer the element; with cycles through the element, a node may stand a layer off its level, but never on the wrong side of the element. So there, "every link's target stands above its source" holds only for links between two levels: a link within a level is an arch or a curve between its two nodes, and its direction is not seen (recorded on #478). Why: ranked, those links stack a level into many layers (the whole chain of the first need of N-036: 16 drawn layers and 3,507 dummy nodes of dagre instead of 5 and 591), and dagre then takes most of AK6's second. The bound is above every graph of `spec/` (under 200 nodes: the largest had 179 on 2026-10-27), so those keep their ranked layout; pressing `+` across it changes the drawing.
  - Either way, every node of a level below 0 stands above the element and every node of a level above 0 below it (AK1): a node whose layout links do not put it on its side (its walk reached it through a node that took its level from the other walk, in a cycle through the element, #519) gets an invisible layout link from the element, or to it (`minlen` 1, `weight` 0), which is never drawn.
  - Look: nodes are HTML boxes of a fixed size over one SVG of B-spline curves (no canvas: text, tokens, focus and aria come for free); no arrowheads, labels, legend or controls (D-062). The ends on one edge of a box are ordered by where each curve is half a layer gap from that edge (where it passes dagre's bend next to the box, else on the straight line to the other box; ties by the other end), so bent and straight curves are compared at one height. That makes crossings at a box rare, not impossible: on `spec/` (2026-10-27) crossings of two curves near their common box fall from 10,025 to 5,039, and 5 of 1,017 graphs get slightly more crossings in all (#555). The links of the selected node are lit up (text colour) only when it has some and they are at most half of the drawn links, so emphasis says something and a big fan (depth 1, a package) stays grey (D-062). A box's hover text gives the ID, type and whole title, which its fixed width may cut.
  - Depth and kinds: `+`/`-` one level more or less; in the command prompt, on a graph only and with no key of their own, "Graph depth" (direct neighbours, 2 to 9 levels, whole chain), "Show only relation kind" (everything, the meanings of `trace.graph`'s input schema from the catalog, every relation kind and property of kind `relation` of `metamodel.get` by its name) and "Also show relation kind" (adds one, while a filter is set). Each entry is the buffer with another depth or filter, so `trace.graph` decides what is followed (ADR-0002); every entry of the kind prompts is a `GraphFilterChoice` (name, hint, `kinds`/`meanings`), so a named view would be one more entry. The modeline names the filter by those names.
- Metamodel (SR-130, D-063): a buffer of its own, one per workspace (`MetamodelBuffer`). One topic per line:
  - Open: "Show metamodel" in the command prompt (the title of `metamodel.get`, which the action `covers`, so the prompt never opens it as a result buffer; initials `sm`), from any buffer, as a graph (AK1); no key of its own (keys are scarce, Ctrl/Cmd+K is the reserved prefix, #472). An open metamodel buffer is shown as a graph and keeps its selection. It is not offered on the metamodel itself (SR-133: there the switch below does it), so `sm` gives no first hit there, and on the text "Show metamodel as graph" needs more letters; that is no gap in AK1.
  - Data: only `metamodel.get`, asked again on each revision of the workspace; every word shown is a field of its output or a word for one ("extends", "Any type", "abstract", "any source", "any target"), so CLI, API and MCP give the same types, inheritance, properties, statuses and relation kinds (AK6, SR-080 AK4); no new command, since nothing is decided (`metamodel-graph.ts`). The one reading the renderer makes: a property of a type is inherited (shown muted) when its key is among the `properties` of the type its `extends` names (review S2); any further condition would be logic and belong in core.
  - Graph: a box per type (name, prefix, "abstract" for an abstract type, every property, the inherited ones muted; its height follows from its lines; its width is that of its widest line, measured in the window's fonts with a canvas, at least 224 px, so no name or property is cut; a label is as wide as its widest line), a curve per ordered pair of boxes with one label line per link: "extends" for the inheritance, the name of each relation kind for each pair of its `source-types` × `target-types`, and the name of each property of kind `relation` from each type that has it as its own to each of its `target-types` (assumption of spec question #619 Q1). A side a relation kind or property leaves out allows every type: it is the box "Any type", present only then, and the label says so ("Based on · any source", "Traces to · any target", "Refines · any source and target", AK3); a kind open on one side is one curve per type of the other side (assumption of #619 Q2). An empty list allows no type: no curve. Types are named as written, their subtypes are shown by the inheritance.
  - Layout: dagre (ADR-0015), ranker `tight-tree`, top-down, a target above its source. The edges join the ranking in the order of the graph, the inheritance first, and only while the ranked edges stay free of cycles (a reachability check per edge), so every parent stands above its subtypes (inheritance has no cycles; core rejects them); an edge that would close a cycle (a relation kind from a parent to its subtype, the opposite of a ranked edge) is drawn afterwards from the bottom of its source down to the top of its target, from the right quarter of each box, and its label takes the first free place beside the curve (review B1). dagre reserves room for the label of every ranked edge and loop; a loop runs from the right edge of its box out to its label. Every curve ends in an arrowhead at its target (the direction reads also where it is not "up"); inheritance in `--muted`, the rest in `--edge`, labels on `--sheet`, no legend, no controls, no colour.
  - Known limitations: a curve that carries both "extends" and a relation kind is drawn in the look of the inheritance; a curve drawn afterwards may cross a box of a layer between its two boxes.
  - Keys (AK4): one tab stop with `aria-activedescendant`; the arrows, Page Up/Down and Home as in the graph of an element (`graph-nav.ts`, whose `NavLayout` both layouts fit), Home the first type. Keys with Ctrl, Cmd or Alt are left to the window. The first type is selected when it opens, the view centred on it across and its top a margin into the view; the curves of the selected box are lit as in the graph of an element (`spotlit`).
  - Text (AK5, `metamodel-text.ts`, `MetamodelTextView.tsx`): the same answer as rows on the sheet, no table chrome. One section per type: name, prefix, key (monospace), "abstract"; "extends" and the parent by its name; "Properties" with one line per property in the output's order (name, key, value kind: `kind`, "list of" for `many`, for kind `relation` "→" its target types; "required"; the inherited ones muted by the rule above; choice values are not listed); "Statuses" by name, "none" when empty. Then one line per relation kind: name, key, source → target types by name, "any type" for a side left out, "none" for an empty list. Then the problems of the output, one line each (no rows). The rows are a list of the main window (below): Down/Up, Ctrl+N/Ctrl+P, Page Up/Down (five rows), Home/End.
  - Graph ↔ text (AK4): Ctrl/Cmd+T, the key that switches the representation of the shown buffer (as list ↔ matrix; the actions "Show metamodel as text" and "Show metamodel as graph" are available only on the metamodel in the other mode, so they and the matrix actions are never available together). The buffer's `mode` says which one is shown, the modeline says "Metamodel · text". The selected type is shared (`selected`): the text opens on its section, a type selected in the text is selected in the graph, and the graph opens on it. A relation kind has a row but no box (its curves are drawn): selecting it in the text keeps the type (`row` holds it), so the graph shows the type selected last.
- Follow agent (SR-117, `follow.ts`, `use-follow.ts`): the mode „Agent folgen“ is display state of the renderer (ADR-0002 rule 3, SR-080 AK1): off at the start, never stored, switched only by the actions "Follow agent" and "Stop following agent" (one key, Ctrl/Cmd+Shift+O, with availability that excludes each other; in the command prompt too), never by a catalog command, an app argument or the bridge (AK4). While it is on, each `agent-activity` shows the element of the access: its open buffer, else its buffer after one `element.get` (also after a change, since the name may have changed; a change of the shown element asks it again). Turning it on shows the access `workspace.activity` gives, and so does a restart of the core process while it is on; an access that is not newer than the one shown or held is dropped, and a lookup a newer access replaced is dropped. Unsaved input holds an access back (AK5): a draft in any buffer or an open prompt, in one function (`holdOf`); the latest held access is shown once neither is there, unless only the prompt held it and the user chose something in it (a buffer, a command, a filter or sort in place, also an action that does not navigate; the minibuffer tells a choice from Escape): his choice is newer, and the next access moves the view again (A3). Escape shows the held access. A dropped access counts as shown, so a pull after a restart does not bring it back. The mode closes the buffer it opened for the access before, in the same batch, never one with a draft and never the target, and only while it is the mode's (the user showing it himself or typing in it makes it his); what the mode shows is no recent element of the overview (SR-118). The modeline mark, after the workspace marks and before `stopped`, is `following agent`, or `following agent: waits for save` while a draft holds an access back (greys only, D-062). Opening another workspace ends the mode.
- All UI text is English, no i18n framework (D-019, SR-074).
- Light and dark (SR-113): colours are custom properties with `light-dark()`; `color-scheme` follows the OS (`prefers-color-scheme`, from `nativeTheme`) at start and while running. "Toggle dark mode" sets `data-theme` on the root for the running app only (nothing is stored, AK1); "Follow system light or dark mode" removes it. The window background at start follows `nativeTheme`. Nothing sets `themeSource` (no bridge function for it).
- Title bar (#490): on macOS the window has `titleBarStyle: "hiddenInset"`: the traffic lights lie on the sheet, and a strip of the sheet at its top (`.titlebar`, 38 px, the `--sheet` colour, so it follows the system and "Toggle dark mode" with the page) is the drag region (`-webkit-app-region: drag`) and shows the window title quietly centred; nothing in it is a control. The renderer shows the strip when `navigator.platform` is macOS, the same test as for the shortcut labels. Windows and Linux keep the native frame: a hidden title bar there needs `titleBarOverlay` colours that follow "Toggle dark mode", which only the renderer knows, so another bridge message from the renderer to main would be needed; the hidden frame also drops the menu bar (File > Open Workspace, shown with Alt) and would change every Electron test, which runs on Linux. Rejected for now; a native frame follows the OS's light or dark setting there.
- The modeline is one quiet rounded bar (#490): every part is a segment, the shown buffer and the workspace on the `--select` tone, the rest on `--raised`, the joints thin rounded edges in `--rule` (the layout of a powerline status line, without its colours, D-062). The candidates of a prompt are a card: `--raised`, a 1 px `--rule` edge, rounded corners and a soft shadow upwards, above the modeline.

## Consequences

- Renderer bugs cannot touch files or the network directly.
- The core process restarts independently if it crashes; the window shows a message and reloads the workspace. After more than 3 stops within 60 s it is not started again, and the window says so.

## Rejected

- Core in the main process: blocks the UI on long checks.
- Monaco: larger, more than a Markdown editor needs.

# ADR-0007: Parsing and writing YAML and Markdown

Status: Proposed · Based on: D-012, D-015, D-056 · SRs: SR-008, SR-009, SR-016, SR-065

## Decision

- **YAML:** the `yaml` package (eemeli/yaml), YAML 1.2 core schema. Reading uses `parseDocument` so errors carry line and column (SR-008 AK1). Writing edits the parsed `Document` in place (set or delete single nodes) and stringifies it, which keeps key order, comments and the style of untouched values (SR-016 AK2, ADR-0004 stable writing). LogReq never re-serialises a whole file from a plain object. The lossless writer for this rule is tracked in #132; `Document.toString()` alone is not lossless (for example `00815` becomes `815`). Reading keeps the raw frontmatter text and parses with `keepSourceTokens`, so the writer can replace single nodes by their source range. YAML warnings (for example an unknown tag) are reported as `file.yaml-warning` with severity `warning`; the file is still read.
- **Frontmatter split** by our own small function: the file must start with a line that is exactly `---` and have a closing line that is exactly `---` (no trailing whitespace; `...` is not accepted as closing line). LF and CRLF are accepted; a UTF-8 byte order mark before the first line is removed when reading and kept on write. No front-matter library.
- **Conflict markers:** before parsing, the whole file (frontmatter and text) is scanned for a conflict: a line starting with `<<<<<<<`, a later line that is exactly `=======` and a later line starting with `>>>>>>>` (the `<` and `>` markers followed by a space or the end of the line). If found, the file is reported as `file.conflict-markers` with the line of the start marker and not parsed (SR-008 AK2). Single marker-like lines do not count: `=======` underlines a Markdown setext heading and `>>>>>>> x` is a nested blockquote. A fenced code example that shows a whole conflict is still reported; that is accepted.
- **Problems:** faulty YAML, and a `---` first line without a closing `---` line, are `file.invalid-yaml` with the line in the file and the reason (SR-008 AK1); a file that cannot be read, is not UTF-8, is a symbolic link or lies in a folder linked outside the root is `file.unreadable`. Messages carry the relative path with `/` and errno codes, never absolute paths, so problems are the same on every machine. One faulty file never stops reading the others (SR-008 AK3).
- **Markdown** is stored and passed through as a string. It is parsed only to extract inline references and image links (ADR-0004) and to render, with `micromark` plus GFM and math extensions (mdast via `mdast-util-from-markdown`). The editor (ADR-0010) works on the text itself, so files stay plain CommonMark with GitHub extensions (SR-065 AK3).
- **Writing files** is atomic. Replace: write and fsync a temporary file in the same folder (opened exclusively, permission bits of the original), then check the target on disk and rename at once. A rename that fails with `EPERM`, `EACCES` or `EBUSY` (transient on Windows) is retried a bounded number of times, and every attempt runs the check again, so a save made in between is never overwritten. After the rename or link the folder is fsynced, best effort (Windows cannot open folders). The check compares the SHA-256 of the bytes on disk with the snapshot taken when the file was read; size and mtime are only cache hints. If it differs, the write fails with `file.changed-on-disk` instead of overwriting (SR-008 AK3, SR-007). The window between check and rename stays a few system calls long; two LogReq processes on one working copy are not locked against each other. Create: temporary file, then hard link, which never replaces an existing file; where hard links are not supported (`EPERM`, `ENOTSUP`, `ENOSYS`) the file is created exclusively in place; if writing it then fails, the partial file that this call just created is removed again (no element is deleted). Refused: symbolic links (`file.not-regular`), read-only files on every OS and folders that are not writable (`file.read-only`), missing folders (`file.folder-missing`), folders linked outside the root (`input.invalid`). Temporary files are named `.<file name>.<8 hex>.logreq-tmp`; they are removed best effort, and listings and watchers ignore that pattern. A snapshot is plain data (canonical relative path with `/`, size, mtime, SHA-256; `./d/../d/a.md` is `d/a.md`); a write returns the snapshot of the written file.
- A file that could not be read is never written by LogReq (SR-008 AK3): before replacing, the current bytes on disk are parsed again (conflict markers, frontmatter split, YAML); if they are faulty or have no frontmatter the write fails with `file.faulty`. Whole-file YAML documents (metamodel, workspace, baseline, filter, mapping) are read with `readYamlFile` and written with the check kind `yaml`: the whole file must parse as YAML 1.2 without errors.

## Rejected

- `gray-matter` or `js-yaml`: lose comments and key order on write.
- remark/unified round-trip for writing Markdown: reformats the user's text.

# ADR-0007: Parsing and writing YAML and Markdown

Status: Proposed · Based on: D-012, D-015, D-056 · SRs: SR-008, SR-009, SR-016, SR-018, SR-065

## Decision

- **YAML:** the `yaml` package (eemeli/yaml), YAML 1.2 core schema. Reading uses `parseDocument` so errors carry line and column (SR-008 AK1). Reading keeps the raw frontmatter text and the line ending of the closing `---` line, so a file can be written back byte for byte. YAML warnings (for example an unknown tag) are reported as `file.yaml-warning` with severity `warning`; the file is still read.
- **Frontmatter split** by our own small function: the file must start with a line that is exactly `---` and have a closing line that is exactly `---` (no trailing whitespace; `...` is not accepted as closing line). LF and CRLF are accepted; a UTF-8 byte order mark before the first line is removed when reading and kept on write. No front-matter library.
- **Conflict markers:** before parsing, the whole file (frontmatter and text) is scanned for a conflict: a line starting with `<<<<<<<`, a later line that is exactly `=======` and a later line starting with `>>>>>>>` (the `<` and `>` markers followed by a space or the end of the line). If found, the file is reported as `file.conflict-markers` with the line of the start marker and not parsed (SR-008 AK2). Single marker-like lines do not count: `=======` underlines a Markdown setext heading and `>>>>>>> x` is a nested blockquote. A fenced code example that shows a whole conflict is still reported; that is accepted.
- **Problems:** faulty YAML, and a `---` first line without a closing `---` line, are `file.invalid-yaml` with the line in the file and the reason (SR-008 AK1); a file that cannot be read, is not UTF-8, is a symbolic link or lies in a folder linked outside the root is `file.unreadable`. The element walk of the model (SR-003) does not even read some files: a linked `*.md` file, a Markdown file whose extension is not lower-case `.md` (`.MD`) and a `*.md` entry that is not a regular file (FIFO, socket, device) are `file.skipped` warnings; linked folders are not followed. Messages carry the relative path with `/` and errno codes, never absolute paths, so problems are the same on every machine. One faulty file never stops reading the others (SR-008 AK3).
- **Markdown** is stored and passed through as a string. It is parsed only to extract inline references and image links (ADR-0004) and to render, with `micromark` plus GFM and math extensions (mdast via `mdast-util-from-markdown`). The editor (ADR-0010) works on the text itself, so files stay plain CommonMark with GitHub extensions (SR-065 AK3).
- **Writing frontmatter** splices the raw text; it never stringifies a parsed `Document` and never re-serialises a whole file from a plain object. `Document.toString()` is not lossless with yaml 2.9.1 (`00815` becomes `815`, `[x,y]` becomes `[ x, y ]`, flow mappings over 80 characters are spread over several lines, long scalars are folded, spacing is normalised). The writer (`editElementFile` in `packages/core/src/files/edit.ts`) is a pure function from the raw texts of a read file and a list of edits to the new bytes:
  - Edits: set a top-level key, remove a top-level key (only where a command needs it; elements are never deleted, D-045), replace, append or remove one item of a list, and set one string scalar inside the value of a key (`set-scalar`, for the stored version a confirmed hint writes, SR-027, and the stored title of a relation target, decision on #307): only that scalar's source range is replaced, in its own quoting (single quotes stay where the value allows them, plain stays where it reads back the same, else double quotes), so the layout, other keys and comments of the item stay byte for byte; it is not combined with another edit of the same key. With `ifPlain` a value that is not a string scalar on one line without an anchor is left as it is instead of refusing the request, so the stored titles of a file are refreshed in one pass (decision on #307). A value equal to the current one is no change, so saving an unchanged element changes no byte (SR-102).
  - It parses the frontmatter with `keepSourceTokens` and replaces only the source ranges of the changed keys: from after the `:` to the end of the value (a trailing comment and the spacing after `:` stay); for a block sequence only the changed items, kept items are copied byte for byte with their comments; a removed key loses the lines from its key to the end of its value. Every other byte stays: comments, quoting, leading zeros, spacing, key order, long lines (SR-016 AK2, SR-102 AK1, AK2).
  - Comments: a replaced list item keeps its dash spacing and its trailing comment (only the item's content is replaced). When a scalar becomes a list, a trailing comment of the key line moves after the last item. Removing an item keeps comment lines above the next item (they belong to that item). A removed key loses its trailing comment with it.
  - New keys are appended at the end of the frontmatter in the order of the type's properties in the metamodel, then in edit order (ADR-0004).
  - New values have one fixed style: scalars plain when that reads back as the same value, else double-quoted with escapes; never folded (one value, one line); lists as block sequences; relation targets as one flow mapping per line `- { id: …, version: …, title: … }` (ADR-0004, SR-102). A list that was a flow sequence becomes a block sequence when it changes.
  - The Markdown text (the body after the closing line; the commands map their text to it with `bodyForText`, ADR-0004 "Text layout") is replaced only when it differs; byte order mark, line endings of the opening and closing lines and existing CRLF are kept. New frontmatter lines use the line ending of the first frontmatter line; a new text sent with LF is converted to the file's line ending before comparing and writing, so an unchanged text on a CRLF file is no change. A text that is plain YAML 1.2 but reads as a boolean, number or date in YAML 1.1 (`yes`, `on`, `1_000`, `12:30`, `2026-10-24`) is written double-quoted, so other tools read the same string. `-0` is written and compared as `0`.
  - The result is parsed again and must hold exactly the old data with the edits applied, in the same key order; otherwise nothing is written (`internal`, for example a YAML alias that points into a changed value). A new text with a whole Git conflict is refused (`input.invalid`), since the file could not be read back. Frontmatter that is not a block mapping (for example `{ id: …, type: … }` on one line) is not written (`file.faulty`).
- **Writing files** is atomic. Replace: write and fsync a temporary file in the same folder (opened exclusively, permission bits of the original), then check the target on disk and rename at once. A rename that fails with `EPERM`, `EACCES` or `EBUSY` (transient on Windows) is retried a bounded number of times, and every attempt runs the check again, so a save made in between is never overwritten. After the rename or link the folder is fsynced, best effort (Windows cannot open folders). The check compares the SHA-256 of the bytes on disk with the snapshot taken when the file was read; size and mtime are only cache hints. If it differs, the write fails with `file.changed-on-disk` instead of overwriting (SR-008 AK3, SR-007). The window between check and rename stays a few system calls long; two LogReq processes on one working copy are not locked against each other. Create: temporary file, then hard link, which never replaces an existing file; where hard links are not supported (`EPERM`, `ENOTSUP`, `ENOSYS`) the file is created exclusively in place; if writing it then fails, the partial file that this call just created is removed again (no element is deleted). Refused: symbolic links (`file.not-regular`), read-only files on every OS, folders that are not writable and read-only file systems (`file.read-only`; `EACCES`, `EPERM`, `EROFS`), missing folders (`file.folder-missing`), folders linked outside the root (`input.invalid`). Temporary files are named `.<file name>.<8 hex>.logreq-tmp`; they are removed best effort, and listings and watchers ignore that pattern. A snapshot is plain data (canonical relative path with `/`, size, mtime, SHA-256; `./d/../d/a.md` is `d/a.md`); a write returns the snapshot of the written file.
- A file that could not be read is never written by LogReq (SR-008 AK3): before replacing, the current bytes on disk are parsed again (conflict markers, frontmatter split, YAML); if they are faulty or have no frontmatter the write fails with `file.faulty`. Whole-file YAML documents (metamodel, workspace, baseline, filter, mapping) are read with `readYamlFile` and written with the check kind `yaml`: the whole file must parse as YAML 1.2 without errors. The YAML files LogReq writes besides the workspace file (saved filters, SR-070, now; baselines and mappings later) go through `files/yaml-document.ts`: a new file in one fixed style (`renderYamlDocument`: block mappings, a list of plain values as one flow list, texts plain when they read back the same, else double-quoted, never folded), an existing one edited by its top-level keys (`editYamlDocument`): a changed key gets the lines from its key to the last line of its value rendered again, a removed key loses them, a new key is appended; every other byte stays (comments, blank lines, layout of the other keys, CRLF, byte order mark), comments inside a changed value go with it. The result is parsed again and must hold exactly the intended data (else `internal`, nothing written); a file that is not a block mapping is `file.faulty`.

## Rejected

- `gray-matter` or `js-yaml`: lose comments and key order on write.
- remark/unified round-trip for writing Markdown: reformats the user's text.

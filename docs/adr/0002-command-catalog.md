# ADR-0002: Command catalog as the only program logic

Status: Proposed · Based on: D-025, D-029, D-045, D-052 · SRs: SR-080, SR-072, SR-017, SR-081

## Context

Every function must be available through app, CLI, API and MCP with the same result (D-029, SR-080). "The app has no logic of its own" (D-029). If four adapters each call the core differently, they drift.

## Decision

1. **One catalog.** `schemas/commands/catalog.json` lists every command: `name` (`group.action`), `title`, `summary`, `effect` (`read` or `write-files`), `stage` (D-035), `implements` (SR IDs), `arguments`, JSON Schema for `input` and `output`. It is the contract; a change is its own PR, announced to the product owner in the stage epic (D-051).
   - `jsonLines` (optional, #319) says that the output is also given as JSON Lines: `items` names a top-level array of the output, one line per item, and `fields` the top-level fields every line carries first (`{ "items": "elements", "fields": ["reqseq-data", "commit", "dirty"] }` for `data.export`, the only entry with it). It is a form of serialisation, not an input, so the generated input schemas of MCP and the app stay the same and no access gets an input it would have to refuse (SR-080 AK2), and core never branches on the access (rule 4). The lines come from one core generator (`jsonLines`, files block), the adapters read only the field (rule 3). `catalog-checks.mjs` checks that `items` is a top-level array and that every field is a top-level non-array property that the item schema does not have.
   - `title` is the name for people: English, sentence case, at most 40 characters, unique, free of delete words except for relations. It is what the app's command prompt offers (SR-108, SR-073 AK2) and the MCP tool `title`. Where an app action does the same as a command, the title is the action's name, so the prompt lists it once.
   - `arguments` says how a prompt asks for the input (SR-108 AK4): every top-level property of `input` exactly once, the required ones first, in the order they are asked, as flat entries `{ field, complete, of? }`. `complete` is a closed list of sources (`element`, `type`, `status`, `invalidStatus`, `relationKind`, `relationTarget`, `relation`, `property`, `value`, `hint`, `filter`, `baseline`, `repository`, `selection`, `choice`, `text`, `number`, `boolean`, `json`); `of` names an earlier field the source depends on (default: the nearest earlier field of the matching kind). A client maps each source to one existing read command (`metamodel.get`, `relation.options`, `element.search`, `hint.list`, `filter.list`, `baseline.list`, `workspace.status`) and shows what core returns; it decides nothing about what is allowed. There is no command for completion: every allowed value already comes from a read command on every access. `scripts/contracts/validate-schemas.mjs` checks titles and arguments (`catalog-checks.mjs`).
2. **One implementation per command** in `packages/core/src/commands/<group>/<action>.ts`, registered with `defineCommand` (`packages/core/src/catalog.ts`). The definition holds only the catalog name and `run`; summary, effect and the input and output schemas are taken from the catalog entry, so they match by construction. A test (`packages/core/src/commands/registry.test.ts`) checks that every implementation has a catalog entry and is registered under the name of its file, and that every catalog entry of a completed stage (`COMPLETED_STAGES`, set when the stage is done) has exactly one implementation (entries of stages in progress arrive one SR at a time).
3. **Adapters are generic.** They know nothing about individual commands:
   - CLI: `reqseq <group> <action>` with flags derived from the input schema, `--input <json|@file>`, `--json` for machine output, and `--jsonl` where the entry has `jsonLines`.
   - API: `POST /v1/commands/<name>` with the input as body (generated `schemas/generated/openapi.json`), JSON Lines for `Accept: application/x-ndjson` where the entry has `jsonLines`.
   - MCP: one tool per command, `group_action` (generated `schemas/generated/mcp-tools.json`; the server lists the implemented ones, ADR-0009).
   - App: the renderer calls `invoke(name, input)` over IPC (ADR-0010). Pure display (layout, selection, editor state) is the only thing outside the catalog (SR-080 AK1).
4. **Calling convention.** `run(ctx, input)` gets a `CommandContext` (the `Workspace` object of rule 7, abort signal, the local path rule `localPaths` of the call's access) and input validated against the catalog with defaults applied; adapters call `invoke(name, input, { workspace })`, which validates and maps every failure to `CommandError` (`packages/core/README.md`); output is validated in tests and in debug builds. Findings and hints are returned as `problems` data, not thrown; `invoke` adds the short ID of the element each problem names (`elementShortId`), from the output schema, so no command does it itself (#315). Real errors throw `CommandError` with a code from `common.schema.json#/$defs/error`. Each adapter maps codes the same way (CLI exit code and stderr, HTTP status and body, MCP tool error). Each adapter also passes its own access name (`access`: `cli`, `api`, `mcp`, `app`), a fact of the transport like the signal; it changes the result only where SR-142 says so. Core decides what it means: outside `UNCONFINED_ACCESSES` (`cli`, `app`) every local path must lie inside the repositories of the workspace (SR-142, an exception to SR-080 AK2): `invoke` checks the `localPath` fields of the input before the command runs, and a command passes every path it derives from file content through `ctx.localPaths.check` (ADR-0009 "Local paths"). It records the element of a successful API or MCP call as the last access of the copy (`FOLLOWED_ACCESSES` in `model/activity.ts`, SR-117, which the app's mode „Agent folgen“ shows); no adapter decides it by passing or leaving out the field. The mode itself is display state of the app; `workspace.activity` gives the recorded access on every access (SR-080 AK4).
5. **Effects.** `read` commands never write. `write-files` commands write only ReqSeq files in the working tree, and return the list of written files. Two exceptions write a file the caller names (`localPath`, also outside every repository on the command line and in the app; through API and MCP only inside one, SR-142). `evidence.enrichJunit` rewrites a JUnit XML file in place or writes it to `output` (SR-029). It writes through `writeFileAtomic` with the root set to the file's own folder and the file kind `xml` (the XML scanner accepts the file), replaces an existing `output` only when it is a JUnit XML file, never writes into a `.git` folder (its real folder is checked, D-036) and creates no folders. With nothing to change the input is not rewritten; a given `output` is still written, unless it holds these bytes already. It returns the written file relative to the workspace root (the folder of the main repository) when it lies in a repository of the workspace, else as an absolute path. `data.store` (SR-062) writes a ReqSeq data file (JSON Lines, one element per line, #319: `<commit>.jsonl` or `<commit>-dirty.jsonl`, file kind `jsonl`) into a folder the caller names. Inside an available repository of the workspace (by the real path; the deepest wins) it may write anywhere the safety rules allow: `refuseUnlisted` with `ignored: false` refuses `.git`, `node_modules`, links into a repository, nested repositories, non-portable names and other spellings than the one on disk, before and again after `createFolder`, which makes a missing folder; ignored folders are allowed, since a data file is never walked. Outside every repository (command line and app only, SR-142) it writes only into an existing folder whose real path is not in a `.git` folder. Every check runs before any folder is created. It replaces only a ReqSeq data file (its first line starts with `"reqseq-data"` 2 or later, valid UTF-8), under its snapshot, and never touches an old `<commit>.json`, and returns `files` as `evidence.enrichJunit` does. No command writes Git (D-036, ADR-0006). No command deletes elements (D-045); `scripts/contracts/validate-schemas.mjs` rejects command names with delete/remove except for relations. Whether a write command may run while the workspace is read-only (a missing or faulty metamodel, SR-011 AK3) is part of its catalog entry, not of the runtime: every `write-files` entry has `whileReadOnly` (`refuse` or `allow`) and a one-line `whileReadOnlyReason`, and a `read` entry has neither (`catalog.meta.schema.json`, #142). `invoke` refuses a `refuse` command with `workspace.read-only` before `run`. `workspace.init`, which creates a workspace, is `allow`; every other write command is `refuse` until its SR decides otherwise.
6. **Status.** Only `element.setStatus` and `element.supersede` change a status (SR-087 AK1); `element.create` always uses the initial status (when the type does not have it or it is marked invalid, the type's first status in metamodel order that is not marked invalid, so no new element is superseded at once, #350; none for a type without status, #306, and none for a type whose statuses are all marked invalid, whose status is optional: an element of it without status is current and `element.supersede` retires it, #344 option 1), `element.setStatus` and `element.supersede` take only statuses of the element's type (`element.setStatus` with `status: null` removes the status line, only where the type's status is optional: a type without status or one whose statuses are all marked invalid, so a leftover status can be cleared and a retired element made current again; refused with `status-required` on any other type, #343), and `element.update`/`element.bulkUpdate` reject `id`, `type` and `status`. A test runs every other write command and asserts that no status changed. Both commands are offered on every access like any function (SR-080): "the tool never sets a status itself" (D-030) means no command changes a status as a side effect or by computation. Who may call them, a person directly or an agent acting for a person, is decided outside ReqSeq (D-029: the tool does not control agents), and the change is reviewed in the merge request (D-024).
7. **One workspace per process state.** All state lives in a `Workspace` object created per workspace root; no globals, no shared cache between copies (SR-081). `workspace.recent` (SR-131) is the one command that reads state of the user rather than of the workspace: the list of the workspaces the app opened last, in `<OS cache>/reqseq/` (ADR-0008). Its `run` does not use `ctx.workspace`, keeps nothing in the process but the bounded existence checker of `workspace/recent.ts` (per process, without data; ADR-0010) and gives the same list from any folder; only the app's core process writes the list.
8. **Cross-access test.** For each command, one scenario runs through core, CLI, API and MCP and compares the outputs (SR-080 AK2). New commands are added to it automatically from the catalog.

## Consequences

- SR-080 holds by construction; adding a function means adding a catalog entry and one implementation.
- The catalog is long-lived API; removing or changing an input field is a breaking change and needs a new ADR. `title` and `arguments` (#404) are additions only: no existing field changed.
- Command names are English (D-019).

## Rejected

- Hand-written REST routes, CLI commands and MCP tools: four places to keep in sync.
- Zod or TypeBox as the source of the schemas: the catalog must be readable and reviewable without TypeScript, and the file formats are JSON Schema anyway (ADR-0003).

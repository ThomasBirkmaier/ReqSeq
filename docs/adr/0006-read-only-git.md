# ADR-0006: Read Git through the git program, read-only

Status: Proposed · Based on: D-014, D-024, D-036, D-039 · SRs: SR-050, SR-051, SR-062, SR-083, SR-092

## Context

LogReq reads Git for the state (commit per repository), the date of a version, uncommitted changes before a baseline (SR-050 AK2), files changed in a merge request (SR-092 AK1) and old file contents (SR-051, ADR-0005). It never commits, pushes, pulls, merges or switches branches (D-036, SR-083).

## Decision

- Use the installed **`git` program** through one module `core/src/git/reader.ts`. It is the only place that spawns processes.
- The module accepts only an allowlist of subcommands with fixed argument shapes: `rev-parse`, `cat-file`, `show <rev>:<path>`, `log` (with `--format`, path limits), `diff --name-only`, `ls-files`, `status --porcelain=v2`. Anything else is a programming error. Paths and object names go to standard input, one per line (`log --stdin`, `cat-file --batch-command`, `--batch`, `--batch-check`), so no command line gets too long on Windows and no path can be read as an option; the only argument after a fixed command line is a checked commit ID. Old contents are read with `cat-file` (`<commit>:<path>`), which does what `show <rev>:<path>` does for many objects in one process (#260): one `cat-file --batch-command --buffer` process answers all rounds of `info` and `contents` of a call (git 2.36 and newer); a git that refuses the option (exit code 129 before any output) gets one `cat-file --batch-check --buffer` or `--batch --buffer` process per round, and the reader remembers that while the program runs.
- **Files changed since a commit** (SR-092, `resolveCommit` and `changedPaths`):
  - A revision the user gives (`--changed-since origin/main`) is never an argument. It goes to the standard input of `cat-file --batch-check --buffer` as `<revision>^{commit}`, which names the commit or answers `missing`.
  - Then `-c diff.autoRefreshIndex=false diff --no-ext-diff --no-renames --relative --name-only -z <commit ID> --` lists the files of the working copy that differ from that commit: committed, staged and not staged. The `--` keeps a file named like the commit from being read as a revision.
  - `-c core.untrackedCache=false ls-files --others --exclude-standard -z` lists the files Git does not track.
  - Both run in the repository folder, and `--relative` keeps the paths relative to it, also where the folder lies below the top level of its work tree.
  - `GIT_OPTIONAL_LOCKS=0` does not stop `diff` from refreshing the index. For a file whose stat data changed but whose content did not, `diff` would refresh the index and write `.git/index`. `diff.autoRefreshIndex=false` turns that off: nothing is written, and no clean filter (LFS) runs, except for a racily clean entry, whose content git hashes to compare. Such a file is listed as changed: the check shows more, never less. `core.untrackedCache=false` keeps `ls-files` from storing an untracked cache. A test makes a stat-only change and asserts that `.git` is byte-identical afterwards.
  - The UUID that a changed element file held at the commit is read with `cat-file` (`<commit>:<path>`). A deleted file, or one whose UUID changed, then keeps the findings of relations to its old UUID.
  - A repository folder without a `.git` entry in it or in a folder above it is in no repository: no process starts, and the check reports an `info` problem `git.unavailable`. So does a folder below the top level where git lists no changed or untracked file and the commit has no tree at the folder (`<commit>:./.`): Git sees none of its files (its work tree ignores it, as a home folder under Git with `*` in `.gitignore` may, or it holds none), and nothing listed would otherwise restrict the check to nothing. A repository without the commit gets an `info` problem `git.revision-missing`; when no repository has it, the check fails with `git.commit-not-found`. In a repository, every other git failure, including output `cat-file` should not give, is `git.unavailable`.
  - Merge bases are not computed, since there is no `merge-base` (spec question #291).
- **A repository folder below the top level of its work tree** (#377; SR-004 and D-041 put the workspace file "im Haupt-Repository", for example `spec/` of a code repository): the work tree is the nearest folder at or above the repository folder (links followed) that holds a `.git` entry, as git looks for one (`workTreeOf`); a nested repository keeps its own. There is no further limit: git's own discovery applies (`safe.directory`, `GIT_CEILING_DIRECTORIES`, a file system boundary), and where git refuses, the information is unknown, except that below the top level a "not a git repository" answer (the `.git` entry found is not the one git uses) makes the folder one without Git, as above. `workspace.status` gives the commit of such a folder only where that commit has a tree at the folder (`<commit>:./.`), so a stray repository above that tracks nothing there is not reported as the folder's. Every path in and out of the reader stays relative to the repository folder, the folder every git runs in:
  - `log` reads its paths relative to that folder but names them from the top level (`--no-relative`, git 2.28 and newer, so a user's `diff.relative=true` cannot name some commits relative to the folder and the merges, which `--cc` never lists relative, from the top level). So the reader takes off as many leading names as `rev-parse --show-prefix` has; that runs beside `log` on every call, as git skips a `.git` entry that is not valid (an empty folder), so the folder's own entry does not tell that it is the top level.
  - Object names are sent as `<commit>:./<path>`, which git reads relative to the folder it runs in (at the top level, `./a` is `a`); `.` names the folder itself. A path with a `..` name is refused, so no path leaves the folder.
  - `diff --relative` and `ls-files` list relative to the folder anyway; `headFiles` and `headCommit` read the HEAD of the work tree.
- Every call sets `GIT_OPTIONAL_LOCKS=0` (so `status` does not refresh the index), `GIT_TERMINAL_PROMPT=0`, `GIT_LITERAL_PATHSPECS=1` (a path is never a glob or `:(magic)`), `GIT_NO_LAZY_FETCH=1` (a partial clone does not fetch a missing object; git 2.44 and newer), `-c protocol.allow=never` (git may use no transport at all, so a partial clone cannot fetch a missing object with an older git either; the object is then unknown), `-c core.fsmonitor=false`, and `--no-pager`; no network operation is on the allowlist. `log` runs with `--no-show-signature` (no GPG) and `--no-follow`; `cat-file` without `--filters` (no checkout filter programs).
- **HEAD from the files of the Git folder** (#260, so that opening an element starts no `rev-parse`): `headFiles` reads, and never writes or locks, the few small files that name HEAD: the `.git` file of a linked worktree or submodule (`gitdir:`) in the folder `workTreeOf` finds, `HEAD`, `commondir`, the branch file under `refs/heads/` or else its line in `packed-refs`, and `shallow`. It gives the commit and a stamp of these files (content, or identity, size and change time); while the stamp stays the same, so does HEAD, and the version date keeps its walks. Where these files cannot tell (a `reftable` folder, a HEAD that names no branch or commit, a branch file that names another branch, no Git folder), the caller runs `rev-parse` as before. It reads no object and no other file.
- A test runs a full scenario and then compares `.git` (refs, HEAD, index, objects count) before and after: nothing may change (SR-083 AK1). Another test asserts the allowlist (SR-083 AK3).
- If `git` is missing or a folder is not a repository, Git-based information is shown as unknown; everything else works (SR-077: no network needed; the app stays usable).
- Comparing a baseline with today (SR-051 AK3) returns the commits and the `git diff` command; the app opens it in the configured Git tool or a terminal. LogReq does not render diffs itself (D-033).

## Consequences

- Works with every Git feature (worktrees, SHA-256 repositories, partial clones) because Git itself reads them.
- `git` (2.30 or newer) becomes a runtime requirement for Git-based information; documented in the installation guide. What the options need: `%cI` 2.2, `cat-file --buffer` 2.5, `--no-show-signature` 2.10, `protocol.allow` 2.12, `rev-parse --is-shallow-repository` and `GIT_OPTIONAL_LOCKS` 2.15, all below 2.30. Newer than 2.30, each with a fallback: `cat-file --batch-command` 2.36 (older: one process per round, above), `GIT_NO_LAZY_FETCH` 2.44 (older: ignored, and `protocol.allow=never` still holds).
- Paths from Git and paths of element files may differ in their Unicode normal form. The element walk reports a file under the name `readdir` gives (NFD on HFS+, or as a macOS tool stored it), while `git` on macOS with `core.precomposeUnicode=true` (the default there) reports NFC. Wherever the reader joins its paths to element files (uncommitted changes, SR-050 AK2; files changed in a merge request, SR-092 AK1; old contents, SR-051; the version date, ADR-0005), it compares both in NFC, as the `ignore` globs do (#218). Where it asks Git for a path, it passes the path as spelled and its NFC and NFD forms, since Git compares paths exactly. A path whose folder and file names Git stores in different forms is therefore found only as spelled (ADR-0005 "Embedded images at an old commit").

## Rejected

- `isomorphic-git`: no external program needed, but slower on large histories and incomplete for newer repository features; also contains write and network code we would have to keep unused.
- `libgit2` bindings (nodegit): native builds per platform and Electron version.

# ADR-0009: CLI, local API and MCP server

Status: Proposed · Based on: D-025, D-029 · SRs: SR-019, SR-079, SR-080, SR-081 · Contracts: `schemas/commands/catalog.json`, `schemas/generated/`

## Decision

**CLI (`packages/cli`)** — binary `logreq`.
- Subcommands generated from the catalog: `logreq <group> <action>`, the action in kebab-case (`element.setStatus` is `logreq element set-status`). Required string fields are positional arguments in schema property order (`logreq element get <ref>`); other strings, numbers and booleans are `--<field>` flags in kebab-case (`--changed-since`; booleans `--x` and `--no-x`); arrays of those repeat the flag (`--changed-files a.md --changed-files b.md`). Objects, mixed types and fields named like a common option are given with `--input <json|@file|->` (inline JSON, a file relative to the current folder, or standard input; files and standard input may be UTF-8 or UTF-16 with byte order mark, as Windows PowerShell writes them); the help names them. The field form is decided from the JSON Schema alone (`$ref`s resolved against the runtime's `contracts.schemas`), never per command. The CLI only converts number-looking values for number fields; validation is core's (`input.invalid`).
- `--input` and arguments together: `--input` is read first; positional values fill the positional fields that `--input` does not give, in order (an extra value is `input.invalid`); flags override the same field from `--input`.
- Local paths: fields that reference `common.schema.json#/$defs/localPath` are relative to the current folder on the command line; the CLI makes them absolute (from arguments, flags and `--input` alike) before the call. API and MCP pass them unchanged; commands resolve relative ones against the workspace root.
- Options follow the command (`logreq workspace check --json`); before it only `--version` (the product version embedded from the root `package.json` by `pnpm contracts:generate`, `PRODUCT_VERSION` in core) and `--help`.
- Catalog commands without implementation are listed in the help with "(not implemented yet)"; calling one gives core's `command.not-implemented` (exit code 2, as every class but `internal`: the call is wrong for this version, as a usage error is, and a script that checks for 2 needs no new case). So the help always shows the whole catalog.
- Default output is human-readable English: the output object without `problems` as YAML, then one line per problem (`severity  code  repository:file:line  message  (element <uuid>)`, the repository only when the problem names one, or `No problems.`). `--json` prints exactly the command output (SR-019 AK3). Problems go to stdout in both modes; errors go to stderr, as `error <code>: <message>` or, with `--json`, as the error object; with `--json` usage errors (unknown command or option) are the error object `{ "code": "input.invalid", "message": ... }` too. Output is UTF-8 and never colored.
- Closed pipe: when the reader of stdout or stderr goes away (`EPIPE`, e.g. `logreq ... | head`), the rest of that output is dropped quietly and the exit code stays the command's. Any other write error ends with exit code 3.
- Ctrl-C and SIGTERM abort the running command through its abort signal; the workspace is still closed, and the call ends with exit code 130 whenever the signal is aborted when the command finishes, whatever the command returned or failed with. A second signal ends the process at once with 130.
- Exit codes:

  | Code | Meaning |
  |---|---|
  | 0 | Success without error findings and with `ok` not false (warnings and info do not count by themselves) |
  | 1 | The output has a problem of severity `error`, or `ok: false` (SR-019, SR-025, SR-029 AK2) |
  | 2 | Usage error (unknown command or option, missing action) or a `CommandError` of any class but `internal` |
  | 3 | `internal`, any failure outside a command, or a failed write to stdout or stderr |
  | 4 | A given commit is not available locally: `git.commit-not-found` (SR-092 AK2; `workspace check --changed-since` when no repository of the workspace has the revision) |
  | 130 | Aborted (Ctrl-C, SIGTERM) |

  The exit code of an error comes from `EXIT_BY_CODE[code]` when a code has its own (only for cases like 4), else from its class (table under "Errors"). An SR that asks for exit code 1 is met by returning problems with severity `error` or `ok: false`, never by throwing: a thrown `CommandError` is a failed call, not a finding. `workspace.check` sets `ok: false` when the workspace has a finding of severity `warning` or `error`, because SR-019 AK2 ends the check with exit code 1 also for the hints of SR-015, SR-016, SR-085 and SR-086, which stay warnings in every access; info (a repository that is not here) keeps `ok` true. Its `severity` input only filters the problems shown; `ok`, and so the exit code, is about all findings, shown or not (SR-019 AK2 knows no such option).
- Workspace discovery: `--workspace <path>` (relative to the current folder), else the nearest folder upwards with `logreq-workspace.yaml` (`findWorkspaceRoot` in core's `workspace` block), else the current folder, so `logreq workspace init` works in an empty folder. One `Workspace` per call, closed at the end; an error while closing never hides the command's own error.
- `argvFor(entry, input)` (exported by `@logreq/cli`) gives the arguments for a command input, positional and flags where they carry the value exactly and the rest in one inline `--input`, for the cross-access test.
- Parser: `commander` (MIT, pinned exactly). The CLI runs headless, without Electron (SR-080 AK3).

**API (`packages/api`)** — `logreq serve api`.
- `node:http`, bound to `127.0.0.1` and `::1` only (`LOOPBACK_HOSTS`), one server per address on the same port; `::1` is skipped where the machine has no IPv6. There is no option to bind elsewhere (SR-079 AK1, AK3); the bind address is a constant and a test greps for it.
- `POST /v1/commands/<name>` with the command input as JSON body (an empty body is `{}`; at most 32 MiB, else 413 with `Connection: close` as soon as the body passes the limit; the rest is read and dropped for at most another 32 MiB, so the client gets the answer, then the connection is cut); the answer is exactly the command output (200, also with error findings or `ok: false`). `GET /v1/commands` returns the catalog entries, each with `implemented` (false for commands of a later stage, as "(not implemented yet)" in the CLI help; both come from the same runtime registry). Calling one of those is `command.not-implemented` with 501. Other paths are 404, other methods 405 with `Allow`; such refusals carry an `input.invalid` error object. Every answer, also a refusal that does not need the body (401, 403, 404, 405) and the catalog, comes after the request body has been read (and dropped), with the same bound: a refusal leaves the keep-alive connection usable, and past 32 MiB it is sent at once with `Connection: close` and its own status, the rest drained as for 413 and then the connection cut (#200). Node's own client sends a `GET` or `DELETE` body without `Content-Length` or `Transfer-Encoding` unless the caller sets one; no server can tell such bytes from the next request, so it answers 400 and closes. A request whose headers do not arrive within 10 s, or whose body does not arrive within 30 s, gets 408 and the connection is closed (`HEADERS_TIMEOUT_MS`, `REQUEST_TIMEOUT_MS`).
- Authentication: a random 256-bit token generated at start and written with mode 0600 to `<cache>/api.json` together with the port, the URLs and the process ID (`schemas/api-endpoint.schema.json`; `<cache>` is the cache folder of the working copy, ADR-0008). On Windows the mode bits do not apply; the file is private because `%LOCALAPPDATA%` in the user profile is readable only by the user, SYSTEM and administrators (its default ACL). Clients send `Authorization: Bearer <token>` (the scheme in any case), else 401. Requests with a `Host` header other than `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>` (the port of the connection) are rejected with 403 (DNS rebinding), and so are requests with an `Origin` header (no browser access). The checks run before any command.
- One API per working copy: while the API of `api.json` runs, a second `serve api` for the same copy refuses to start (`input.invalid`). When the process ID of the file does not run, the file is stale and replaced at once. When it runs (it may be reused by another process), the file's URLs are asked: the API runs when `GET /v1/commands` with the token of the file answers 200, or when a URL accepts the connection and gives no answer within 1 s (a busy API). Only URLs of the form `http://127.0.0.1:<port>` or `http://[::1]:<port>` are asked, through a fresh HTTP agent that never uses a proxy (`HTTP_PROXY`, `NODE_USE_ENV_PROXY`), so the check never leaves the machine. Any other file (a refused connection, a wrong token, a broken file) is replaced. The API removes its own `api.json` when it stops. So that two starts at the same moment never both pass this check, a start holds the lock file `<cache>/api.json.lock` (exclusive create, mode 0600, with its process ID and the time it was taken, `created`; `lockCacheFile` in core) from before the check until `api.json` is written or the start failed; a start that finds the lock held refuses with `input.invalid` too. A lock is stale when its process does not run, or when its `created` time (the file's modification time only for a lock without one, e.g. one that a crashed start left half written) is more than 30 s before now, or more than 30 s after now: a clock that went back makes a lock stale, never held for ever. On Windows, where process IDs are reused soon, the lock of a crashed start can name an ID that runs again; then starts refuse for up to 30 s, until the lock is stale by age. Only one start at a time breaks a stale lock: the one that creates `<cache>/api.json.lock.break` exclusively. It removes the lock only while the lock's text and modification time are still those of the stale lock it judged, so a lock that another start took meanwhile is not removed; the break file of a breaker that crashed is removed once it is stale itself (and still the same on a second look), and that start then breaks the lock. Two corners remain, both negligible: after a breaker crashed, two starts that clear its break file at the same moment can both break; and a lock held longer than 30 s (a start normally takes about a second) is stale and can be broken while its start still runs.
- A request whose client goes away, and every running request when the server stops, is aborted through the command's abort signal.
- Port: `--port`, default 0 (any free port, SR-081). With 0, when `::1` has the port taken that `127.0.0.1` got, the server tries again with a new free port (at most 5 times). A port in use or reserved is `input.invalid` (exit code 2).
- One workspace per server process, found as for CLI commands (`--workspace`, else upwards, else the current folder) and kept open until the server stops. The server runs until Ctrl-C or SIGTERM and then ends with exit code 0.

**MCP server (`packages/mcp`)** — `logreq mcp`.
- The official MCP TypeScript SDK, v2 package `@modelcontextprotocol/server` (Apache-2.0; its runtime dependencies are only `@modelcontextprotocol/core` and `zod`; the v1 package `@modelcontextprotocol/sdk` brings `express`, `hono` and other HTTP server code). **stdio** transport only, as newline-delimited JSON-RPC over the CLI's standard input and output (`LineTransport`, framing by the SDK); the SDK's `serveStdio` serves both protocol eras. No network listener at all (SR-079). Nothing else is written to standard output.
- `tools/list` has one tool per **implemented** command (`group_action`). An agent puts the whole list into its context, so commands of a later stage are not listed, and the list stays small (#303: it was 1 MB when every schema carried whole schema files). A call to a catalog command that is not listed still reaches `invoke` and gives the tool error `command.not-implemented`, as on every access (cross-access test); a name outside the catalog is the SDK's protocol error "Tool X not found". For that the server sets its own `tools/list` and `tools/call` handlers on the protocol server of its `McpServer` (results go through the SDK's era projection, `projectCallToolResult`) and registers no tools: with `registerTool` or the `tools` capability in its options, `McpServer` installs its own handlers, which answer every unregistered tool with a protocol error.
- Input schemas are those of `schemas/generated/mcp-tools.json` (derived from the runtime catalog with the same `$ref` rewriting; a test checks equality for the product catalog), made self-contained per tool: each carries only the definitions it reaches, one by one and flat (`#/$defs/common.uuid`, `#/$defs/data-export` for a whole file), the form JSON Schema tooling of clients resolves best; inlining is not possible, because filter conditions are recursive. Tools carry no `outputSchema`: MCP (2025-11-25) does not require one for `structuredContent`, and they were four fifths of the list; `mcp-tools.json` keeps them as the contract. Every output schema there has `type: "object"` at its root, also next to a `$ref` (`data.export`); `catalog.meta.schema.json` requires it, so the SDK's 2025-era projection never wraps a result as `{ result }`. Read commands carry `readOnlyHint`. Input validation is core's alone (the server checks nothing), so a wrong input is the same `input.invalid` as on every access. A test pins upper bounds on the size of the product `tools/list` and of each tool.
- The `initialize` result carries `instructions` for agents: what LogReq is, the first commands to call, element references, short IDs and hint IDs, and how errors look. Core builds them from the catalog summaries and the schema descriptions (`agentInstructions`); the adapter adds no text.
- Results: the command output as `structuredContent` and the same JSON as text content (MCP recommends both). A `CommandError` of any class is a tool error (`isError: true`) with the error object as JSON text only. There is no `structuredContent`: it is the command output, whose schema is the output schema of `mcp-tools.json`, and the error object is not.
- One workspace per session, found as for CLI commands. The server runs until its standard input ends, Ctrl-C or SIGTERM, and then ends with exit code 0.
- LogReq never starts or controls agents (D-029).

The CLI starts both servers (`logreq serve api`, `logreq mcp`); they are its only commands outside the catalog, and no catalog group may be named `serve` or `mcp`. Start failures are printed and mapped like command errors.

**App** calls the same commands via IPC (ADR-0010).

**Errors.** Every adapter maps `CommandError.code` (`common.schema.json#/$defs/error`) with one table: `errorClass(code)` and `COMMAND_ERROR_CLASSES` in `packages/core/src/catalog.ts`, which the compiler (its `Record<CommandErrorCode, ...>` type) and a test keep complete. Each adapter maps the class: the CLI to an exit code (`EXIT_BY_CLASS`), the API to an HTTP status with the error object as body (`HTTP_STATUS_BY_CLASS`, documented in `openapi.json`), the MCP server to a tool error with the error object (every class).

| Class | Codes | CLI exit code | HTTP status |
|---|---|---|---|
| `input` | `input.invalid`, `ref.ambiguous`, `relation.not-allowed`, `variant.nested`, `reqif.invalid`, `reqif.unmapped` | 2 | 400 |
| `not-found` | `ref.unknown`, `element.not-found`, `workspace.not-found`, `file.folder-missing`, `git.commit-not-found` (exit code 4 by `EXIT_BY_CODE`) | 2 | 404 |
| `conflict` | `workspace.read-only`, `element.read-only`, `file.read-only`, `file.changed-on-disk`, `file.faulty`, `file.not-regular`, `baseline.uncommitted-changes`, `metamodel.meaning-unassigned` | 2 | 409 |
| `unavailable` | `git.unavailable` | 2 | 503 |
| `not-implemented` | `command.not-implemented` (a catalog command this version does not implement yet) | 2 | 501 |
| `internal` | `internal` | 3 | 500 |

A new code is added to the schema and to `COMMAND_ERROR_CLASSES` in the same PR; its type `Record<CommandErrorCode, ...>`, with `CommandErrorCode` generated from the schema (ADR-0003), does not compile until the new code is classified. `internal` errors carry no original error text (it stays in `cause` for local logs). Messages of `CommandError`s thrown on purpose by commands and blocks are sent as they are; they may name file paths relative to the workspace, never absolute paths or element content. A call aborted by its caller (closed window, cancelled request, the abort signal) ends as `internal` with `details.aborted: true`; there is no separate code because nobody is left to act on it.

**Same result everywhere (SR-080 AK2):** adapters only translate transport. Output objects are produced by `core`; adapters must not reshape them. The cross-access test (ADR-0011, `packages/cli/test/cross-access.test.ts`) enforces this: every catalog command runs through core `invoke`, `runCli` (with `argvFor`), the API and the MCP server on the same fixture workspace, with a default scenario (input `{}`) and the explicit scenarios listed there, and the outputs or error objects must be equal. Read commands share one copy of the fixture; write commands get a fresh copy per access; absolute fixture paths are compared as `<root>`. A new catalog command joins with the default scenario; whoever implements it adds explicit scenarios.

**Open for stage 6:** the `mapping` fields of the `reqif.*` commands and `reqif.saveMapping.file` are typed `common.schema.json#/$defs/localPath`, but SR-054 AK1 stores the mapping "als YAML-Datei im Repository". Before stage 6 they become repository-relative, or the commands check that an absolute path lies inside a repository.

## Rejected

- MCP over HTTP/SSE: would need a port and the same protections as the API for no benefit to local agents.
- gRPC or GraphQL for the API: more tooling, harder for pipelines that use curl.

# From review to merge

**Draft first (#303).** The issue carries `agent:working` from the first change (CLAUDE.md, Issues); the PR's `Closes #` sets it too, through the workflow `issue-working`. Open every PR as a draft: a draft runs only the Ubuntu lane of CI, so the pushes while it is worked on are cheap. Push once per round (the first push, then one push per fix round), never in between. When the Ubuntu lane is green on the last push of the review round (or of the first push, if the review had no blocking finding), mark the PR ready for review with the GitHub MCP tool `update_pull_request` (`draft: false`). When the review has no open blocking finding by then, enable auto-merge in the same step (Merge as soon as it is green), unless the PR is labelled `needs-human` or works on performance. That run and each later push run both lanes at once (#412). At most three PRs are ready at a time across all sessions, more for a while when the coordinator says CI has room (count them: `gh api 'repos/ThomasBirkmaier/ReqSeq/pulls?state=open&per_page=100' --jq '[.[]|select((.draft|not) and .user.type != "Bot")]|length'`; a bot's PR, such as Dependabot's, waits without runners and does not count); the others stay drafts until one has merged, because a ready PR starts fourteen jobs, three of them on macOS, and the account runs at most 40 at once, 5 on macOS (#739). Docs- and rule-only PRs skip the builds and do not count. A PR that only changes docs or rules may be opened ready at once.

**Labels.** A PR needs no labels; the board follows the issues, and labels on a PR are optional. `perf` starts the performance suite (below). No check reads the PR text or its labels, so editing them never needs a new CI run.

**Size.** `static` warns when a PR changes more than 800 lines without generated files (step `Pull request size`). Split such a PR before marking it ready, unless its change cannot be split; then the PR text says why.

**Review.** A second agent reviews each PR once with the built-in `/code-review`. It runs at effort `medium`, or `high` for a risky change as CLAUDE.md defines it. It starts at the push and does not wait for CI. Give it the issue and the SR as well as the PR. Besides the code, it checks what only ReqSeq has: the product rules and the repository text rule in CLAUDE.md, AK tags and trace, and written reasons for every ignore (ADR-0016). For every AK of the SR with method Test it names the test, the access through which the test triggers the behaviour, and the result it asserts; for the other methods it checks the record in `verification/` (#389). For each blocking finding it gives the file and line, why it is wrong, and how to show that it fails (a test, an input or a command). For a PR that changes user docs (`docs/guide/`, or the descriptions in `schemas/` the reference is generated from), it checks the whole changed guide page, or every description in a changed schema file, not only the diff: each statement about a concept or behaviour with its source (glossary term, SR, decision, ADR, or code file), and every statement without one or against it, and every cited ID that does not say what it is cited for, is blocking (CLAUDE.md, Repository text). For an AK with visible behaviour, the PR shows the evidence: the CLI output, or a light-theme screenshot from the PR's Electron test; a PR writes no demo file. For a spec PR, it checks that the PR names the touchpoints of the dependency check (`spec-change`) and what was done with each, and, for a content change as CLAUDE.md (How we work) defines it, the concept review (`spec-change`); a missing one is blocking. Use `/security-review` in addition for changes to file access, the bridge between the app's processes, or the dependencies.

## Filter: a separate step by the author or the session that started the review

The filter applies this list and never downgrades a finding on it. Blocking findings are correctness, a broken product rule, wrong or missing AK tags or trace, an AK with method Test that no test triggers through the access the AK names (for all four accesses, a core test plus a tagged cross-access scenario; an app test only for app UI), a breach of the repository text rule (also a doc statement without a source or against it), and an unjustified ignore or weakened gate. A blocking finding or red CI the PR caused starts one fix round (a red job it did not cause: below, Merge as soon as it is green), which also takes that PR's should-fix items. Send the fix round to the agent that wrote the code (SendMessage) while it is reachable, because it still has the context; send the findings soon after the review. Otherwise start a fresh agent with the plan, the findings and the diff. The fix needs no new review, unless it adds logic the findings did not ask for. A blocking finding too large for the PR is fixed in a PR of its own, and this PR stays a draft until that one merged; the fix becomes an issue only if CLAUDE.md (Issues) allows one. Without a blocking finding, small should-fix items are fixed in the PR, the rest stay as notes in the PR description and become no issue (CLAUDE.md, Issues), and the PR merges on green CI.

## CI changes

`main` blocks force-pushes and deletion and requires the checks `static` plus `checks` and `electron` on each of `ubuntu-24.04`, `macos-26` and `windows-2025`. A CI change that aims at speed or cost names its measure and its baseline, and is measured again two days after its merge with the same method (set the reminder when it merges); it is reverted if it missed its target (#412). When a condition behind the CI strategy changes (runner cost, visibility, required checks), check the strategy again.

## Conflicts and stacked PRs

No stacked PRs (#412): branch every PR from `main`, never from another PR's branch. A squash merge of the lower PR forces every PR above it to merge `main` and run the whole CI again. Work that builds on an open PR waits for its merge, or goes into the same PR.

Merge `main` into a PR only when GitHub reports a conflict, after a change of its base branch (below), or when the PR is red because `main` is (an open issue labelled `main-red`, written by `main-check.yml`, #796; fix `main` first, then merge it into the PRs it broke). The ruleset does not require an up-to-date branch, so merging `main` without a conflict only starts a full run. Merge it with `pnpm merge:main`, which regenerates conflicting generated files. A conflict resolved by hand needs a look at that diff before the merge. If the two sides cannot both be kept, label the PR `needs-human` and give the product owner the options.

## Merge as soon as it is green

PRs labelled `needs-human` are not merged. Once the review has no open blocking finding and the PR is not a draft, enable GitHub auto-merge with the GitHub MCP tool `enable_pr_auto_merge` (`mergeMethod: SQUASH`) and subscribe to the PR's activity (#412): GitHub merges when the required checks pass. Set one check-in for about 40 minutes later as well: auto-merge sometimes does not fire, and a job the runner cancelled sends no event; then read the head's check runs and merge by hand. A later push keeps auto-merge on, so disable it (`disable_pr_auto_merge`) before a push that needs a new review. Auto-merge reads only the required checks, not the other checks below: so a PR that works on performance (`perf` below) is merged by hand. If GitHub refuses it, or another check below is red, merge by hand on the check-run event, when the check runs of the head commit (`GET /repos/ThomasBirkmaier/ReqSeq/commits/{sha}/check-runs?per_page=100`) show all of this:

- The PR is not a draft, and `static` as well as `checks` and `electron` for `ubuntu-24.04`, `macos-26` and `windows-2025` exist on the head commit and concluded `success`. Each of these names needs one `success` on the head commit; cancelled runs of the same name from superseded runs do not count against it, and skipped matrix jobs show names like `checks (${{ matrix.os }})` or `electron (ubuntu-24.04, ${{ matrix.shard }}/2)` and do not count; one green workflow is not enough, and `electron` is green with skipped steps on a docs-only PR (ThomasBirkmaier/ReqSeq-archive#520).
- Every other check run completed with `success` or `skipped`. The one exception is a PR that works on performance: there `perf` may be red when every row over its limit was already over it on main and no measurement is worse. The PR names the rows and the comparison. The label `perf` starts the perf job once when it is added, not on later pushes, so add it after the last reviewed push, and measure the comparison locally in the container.

A change of the base branch starts no CI run (#372): after it, merge the new base with `pnpm merge:main` and push before the merge, so the checks ran against it.

**A red job the PR did not cause** (a flaky or timed-out test, or a step that fails on code the PR does not touch) is a bug on `main`, so it gets an issue before any re-run (CLAUDE.md, Issues: a failing test). If a `main-red` issue is open, that is the issue: do not re-run, fix `main` first (Conflicts and stacked PRs). Otherwise search the open issues for the test file or test title, not the error text (`gh api -X GET search/issues -f q='repo:ThomasBirkmaier/ReqSeq is:issue is:open servers.test.ts'`); if one exists, comment there with the new job link. Else open a `bug` following CLAUDE.md, Issues, with the area of the failing code and `P2` unless it blocks most PRs, naming the job link, the step, the test and its error. You find the failed step with `GET .../actions/runs/{run_id}/jobs` (`steps[].conclusion`), because the annotation only says "exit code 1" (ThomasBirkmaier/ReqSeq-archive#566). A pure runner fault (a lost runner, a GitHub outage) needs no issue. Then, once the whole run has completed, re-run only its failed jobs (`POST .../actions/runs/{run_id}/rerun-failed-jobs`, or the GitHub MCP tool `actions_run_trigger` with `method: rerun_failed_jobs`); never push an empty commit for it. A red nightly run gets its issue from `nightly-check.yml` (below).

Merge with `PUT /repos/ThomasBirkmaier/ReqSeq/pulls/{n}/merge` and `merge_method: squash`, keeping the `Implements:` trailers; GitHub deletes the branch. Use `rebase` instead only when the commits should stay revertible one by one. Never merge red.

## After the merge

The steps below follow every merge, an auto-merge too: its `closed` event wakes the subscribed session.

`main` gets no full CI run after a merge, only `main-check` (typecheck and lint), the nightly run and a manual one. A red nightly run is the first work of the morning, fixed through a PR to `main` (#340); `nightly-check.yml` opens an issue `Nightly run is red: <workflow>` for it and closes it on the next green nightly run. This is no licence to merge without green PR CI.

Comment on the issue the PR closes with the merge commit and, for an SR, the tests that cover each AK (`pnpm trace-check --require SR-xxx` lists them and fails on an AK without its test or record). The workflow `issue-working` removes `agent:working` from the issues the PR closes.

## Release

A release x.y.z needs only steps 3 and 4; a release x.y with its milestone needs all four.

1. The milestone's issues are closed, and `pnpm trace-check --require <the SRs its issues complete> --report trace-<milestone>.md` passes.
2. Prepare the acceptance: what to try in the app or CLI, the `verification/` records with method Inspektion or Demonstration, and the known limitations. Count the keys three tasks take in the app and compare them with the last milestone: (1) open a given requirement, (2) all requirements of a need, (3) all requirements without a passed test; note the numbers (#362).
3. A PR bumps the root `version` (and runs `pnpm contracts:generate`); for a version x.y its description carries the trace-check report and the acceptance notes of steps 1 and 2, for x.y.z only the version. The same PR adds the summary for the user, `docs/releases/<version>.md`, as its README there says: what changed for the user since the last release, in words of the app. After its merge, start the `Release` workflow by hand once on `main` (`ref: main`, not the PR branch); it publishes nothing, finds packaging regressions (ADR-0014), and saves the download cache where the tag run can read it, because a tag run reads only the caches of its tag and of `main` (#1238). The tag goes on the commit this run checked: after a fix, or when the tag follows more than 7 days later (GitHub evicts an unused cache after 7 days), run it again on the new `main`.
4. After the product owner accepts, the product owner sets the release tag ADR-0014 names on the checked commit; agents cannot create tags. The tag starts the `Release` workflow, which writes the release text from the summary and the commits. When a summary of a published release changes, start the workflow `Release texts` by hand on `main`. Never mark a milestone accepted yourself.

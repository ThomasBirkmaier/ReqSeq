# Stage run

The lead engineer agent runs this skill and keeps the issues tidy. The GitHub project "LogReq" is the overview board. It is filled by the workflow `project-sync` from the labels, so manage issues **only through labels, state and sub-issues** (REST). Never edit project fields by hand; they are overwritten. Mapping: `stage:<n>`/`querschnitt` -> Stage; `sr`/`enabler`/`bug`/`spec-frage`/epic marker -> Kind; closed -> Done, `needs-human` -> Needs human, `blocked` or `spec-frage` -> Blocked, `agent:working` -> Working, else Ready -> Agent state; `thema:<slug>` -> Thema; title prefix -> SR.

Hygiene on every run: each open issue has exactly one of `sr`, `enabler`, `bug`, `spec-frage`; SR and enabler issues have a stage label or `querschnitt` and hang under their epic; `agent:working` is removed when an agent stops; stale `blocked` labels are cleared when the blocking issue closed.

1. **Preconditions.** Stage 0 (architecture, D-052) is merged before stage 1 starts. Previous stage accepted (release tag `v0.<n-1>` exists), except stage 0 and 1.
2. **Order.** Run `github-issue-dependency-analysis` for the stage if it has not run since the spec last changed.
3. **Pick work.** Open issues with `stage:<n>`, without `blocked`, `spec-frage`, `needs-human`, `agent:working`, in the order from step 2. Respect parallelism: stage 0 and 1 at most 2 agents, later stages at most 5. Avoid two agents on the same package at once when the plans overlap.
4. **Start agents.** Each agent runs `github-issue-workflow` for one issue in its own session or worktree, then `github-pr-review-merge`. Agents that plan, review or decide architecture run with effort `high`; routine implementation runs with normal effort (CLAUDE.md).
   Keep the lead's own context small (#392): short agent reports, side questions that are not about the stage go to the coordinator for their own thread, and once a day or when the context grows large, save the state to project memory (file `logreq-stufe<n>`) and the stage epic, and ask the coordinator for a fresh lead thread.
5. **Watch.** On each merge, refresh blocked labels (dependency markers) and pick the next issue. Agents that stopped with `blocked` or `needs-human` are listed for the human.
6. **Spec questions.** Collect open `spec-frage` issues into one message for the product owner (question, options, recommendation), at most once a day. After answers: an agent enters the product owner's answer into `spec/` with the LogReq CLI or MCP (a new version of the element with `element update`, or a new element with `element create` and `element supersede` for the old one), in its own PR with label `enabler`, in German, with exactly the decided content (nothing added, left out or reinterpreted) written as requirement text, not as a quote of the answer (CLAUDE.md, "Sources of truth"). An agent changes a status in `spec/` only to carry out a decision the product owner stated explicitly (decision card, issue comment or a statement in the chat), names it in the PR and commit (an issue comment by its link; a decision card or a chat statement by date and paraphrase, without chat quotes, message times or thread links, CLAUDE.md "Repository content"), and never sets `accepted` (or any approving status) on text it wrote. Superseding the predecessor of such a decision is allowed in the same PR. The product owner accepts agent-written successors in person, prompted in the stage epic. Then `sr-issues`.
7. **Stage done** when all SR issues of the stage are closed and `trace-check --stage <n>` passes. Then open a PR that adds `<n>` to `COMPLETED_STAGES` in `packages/core/src/commands/registry.test.ts` (from then on every catalog command of the stage must have an implementation) and merge it with green CI. Then prepare acceptance: a short list of what to try in the app or CLI, all `verification/` records with method Inspektion or Demonstration, known limitations. **Stage 3 only, gate G2a (N-032):** Thomas personally accepts the look and feel of the app (simple, minimalist, aesthetic, Logseq as the benchmark). There is no SR for it: prepare screenshots and a short demo, label the stage 3 epic `needs-human`, and never mark it as accepted yourself. Thomas accepts; then tag `v0.<n>` and start the next stage.

# Changing the spec

The product owner follows a spec change by these steps and should not have to check the process themselves. Keep one checklist line per step. A step is done, or it reads "not needed, because …". Every message that asks for an approval names the step, what was checked and what comes next. An approval covers only the step it was asked for: approving a mockup or a concept does not approve the wording, the issue cut, a status or the implementation.

1. **Dependency check**, before any question, mockup, card or element change (below). Result: the touchpoints.
2. **Content change?** Yes for a new or superseding element, a changed title, text or acceptance criterion, a new or removed relation (CLAUDE.md, How we work). No for confirming outdated relations, setting a status or fixing a typo: say why and go on with step 7; a status still needs the decision that "Status is set by people" asks for.
3. **Open questions** the concept needs, each with a recommendation; wait for the answers (Questions before the spec PR).
4. **Mockup**, when the change alters what the app shows or how it is operated: a clickable mockup (an Artifact where the session has one) in the app's real sizes (window, card width, font size), shown to the product owner before the concept is written; the concept review reads it too (its path or link in the `fable-reviewer` prompt). The spec PR's Mockup heading says what it showed and that it was shown, without a link. Not needed when the product owner waives it, or when the change adds, moves or removes no visible element and changes no interaction (a text, a value, a colour).
5. **Concept and its review.** The concept has the edge cases and the proposed cut into issues with their SR lines; `fable-reviewer` reviews it once (below).
6. **Approval of the wording and the issue cut**, with the questions the review raised, on one decision card. A status follows "Status is set by people".
7. **Spec PR.** Its text has these headings: Content change, Mockup, Dependency check, Concept review, Outdated relations, Issue cut; each says what was done or why it was not needed.
8. **Issues and their check**, after the spec PR has merged. Create the issues from the approved cut (CLAUDE.md, Issues). Before `agent:working` is set on the first of them, run `pnpm issue-check --epic <n> --require <each SR the PR added or changed>` for the countable part, and a fresh agent reads them in full against the concept, the approved wording and the merged spec PR: every acceptance criterion the PR added, changed or removed, and every SR it superseded, is in the SR line of an issue or the check says why none is needed (for example the tagged test that already shows it), the SR line of an epic equals the union of its sub-issues, the order works, and no issue goes beyond the approved wording. Fix the gaps in the issues, then post the result as a comment on the epic (where the cut has no epic, on each of its issues): the issues read, each gap and its fix, and what was not checked; report its link to the product owner.
9. **Implementation** starts after step 8; the `implementer` prompt links the issue-check comment.

## Mechanics

`spec/` is a ReqSeq workspace, and `spec/README.md` has the layout and the common commands. ReqSeq changes it, nothing else does: `node packages/cli/dist/bin.js element create|update|set-status|supersede ... --workspace spec`, or the MCP server `node packages/cli/dist/bin.js mcp --workspace spec` (server `reqseq` in `.mcp.json`, after `pnpm build`). An `element update` of the title, the text or single list items needs `--expected-file-sha256` with the `fileSha256` that `element get` gave (#269). Change one acceptance criterion with `--set-items 'acceptance-criteria={"2":"…"}'` (position from 1, as the AK number; the next position appends), not by sending the whole list (#177). A spec PR holds no code change; changes that belong together (one wish, one review pass) share it. It must pass `pnpm spec:check`. A new spec ID (`spec-id`, such as SR-036) takes the next number after the highest one on `main` and in the open spec PRs, because ReqSeq sees only the working tree: `git fetch origin && git grep -h -o 'spec-id: "\?SR-[0-9]*' $(git for-each-ref --format='%(refname:short)' refs/remotes/origin | grep -v '^origin$') -- spec/ | grep -o 'SR-[0-9]*' | sort -t- -k2 -n | tail -1` (for other prefixes, replace `SR`). `pnpm trace-check` reports an SR spec ID used twice, and `pnpm spec:check` warns about any duplicate spec ID, once both are on one branch. The metamodel (`spec/metamodel/`) and `spec/reqseq-workspace.yaml` have no command and are changed by hand in such a PR.

**Dependency check first.** Every new or changed element starts with its touchpoints, before any question, card or element change: `trace affected <ref>` for each element the change touches, `hint list --ref <ref>` for the hints open on them, and one `element search` per changed or new term and per `synonyms` entry of its glossary term (every word of one query must match, so a combined query finds too little). For a new element, the elements it will relate to and those the `element search` finds are its touchpoints, and `trace affected` runs on each of them. `trace` follows relations and inline references only, not words in a text: for the glossary term „Paket“ it returns 1 affected element, while 48 SR files contain the word. Read each touchpoint against the change. For every content change of the spec (step 2), write a concept with its edge cases, have it reviewed once by the independent agent `fable-reviewer` (prompt: `Case: concept review`, the path of the concept, the result file) (by an Opus agent at effort high when the product owner names Opus for it), which also checks the cut into issues and lists what must change in the issues of the SRs involved, and only then put it on a decision card. The spec PR names the concept review (number of findings and what was done with each high one; findings about code or tests are checked against them first) and each touchpoint and what was done with it: unchanged and why, changed in the PR, or a `question` issue; the outdated relations after the change follow the paragraph below.

**Glossary terms.** A new glossary term names an `english-term` that no other term carries; a short form is the last word of the phrase and only where that word is not another term's value (metamodel, #1428). A changed `english-term` lists the places in `schemas/`, `packages/` and `docs/guide/` that use the old word as touchpoints.

**Questions before the spec PR.** When a wish leaves anything open (a value, a scope, a choice between variants), ask the product owner first, on a decision card or in the thread, with a recommendation for each question, and wait for the answers with the element and the spec PR; work that does not depend on them goes on. Only then create or change the element and open the spec PR. Never write a draft element on your own assumptions to have them confirmed later; an assumption in a spec PR is allowed only where the product owner said to proceed without an answer.

**Texts.** They are German and carry exactly what the product owner decided, with nothing added, left out or reinterpreted. Decisions in `spec/decision/` are about the system, not about the way of working. They read as requirement text, not as a quote of the chat; a rationale states the reason in neutral words, without person or date (CLAUDE.md, Repository text). Before a new SR, check whether an existing SR or decision already covers the wish. A new SR links the glossary terms of its text inline at their first occurrence (`[Term](reqseq:<uuid>)`, the UUID of the glossary entry); existing SRs are not changed for this. Add a relation only where its kind holds between the two elements (for example, one derives from, refines or rests on the other), not for a loose connection. A wish of the product owner becomes a draft element in the package of its topic once its open questions are answered (above); it has no issue. An idea of an agent goes to the product owner as a proposal in the thread first. A pure bug stays an issue, with a reproduction or a failing test (issue threshold in CLAUDE.md).

**Status is set by people.** An agent changes a status only to carry out a decision the product owner stated explicitly: on a decision card, in an issue comment or in the chat. The PR and the commit state what was decided and, where the decision gives one, why, in neutral words (CLAUDE.md, Repository text); an issue comment is named by its link, a card or a chat statement by a paraphrase of what it decided, without person or date. An agent never sets an approving status on text it wrote itself, with one exception: the product owner accepted these elements by name, on a decision card or in the chat, for a text that exists or explicitly in advance for a text still to be reviewed. That counts as the product owner's own acceptance. Superseding the predecessor is allowed in the same PR. Successors an agent wrote are accepted by the product owner in person, in the chat or on a decision card, prompted on a decision card or in the thread.

**Packages and issues.** Packages give the structure of the spec by topic, not the schedule. Every SR and need is in exactly one topic package; a new one goes into the package of its topic, set with `element update <ref> --workspace spec --set 'packages=[{"id":"<UUID>"}]'` (`element get <package> --workspace spec` gives the UUID). No script creates issues from the spec: issues are the reviewed cut of a spec change (step 8), and get their milestone and epic as CLAUDE.md, Issues says.

**Criterion numbers in prose.** Each acceptance criterion carries a criterion key that ReqSeq gives it and keeps when it moves (SR-204); tests name it by that key (`[SR-047/AK-k7f3]`, CLAUDE.md, Traceability), so they need no change. Prose names it by its number („SR-047 AK3“ in element texts and rationales, decisions, ADRs, docs, `verification/` and code comments), and that number shifts. When a spec PR inserts, moves or removes a criterion, find the prose references to that SR's criteria from the changed position on: `git grep -n -E 'SR-047 AK[0-9]|SR-047/AK[0-9]'` outside `spec/evidence/`, and `element search "SR-047"` for the elements. Correct the elements in the same spec PR with ReqSeq, and list the references outside `spec/` in its text; the PR that implements the change corrects them by hand. Stored records in `spec/evidence/` are never rewritten (D-076).

**Outdated relations in the same PR.** A content change of an element makes every relation and reference that points at it outdated (`relation.outdated`, SR-025). Before opening the spec PR, list them with `node packages/cli/dist/bin.js hint list --workspace spec --kind relation.outdated --json` and take those whose `targetIdentifier` is an element the PR changed. Read each source against the change, and either confirm the hint with `hint confirm --workspace spec --hint-ids <hintId>` (SR-027; it changes only the stored versions and titles of the targets) or change the source in the same PR when the change contradicts it. The PR text names the sources and the result. A superseded source whose text no longer matches the target is neither confirmed nor changed; its hint stays open.

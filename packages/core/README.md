# @logreq/core

All program logic of LogReq (ADR-0002). CLI, API, MCP server and app are adapters that only call `invoke`.

## Calling a command (adapters)

```ts
import { CommandError, Workspace, invoke } from "@logreq/core";

const workspace = new Workspace(root); // one object per workspace root, kept for the process
try {
  const output = await invoke("element.get", { ref: "SR-46fb54" }, { workspace, signal });
} catch (error) {
  if (error instanceof CommandError) {
    // error.toJSON() is common.schema.json#/$defs/error: { code, message, details? }
  }
}
```

`invoke(name, input, { workspace, signal? })`:

1. Looks up the implementation. A catalog command without implementation gives `input.invalid` ("Command X is not implemented yet"), a name outside the catalog `input.invalid` ("Unknown command: X").
2. Copies the input, fills in `default` values from the catalog schema and validates it with Ajv against the entry's `input` schema in `schemas/commands/catalog.json`. `$ref`s like `../common.schema.json#/$defs/uuid` resolve against `schemas/*.schema.json`. A mismatch gives `input.invalid` with `details.errors` (`path`, `keyword`, `message`, `params` per check). `run` is not called.
3. A `write-files` command (except `workspace.init`, which creates the workspace) is refused with `workspace.read-only` while the workspace is read-only (`src/metamodel/access.ts`, SR-011 AK3); `details.problems` gives the reasons. The exemption is an interim list in `runtime/invoke.ts` until the catalog entry carries it (#142). `run` is not called.
4. Calls `run(ctx, input)` with `ctx = { workspace, signal }`.
5. Maps failures: a thrown `CommandError` passes through unchanged; anything else becomes `internal` with the message `Internal error in X`. The original error, and its text, is only in `cause`, never in what adapters send. An abort (the signal fired, or an `AbortError`) is `internal` with `details.aborted: true` (ADR-0009).
6. With output validation on (`LOGREQ_VALIDATE_OUTPUT=1`, always in tests via `vitest.config.ts`, and in debug builds) the output is checked against the entry's `output` schema; a mismatch is `internal`.

Findings are never thrown: commands return them as `problems` (`common.schema.json#/$defs/problem`). Adapters map a `CommandError` code with `errorClass(code)` (`input`, `not-found`, `conflict`, `unavailable`, `internal`; the table is `COMMAND_ERROR_CLASSES`); how each class becomes an exit code, HTTP status or MCP tool error is ADR-0009.

`cacheFolder(root)` (workspace block, `src/workspace/cache.ts`) is the cache folder of a working copy, `<OS cache>/logreq/<sha256 of the canonical root>` (absolute, symbolic links resolved, lower case on Windows; ADR-0008, SR-081 AK2); `writeCacheFile(folder, name, text)` writes a private file there (mode 0600, through `writePrivateFile` of the files block), e.g. `api.json` of the local API (ADR-0009), `readCacheFile` reads one back (`undefined` when missing) and `removeCacheFile` removes one (through `removePrivateFile`). `lockCacheFile(folder, name)` takes the lock `<name>.lock` next to a cache file (`lockPrivateFile` of the files block, `src/files/lock.ts`: exclusive create, mode 0600, with the process ID and `created`; stale when that process does not run (`processRuns`) or `created` is more than `LOCK_STALE_MS` away from now; one breaker at a time through `<name>.lock.break`) and resolves `undefined` while another process holds it; `release()` removes only its own lock and never rejects.

`findWorkspaceRoot(start)` (workspace block, `src/workspace/root.ts`) returns the nearest folder from `start` upwards that holds `logreq-workspace.yaml` (`WORKSPACE_FILE`), or `undefined`; adapters use it when no workspace is given (ADR-0009). `PRODUCT_NAME` and `PRODUCT_VERSION` come from the root `package.json` (embedded by `pnpm contracts:generate`), so every access reports the same version. `contracts.schemas` are the schemas that `$ref`s of the catalog resolve against; adapters that read input schemas (CLI flags) use them.

Adapters share one runtime per process: `getCommandRuntime()` returns it (created with the defaults on first use) with the catalog (`contracts.commands`, for CLI subcommands, API routes and MCP tools) and the implemented commands (`commands`). `configureCommandRuntime(options)` sets it, e.g. with `validateOutput`: adapters configure before the first call; replacing it later is for tests. `createCommandRuntime({ commands, contracts, validateOutput })` builds a separate one with other implementations or another catalog (`loadContracts({ catalog })`); tests use it for test-only commands.

## Writing a command (SR work)

1. The catalog entry exists in `schemas/commands/catalog.json` (name, effect, stage, implements, input and output schema). Changing it is a contract change (ADR-0002 rule 1).
2. Write `src/commands/<group>/<action>.ts`:

   ```ts
   import { defineCommand } from "../../catalog.js";

   export default defineCommand({
     name: "element.get",
     run: async (ctx, input) => {
       // input: ElementGetInput, the result must be ElementGetOutput; both come from the catalog.
       const store = ctx.workspace.get(elementStore); // per-workspace state, see below
       // ...
     },
   });
   ```

   The definition has only `name` and `run`. Summary, effect and schemas come from the catalog, so they cannot drift. The name picks the catalog entry, and `input` and the result of `run` get its generated types (`CommandInput<"element.get">`, `CommandOutput<"element.get">`; see "Generated types"), so a command never writes its own interfaces for them. `input` has already passed the schema, with defaults filled in. The compiler reports extra properties in the result only where it checks object literals against a declared type: write the return type (`Promise<CommandOutput<"element.get">>`) to get that; otherwise the output check in tests catches them. Tests with a test-only catalog use `defineTestCommand<In, Out>({ name, run })`, which takes the types instead of a catalog name.
3. Import it in `src/commands/index.ts` and add it to `commands` (sorted by name). Every `.ts` file in a group folder is taken as a command, so helpers belong in the blocks (`src/model/`, `src/metamodel/`, ...), not next to the commands.
4. `src/commands/registry.test.ts` checks that files, the list and the catalog agree: every file is registered under the name of its path, every implementation has a catalog entry, and every catalog command of a completed stage (`COMPLETED_STAGES`) has exactly one implementation. A stage is added to `COMPLETED_STAGES` when it is done, in a PR with green CI before its acceptance is prepared (stage-run skill, step 7).
5. Errors: `throw new CommandError("element.not-found", "No element SR-46fb54", { ref })`. Codes are `CommandErrorCode`, the generated union of `common.schema.json#/$defs/error`; a new code goes into the schema (then `pnpm contracts:generate`) and into `COMMAND_ERROR_CLASSES` in the same PR (its `Record<CommandErrorCode, ...>` type does not compile until the code is classified). Problems use `ProblemCode` from `#/$defs/problemCode` the same way.

## Workspace state

All state lives in the `Workspace` object of its root (ADR-0002 rule 7); there are no globals, so two copies of a workspace never share anything (SR-081). A block defines its state at module level and gets it lazily:

```ts
import { defineWorkspaceState } from "../runtime/workspace.js";

// Async state: create returns a Promise; every caller gets the same one, a rejected one is dropped.
export const metamodelState = defineWorkspaceState("metamodel", (ws) => loadMetamodel(ws.root));

export const modelState = defineWorkspaceState("model", async (ws) => buildModel(await ws.get(metamodelState)), {
  dependsOn: [metamodelState], // reset of the metamodel resets the model too
  dispose: async (model) => (await model).stopWatcher(), // on reset and close, only after a successful build
});

await ctx.workspace.get(modelState); // created on first use, then kept
await ctx.workspace.reset(metamodelState); // e.g. after the watcher saw a change: drops metamodel and model
await workspace.close(); // adapters, when the workspace is closed: disposes everything
```

`new Workspace(root, { cacheFolder })` reads nothing; with `cacheFolder` (the CLI passes `cacheFolder(root)`) the element store is loaded through the model cache there (below), without it every load reads all files and nothing is written outside the working tree (the default for tests). State is built when a command first asks for it. `reset` and `close` remove the values at once and then dispose them one by one, dependents first (independent states newest first). They wait for pending async builds and skip builds that rejected, so they never fail with a build's error. Every disposal runs even if one fails; then they reject with an `AggregateError`. A `get` during a reset may build new state while the old one is still being disposed. A rejected async build is dropped without resetting its dependents. After `close`, `get` throws. `peek(key)` gives the current value without building it; `replace(key, from, to)` sets a new value only while the current one is still `from`, resets the dependents and then disposes `from` (the watcher's file-by-file update of the store, SR-007).

## Generated types

`src/generated/types.ts` holds the TypeScript types of all schemas and catalog commands, written by `pnpm contracts:generate` (`scripts/contracts/types.mjs`) and checked by `pnpm contracts:check`; never edit it, never write a type by hand that mirrors a schema (ADR-0003). `@logreq/core` exports all of them.

- File formats: `WorkspaceFile`, `MetamodelFile`, `ElementFile`, `BaselineFile`, `DataExportFile`, ... (root of `schemas/<name>.schema.json`).
- `$defs`: shared ones of `common.schema.json` by their name (`Uuid`, `ShortId`, `ElementRef`, `Version`, `Key`, `Problem`, `ProblemCode`, ...; renamed where a name would shadow a global: `error` is `CommandErrorObject`, `date`/`dateTime` are `IsoDate`/`IsoDateTime`, `selection` is `ElementSelection`), others prefixed with their file (`FilterCondition`, `MetamodelType`, `WorkspaceRepository`, `DataExportElement`).
- Commands: `<Group><Action>Input` and `...Output` (`ElementGetInput`), and `CommandTypes` from name to both. `catalog.ts` builds on it: `CommandName`, `CommandInput<N>`, `CommandOutput<N>`, `CatalogCommand<N>`, `CommandErrorCode`, `CatalogEntry` (`runtime/contracts.ts`, from `catalog.meta.schema.json`).
- An input type is what `run` gets: a property with a `default` is required (`ElementListInput.limit` is `number`), because the input validator fills it in, also through `$ref` and `allOf`. A referenced `$defs` entry that reaches a default is used in inputs as `<Name>WithDefaults` (`FilterSortKeyWithDefaults`, `order` required); the plain type stays for outputs and files. Below `anyOf`/`oneOf` (and in `if`/`then`/`else`) the type keeps such properties optional; Ajv may still fill them, which optional covers.
- Formats, patterns and lengths are not types: a `Uuid` is a `string`. Values come from validated input or from the command itself; the output check in tests catches the rest.

## Workspace block (`src/workspace/`)

`workspaceLayoutState` (async Workspace state) reads `logreq-workspace.yaml` in `Workspace.root` (checked against `workspace.schema.json`) and the optional, untracked `.logreq/local.yaml` (`workspace-local.schema.json`), and locates every repository (SR-004):

- Path: the local override, else `path` of the workspace file, else `../<name>`. The main repository (the entry with `main: true`; the only entry of a one-repository workspace) is always the root, `.`. Relative paths are relative to the root. Committed paths use `/` (a `\` is warned about and replaced); an absolute committed path is warned about and ignored, absolute paths belong in `.logreq/local.yaml`. There is no `~` expansion.
- `available` means the folder exists; `folder` is then its real path. A missing repository is normal (N-041): `available: false` and an `info` problem `workspace.repository-missing`; nothing else changes (SR-004 AK3).
- A repository in the same folder as another one is left out (`workspace.invalid` error; the main repository always stays). `excludes` lists the folders of other available repositories nested inside a repository (e.g. submodules); discovery skips them.
- `availableRepositories(layout)` gives the roots in which elements are discovered (SR-003). `locate(layout, location)` resolves a `{ repository, path }` location; `settingLocation(layout, "baselines" | "filters" | "mappings")` gives the configured location or the default in the main repository.
- `layout.metamodel` names the metamodel folder and whether it exists (`metamodel.invalid` error with the reason otherwise); loading it is the metamodel block (SR-011, below). `layout.file` is the checked workspace file for later blocks (evidence, ignore).
- No workspace file: `CommandError workspace.not-found`. A faulty one (YAML, schema, a repository name listed twice): `file.faulty` with `details.problems`; it is never used in part. A location naming an unknown repository and a faulty local file are problems; the workspace still opens.
- The layout, including availability, is kept until `workspace.reset(workspaceLayoutState)` (the watcher, SR-007). Finding the workspace root upwards from a folder is the CLI's job.
- `isWritableFolder(folder)` (`src/workspace/writable.ts`) asks the operating system whether this process may write the repository folder itself (`access(W_OK)`); it writes nothing. `workspace.status` uses it on every call for `repositories[].readOnly` of each available repository. Rights to change a repository are enforced by the Git server (D-016, D-024): the usual read-only metamodel repository is a writable local clone whose pushes are refused, and LogReq never pushes (D-036). A locally read-only repository (a read-only file system, a checkout without write permission) is normal too: it never makes the workspace read-only, and a write into it is refused by the files block with `file.read-only` (SR-018 AK2). On Windows `access` never reports a folder as read-only, so `isWritableFolder` returns undefined there and `readOnly` is left out (unknown); the write itself is still refused with `file.read-only`.

`workspace.init` (`src/commands/workspace/init.ts`, SR-014) creates a workspace with `createWorkspace(root, { name, metamodel, metamodelFile })` (`src/workspace/init.ts`); the command passes the shipped standard model as `metamodelFile`:

- `path` is resolved against the root of the call (`localPath`: the CLI passes it absolute, API and MCP relative to the root). It must be an existing folder (`file.folder-missing`, `input.invalid` for a file). Other files in it are fine (a fresh clone has `.git`), but `logreq-workspace.yaml` and the metamodel file must not exist (`file.changed-on-disk`); nothing is written then. `path` is not confined to the root of the call: an absolute path, or one with `..`, creates the workspace outside the root that an API or MCP server serves (wherever the process may write); `workspace.init` creates a new workspace, so it has no workspace of its own to stay inside.
- It writes `<metamodel path>/standard-model.yaml` (default folder `metamodel`, created by `createFolder` of the files block; `.` is the root) and then `logreq-workspace.yaml`: `name`, one repository named after the folder (`repositoryNameFor`: `Weather Station` becomes `weather-station`, `main` when nothing is left), `url: ""` for the person to fill in, and the metamodel location. The file is checked against `workspace.schema.json` before anything is written (`input.invalid` with `details.errors`). If the workspace file then cannot be written, the error keeps its code and names the metamodel file that was written before it (message and `details.written`); it is left in place.
- `metamodel.repository` naming another repository (SR-018) lists it in the workspace file with `url: ""` and its default path; nothing is written outside the folder, so that repository keeps (or gets) its own metamodel.
- Output: `files` (written, relative to the new root) and `problems`, the layout and metamodel problems of the new workspace as opened afterwards (none for the standard model). When the root of the call is the new folder (compared with links resolved), its layout state is reset. No Git command runs (D-036).

## Metamodel block (`src/metamodel/`)

`metamodelState` (async Workspace state, depends on `workspaceLayoutState`) reads the metamodel of the checked-out state (SR-011, D-021) with `loadMetamodel(layout)`:

- Every `*.yaml` file directly in the folder that `layout.metamodel` names, from the working tree, sorted by name (code-unit order). Subfolders and hidden files (`.` first) are not read; a `*.yml` file gives a `metamodel.invalid` warning. Nothing else is read: no built-in model, no other folder, nothing from Git. When the folder is the root of the main repository (`path: .`), `logreq-workspace.yaml` is not a metamodel file, but every other `.yaml` file there is, including unrelated ones; give the metamodel its own folder.
- Each file is read with `readYamlFile` and checked against `metamodel.schema.json`. `types`, `properties`, `relations` and `statuses` of all valid files are merged in file order, as written. A key defined a second time in the same list, and a property key that a relation kind already uses or the other way round (keys are unique across both, ADR-0004), is a `metamodel.invalid` error on its line; the first definition is kept and the second left out. Problems come in file order, and within a file in line order.
- Faulty YAML is the problem of the files block (`file.invalid-yaml` with file, line and reason); a schema violation is `metamodel.invalid` with file and line. A faulty file contributes nothing; the valid files are still used (open question #141). Every problem of the metamodel files names the metamodel repository in `repository`, and `file` is relative to it (SR-018: the metamodel may lie in its own repository); a problem of the whole folder names the folder (`.` for the repository root). Problems of the layout (a missing folder or repository) name `logreq-workspace.yaml` in the main repository.
- The metamodel folder may lie in any repository of the workspace: a folder in the main repository or an own repository (SR-018, D-021). Both are read the same way.
- `valid` is false when the folder is missing (the layout reports that), unreadable or has no `.yaml` file, or any file has an error. The workspace is then read-only (`workspaceAccess`, `assertWritable` in `src/metamodel/access.ts`): reads work, write commands are refused by `invoke` (SR-011 AK3; a missing metamodel repository counts too, open question #141). `workspace.status` shows `metamodel.valid`, `readOnly` and the problems. Only the metamodel decides this: a metamodel repository that cannot be written leaves the workspace writable (SR-018 AK2).
- Kept until `workspace.reset(metamodelState)` (the watcher, SR-007, SR-015) or a reset of the layout; a new `Workspace` reads it again. Nothing is cached elsewhere, so after a checkout the tool works with the metamodel of the checked-out state (SR-011 AK2).
- The definitions have the generated types of `metamodel.schema.json` (`MetamodelFile`, `MetamodelType`, `MetamodelProperty`, `MetamodelRelationKind`, `MetamodelStatus`).
- Inheritance (SR-012, `src/metamodel/inheritance.ts`): after merging, `effectiveTypes` holds every type of `types` (same order) as an `EffectiveType`: `ancestors` (parent first, up to the root), `properties` and `required` with all own and inherited keys, each once, root type first (the key order for new keys in element files, ADR-0004); required keys count as properties. `meaning` is the own one, else the closest ancestor's; `abstract` is not inherited (default false). A parent that is not defined (only when every metamodel file was read, see below) and every type on an inheritance cycle (also across files, `a -> b -> a`) are `metamodel.invalid` errors at the line of `extends`; they make the metamodel invalid. A type naming a property that is not defined is only a `metamodel.invalid` warning at the line of the list item (#141 c, option 2, #238; the message says when the key is a relation kind): the workspace stays writable, and the effective type and every type inheriting from it leave the key out, so a value under it in an element is an `element.unknown-property` hint (D-012) and no value is required for it; `types` keeps the key as written. While a file is faulty this is neither reported nor left out. These problems come after the problems of the files, in type order. Resolution stops at an unknown parent or a cycle, so a read-only workspace still has effective types.
- References and the initial status (#157): after inheritance and meanings, every entry of `target-types` (property) and of `source-types`/`target-types` (relation kind) that names no defined type is a `metamodel.invalid` error on the line of the entry; the definition is kept as written. Exactly one status must have `initial: true`: none is an error on the first status (on the folder, without a line, when there is no status), every further one an error on the line of its `initial`. An unknown type and a missing initial status are reported only when every metamodel file was read, since a faulty file may define them; its own error already makes the metamodel invalid. The same holds for the inheritance checks (an unknown parent in `extends`, an unknown property in `properties`/`required`, #172); an inheritance cycle and a further initial status are always reported.
- Reserved prefix (#154, #239): `UNKNOWN` (`UNKNOWN_TYPE_PREFIX`) is the prefix of the short ID of an element whose type the metamodel does not know, and of a relation target that is not available. A type with this prefix is a `metamodel.invalid` error on the line of its `prefix`, reported always (also while a file is faulty); the type is kept, the metamodel is invalid. A prefix that only starts with `UNKNOWN` is allowed.
- Meanings (SR-013, D-012, D-059, `src/metamodel/meanings.ts`): the tool knows the built-in meanings that the metamodel assigns with `meaning` (`MEANINGS`: `requirement`, `need`, `variant`, `package` for types; `title`, `validity`, `packages`, `emergent`, `verification-method`, `statement`, `source`, `source-identifier`, `import-date`, `delivery` for properties; `derivation`, `replacement`, `exclusion` for relation kinds). `metamodel.meanings` gives, for every meaning, the keys whose own definition declares it, in metamodel order; a type that inherits a meaning, or sets the one it inherits anyway, is not a second assignment. A type or property meaning that a second key declares is a `metamodel.invalid` error at the line of its `meaning` (after the inheritance problems), so the workspace opens read-only (open question #141); several relation kinds may share a meaning. Functions never look for a fixed key: they first call `requireMeaning(metamodel, meaning, command)` (`command` is their `CommandName`), which throws `metamodel.meaning-unassigned` with `details: { meaning, list, command }` and a message naming the missing assignment when no key has it (SR-013 AK3), and then take the definitions from `typesWithMeaning` (effective types, so subtypes that inherit the meaning count), `propertyWithMeaning` or `relationKindsWithMeaning`. The three meaning enums are `$defs` of `metamodel.schema.json` (`typeMeaning`, `propertyMeaning`, `relationMeaning`). The structural keys `id`, `type`, `status` and the flags `content` (property) and `invalid` (status) are fields, not meanings.
- Standard model (SR-014, D-037, D-059, D-060, `src/metamodel/standard-model.ts`): `STANDARD_MODEL_TEXT` is `schemas/examples/metamodel/standard-model.yaml`, embedded unchanged by `pnpm contracts:generate` as `src/generated/standard-model.json` (`contracts:check` keeps them equal; never copy it by hand). Only `workspace.init` uses it; a workspace is never given the standard model at run time.
- `metamodel.get` (`src/commands/metamodel/get.ts`, SR-012, SR-013): the effective types (`metamodel.schema.json#/$defs/effectiveType`, the type of `EffectiveType`), the properties, relation kinds and statuses as written, `meanings` (every meaning, an empty list when unassigned) and the metamodel problems of the layout and the files (`metamodelProblems(workspace)` in `src/metamodel/access.ts`, whose errors are also the reasons of a read-only workspace). It reads, so it also works on a read-only workspace.
- Lookup (`src/metamodel/lookup.ts`): element files hold the type key, the tool shows its `name` (D-043). `findType(metamodel, key)` finds a type only by key (an index per metamodel object). `typeForNewElement(metamodel, key)` is the type `element.create` uses: it throws `input.invalid` with `details.type` and `details.reason` (`unknown` or `abstract`) when no element of that type can be created.

## Model block (`src/model/`)

`elementStoreState` (async Workspace state, depends on `workspaceLayoutState`) holds every element of the workspace, found by its frontmatter in whatever folder it lies (SR-003, D-056), with `loadElements(layout)`:

- Each available repository in the order of the workspace file (a missing one is skipped, SR-004 AK3), one folder walk each (`listMarkdownFiles`), no process spawned (N-036). Every `*.md` file counts, in any folder, hidden ones too. Left out: `.git` and `node_modules`; the `excludes` of the layout (repositories of the workspace nested in this one are read once, under their own name); folders below the repository root that hold a `.git` entry (a nested repository that is not in the workspace; spec question #145 b); paths matching an `ignore` glob of the workspace file. Links are never followed: a linked folder is skipped, a linked `*.md` file is a `file.skipped` warning (e.g. `CLAUDE.md` linked to `AGENTS.md`), and so is a Markdown file whose extension is not lower-case `.md` (`.MD`). A folder that cannot be listed is a `file.unreadable` error (`.` for the repository root).
- `ignore` globs (`ignoreMatcher`, `compileGlob` in `src/model/ignore.ts`, for the watcher too): compiled once per pattern, the same on every OS. Relative to each repository and anchored at its root; `*` any characters within one name, `?` one code point after NFC, `**` as a whole name any number of names; everything else literal; case-sensitive; patterns and paths compared in Unicode NFC, so `Übersicht/**` names that folder whether it is stored composed or decomposed (NFD, as HFS+ stores it and `readdir` then gives it; #218); wildcards match names starting with `.`; `x/**` matches `x` itself, so the folder is not even listed. Use it for folders of other tools whose Markdown frontmatter has `id` and `type` but is no element, for example documentation sites (Docusaurus, Hugo): `ignore: ["website/**"]`; otherwise each such file is an `element.invalid` error.
- Each file is read with `readElementFile` (32 at a time) and classified at once, so no parsed YAML `Document` is held for more than one file. A file is an element when its frontmatter is a mapping with `id` and `type` (ADR-0004; spec question #145, option 1). Every other Markdown file is listed in `nonElements` and never written (SR-003 AK2). A type the metamodel does not know is still an element (SR-016 AK3). An `id` that is not a UUID or a `type` that is not a non-empty string is an `element.invalid` error on its line (without a line when the key is written as an alias); that file is not loaded.
- `ElementStore`: `elements` (by repository, then path in code-unit order), `byId` (UUID to every record with it, so a copied file shows as two records; reporting that is SR-088), `nonElements`, `problems`. Every problem names its `repository`; `file` is relative to it. An `ElementRecord` is small plain data (ADR-0008): `id`, `type`, `repository`, `file`, `data` (the frontmatter values), `eol`, `closingEol`, `bom` and the `snapshot` for `writeFileAtomic`. The raw frontmatter and the Markdown text are not kept: read them with `readElementFile(repository folder, record.file)` when needed (text display, version, edit; the write checks the snapshot anyway). A lazy text cache (LRU, ADR-0008) comes with the commands that need it.
- Relations name their target by UUID, so moving a file to another folder keeps every relation to it (SR-003 AK3): look the target up with `resolveTarget(store, sourceRepository, target)` in the repository it names (relation targets below).
- Kept until `workspace.reset(elementStoreState)` or a reset of the layout. The store also keeps, per repository, what each file contributed (`repositories`), so `updateElements(store, layout, changes)` can update it file by file: list again, drop gone files (also one deleted while it is read), read new and changed ones, keep a record whose snapshot (SHA-256, size, mtime) is unchanged; the result equals a full `loadElements`, or is `undefined` when nothing changed. Change the store only through `applyStoreChange(workspace, (store) => ...)`: one queue per workspace, compare and set with `Workspace.replace`, a retry on the newer store when it was replaced meanwhile, nothing when it was never read or was reset. Versions and indexes come with their SRs (SR-091).
- Model cache (`src/model/model-cache.ts`, ADR-0008, SR-082): for a workspace with a cache folder, `elementStoreState` loads through `loadThroughCache`. `model.json` holds a header (format, `codeFingerprint()`: product version, core's dependency versions and code, written by core's build to `dist/code-fingerprint.json`; canonical root; start time of the load that wrote it) and, per repository (name and canonical folder), what each file that parsed contributed, with the inode and change time of the file. A cache that is not JSON, has another format, code or root, or an entry of the wrong shape is discarded whole. After the walk each file with an entry is `lstat`ed (blocking, 2,000 per turn of the event loop); the entry is reused when size, mtime, inode and change time match and the mtime is more than `RACY_MS` (2 s) older than the start of the load that wrote the cache; a file whose change time is less than `RACY_MS` older than that start is not written at all (inode and change time are taken at the write). `loadThroughCache` takes the clock as its last parameter (tests). Everything else is read as usual (`ReadOptions.reuse` of `loadElements`). The cache is written again in the background when `STALE_FILES` (1,000) or `STALE_SHARE` (1 %) of the files are out of date (one save after the other per workspace; `close` waits; a failed write is ignored). Only values JSON gives back exactly are cached (no `Date`, `Uint8Array`, `Set`, `Map`, non-finite numbers, `-0` or cycles); such entries, files without a snapshot and a cache folder inside a repository (also one that does not exist yet and lies there through a symbolic link) are never cached. `warmWorkspace(workspace)` (public) loads metamodel, store and short IDs and never rejects; `serve api` awaits it before it listens.
- Consistency: the store, and the states built on it (short IDs, findings), may be swapped while a command runs (the watcher). A command that needs one consistent view reads `elementStoreState` once and derives the rest from that object (`buildShortIds(store.byId, metamodel)`, `duplicateIdFindings(store)`, `valueKindFindings(store, metamodel)`) instead of reading several states one after the other. A state built on the store (a search index, SR-068) depends on `elementStoreState`, so a swap resets it.
- Watcher (`src/model/watch.ts`, `src/model/watch-tree.ts`, SR-007, ADR-0008): `watchWorkspace(workspace)` (public) starts one watcher per workspace as a workspace state; closing the workspace stops it. The CLI starts it for `logreq serve api` and `logreq mcp`. macOS and Windows: `fs.watch` with `recursive` per repository; Linux: one plain watch per folder (`FolderTree`; Node's recursive watch on Linux loses files replaced by a rename and costs one inotify watch per file). It batches events (100 ms debounce, at most 1 s), resets the layout on a change of the workspace or local file, resets the metamodel on a change in its folder, and updates the store with `updateElements` through `applyStoreChange`. Event paths are compared with the walk's paths in Unicode NFC, so FSEvents may spell a name in another normal form than `readdir` (#225). The layout gives an existing metamodel folder as its real path (`fs.realpath`: links resolved, the name as stored), so on macOS a folder typed in another letter case or normal form matches the events; events are compared with it in NFC and lower case (a safety net; a twin folder on Linux costs an extra reset). An event at the folder or a folder above it, or in a missing one, reads the layout again and compares it, so a metamodel folder that is renamed, moved, deleted or appears is noticed (#231). A metamodel folder reached through a link out of its repository is not watched. A folder watch belongs to one folder (`dev:ino`): a folder deleted and created again, replaced or emptied by a checkout is watched anew. Folders it cannot watch (`ENOSPC`) are `workspace.not-watched` warnings in `workspace.status` (`watcherProblems`), once per repository and folder; only processes with a watcher report them. `ready` resolves once the folders are watched, `settled()` once no batch or folder walk is left. `startWatcher(workspace, { watch, recursive, debounceMs, maxWaitMs })` is the same with an injected watch function, for tests; tests wait with `untilWatching` (testkit) for a probe change before the change they check.

`shortIdState` (async Workspace state, depends on `elementStoreState` and `metamodelState`, `src/model/short-id.ts`) is what every display of an element ID uses (D-017, D-056, SR-084). Build it with `buildShortIds(store.byId, metamodel)` for tests:

- `of(element)`: `SR-46fb54`, the prefix of the element's type (`findType(...).prefix`; `UNKNOWN_TYPE_PREFIX` = `UNKNOWN` for a type the metamodel does not know, decision on #154), a dash and `tail(element.id)`.
- `tail(id)`: the last hex digits of the UUID without dashes, at least `SHORT_ID_MIN_LENGTH` (6), and one more than the UUID shares at its end with any other UUID of the workspace. Unique by the end of the UUID alone, whatever the type and repository (SR-084 AK2), so each displayed tail names one UUID. Missing repositories cannot be taken into account (D-056). For a UUID of no element (a target in a missing repository) it gives the tail that tells it apart from every element.
- `find(shortId)`: `{ kind: "found", element }`, `{ kind: "unknown" }` or `{ kind: "ambiguous", elements }`, used through `resolveRef` by every command that takes an `elementRef` (`element.get`, `element.resolve`, `element.update`, `element.setStatus`, `element.supersede`; SR-060 AK3 maps them to `ref.unknown` and `ref.ambiguous`). Matches the elements whose UUID ends with the 6 to 32 digits (a displayed short ID, the 12 digits of the file name, or all 32) and whose type has the given prefix. A tail shorter than the displayed one is ambiguous unless the prefix leaves one element (a short ID another tool stored before the display grew, SR-060); files sharing a UUID (SR-088) are ambiguous; a wrong prefix or a malformed short ID is unknown, so a reference to a gone element is never retargeted to another element with the same tail.
- `withTail(shortId)`: the elements whose UUID ends with the digits, whatever their type (none for a malformed short ID). Never a match: `element.resolve` names the one element it gives as `details.candidates` of `ref.unknown` ("prefix may be outdated; did you mean ...?"), for a reference from before a change of type or prefix (#275).
- One pass: UUIDs grouped by their last 6 digits, each group sorted by code units, neighbours compared; O(n log n), independent of file order. `of` and `find` take constant time on average. Nothing is read or written: file names keep their 12 digits (D-056, SR-084 AK3).

Current versions (`src/model/current-versions.ts`, ADR-0008 "Current versions", #259): `currentVersions(workspace)` gives the current version of every element of the store (`CurrentVersions`: `store`, `byRecord`, read one with `currentVersionOf(versions, record)`), for the checks that compare stored versions with it (SR-025 and later). Built on first use, once per store, in the calling thread (each file read again with `readElementBodySync`, no YAML parse while the bytes are those of the store's snapshot; 4 to 5 s at N-036 in local runs of the performance suite); not cached. An element whose file no longer holds it, whose images cannot be read or whose counted values have no normal form has an `unknown` entry with its reason, never a failed command; such entries are computed again on the next use. `currentVersionsState` is carried over watcher batches and LogReq's own writes (`recordWrites`) and reset with the metamodel or the layout; images are checked on use (`checkImages`, `imagesUnchanged` in `src/model/images.ts`), since the watcher does not report them. Use `versions.store` for everything else the command needs, so it sees one consistent store.

`currentVersionsOf(workspace, records)` gives the current versions of some records only, in their order: from the kept `currentVersionsState`, checking the images of these records only and computing the stale ones again (the state is not changed), or, when none is kept and the records are at least a quarter of the store, from `currentVersions(workspace)`, which builds and keeps it, otherwise computed from the files of these records only, without building the state (a page of a large workspace in a fresh CLI process reads only its own files). A version entry of a file that changed since the store read it (same UUID) carries the element as the file holds it now (`element`). List commands use it through `listElements(workspace, context, records)` (`src/model/list.ts`): each record as `element.get` shows it without text, hints and `readOnly` (`listedElement` in `src/model/view.ts`, which `elementView` builds on), as its file holds it now, with its current version. An element without one is listed without `version` (optional in the data-export schema) and with one `file.faulty` warning in its `problems`; it never fails the list. At N-036 a page of 200 elements costs about 30 to 60 ms; 42,000 listed elements about 5 s with kept versions.

Value kinds (SR-085, `src/model/values.ts`): every top-level key of an element that the metamodel defines as a property (by key, whatever the element's type, D-043) or as a relation kind is checked against its kind. A mismatch is the problem `element.wrong-value-kind` with severity `warning` (a hint: it blocks nothing and changes no status), `repository`, `file`, `line` and `elementId`, and an English message with the property's name and key; for a choice it lists the allowed keys with their names (SR-085 AK2).

- text: a string (a YAML number such as `1.0` in a text property is a wrong kind; quote it). number: a finite number. date: a string `YYYY-MM-DD` that is a calendar date. choice: one of the property's choice keys. relation: a relation target (`common.schema.json#/$defs/relationTarget`); only its format: which target types are allowed is SR-086, which can take the values that pass. A relation kind holds a list of relation targets (ADR-0004).
- `many: true`: the value must be a list (empty is fine) and every item is checked, one problem per wrong item with the item's line. Otherwise a list is a wrong kind. An empty value (`key:` without value, a blank string, an empty list: `isEmptyValue` in `src/model/required.ts`) is never a wrong kind (a required one gives `element.missing-required`), but an empty item in a list (`- ` without value) is. `id`, `type`, `status` and keys the metamodel does not know (SR-016) are not checked here.
- `valueFindings(element, metamodel)`: the findings of one element, for `element.get` (with `locateFindings(layout, findings)` for the lines of just that element) and for a command that has just written it (`element.update`, SR-001). `valueKindFindings(store, metamodel)` is the one pass over all elements in memory, without reading a file (N-036; about 0.5 s at 50,000 elements). `valueKindProblemsState` (async Workspace state, depends on the element store and the metamodel) holds all of them with lines, in store order, then key order in the file, then item order, for `workspace.check` (SR-019). Its lines read every file with findings again: at 50,000 elements that all have one, that is a full read of the workspace (about 24 s).
- Lines (`locateFindings(layout, findings, { signal })`, `src/model/locate.ts`): the store keeps no YAML `Document` (ADR-0008), so the files with findings are read again with `readElementFiles`, once each and per repository, and each finding gets the line of its key path (`[key]` or `[key, item]`, `lineOf` in `src/model/elements.ts`). For a block value (a list or mapping over several lines) that is the value's first line. A file that changed since the store read it (other SHA-256), cannot be read or does not find the key by name (a key written as an alias) gives its problems without a line. An aborted `signal` stops the reading. Other checks with findings on frontmatter keys (SR-016, SR-086) can use it the same way.

Required properties without a value (SR-015 AK3, `src/model/required.ts`; it is also the hint SR-064 AK2 asks for, which that SR's own tests still have to cover for `element.create`): for each element of a known type, every key of its effective `required` (inheritance resolved, SR-012) whose value is absent, `null`, an empty or blank string or an empty list is the problem `element.missing-required` with severity `warning` (a hint: the file is kept, nothing is blocked), `repository`, `file`, `elementId` and the line of the key when the file has it. An element of an unknown type gets none (it has `element.unknown-type`). `requiredFindings(element, metamodel)` is used by `elementView`; `allRequiredFindings(store, metamodel)` is one pass in memory; `requiredProblemsState` (depends on the element store and the metamodel) holds them with lines for `workspace.check`. Its lines read every file with a finding again: a new required property that no element has yet makes that a full read of the workspace (about 24 s at 50,000 elements, as for value kinds). "Empty" here counts a blank string as no value, unlike the version's normal form (ADR-0005), which keeps it as a value: the hint is about whether a person filled the property in.

Metamodel changes (SR-015, D-043): every check, short ID, view and version reads the metamodel from `metamodelState`, by key only. The watcher resets that state when a file in the metamodel folder changes, so the states built on it are computed anew on their next read; the element store is kept and no element file is written. A renamed type, property or status changes no file and no version. A changed `content` flag changes the version of the elements that have a value for it (ADR-0005; spec question #181, assumed option 1: the version follows the current metamodel).

Writing elements (SR-001, SR-002, `src/model/write.ts`, used by `element.create` and `element.update`):

- File names come only from `fileNameFor({ prefix, id })` (`src/model/file-name.ts`): the type prefix, a dash, the last 12 hex digits of the UUID (`FILE_NAME_DIGITS`) and `.md` (D-056, ADR-0004), e.g. `SR-825b7146fb54.md`. Given once on create; nothing renames a file afterwards (title, type or a longer displayed short ID, SR-001 AK2, SR-084 AK3).
- `createElement(workspace, input, extraFindings?)`: type from `typeForNewElement`; a new UUID from `crypto.randomUUID()` (v4, D-017); the status is the one status with `initial: true` (none or several: `input.invalid`, `details.reason: "initial-status"`; ADR-0002 rule 6; through `element.create` such a metamodel is already invalid, so the command refuses with `workspace.read-only` first); the title goes under the key of the property with the meaning `title` (`metamodel.meaning-unassigned` when none, `input.invalid` with `reason: "no-title-property"` when the type lacks it). `properties` may only hold properties of the type (`reason: "not-a-property"`), never a relation kind (`"relation"`: add relations with `relation.add`), `id`, `type`, `status` (`"structural"`) or the title key (`"title"`). Every key is checked first, then `null` and `[]` are left out (so `status: null` is refused). The folder is created only after every check passed and the bytes are verified. Repository: `input.repository` or the main one (`reason: "unknown"` / `"not-available"`). Folder: `input.folder` or the type key, relative to the repository, created when missing (`createFolder` of the files block); `.` is the repository folder. Before anything is written (also into the default type folder), a file the element walk would not list is refused with `input.invalid`, `reason: "not-listed"`, and `details.rule` and `details.path` say why and where (`newFileTarget` in `src/model/discover.ts`, #183): `skipped-name` (`.git` or `node_modules` in any case and with trailing dots or spaces, as Windows and macOS read them), `ignored` (an `ignore` glob), `nested-repository` (give `repository` instead), `git-entry`, `link`, `unreadable`, `not-a-folder` (a file in the way), `spelling` (an existing folder spelled in another case; `details.existing` is the spelling on disk). A spelling that differs from the existing folder only in its Unicode normal form (NFC input, an NFD folder on macOS) is not refused: the path is judged again as spelled on disk, and the file is written there under that spelling (#194). A name Windows changes or refuses (trailing dot or space, `<>:"|?*`, control characters, device names such as `CON` or `nul.txt`, short names such as `GIT~1`) is refused with `reason: "not-portable"`, and so is a folder still to create whose name holds an invisible format character (`\p{Cf}`: zero-width and direction marks, byte order mark, soft hyphen; `rule: "invisible"`, #194). After `createFolder` the check runs again on the folders as they are now, before the file is written, and the file goes under the spelling it finds (a file system such as HFS+ may store a new name in NFD). So LogReq never writes below `.git` (D-036). The bytes come from `editElementFile` on an empty file: `id`, `type`, `status`, the title, then the properties in the order of the type; LF, a final line break after a text. Written with `writeFileAtomic(..., null)`, which never replaces a file.
- `updateElement(workspace, input, extraFindings?)`: `ref` is a UUID or short ID (`resolveRef` in `src/model/resolve.ts`: `ref.unknown`; `ref.ambiguous` with `details.candidates` for a short tail or two files with one UUID). An element of a type the metamodel does not know is `element.read-only` (SR-016 AK3). `set`/`unset` follow the key rules of `properties` (and a key in both is `reason: "set-and-unset"`); the schema already refuses `id`, `type` and `status`. The file is read again; when it is gone, faulty or its SHA-256 is not the store's, the store is reset and the call fails with `file.changed-on-disk` (the next call works on the new content). `editElementFile` rewrites only the lines of changed keys and the text; unknown keys, comments, quoting, key order, CRLF and byte order mark stay byte for byte (SR-102, SR-016 AK2). New keys are appended in the order of the type. No change, no write (`files: []`). `affected` (SR-024 AK2, AK3): when the write changed the version (the version of the file as read, `undefined` when an embedded image could not be read (`file.faulty`) or a value had no normal form (`versionOrRangeError`, shared with the current versions), against the version of the written view), the number of distinct other elements whose files hold a relation or an inline reference to it (`directlyAffectedCount`, `src/model/affected.ts`, on the incoming index of the store before the write, built before `recordWrites`, so the carry of #273 takes it over); 0 for a title, a property that does not count, or no change. At 50,000 elements and 200,000 relations a content save with the count takes about 0.11 to 0.14 s once the index of the store was built, also a second save right after a save, which gets the index carried over (#273).
- Both return the element as `elementView` builds it (`src/model/view.ts`, `data-export.schema.json#/$defs/element`): text, version (`elementVersion`, which counts the images the text embeds, read with `embeddedImages` in `src/model/images.ts` by the normative rules of ADR-0005 "Files", #178; a reading error other than "not there" is `file.faulty`), properties (every key but `id`, `type`, `status`, the title and relation kinds; unknown keys included), the element's own relations (kind, meaning, `direction: "out"`, target UUID, `targetState` from `targetState(layout, store, record.repository, target)` (D-058, see relation targets below), `accessible` only when it is `available`, then also short ID and title, also across repositories (SR-005 AK2); a target in a repository that is not on this machine shows only the short ID `UNKNOWN-<tail>` (`ShortIds.tail`; its type is not known, prefix per the decisions on #154 and #193) and no title (SR-006 AK1); stored version; then the targets of properties of kind `relation` such as `validity` and `packages`, in the order of the properties, with the property key as kind, `property: true` and no meaning, the same target state, short ID and title (#187), while `properties` keeps them as stored; items are read as the checks read them, `relationKey` + `relationItems` + `hasId`: a list for a relation kind or a property with `many`, one target otherwise) and the value-kind hints with their lines (SR-085), the hints on relations between types the metamodel does not allow (`relationTypeFindings`, SR-086), then the hints on its relations to superseded elements (`supersededFindingsOf`, SR-072 AK2); while the metamodel is not valid it gives none of these hints (#208, decision of spec question #220 option 1), like the whole-workspace states. A superseded element (status marked `invalid`) also lists the relations from its successors after its own (`successors.ts`, SR-072 AK3), also while the metamodel is not valid, since they are relations, not hints: kind, `meaning: "replacement"`, `direction: "in"`, the successor's UUID, `targetState` of the successor (`available` with short ID and title, also across repositories; `ambiguous` without them, SR-088) and the version it stores when that is one; the superseded file itself has no relation to them (D-045). Other relations pointing at the element and `affected` come with stage 2; `element.get` adds the version date (`versionDates`, below). `files` are relative to the workspace root (`../sensor/...` for another repository). After a write the element store gets the file as written in place (`recordWrites`, #166; a reset when that could differ from a full read), and the states built on it (short IDs, value-kind and duplicate-ID problems) follow; the short ID of a new element is computed from the store before the write plus the new record, without reading every file again.

Reading one element (`src/model/get.ts`, used by `element.get` and `element.resolve`; `element.resolve` adds `current`, whether a given version equals the `version` of the element shown, SR-060 AK2, refuses a version of another normal form than `NORMAL_FORM` with `input.invalid`, names the candidate of a short ID with an outdated prefix, see `withTail`, and takes the same input `versionDate` as `element.get`):

- `getElement(workspace, ref, extra, withDate)`: `resolveRef` (`ref.unknown`, `ref.ambiguous`), then the file is read again (the store keeps no text) and shown with `elementView`, with the successions of `successionsFor` for the element (SR-072 AK3) and, through `successionsOf`, for the targets of its relations to superseded elements (the successors their hints name, looked up in the succession index instead of a walk over the store, N-036). A file changed since the store read it is shown as it is now. A file that is gone or no longer holds the element makes the store be read again: `file.faulty` with its errors when the new store reports the file as faulty (SR-008), `ref.unknown` otherwise. `readOnly` is always given: true for a type the metamodel does not know (SR-016 AK3), while the metamodel is not valid (SR-011 AK3), and when this process cannot write the root folder of the element's repository (`isWritableFolder`, as `workspace.status` checks it; unknown on Windows; SR-018 AK2). While the metamodel is not valid there are no hints (#220 option 1). A valid metamodel may assign the meaning `title` to no property (SR-013 AK3): then the title is empty, the key stays under `properties`, and a hint `metamodel.meaning-unassigned` (warning, the text of `requireMeaning`, `meaningUnassignedMessage`) names the missing assignment. `extra(context, record)` adds hints of blocks that import the model (`element.get` passes `supersededValidityFindingsOf` of `src/variants/superseded-validity.ts`, SR-040 AK3); `elementView` asks them (`extraFindings`) only while the metamodel is valid and lists them after its own; `element.create` and `element.update` pass the same function to `createElement`/`updateElement`, so they return the element as `element.get` shows it (apart from `readOnly` and `versionDate`). `showElement(context, ref, extra, withDate)` is the same on given states. `element.get` refuses `view` (SR-043, stage 5) with `input.invalid`. `versionDate` is the date of the version shown, only with the input `versionDate: true` (`versionDates`, D-013, ADR-0005 "Where the date is shown"; `null` for content no commit has and when Git cannot tell); without it no git runs and the field is left out (SR-082 AK3). Left out: other incoming relations and `verification`/`validation`; the variants that replace or exclude the element (SR-046, stage 5) have no field in the schema yet.

Setting a status (SR-017, D-030, `src/model/status.ts`, used by `element.setStatus`):

- The status values the tool offers are the keys of the metamodel's `statuses`, in metamodel order (`statusValues(metamodel)`; `metamodel.get` lists the statuses with names). There is no fallback to the standard model's values.
- `setElementStatus(workspace, { refs, status })`: `status` must be one of them, else `input.invalid` with `details: { status, reason: "unknown-status", allowed }`. Any metamodel status may be set, also one marked `invalid` (superseding with a successor is `element.supersede`, SR-072). The value always comes from the caller; the tool never picks one (ADR-0002 rule 6). Every check comes before the first write: the status, each `ref` (`resolveRef`), `assertElementWritable` (SR-016 AK3), and that no file changed since the store read it (`file.changed-on-disk`, store reset). Only the `status` line is rewritten (`editElementFile`; a missing key is appended); UUID, type, file name, comments and everything else stay. A ref given twice is written once; an element that has the status already is not written. The files are written with `writeElementFiles`. Returns `files` (relative to the workspace root) and `problems`: with a status marked `invalid`, the hints on relations to these elements (`supersededTargetProblems`, the same as `element.supersede` gives, SR-072 AK2); otherwise none.
- `readUnchanged(workspace, layout, record)` (`src/model/write.ts`, also used by `element.update`): the file of a stored element read again for a write; `file.changed-on-disk` (store reset) when it is gone, faulty or its SHA-256 is not the store's.
- `writeElementFiles(workspace, layout, writes)` (`src/model/write.ts`, for every command that changes several elements: `element.setStatus`, `element.supersede`, later `element.bulkUpdate`): writes each file atomically against the snapshot it was read with and returns, per file, the element as written (`writtenElement`, which verifies the bytes), the snapshot it replaced and its path. All-or-nothing is best effort: a write can still be refused after every check (`file.read-only`, a file changed in the meantime, a disk error). Then the files already written are written back with their bytes as read, only while they still hold what the call wrote (nothing is deleted), and the error is thrown again with its code; `details.written` lists the files not restored (relative to the workspace root); it is absent when every file was restored. After the writes the element store gets all written files in place with one `recordWrites` call (#166); after a failure it is reset.

Superseding (SR-072, D-045, `src/model/supersede.ts`, used by `element.supersede`; there is no delete):

- `supersedeElement(workspace, { ref, status, successor?, relation? })`: `status` must be a status the metamodel marks `invalid` (D-044), else `input.invalid` with `details: { status, reason: "unknown-status" | "not-invalid", allowed }` (the invalid statuses). The tool never picks it (D-030). Only the `status` line of the element's file changes.
- With `successor`, a relation with the meaning `replacement` (D-059) goes from the successor to the element and is written into the successor's file (ADR-0004: source = new, target = old). The kind is `relation` or the one replacement kind whose `source-types` and `target-types` allow the two types (`allowsType`, subtypes count): none is `relation.not-allowed`, several is `input.invalid` with `reason: "relation-ambiguous"` and `candidates` unless the successor already has a relation to the element under exactly one of them, which is then used (so a repeat needs no `relation`, #196) (the standard model has `supersedes` and `replaces` for two system requirements), a named kind without the meaning is `reason: "not-a-replacement"`, a named kind that does not fit is `relation.not-allowed`; no replacement kind at all is `metamodel.meaning-unassigned` (SR-013 AK3). `relation` without `successor` is `reason: "relation-without-successor"`; the element as its own successor is `reason: "self"`. The target is `currentTarget` (UUID and current version; title in the same repository, repository name across repositories, D-058), appended with `append-item`. A target the successor already has under that key (same UUID and repository) is kept with its stored version and not added again (#177 (a)).
- Every check comes before the first write (status, refs, `assertElementWritable` for both, SR-016 AK3, the kind, `readUnchanged` for both files); both files are written with `writeElementFiles`. A file that would not change is not written, so a repeated call writes nothing. Returns `files` and `problems`: the hints on relations to the element.

Adding and removing relations (#264, `src/model/relation-write.ts`, used by `relation.add` and `relation.remove`; ADR-0004: a relation lives only in its source's file):

- `addRelation(workspace, { source, kind, target })`: `source` and `target` are UUIDs or short IDs (`resolveRef`); the source must be writable (`assertElementWritable`, SR-016 AK3). `kind` must be the key of a relation kind (`keyDefinition`: a property key is `input.invalid` with `reason: "property"`, any other key `reason: "unknown-relation"` with `allowed`, the relation kinds whose `source-types` allow the source's type). A relation the source already has under the kind (same UUID and repository) is kept with its stored version and nothing is written (#177 (a)). Otherwise the target is `currentTarget` (UUID and current version, SR-021 AK1; title within the repository, repository name and no title across repositories, SR-005 AK1, D-058), checked with the rule of SR-086 (`relationTypeFindings` on the source with only the new relation): a relation the metamodel does not allow is refused with `relation.not-allowed` and the message of the hint (assumption of #264: the tool sets only allowed relations, SR-067 AK1; a target of an unknown type is allowed, as in the check). A value under the key that is not a list is `reason: "not-a-list"`. The target is appended with `append-item` (one flow mapping per line, SR-102) and written with `writeElementFiles` (`file.changed-on-disk`, `recordWrites`). Returns the written files, the kind, the position of the relation and the source as written.
- `relation.add` then looks for a cycle when the kind has the meaning `derivation` (SR-067 AK3): on the store after the write, `closedCycle(graph, child, key, index)` (`src/trace/new-cycle.ts`) walks up from the target (`walkDerivation`, `direction: "up"`) on `upwardGraph`, the derivation graph without the incoming index of the whole store (a walk up reads only each element's own relations, so only the elements above the target are read); when it reaches the source, the relation closes a cycle (an element that derives from itself is one too), and `cycleFindings` with `locateFindings` give one `trace.cycle` warning per element of that cycle (the source first, then the target and up), the same messages as `workspace.check` (SR-090). The hint names the shortest way back through the new relation (breadth first), not every element of the strongly connected component it joins; `workspace.check` reports those. The relation is written anyway: AK3 asks for a hint. A repeat call where nothing is written gives the same hint.
- `removeRelation(workspace, { source, kind, target, repository? })`: source and kind as above (no type check: a relation the metamodel does not allow can be removed). A target given as UUID is matched against the stored items as written, so a relation to a target that is gone (SR-089) can be removed; a short ID names an element and only items into its repository. Every item naming the target is removed (`remove-item`, comments of the others stay), the key with its last item. `repository` keeps only the items into that repository (an item without `repository` points into the source's own, D-058); with a short ID it must be the element's repository (`input.invalid`, `reason: "repository-mismatch"`). Items with that UUID into several repositories are `ref.ambiguous` (give the short ID or `repository`) when one of these repositories may hold an element with the UUID: it has one, is not on this machine, or is not in the workspace file. When each is here and has none, no short ID could tell them apart, so they are all removed. Nothing to remove: no file is written, and `problems` holds one `info` `relation.not-found` naming the source, kind and target. No element and no file is deleted (D-045).

Hints on relations to superseded elements (SR-072 AK2, `src/model/superseded.ts`):

- An element is superseded when its status is marked `invalid` (`invalidStatuses(metamodel)`), whichever command or person set it. Every item of a relation kind's list whose target resolves to one such element (`resolveTarget`) is one hint `relation.target-superseded`, severity `warning`, with `repository`, `file`, `line` of the item, `elementId` (source) and `targetId`. The message names the relation kind, both elements, the target's status and its successors (sources of `replacement` relations to it). Also the successor's own replacement relation gets one (assumption, spec question #192). Relation-valued properties and inline references are not counted (validity has `variant.superseded-in-validity`, SR-040 AK3, `src/variants/`). Missing, ambiguous and malformed targets are other checks.
- `elementLabel(context, record)`: how messages name an element, type name (its key when unknown) and short ID; shared with the variants block.
- `supersededTargetFindings(context, targets?)`: one pass over the store, in store order, then key order in the file, then items; with `targets`, an item is first tested by its UUID, before the schema check and the lookup (about 80 ms for one element at 50,000 elements and 200,000 relations). With `incoming`, the incoming relation index of the same store and metamodel (ADR-0008, #272), only the sources of relations to the UUIDs of `targets` under relation kinds are looked at, in store order, with the same rules (about 7 ms); an index of another store or metamodel, or one that cannot hold every relation kind's key as a list of relations, is ignored. `supersededTargetProblems(workspace, targets)` with lines, for command outputs, passes the index of the store when the workspace holds it (`workspace.peek(incomingState)`; it never builds one); `supersededTargetProblemsState` (depends on the element store, the metamodel and the short IDs) for `workspace.check` (SR-019).
- Successors (SR-072 AK3, `src/model/successors.ts`): `buildSuccessionIndex(store, metamodel)` collects, in one pass over the store, every item with a UUID under a relation kind with the meaning `replacement`, by the repository it names (the source's own when it names none) and its UUID. It reads items as the element view reads its own relations (`relationItems`, `hasId`, `isUuid`), so a target without a version or with another key still names its successor; the AK2 hints above read only complete relation targets (`isRelationTarget`), so such an item names a successor in the view but gets no `relation.target-superseded` hint. `successionIndexState` is a `WeakMap` from an element store to its index (which records the metamodel it was built with); it depends on no state and is not carried over a change of the store (ADR-0008): the first view of a superseded element after a save or watcher batch builds the index of the new store. `successionsOf(index, metamodel, record)` is a lookup: none unless the record's status is marked `invalid` and its repository has exactly one element with its UUID; its own file is left out. `successionsFor(workspace, store, metamodel, record)` is synchronous and loads no state, so it cannot fail after a command wrote its file: it builds no index for an element with a valid status, and otherwise reads the incoming relation index of `store` when the workspace holds it with the same metamodel (#272: the `replacement` links into the record's repository and UUID with a UUID as `id`, in the order of the succession index: store order, then relation kind, then item; not when a replacement kind's key is not a list of relations), else takes the succession index of `store`, building it when there is none or it was built with another metamodel. `elementView` takes it as `successionsOf` (a function of the element) and asks it for the element itself and for the superseded targets of its relations; every caller must give `successionsFor` on the store of the view. Cost at 50,000 elements and 200,000 relations: about 23 ms to build the index once per store, then about 0.2 ms per view of a superseded element (`test/perf/large-workspace.test.ts`), instead of a walk over the store (about 50 ms) per superseded view.
- The message says `successor:` for one successor and `successors:` for several.
- Incoming relations (ADR-0008, #258, `src/model/incoming.ts`): `buildIncomingIndex(store, metamodel)` collects, in one pass over the store and each element's own frontmatter keys, every item with a text `id` (`hasId`) under a key that holds relations (`relationKey`: relation kinds and properties of kind `relation`, validity and packages included; a value of the wrong shape has no items) and every inline reference, by the UUID it names. `relationsById` holds `IncomingRelation`s (`source`, `key`, `index` in the list under the key or undefined for a single target, `relationPath(link)` for `[key, index]`, `item` as parsed, `repository` it points into: the item's, else the source's own; an item whose `repository` is not text is left out), `referencesById` the `IncomingReference`s; each list in store order of the sources, the relations per source in the order of its frontmatter keys and by item, the references in text order (the order of the UUIDs in the maps is not defined: a carried index adds new ones last). `incomingTo(index, repository, id)` gives the links into one repository and UUID: the relations, then the references (one without `repository` points where `resolveReference` resolves it, #250: the source's own when the UUID is there or nowhere, else the one other repository with it, and each of them when several have it, `ambiguous`). Raw: relations of an element to itself and links to a UUID that several files of a repository share (SR-088) are kept; the reader decides. `incomingFor(workspace, store, metamodel)` is synchronous and keeps one index per store (`incomingState`, a `WeakMap`; built again for another metamodel object). 0.3 to 0.5 s at 50,000 elements and 200,000 relations (`test/perf/open-filter-chain.test.ts`). Carried over a change of the store (#184, #267): when `applyStoreChange` replaces a store that has an index, the `carry` hook of `incomingState` adds the index of the new store to the memo, `carryIncomingIndex(index, update)`: the links whose source lies in a changed file are dropped, the links of the records in those files now are merged in by store order, every other list and link object is kept, the old index is not changed; a store without an index gets none, and so does one after a change of more than `CARRY_LIMIT` (1,000) UUIDs, whose carry would cost about as much as the build (the next chain builds it, #273); any other change of the store drops the memo. At 50,000 elements and 200,000 relations a fixed 30 to 50 ms (two map copies) plus about 0.1 ms per changed record (0.13 to 0.25 s for 1,000), so a chain right after a save takes 0.11 to 0.17 s (0.30 to 0.41 s for the first chain of a process) instead of paying the build too.
- `supersededFindingsOf(context, source, successionsOfTarget)`: the hints on the relations of one element, for `elementView` (`element.create`, `element.update`, `element.get`), like `unknownFindings`; the successors of each target come from the succession index of the store (`successionsOfTarget`, which `elementView` takes as `successionsOf` and the commands give as `successionsFor`; only items in a list that are complete relation targets count, as in the whole-workspace hints), each successor once in store order and never the target itself (an element that replaces itself is no successor of itself, also in the whole-workspace hints), and never the hint's own source. No walk over the store, so opening an element stays within 200 ms at 50,000 elements (ADR-0008, SR-082 AK3).

Duplicate IDs (SR-088, `src/model/duplicates.ts`): element files that share a UUID (a copied file) are all reported, and none of them is changed; the tool does not decide which one is the copy.

- `duplicateIdFindings(store)`: one finding per such file, in store order, at the `id` key: `element.duplicate-id` with severity `error`, `repository`, `file`, `elementId` (the shared UUID) and the other files in the message. The severity is `error` because a shared UUID breaks the identity of an element (D-017); it is not a hint ("Hinweis"). One pass over the store, no file read.
- `duplicateIdProblemsState` (async Workspace state, depends on the element store): the same findings with the line of `id` (`locateFindings`), for `workspace.check` (SR-019; exit code 1, SR-088 AK3).
- `resolveId(byId, id)`: the elements a UUID names, `{ kind: "found", element }`, `{ kind: "unknown" }` or `{ kind: "ambiguous", elements }` (every record, in store order). A relation display marks a relation whose target is `ambiguous` as ambiguous (SR-088 AK2).

Relation targets (`src/model/relations.ts`): `isRelationTarget(value)` tells whether a value has the format of a relation target (`common.schema.json#/$defs/relationTarget`; SR-085 and SR-086 use it). `resolveTarget(store, sourceRepository, target)` is the one lookup of the element a relation points at, for every check that follows a relation (SR-086, SR-089, SR-006): the records of `store.byId` for `target.id` that lie in `target.repository ?? sourceRepository` (D-058), as an `ElementMatch`: `found` (one record), `unknown` (none there: the target is missing, or its repository is) or `ambiguous` (several files there share the UUID, SR-088). A record of the UUID in another repository does not count. `resolveId` (SR-088) stays the check whether a UUID names one element in the whole workspace. `targetState(layout, store, sourceRepository, target)` adds the workspace layout; the element view and the missing-target check (SR-089) use it, and the relation-type check (SR-086, which uses `resolveTarget` today) is to share it (SR-080): `available` (with the record), `inaccessible` (the repository is in the workspace file but not on this machine, N-041, SR-006), `missing` (the repository is here, the UUID is not in it, N-065, SR-089), `ambiguous` (SR-088) or `unknown-repository` (no repository of that name in the workspace file, or a `repository` that is not text); `isUnavailableRepository(layout, name)` is its test for a listed repository that is not here. `followTargets(layout, store, sourceRepository, targets)` is the step chain, coverage and degree of evidence take per element: the elements of the available targets, and `incomplete: true` when a target is `inaccessible` or `unknown-repository` (SR-006 AK2, spec question #193; a missing or ambiguous target does not make a result incomplete, it is a finding of its own). Setting a new target in a repository that is not on this machine is `ref.unknown` with `reason: "repository-not-available"` (its version cannot be read; spec question #193); a target already stored there is kept.

Missing targets (SR-089, `src/model/missing-targets.ts`): a relation whose target is `missing` (`targetState`: its repository is on this machine and has no element with the UUID, for example because the target file was removed) is the problem `relation.missing-target` with severity `error`, `repository`, `file`, `line` (of the item), `elementId` (the source), `targetId` (the target's UUID) and an English message, e.g. `Relation Derives from (derives-from) of System Requirement SR-f7a8b9 points to 3b8e1f2a-6c4d-4e7f-9a1b-2c3d4e5f6a7b, which is not in repository system`. LogReq changes no file.

- Severity `error`: SR-089 asks for a finding ("Befund"), not a hint, and SR-019 AK2 ends the check with exit code 1 for it (ADR-0009).
- Not reported: a target in a repository that is in the workspace file but not on this machine (`inaccessible`, SR-089 AK2, shown as not accessible by SR-006), one in a repository the workspace file does not list (`unknown-repository`, treated like `inaccessible`, spec question #193), an ambiguous one (SR-088), and values that are no relation target (SR-085).
- Checked: the items of relation kinds and the values of relation-valued properties (`relationItems` in `src/model/relation-keys.ts`, shared with SR-086; `keyDefinition`, so a property wins over a relation kind), whatever the source's type, also an unknown one (the message then names the type key). An item is a target when it is a mapping with a UUID as `id` (`isUuid`, as in the element view); a missing or wrong `version` and other keys do not matter (ADR-0004 keeps such entries). Other values, also one mapping where a list belongs or the reverse, are left to the value-kind check (SR-085).
- Also checked (decision on spec question #177 (c), #240): the inline references in the text, which the element store keeps per record (`ElementRecord.references`, from `textReferences` in `src/model/references.ts`, with the line of each link in the file), so no text is read. Their target comes from `referenceTargetState`: with `repository=<name>` in the link as for a relation; without, in the source's own repository (D-058), and, when it is not there, in the one other repository that has the UUID (links written before references named their repository). Such a link is `missing` when no repository here has the UUID, also while some repository is not on this machine. Message e.g. `Reference in the text of System Requirement SR-f7a8b9 points to 3b8e1f2a-…, which is not in repository system`; `line` is the line of the link.
- A target whose file cannot be read (faulty YAML, conflict markers, SR-008) is not in the store, so it is missing too. When a file with a problem in the target's repository carries the last 12 hex digits of the target's UUID in its name (D-056), the message adds `; its file may be <file>, which LogReq cannot read`.
- Cost (N-036): a cheap test (a mapping with a text `id`) and `targetState` (map lookups) per item; `isUuid` runs only for the missing ones. 50,000 elements with 200,000 relations and 100,000 references take well under the 5 s budget of the unit test.
- `missingTargetFindings(element, { layout, store, metamodel, shortIds })` and `missingReferenceFindings(element, context)` for one element, `allMissingTargetFindings(context)` and `allMissingReferenceFindings(context)` for all in one pass without reading a file, and `missingTargetProblemsState` (async Workspace state, depends on the element store, the metamodel and the short IDs) with lines, in store order, per element its relations (key order, then item order), then its references (text order), for `workspace.check` (SR-019).

Relation types (SR-086, `src/model/relation-types.ts`): a relation kind may name the types it goes from (`source-types`) and to (`target-types`), a property of kind `relation` the types it goes to (`target-types`). A relation between other types is the problem `relation.not-allowed` with severity `warning` (a hint), `repository`, `file`, `line` (of the list item), `elementId` (the source), `targetId` (the target's UUID as written) and an English message with the relation kind's name and key, source and target and what is allowed, e.g. `Relation Derives from (derives-from) from Need N-34824e to System Requirement SR-b185f3 is not allowed; allowed: from System Requirement to Need`.

- Allowed types: `allowsType(list, typeKey, metamodel)` in the metamodel block (`src/metamodel/lookup.ts`, also for SR-067): an absent list allows every type, an empty one none, and a type in the list also allows every type that extends it (SR-012; spec question #163). A key in the list that names no type is shown as written. Which definition a key has comes from `keyDefinition(metamodel, key)`: a property wins over a relation kind of the same key, as in the value-kind check.
- Source: an element of a type the metamodel does not know is not checked (SR-016). A source type that is not allowed is reported whatever the target (spec question #163); a target that does not resolve is then named by the tail of its UUID (`shortIds.tail`), one of an unknown type by its type key and short ID.
- Target: its type is checked only when `resolveTarget` finds one element of a known type. A missing target or one in a missing repository (SR-089, SR-006), an ambiguous one (SR-088), one of an unknown type (SR-016), and values that are no relation target or have the wrong shape (SR-085) are other checks.
- `relationTypeFindings(element, { store, metamodel, shortIds })`: the findings of one element (a `LocatableFinding` plus the `target` as written), for `element.get` (with `locateFindings`) and for a command that has just written it. `allRelationTypeFindings(context)` is the one pass over all elements in memory without reading a file (N-036). `relationTypeProblemsState` (async Workspace state, depends on the element store, the metamodel and the short IDs) holds all of them with lines, in store order, then key order, then item order, for `workspace.check` (SR-019). Carried over a change of the store (ADR-0008, #184): when a changed UUID came, went or changed its repository or type, `relationTypeAgain(update, metamodel, incoming)` names the unchanged elements to look at again: with the incoming relation index of `update.from` (read from the workspace's memo once the change is carried; never built for it, #272) a list, the records with a UUID in a short-ID group of a changed UUID and the sources of relations under a key with a rule to a UUID of such a group, else a test that `carryProblems` puts every element to.

## Checking the whole workspace (`workspace.check`, SR-019)

`src/commands/workspace/check.ts` collects, in this order: the problems of the workspace layout and of the metamodel, those of the element store (SR-008, unreadable and skipped files), then the whole-workspace states of `FINDING_STATES`: `requiredProblemsState` (SR-015), `unknownProblemsState` (SR-016), `supersededTargetProblemsState` (SR-072), `supersededValidityProblemsState` (SR-040, variants block), `valueKindProblemsState` (SR-085), `relationTypeProblemsState` (SR-086), `duplicateIdProblemsState` (SR-088), `missingTargetProblemsState` (SR-089) and `derivationCycleProblemsState` (SR-090, trace block). A new whole-workspace finding joins by adding its state to `FINDING_STATES` (exported for tests that need every finding state). `ok` is false when any finding of severity `warning` or `error` exists, whatever `severity` shows (ADR-0009: CLI exit code 1); `severity` only filters the problems shown. Problems are appended in a loop, never spread into `push`, so hundreds of thousands of findings do not overflow the stack (N-036). `changedFiles` and `changedSince` are refused with `input.invalid` until SR-092. Outdated relations (SR-025) come with stage 2.

## Variants block (`src/variants/`)

Validity and views of the core and the variants (SR-040, D-020). Stage 1 has the validity; the view commands follow in stage 5 (#127 option 1).

- `validityOf(metamodel)`: the property with the meaning `validity` as a relation key (`relationKey`: key, label, `many`), undefined when none has it or it holds no relations. Then nothing has a validity and everything applies everywhere; the stage-5 view commands must call `requireMeaning` first and report `metamodel.meaning-unassigned` instead (SR-013 AK3).
- `validityEntries(validity, element)`: the entries with their paths. Absent, `null` and `[]` give none. Under a key with `many` only a list has entries (`[key, i]`); one value there gives none, and the value-kind check reports it (SR-085). Without `many` the one value is the entry (`[key]`). It is `relationItems` of `src/model/relation-keys.ts`, the same reading as the missing-target check (SR-089).
- `validityTarget(entry, source)`: the one cheap predicate that view and hint share. An entry for which `hasId` holds (a mapping, not a list, with a text `id`; `src/model/relation-keys.ts`) names that UUID in the repository it names, or in the source's own when it names none (D-058); a `repository` that is not text, a free name or any other value names nothing (D-020). Other keys are SR-085's.
- `appliesIn(validity, element, view)`, with `View = { kind: "core" } | { kind: "variant", variant }`: without entries the element applies in the core and every variant (SR-040 AK1); with entries only in the variants they name, never in the core (SR-040 AK2, SR-043 AK3). Pure: no store lookup, no schema validation. Replacement and exclusion (SR-041, SR-042) are not part of it.
- `variantTypes(metamodel)`, `variantsOf(store, metamodel)`: the types with the meaning `variant` (own or inherited) and their elements, in store order.
- `supersededValidityFindingsOf(context, record)`: the same hints for one element, for `element.get` (one filter over the store for the superseded variants, then only the entries of `record`).
- `supersededValidityFindings(context)`, `supersededValidityProblemsState` (depends on the element store, the metamodel and the short IDs), for `workspace.check` (SR-019): one hint `variant.superseded-in-validity`, severity `warning`, per entry whose `validityTarget` resolves (`resolveTarget`) to one element of a variant type with an invalid status (D-044), with `repository`, `file`, `line`, `elementId` and `targetId`. So every requirement with an entry that names a superseded variant (`validityTarget`) gets it (SR-040 AK3); a requirement with an empty validity applies in that view too but gets none. Missing and ambiguous targets are other checks. N-036: one pass collects the UUIDs of superseded variants and the check ends without any; only entries naming one are looked up.

## Trace block (`src/trace/`)

The derivation graph and the walk that the chain (SR-022), related elements (SR-023), affected elements (SR-024) and cycles (SR-090) share (#258). No command of its own; it imports the model, metamodel and workspace blocks, never `commands`.

- `traceContext(workspace)` reads layout, metamodel and store once and takes `incomingFor` of that store. `derivationGraph(context, command)` throws `metamodel.meaning-unassigned` naming `command` when no relation kind has the meaning `derivation` (`requireMeaning`, SR-013 AK3), and otherwise holds the kinds with that meaning (`relationKindsWithMeaning`; a property of the same key wins), never fixed keys.
- Direction (ADR-0004): the source of a derivation relation is the child, its target the parent. A `DerivationLink` is the child's relation in the shape of `IncomingRelation` (`source` = child, `key`, `index`, `item`; `relationPath` for its path). Inline references are not part of the chain.
- `parentsOf(graph, element)`: the element's own derivation items with `hasId`, each looked up with `targetState` (D-058). `available` is a step; any other state is `unresolved` with its state; `inaccessible` and `unknown-repository` make the expansion `incomplete` (SR-006 AK2), `missing` (SR-089) and `ambiguous` (SR-088) do not.
- `childrenOf(graph, element)`: the index's relations under a derivation key that point into the element's repository and UUID. While several files of that repository share the UUID (SR-088), each of them is `unresolved` with the state `ambiguous` (repository and the records), as `targetState` calls the same relation going up, so a chain shows the gap (SR-022 AK3). While the workspace file lists a repository that is not on this machine, every expansion down is `incomplete`: children there cannot be seen (assumption, spec question #262 option 1).
- `derivationEdges(graph)`: every derivation relation of the store as an edge from the child to the parent, when the parent is available (the one record of its UUID in the repository the relation points into), read from the index without a `targetState` each; `cyclesOf(store.elements, derivationEdges(graph))` gives the cycles of the whole store (SR-090).
- `walk(starts, expand, { maxDepth, leaves })`, `walkDerivation(graph, starts, { direction: "up" | "down", maxDepth, leaves })`: breadth first; `nodes` has each element once at its shortest depth (starts at 0, in the given order, then level by level) with `via`, the edge it was first reached through; `pathTo(result, element)` gives the edges from the start. `edges` holds every step in walk order, also into elements reached before; `cyclic` marks an edge inside a cycle. A start stays at depth 0 without `via`, also when another start leads to it (the edge is in `edges`). `maxDepth`: elements at that depth are reached but not expanded (`expanded` is false only for them). `unresolved` lists `{ from, link, state }`; `incomplete` is set when any expansion says so. `leaves(element)` is called once per node (evidence of stage 4; default none).
- Cycles: the strongly connected components of the walked subgraph with more than one element or an edge to itself, each with its elements in node order and its edges in edge order. Back edges on the tree path are not enough (a cycle entered through a diamond is missed). The vertices without an edge in are peeled off first (Kahn), then iterative Tarjan runs on the rest; a component that is no cycle allocates nothing. A cycle that closes only beyond `maxDepth` is not reported. `cyclesOf(elements, edges)` gives the cycles of any graph.
- Chain (`chain.ts`, SR-022, command `trace.chain`): `traceChain(graph, root, { direction, maxDepth, includes, leaves })` walks up (`parentsOf`) and/or down (`childrenOf`) from the root; `includes` filters the steps (the view, `appliesIn`; the root always stays), `leaves` gives the evidence below an element of the downward walk (none until stage 4; core tests pass their own, #127 option 1). Gaps (AK3), downward and only for expanded nodes: a type with the meaning `need` without a child is `no-child`, one with the meaning `requirement` without a child and without evidence `no-evidence`; a missing `need` or `requirement` meaning is named in `unassigned`. The cycles of both walks, a cycle through the root once. `chainOutput(chain, { metamodel, shortIds })` gives the catalog output: nodes (root first, then up, then down, each with depth and `expanded`), edges (source = child, target = parent, `cyclic`), gaps, unresolved links (up: a parent that is not available, `UNKNOWN-…` when its repository is not here; down: a child of an ambiguous UUID), `incomplete`, and the hints `trace.cycle` (one per cycle, at its first element) and `metamodel.meaning-unassigned`. `resolveView` (`variants/views.ts`) turns the `view` input into a view (`core` or a variant; needs the meanings `validity` and `variant`). Elements are named by UUID and repository (`sourceRepository`, `targetRepository`, `fromRepository`, gap `repository`); two files of one repository with one UUID (SR-088) differ only by the node's `file`. Outputs can be large. In the generated workspace (50,000 elements, 200,000 relations) the largest chain is that of the first need in generator order (N-cd15ae, the need of `test/perf/open-filter-chain.test.ts`): 42,279 nodes, 111,865 edges, 14,677 gaps, about 36.5 MB of JSON, 650 to 810 ms for the whole command on a warm workspace (4 cores, noisy; the first call after a load also builds the incoming index, about 1.2 s more; after a save or a watcher batch the index is carried over, #273). So the full chain of the largest need is over SR-082 AK4's 500 ms; the product-level measurement and any optimisation belong to #227. A smaller need (N-126d75, 22,193 nodes, 12 MB) takes 270 to 310 ms, and `maxDepth: 1` about 6 ms. The app and MCP clients should ask with `maxDepth: 1` and ask again below a node that is not `expanded`.
- `derivationCycleProblemsState` (depends on the element store, the metamodel and the short IDs; no `carry` hook, so a change of the store builds it again), for `workspace.check` (SR-090, SR-019): one problem `trace.cycle`, severity `warning` (SR-022 AK4 calls a cycle a "Hinweis"; `ok` false, CLI exit code 1), per element of each cycle of `cyclesOf(store.elements, derivationEdges(graph))`, with `repository`, `file`, `elementId`, `targetId` (its first edge among the cycle's own edges: relation kinds in metamodel order, then items in file order, so target and cycle always agree) and the `line` of that item. The message names every element of the cycle by type name and short ID, the first `CYCLE_NAMES_SHOWN` (20) of a longer one. Cycles by their first element in store order, elements in store order. A target that is missing, ambiguous or in a repository not here is no edge, so it closes no cycle. Without a relation kind with the meaning `derivation`, one `metamodel.meaning-unassigned` with severity `info` (SR-013 AK3; spec question #270 option 1); against an invalid metamodel nothing. `derivationCycleFindings(graph, shortIds)` gives the findings without lines; `cycleFindings(graph, shortIds, cycle)` those of one cycle of derivation edges, also one a command puts together (SR-067 AK3: an element without an edge in it is named without a target). Without a cycle the state costs about 0.5 to 0.7 s at 50,000 elements; the lines of a cycle of all 50,000 elements cost about 30 s more (`locateFindings` reads every file again), within SR-020's 60 s.
- Affected elements (`affected.ts`, SR-024, command `trace.affected`): `traceAffected(graph, element, { evidence })` walks breadth first from the element, a walk of its own (no edges, no cycle search): distance 1 along every link of `directLinks` (`src/model/affected.ts`: the relations of any kind or relation-valued property and the inline references of other elements, `incomingTo`), from there only along the derivation chain (incoming relations of a kind in `graph.kindByKey`) and inline references (ADR-0004; assumption of #36: "direkt oder über die Kette"). `reached` holds each reached element once (`AffectedNode`: depth, the link and the node it was reached from), the element asked for first; it is never affected, also not through a cycle. `incomplete` while a repository of the workspace file is not here. `evidence: { version, records }` is the seam for stage 4 (SR-028): the records whose version is not the current one are the records of an old version (AK4, `data-export.schema.json#/$defs/evidenceRecord`); the command passes none, the core tests their own (#127 option 1). `affectedOutput(affected, { metamodel, shortIds }, { limit, offset })` gives one page (`total` counts all) with short ID, type, title, file, `distance`, `path` (`{ id, repository }` from the element to it, built for the page only by walking back) and `via` (`{ kind: "relation", key }` or `{ kind: "reference" }`, how it points at the element before it), the records and `incomplete`. From the first need of the generated workspace (about 48,500 affected elements, 222,000 links of which 96,000 references) the command with the default page took about as long as the chain from the same need in the same run (`test/perf/open-filter-chain.test.ts`, SR-082 AK4's 500 ms; the output of all 48,500 is recorded on its own).

- `relatedElements(graph, selection, { direction: "children" | "parents", maxDepth, includes })` (`src/trace/related.ts`, SR-023, command `trace.related`): one breadth-first walk from every element of the selection along `childrenOf` or `parentsOf`; lists each element reached through a step once (AK2), by distance, then in the order reached. An element of the selection that another one (or a cycle) leads to is listed too, at the distance of its first step in. `maxDepth` 0 lists none. `includes` (a view, `appliesIn`) drops the steps to elements outside it; the selection is walked from as given. Its own walk, not `walk`: a list needs no edges, nodes or cycles; the 42,278 children of the first need at N-036 take about 0.2 s instead of 0.35 s. The command walks completely, counts all in `total` and builds only the page (`limit`, default 200, at most 5,000; `offset`): the first page of those children about 0.2 to 0.33 s (perf test, SR-082 AK4 500 ms).

## Git reader (`src/git/reader.ts`)

The only module that spawns processes (ADR-0006). It exports only typed functions (and the check `isGitPath` for callers); each runs one fixed command line, at most followed by a checked commit ID, with paths and object names on standard input, so no other subcommand or argument can be passed. Every call runs with `--no-pager -c core.fsmonitor=false -c protocol.allow=never`, `GIT_OPTIONAL_LOCKS=0`, `GIT_TERMINAL_PROMPT=0`, `GIT_LITERAL_PATHSPECS=1`, `GIT_NO_LAZY_FETCH=1`, without inherited repository variables (`GIT_DIR`, ...) and with a time limit (10 s for `rev-parse`, 60 s for reads of history and objects); a caller may pass an `AbortSignal` that stops the process. An unknown result is `{ known: false, reason, detail }` with `no-git`, `refused` (`safe.directory`), `timeout` (also stopped by the caller) or `not-a-repository` (also for output the reader cannot parse).

- `headCommit(folder, { signal })`: `rev-parse --show-toplevel --is-shallow-repository --verify HEAD`, `{ known: true, commit, shallow }` for the top level of a repository. `workspace.status` reports `refused` as an `info` problem `git.unavailable`.
- `headFiles(folder)`: no process; reads the files of the Git folder that name HEAD (ADR-0006): `{ stamp, commit?, shallow }`, undefined where only git can tell (then `headCommit`). The stamp changes whenever HEAD may have moved.
- `fileHistory(folder, head, paths, { signal })`: `log --no-show-signature --no-follow --no-renames --root --full-history --cc --name-only -z --parents --format=%H %cI %P%x00 --stdin <head>`, the paths after `--` on standard input (literal; none: no process and no commits). Commits newest first with committer date in UTC (`YYYY-MM-DDTHH:MM:SSZ`), their parents among the listed commits, and the given paths each one changed, as Git spells them; a merge names a path only when it differs from every parent, and a merge that took each path from one side is listed with none; every merge is listed (no history simplification), so the list for one path does not depend on the other paths. Read as it streams.
- `openObjectReader(folder, { signal })`: an `ObjectReader` whose rounds `info(names)` and `read(names, open)` share one `cat-file --batch-command --buffer` process (git 2.36 and newer; older: one `--batch-check` or `--batch` process per round). Names are object IDs or `<commit ID>:<path>`; `null` for every answer of git that names no object: `missing` (also a missing object of a partial clone, which is never fetched), `ambiguous`, `excluded`, and a submodule entry (newer git prints `<ID> submodule`) or anything below it. `read` streams the bytes of each object as Git stores them (no filters; a link is its link text) to the sink `open(info, index)` gives, so no object is held whole. After a failed round every later round gives the same failure. `close()` ends the process.

## Version date (`src/model/version-date.ts`)

`versionDates({ workspace, layout, metamodel }, requests)` gives, for each (repository, file, element UUID, version), the committer date in UTC of the newest commit that started that version (the file held the element with it there, and no parent had it), or `null` (ADR-0005 "Version date": which commits count, starts, how embedded images count at an old commit, when there is no date). One walk per (repository folder, file, UUID) and HEAD lists the commits that changed the file or an image its texts embed, and the merges whose sides do not all lead to the same evaluated commit (`log` is asked for the folders of these paths, the paths are picked from its answer) (`fileHistory` again when a text embeds an image not walked yet; a request with the current `text` walks its images from the start, as `element.get` does). Versions are computed lazily, newest commit first in growing rounds, until the asked version's newest start is certain; each round is one `info` and one `read` for the texts and the same for the image blobs, on one `openObjectReader` per call. The walks are a workspace state (`version-dates`, reset with the metamodel and the layout; reset or close stops their git processes); they stay while `headFiles` gives the same stamp or HEAD the same commit, and a new HEAD replaces the walks of its repository. A walk git could not finish because it timed out, was stopped or is missing is dropped; one Git refused for another reason stays `null` until HEAD moves. A call waits for its walks (no time limit besides those of the git calls), so the same request gives the same answer at the same HEAD (D-029). `prepareVersionDates(context, walks)` starts the walks without waiting, so `element.get` with `versionDate` lets git read the history while it builds the view. A repository folder without a `.git` entry starts no process.

## Schemas at runtime

`loadContracts()` uses `src/generated/contracts.json`: all `schemas/*.schema.json`, the catalog meta schema and the catalog in one JSON module, written by `pnpm contracts:generate` and checked by `pnpm contracts:check`. So the package needs no `schemas/` folder at run time (ADR-0014) and works from `src/` without a build. After changing a schema or the catalog, run `pnpm contracts:generate`. Validation uses the Ajv options of `scripts/contracts/load.mjs` plus ajv-formats.

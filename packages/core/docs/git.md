# Git reader (`src/git/reader.ts`)

Part of the [`@reqseq/core` README](../README.md).

The only module that spawns processes (ADR-0006). It exports only typed functions (and the check `isGitPath` for callers); each runs one fixed command line, at most followed by a checked commit ID, with paths and object names on standard input, so no other subcommand or argument can be passed. Every call runs with `--no-pager -c core.fsmonitor=false -c protocol.allow=never`, `GIT_OPTIONAL_LOCKS=0`, `GIT_TERMINAL_PROMPT=0`, `GIT_LITERAL_PATHSPECS=1`, `GIT_NO_LAZY_FETCH=1`, without inherited repository variables (`GIT_DIR`, ...) and with a time limit (10 s for `rev-parse`, 60 s for reads of history and objects); a caller may pass an `AbortSignal` that stops the process. git is started by the absolute path `gitProgram()` (`src/git/program.ts`, #940) gives: the first `git` (Windows: `git.exe`) in an absolute folder of `PATH`, kept while `PATH` stays the same; without one, every call looks again, is `no-git` and starts no process. A bare `git` would let a repository run its own program: Node on Windows looks in the working folder of the child before `PATH`, and a relative `PATH` entry names that folder everywhere. An unknown result is `{ known: false, reason, detail }` with `no-git`, `refused` (`safe.directory`), `timeout` (also stopped by the caller) or `not-a-repository` (also for output the reader cannot parse).

- A repository folder may lie below the top level of its Git work tree (ThomasBirkmaier/ReqSeq-archive#377, ADR-0006): every path in and out of the reader is relative to the folder git runs in. `workTreeOf(folder)` (no process) gives the nearest folder at or above it, links followed, that holds a `.git` entry, and the depth below it; undefined where there is none.
- `headCommit(folder, { signal })`: `rev-parse --show-toplevel --is-shallow-repository --verify HEAD`, `{ known: true, commit, shallow }` for the repository whose work tree holds the folder (at its top level or below). `workspace.status` reports `refused` as an `info` problem `git.unavailable`. `repositoryCommit(repository)` (`model/repository-commit.ts`) is the commit of a repository as `workspace.status` and `data.export` give it: the HEAD, left out below the top level of a work tree whose commit has no tree at the folder (`treeAt`), with the `git.unavailable` info for a refusal, and `unknown` (`no-git`, `refused`, `timeout`, `not-a-repository`, `no-commit`, `no-tree`) when it has none, for the message of `data.store`. `repositoryState(rules, embeds)` (`model/uncommitted.ts`) adds `dirty` to it: `stateRules` and `isStateFile`/`stateFiles` say which files the data is made of, `uncommittedStateFiles` keeps those of `changedPaths`, and `gitBlobId` hashes working bytes as Git hashes a blob ([evidence views](evidence-views.md), "Data export and store"). `uncommittedFiles(folder, commit, files, counts)` is that check on a given set of files and returns the changed ones; `repositoryState` and `baseline.create` (SR-050 AK2) use it.
- `headFiles(folder)`: no process; reads the files of the Git folder of `workTreeOf(folder)` that name HEAD (ADR-0006): `{ stamp, commit?, shallow }`, undefined where only git can tell (then `headCommit`). The stamp changes whenever HEAD may have moved.
- `fileHistory(folder, head, paths, { signal })`: `log --no-show-signature --no-follow --no-renames --root --full-history --cc --name-only -z --parents --format=%H %cI %P%x00 --stdin <head>`, the paths after `--` on standard input (literal, relative to the folder; none: no process and no commits). Below the top level, `rev-parse --show-prefix` runs beside it and the prefix is taken off every listed path, also those of a merge, which `--relative` would not do. Commits newest first with committer date in UTC (`YYYY-MM-DDTHH:MM:SSZ`), their parents among the listed commits, and the given paths each one changed, as Git spells them; a merge names a path only when it differs from every parent, and a merge that took each path from one side is listed with none; every merge is listed (no history simplification), so the list for one path does not depend on the other paths. Read as it streams.
- `fileMoves(folder, commits, { signal })`: `-c log.showRoot=false log --no-show-signature --no-walk --relative --find-renames=50% -l1000 --diff-filter=R --raw --no-abbrev -z --format=%H --stdin`, the commit IDs on standard input (none: no process); in a partial clone (a remote with `promisor = true` or `extensions.partialClone` in the config file of the Git folder), and where `headFiles` cannot tell, `--find-renames=100%`, which needs no blob. For each commit that moved a file within the folder, its moves `{ from, to }` relative to the folder; a merge, a first commit and a move from outside the folder give none. Used by the version date to follow moves (ADR-0005 "Moves").
- `openObjectReader(folder, { signal })`: an `ObjectReader` whose rounds `info(names)` and `read(names, open)` share one `cat-file --batch-command --buffer` process (git 2.36 and newer; older: one `--batch-check` or `--batch` process per round). Names are object IDs or `<commit ID>:<path>` with the path relative to the folder (sent as `<commit ID>:./<path>`; `.` is the folder itself); `null` for every answer of git that names no object: `missing` (also a missing object of a partial clone, which is never fetched), `ambiguous`, `excluded`, and a submodule entry (newer git prints `<ID> submodule`) or anything below it. `read` streams the bytes of each object as Git stores them (no filters; a link is its link text) to the sink `open(info, index)` gives, so no object is held whole. After a failed round every later round gives the same failure. `close()` ends the process.
- `trackedFile(folder, file, { signal })` (SR-004 AK8, #1456): whether Git tracks `file` (relative to the folder), both under the short time limit of a `rev-parse`: one `cat-file --batch-check --buffer` with the names `:./<file>`, `:1:./<file>`, `:2:./<file>`, `:3:./<file>` (the index: staged, `git add -N`, unmerged) and `HEAD:./<file>` (missing without a commit) on standard input, and `ls-files --cached -z`, whose entries are compared in NFC and lower case (Git of a case-insensitive file system may check out a committed `.REQSEQ/local.yaml` into an existing `.reqseq`). Any object or entry counts; `{ known: true, tracked }`, else unknown. These names are built only here, so `openObjectReader` keeps taking object IDs and `<commit ID>:<path>` only. A `file` that is no `isGitPath` is a programming error.
- `commitBlobs(folder, commit, paths, { signal })`: `ls-tree -r -z <commit>` (no `--full-tree`, so only the files below the folder, relative to it, ThomasBirkmaier/ReqSeq-archive#377), `{ known: true, ids }` with the blob ID of each of `paths` that is a blob at that commit (a folder or submodule is none). The listing is read as it streams and only the asked paths are kept. One process instead of one `cat-file` lookup per path (#439); `uncommittedFiles` (`model/uncommitted.ts`) uses it for `data.export`, `data.store` and `baseline.create`. A `commit` that is no object ID is a programming error.

# Metamodel block (`src/metamodel/`)

Part of the [`@reqseq/core` README](../README.md).

`metamodelState` (async Workspace state, depends on `workspaceLayoutState`) reads the metamodel of the checked-out state (SR-011, D-021) with `loadMetamodel(layout)`:

- Every `*.yaml` file directly in the folder that `layout.metamodel` names, from the working tree, sorted by name (code-unit order). Subfolders and hidden files (`.` first) are not read; a `*.yml` file gives a `metamodel.invalid` warning. Nothing else is read: no built-in model, no other folder, nothing from Git. When the folder is the root of the main repository (`path: .`), `reqseq-workspace.yaml` is not a metamodel file, but every other `.yaml` file there is, including unrelated ones; give the metamodel its own folder.
- Each file is read with `readYamlFile` and checked against `metamodel.schema.json`. `types`, `properties`, `relations` and `statuses` of all valid files are merged in file order, as written. A key defined a second time in the same list, and a property key that a relation kind already uses or the other way round (keys are unique across both, ADR-0004), is a `metamodel.invalid` error on its line; the first definition is kept and the second left out. Problems come in file order, and within a file in line order.
- Faulty YAML is the problem of the files block (`file.invalid-yaml` with file, line and reason); a schema violation is `metamodel.invalid` with file and line. A faulty file contributes nothing; the valid files are still used (open question #141). Every problem of the metamodel files names the metamodel repository in `repository`, and `file` is relative to it (SR-018: the metamodel may lie in its own repository); a problem of the whole folder names the folder (`.` for the repository root). Problems of the layout (a missing folder or repository) name `reqseq-workspace.yaml` in the main repository.
- The metamodel folder may lie in any repository of the workspace: a folder in the main repository or an own repository (SR-018, D-021). Both are read the same way.
- `valid` is false when the folder is missing (the layout reports that), unreadable or has no `.yaml` file, or any file has an error. The workspace is then read-only (`workspaceAccess`, `assertWritable` in `src/metamodel/access.ts`): reads work, write commands are refused by `invoke` (SR-011 AK3; a missing metamodel repository counts too, open question #141). `workspace.status` shows `metamodel.valid`, `readOnly` and the problems. Only the metamodel decides this: a metamodel repository that cannot be written leaves the workspace writable (SR-018 AK2).
- Kept until `workspace.reset(metamodelState)` (the watcher, SR-007, SR-015) or a reset of the layout; a new `Workspace` reads it again. Nothing is cached elsewhere, so after a checkout the tool works with the metamodel of the checked-out state (SR-011 AK2).
- The definitions have the generated types of `metamodel.schema.json` (`MetamodelFile`, `MetamodelType`, `MetamodelProperty`, `MetamodelRelationKind`, `MetamodelStatus`).
- Inheritance (SR-012, `src/metamodel/inheritance.ts`): after merging, `effectiveTypes` holds every type of `types` (same order) as an `EffectiveType`: `ancestors` (parent first, up to the root), `properties` and `required` with all own and inherited keys, each once, root type first (the key order for new keys in element files, ADR-0004); required keys count as properties. `meaning` is the own one, else the closest ancestor's; `abstract` is not inherited (default false). A parent that is not defined (only when every metamodel file was read, see below) and every type on an inheritance cycle (also across files, `a -> b -> a`) are `metamodel.invalid` errors at the line of `extends`; they make the metamodel invalid. A type naming a property that is not defined is only a `metamodel.invalid` warning at the line of the list item (#141 c, option 2, #238; the message says when the key is a relation kind): the workspace stays writable, and the effective type and every type inheriting from it leave the key out, so a value under it in an element is an `element.unknown-property` hint (D-012) and no value is required for it; `types` keeps the key as written. While a file is faulty this is neither reported nor left out. Statuses per type (#306): `statuses` of the effective type are the statuses its elements may have, in the order of the metamodel's `statuses`: every status when neither the type nor an ancestor has `statuses`, else the union of their lists (inherited like properties; an empty list adds nothing), so an empty union is a type without status. Once any type in the chain has a list, only listed statuses count: a type with a list below a parent without one has only its own statuses. A key no status defines is a `metamodel.invalid` warning at the line of the list item and left out (kept, after the known ones, while a file is faulty); when no key is left, the message says the type has no status. A type that is not abstract and has statuses, all marked invalid, is a `metamodel.invalid` warning on its `statuses` (on its key when inherited), as `element.create` refuses its new elements. These problems come after the problems of the files, in type order. Resolution stops at an unknown parent or a cycle, so a read-only workspace still has effective types.
- References and the initial status (#157): after inheritance and meanings, every entry of `target-types` (property) and of `source-types`/`target-types` (relation kind) that names no defined type is a `metamodel.invalid` error on the line of the entry; the definition is kept as written. Exactly one status must have `initial: true`: none is an error on the first status (on the folder, without a line, when there is no status), every further one an error on the line of its `initial`. An initial status that is also marked `invalid` is a warning on the line of its `invalid`: `element.create` never gives it, as a new element would be superseded at once (D-044, #350). A type whose statuses are all marked invalid is no problem (its status is optional, #344). An unknown type and a missing initial status are reported only when every metamodel file was read, since a faulty file may define them; its own error already makes the metamodel invalid. The same holds for the inheritance checks (an unknown parent in `extends`, an unknown property in `properties`/`required`, #172); an inheritance cycle and a further initial status are always reported.
- Reserved prefix (#154, #239): `UNKNOWN` (`UNKNOWN_TYPE_PREFIX`) is the prefix of the short ID of an element whose type the metamodel does not know, and of a relation target that is not available. A type with this prefix is a `metamodel.invalid` error on the line of its `prefix`, reported always (also while a file is faulty); the type is kept, the metamodel is invalid. A prefix that only starts with `UNKNOWN` is allowed.
- Markdown properties (SR-127, `markdown: true` in `metamodel.schema.json#/$defs/property`): a property of kind `text` whose values are Markdown like the text: emphasis, code and inline references that are followed, checked and confirmed like those in the text. Not with another kind and not with the meaning `title` or `identifier`: `metamodel.invalid` with the line of `markdown` (`markdownProblems` in `src/metamodel/meanings.ts`). `markdownKeysOf(metamodel)` (`src/metamodel/lookup.ts`) gives the marked keys, built once per metamodel object and empty for a metamodel that is not valid. The standard model marks `acceptance-criteria` and `rationale`. The flag is no part of the version (ADR-0005).
- Meanings (SR-013, D-012, D-059, `src/metamodel/meanings.ts`): the tool knows the built-in meanings that the metamodel assigns with `meaning` (`MEANINGS`: `requirement`, `need`, `variant`, `package` for types; `title`, `validity`, `packages`, `emergent`, `verification-method`, `statement`, `source`, `source-identifier`, `import-date`, `delivery`, `import-version` for properties; `derivation`, `replacement`, `succession`, `exclusion` for relation kinds). `metamodel.meanings` gives, for every meaning, the keys whose own definition declares it, in metamodel order; a type that inherits a meaning, or sets the one it inherits anyway, is not a second assignment. A type or property meaning that a second key declares is a `metamodel.invalid` error at the line of its `meaning` (after the inheritance problems), so the workspace opens read-only (open question #141); several relation kinds may share a meaning. `meaningKindProblems` checks the value kind a meaning needs: `identifier` of kind `text` without `many` (an error, #305); `import-version` (Importfassung, D-059) of kind `text` without `many` and never `content` (an error, #357: otherwise every imported element would read as locally changed); `emergent` of kind `choice` without `many` with a choice `yes`, the mark (a warning, SR-035, #591 Q1: the metamodel stays valid and the workspace writable, and no element is marked emergent until the property is fixed). `ORIGIN_MEANINGS` lists the five meanings of the origin of an imported element (SR-057), and `originMeaning(definition)` tells whether a property holds one; only `reqif.import` writes them. Functions never look for a fixed key: they first call `requireMeaning(metamodel, meaning, command)` (`command` is their `CommandName`), which throws `metamodel.meaning-unassigned` with `details: { meaning, list, command }` and a message naming the missing assignment when no key has it (SR-013 AK3), and then take the definitions from `typesWithMeaning` (effective types, so subtypes that inherit the meaning count), `propertyWithMeaning` or `relationKindsWithMeaning`. The three meaning enums are `$defs` of `metamodel.schema.json` (`typeMeaning`, `propertyMeaning`, `relationMeaning`). The structural keys `id`, `type`, `status` and the flags `content` (property) and `invalid` (status) are fields, not meanings.
- Standard model (SR-014, D-037, D-059, D-060, `src/metamodel/standard-model.ts`): `STANDARD_MODEL_TEXT` is `schemas/examples/metamodel/standard-model.yaml`, embedded unchanged by `pnpm contracts:generate` as `src/generated/standard-model.json` (`contracts:check` keeps them equal; never copy it by hand). Only `workspace.init` uses it; a workspace is never given the standard model at run time.
- `metamodel.get` (`src/commands/metamodel/get.ts`, SR-012, SR-013): the effective types (`metamodel.schema.json#/$defs/effectiveType`, the type of `EffectiveType`), the properties, relation kinds and statuses as written, except that every property carries `content` (false when not written), so each access says whether it counts to the version (D-057, SR-130 AK5, #624), `meanings` (every meaning, an empty list when unassigned) and the metamodel problems of the layout and the files (`metamodelProblems(workspace)` in `src/metamodel/access.ts`, whose errors are also the reasons of a read-only workspace). It reads, so it also works on a read-only workspace. The app's metamodel buffer (SR-130) shows this output as a graph and as text; nothing else is read.
- Lookup (`src/metamodel/lookup.ts`): element files hold the type key, the tool shows its `name` (D-043). `findType(metamodel, key)` finds a type only by key (an index per metamodel object). `typeForNewElement(metamodel, key)` is the type `element.create` uses: it throws `input.invalid` with `details.type` and `details.reason` (`unknown` or `abstract`) when no element of that type can be created.

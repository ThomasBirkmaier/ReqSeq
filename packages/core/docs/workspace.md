# Workspace block (`src/workspace/`)

Part of the [`@reqseq/core` README](../README.md).

`workspaceLayoutState` (async Workspace state) reads `reqseq-workspace.yaml` in `Workspace.root` (checked against `workspace.schema.json`) and the optional `.reqseq/local.yaml` (`workspace-local.schema.json`) when Git does not track it (`localFileUse`, below), and locates every repository (SR-004):

- Path: the local override, else `path` of the workspace file, else `../<name>`. The main repository (the entry with `main: true`; the only entry of a one-repository workspace) is always the root, `.`. Relative paths are relative to the root. Committed paths use `/` (a `\` is warned about and replaced); an absolute committed path is warned about and ignored, absolute paths belong in `.reqseq/local.yaml`. So is a committed path that leaves the folder holding the main repository (`../../../../net/host/r` or `../../other/r`, which an automounter can mount), or that passes a link out of the first folder it enters there, a clone or the main repository (`../a/x` with `x -> /net/host/b`; `linksStayInside`, judged before anything follows it); with the main repository directly below a file system root, only a folder next to it or a path into it is taken: it comes from repository content, which ReqSeq does not let open a network share (#294, to refuse workspace-file paths to a network share). `.reqseq/local.yaml` belongs to the user's machine and may name any folder. There is no `~` expansion.
- `available` means the folder exists; `folder` is then its real path, which `workspace.status` gives as `repositories[].absolutePath` (#1793). The metamodel folder must not be reached through a link out of its repository: such a folder is a `metamodel.invalid` error and counts as missing, judged by the link's text before it is followed (#294, ADR-0007). The folders of baselines, filters, perspectives and YAML state files are listed only with the same check (`listFolderFiles` with the repository), and the mappings folder is checked the same way before a mapping is written. A missing repository is normal (N-041): `available: false` and an `info` problem `workspace.repository-missing`; nothing else changes (SR-004 AK3).
- `variantIndependent` (SR-173): the mark `variant-independent` of the workspace file (default false). Only the shared file sets it; `.reqseq/local.yaml` cannot (its schema has no such key, so it is ignored with a warning), so every copy computes the same status. `variantIndependentOf(layout)` gives the marked names as a set, built once per layout; the evidence status, "has evidence", the lists and the outdated hint read it (records without variant of an element of a marked repository hold in every view, [evidence-status.md](evidence-status.md)). `workspace.status` shows `variantIndependent: true` per marked repository. An older ReqSeq rejects a workspace file with the mark (`file.faulty`); the format stays `reqseq-workspace: 1`.
- A repository in the same folder as another one is left out (`workspace.invalid` error; the main repository always stays). `excludes` lists the folders of other available repositories nested inside a repository (e.g. submodules); discovery skips them.
- `availableRepositories(layout)` gives the roots in which elements are discovered (SR-003). `locate(layout, location)` resolves a `{ repository, path }` location; `settingLocation(layout, "baselines" | "filters" | "perspectives" | "mappings")` gives the configured location or the default in the main repository.
- `layout.metamodel` names the metamodel folder and whether it exists (`metamodel.invalid` error with the reason otherwise); loading it is the metamodel block (SR-011, below). `layout.file` is the checked workspace file for later blocks (evidence, ignore).
- No workspace file: `CommandError workspace.not-found` with `details.file`; with workspaces one level below, `details.below` and a message naming them; else, where `workspace.init` can create a workspace (an existing folder, or a missing one in an existing folder), `details.next` with that step (`createWorkspaceStep` of `src/next-steps.ts`, SR-226 AK1). A faulty one (YAML, schema, a repository name listed twice): `file.faulty` with `details.problems`; it is never used in part. A location naming an unknown repository and a faulty local file are problems; the workspace still opens. A folder ReqSeq writes into (filters, perspectives, baselines and mappings, configured or by default, and each evidence location) that meets Git inside its repository is a `workspace.invalid` warning per folder (`gitPlaceOf` in `git-folder.ts`): a name below the repository folder that some system takes for `.git` (`isTakenForGit` in `files/paths.ts`: any case, trailing dots and spaces, invisible format characters, an NTFS stream suffix, `GIT~1`), an existing folder with a `.git` entry, or a real path into such a name. It is judged relative to the repository, so a repository below a `.git` folder (a worktree) gets none. `filter.save`, `perspective.save` and `baseline.create` refuse such a file right before they write it (`refuseGitPlace`, `input.invalid`, `reason: "git-folder"`); mappings and evidence records are refused by the walk rules (`refuseUnlisted`) (D-036, #1487).
- The local file is used only when `localFileUse` (`src/workspace/local-use.ts`, SR-004 AK8, #1456) allows it; otherwise a `workspace.invalid` warning on `.reqseq/local.yaml` (a constant text, without git's message) and the places of the workspace file apply. In this order: used when the root has no `.git` entry (`workTreeOf`, SR-004 AK6), whatever `.reqseq` is. Then not used when `.reqseq` is a link (also one inside the root), when the names on disk are not exactly `.reqseq` and `local.yaml` (a case-insensitive file system opens other spellings), when the root or `.reqseq` cannot be listed, or when `.reqseq` lies in another work tree than the root (a submodule or any nested repository). Then `trackedFile` of the git reader asks the index (all stages, also entries that name the same file on disk by another spelling) and HEAD; tracked: not used; no git program: used (SR-004 AK6). When git refuses the repository, fails or does not answer in time, the file is not used either (assumption of the open question #1475). A file staged or removed from Git while the app is open counts at the next layout load (the watcher does not watch `.git/index`; every CLI call loads it again). The disk can change between the checks and the read; whoever can change `.reqseq` there can change the workspace file too.
- The layout, including availability, is kept until `workspace.reset(workspaceLayoutState)` (the watcher, SR-007). Finding the workspace root upwards from a folder is the CLI's job.
- `isWritableFolder(folder)` (`src/workspace/writable.ts`) asks the operating system whether this process may write the repository folder itself (`access(W_OK)`); it writes nothing. `workspace.status` uses it on every call for `repositories[].readOnly` of each available repository. `workspace.status` also lists the `evidence` locations of the workspace file as written, each with `available`: whether the evidence walk reads it (`isReadEvidenceLocation` of the evidence block, the same rules as `evidenceFiles`, on every call, #625); why not is for the evidence block to say (`evidence.folder-missing`, `file.skipped`, `file.unreadable`). Each also has `folder`: the location relative to the workspace root in the form `folder` of `evidence.record` takes (`evidenceFolder` of the evidence block, the rule `evidence.record` resolves it with; `.` for the root, left out for a repository the workspace file does not list), which `evidence.record` refuses while the repository is not on this machine. Rights to change a repository are enforced by the Git server (D-016, D-024): the usual read-only metamodel repository is a writable local clone whose pushes are refused, and ReqSeq never pushes (D-036). A locally read-only repository (a read-only file system, a checkout without write permission) is normal too: it never makes the workspace read-only, and a write into it is refused by the files block with `file.read-only` (SR-018 AK2). On Windows `access` never reports a folder as read-only, so `isWritableFolder` returns undefined there and `readOnly` is left out (unknown); the write itself is still refused with `file.read-only`.

`workspace.init` (`src/commands/workspace/init.ts`, SR-014) creates a workspace with `createWorkspace(root, { name, metamodel, metamodelFile })` (`src/workspace/init.ts`); the command passes the shipped standard model as `metamodelFile`:

- `path` is resolved against the root of the call (`localPath`: the CLI passes it absolute, API and MCP relative to the root). It must be an existing folder (`file.folder-missing`, `input.invalid` for a file). A folder or metamodel folder in a `.git` folder, in any case and through links, is `input.invalid` with `reason: git-folder` before anything is written (`refuseGitAt`, D-036, #1449). Other files in it are fine (a fresh clone has `.git`), but `reqseq-workspace.yaml` and the metamodel file must not exist (`file.changed-on-disk`); nothing is written then. On the command line and in the app `path` is not confined to the root of the call: an absolute path, or one with `..`, creates the workspace wherever the process may write. Through API and MCP it must lie inside the repositories of the workspace the server serves, or inside its root when that has no workspace file yet (SR-142, ADR-0009 "Local paths").
- It writes `<metamodel path>/standard-model.yaml` (default folder `metamodel`, created by `createFolder` of the files block; `.` is the root) and then `reqseq-workspace.yaml`: `name`, one repository named after the folder (`repositoryNameFor`: `Weather Station` becomes `weather-station`, `main` when nothing is left), `url: ""` for the person to fill in, the metamodel location, and the evidence location `evidence` in the main repository (`DEFAULT_EVIDENCE_FOLDER`, SR-230 AK4); then the folder `evidence` with an empty `evidence/.gitkeep` (`EVIDENCE_KEEP_FILE`, SR-230 AK4), only when nothing, not even a link, was at that path before the call (`lstat` before anything is written, so a metamodel folder there is no folder that was there): a folder, file or link there is left as it is and not listed, and a failure of `createFolder` or the write leaves the workspace created and becomes the warning `workspace.evidence-folder-not-created` (`something is already at evidence/.gitkeep` for `file.changed-on-disk`, else the files block's message, any other failure only its error code, ADR-0009), first in `problems`; a failed `.gitkeep` can leave the folder `evidence` created, empty and not listed; last, the lines `*.reqseq-tmp` and `.reqseq/local.yaml` in `.gitignore` of the folder (SR-014 AK1; created, or the missing lines appended in one write with the file's own line ending; a linked `.gitignore` is left alone; #271, #1456), so temp files left by a crash and the local file are not committed. The workspace file is checked against `workspace.schema.json` before anything is written (`input.invalid` with `details.errors`). If the workspace file then cannot be written, the error keeps its code and names the metamodel file that was written before it (message and `details.written`); it is left in place.
- `metamodel.repository` naming another repository (SR-018) lists it in the workspace file with `url: ""` and its default path; nothing is written outside the folder, so that repository keeps (or gets) its own metamodel.
- Then, unless `skill` is false, the skill file at each place of D-079 (SR-229 AK9): `writeSkillFiles` of `tool/guide/skill-file.ts` on the new workspace with `replace: false` and the `localPaths` of the call, so through API and MCP a Git root outside the repositories of the served workspace is refused at both places. Each place written joins `files` in the order of D-079 (`../.claude/…`, `../.agents/…` below a Git root); `keepOwn` leaves ReqSeq's own unchanged file of any version (`unchanged`, not listed; SR-014 AK1, SR-229 AK9); each refused place leaves the workspace created and becomes one warning `workspace.skill-not-written` with the refusal's message and the place as `file`. An error that is no refusal (a bug) stops the step at its place and becomes one such warning with only its error code and no file (no absolute path, ADR-0009), and `files` then lists no skill file.
- Output: `files` (written, relative to the new root), `next`, the next steps (`afterInitSteps` of `src/next-steps.ts`, SR-226 AK2: `workspace.connectAgent` with `client` open, then `element.create` with `type` and `title` open, each with the absolute `workspace`, which the CLI names with `--workspace` when it is not the current folder; without `element.create` while the new workspace is read-only, `runnableSteps`, SR-226 AK6), and `problems`: the warning of the evidence folder, if any, then the layout and metamodel problems of the new workspace as opened afterwards (none for the standard model). `FIRST_STEPS` of the same file (`@reqseq/core/next-steps`, SR-118 AK9) are the steps the app's overview shows in a workspace without elements: `element.create`, `reqif.import`, `workspace.connectAgent`. When the root of the call is the new folder (compared with links resolved), its layout state is reset. No Git command runs (D-036).

## Recent workspaces (SR-131, `src/workspace/recent.ts`)

The workspaces opened last, for `workspace.recent`: `<OS cache>/reqseq/recent-workspaces.json` (`recentWorkspacesFolder`, next to the cache folders of the copies; `schemas/recent-workspaces.schema.json`, ADR-0008), `{ format: 1, workspaces: [{ root, key, opened }] }`, the most recent first, at most 20 (`RECENT_WORKSPACES_KEEP`).

- `rememberWorkspace(root, { now, key, environment })` puts an absolute root first as opened now (a root or key with NUL or more than 4096 characters is skipped); the entry with the same `key` goes (`workspaceKey`: `canonicalRoot`, so two names of one folder are one entry, and the stored `root` keeps the newest spelling). Read, change and write run under `lockCacheFile`; while another process holds the lock it waits once (200 ms) and then skips (`false`). It writes with `writeCacheFile` (mode 0600); the oldest entries are left out while the file would exceed 64 KiB. A failing write rejects.
- `readRecentWorkspaces()` reads with `readCacheFile(…, 64 KiB)` and never resolves a root again (the `key` is stored): content that is not JSON, of another format, with an entry of the wrong shape (also a root or key with NUL or longer than 4096 characters) or larger than 64 KiB is the empty list, and the next record overwrites it. `readCacheFile` with a size bound opens without waiting (`O_NONBLOCK`) and reads only a file: a FIFO or a device at the path is no content. It never rejects.
- `createBoundedRunner(slots)` runs file-system jobs with at most `slots` at once and a timeout per call (`"timeout"`; a job still waiting then never starts, and a running one learns it through `expired()`); a slot is freed only when its job settles. `createExistenceChecker({ stat, timeoutMs, slots })` is built on it and answers whether `<root>/reqseq-workspace.yaml` is a file, for the root itself, never a folder above it. At most 2 `stat`s run at once across all calls of a checker; a slot is freed only when its `stat` returns; 1 s after the call every root without an answer is `"timeout"` (missing wherever only existence counts), and a root still waiting for a slot gets no `stat`. A hung share or automount therefore never takes more threads of the thread pool than a checker has slots. `recentWorkspaceStates()` (the list with `exists`) uses one such checker per process.
- `workspace.recent` (`src/commands/workspace/recent.ts`) reads the list on every access: `recentWorkspaceStates()` of the process environment as `{ workspaces: [{ root, opened, exists }] }`, without `key`. It does not use the workspace of the call (ADR-0002 rule 7), so it gives the same list from any folder.
- `workspace.markOpened` (`src/commands/workspace/markOpened.ts`, SR-250) marks the workspace of the call, the only command that changes the list (SR-250 AK4): `markOpenedWorkspace(workspace)` of `src/model/recent-record.ts` refuses with `file.read-only` (`reason: inside-repository`) when the list would lie inside a repository of the workspace (`insideRepository` of the model cache, the rule of `usableCacheFolder`, D-036), then calls `markWorkspace(root)`, the strict form of `rememberWorkspace`. It never skips and never replaces a list it cannot read; each refusal leaves the list as it was (the file is replaced in one rename) and becomes a `CommandError` without an absolute path (ADR-0009), with `details.reason`: `locked` (`file.changed-on-disk`: another process still holds the lock after the one wait), `unreadable` (`file.faulty`: a read error, something other than a file of at most 64 KiB at the path, or content that is no list of format 1), `unwritable` (`file.read-only`: the lock or the file cannot be written) and `root-not-held` (`file.read-only`: a root that is not absolute or, links resolved, longer than 4096 characters). A missing list is created with the one entry (SR-250 AK3). Output `{ root, opened }`, the entry as the list now holds it first. It runs while the workspace is read-only (`whileReadOnly: allow`).

## `~` in the app (SR-143 AK2)

- The app has no shell that expands `~`, so its local path rule (`appLocalPaths`, `src/workspace/local-paths.ts`) carries the home folder (`LocalPaths.home`), and `invoke` replaces a leading `~`, `~/` (and `~\` on Windows) of every `localPath` field of an `app` call with it before the command runs (`replaceLocalPaths`, `expandHome` of `path-text.ts`). The command line keeps `~` as it gets it (its shell expands it), and API and MCP refuse it (SR-142).

## List folder (SR-143, `src/workspace/list-folder.ts`, `src/commands/workspace/listFolder.ts`)

The entries a path argument of the app's command prompt is completed with (ADR-0002 rule 1).

- `listTypedFolder(text, { files, home?, base?, check?, platform })` splits the typed text at its last separator (`splitTypedPath`: `/`, and `\` on Windows only): the part before names the folder, the rest is the typed `name`. The folder is checked by its text (`localFolder` of `src/workspace/path-text.ts`; with a `base` a relative path is resolved from it, without one only an absolute path is taken; `~` is home only with a `home`, else an ordinary name; a share the base already lies on stays allowed). A refused text gives `problem: "invalid"` without any file-system call. Then `check(folder)` runs (the command passes `ctx.localPaths.check`, so API and MCP list only inside the repositories, SR-142) and `listFolder` lists it.
- `listFolder(folder, { files, dots })` reads the entries with `opendir` and nothing else: no `stat`, no link followed (SR-078, SR-142), so a link is kind `link`, whatever it points to (on Windows every reparse point: junctions, OneDrive and Cloud Files placeholders, deduplicated files, app execution aliases); sockets and devices are left out, files only with `files`, names starting with "." only with `dots` (the typed name starts with "."). Order: folders and links, then files, each by the code units of the NFC form; names keep the spelling on disk. At most 50,000 (`truncated`; folders and links first, then the files read first). `opendir` reads 1,024 entries per call, and the NFC sort key is computed once per entry (SR-143 AK5). `ENOENT` is `missing`, every other error (`ENOTDIR`, `EACCES`, `EPERM`, `EIO`) and no answer within 1 s `unreadable`. It runs in one bounded slot of its own per process (`createBoundedRunner(1)`), so a hung share blocks only further listings: one hung listing makes every later listing of that process `unreadable` until it returns. Known limit: where the file system gives no entry type with the names (`DT_UNKNOWN`: NFS without readdirplus, some FUSE file systems, XFS without `ftype`), Node finds it with a synchronous `lstat` per entry on the event loop, outside the slot and the timeout (never through a link).
- `workspace.listFolder` gives `{ folder?, name, entries: [{ name, kind }], problem?, truncated? }`; a relative `path` (a plain text, not a `localPath`, so the CLI keeps its trailing separator) is resolved from the workspace root on every access; `~` is home with `absolute` (every access) and otherwise where the path arguments of the access take it so (`ctx.localPaths.home`: the app), so a suggestion and the file a command then writes agree.

## About ReqSeq (SR-161, `src/commands/tool/info.ts`, `src/build-info.ts`)

- `tool.info` (title "About ReqSeq"; CLI `reqseq tool info`, MCP `tool_info`) gives the versions of CLI and MCP server (the one product version, AK4), the build, the runtime, the open workspace (root, name, repository names, number of elements in the available repositories, no view), the licence notice (`LICENSE`, embedded in `generated/product.json` by `pnpm contracts:generate`) and the addresses of the documentation and the releases as text (AK2: no network).
- Commit and build date come from `dist/build-info.json`, which `scripts/package/stage.mjs` writes into each staged core (`writeBuildInfo`; the date is the commit date). A checkout build has none: `build.development: true`, and the delivery files (`license.thirdParty`, `documentation.bundled`) are left out. `bundled` names the documentation site of the delivery, `lib/docs` in its folder (SR-141, ADR-0020), which `reqseq serve docs` serves.
- The runtime is `process.versions` of the calling process. The delivered CLI, API, MCP server and UI server run on the delivery's Node (ADR-0020), so they give the same `node` (AK5).

## Agent guide (SR-229, `src/commands/tool/guide.ts`, `src/commands/tool/guide/`)

- `tool.guide` gives `{ guide }`, the agent guide as Markdown; `names` (`cli`, the default, or `mcp`) picks command-line calls or MCP tool names, and the pipeline paragraph always has command-line calls (AK1, AK11). The CLI prints the text as it is (`textOutput`). With `instructions` it gives the MCP server instructions instead (AK17, `serverInstructions` in `guide/text.ts`): the title, a paragraph that points to the guide, and the rules section with MCP tool names, nothing from the workspace, at most 4,000 characters; `instructions` with `skill` is `input.invalid`. The MCP server invokes it once with `instructions` before it serves and sends the text as the `instructions` of its `initialize` result.
- `guide/text.ts` is the one place of the text: `GUIDE_SECTIONS` in order (a new section is one more entry), with the impact check before the need step (AK12) and the writing rules after the requirement step (AK13) and the metamodel section with `metamodel.get` and the commands of `METAMODEL_CHANGES` after the workspace check (AK15), then `GUIDE_TAIL`, the pipeline paragraph (AK11) with the HTML export as a step (AK14) and the page of the installation guide by its title `INSTALL_PAGE_TITLE`, fixed text that a test compares with the `title` of `docs/guide/how-to/install-reqseq.md`; `GUIDE_RULES` are the rules of AK5 and `GUIDE_WRITING_RULES` those of AK13 (English, question #1928). A call names an evidence location of at most 40 characters, else a placeholder, so a long path does not count twice against the length of AK1 (10,000 characters with the standard model and at most three evidence locations of together 60 characters). `guide/calls.ts` writes each call from its catalog command and input (typed by `CommandName`); a CLI test parses every call back and compares it with the MCP form.
- `guide/facts.ts` reads only the layout and the metamodel, never the elements: the creatable types with the meaning need or requirement, their statuses with the initial and the invalid ones, the derivation kinds, the properties with the meanings acceptance criteria and verification method, and the evidence locations (AK4). A `CommandError` while reading them (no workspace, a faulty workspace file) or a metamodel that is not valid gives the guide without these facts, with the reason (AK2).
- Workspace text goes into an agent's prompt: every name, path and reason passes `guideValue` (one line, no control characters, Markdown escaped, at most 80 code points, 300 for a reason), keys and prefixes appear only in code spans, no description is taken, and the facts stand under "Values from this workspace".
- Skill file (AK6 to AK8, D-079): with `skill`, `guide` holds the skill file `managing-requirements` instead (`guide/skill.ts`), built from the catalog only, so it has no name of a metamodel and is the same for every workspace of a version; its workflows are `SKILL_WORKFLOWS`, the last one "Change the metamodel" (AK15). Each call appears as MCP tool and command-line call (`renderCall` twice; a boolean is `--x` or `--no-x`). Its frontmatter `metadata` holds `generator: "ReqSeq"`, `reqseq-version` and `reqseq-checksum: "sha256:<hex>"`; `skillChecksum` hashes the canonical form (no BOM, LF, the checksum value blanked to `sha256:`, UTF-8) and both computes and checks it, `identifySkill` tells ReqSeq's own file, `compareVersions` orders versions as Semantic Versioning does (#1920).
- `guide/skill-file.ts` writes it (`write`, `replace` needs `write`, `write` needs `skill`) at each place of D-079, in its order (`SKILL_FILES`: `.claude/skills/managing-requirements/SKILL.md`, then `.agents/skills/managing-requirements/SKILL.md`): `skillLocations` puts both in `gitRootOf(realpath(root))` (`workspace/git-root.ts`, the nearest `.git` entry git accepts, `workTreeOf`), else in the workspace folder; `path` is relative to the real workspace root (`../.claude/…` below a Git root). `writeSkillFiles` first reads the layout (no workspace throws, once), then handles each place on its own, in this order, nothing written before the last step: the SR-142 check of the call (`localPaths.check`, field "skill file"), whose refusal names the place and `reqseq tool guide --skill --write` and no absolute path; `lstat` (a link or folder is `file.not-regular`; so is a file in the way of the folders, found by walking from the root, since Windows says ENOENT there; a file over 64 KiB counts as foreign); ReqSeq's own intact file is left (`unchanged`) or replaced (`previousVersion`), any other file only with `replace`, else `file.exists` (`details.reason` `foreign` or `changed`); `refuseGitAt` on the real folder (D-036); then `createFolder` and `writeFileAtomic` with the snapshot of the look. A refusal of a place is a value, and the next place is written all the same; a folder of `.agents/…` linked to that of `.claude/…` finds the file just written, so it is `unchanged`. `tool.guide` returns `places` (path, action, `previousVersion`) in that order, or, when a place is refused, throws (`writtenOrThrow`): the code of the first refused place, a message with each place and its result (a reason given once), and `details.places` with a refused place's `error`. `readSkillFiles` tells what lies at each place (`missing`, `foreign`, `own` with `sameContent`, or `blocked` when the look or the Git check refuses it) for the workspace check (`workspace.skill-older-version`, `workspace.skill-missing`, AK10, [workspace-check.md](workspace-check.md)). `workspace.init` writes both places with `keepOwn` and gives one `workspace.skill-not-written` per refused place (AK9). The command is `write-files` with `whileReadOnly: allow` (SR-229 AK8).

## Connect AI agent (SR-227, `src/commands/workspace/connectAgent.ts`, `src/agent-setup.ts`, `src/installation.ts`)

- `workspace.connectAgent` (CLI `reqseq workspace connect-agent --client <client>`, MCP `workspace_connectAgent`) gives the setup a client of an agent needs to start `reqseq mcp` for the workspace: `server` (program, arguments, environment) and `setup` (a command for sh or PowerShell, or a JSON block with the client's configuration file on this system); for every client but Claude Desktop, `next` also names the command-line call that writes the skill file (SR-227 AK2), with the program of the setup (`skillCall`), for sh or PowerShell as the system's terminal (`skillSentence`). The templates per client are data in `agent-setup.ts`; their sources are named in the PR of #1888. It reads only: the workspace file for the name, and whether the entry and the launcher exist (AK6).
- The installation is that of the process (`installation.ts`): `process.execPath` and `argv[1]`, the CLI's `bin.js`, in the CLI, `reqseq mcp` and `reqseq serve api`. Tests set another one (`setInstallation`).
- The launch form: on macOS and Linux the launcher `bin/reqseq` of a delivery, when the runtime is `<folder>/runtime/node` and the entry `<folder>/lib/dist/bin.js` (ADR-0020) and the launcher exists; on Windows `runtime\node.exe` with `bin.js` and no variable (a `.cmd` starts only through a shell; the form is the assumption of #2352); elsewhere (checkout, npm tarball) the runtime with `bin.js`, and `ELECTRON_RUN_AS_NODE=1` only on Electron.
- Errors: `agent.app-translocated` (macOS runs the app from an `AppTranslocation` folder, AK4), `agent.path-unsupported` (VS Code on Windows: `code` is `code.cmd`, which cannot take `&^%<>|!"` in a path), `agent.cli-missing` (no `bin.js`).

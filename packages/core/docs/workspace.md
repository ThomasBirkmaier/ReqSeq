# Workspace block (`src/workspace/`)

Part of the [`@reqseq/core` README](../README.md).

`workspaceLayoutState` (async Workspace state) reads `reqseq-workspace.yaml` in `Workspace.root` (checked against `workspace.schema.json`) and the optional `.reqseq/local.yaml` (`workspace-local.schema.json`) when Git does not track it (`localFileUse`, below), and locates every repository (SR-004):

- Path: the local override, else `path` of the workspace file, else `../<name>`. The main repository (the entry with `main: true`; the only entry of a one-repository workspace) is always the root, `.`. Relative paths are relative to the root. Committed paths use `/` (a `\` is warned about and replaced); an absolute committed path is warned about and ignored, absolute paths belong in `.reqseq/local.yaml`. So is a committed path that leaves the folder holding the main repository (`../../../../net/host/r` or `../../other/r`, which an automounter can mount), or that passes a link out of the first folder it enters there, a clone or the main repository (`../a/x` with `x -> /net/host/b`; `linksStayInside`, judged before anything follows it); with the main repository directly below a file system root, only a folder next to it or a path into it is taken: it comes from repository content, which ReqSeq does not let open a network share (#294, to refuse workspace-file paths to a network share). `.reqseq/local.yaml` belongs to the user's machine and may name any folder. There is no `~` expansion.
- `available` means the folder exists; `folder` is then its real path. The metamodel folder must not be reached through a link out of its repository: such a folder is a `metamodel.invalid` error and counts as missing, judged by the link's text before it is followed (#294, ADR-0007). The folders of baselines, filters, perspectives and YAML state files are listed only with the same check (`listFolderFiles` with the repository), and the mappings folder is checked the same way before a mapping is written. A missing repository is normal (N-041): `available: false` and an `info` problem `workspace.repository-missing`; nothing else changes (SR-004 AK3).
- `variantIndependent` (SR-173): the mark `variant-independent` of the workspace file (default false). Only the shared file sets it; `.reqseq/local.yaml` cannot (its schema has no such key, so it is ignored with a warning), so every copy computes the same status. `variantIndependentOf(layout)` gives the marked names as a set, built once per layout; the evidence status, "has evidence", the lists and the outdated hint read it (records without variant of an element of a marked repository hold in every view, [evidence-status.md](evidence-status.md)). `workspace.status` shows `variantIndependent: true` per marked repository. An older ReqSeq rejects a workspace file with the mark (`file.faulty`); the format stays `reqseq-workspace: 1`.
- A repository in the same folder as another one is left out (`workspace.invalid` error; the main repository always stays). `excludes` lists the folders of other available repositories nested inside a repository (e.g. submodules); discovery skips them.
- `availableRepositories(layout)` gives the roots in which elements are discovered (SR-003). `locate(layout, location)` resolves a `{ repository, path }` location; `settingLocation(layout, "baselines" | "filters" | "perspectives" | "mappings")` gives the configured location or the default in the main repository.
- `layout.metamodel` names the metamodel folder and whether it exists (`metamodel.invalid` error with the reason otherwise); loading it is the metamodel block (SR-011, below). `layout.file` is the checked workspace file for later blocks (evidence, ignore).
- No workspace file: `CommandError workspace.not-found`. A faulty one (YAML, schema, a repository name listed twice): `file.faulty` with `details.problems`; it is never used in part. A location naming an unknown repository and a faulty local file are problems; the workspace still opens. A folder ReqSeq writes into (filters, perspectives, baselines and mappings, configured or by default, and each evidence location) that meets Git inside its repository is a `workspace.invalid` warning per folder (`gitPlaceOf` in `git-folder.ts`): a name below the repository folder that some system takes for `.git` (`isTakenForGit` in `files/paths.ts`: any case, trailing dots and spaces, invisible format characters, an NTFS stream suffix, `GIT~1`), an existing folder with a `.git` entry, or a real path into such a name. It is judged relative to the repository, so a repository below a `.git` folder (a worktree) gets none. `filter.save`, `perspective.save` and `baseline.create` refuse such a file right before they write it (`refuseGitPlace`, `input.invalid`, `reason: "git-folder"`); mappings and evidence records are refused by the walk rules (`refuseUnlisted`) (D-036, #1487).
- The local file is used only when `localFileUse` (`src/workspace/local-use.ts`, SR-004 AK8, #1456) allows it; otherwise a `workspace.invalid` warning on `.reqseq/local.yaml` (a constant text, without git's message) and the places of the workspace file apply. In this order: used when the root has no `.git` entry (`workTreeOf`, SR-004 AK6), whatever `.reqseq` is. Then not used when `.reqseq` is a link (also one inside the root), when the names on disk are not exactly `.reqseq` and `local.yaml` (a case-insensitive file system opens other spellings), when the root or `.reqseq` cannot be listed, or when `.reqseq` lies in another work tree than the root (a submodule or any nested repository). Then `trackedFile` of the git reader asks the index (all stages, also entries that name the same file on disk by another spelling) and HEAD; tracked: not used; no git program: used (SR-004 AK6). When git refuses the repository, fails or does not answer in time, the file is not used either (assumption of the open question #1475). A file staged or removed from Git while the app is open counts at the next layout load (the watcher does not watch `.git/index`; every CLI call loads it again). The disk can change between the checks and the read; whoever can change `.reqseq` there can change the workspace file too.
- The layout, including availability, is kept until `workspace.reset(workspaceLayoutState)` (the watcher, SR-007). Finding the workspace root upwards from a folder is the CLI's job.
- `isWritableFolder(folder)` (`src/workspace/writable.ts`) asks the operating system whether this process may write the repository folder itself (`access(W_OK)`); it writes nothing. `workspace.status` uses it on every call for `repositories[].readOnly` of each available repository. `workspace.status` also lists the `evidence` locations of the workspace file as written, each with `available`: whether the evidence walk reads it (`isReadEvidenceLocation` of the evidence block, the same rules as `evidenceFiles`, on every call, #625); why not is for the evidence block to say (`evidence.folder-missing`, `file.skipped`, `file.unreadable`). Rights to change a repository are enforced by the Git server (D-016, D-024): the usual read-only metamodel repository is a writable local clone whose pushes are refused, and ReqSeq never pushes (D-036). A locally read-only repository (a read-only file system, a checkout without write permission) is normal too: it never makes the workspace read-only, and a write into it is refused by the files block with `file.read-only` (SR-018 AK2). On Windows `access` never reports a folder as read-only, so `isWritableFolder` returns undefined there and `readOnly` is left out (unknown); the write itself is still refused with `file.read-only`.

`workspace.init` (`src/commands/workspace/init.ts`, SR-014) creates a workspace with `createWorkspace(root, { name, metamodel, metamodelFile })` (`src/workspace/init.ts`); the command passes the shipped standard model as `metamodelFile`:

- `path` is resolved against the root of the call (`localPath`: the CLI passes it absolute, API and MCP relative to the root). It must be an existing folder (`file.folder-missing`, `input.invalid` for a file). A folder or metamodel folder in a `.git` folder, in any case and through links, is `input.invalid` with `reason: git-folder` before anything is written (`refuseGitAt`, D-036, #1449). Other files in it are fine (a fresh clone has `.git`), but `reqseq-workspace.yaml` and the metamodel file must not exist (`file.changed-on-disk`); nothing is written then. On the command line and in the app `path` is not confined to the root of the call: an absolute path, or one with `..`, creates the workspace wherever the process may write. Through API and MCP it must lie inside the repositories of the workspace the server serves, or inside its root when that has no workspace file yet (SR-142, ADR-0009 "Local paths").
- It writes `<metamodel path>/standard-model.yaml` (default folder `metamodel`, created by `createFolder` of the files block; `.` is the root) and then `reqseq-workspace.yaml`: `name`, one repository named after the folder (`repositoryNameFor`: `Weather Station` becomes `weather-station`, `main` when nothing is left), `url: ""` for the person to fill in, and the metamodel location; last, the lines `*.reqseq-tmp` and `.reqseq/local.yaml` in `.gitignore` of the folder (SR-014 AK1; created, or the missing lines appended in one write with the file's own line ending; a linked `.gitignore` is left alone; #271, #1456), so temp files left by a crash and the local file are not committed. The workspace file is checked against `workspace.schema.json` before anything is written (`input.invalid` with `details.errors`). If the workspace file then cannot be written, the error keeps its code and names the metamodel file that was written before it (message and `details.written`); it is left in place.
- `metamodel.repository` naming another repository (SR-018) lists it in the workspace file with `url: ""` and its default path; nothing is written outside the folder, so that repository keeps (or gets) its own metamodel.
- Output: `files` (written, relative to the new root) and `problems`, the layout and metamodel problems of the new workspace as opened afterwards (none for the standard model). When the root of the call is the new folder (compared with links resolved), its layout state is reset. No Git command runs (D-036).

## Recent workspaces (SR-131, `src/workspace/recent.ts`)

The workspaces the app opened last, for its "Open workspace": `<OS cache>/reqseq/recent-workspaces.json` (`recentWorkspacesFolder`, next to the cache folders of the copies; `schemas/recent-workspaces.schema.json`, ADR-0008), `{ format: 1, workspaces: [{ root, key, opened }] }`, the most recent first, at most 20 (`RECENT_WORKSPACES_KEEP`).

- `rememberWorkspace(root, { now, key, environment })` puts an absolute root first as opened now (a root or key with NUL or more than 4096 characters is skipped); the entry with the same `key` goes (`workspaceKey`: `canonicalRoot`, so two names of one folder are one entry, and the stored `root` keeps the newest spelling). Read, change and write run under `lockCacheFile`; while another process holds the lock it waits once (200 ms) and then skips (`false`). It writes with `writeCacheFile` (mode 0600); the oldest entries are left out while the file would exceed 64 KiB. A failing write rejects.
- `readRecentWorkspaces()` reads with `readCacheFile(…, 64 KiB)` and never resolves a root again (the `key` is stored): content that is not JSON, of another format, with an entry of the wrong shape (also a root or key with NUL or longer than 4096 characters) or larger than 64 KiB is the empty list, and the next record overwrites it. `readCacheFile` with a size bound opens without waiting (`O_NONBLOCK`) and reads only a file: a FIFO or a device at the path is no content. It never rejects.
- `createBoundedRunner(slots)` runs file-system jobs with at most `slots` at once and a timeout per call (`"timeout"`; a job still waiting then never starts, and a running one learns it through `expired()`); a slot is freed only when its job settles. `createExistenceChecker({ stat, timeoutMs, slots })` is built on it and answers whether `<root>/reqseq-workspace.yaml` is a file, for the root itself, never a folder above it. At most 2 `stat`s run at once across all calls of a checker; a slot is freed only when its `stat` returns; 1 s after the call every root without an answer is `"timeout"` (missing wherever only existence counts), and a root still waiting for a slot gets no `stat`. A hung share or automount therefore never takes more threads of the thread pool than a checker has slots. A process has three checkers (`createWorkspaceChecks`): `recentWorkspaceStates()` (the list with `exists`) uses the one for the list, `workspaceExists(root)` the one for a chosen root, with one slot of its own, so roots of the list that hang cannot keep a local workspace from opening, and `findTypedWorkspace` the one for typed paths, with one slot of its own, so a typed path on a dead mount blocks only further typed paths (at most 4 `stat`s at once in all).
- `typedWorkspaceFolder(text, { platform, home })` (`localFolder` of `src/workspace/path-text.ts` without a base) is the lexical check of a path typed in "Open workspace" (SR-131 AK5), before any file-system call: `~` and `~/…` are the home folder; a relative path, NUL, more than 4096 characters and on Windows any path that is not on a drive (`C:\…`) after `~` is expanded and the path normalised (UNC, `\\?\`, `\\.\`, the NT prefix `\??\` also written `/??/`, a UNC home folder, and `\foo` on the current drive) and Windows device and stream names (`CON`, `nul.txt`, `a:b`) are refused (`undefined`), because checking such a path could make Windows connect to the host (SR-078). The result is normalised by its text and has no separator at its end. `findTypedWorkspace(folder)` then finds the nearest folder from it upwards whose `reqseq-workspace.yaml` is a file (as `--workspace` of the CLI), with the checker for typed paths, or `undefined`; a folder whose check timed out ends the walk with `undefined`, so a slow folder never opens a workspace above it.
- `recordOpenedWorkspace(workspace, options)` (`src/model/recent-record.ts`) is what the app's core process calls once a workspace is open: it records the root unless the folder of the list lies inside a repository of the workspace (`insideRepository` of the model cache, the rule of `usableCacheFolder`), so the file never lands in a working tree (D-036).
- The module has its own entry, `@reqseq/core/recent-workspaces`: the app's main process imports it lazily, and it loads only `node:*`, `cache.ts`, the private-file modules of the files block and `workspace-file.ts` (no schema validator, no command). It makes no synchronous file-system call on reading.
- CLI, API and MCP never record; they read the list with the read command `workspace.recent` (`src/commands/workspace/recent.ts`, SR-080 AK4, assumption of spec question ThomasBirkmaier/ReqSeq-archive#522): `recentWorkspaceStates()` of the process environment as `{ workspaces: [{ root, opened, exists }] }`, without `key`. It does not use the workspace of the call (ADR-0002 rule 7), so it gives the same list from any folder.

## `~` in the app (SR-143 AK2)

- The app has no shell that expands `~`, so its local path rule (`appLocalPaths`, `src/workspace/local-paths.ts`) carries the home folder (`LocalPaths.home`), and `invoke` replaces a leading `~`, `~/` (and `~\` on Windows) of every `localPath` field of an `app` call with it before the command runs (`replaceLocalPaths`, `expandHome` of `path-text.ts`). The command line keeps `~` as it gets it (its shell expands it), and API and MCP refuse it (SR-142).

## List folder (SR-143, `src/workspace/list-folder.ts`, `src/commands/workspace/listFolder.ts`)

The entries a path argument of the app's command prompt is completed with (ADR-0002 rule 1).

- `listTypedFolder(text, { files, home?, base?, check?, platform })` splits the typed text at its last separator (`splitTypedPath`: `/`, and `\` on Windows only): the part before names the folder, the rest is the typed `name`. The folder is checked by its text (`localFolder` of `src/workspace/path-text.ts`, the rules of `typedWorkspaceFolder`; with a `base` a relative path is resolved from it, without one only an absolute path is taken; `~` is home only with a `home`, else an ordinary name; a share the base already lies on stays allowed). A refused text gives `problem: "invalid"` without any file-system call. Then `check(folder)` runs (the command passes `ctx.localPaths.check`, so API and MCP list only inside the repositories, SR-142) and `listFolder` lists it.
- `listFolder(folder, { files, dots })` reads the entries with `opendir` and nothing else: no `stat`, no link followed (SR-078, SR-142), so a link is kind `link`, whatever it points to (on Windows every reparse point: junctions, OneDrive and Cloud Files placeholders, deduplicated files, app execution aliases); sockets and devices are left out, files only with `files`, names starting with "." only with `dots` (the typed name starts with "."). Order: folders and links, then files, each by the code units of the NFC form; names keep the spelling on disk. At most 50,000 (`truncated`; folders and links first, then the files read first). `opendir` reads 1,024 entries per call, and the NFC sort key is computed once per entry (SR-143 AK5). `ENOENT` is `missing`, every other error (`ENOTDIR`, `EACCES`, `EPERM`, `EIO`) and no answer within 1 s `unreadable`. It runs in one bounded slot of its own per process (`createBoundedRunner(1)`), so a hung share blocks only further listings: one hung listing makes every later listing of that process `unreadable` until it returns. The app's main process can use the slot for typed paths instead (`typedPathRun`, `WorkspaceChecks.typedRun`), so it takes no fifth thread. Known limit: where the file system gives no entry type with the names (`DT_UNKNOWN`: NFS without readdirplus, some FUSE file systems, XFS without `ftype`), Node finds it with a synchronous `lstat` per entry on the event loop, outside the slot and the timeout (never through a link).
- `workspace.listFolder` gives `{ folder?, name, entries: [{ name, kind }], problem?, truncated? }`; a relative `path` (a plain text, not a `localPath`, so the CLI keeps its trailing separator) is resolved from the workspace root on every access; `~` is home with `absolute` (every access) and otherwise where the path arguments of the access take it so (`ctx.localPaths.home`: the app), so a suggestion and the file a command then writes agree. The module has its own entry, `@reqseq/core/list-folder`, for the app's main process (only `node:*`, `path-text.ts` and `recent.ts`).

## About ReqSeq (SR-161, `src/commands/tool/info.ts`, `src/build-info.ts`)

- `tool.info` (title "About ReqSeq"; CLI `reqseq tool info`, MCP `tool_info`) gives the versions of app, CLI and MCP server (the one product version, AK4), the build, the runtime, the open workspace (root, name, repository names, number of elements in the available repositories, no view), the licence notice (`LICENSE`, embedded in `generated/product.json` by `pnpm contracts:generate`) and the addresses of the documentation and the releases as text (AK2: no network).
- Commit and build date come from `dist/build-info.json`, which `scripts/package/stage.mjs` writes into each staged core (`writeBuildInfo`; the date is the commit date). A checkout build has none: `build.development: true`, and the delivery files (`license.thirdParty`, `documentation.bundled`) are left out. `bundled` names the documentation site of the delivery, `cli/docs` in its resources folder (SR-141, ADR-0014), which `reqseq serve docs` serves.
- The runtime is `process.versions` of the calling process. The app's core process and the delivered CLI, API and MCP server run on the delivery's Electron (`ELECTRON_RUN_AS_NODE`, ADR-0014), so they give the same `electron`, `node` and `chromium` (AK5); on plain Node `electron` and `chromium` are left out.

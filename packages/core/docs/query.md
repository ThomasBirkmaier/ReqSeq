# Query block (`src/query/`)

Part of the [`@reqseq/core` README](../README.md).

The filter conditions (SR-069), saved filters (SR-070), the selection of a command (SR-101), the evidence provider the filter asks (#81) and the full-text search index (#323, SR-068). It imports the model, metamodel, variants, evidence, files and workspace blocks; `element.list`, `element.bulkUpdate`, `element.search`, `filter.save` and `filter.list` use it now. Semantics and measurements: ADR-0008 "Filter and selection" and "Search".

- `compileWhere(context, condition, at)` (`condition.ts`): compiles a `filter.schema.json#/$defs/condition` once into a predicate on element records plus `notes` (`incomplete`); `at` is the path of the condition in the input (`selection.where`), which every `input.invalid` names in its message and `details.fields`. Operators: `all`, `any`, `not`; `type` (with subtypes unless `subtypes: false`), `status`, `invalid`, `package`, `validFor`, `source` and property conditions (`property.ts`); relation conditions (`relation.ts`: `up` through `targetState`, `down` through `incomingFor`, `evidence` through the provider); `verification`, `validation`; `text` (SR-068): the elements `element.search` finds for the query (`searchIndex`, `matchingKeys`, by repository and file). `emergent` (SR-035): `isEmergent` of `model/emergent.ts`, the mark the output and the status use; a new operator is one more branch in `compileLeaf`, and the compiler refuses a schema operator without one (`never` check, #336). A compiled condition is for one run: it holds the states it was compiled against and its `notes` only gain `incomplete`, so #82 and #83 compile again per run and never keep one. The short semantics of each operator are in the descriptions of `filter.schema.json`, which agents read in the MCP tool schemas.
- `resolveSelection(workspace, selection, command)` (`selection.ts`): the elements of `ids`, `filter`, `where`, `package` and `view` (the view rule `viewRuleOf` of the [variants block](variants.md)) together, in store order, with `incomplete` (SR-006 AK2), the states it read and the saved filter (`filter`, for its sort), for the output. `filter` names a saved filter (`savedFilterFor`): its `where` and its `view` hold like the other parts; its `verification` conditions without `variant` take its own view, else the selection's, and the selection's `where` the selection's view, else the filter's. `element.list` without `sort` uses the filter's sort. Sort key `identifier` (#418, `query/sort.ts`) orders by the property with the meaning `identifier` with digit runs as numbers (SR-9 before SR-10), elements without one after by short ID; `element.list` without `sort` keeps the workspace order, the app sends `type` and `identifier` as its default. An error in a hand-written filter file names the filter and its file (`inSavedFilter`, the code stays); an unknown name is `input.invalid` at `selection.filter`, a name only a faulty file holds `file.faulty`. `baseline` is taken only by a command that opts in (`resolveSelection(…, command, { baseline: true })`, `SelectionOptions`; so far `data.export`, SR-061 AK2, and `data.store`, SR-062): the elements the baseline file lists, as they are now (`Baseline.selects`, [baselines block](baselines.md)), found by `findBaseline`; none is `input.invalid` at `selection.baseline` (with the reason when the baselines folder is not on this machine), a name two files share too, a text that names only a faulty file `file.faulty`. Every other command refuses it with `input.invalid` naming itself and stage 5, until #530 Q4 decides what a baseline means for it; `baseline.create` refuses it for good (SR-050).
- Saved filters (`saved.ts`, SR-070, D-056): `readSavedFilters(layout)` reads every `*.yaml` file directly in the `filters` location of the workspace file (default `filters` in the main repository; `reqseq-workspace.yaml` is never one), on every call, so a filter another person committed is there at once (AK2). A file that does not parse (files block problems) or match `filter.schema.json` (`filter.invalid`, readable messages as for inputs, with the line), and a `.yml` file (`filter.invalid`, warning), is reported and not listed; a faulty file whose `name` can still be read holds that name (`faultyNames`). Names compare ignoring case and normal form (`fold`, spec-frage #363); the first file in file order with a name is that filter, a later valid one `filter.duplicate-name` (warning). `incomplete` while the folder's repository is not on this machine. `findSavedFilter`, `newFilterFile(name, entries)` (the name's letters and digits, lower case, accents dropped, `-` between, at most 64 characters, `-2`, `-3` ... while an entry of the folder has the name ignoring case; Windows device names get `-filter`). Filters are not elements: nothing is deleted, moved or renamed.
- `canonicalCondition(context, condition, at)` and `canonicalView` (`canonical.ts`): a compiled condition as `filter.save` writes it: element references as UUIDs (`package`, `validFor`, `variant`, the view, values of keys that hold relations, also inside `relation.to`), choices given by display name as keys (product owner's note on #82).
- `evidenceStatusState` (`evidence.ts`): the evidence provider (`EvidenceStatuses`: `verification(element, view)`, `validation(element)`, `hasEvidence(element, view)`, and `ready()`, which the conditions `verification` and `validation` await once in `compileEvidence` before they ask: it reads the current versions of every element with records in one batch, `prepare(store.elements, { own: true })`, again after a failed read; `hasEvidence` needs none, so the condition without evidence reads no element file, #439; a test's provider may leave `ready` out). The verification status comes from the evidence records and, for a requirement without own record, from its children (`indirect`, SR-031, SR-034; the evidence block's `verificationState`, shared with `element.get` and `evidence.status`, [evidence-status.md](evidence-status.md)); `hasEvidence` is `hasVerificationRecord` in the view of the selection, else the core; the validation status comes from the validation records of the core (SR-038, the same state): every need has one, any other element only with a validation record (#534). While the metamodel is not valid nothing has evidence and `ready` reads nothing. Tests give records through `evidenceRecordsState` or replace the state with a provider (`workspace.replace`, #127 option 1).
- `searchIndexState` / `searchIndex(workspace)` (`search-state.ts`): the `SearchIndex` of the workspace's store (MiniSearch 7.2.0 over title, visible text and property values; IDs matched against the records), built in slices of 5 ms that pause while a command runs (`Workspace.busy`, `Workspace.runCommand` from `invoke`) unless a search waits (`searchIndex`), stopped when the workspace closes or the state is reset, carried over saves and watcher batches (`carrySearchIndex`: the documents of the changed files removed exactly and replaced in the same MiniSearch object, never vacuumed; more than `SEARCH_CARRY_LIMIT` UUIDs build it again), reset with the metamodel or layout. A one-shot process uses `search.json` in the cache folder (`search-cache.ts`: header with format, code fingerprint, root and `searchDigest`, used only as a whole); a server builds it in the background a second after its warm-up (`warmSearchIndex`, from `warmWorkspace` in `src/runtime/warm.ts`) and never uses the cache.
- `searchElements(index, query, options)` (`search-index.ts`): `SearchResults` (`total`, one page of `SearchHit`: record, score, fields, matched terms) for a query of words (AND by default; fuzzy from 4 letters and never for a query word with a digit, prefix from 2, any case and Unicode form; type and status by name) and IDs (short ID, identifier (#305) or at least 6 hex digits of a UUID, exactly); `within` restricts it to records of the selection of a view or filter (by repository and file, SR-068 AK3, SR-088), `fields` to some fields. `matchingKeys(index, query)`: the keys of every hit, for the condition `text`.
- Command `element.search` (`src/commands/element/search.ts`, SR-068): the selection first, then `searchIndex` and the search in the same turn; one page of hits (UUID, repository, short ID, identifier, type, status, title, score, fields, terms), `total`, `incomplete`; waits for a build that runs (ADR-0008 "Search").
- `groupingOf(selected, command, by)` (`group.ts`) and `orderedGroups` (`ordered.ts`), `element.list` `group` (SR-149): the groups of a selection by `type` (as written), `status`, `package` (the available targets of the property with the meaning `packages`) or a property whose values `element.facets` offers (`offersValues` of `facets.ts`, with its default threshold `FACET_MAX_VALUES`: choice and relation properties, text, number and date with few shared values, so a topic but not a title); any other key is `input.invalid` at `group`, a relation kind with its own message. For text, number and date this follows the data of the workspace, so the same key can become `input.invalid` as the data changes. Relation items are read as `element.facets` and `property eq` read them (`valuesOf`, whatever `many` says), not by `many` as the condition `package` does: the two differ only for a value of the wrong shape. An item that names no element is no value; one whose target is not found counts as `unavailable`. An element is in the group of each of its values (AK2; a choice written by its display name in that choice's group), without one in the last group, which also takes elements whose targets are all not available and counts them (`unavailable`). A status written as a list is no status here, as for the status filter and the facets. Groups come in the order the sort ranks their values (`sortValueOf` and `compareSortValues` of `sort.ts`: metamodel order, then numbers, texts ignoring case, booleans); packages and other targets, which are no sort key, by title ignoring case, then short ID, as `element.facets` gives them (spec-frage #978). `sortGroups` (`sort.ts`) sorts the selection once and deals it into the groups in that order (AK3); under `hierarchy` each group is a tree of its own elements, built from the rows sorted once, with the parents looked up among the group's rows by store position, so the store is walked once and not once per group (N-036). `element.list` gives the page of the grouped list (an element once per group: `listElements` runs on the page's distinct records, then the rows are laid out again), `groups` with value, name, count and first row, `offset` and `rows`. Nothing is written (AK5).
- `element.list` `fields` (#982, `src/commands/element/list.ts`): the page in `partial` instead of `elements` (`data-export.schema.json#/$defs/elementPart`), each element with the fields asked for and always `id`, `shortId`, `repository` and its `problems` (`partOf`), plain, grouped or as a tree alike. `text` in `fields` or `withText` gives the text; the relations are looked up only when `relations` is asked for (`listElements` with `withRelations: false`), the larger part of the cost of a page. The other fields are built and then left out.
- `facetsOf(selected, maxValues)` (`facets.ts`) and command `element.facets` (`src/commands/element/facets.ts`, #425, SR-069, SR-124, SR-118): one pass over the selection counts `types`, `statuses` and the values of the properties (details in the file comment). `types` (SR-118: the overview of the app) are the types as written in the files, each element once under exactly its own type (a subtype is not added to its parent, so the lines add up to `total`; the list of a line is `{ type: [key], subtypes: false }`): types of the metamodel in metamodel order with their name, then other keys in store order (name = key, any non-empty string, since a file may hold one the metamodel does not know); a type without a selected element is not listed. The type tally is one map update in the existing loop; the 50,000-element budget of `facets({})` (500 ms, `test/perf/element-facets.test.ts`) covers it.

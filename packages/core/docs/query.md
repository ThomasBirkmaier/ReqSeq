# Query block (`src/query/`)

Part of the [`@reqseq/core` README](../README.md).

The filter conditions (SR-069), saved filters (SR-070), perspectives (SR-213), the selection of a command (SR-101), the evidence provider the filter asks (ThomasBirkmaier/ReqSeq-archive#81) and the full-text search index (ThomasBirkmaier/ReqSeq-archive#323, SR-068). It imports the model, metamodel, variants, evidence, files and workspace blocks; `element.list`, `element.bulkUpdate`, `element.search`, `filter.save`, `filter.list`, `perspective.save` and `perspective.list` use it now. Semantics and measurements: ADR-0008 "Filter and selection" and "Search".

- `compileWhere(context, condition, at)` (`condition.ts`): compiles a `filter.schema.json#/$defs/condition` once into a predicate on element records plus `notes` (`incomplete`); `at` is the path of the condition in the input (`selection.where`), which every `input.invalid` names in its message and `details.fields`. Operators: `all`, `any`, `not`; `type` (with subtypes unless `subtypes: false`), `status`, `invalid`, `package`, `validFor`, `source` and property conditions (`property.ts`); relation conditions (`relation.ts`: `up` through `targetState`, `down` through `incomingFor`, `evidence` through the provider); `verification`, `validation`; `text` (SR-068): the elements `element.search` finds for the query (`searchIndex`, `matchingKeys`, by repository and file). `emergent` (SR-035): `isEmergent` of `model/emergent.ts`, the mark the output and the status use; a new operator is one more branch in `compileLeaf`, and the compiler refuses a schema operator without one (`never` check, ThomasBirkmaier/ReqSeq-archive#336). A compiled condition is for one run: it holds the states it was compiled against and its `notes` only gain `incomplete`, so ThomasBirkmaier/ReqSeq-archive#82 and ThomasBirkmaier/ReqSeq-archive#83 compile again per run and never keep one. The short semantics of each operator are in the descriptions of `filter.schema.json`, which agents read in the MCP tool schemas.
- `resolveSelection(workspace, selection, command)` (`selection.ts`): the elements of `ids`, `filter`, `where`, `package` and `view` (the view rule `viewRuleOf` of the [variants block](variants.md)) together, in store order, with `incomplete` (SR-006 AK2), the states it read and the saved filter (`filter`, for its sort), for the output. `filter` names a saved filter (`savedFilterFor`): its `where` and its `view` hold like the other parts; its `verification` conditions without `variant` take its own view, else the selection's, and the selection's `where` the selection's view, else the filter's. `element.list` without `sort` uses the filter's sort (with a perspective, see Perspectives below). Sort key `identifier` (ThomasBirkmaier/ReqSeq-archive#418, `query/sort.ts`) orders by the property with the meaning `identifier` with digit runs as numbers (SR-9 before SR-10), elements without one after by short ID; `element.list` without `sort` keeps the workspace order, the app sends `type` and `identifier` as its default. An error in a hand-written filter file names the filter and its file (`inSavedFilter`, the code stays); an unknown name is `input.invalid` at `selection.filter`, a name only a faulty file holds `file.faulty`. `baseline`, for every command that takes a selection (SR-101, #1353; "as they are now" is SR-061 AK2 for the export and, for the others, the answer to ThomasBirkmaier/ReqSeq-archive#530 Q4): the elements the baseline file lists, as they are now (`Baseline.selects`, [baselines block](baselines.md)), found by `findBaseline`; none is `input.invalid` at `selection.baseline` (with the reason when the baselines folder is not on this machine), a name two files share too, a text that names only a faulty file `file.faulty`. The versions at the baseline are what `baseline.get` shows (SR-051); `baseline.create` refuses it, since a baseline is not made of another one.
- Saved files (`saved-files.ts`, D-056): one reader (`readSavedFolder(layout, kind)`), lookup (`findSaved`, `faultySaved`), error wrapper (`inSavedFile`) and writer (`writeSaved(layout, kind, data, editsOf)`) for the folders of named YAML files the user saves, by `SavedKind` (setting, schema, label, word of new file names, problem codes): saved filters and perspectives. `writeSaved` refuses a name only a faulty file holds (`file.faulty`) and a missing repository (`file.folder-missing`), edits an existing file in place with the caller's edits (`file.changed-on-disk` when it changed since it was read), and checks each file with `refuseGitPlace` before it writes it.
- Saved filters (`saved.ts`, SR-070, D-056), the `FILTERS` kind of `saved-files.ts`: `readSavedFilters(layout)` reads every `*.yaml` file directly in the `filters` location of the workspace file (default `filters` in the main repository; `reqseq-workspace.yaml` is never one), on every call, so a filter another person committed is there at once (AK2). A file that does not parse (files block problems) or match `filter.schema.json` (`filter.invalid`, readable messages as for inputs, with the line), and a `.yml` file (`filter.invalid`, warning), is reported and not listed; a faulty file whose `name` can still be read holds that name (`faultyNames`). Names compare ignoring case and normal form (`fold` in `fold.ts`, which the app imports as `@reqseq/core/fold` to key perspective buffers the same way; spec-frage ThomasBirkmaier/ReqSeq-archive#363); the first file in file order with a name is that filter, a later valid one `filter.duplicate-name` (warning). `incomplete` while the folder's repository is not on this machine. `findSavedFilter`, `newFilterFile(name, entries)` (the name's letters and digits, lower case, accents dropped, `-` between, at most 64 characters, `-2`, `-3` ... while an entry of the folder has the name ignoring case; Windows device names get `-filter`). `filter.save` checks the file right before it writes it (`refuseGitPlace`, [workspace block](workspace.md)), so it never writes into Git, also when the workspace file places the filters folder there: `input.invalid` with `reason: "git-folder"` (D-036, SR-083 AK4). Filters are not elements: nothing is deleted, moved or renamed.
- Perspectives (`perspectives.ts`, SR-213, D-056), the `PERSPECTIVES` kind of `saved-files.ts`: `readPerspectives(layout)` reads the `perspectives` location of the workspace file (default `perspectives` in the main repository) as saved filters are read, with `perspective.schema.json` (no `view`), `perspective.invalid` and `perspective.duplicate-name`. Their names are their own: a saved filter may have the same name. `perspective.save` checks `where` and `sort` as `filter.save` does, `group` with `checkGroupKey` (`group.ts`: the rule of `element.list` over the whole workspace) and `filter` against the saved filters, and keeps a `description` the input leaves out (an empty one removes it). `workspace.check` does not check perspectives. `element.list` `perspective` (SR-213 AK4 to AK7): `perspectiveFor` finds it by name (unknown: `input.invalid` at `perspective`; only a faulty file: `file.faulty`) and `perspectiveFilterFor` its saved filter, both read on every call (AK6; a missing filter `input.invalid` at `perspective`, a faulty one `file.faulty`, each naming perspective and filter). `resolveSelection` takes them as `stored`: the perspective's `where` and its filter hold beside the selection, the filter's `view` holds, its `where` in its own view, else the selection's, and the perspective's `where` in the selection's view (its own, else its saved filter's, as the selection's `where`), else its filter's, else the core; errors name the perspective and its file (`inPerspective`). `orderedSelection` and `orderedGroups` without `sort` take the first stored sort of the selection's filter (the input's sort, above the perspective's, SR-213 AK5), the perspective, its filter, also an empty one, else workspace order. The input `group` replaces the stored one; a stored `group` by a property `groupUnavailable` finds (`group.ts`: a property of the metamodel whose values `offersValues` no longer offers over the whole workspace) gives the list without groups and the warning `perspective.group-unavailable` in `problems` (AK7), any other stored key the error of `groupingOf`, naming the perspective.
- `canonicalCondition(context, condition, at)` and `canonicalView` (`canonical.ts`): a compiled condition as `filter.save` writes it: element references as UUIDs (`package`, `validFor`, `variant`, the view, values of keys that hold relations, also inside `relation.to`), choices given by display name as keys (product owner's note on ThomasBirkmaier/ReqSeq-archive#82).
- `evidenceStatusState` (`evidence.ts`): the evidence provider (`EvidenceStatuses`: `verification(element, view)`, `validation(element)`, `hasEvidence(element, view)`, and `ready()`, which the conditions `verification` and `validation` await once in `compileEvidence` before they ask: it reads the current versions of every element with records in one batch, `prepare(store.elements, { own: true })`, again after a failed read; `hasEvidence` needs none, so the condition without evidence reads no element file, #439; a test's provider may leave `ready` out). The verification status comes from the evidence records and, for a requirement without own record, from its children (`indirect`, SR-031, SR-034; the evidence block's `verificationState`, shared with `element.get` and `evidence.status`, [evidence-status.md](evidence-status.md)); `hasEvidence` is `hasVerificationRecord` in the view of the selection, else the core; the validation status comes from the validation records of the core (SR-038, the same state): every need has one, a requirement only with a validation record, no other element (SR-038 AK5). While the metamodel is not valid nothing has evidence and `ready` reads nothing. Tests give records through `evidenceRecordsState` or replace the state with a provider (`workspace.replace`, ThomasBirkmaier/ReqSeq-archive#127 option 1).
- `searchIndexState` / `searchIndex(workspace)` (`search-state.ts`): the `SearchIndex` of the workspace's store (MiniSearch 7.2.0 over title, visible text and property values, and one field per property a search can be restricted to, `property:<key>` (`searchPropertyKeys`, SR-216); IDs matched against the records), built in slices of 5 ms that pause while a command runs (`Workspace.busy`, `Workspace.runCommand` from `invoke`) unless a search waits (`searchIndex`), stopped when the workspace closes or the state is reset, carried over saves and watcher batches (`carrySearchIndex`: the documents of the changed files removed exactly and replaced in the same MiniSearch object, never vacuumed; more than `SEARCH_CARRY_LIMIT` UUIDs build it again), reset with the metamodel or layout. A one-shot process uses `search.json` in the cache folder (`search-cache.ts`: header with format, code fingerprint, root and `searchDigest`, used only as a whole); a server builds it in the background a second after its warm-up (`warmSearchIndex`, from `warmWorkspace` in `src/runtime/warm.ts`) and never uses the cache.
- `searchElements(index, query, options)` (`search-index.ts`): `SearchResults` (`total`, one page of `SearchHit`: record, score, fields, matched terms) for a query of words (AND by default; fuzzy from 4 letters and never for a query word with a digit, prefix from 2, any case and Unicode form; type and status by name) and IDs (short ID, identifier (ThomasBirkmaier/ReqSeq-archive#305) or at least 6 hex digits of a UUID, exactly); `within` restricts it to records of the selection of a view or filter (by repository and file, SR-068 AK3, SR-088), `fields` and `propertyKeys` to some fields and single properties (SR-216: only their words find and rank a hit, an ID match comes first only with `id`, and a word that can match nothing there finds nothing). `matchingKeys(index, query)`: the keys of every hit, for the condition `text`.
- `searchFieldsOf(command, metamodel, fields)` (`search-fields.ts`, SR-216 AK2): `element.search` `fields` as search options: `title`, `text`, `properties`, `id` are always the fixed fields, any other name the key of a single property of `searchPropertyKeys`; `properties` beside single properties is `properties`. `type`, `status`, the title's key, a key that holds relations and a key the metamodel does not know are `input.invalid` at `fields`, naming the key, the title's key with a hint to `title` (SR-216 AK2). `searchFieldChoices(metamodel, store)` and command `element.searchFields` (`src/commands/element/searchFields.ts`, SR-216 AK3): the fields a search can be restricted to, each with key and name: title (the title property's name, "Title" without one), text, IDs, all properties, then the keys of `searchPropertyKeys` that an effective type of the store's elements has, in metamodel order; the set of types is kept per store, the rest built from the metamodel on each call.
- `searchSnippet(index, hit, propertyKeys?)` and `titleMarks(title, terms)` (`search-snippet.ts`, SR-174): the snippet of a hit, one line of at most 120 code points around the first visible match in reading order (the text, then the property values: the type's properties in metamodel order, then the other keys in file order; each list item and nested value on its own; a choice by its name), with the matched words marked (UTF-16 offsets); a choice found by its key shows its name; none for a match only in the title, an ID, type or status; with `propertyKeys` only those properties are read (SR-216 AK5). Only the line of the raw match is parsed with mdast (with the lines a hard-wrapped link or emphasis spans, GFM only when needed, link destinations left out, the labels of `markdownDefinitions` added), its block (`markdownBlocks` of `model/markdown-links.ts`) deciding whether it is code, a table row or HTML; it reads the file of a hit found in its text (`elementNow` of `search-index.ts`), synchronously.
- Command `element.search` (`src/commands/element/search.ts`, SR-068, SR-174, SR-216): the selection first, `fields` checked against its metamodel, then `searchIndex` (and `fields` checked against the index's metamodel) and the search in the same turn; one page of hits (UUID, repository, short ID, identifier, type, status, title, score, fields, terms, title marks, snippet), `total`, `incomplete`; waits for a build that runs (ADR-0008 "Search"). With `group` (SR-149 AK6), `rankedHits` puts every hit in order (scores rounded, one sort) and `groupingOf` runs over the hit records, so the groups are those of `element.list` for the same elements and each keeps the search order; `hits` is the page of the rows, `groups`, `offset` and `rows` as in `element.list`, and only the page's distinct hits are described (`describeHit`). The key is checked whatever the query finds. Targets are looked up in the selection's store: after a swap a package only in the newer one counts as not available. The hits take no sort (question #1076). Imported on its first call (`lazyCommand`), since the snippet needs the Markdown parser (#178); a server imports the snippet module once its index is built (`warmSearchIndex`).
- `groupingOf(selected, command, by)` (`group.ts`) and `orderedGroups` (`ordered.ts`), `element.list` `group` (SR-149): the groups of a selection by `type` (as written), `status`, `package` (the available targets of the property with the meaning `packages`) or a property whose values `element.facets` offers (`offersValues` of `facets.ts`, with its default threshold `FACET_MAX_VALUES`: choice and relation properties, text, number and date with few shared values, so a topic but not a title); any other key is `input.invalid` at `group`, a relation kind with its own message. For text, number and date this follows the data of the workspace, so the same key can become `input.invalid` as the data changes. Relation items are read as `element.facets` and `property eq` read them (`valuesOf`, whatever `many` says), not by `many` as the condition `package` does: the two differ only for a value of the wrong shape. An item that names no element is no value; one whose target is not found counts as `unavailable`. An element is in the group of each of its values (AK2; a choice written by its display name in that choice's group), without one in the last group, which also takes elements whose targets are all not available and counts them (`unavailable`). A status written as a list is no status here, as for the status filter and the facets. Groups come in the order the sort ranks their values (`sortValueOf` and `compareSortValues` of `sort.ts`: metamodel order, then numbers, texts ignoring case, booleans); packages and other targets, which are no sort key, by title ignoring case, then short ID, as `element.facets` gives them (spec-frage #978). `sortGroups` (`sort.ts`) sorts the selection once and deals it into the groups in that order (AK3); under `hierarchy` each group is a tree of its own elements, built from the rows sorted once, with the parents looked up among the group's rows by store position, so the store is walked once and not once per group (N-036). `element.list` gives the page of the grouped list (an element once per group: `listElements` runs on the page's distinct records, then the rows are laid out again), `groups` with value, name, count and first row, `offset` and `rows`. Nothing is written (AK5).
- `element.list` `fields` (#982, `src/commands/element/list.ts`): the page in `partial` instead of `elements` (`data-export.schema.json#/$defs/elementPart`), each element with the fields asked for and always `id`, `shortId`, `repository` and its `problems` (`partOf`), plain, grouped or as a tree alike. `text` in `fields` or `withText` gives the text; the relations are looked up only when `relations` is asked for (`listElements` with `withRelations: false`), the larger part of the cost of a page. The other fields are built and then left out.
- `withVerification` of `element.list` and `element.search` (SR-137): `rowVerification`, parallel to the rows (`elements`, `partial` or `hits`, so a grouped row repeats its entry), each the `verification`, `criteria` and `degree` the element's node in `trace.graph` carries, from `rowsVerification` (`evidence/graph-status.ts`, `graphVerification` over the page's distinct records) in the selection's view (`views[0]`, the core without one), the view `evidence.degree` counts the same selection in. A search reads its hits' records, which may be newer than the store of the verification state after a swap, until the next call. The first call on a workspace builds the shared `verificationState` (a few seconds at N-036), so the app asks for it after the rows stand. A superseded requirement keeps its status in its row, as its node does, though the degree does not count it (D-044).
- `facetsOf(selected, maxValues)` (`facets.ts`) and command `element.facets` (`src/commands/element/facets.ts`, ThomasBirkmaier/ReqSeq-archive#425, SR-069, SR-124, SR-118): one pass over the selection counts `types`, `statuses` and the values of the properties (details in the file comment). `types` (SR-118: the overview of the app) are the types as written in the files, each element once under exactly its own type (a subtype is not added to its parent, so the lines add up to `total`; the list of a line is `{ type: [key], subtypes: false }`): types of the metamodel in metamodel order with their name, then other keys in store order (name = key, any non-empty string, since a file may hold one the metamodel does not know); a type without a selected element is not listed. The type tally is one map update in the existing loop; the 50,000-element budget of `facets({})` (500 ms, `test/perf/element-facets.test.ts`) covers it.

# Checking the whole workspace (`workspace.check`, SR-019)

Part of the [`@reqseq/core` README](../README.md).

`src/commands/workspace/check.ts` collects, in this order: the problems of the workspace layout and of the metamodel, those of the element store (SR-008, unreadable and skipped files), then the whole-workspace states of `FINDING_STATES`: `requiredProblemsState` (SR-015), `unknownProblemsState` (SR-016), `statusProblemsState` (#306), `supersededTargetProblemsState` (SR-072), `supersededValidityProblemsState` (SR-040, variants block), `valueKindProblemsState` (SR-085), `relationTypeProblemsState` (SR-086), `duplicateIdProblemsState` (SR-088), `missingTargetProblemsState` (SR-089) and `derivationCycleProblemsState` (SR-090, trace block). A new whole-workspace finding joins by adding its state to `FINDING_STATES` (exported for tests that need every finding state). `ok` is false when a finding at or above `failOn` (default `error`, #304) exists, whatever `severity` shows (ADR-0009: CLI exit code 1); `severity` only filters the problems shown, and the findings it leaves out are counted in `hidden` (`below`, `warning`, `info`; only when it leaves out at least one). Problems are appended in a loop, never spread into `push`, so hundreds of thousands of findings do not overflow the stack (N-036). `changedFiles` and `changedSince` restrict the check to a merge request (SR-092, `model/changed.ts`, spec question #291): the changed elements (their file or an embedded image differs from the revision in the working copy, untracked files included, or the file is named) and their direct targets. A problem with an element is kept when its element is one of them or its target is a changed element; a problem with only a file when the file changed or belongs to one of them; the problems of the layout and the metamodel always. The revision is looked up in every available repository (`resolveCommit`, `changedPaths` of the git reader); a repository without it, or without Git, adds nothing and gets an `info` problem (`git.revision-missing`, `git.unavailable`), as does a folder below the top level of its work tree of which Git sees no file (nothing listed, and no tree at the folder in the commit, #377); none has it: `git.commit-not-found` (CLI exit code 4); any git failure in a repository: `git.unavailable`. The UUIDs the changed element files held at the commit count as changed too, so relations to a deleted element or an old UUID are kept. A folder in `changedFiles` is `input.invalid`. The outdated relations are restricted before `datedProblems`, so only the kept ones are dated.

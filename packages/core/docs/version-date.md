# Version date (`src/model/version-date.ts`)

Part of the [`@reqseq/core` README](../README.md).

`versionStarts({ workspace, layout, metamodel }, requests)` gives, for each (repository, file, element UUID, version), the committer date in UTC and the object name of the newest commit that started that version (the file held the element with it there, and no parent had it; of commits of one second, the one with the greatest object name, so the answer never depends on what else a call walks, #252), or `null`; `versionDates` gives only the dates (ADR-0005 "Version date": which commits count, starts, how embedded images count at an old commit, when there is no date). One walk per (repository folder, file, UUID) and HEAD lists the commits that changed the file or an image its texts embed, and the merges whose sides do not all lead to the same evaluated commit (`log` is asked for the folders of these paths, the paths are picked from its answer) (`fileHistory` again when a text embeds an image not walked yet, or the file had an older path; ADR-0005 "Moves", #460: after each history read, `fileMoves` looks up what the commits that changed the file's paths moved, one `log` for all of them, and the walk follows each old path, so its paths depend on the history alone; a request with the current `text` walks its images from the start, as `element.get` does). Versions are computed lazily, newest commit first in growing rounds, until the asked version's newest start is certain; each round is one `info` and one `read` for the texts and the same for the image blobs, on one `openObjectReader` per call. The walks are a workspace state (`version-dates`, reset with the metamodel and the layout; reset or close stops their git processes); they stay while `headFiles` gives the same stamp or HEAD the same commit, and a new HEAD replaces the walks of its repository. A walk git could not finish because it timed out, was stopped or is missing is dropped; one Git refused for another reason stays `null` until HEAD moves. A call waits for its walks (no time limit besides those of the git calls), so the same request gives the same answer at the same HEAD (D-029). `prepareVersionDates(context, walks)` starts the walks without waiting, so `element.get` with `versionDate` lets git read the history while it builds the view. A repository folder without a `.git` entry in it or above it starts no process; one below the top level of its work tree gets the dates of that repository (#377).

`undatedCause(context, repository)` says why versions of a repository can have no date, for a message to name once (#252): `no-git` (not on this machine, no `.git` entry, no commit, or git missing or refusing where HEAD must be asked of git), `shallow`, or `unknown` (not committed, or a git call failed or timed out). It reads HEAD as the walks do (`headFiles`, else `headCommit`).

`metamodelChange(context)` gives the newest commit reachable from HEAD of the metamodel's repository that changed a file in the metamodel folder (one `fileHistory` for the folder), or `null` when Git cannot tell (as `undatedCause`, and also for a shallow clone), the folder is the repository itself, or no commit changed it (#252, P-2-09).

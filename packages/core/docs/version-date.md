# Version date (`src/model/version-date.ts`)

Part of the [`@reqseq/core` README](../README.md).

`versionStarts({ workspace, layout, metamodel }, requests)` gives, for each (repository, file, element UUID, version), the committer date in UTC and the object name of the newest commit that started that version (the file held the element with it there, and no parent had it; of commits of one second, the one with the greatest object name, so the answer never depends on what else a call walks, #252), or `null`; a version of either normal form (n1, n2) is dated in its own form, each evaluated commit's version computed in both (`elementVersions`, ADR-0005 "Normal form 2"), any other form is `null`; `versionDates` gives only the dates (ADR-0005 "Version date": which commits count, starts, how embedded images count at an old commit, when there is no date). One walk per (repository folder, file, UUID) and HEAD lists the commits that changed the file or an image its texts embed, and the merges whose sides do not all lead to the same evaluated commit (`log` is asked for the folders of these paths, the paths are picked from its answer) (`fileHistory` again when a text embeds an image not walked yet, or the file had an older path; ADR-0005 "Moves", #460: after each history read, `fileMoves` looks up what the commits that changed the file's paths moved, one `log` for all of them, and the walk follows each old path, so its paths depend on the history alone; a request with the current `text` walks its images from the start, as `element.get` does). Versions are computed lazily, newest commit first in growing rounds, until the asked version's newest start is certain; each round is one `info` and one `read` for the texts and the same for the image blobs, on one `openObjectReader` per call; from 500 names at one commit, one `commitBlobs` listing gives the blobs it has, and the reader answers the rest (and all of them where Git refuses the listing). From 100 walks open at one merge, one `firstParentChanges` lists what the merge changed against its first parent (#2382): a walk none of whose tracked paths it lists gets the version of its source on that side (none where that side has no file) without a read, where the walk's evaluated commits were read for its current tracked paths and that version is computed and known; the copied version keeps what `inNestedRepository` said where it was computed. Git that does not answer in time makes the call late; one that refuses `--diff-merges` (before 2.31) or fails, and a merge it does not print, leave the merge to be read. The walks are a workspace state (`version-dates`, reset with the metamodel and the layout; reset or close stops their git processes); they stay while `headFiles` gives the same stamp or HEAD the same commit, and a new HEAD keeps the facts the walks read from object names (texts, image hashes, versions, moves), which hold at any HEAD, and carries the walks over (SR-082 AK4, #2346): one `historyRange` of their folders lists the commits of `new ^old` with their real parents, and `commitsBetween` lists `old ^X` for each parent X outside the range other than the old HEAD (or for the new HEAD where the range is empty, a move back). An evaluated commit stays where some X reaches it (it is not in that list) and is dropped otherwise; the source of X is the one evaluated commit it reaches that no other one it reaches has as a parent source; the range is then evaluated from these sources as `evaluatedList` does, so an amend, a rebase, a merge of a branch from an older commit, a reset or a switch to another branch keep the walks. A walk keeps its answers where no evaluated commit came or went, since HEAD's source then stays. Only a settled walk is carried (its history read and no answer round holding it: `busy`), as a copy, so a call still running at the old HEAD changes nothing of it; a walk Git refused, one whose names a move in the range adds to, one with an old name that lost evaluated commits (the move that gave the name may be one of them), and every walk where the range or a list has more than 1,000 commits, the clone is shallow or Git refuses, are walked again. Calls that see the same move wait for one carry (`moving`), and a carry that ends after a later move of the folder leaves that move's walks; where Git cannot tell now (it refuses, does not answer in time or is missing), the walks are walked again. What `inNestedRepository` said when a version was computed stays with the carried versions. A walk whose history grows reads it again and drops the versions of the commits it no longer evaluates. A walk whose tracked paths grew since its history was read (a text embeds a new image path) answers nothing, kept or new, until that history is read again: a call waits for the read another call runs for the walk and reads it itself only where the paths grew again or that read failed and no other call started a newer read meanwhile (`fitWalks`, #2408). A walk git could not finish because it timed out, was stopped or is missing is dropped; one Git refused for another reason stays `null` until HEAD moves. A call waits for its walks (no time limit besides those of the git calls), and takes a walk that is settled without waiting (`settled`, kept beside its promise), so the same request gives the same answer at the same HEAD (D-029). A walk keeps the finished answer of each version (`dates`). `versionTimes(context, requests)` gives the time a sort by `versionDate` reads (SR-075), decided from HEAD first, whichever call came before: `dated` with the date of the start when the commit HEAD's file comes from (by the parents, not the committer dates) has the version, `uncommitted` when its version is known and another, or no commit has the file, whatever older commits Git could not tell (content that differs from the last commit counts as newer than every committed one; no older commit is read for it, and nothing of it is kept, so `versionStarts` still finds the start), `late` when a git call of the walk timed out or was stopped (the walk is dropped and asked again; also a `rev-parse` of HEAD that timed out), and `undated` otherwise (no Git or git missing, a shallow clone, a walk Git refused, a version of no normal form, or HEAD's version Git could not tell because it lacks a text or image blob). `prepareVersionDates(context, walks)` starts the walks without waiting, so `element.get` with `versionDate` lets git read the history while it builds the view. A repository folder without a `.git` entry in it or above it starts no process; one below the top level of its work tree gets the dates of that repository (ThomasBirkmaier/ReqSeq-archive#377).

`undatedCause(context, repository)` says why versions of a repository can have no date, for a message to name once (#252): `no-git` (not on this machine, no `.git` entry, no commit, or git missing or refusing where HEAD must be asked of git), `shallow`, or `unknown` (not committed, or a git call failed or timed out). It reads HEAD as the walks do (`headFiles`, else `headCommit`).

`classifyUndated(workspace, versions)` (`model/undated.ts`, SR-254) sorts the versions an output names without a date by repository: the first reason of SR-254 AK2 that holds (`missing`: not on this machine or no repository of the workspace; `unreadable`: no `.git` entry, git missing, refusing or finding no work tree, from `headCommit` and, where HEAD names no commit, `readsWorkTree`; `shallow`), none where git did not answer in time, and which are not committed (AK3): the element's current version (`currentVersionsOf`, `sameVersion`) in a repository git reads, by `versionTimes` (`uncommitted`) with a commit and the whole history, by `uncommittedFiles` of the element file and its images (byte by byte) in a shallow clone, and always without a commit. `undatedProblems` gives each warning once per repository: `version.uncommitted` with the number of elements, then `version.date-unavailable` with the reason for the other versions, or else `version.date-unknown` with their number; an element counts once. `undatedWarnings` does both; `element.get` and `element.resolve` (with `versionDate`), `baseline.get` (the page) and `html.export` (once for all pages) give them, `baseline.changes` and `baseline.prepare` leave them out (`UNDATED_CODES`, SR-241 AK6, SR-242 AK3). A sort by `versionDate` (SR-075 AK5, `versionTimesOf`) counts a version not committed in a shallow clone or a repository without a commit as newer than every committed one and gives only `version.date-unavailable` (`sortReasonProblems`). The hints keep their own reason text (`undatedCause`).

`metamodelChange(context)` gives the newest commit reachable from HEAD of the metamodel's repository that changed a file in the metamodel folder (one `fileHistory` for the folder), or `null` when Git cannot tell (as `undatedCause`, and also for a shallow clone), the folder is the repository itself, or no commit changed it (#252, P-2-09).

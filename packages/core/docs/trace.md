# Trace block (`src/trace/`)

Part of the [`@logreq/core` README](../README.md).

The derivation graph and the walk that the chain (SR-022), related elements (SR-023), affected elements (SR-024) and cycles (SR-090) share (#258). No command of its own; it imports the model, metamodel and workspace blocks, never `commands`.

- `traceContext(workspace)` reads layout, metamodel and store once and takes `incomingFor` of that store. `derivationGraph(context, command)` throws `metamodel.meaning-unassigned` naming `command` when no relation kind has the meaning `derivation` (`requireMeaning`, SR-013 AK3), and otherwise holds the kinds with that meaning (`relationKindsWithMeaning`; a property of the same key wins), never fixed keys.
- Direction (ADR-0004): the source of a derivation relation is the child, its target the parent. A `DerivationLink` is the child's relation in the shape of `IncomingRelation` (`source` = child, `key`, `index`, `item`; `relationPath` for its path). Inline references are not part of the chain.
- `parentsOf(graph, element)`: the element's own derivation items with `hasId`, each looked up with `targetState` (D-058). `available` is a step; any other state is `unresolved` with its state; `inaccessible` and `unknown-repository` make the expansion `incomplete` (SR-006 AK2), `missing` (SR-089) and `ambiguous` (SR-088) do not.
- `childrenOf(graph, element)`: the index's relations under a derivation key that point into the element's repository and UUID. While several files of that repository share the UUID (SR-088), each of them is `unresolved` with the state `ambiguous` (repository and the records), as `targetState` calls the same relation going up, so a chain shows the gap (SR-022 AK3). While the workspace file lists a repository that is not on this machine, every expansion down is `incomplete`: children there cannot be seen (assumption, spec question #262 option 1).
- `derivationEdges(graph)`: every derivation relation of the store as an edge from the child to the parent, when the parent is available (the one record of its UUID in the repository the relation points into), read from the index without a `targetState` each; `cyclesOf(store.elements, derivationEdges(graph))` gives the cycles of the whole store (SR-090).
- `walk(starts, expand, { maxDepth, leaves, maxNodes })`, `walkDerivation(graph, starts, { direction: "up" | "down", maxDepth, leaves })`: breadth first; `nodes` has each element once at its shortest depth (starts at 0, in the given order, then level by level) with `via`, the edge it was first reached through; `pathTo(result, element)` gives the edges from the start. `edges` holds every step in walk order, also into elements reached before; `cyclic` marks an edge inside a cycle. A start stays at depth 0 without `via`, also when another start leads to it (the edge is in `edges`). `maxDepth`: elements at that depth are reached but not expanded (`expanded` is false only for them, and for the elements beyond `maxNodes`, see Graph). `unresolved` lists `{ from, link, state }`; `incomplete` is set when any expansion says so. `leaves(element)` is called once per node (evidence of stage 4; default none).
- Cycles: the strongly connected components of the walked subgraph with more than one element or an edge to itself, each with its elements in node order and its edges in edge order. Back edges on the tree path are not enough (a cycle entered through a diamond is missed). The vertices without an edge in are peeled off first (Kahn), then iterative Tarjan runs on the rest; a component that is no cycle allocates nothing. A cycle that closes only beyond `maxDepth` is not reported. `cyclesOf(elements, edges)` gives the cycles of any graph.
- Chain (`chain.ts`, SR-022, command `trace.chain`): `traceChain(graph, root, { direction, maxDepth, includes, leaves })` walks up (`parentsOf`) and/or down (`childrenOf`) from the root; `includes` filters the steps (the view, `appliesIn`; the root always stays), `leaves` gives leaves below an element of the downward walk (`Chain.evidence`; core tests pass their own, #127 option 1), and `hasEvidence` whether an element has evidence that closes its gap (asked only for a requirement without a child; default: it has leaves). Gaps (AK3), downward and only for expanded nodes: a type with the meaning `need` without a child is `no-child`, one with the meaning `requirement` without a child and without evidence `no-evidence`; a missing `need` or `requirement` meaning is named in `unassigned`. Evidence (SR-033): the trace block never imports the evidence block (which imports `trace`), so the command wires the index in: `hasEvidence` is `hasVerificationRecord` in the view (the core without one) for the gaps of the whole chain, and `ChainOutputContext.evidenceOf` (`chainEvidenceOf`, [evidence views](evidence-views.md)) gives the `evidence` output (`ChainEvidenceLeaf`: test cases and records without a test case, at the element's depth plus one). `chainOutput` asks `evidenceOf` only for the expanded downward nodes of the page (the root included when it is on the page), not in the walk, because the walk reaches every node of the chain (42,279 at N-036) and a page shows 200: the content is built per page, the gap needs only a lookup. `lacksEvidence(graph, includes)` keeps its signature for `trace.graph` (SR-111); the graph passes no records until #565, so with records the graph's `no-evidence` mark and the chain's gap can differ until then. The cycles of both walks, a cycle through the root once. `chainOutput(chain, { metamodel, shortIds })` gives the catalog output: nodes (root first, then up, then down, each with depth and `expanded`), edges (source = child, target = parent, `cyclic`), gaps, unresolved links (up: a parent that is not available, `UNKNOWN-…` when its repository is not here; down: a child of an ambiguous UUID), `incomplete`, and the hints `trace.cycle` (one per cycle, at its first element) and `metamodel.meaning-unassigned`. `resolveView` (`variants/views.ts`) turns the `view` input into a view (`core` or a variant; needs the meanings `validity` and `variant`). Elements are named by UUID and repository (`sourceRepository`, `targetRepository`, `fromRepository`, gap `repository`); two files of one repository with one UUID (SR-088) differ only by the node's `file`. Outputs can be large. In the generated workspace (50,000 elements, 200,000 relations) the largest chain is that of the first need in generator order (N-cd15ae, the need of `test/perf/open-filter-chain.test.ts`): 42,279 nodes, 111,865 edges, 14,677 gaps, about 36.5 MB of JSON, 650 to 810 ms for the whole command on a warm workspace (4 cores, noisy; the first call after a load also builds the incoming index, about 1.2 s more; after a save or a watcher batch the index is carried over, #273). So the full chain of the largest need is over SR-082 AK4's 500 ms; the product-level measurement and any optimisation belong to #227. A smaller need (N-126d75, 22,193 nodes, 12 MB) takes 270 to 310 ms, and `maxDepth: 1` about 6 ms. The app and MCP clients should ask with `maxDepth: 1` and ask again below a node that is not `expanded`.
- `derivationCycleProblemsState` (depends on the element store, the metamodel and the short IDs; no `carry` hook, so a change of the store builds it again), for `workspace.check` (SR-090, SR-019): one problem `trace.cycle`, severity `warning` (SR-022 AK4 calls a cycle a "Hinweis"; with `failOn: warning` (#304) `ok` false, CLI exit code 1), per element of each cycle of `cyclesOf(store.elements, derivationEdges(graph))`, with `repository`, `file`, `elementId`, `targetId` (its first edge among the cycle's own edges: relation kinds in metamodel order, then items in file order, so target and cycle always agree) and the `line` of that item. The message names every element of the cycle by type name and short ID, the first `CYCLE_NAMES_SHOWN` (20) of a longer one. Cycles by their first element in store order, elements in store order. A target that is missing, ambiguous or in a repository not here is no edge, so it closes no cycle. Without a relation kind with the meaning `derivation`, one `metamodel.meaning-unassigned` with severity `info` (SR-013 AK3; spec question #270 option 1); against an invalid metamodel nothing. `derivationCycleFindings(graph, shortIds)` gives the findings without lines; `cycleFindings(graph, shortIds, cycle)` those of one cycle of derivation edges, also one a command puts together (SR-067 AK3: an element without an edge in it is named without a target). Without a cycle the state costs about 0.5 to 0.7 s at 50,000 elements; the lines of a cycle of all 50,000 elements cost about 30 s more (`locateFindings` reads every file again), within SR-020's 60 s.
- Affected elements (`affected.ts`, SR-024, command `trace.affected`): `traceAffected(graph, element, { evidence })` walks breadth first from the element, a walk of its own (no edges, no cycle search): distance 1 along every link of `directLinks` (`src/model/affected.ts`: the relations of any kind or relation-valued property and the inline references of other elements, `incomingTo`), from there only along the derivation chain (incoming relations of a kind in `graph.kindByKey`) and inline references (ADR-0004; assumption of #36: "direkt oder über die Kette"). `reached` holds each reached element once (`AffectedNode`: depth, the link and the node it was reached from), the element asked for first; it is never affected, also not through a cycle. `incomplete` while a repository of the workspace file is not here. `evidence: { version, records }` is the seam for stage 4 (SR-028): the records whose version is not the current one are the records of an old version (AK4, `data-export.schema.json#/$defs/evidenceRecord`); the command passes none, the core tests their own (#127 option 1). `affectedOutput(affected, { metamodel, shortIds }, { limit, offset })` gives one page (`total` counts all) with short ID, type, title, file, `distance`, `path` (`{ id, repository }` from the element to it, built for the page only by walking back) and `via` (`{ kind: "relation", key }` or `{ kind: "reference" }`, how it points at the element before it), the records and `incomplete`. From the first need of the generated workspace (about 48,500 affected elements, 222,000 links of which 96,000 references) the command with the default page took about as long as the chain from the same need in the same run (`test/perf/open-filter-chain.test.ts`, SR-082 AK4's 500 ms; the output of all 48,500 is recorded on its own).
- Cost at 50,000 elements and 200,000 relations: the chain from the first need (about 42,000 elements, 112,000 edges) 0.25 to 0.38 s on the index (the cycle search 8 to 25 ms of it), an upward chain a few ms, the cycles of the whole store about 0.3 s (`test/perf/open-filter-chain.test.ts`, SR-082 AK4).
- Neighbourhood (`neighbourhood.ts`, SR-107, command `trace.neighbourhood`): the walks of the chain over every relation key (`relationKeysOf`: relation kinds and properties of kind `relation`) and inline reference, narrowed by `kinds` and `meanings` (`neighbourhoodContext`). `traceNeighbourhood(context, root, { direction, maxDepth, includes })` walks up along what the element's file stores (`outgoingOf`: its followed keys in frontmatter order, then its references; an `available` target is a step, one in a repository that is not here or not in the workspace file makes the walk incomplete, a missing or ambiguous one is no step) and down along what points at it (`incomingOf`: `incomingTo` filtered, relations then references; no step while two files of its repository share its UUID; incomplete while a repository of the workspace file is not here). `neighbourhoodOutput(n, { metamodel, shortIds }, { limit, offset }, versionsOf)` pages as `chainOutput` (nodes by `chainNode`) and gives each edge `source`/`target` (ADR-0004), `link` (`relation` or `reference`), `kind`, `property`, `meaning`, `cyclic`, `repeated` and `outdated`. `repeated` is `walk.byElement.get(edge.to).via !== edge` of the edge's own walk: it holds within one call and within the followed links (asking again from a child loses it, and a derivation edge is marked when a reference reached the element first), and "first" is the first reached breadth first (spec question #421, option A). `outdated` is `isOutdatedVersion` (`model/is-version.ts`, the rule of the hints, SR-025) against the current version of the target, read for the targets of the page only (`currentVersionsOf`). The command's `maxDepth` defaults to 1 (`allLevels` walks as far as the links go), so the default cost is the direct links of one element; a hub (a package with thousands of members) puts them all on one page unless `kinds` or `meanings` leave it out. The optional `repository` picks the copy of a UUID that lies in that repository (as `element.get`, #255; the app names elements by UUID and repository). Unresolved links are not listed (`element.get` and `workspace.check` report them).
- Graph (`element-graph.ts`, SR-111, D-063, command `trace.graph`; `graph.ts` is the derivation graph): `elementGraph(context, root, { maxDepth, includes, limit })` runs the two neighbourhood walks with `maxNodes: limit` (the walk stops expanding once it has reached that many elements besides the starts and sets `cut`; the bound is `limit` plus the steps of the last element expanded), so the whole chain over every kind costs about `limit` elements instead of 42,000. Each element is one node at its smaller distance (above on a tie), level 0 for the root, −d up, +d down; order: the root, then per distance the up nodes, then the down nodes, in walk order; the first `limit` are kept. Nothing is lost by the bound: a cut walk reached at least `limit` elements, and each comes before every element it did not reach. `expanded` holds when the walk expanded the node and every element its steps lead to is kept; `truncated` when a walk was cut or nodes were left out. `elementGraphOutput(graph, { ...context, shortIds }, versionsOf, marksOf)` lists every followed link between two nodes once (`outgoingOf` per node in node order; links the walks did not take too; no link to itself) with `outdated` against the current version of the target. The marks come from the command, because `hints` imports `trace`: `outdated` is `outdatedAmong` (`hints/outdated.ts`, the rule of `outdatedOfShown`, one `currentVersionsOf` for the targets of all nodes), `superseded` an invalid status (`invalidStatuses`), `no-evidence` `lacksEvidence(graph, includes)` of `chain.ts`, which shares `gapOf` and the children of the down walk (`childrenWithin`) with `traceChain`, so the chain's gaps and the graph's marks agree in the children, also in a view (spec question #478); the chain decides evidence with the records (`hasEvidence`, SR-033), the graph passes none until #565. Cost at N-036 (`test/perf/trace-graph.test.ts`): the walks and the output a few tens of ms; most of a 500-node graph is the current versions of the link targets of its nodes (about 2,600 files) while the versions of the whole store are not built.
- Matrix (`matrix.ts`, SR-125, command `trace.matrix`): the traceability matrix of a selection. Rows are the selection in the order of `element.list` (`orderedSelection`, `query/ordered.ts`, which `element.list` uses too, so AK1 holds by construction; with `hierarchy` the tree places give `depth`). Columns are the relation kinds of the metamodel (`matrixKeys`; D-043, D-037: a Beziehungsart is a relation kind, the relation properties `packages` and `validity` are their own meanings, D-012, so they form a column only when `kinds` names them, inline references never) in both directions, only those a row of the selection has (`matrixColumns`: one pass over the records and the incoming index, no file read, a target lookup only in a view). One enumerator (`outgoingItems`, `incomingRelations`) serves the counts and the cells: the items as `relationsUnder` reads them (`relationItems`, `hasId`, `isUuid`), the incoming relations of followed keys into the row's repository, none while other files of it share its UUID (SR-088, as `incomingOf`), and in a view (`Selected.view`: the selection's, else the saved filter's) an available other end that does not apply is left out of both. A relation to a missing or unreachable target counts and is in the cell (AK4: marked, not a gap). `matrixRows` builds the cells of the page with `relationLink` and `sourceLink` (`model/view.ts`, the builders of `element.get`) and reads current versions only for the page's rows and their available targets (`currentVersionsOf`); `outdated` is `isOutdatedVersion`, for an incoming relation against the row's version. `incomplete` is the selection's (SR-006 AK2, includes a repository of the workspace file that is not here). Cost on 50,000 elements: selection and sort as `element.list`, plus the counting pass (`test/perf/trace-matrix.test.ts`). SR-126 will add columns of another `type` (the column `type` and the cell shape per type are open for it).
- `relatedElements(graph, selection, { direction: "children" | "parents", maxDepth, includes })` (`src/trace/related.ts`, SR-023, command `trace.related`): one breadth-first walk from every element of the selection along `childrenOf` or `parentsOf`; lists each element reached through a step once (AK2), by distance, then in the order reached. An element of the selection that another one (or a cycle) leads to is listed too, at the distance of its first step in. `maxDepth` 0 lists none. `includes` (a view, `appliesIn`) drops the steps to elements outside it; the selection is walked from as given. Its own walk, not `walk`: a list needs no edges, nodes or cycles; the 42,278 children of the first need at N-036 take about 0.2 s instead of 0.35 s. The command walks completely, counts all in `total` and builds only the page (`limit`, default 200, at most 5,000; `offset`): the first page of those children about 0.2 to 0.33 s (perf test, SR-082 AK4 500 ms).

# Evidence block: views and export (`src/evidence/`, `src/data/`)

Part of the [`@reqseq/core` README](../README.md). It covers coverage, the evidence list, the test cases in the chain and matrix, the requirements without passed test, and data export; the records, folders and index are in [evidence-records.md](evidence-records.md).

"Has evidence" is `hasVerificationRecord` of the index for every view below (ThomasBirkmaier/ReqSeq-archive#535); SR-120 asks something narrower, a passed test (`isPassedTest`, below).

## Coverage

SR-036 (ThomasBirkmaier/ReqSeq-archive#48), `evidence.coverage` (`commands/evidence/coverage.ts`), block file `evidence/coverage.ts`:

- `coverageRules(graph, index, views, includes)`: what decides the coverage of each element, on one derivation graph (trace block) and the evidence index, for the views of the selection (`Selected.views`: its own view, then the saved filter's).
  - Levels: the element types with the meaning `need` or `requirement` (own or inherited; a subtype is its own level), in metamodel order. Other types have no level. Evidence counts only for requirement types (D-012).
  - Views: the selection's; without one the core (AK5, #203 Q4), so a requirement valid only in a variant, its children there and the records of a variant count only when that variant is selected, as in the degree, the matrix and the filter.
  - Counted: an element whose status the metamodel does not mark invalid (AK4, D-044) and that every view holds (`viewsInclude`, the view rule).
  - Child: a derivation child of `childrenOf` (incoming relations of a kind with the meaning `derivation`, in any repository; one named only by an ambiguous relation is none, SR-088) that is counted by the same rule (a core requirement the variant excludes or replaces is no child there, SR-043 AK5).
  - Evidence: `hasVerificationRecord` in the first view (as the filter condition `verification`); any version and result (spec question ThomasBirkmaier/ReqSeq-archive#527).
- `coverageOf(elements, rules)`: one `CoverageLevel` per level type with a counted element, with the counts and the UUIDs behind each number in selection order (AK2). The command adds `incomplete`: a repository of the workspace file is not on this machine (the selection's `incomplete`, AK3), or the evidence state is incomplete; and `names` (ThomasBirkmaier/ReqSeq-archive#588): every element the levels list, once, in selection order, by short ID, identifier and title (`namesOfRecords`, model block), so the readable CLI names them without a lookup; `--json` keeps the UUID lists unchanged.
- Cost: one pass over the selection and each element's incoming relations once (N-036); `names` one more pass over the selection, from the store's frontmatter and the built short IDs (nothing read), and about 150 bytes of JSON per counted element. `names` is not bounded by a page: on `spec` (210 counted elements) the compact JSON grows from 13.7 KB to 45.7 KB (`names` 31.9 KB, about 2.3 times `levels`), so about 7.6 MB of `names` next to about 2 MB of UUID lists at 50,000 requirements, and MCP sends the output twice (`structuredContent` and text, ADR-0009). E4 (ThomasBirkmaier/ReqSeq-archive#583) measures the coverage JSON size with `names` at N-036; if it is too large for MCP, the remedy is an opt-in input or a page on coverage, decided there, never trimming in the presenter.
- The assumptions of spec question ThomasBirkmaier/ReqSeq-archive#527 (level = type, needs count for children only, evidence = any verification record in the view) are still open there. SR-042 (exclusion for a variant) narrows the view's selection there.

## Evidence list and baselines

Every function here that takes `independent` gets the mark of the element's repository (`variant-independent`, SR-173; `variantIndependentOf` of the layout, or `StatusSource.independent`): per element, never per UUID, since twins in two repositories may differ (SR-088).

SR-032 (ThomasBirkmaier/ReqSeq-archive#44), `evidence.list` (`commands/evidence/list.ts`), block file `evidence/views.ts`; the baselines come from the read-only reader of the [baselines block](baselines.md). The optional `repository` and `file` pick one copy of a UUID several files share, as in `element.get` (SR-088, #821): the records stay those of the UUID, and the chosen copy decides only whether its repository is `variant-independent` and which version is current:

- `listedRecords(records, view, independent, containing)`: the element's records of the index (`byElement`, newest first) that hold for the view (`recordHoldsIn`: the core takes the records without a variant, a variant the records for it, SR-047, and those without a variant when the element's repository is marked `variant-independent`, SR-173; no view every record), each with `baselines`, the names `containing(element, version)` gives (an empty list when no baseline holds the version). The fields of AK1 (version, item, date, result, evidence) are the record's own, shown as read; the command adds `evidenceSource` on copies ([evidence-records.md](evidence-records.md), #821). The evidence (Beleg) is text and is never fetched or opened (offline).
- Criteria a record names (SR-205 AK2, `evidence/criterion-names.ts`): every command that lists records gives each record that names criteria `criterionNames`, each criterion with number, key and text (`namedCriterion` of `criteria.ts`): `evidence.list` (its `records` and the executions and `last` of its `testCases`), `trace.chain` (`evidence`), `trace.matrix` (`last` of a test case), `trace.affected` (`records`) and `evidence.record` (the record it wrote, whole texts). `recordNamer(workspace, listed)` takes the elements (the store's records, so two copies of one UUID stay apart, SR-088) and records of one command call, reads `verificationState` and the current versions of those elements once, and the items of older versions that records name by number only where the status lookup has none, in one `versionValues` walk for the whole call; a call without such records reads nothing. `baseline.get` names its `later` records with the items of the baseline's version (`withCriterionNames` in `evidence/baseline.ts`), which are those records' own version.
- The command adds `problems`: those of the baseline files (a faulty file names no baseline), and `incomplete`: an evidence location (`evidenceReadState`) or the baselines folder is in a repository that is not on this machine (SR-006 AK2).
- `bearing` (SR-032 AK3, `evidence/bearing.ts`, `bearingRecords(records, current, count)`): the positions in `records`, ascending, of the records that bear the element's status, which the app shows open and folds the others away. Per kind and variant (the record's own `variant`, none for the core) and, for verification records of an element with `count` acceptance criteria (the property with the meaning `acceptance-criteria`), per criterion (D-072): the newest records of the current version (as the status counts them: an inconclusive verification record is of no current version), else the newest of an older version. A record without `criteria` counts for every criterion (SR-031 AK6), one naming a number beyond `count` for none; with `count` 0 and for validation records the kind and variant are one group. Every record at the newest date bears its group, so the whole run of a CI (which dates all its test cases alike) stays open (AK3 as of 2026-11-09); the status still follows `status.ts`. In a repository marked `variant-independent` (SR-173) a variant's verification records are pooled with those without variant, as its status pools them. A record that names only numbers beyond `count` bears nothing, and the records are compared also while the metamodel is not valid (when the status compares none). O(records × (count + 1)), after the records are listed.
- `display` (SR-032 AK3 to AK5, `evidence/display.ts`, `displayOf(records, { bearing, current, count, views, independent, validates })`, #1320): the Evidence section at a glance, so the app only lays it out. `shared`: each of date (as an instant), item, version and baselines that every bearing record has, equal. `rows`: with a verification record one row per acceptance criterion 1..count (one without `criterion` for count 0), also for a criterion without record; `views` gives its status in each view the element applies in (the holders of `verificationState` that include it, without an invalid variant's, SR-047 AK6; with `view` that view alone, also an invalid variant's, as the records are only its; none for an element that is no requirement, which then has no verification row) by `criterionStatusesOf` of `status.ts`, so the row agrees with the status (not while the metamodel is not valid: the status is then open everywhere, the rows still compare the records), and `status` is the worst (failed, outdated, open, verified). With a validation record a validation row with the validation status. `cases`: the row's bearing records that hold in one of those views, by test case, worst result first, then class name and name in code units, records without test case last; the records of one execution in two views are both in the case. `older`: the records no row shows by instant and version as written (one version in both normal forms is two runs), newest first; a record naming only criteria beyond the count lands here, as does a bearing record for a view the element does not apply in. `shared` is computed over the records the rows show. O(records × (count + 1) × views).
- `testCases`: the element's test cases (SR-033, `testCasesIn` below), every kind of record as `records`, with `view` as for `records`; always given.
- Cost: the element's records, its current version when it has any (`currentVersionsOf`, one file), for `display` the workspace status `verificationState` (built once for the workspace and kept, as `element.get` and `evidence.status` use it; a cold CLI call pays its build), and for each record two set lookups per baseline file (one per normal form); the baseline files are parsed once and kept by size and time (`baselineFilesState`).
- `trace.affected` (SR-024 AK4) takes its records from the same index: the element's records whose version is not its current one (`currentVersionsOf`, only when it has records); none while its current version cannot be computed.
- The element view of the app shows this list (`EvidenceLines.tsx`, `packages/app/docs/buffers.md`).

## Test cases in the chain and the matrix

SR-033 (ThomasBirkmaier/ReqSeq-archive#45), block file `evidence/views.ts`; `trace.chain` (`commands/trace/chain.ts`) and `evidence.list` use it. SR-126 (ThomasBirkmaier/ReqSeq-archive#443), block file `evidence/matrix.ts`: the matrix (`trace.matrix`) uses it for its test case column.

- `testCasesIn(index, id, view, independent, kinds?)`: the test cases that name the element (`index.testCasesOf`, `$defs/testCase` seen from that element, by class name then name), each with only the executions that hold for `view` (`recordHoldsIn`) and are of one of `kinds`; `last` is recomputed. A test case that had executions and has none left is left out; one that was only skipped (`executed: false`) stays in every view, since `SkippedTestCase` carries no variant. So a test case executed only for a variant and skipped in the core run is left out of the core view, not shown as not executed (it had executions, none of them hold there). When nothing is filtered out (the usual case: JUnit records are always verification) it returns the index's own array, no copy.
- `verificationTestCasesIn(index, id, view, independent)`: `testCasesIn(…, ["verification"])`, the test cases of the chain and of the matrix, so both show the same test cases for the same view. The chain without a view shows the executions of every variant; the matrix always has one view, so the two agree only when the chain is asked in that view (plan review N3).
- `chainEvidenceOf(index, id, view, independent)`: what `trace.chain` shows below an element (`evidence`): `testCasesIn(…, ["verification"])` and the element's verification records without a test case (inspection, analysis, demonstration, a manual record without `test-case`), newest first, those that hold for `view` (every one without a view, as `evidence.list`). Validation records are not Nachweise (D-007) and stay out of `evidence`. Undefined when the element has neither.
- `validationRecordsOf(index, id)`: the element's validation records, every one, newest first, those with a test case too; no view narrows them, since a validation record names no variant (SR-038 AK4) and holds for its element, as `validationOf` counts it (unlike `evidence.list` in a variant's view, which drops them). `trace.chain` gives those of its root as `validationRecords` (#646).
- The Beleg of an execution (AK1 „mit Datum, Ergebnis, Prüfling und Beleg“) is the record's `evidence`; a JUnit execution has none, so its Beleg is its record file (`repository`, `file`, `line`; D-007: for automatic tests the record is the result file; assumption A5, spec question ThomasBirkmaier/ReqSeq-archive#528 Q4). Core gives it as `evidenceSource` (#821). Belege are text and never opened.
- The `no-evidence` gap of the chain is `hasVerificationRecord` in the view, the core without one (as coverage and the filter); a skipped test case gives no record, so it does not close a gap. Without a view the chain shows the records of every variant but decides the gap in the core (spec question ThomasBirkmaier/ReqSeq-archive#527 Q4). A requirement the view (without one: the core) does not hold is no gap there but `not-in-view`, with the views that hold it (#674).
- Assumptions (spec questions ThomasBirkmaier/ReqSeq-archive#528 Q1 and Q4): a „Testfall ohne Durchführung“ is a JUnit test case that is `<skipped>` everywhere it names the element (A1; one skipped in one run and executed in another is executed); the chain shows verification records only, records without a test case next to the test cases (A2); a test case that names several requirements is shown at each with that requirement's own executions and counts as evidence for each (A3, SR-033 AK2); two files of one repository with one UUID show the same evidence (A4).
- Cost: `trace.chain` asks `hasVerificationRecord` for each requirement without a child of the whole downward chain (one map lookup, no allocation) and builds `chainEvidenceOf` only for the expanded downward nodes of the page (`ChainOutputContext.evidenceOf`, [trace block](trace.md)), so a page of 200 nodes builds the evidence of 200 elements, and `testCasesOf` caches only those. The first chain also builds `evidenceReadState` and `evidenceIndexState`, the upward one too since #646 for the root's `validationRecords` (so a cold upward chain pays the index build below once; the default `both` and every downward chain already did). Measured on the generated workspace (50,000 elements, 4 cores, the machine under a load average of 13 to 17, so the absolute times are high): `[SR-082/AK4]` (`test/perf/open-filter-chain.test.ts`, no evidence location) gave 480 and 486 ms for the first page before SR-033 and 516 and 803 ms after it, run alternately, while the walk-only line of the same test (no evidence code) moved from 517–806 to 772–878 ms, so the difference is the load. In one process, alternating 15 times on the first need, first page (medians): the chain without evidence 248 and 276 ms, with the evidence wiring on an empty index 227 ms, with 77,599 JUnit records (1 to 3 per system requirement) 264 ms. Building the evidence index of those records took 0.84 to 1.24 s, once per load of the records (the first downward chain or any other evidence command pays it). That cold build of `evidenceIndexState` at N-036 and the chain with records shaped like real data (time, heap and the JSON size at `limit` 5000, since a test case that names several requirements repeats `elements` at each) are measured in E4 (ThomasBirkmaier/ReqSeq-archive#583).
- Matrix (SR-126, `evidence/matrix.ts`, called by `commands/trace/matrix.ts` through the `rowFields` seam of `matrixRows`, [trace block](trace.md); the trace block imports no evidence):
  - When (assumption A1, spec question ThomasBirkmaier/ReqSeq-archive#593 Q1, `showsEvidence`): the workspace file names an evidence location, the metamodel is valid (otherwise records are not compared, as in `verificationState`) and the selection holds an element of a type with the meaning `requirement`. Otherwise nothing is read, no evidence state is built and the output is SR-125's, byte for byte. The evidence columns are no column `type`: the header is the top-level `evidence` and the cells are `rows[].testCases` and `rows[].verification`, so SR-125's readers of `columns` and `cells` stay unchanged (plan D1).
  - One view (assumption A4, ThomasBirkmaier/ReqSeq-archive#593, ThomasBirkmaier/ReqSeq-archive#592 Q1, ThomasBirkmaier/ReqSeq-archive#527): the selection's, else its saved filter's, else the core, as `evidence.degree`; `evidence.view` names it (`viewIdOf`). Status, test cases and degree are given for it; `element.get` and `evidence.status` give every view. The export (`data.export`, SR-061) gives every view (`verificationOf`); the matrix gives one. Both are right; do not "fix" one to match the other.
  - Test case cell (AK1, AK2, `matrixTestCases`): the items of `verificationTestCasesIn` for the view, compact: `name`, `className`, `executed`, `last` (the newest execution in the view, of any version, of several equally new ones the first failed one, SR-126 AK1, as `$defs/evidenceRecord`; for JUnit its record file is the Beleg, A5; given as `evidenceSource`, #821) and `mark`. An empty array is the gap „ohne Testfall“. Records without a test case (inspection, analysis, manual records without `test-case`) are not in the cell; they count only for the status (A3, ThomasBirkmaier/ReqSeq-archive#528 Q3). The chain and `evidence.list` give every execution.
  - Mark (A2, ThomasBirkmaier/ReqSeq-archive#528 Q1/Q2, ThomasBirkmaier/ReqSeq-archive#593 Q2, `testCaseMark`), the first that holds: `not-executed` without an execution; `outdated` when no execution is of the row's current version, or the current version is not known (ThomasBirkmaier/ReqSeq-archive#276), the version test of `recordStatusOf`; `failed` when the newest execution of the current version failed; none otherwise. The mark follows the status (#201): a newer run of an older version does not mark the test case `outdated` while a run of the current version exists, though `last` still shows that newer run. Ties: as `recordStatusOf` gives `failed` when records of the newest instant of the current version tie and one failed (ThomasBirkmaier/ReqSeq-archive#525 Q2), the mark is `failed` then too, and `last` is that failed one (SR-126 AK1: „bei mehreren gleich neuen die schlechteste“).
  - Status cell (AK1, AK3, `matrixEvidence`): one `$defs/verificationEntry` for the view from `status.evaluate(element, view, { current })`, `current` being the version `matrixRows` read for the row (as `withEvidenceStatus` measures against the version shown); `indirect` for a requirement verified through its children (AK3), `missingChildren` as everywhere. A row that is no requirement, or a requirement that does not apply in the view (valid only in variants, in a matrix without a view), gets neither field: not applicable, no gap.
  - Degree (AK4): `evidence.degree` is `degreeOf(status, selected.elements, view)` over the whole selection, recomputed for every page, so `trace.matrix` and `evidence.degree` agree by construction (SR-080 AK2). Order (plan review S1): `prepare(selected.elements, { own: true })` on the whole selection once, then `degreeOf`, then the rows. Not `selectionDegree`: it prepares only the counted requirements, and an obsolete page row without own record would then be evaluated against unprepared children.
  - `incomplete`: the selection's, or an evidence location in a repository that is not on this machine (`evidenceReadState.incomplete`, SR-006 AK2).
  - Order and names: `evidence` comes right after `columns`, before `rows`, so the readable output prints the degree above the rows that hold the status (AK4 „über der Spalte des Nachweisstatus“); the row fields `testCases` and `verification` come before `cells`, in schema order. `names` (ThomasBirkmaier/ReqSeq-archive#588) names the variant of the view and the missing children of the page's rows (`verificationNameIds`, `namesOf`).
  - Cost: without an evidence location none. With one, the first call builds `evidenceReadState`, `evidenceIndexState` and `verificationState` (as any evidence command) and prepares the whole selection in one batch of versions; each page then evaluates the degree over the whole selection (memoised per element and view in the evaluator) and builds the test cases of its rows only. A page row's version is read twice, once by `prepare` (`own`) and once by `matrixRows`' `versionsOf`. Measured in E4 (ThomasBirkmaier/ReqSeq-archive#583): cold and warm first page, a deep page, `limit` 5000 (time and JSON size), the degree alone, and the matrix without an evidence location.

## Requirements without passed test

SR-120 (ThomasBirkmaier/ReqSeq-archive#431), `evidence.withoutPassedTest` (`commands/evidence/withoutPassedTest.ts`), block file `evidence/without-passed-test.ts`; the assumptions are those of spec question ThomasBirkmaier/ReqSeq-archive#532 (answered from the spec and the glossary in the plan review).

- `isPassedTest(record, view, independent)`: a record with `kind: verification`, `method: test` and `result: passed` that holds in the view (`holdsIn`, SR-047, SR-173). Of any version, and also when a later run failed (AK2 „mindestens einer bestandenen Testausführung“). Inspection, analysis, demonstration and validation records are none (D-007); a skipped JUnit test case gives no record, so it is none either.
- `withoutPassedTest(source, elements, view, includes)`: the elements `evidence.degree` counts (`countedIn`: a type with the meaning `requirement`, status not marked invalid, D-044) that apply in the view and have no passed test there, in the order given. Pure. An indirectly verified parent without own test is listed (AK2 „ohne Testausführung … steht darin“), and so is a requirement verified by inspection only. While the metamodel is not valid the source has no records: every requirement is listed (`evidence.status` gives them `open`).
- Not the filter's „ohne Nachweis“ (`hasVerificationRecord`, SR-069 AK3) and not a verification status: a requirement with only failed records, or only an inspection, is without a passed test but has a Nachweis; one whose newest run failed after a passed one has the status `failed` and is not listed. There is no filter operator for it; CLI, API, MCP and app get the list through the command (SR-080).
- The command takes `view` (default the core; a variant: its records and the requirements its view holds, `viewRuleOf`), `limit` (default 200) and `offset`, and no selection (SR-120: „alle Requirements“): the app's command prompt runs it without asking (AK1, title "List requirements without a passed test", found by "without passed" and "passed test"; #234 replaced the double negative "without passed/no test"). Order: type, then identifier, then short ID, the keys of the app's `DEFAULT_SORT` (change both). Each row as `evidence.status` gives it (`withEvidenceStatus`), so it says why it is listed; `total` counts the whole list; `incomplete` is the selection's or the evidence state's.
- Cost: one pass over the store with set lookups, `appliesIn` and the records of each element; no file is read and no current version computed for the list (any version counts). The listed requirements are sorted on every call (O(k log k)); only the page is prepared (`workspaceStatus`) and built. The first call builds `evidenceReadState` and `verificationState` (with the trace context) like any evidence command. Measured in E4 (ThomasBirkmaier/ReqSeq-archive#583).

## Data export and store

SR-061 (ThomasBirkmaier/ReqSeq-archive#73), `data.export` (`commands/data/export.ts`), block `data` (`data/export.ts`; it imports the model, evidence, variants and workspace blocks and never `commands`). SR-062 (ThomasBirkmaier/ReqSeq-archive#74, `data.store`, `commands/data/store.ts`, `data/store.ts`) writes the same data to a file as JSON Lines (below, #319). The output is `data-export.schema.json`, embedded in `contracts.json` (ADR-0014; the shipped schema of AK3, assumption A4 of ThomasBirkmaier/ReqSeq-archive#590 Q2). Its assumptions are asked in spec questions ThomasBirkmaier/ReqSeq-archive#530 (Q2, Q4, Q5) and ThomasBirkmaier/ReqSeq-archive#590.

- `exportData(workspace, selected, selection)`: the elements of `resolveSelection(…, "data.export")` ([query block](query.md)), in store order, superseded ones included (D-045), each as `element.list` gives it (`listElements`), with:
  - `verification` and `validation` from `withEvidenceStatus` (the one status source of `evidence.status` and `element.get`, SR-080 AK2): the verification in the core and each variant whose view holds the element (none for one that excludes or replaces it, or whose status is invalid, SR-047 AK6), whatever view selected it (SR-047 AK3, A2), and the validation status (SR-038) with `validationReason` when it is inconclusive (SR-172; the export's `validationStatus` and record `result` enums grow by `inconclusive`, `reqseq-data` stayed 3 for SR-172);
  - `validity` and `packages` (`exportedElement`): the UUIDs the properties with the meanings `validity` and `packages` name, in their order (entries that name no UUID are left out); `[]` for none, which for `validity` means the core and every variant (SR-040 AK1, D-020); each field is left out when the metamodel has no such property of kind relation;
  - `replacedBy` and `excludedBy` of a core requirement (`withReplacedExcluded`, `replacedExcludedOf` of `variants.md`, SR-046 AK3), whatever view selected it; each left out when empty;
  - every relation with `currentVersion` (when its other end is available and has one) and `outdated` (SR-025, `isOutdatedVersion`), as `trace.matrix` gives them: an outgoing relation against its target, an incoming one (a successor's, SR-072 AK3) against the element itself. `withRelationVersions` is a second pass over the listed elements, since a target may come later in store order; targets outside the selection are read in one batch, none when there is none.
  - Not exported: the text, incoming relations other than successors (each relation is at its source), the version date (D-013 is about display; history per element is too slow at N-036), the records themselves (`evidence.list`).
- Header (`exportHeader`): `reqseq-data: 5` (5: records name criteria by number or key, and a criterion an output names has its number, key and text, SR-205 AK2); `commit`, HEAD of the main repository (the one with the workspace file; left out when Git cannot tell), and `dirty`, `false` only when every available repository has a known commit and is known clean (the `-dirty` rule of `data.store` below, which takes the name from them); then the workspace name, `generated` (the time of the call, UTC, seconds), `selection` as given (left out without one), every repository of the workspace file with `available` and, when Git tells it, `commit` (`repositoryCommit`, as `workspace.status`) and `dirty` (SR-062, ThomasBirkmaier/ReqSeq-archive#531 Q2: `repositoryState`, below), and `incomplete` (SR-006 AK2): a repository, and so an evidence location, is not on this machine, or a condition of the selection met a target in a repository the workspace file does not list.
- JSON Lines (#319, SR-061 AK4): the catalog entry has `jsonLines: { items: "elements", fields: ["reqseq-data", "commit", "dirty", "repositories", "incomplete"] }`, so `data export --jsonl` and the API with `Accept: application/x-ndjson` give one line per element: `reqseq-data`, `commit` (when known), `dirty`, `repositories` and `incomplete` first, then the element unchanged (`data-export.schema.json#/$defs/line`; `$defs/element` and `$defs/line` share `$defs/elementFields`, and both forms `$defs/repository`). `repositories` and `incomplete` are on every line since `reqseq-data` 4 (SR-062 AK1, #1454), so a file names the commit of each available repository and a repository that is not on this machine; at N-036 (four repositories) they add about 440 bytes per line, about 22 MB at 50,000 elements. `workspace`, `generated` and `selection` are not in the lines, so many such files load as one table, by `commit` and `dirty` (`read_json_auto('*.jsonl')` in DuckDB); files of version 3 and 4 load together, the newer ones with two more columns (version 5 names a criterion that is not verified as an object instead of a number). A selection without elements gives no line, so its file names only the main commit, by its name (assumption of the open question #1461). The lines come from `jsonLines` of the files block (`files/json-lines.ts`): one native `JSON.stringify` per element, joined into chunks of about 1 MB, so no measuring walk as in `jsonChunks`. MCP keeps the object (ADR-0009). An evaluation selects by filter, package, baseline or variant (SR-061 AK2) instead of exporting everything.
- A baseline selection exports the elements the baseline lists as they are now (A1): an element changed since the baseline has another `version` than the baseline lists, and nothing marks it. Marking it would be a new schema field (ThomasBirkmaier/ReqSeq-archive#530 Q4 asks which reading holds).
- Workspace problems (A6): the schema has no top-level `problems`. Element problems stay in `elements[].problems` (an element without version gets its `file.faulty` warning). Left out, for `workspace check` to report: layout and metamodel problems (an invalid metamodel exports every requirement `open`), a refused Git (`git.unavailable`; the repository then has no `commit`), record problems (`evidence.invalid-record`, `evidence.not-enriched`, ...) and faulty baseline files other than the one selected. A broken workspace is exported with exit code 0; whether a pipeline export must fail is asked for SR-062 (ThomasBirkmaier/ReqSeq-archive#590 Q3).
- `data.export` writes nothing; neither command sets a status (D-030, SR-087). Git is only read (`rev-parse`, `ls-tree`, `diff` without index refresh, `ls-files`, `cat-file --batch-check`; ADR-0006).
- **`data.store`** (SR-062; its assumptions are in ThomasBirkmaier/ReqSeq-archive#531 and ThomasBirkmaier/ReqSeq-archive#590 Q3). `storeData(workspace, selected, input)`:
  1. `repositoryCommit` of the main repository first (K1, K3). Without a commit (no Git, no repository, no commit yet, no tree at a folder below the top level, Git refuses or does not answer; `RepositoryCommit.unknown` names which) nothing is written and no folder is created: `{ files: [], problems: [git.unavailable error] }`, exit code 1.
  2. The folder (K4, ADR-0002 rule 5), checked with both possible names before the export is built: `realpath` of the deepest existing folder (`ENOENT` goes up, `ENOTDIR` is `input.invalid` with `rule: "not-a-folder"` inside and `file.folder-missing` outside, any other error `file.unreadable`). Inside an available repository (the deepest wins) `refuseUnlisted(…, { ignored: false })`: `.git`, `node_modules`, links into a repository, nested repositories, non-portable names and spellings are refused; ignored folders are allowed, since a data file is never walked; a missing folder is created and the name checked again. Outside every repository (command line and app only; API and MCP refuse such a folder, SR-142) the folder must exist and its real path must not hold a `.git` segment (`refuseGit`, `workspace/shown-path.ts`).
  3. `exportDataWithProblems`: the same object as `data.export`, `dirty` included, and the problems that concern the file: `git.unavailable` warnings for a repository other than the main one without a known commit, or for one whose `dirty` Git cannot tell, and the `workspace.repository-missing` info when the file is `incomplete` (ThomasBirkmaier/ReqSeq-archive#531 Q6). Element problems stay in the file; everything else is left to `workspace check`.
  4. The name from the header (`commit`, `dirty`): `<commit>.jsonl` only when every available repository has a known commit and is known clean, else `<commit>-dirty.jsonl` (ThomasBirkmaier/ReqSeq-archive#531 Q2, review B1). An old `<commit>.json` of the former JSON form is neither read nor replaced and stays where it is; a pipeline removes it. The commit is the full ID (40 or 64 digits). A repository that is not here does not make the name `-dirty`.
  5. An existing file of the name is replaced only when it is a ReqSeq data file (`readJsonlSnapshot` and `jsonl-data.ts` of the files block, #319): its first line starts, within the first MiB, with `"reqseq-data"` as the first key and an integer of at least 2 (only that signature is read, whatever the length of the line), and the file is valid UTF-8 (a sequence cut at the very end is allowed); an empty file (a selection without elements) counts too. No later line is scanned (review PS3), so a file of ReqSeq that a crash cut in the middle is replaced on the next run. The same check guards the rename (`writeFileAtomic` with `{ kind: "jsonl" }`), so the two never disagree; anything else is `input.invalid` (`not-a-data-file`). The file is read in pieces of 1 MiB and hashed as it goes, never held whole. The content is the lines of `data export --jsonl` (`jsonLines` with `DATA_LINES`, which a test keeps equal to the catalog's `jsonLines` of data.export): per element `reqseq-data`, `commit`, `dirty`, `repositories` and `incomplete`, then the element; compact, LF, UTF-8 without BOM, in chunks of about 1 MB given lazily to `writeFileAtomic`. `workspace`, `generated` and `selection` are not in the file; a missing repository is on every line (`repositories`, `incomplete`) and in the `workspace.repository-missing` info of the output.
  6. `files`: relative to the workspace root when the file lies in a repository of the workspace, else absolute (`shownPath`).
  - The file name holds the main commit only (K1). A newer state of another repository under the same main commit, an incomplete run, and another selection in the same folder replace the file of that commit; a pipeline uses one folder per selection. The optional refusal to replace a complete file with an incomplete one is offered in ThomasBirkmaier/ReqSeq-archive#531, not built.
- **`dirty`** (`model/uncommitted.ts`, `repositoryState` on `uncommittedFiles`, which `baseline.create` uses for SR-050 AK2): uncommitted changes, by content, to the state files of a repository: the workspace file, the `*.yaml`/`*.yml` files directly in the metamodel, filter and baselines folders, every `*.md` the walk reads outside the evidence locations (also a Markdown file that is no element, such as a `README.md`), and every file an element embeds. Not counted: evidence records (the pipeline writes them in the same run, D-026), `.reqseq/local.yaml`, code and every other file, the stored data files. `changedPaths` lists candidates; one `commitBlobs` listing (`ls-tree` of the commit, #439) gives the blob IDs at the commit of every state file (NFC and NFD), so a state file without a blob that is on disk (new, also one Git ignores) is dirty, one that is neither in the commit nor on disk (a link to an image that exists nowhere) is no change, and a listed file with a blob is dirty only when Git's blob hash of its working bytes differs (`gitBlobId`, SHA-1 or SHA-256 by the commit length). A copied work tree with only new stat data is clean; a checkout filter (`autocrlf`, LFS) makes a file dirty (more, never less). `dirty` is left out when Git cannot tell.
- Cost (N-036): one `listElements` (the versions of the selection, the whole store's when it is a large share), the versions the status needs in one batch (`verificationState`, `versionBatches()`), at most one more batch for relation targets outside the selection. No paging: one call gives the whole selection, about 1.2 to 2.3 KB per element (60 to 115 MB at 50,000 elements; over MCP about 2.2 times that in one line). The measurement and the decision rule for MCP and the API are rows of ThomasBirkmaier/ReqSeq-archive#583. `dirty` adds `changedPaths` per repository, the image links of the store and one `ls-tree` listing of the commit per repository (`commitBlobs`, #439) for every state file, plus a read and hash per listed file (all of them in a copied work tree); `data.store` adds one write in chunks (`jsonLines`: one native `JSON.stringify` per element), and replacing a file reads the old one twice in pieces (the check before the export and the one before the rename) to hash it and check its first line and UTF-8. The rows of `packages/cli/test/perf/data-store.test.ts` record the store at N-036 (time, memory of the CLI process, bytes) and `jsonLines` of the export. These are rows of ThomasBirkmaier/ReqSeq-archive#583 too; over MCP and the API `data.store` answers with one path.

# Model block: writing, reading, status, bulk update, supersede, relations (`src/model/`)

Part of the [`@reqseq/core` README](../README.md); the model block is split into [store](model-store.md), [checks](model-checks.md), [writing](model-write.md) and [findings](model-findings.md).

Writing elements (SR-001, SR-002, `src/model/write.ts`, used by `element.create` and `element.update`):

- File names come only from `fileNameFor({ prefix, id })` (`src/model/file-name.ts`): the type prefix, a dash, the last 12 hex digits of the UUID (`FILE_NAME_DIGITS`) and `.md` (D-056, ADR-0004), e.g. `SR-825b7146fb54.md`. Given once on create; nothing renames a file afterwards (title, type or a longer displayed short ID, SR-001 AK2, SR-084 AK3).
- `createElement(workspace, input, extraFindings?)`: type from `typeForNewElement`; a new UUID from `crypto.randomUUID()` (v4, D-017); the status is the one status with `initial: true` (none or several: `input.invalid`, `details.reason: "initial-status"`; ADR-0002 rule 6; through `element.create` such a metamodel is already invalid, so the command refuses with `workspace.read-only` first) when the type has it and it is not marked invalid (#350), else the type's first status in metamodel order that is not marked invalid, as a new element must not be superseded at once (D-044); a type without status, or one whose statuses are all marked invalid (#344, option 1), gets no `status` line (#306); the title goes under the key of the property with the meaning `title` (`metamodel.meaning-unassigned` when none, `input.invalid` with `reason: "no-title-property"` when the type lacks it). `properties` may only hold properties of the type (`reason: "not-a-property"`), never a relation kind (`"relation"`: add relations with `relation.add`), `id`, `type`, `status` (`"structural"`) or the title key (`"title"`). Every key is checked first, then `null` and `[]` are left out (so `status: null` is refused). The folder is created only after every check passed and the bytes are verified. Repository: `input.repository` or the main one (`reason: "unknown"` / `"not-available"`). Folder: `input.folder` or the type key, relative to the repository, created when missing (`createFolder` of the files block); `.` is the repository folder. Before anything is written (also into the default type folder), a file the element walk would not list is refused with `input.invalid`, `reason: "not-listed"`, and `details.rule` and `details.path` say why and where (`newFileTarget` in `src/model/discover.ts`, #183): `skipped-name` (`.git` or `node_modules` in any case and with trailing dots or spaces, as Windows and macOS read them), `ignored` (an `ignore` glob), `nested-repository` (give `repository` instead), `git-entry`, `link`, `unreadable`, `not-a-folder` (a file in the way), `spelling` (an existing folder spelled in another case; `details.existing` is the spelling on disk). A spelling that differs from the existing folder only in its Unicode normal form (NFC input, an NFD folder on macOS) is not refused: the path is judged again as spelled on disk, and the file is written there under that spelling (#194). A name Windows changes or refuses (trailing dot or space, `<>:"|?*`, control characters, device names such as `CON` or `nul.txt`, short names such as `GIT~1`) is refused with `reason: "not-portable"`, and so is a folder still to create whose name holds an invisible format character (`\p{Cf}`: zero-width and direction marks, byte order mark, soft hyphen; `rule: "invisible"`, #194). After `createFolder` the check runs again on the folders as they are now, before the file is written, and the file goes under the spelling it finds (a file system such as HFS+ may store a new name in NFD). So ReqSeq never writes below `.git` (D-036). The bytes come from `editElementFile` on an empty file: `id`, `type`, `status`, the title, then the properties in the order of the type; then the body `bodyForText` (`src/files/text.ts`, ADR-0004 "Text layout", #308) makes of the text: one blank line after the closing `---`, which is not part of the text, then the text with LF and a final line break; an empty text is nothing. Written with `writeFileAtomic(..., null)`, which never replaces a file.
- `updateElement(workspace, input, extraFindings?)`: `ref` is a UUID or short ID (`resolveRef` in `src/model/resolve.ts`: `ref.unknown`; `ref.ambiguous` with `details.candidates` for a short tail or two files with one UUID). An element of a type the metamodel does not know is `element.read-only` (SR-016 AK3). `set`/`unset` follow the key rules of `properties` (and a key in both is `reason: "set-and-unset"`); the schema already refuses `id`, `type` and `status`. The file is read again; when it is gone, faulty or its SHA-256 is not the store's, the store is reset and the call fails with `file.changed-on-disk` (the next call works on the new content). The write precondition of the caller (`expectedFile`, SR-106): with `expectedFileSha256` that is not the SHA-256 of the file as read (which then equals the store's), the call fails with the same `file.changed-on-disk` before anything is planned, also when the input would change nothing, and without resetting the store; the result gives `fileSha256`, the SHA-256 of the file as written or, with no change, as read, for the next save. `repository` narrows `ref` as in `getElement` (`resolveRef` with a copy, #255). `editElementFile` rewrites only the lines of changed keys and the text; the text becomes the body through `bodyForText`: a text equal to the stored one (line endings aside) changes no byte, any other gets LF and a final line break in the file's layout (the blank line after `---` stays, a file written without it stays without, #308); unknown keys, comments, quoting, key order, CRLF and byte order mark stay byte for byte (SR-102, SR-016 AK2). New keys are appended in the order of the type. No change, no write (`files: []`). `affected` (SR-024 AK2, AK3): when the write changed what the version is computed from (`elementContent`: the canonical content of ADR-0005 with a non-finite number written out, `comparableContent`, so an element without a version (`.inf`, `.nan`, #276) is compared too; of the file as read, `undefined` when an embedded image could not be read (`file.faulty`), against that of the written file), the number of distinct other elements whose files hold a relation or an inline reference to it (`directlyAffectedCount`, `src/model/affected.ts`, on the incoming index of the store before the write, built before `recordWrites`, so the carry of #273 takes it over); 0 for a title, a property that does not count, or no change. At 50,000 elements and 200,000 relations a content save with the count takes about 0.11 to 0.14 s once the index of the store was built, also a second save right after a save, which gets the index carried over (#273).
- Both return the element as `elementView` builds it (`src/model/view.ts`, `data-export.schema.json#/$defs/element`): text (`elementText`: the body without the blank line after `---`, which is not part of the text, #308), version (`elementVersion`, which counts the images the text embeds, read with `embeddedImages` in `src/model/images.ts` by the normative rules of ADR-0005 "Files", #178; a reading error other than "not there" is `file.faulty`), properties (every key but `id`, `type`, `status`, the title and relation kinds; unknown keys included), the element's own relations (kind, meaning, `direction: "out"`, target UUID, the repository of the target (`targetRepository`: the one looked in, also when the target is not available; left out only for a stored `repository` that is not text, #416), `targetState` from `targetState(layout, store, record.repository, target)` (D-058, see relation targets below), `accessible` only when it is `available`, then also short ID and title, also across repositories (SR-005 AK2); a target in a repository that is not on this machine shows only the short ID `UNKNOWN-<tail>` (`ShortIds.tail`; its type is not known, prefix per the decisions on #154 and #193) and no title (SR-006 AK1); stored version; then the targets of properties of kind `relation` such as `validity` and `packages`, in the order of the properties, with the property key as kind, `property: true` and no meaning, the same target state, short ID and title (#187), while `properties` keeps them as stored; items are read as the checks read them, `relationKey` + `relationItems` + `hasId`: a list for a relation kind or a property with `many`, one target otherwise) and the value-kind hints with their lines (SR-085), the hints on relations between types the metamodel does not allow (`relationTypeFindings`, SR-086), then the hints on its relations to superseded elements (`supersededFindingsOf`, SR-072 AK2); while the metamodel is not valid it gives none of these hints (#208, decision of spec question #220 option 1), like the whole-workspace states. A superseded element (status marked `invalid`) also lists the relations from its successors after its own (`successors.ts`, SR-072 AK3), also while the metamodel is not valid, since they are relations, not hints: kind, `meaning: "replacement"`, `direction: "in"`, the successor's UUID and repository, `targetState` of the successor (`available` with short ID and title, also across repositories; `ambiguous` without them, SR-088) and the version it stores when that is one; the superseded file itself has no relation to them (D-045). Other relations pointing at the element and `affected` come with stage 2; `element.get` adds the version date (`versionDates`, below). `files` are relative to the workspace root (`../sensor/...` for another repository). After a write the element store gets the file as written in place (`recordWrites`, #166; a reset when that could differ from a full read), and the states built on it (short IDs, value-kind and duplicate-ID problems) follow; the short ID of a new element is computed from the store before the write plus the new record, without reading every file again.

Reading one element (`src/model/get.ts`, used by `element.get` and `element.resolve`; `element.resolve` adds `current`, whether a given version equals the `version` of the element shown (SR-060 AK2): `"current"`, `"outdated"`, `"unknown"` when the element has no version (a value that counts has no normal form, #276), `null` when no version was given; all strings, so no caller takes `"unknown"` for true. It refuses a version of another normal form than `NORMAL_FORM` with `input.invalid`, names the candidate of a short ID with an outdated prefix, see `withTail`, and takes the same input `versionDate` as `element.get`):

- `getElement(workspace, ref, extra, withDate, copy)`: `resolveRef` (`ref.unknown`, `ref.ambiguous`; with `copy`, the inputs `repository` and `file` of `element.get` and `element.resolve`, only the elements `ref` names there, #255), then the file is read again (the store keeps no text) and shown with `elementView` (returned as `{ element, fileSha256 }`, the SHA-256 of that file, SR-106), with the successions of `successionsFor` for the element (SR-072 AK3) and, through `successionsOf`, for the targets of its relations to superseded elements (the successors their hints name, looked up in the succession index instead of a walk over the store, N-036). A file changed since the store read it is shown as it is now. A file that is gone or no longer holds the element makes the store be read again: `file.faulty` with its errors when the new store reports the file as faulty (SR-008), `ref.unknown` otherwise. `readOnly` is always given: true for a type the metamodel does not know (SR-016 AK3), while the metamodel is not valid (SR-011 AK3), and when this process cannot write the root folder of the element's repository (`isWritableFolder`, as `workspace.status` checks it; unknown on Windows; SR-018 AK2). While the metamodel is not valid there are no hints (#220 option 1). A valid metamodel may assign the meaning `title` to no property (SR-013 AK3): then the title is empty, the key stays under `properties`, and a hint `metamodel.meaning-unassigned` (warning, the text of `requireMeaning`, `meaningUnassignedMessage`) names the missing assignment. `extra(context, record, withDate)` (`ElementHints`, async) adds hints of blocks that import the model (`element.get` passes `elementHints` of `src/hints/element.ts`: the superseded variants of SR-040 AK3 and the outdated relations of SR-026 AK3); `showElement` asks them only while the metamodel is valid and `elementView` lists them after its own (`extraFindings`), with lines from the file just read (a `LocatableFinding` with `at: "line"` keeps the line it has: an inline reference); `element.create` and `element.update` pass the same function to `createElement`/`updateElement`, so they return the element as `element.get` shows it (apart from `readOnly` and `versionDate`). `showElement(context, ref, extra, withDate, copy)` is the same on given states. `element.get` refuses `view` (SR-043, stage 5) with `input.invalid`. `versionDate` is the date of the version shown, only with the input `versionDate: true` (`versionDates`, D-013, ADR-0005 "Where the date is shown"; `null` for content no commit has and when Git cannot tell); without it no git runs and the field is left out (SR-082 AK3). Left out: other incoming relations and `verification`/`validation`; the variants that replace or exclude the element (SR-046, stage 5) have no field in the schema yet.

Setting a status (SR-017, D-030, `src/model/status.ts`, used by `element.setStatus`):

- The status values the tool offers are the keys of the metamodel's `statuses`, in metamodel order (`statusValues(metamodel)`; `metamodel.get` lists the statuses with names). There is no fallback to the standard model's values. For one element they are the statuses of its type (`statuses` of the effective type, #306; every status unless the type restricts them, none for a type without status).
- `setElementStatus(workspace, { refs, status })`: `status` must be one of them, else `input.invalid` with `details: { status, reason: "unknown-status", allowed }`; and a status of each element's type (`assertTypeHasStatus`, #306), else `input.invalid` with `details: { ref, type, status, allowed, reason }`, `reason` `type-without-status` (the type has no status) or `status-not-allowed` (`allowed`: the type's statuses). Any metamodel status may be set, also one marked `invalid` (superseding with a successor is `element.supersede`, SR-072). The value always comes from the caller; the tool never picks one (ADR-0002 rule 6). Every check comes before the first write: the status, each `ref` (`resolveRef`), `assertElementWritable` (SR-016 AK3), and that no file changed since the store read it (`file.changed-on-disk`, store reset). Only the `status` line is rewritten (`editElementFile`; a missing key is appended); UUID, type, file name, comments and everything else stay. A ref given twice is written once; an element that has the status already is not written. The files are written with `writeElementFiles`. Returns `files` (relative to the workspace root) and `problems`: with a status marked `invalid`, the hints on relations to these elements (`supersededTargetProblems`, the same as `element.supersede` gives, SR-072 AK2); otherwise none.
- `status: null` removes the `status` line instead (#343): only on elements whose type has an optional status (no status, or only statuses marked invalid: `hasWorkingStatus` is false), else `input.invalid` with `details: { ref, type, status: null, allowed, reason: "status-required" }` (`assertStatusOptional`), checked before any write like the rest. The line goes with the lossless `remove` edit (ADR-0007), the element stays (D-045); an element without the line is not written; `problems` is empty. The metamodel gives an `info` note `metamodel.invalid` for every type, not abstract, whose statuses are all marked invalid ("Type X has an optional status (only invalid statuses: ...)", `metamodel/load.ts`), so a metamodel that marks them all invalid by mistake is visible.
- `readUnchanged(workspace, layout, record)` (`src/model/write.ts`, also used by `element.update`): the file of a stored element read again for a write; `file.changed-on-disk` (store reset) when it is gone, faulty or its SHA-256 is not the store's. `readAllUnchanged(workspace, layout, items)` does the same for many records at once (`element.bulkUpdate`): the files of each repository are read 32 at a time (`readElementFiles`), then checked in order, so the first changed one throws.
- `writeElementFiles(workspace, layout, writes, { titles, concurrency })` (`src/model/write.ts`, for every command that changes existing element files: `element.setStatus`, `element.supersede`, `element.bulkUpdate`, `relation.add`, `relation.remove`, `hint.confirm`; `titles` is the metamodel and the element store the command read): writes each file atomically against the snapshot it was read with and returns, per file, the element as written (`writtenElement`, which verifies the bytes), the snapshot it replaced and its path. All-or-nothing is best effort: a write can still be refused after every check (`file.read-only`, a file changed in the meantime, a disk error). Then the files already written are written back with their bytes as read, only while they still hold what the call wrote (nothing is deleted), and the error is thrown again with its code; `details.written` lists the files not restored (relative to the workspace root); it is absent when every file was restored. After the writes the element store gets all written files in place with one `recordWrites` call (#166); after a failure it is reset. `concurrency` (default 1) writes several files at a time: each write syncs the file and its folder, so `element.bulkUpdate` writes 16 at once; after the first failure no further write starts, the writes in flight end, and every written file is restored as above.
- Stored titles follow their targets (`withCurrentTitles`, `src/model/relation-titles.ts`; decision on spec question #307): every file `writeElementFiles` and `updateElement` write gets, before the write, the current title of each same-repository relation target it stores (relation kinds and relation-valued properties, list or single), so `element.update`, `element.setStatus`, `element.supersede`, `element.bulkUpdate`, `relation.add`, `relation.remove` and `hint.confirm` refresh them. Only the text of a stale `title` scalar changes (`set-scalar`, its own quoting), never a version, an entry naming another repository, an entry without `title`, an unknown key or the label of an inline reference (text counts to the version). The title comes from the element store the command read (`writeElementFiles` takes it as `titles`; for an element the same call writes, from its planned bytes). An entry the same call set (a new target, whose title `currentTarget` just read from disk) is left as set: only entries the file held before, `version` aside, are refreshed. A missing, ambiguous or untitled target and a title the writer cannot change in place (alias, anchored scalar, block scalar; `set-scalar` with `ifPlain`) are left as they are, without blocking the write. All stale titles of a file go in one pass of the writer. A planned write that changes nothing is passed as it is, and nothing is written that the command would not write. Cost: one parse and one writer pass per written file and one `byId` lookup per relation entry (N-036; perf suite `test/perf/relation-titles.test.ts`). The `element.bulkUpdate` preview does not show the refresh.

Changing one property of many elements (SR-071, `src/model/bulk-update.ts`, used by `element.bulkUpdate` with the elements of its selection, `resolveSelection`):

- Inline references in Markdown properties (SR-127): `element.create`, `element.update` and `element.bulkUpdate` (`set`, `add`) give a reference in a value of a property marked `markdown` the version of its target (`setMarkdownReferences` in `src/model/targets.ts`, which runs `setInlineReferences` over each string against all strings the property stores now), only for the properties the input sets. `ref.unknown` and `ref.ambiguous` name the property in the message and in `details.key`.
- `bulkUpdateElements(workspace, selection, { property, operation, value, confirm, expected })`: `property` must be a property of the metamodel, not the title key and not a relation kind (`input.invalid`, `reason` `not-a-property`, `title`, `relation`; `id`, `type` and `status` are refused by the schema, ADR-0002 rule 6). `set` replaces the value; `add` appends the items an element does not hold yet (a property with `many`; relation targets are the same by UUID and repository), each on its own line; `remove` removes the key, or with a value only these items (`many`), the key with its last item. `set` and `add` need a value (`value-missing`), an empty one is refused (`value-empty`), `add`/`remove` with a value on a property without `many` too (`not-many`). Choices by key or display name (`withChoiceKeys`); relation targets as `element.update` stores them (`setRelationTargets`; a target that `add` adds gets `currentTarget`, read once per call). These are spec question #353, option 1.
- An element whose type does not have the property (`not-a-property`) or whose type is unknown (`unknown-type`, SR-016 AK3) is skipped and named with its short ID and a message (AK3). The other files are read with `readAllUnchanged`, edited with `editElementFile` (only that key, SR-102) and, with `confirm`, written with `writeElementFiles`. Without `confirm` nothing is written: the result is the plan (AK2). `expected` with `confirm` refuses (`reason: count-changed`, nothing written) when the plan now affects another number of elements than the preview showed.
- Returns `applied`, `affected` (`{ id, shortId }` in store order), `unchanged`, `skipped`, `files` and `problems`: the value-kind (SR-085) and relation-type (SR-086) hints at the property in the affected elements as written, or as a preview would write them (`locateIn`, lines in the new bytes).

Superseding (SR-072, D-045, `src/model/supersede.ts`, used by `element.supersede`; there is no delete):

- `supersedeElement(workspace, { ref, status, successor?, relation? })`: `status` must be a status of the element's type (#306) that the metamodel marks `invalid` (D-044), else `input.invalid` with `details: { status, reason: "unknown-status" | "not-invalid" | "status-not-allowed", allowed }` (the type's invalid statuses; the message names the type when it has fewer than the metamodel). A type without invalid status is `reason: "no-invalid-status"`: its elements cannot be superseded. An element without status of a type whose statuses are all invalid gets the `status` line, appended at the end of the frontmatter like every new key (ADR-0007, #344). The element is resolved before the status is checked. The tool never picks it (D-030). Only the `status` line of the element's file changes.
- With `successor`, a relation with the meaning `replacement` (D-059) goes from the successor to the element and is written into the successor's file (ADR-0004: source = new, target = old). The kind is `relation` or the one replacement kind whose `source-types` and `target-types` allow the two types (`allowsType`, subtypes count): none is `relation.not-allowed`, several is `input.invalid` with `reason: "relation-ambiguous"` and `candidates` unless the successor already has a relation to the element under exactly one of them, which is then used (so a repeat needs no `relation`, #196) (the standard model has `supersedes` and `replaces` for two system requirements), a named kind without the meaning is `reason: "not-a-replacement"`, a named kind that does not fit is `relation.not-allowed`; no replacement kind at all is `metamodel.meaning-unassigned` (SR-013 AK3). `relation` without `successor` is `reason: "relation-without-successor"`; the element as its own successor is `reason: "self"`. The target is `currentTarget` (UUID and current version; title in the same repository, repository name across repositories, D-058), appended with `append-item`. A target the successor already has under that key (same UUID and repository) is kept with its stored version and not added again (#177 (a)).
- Every check comes before the first write (the element's ref, status, the successor's ref, `assertElementWritable` for both, SR-016 AK3, the kind, `readUnchanged` for both files); both files are written with `writeElementFiles`. A file that would not change is not written, so a repeated call writes nothing. Returns `files` and `problems`: the hints on relations to the element.

Adding and removing relations (#264, `src/model/relation-write.ts`, used by `relation.add` and `relation.remove`; ADR-0004: a relation lives only in its source's file):

- `addRelation(workspace, { source, kind, target })`: `source` and `target` are UUIDs or short IDs (`resolveRef`); the source must be writable (`assertElementWritable`, SR-016 AK3). `kind` must be the key of a relation kind (`keyDefinition`: a property key is `input.invalid` with `reason: "property"`, any other key `reason: "unknown-relation"` with `allowed`, the relation kinds `relation.options` offers the source's type; `relationKindFor` in `src/metamodel/relation-options.ts`). A relation the source already has under the kind (same UUID and repository) with a valid version is kept with its stored version and nothing is written (#177 (a)). When it has the relation only without a valid version (a migration script writes `{ id, title }`, ADR-0005), the first such entry is set anew in its place with the same checks as a new relation (`replace-item`, its line only), and `problems` holds one `info` `relation.version-added` with the line, `targetId` and `currentVersion` (ADR-0004 "Setting a target", #302). Otherwise the target is `currentTarget` (UUID and current version, SR-021 AK1; title within the repository, repository name and no title across repositories, SR-005 AK1, D-058), checked with the rule of SR-086 (`relationTypeFindings` on the source with only the new relation): a relation the metamodel does not allow is refused with `relation.not-allowed` and the message of the hint (assumption of #264: the tool sets only allowed relations, SR-067 AK1; a target of an unknown type is allowed, as in the check). A value under the key that is not a list is `reason: "not-a-list"`. The target is appended with `append-item` (one flow mapping per line, SR-102) and written with `writeElementFiles` (`file.changed-on-disk`, `recordWrites`). Returns the written files, the kind, the position of the relation and the source as written.
- `relation.add` then looks for a cycle when the kind has the meaning `derivation` (SR-067 AK3): on the store after the write, `closedCycle(graph, child, key, index)` (`src/trace/new-cycle.ts`) walks up from the target (`walkDerivation`, `direction: "up"`) on `upwardGraph`, the derivation graph without the incoming index of the whole store (a walk up reads only each element's own relations, so only the elements above the target are read); when it reaches the source, the relation closes a cycle (an element that derives from itself is one too), and `cycleFindings` with `locateFindings` give one `trace.cycle` warning per element of that cycle (the source first, then the target and up), the same messages as `workspace.check` (SR-090). The hint names the shortest way back through the new relation (breadth first), not every element of the strongly connected component it joins; `workspace.check` reports those. The relation is written anyway: AK3 asks for a hint. A repeat call where nothing is written gives the same hint.
- `relation.options` (`src/commands/relation/options.ts`, SR-067 AK1, AK2): the relation kinds an element may get, from `relationOptions(metamodel, typeKey)` (`src/metamodel/relation-options.ts`), the rule `relation.add` checks: in metamodel order every relation kind whose `source-types` allow the element's type and whose `target-types` allow some type (`allowsType`, subtypes count; a kind with `target-types: []` can never be set and is not offered), each with its key, name and `targetTypes`: every type of the metamodel the kind allows, subtypes included, in metamodel order. An element of a type the metamodel does not know gets none (SR-016 AK3). `kind` keeps only that kind (none when the type does not allow it); a key that is no relation kind is the `input.invalid` of `relation.add`. Whether the element may be written does not matter here. The target is searched with `element.search` and `selection.where: { type: targetTypes }` (AK2): the search then shows only elements of allowed target types, with or without `subtypes`, and since both are catalog commands every access gives the same result. A target of an unknown type, which `relation.add` accepts as the check does, is never offered.
- `removeRelation(workspace, { source, kind, target, repository? })`: source and kind as above (no type check: a relation the metamodel does not allow can be removed). A target given as UUID is matched against the stored items as written, so a relation to a target that is gone (SR-089) can be removed; a short ID names an element and only items into its repository. Every item naming the target is removed (`remove-item`, comments of the others stay), the key with its last item. `repository` keeps only the items into that repository (an item without `repository` points into the source's own, D-058); with a short ID it must be the element's repository (`input.invalid`, `reason: "repository-mismatch"`). Items with that UUID into several repositories are `ref.ambiguous` (give the short ID or `repository`) when one of these repositories may hold an element with the UUID: it has one, is not on this machine, or is not in the workspace file. When each is here and has none, no short ID could tell them apart, so they are all removed. Nothing to remove: no file is written, and `problems` holds one `info` `relation.not-found` naming the source, kind and target. No element and no file is deleted (D-045).

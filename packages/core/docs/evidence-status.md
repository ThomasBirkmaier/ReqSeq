# Evidence block: status and degree (`src/evidence/`)

Part of the [`@reqseq/core` README](../README.md). It covers the verification status, indirect verification, the validation status and the verification degree; the records, folders and index are in [evidence-records.md](evidence-records.md).

The verification status (Nachweisstatus) and validation status (Validierungsstatus) are derived views of the records; they never change the `status` of an element (D-030, ADR-0012 "Status rules").

## Verification status

SR-031 (ThomasBirkmaier/ReqSeq-archive#43), `status.ts`; the rules are ADR-0012 "Status rules".

- `recordStatusOf(records, kind, current, view)`: what the records of one element say in a view, `open`, `passed`, `failed`, `inconclusive` or `outdated`. Only records of `kind` that hold in the view count (`holdsIn` of `holds.ts`: in the core a record without variant, in a variant a record for it, SR-047, and also one without variant when `independent`, the element's repository is marked `variant-independent`, SR-173; there both are pooled and the rule below decides). `current` is the version in both normal forms (`VersionForms`, ADR-0005), and a record of either form is of it (`sameVersion`). Of the records of the `current` version the newest (`date` as an instant, an unreadable date the oldest) decide; when several share that newest date and one failed, the result is `failed` (ThomasBirkmaier/ReqSeq-archive#525 Q2), else one inconclusive gives `inconclusive` (#807 Q3). An inconclusive record of kind `verification` (only through the state; the format refuses it) counts as a record of another version. Records only of other versions are `outdated` (AK4), none is `open` (AK1); with `current` undefined (no version, ThomasBirkmaier/ReqSeq-archive#276) every record is of another version. One pass, any order. SR-038 uses it with `validation`.
- `verificationStatusOf(records, current, view, independent, count = 0)`: the same for `verification`, `passed` named `verified` (AK2, AK3); the status of `ownVerificationOf`.
- `ownVerificationOf(records, current, view, independent, count)` (SR-031 AK5 to AK8, D-072, #963): `{ status, criteria? }` for an element with `count` acceptance criteria (`StatusSource.criteriaOf`: `criteriaCount` of the property with the meaning `acceptance-criteria`). With 0 it is `recordStatusOf` for the whole requirement (AK7). Otherwise one pass keeps one tally for the records without `criteria` (AK6) and one per number named (up to `count`), then each criterion merges the two (newest wins, a failed one a tie). First that holds: a criterion failed, `failed`; all verified, `verified`; no counted record at all, `open`; none of the current version, `outdated` (both over every counted record, whatever it names; plan review B1); a criterion without record, `open`; else `outdated` (AK8). `criteria` is `{ verified, total, notVerified? }` (`$defs/criteriaCount`); without any counted record `open` with 0 of `count`, one frozen result per count (`openWith`, no allocation per element). The evaluator (`indirect.ts`) gives it for an own-record status, and `entryOf` (`verification.ts`) writes it into the entries of `verificationOf` and the matrix. Cost: O(records + count) per element; the count is read from the element in memory, no version or file read.
- `statusSource(metamodel, index, independent)`: `independent` is `variantIndependentOf(layout)`, the repositories the workspace file marks (SR-173), asked per element by `StatusSource.independent` (the element's repository, not the record's folder; twins follow their own, #817 Q1, Q8). Further the requirement types (meaning `requirement`, own or inherited), the need types (meaning `need`, SR-038), the validity property, the records by element, and whether an element is emergent (its property with the meaning `emergent` is `yes`, SR-035); without `index` no element has records (the metamodel is not valid: the versions follow the metamodel, so the records are not compared and every requirement is `open`).
- `verificationState` (`verification.ts`): one memoised workspace state, reset with the metamodel, the layout (so also when the mark `variant-independent` changes, SR-173) and the records, carried over a change of the element store (below) and over one record written by `evidence.record` (#278, [evidence-records.md](evidence-records.md) rule 8: the records of the element's UUID and the volatile ones, with their ancestors, are computed again against a new source; the versions are kept), that `evidence.status`, `element.get`, `element.resolve` and the filter share, so they give the same status by construction (SR-080 AK2). It holds the source, the variants, the child rules and the evaluator of `indirect.ts`, and the current versions it has read. `prepare(elements, { own })` walks down from `elements` through their counted children (iteratively, each element once for the life of the state), down to the children with an own record in every view they apply in, and reads the versions of those with records it does not know yet in one batch (`currentVersionsOf`); with `own` also those of `elements`. A page or a leaf reads only what it needs, and a repeated `element.get` of the same parent reads nothing (plan review B1, SR-082 AK3); `versionBatches()` counts the batches for tests and measurements. `workspaceStatusOf(source, variants, children, read, scope)` builds it from parts (tests).
- `verificationOf(status, element, shown?)`: the `verification` entries of `data-export.schema.json#/$defs/element`: the views of `WorkspaceStatus.holders` (the core, then each variant in store order, each with what its view holds), each where the element applies, with `missingChildren` (SR-034); undefined for an element that is no requirement.
- `workspaceStatus(workspace, shown)` gets the state and prepares it for the elements shown (a page, or the one element of `element.get`); `withEvidenceStatus(status, record, element, forms)` adds the verification entries and the validation status to a shown element, its own records measured against the `version` it shows in both normal forms (`forms`, `storedForms`; a write passes those `currentVersionsOf` reads for the file as written, also with images) (`Shown`, never kept). Children are measured against the versions of the store as read: a change made outside ReqSeq shows once the watcher's batch carries the state over (next bullet) or resets it (review of ThomasBirkmaier/ReqSeq-archive#581, N2); every reset of the store, the metamodel or the records builds a new state.
- Carried over a change of the element store (ThomasBirkmaier/ReqSeq-archive#698, ADR-0008 file-watching "carry"): a save or a watcher batch (`applyStoreChange` with a `StoreUpdate`) gives `verificationState` a `carry` hook (`carryStoreUpdate`) instead of a reset. The hook takes everything it uses synchronously inside `Workspace.replace` (review B5 of the ThomasBirkmaier/ReqSeq-archive#698 plan): the new store `update.to` and the memo of `incomingState`, which was carried first and holds the index of exactly that store; the metamodel, the layout and the records are those of the old state (`StatusInputs`), so two changes right after each other each pair their own store and index, and nothing calls `get` later. It resets the state when the memo has no index for `update.to` (the change named more than `CARRY_LIMIT` UUIDs, or the old store had none). It also takes the memo of `viewRuleIndexState`, carried first (a dependency, `carryViewRuleIndex`, #215), and reads the rule index of `update.to` from it with `viewRuleIndexIn` (`StatusInputs.rules`), which builds it only when the old store had none. `carriedStatus` then builds the status of the new store from the old one, which it never changes (a command that still holds it keeps a consistent view): when the old state had no children (the metamodel is not valid, or has no derivation) or the variants are not the same records in the same order (the views change), a new state from the values of the change, with nothing kept; otherwise it forks the versions read, the walks of `prepare` (`walked`) and the caches of the evaluator (`carriedEvaluator` in `indirect.ts`: candidate children, seeds below, the core, neutral and variant memos) without what the change may reach: each is a `LayeredMap` (`model/layered-map.ts`, #215), whose fork shares what the memo held, drops the affected keys and keeps what either state finds later to itself, in O(changed); a key it drops is a marker among the fork's own entries when its base holds the key (a base never changes, so other keys need none), and from `compactAt` own entries and markers a fork gets a base of its own, so the entries a fork dropped (and the records they name) stay alive until then, at most `compactAt` per memo. Affected are the records of the UUIDs of the update (before and after: the changed records and their twins, since a twin that comes or goes changes the children of its UUID, SR-088), and the records whose version may change while their file does not (`volatile`: one that embeds images, which the watcher does not report, or one whose read gave no version; review S4), and the elements the rule items of the changed records name in each store (`ruleTargetsOf`: a `replaces` added or removed, or a validity of its source changed, moves its target in or out of a view; SR-041), with their ancestors before the change (in the old store) and after it (in the new one), found by following every derivation item to every record of its UUID, a superset of the parents the trace block resolves. A child stores its derivation (ADR-0004), so the old and the new parents of a changed element are among them. Their entries are dropped (by repository and UUID, so twins share them; the memos by record drop the records of both stores under those keys, so none keeps a record of an earlier store), the versions of the old records among them too; the next `prepare` reads the versions of the new and the volatile records again in one batch and walks again from the ancestors, and `versionBatches()` goes on counting. It resets also when the update names more than `CARRY_LIMIT` UUIDs, and builds afresh when the status in place is of another store than `update.from`. Cost at N-036 (`test/perf/evidence.test.ts`): opening the top right after one changed file takes about 35 to 60 ms (about 550 to 700 ms after a reset of the status state), about 140 to 170 ms after a change deep below it (3,601 ancestors to walk again); the caches are forked, not copied (#215): the CPU of one edited file in a warmed server went from 156 to 158 ms to 115 to 125 ms (`test/perf/watch-carry.test.ts`), where copying them cost 35 to 45 ms; a lookup through a fork that misses its own entries looks into the base too (two lookups instead of one), so the open after a deep change is about 130 to 145 ms with copies. The path of records that embed images or had no version (read again, with their ancestors, at every change) is not measured at N-036: the generated workspace has no images. Tests: `verification-carry.test.ts` compares the carried state with a fresh workspace for every element and view after each kind of change (text, derivation added, removed and pointed elsewhere, validity at the top and deep in the tree, an invalid status, emergent, twins, a parent that gets a twin, a file deleted and created, a type changed, a missing target that comes, two repositories with a parent in the other one, a UUID in both and a move between them, seeded random changes with partly filled caches, only the top prepared), the old caches unchanged after a change that removes a variant's only seed, no record of an earlier store kept over a chain of changes, two changes before the first carried value resolved, a `prepare` of the old state still reading, a changed image and a version that could not be read, and every reset case.

Who shows it:

- `evidence.status`: one page of a selection (`limit`, default 200, and `offset`, as `element.list`), each element as `element.list` gives it (`listElements`, current versions of the page only) with `verification`; `total` and `incomplete` of the whole selection; `names` (ThomasBirkmaier/ReqSeq-archive#588): the variants of the views and the missing children the page's `verification` gives by UUID only (`verificationNameIds` of `evidence/names.ts`, `namesOf` of the model block), each once, so the readable CLI names them by short ID though they are not on the page. `element.get` and `element.resolve` name them the same way (`shownWithNames` of `data/`, #456).
- `element.get` and `element.resolve`: the element shown with `verification`, against the version of its file as read (`ShownElement.record`).
- `baseline.get` with `withEvidence` (SR-094, `evidence/baseline.ts`, [baselines](baselines.md)): rows per view of `holders` from the own records that count for the baseline, at its versions, never `indirect`; `baselineStatusOf` counts the acceptance criteria of the baseline version (SR-031: the element's values when it is the current version, else `versionDatesAndValues` of the walk of the version dates, page only; unknown when Git does not have it, #985).
- The filter (`query/evidence.ts`, `evidenceStatusState`): the conditions `verification` and `{relation: {direction: evidence}}` (`hasVerificationRecord` in the view of the selection, else the core). Only requirements with records get a current version (`currentVersionsOf`: their files, or the whole store when they are at least a quarter of it), so a workspace without records reads no element file for the filter. The provider is reset with the metamodel, the element store and the records.

Cost at N-036: one pass over the records of each element shown; the filter computes the current versions of the requirements with records once per store (`currentVersionsOf`, the cost ThomasBirkmaier/ReqSeq-archive#489 measures for `trace.graph`), measured with records in E4. A filter that asks only "has evidence" reads none: the provider reads them on the first `ready()`, which only the `verification` and `validation` conditions await (#439); E4 measures that path as its own row.

`element.create` and `element.update` return their element with `verification` and `validation` as `element.get` gives them, from the record of the store after the write (`writtenWithNames` in `data/shown.ts`, #214), and `names` for the variants of its validity and the views and missing children of `verification`, so the CLI shows them by short ID as after `element.get` (#1216); `replacedBy`, `excludedBy` and `incomplete` stay with `element.get`. In a process that has not built the status yet (a single CLI or MCP call), the first write builds it like the first `element.get`; in the app and the API it is carried over the save (above). The `evidence.outdated` hint of SR-025 AK4 (`hints/evidence.ts`) follows the status: it is given for each kind and variant of an element's records whose status in that view is `outdated`, also by one acceptance criterion (SR-031 AK8; #201).

## Indirect verification and emergent

SR-034 (ThomasBirkmaier/ReqSeq-archive#46), `indirect.ts`; the rules are ADR-0012 "Status rules", bullet "Indirect verification".

- `childRulesOf(context)`: the child rules of a trace context: `childrenOf` gives the derivation children of the trace block (`childrenOf`, so one named only by an ambiguous relation is none), `counts` is false for a status the metamodel marks invalid (D-044, AK3). Undefined while the metamodel is not valid or no relation kind has the meaning `derivation`: then no element has children and nothing is indirect, without `metamodel.meaning-unassigned`.
- `verificationEvaluator(source, children, currentOf, scope)`: `scope` (`ViewScope`) says which elements a view holds and which variants may remove an element; `verificationState` passes `ruleScope` of the store's view rule index, so a core requirement a variant excludes or replaces has no entry for it and counts as no child there (SR-043 AK7, SR-047 AK3), and its children count where their validity puts them (SR-041 AK5). `validityScope` (validity alone) is for tests without replacements or exclusions; `indirect-oracle.test.ts` checks the walk with random removals and with the exclusions of a generated workspace. `(element, view, shown?) => { status, missingChildren? }`, undefined for no requirement or a view the element does not apply in. A requirement with a verification record that holds in the view has its SR-031 status there, against `shown.current` when given, else `currentOf` (ThomasBirkmaier/ReqSeq-archive#526 Q1, Q4). One without takes it from its counted children (type with the meaning `requirement`, `counts`, held by the view, each once; ThomasBirkmaier/ReqSeq-archive#526 Q2): all `verified` or `indirect` gives `indirect` (AK1), none gives `open` (ThomasBirkmaier/ReqSeq-archive#526 Q3), else `open` with the UUIDs of the direct children that are `open`, `failed` or `outdated`, in child order, each once (AK2; ThomasBirkmaier/ReqSeq-archive#526 Q4). The walk is iterative with an explicit stack; an element being computed counts as `open` for its descendants, so an element on a derivation cycle of elements without own record is never indirect, whatever is computed first (ThomasBirkmaier/ReqSeq-archive#526 Q5). Results from children are kept per view by repository and UUID (twins of one repository share their children, SR-088); results from own records are not kept, so `shown` never leaks into another call.
- `hasOwnRecordIn(source, element, view)`: rule 1, a verification record that holds in the view; in a variant also one without variant of an element of a marked repository (SR-173; the mark is asked only when such a record exists). Validation records never count (D-007). The views in which a UUID has an own record (the core, the variants by UUID) are found once per UUID and kept with the source.
- Shared views (ThomasBirkmaier/ReqSeq-archive#698): besides the core and the variants the evaluator keeps an internal neutral view, the applicability of the core (no validity) in which only the records without variant of an element of a `variant-independent` repository hold (SR-173: they hold in every variant, so they are no seed). In a variant `v` an element whose subtree holds no seed of `v` has the neutral result: a seed is a requirement whose validity names `v` (repository and UUID, as `appliesIn`), an element with a verification record for `v` (its UUID, as `holdsIn`), or a core requirement the rule of `v` may remove (`removersOf`: an exclusion of `v`, a replacement valid in `v`; plan review B1 of the view rule). The subtree is that of the candidate children (requirements that count, whatever their validity; none below an emergent element), the lists the walk uses, so the seeds and the walk see the same edges. Below such an element `appliesIn` and `holdsIn` give in `v` what they give in the neutral view and no rule reads anything else per view, so the variants share the one neutral walk and each walks itself only through the elements above its seeds. The seeds below each element are found by one walk over its subtree, a fixpoint over the elements of that walk when it meets a cycle. Memos: the core, the neutral view, and per variant (by repository and UUID, never by the view object, since every caller builds its own) the elements above its seeds. Proven against the evaluator before ThomasBirkmaier/ReqSeq-archive#698 (`indirect-oracle.test.ts`: random workspaces with cycles, twins, emergent elements, validities of every shape, records per variant, any order of first evaluation, and a small workspace of the performance generator). Any other rule that reads the view must add its elements to the seeds of that variant, as the view rule does.

What SR-034 does not change: "has evidence" (`hasVerificationRecord`: the filter's „ohne Nachweis“, SR-069 AK3), the coverage's `withEvidence` (SR-036) and the chain's `no-evidence` gap stay "a verification record in the view" (the chain's only for a requirement the view holds, else `not-in-view`, #674), so an indirectly verified parent counts as without Nachweis there (assumption, spec question ThomasBirkmaier/ReqSeq-archive#527). The `evidence.outdated` hint (`hints/evidence.ts`) looks at the element's own records only.

Emergent (SR-035, ThomasBirkmaier/ReqSeq-archive#47; ADR-0012 bullet "Emergent"): `StatusSource.emergent` asks `isEmergent` (`model/emergent.ts`: the property with the meaning `emergent` holds `yes`, assumption ThomasBirkmaier/ReqSeq-archive#591 Q1). `counted` gives an emergent element no counted children, so without an own record in the view it is `open` there with no `missingChildren`, never `indirect` (ThomasBirkmaier/ReqSeq-archive#591 Q2, Q3), and as a child it is open, so its parent names it. `decidedByChildren` in `verification.ts` is false for it, so `prepare` never walks below it or reads the versions of its children (state test with `versionBatches()`). The mark costs one property read per element; the key is memoised per metamodel (`emergentKeyOf`).

Cost at N-036: a filter on `verification` or `validation` prepares every requirement once per state (one walk over requirements and derivation edges, the versions of all requirements with records in one batch, as SR-031) and evaluates each requirement once per view (memo). `element.get` on the top of a large tree reads, the first time, the versions of the recorded children below it (cold cost), then nothing (warm). E4 (ThomasBirkmaier/ReqSeq-archive#583, `test/perf/evidence.test.ts`) measured at N-036 with 100 variants: about 20 s cold and again about 16 s after one changed file (the store change reset the state; it is carried since ThomasBirkmaier/ReqSeq-archive#698), when the walk ran once per view (101 walks below the top, a variant about 4 times the core since no core record holds there), about 0.2 s warm. With the shared views (ThomasBirkmaier/ReqSeq-archive#698) the walk runs in the core and the neutral view and, per variant, through the few hundred elements above its seeds (about 400 of the 20,577 below the top): see the rows of `test/perf/evidence.test.ts` in `verification/performance.md` (branch `perf-record`).

## Validation status

SR-038 (ThomasBirkmaier/ReqSeq-archive#50), `status.ts` and `verification.ts`; the rules are ADR-0012 "Status rules", bullet "Validation status".

- `validationOf(records, current)`: `{ status, reason? }`, `recordStatusOf` with kind `validation` in the core (a record with `variant` does not count; the reader refuses one, SR-038 AK4), `passed` named `validated` (AK3); records only of other versions `outdated` (AK2, AK3), none `open`. For `inconclusive` (SR-172 AK2) a second pass, on that path only, finds the reason: the first inconclusive record of the index among the newest of the current version. `hasValidationRecord(records)`: a validation record that counts.
- `WorkspaceStatus.validate(element, shown?)`: the validation status for a need (`source.needs`, meaning `need`, own or inherited) and for a requirement (`source.requirements`) with a counted validation record; no other element (SR-038 AK5); undefined otherwise. Measured against `shown.current` when `shown` is given, also when that is undefined (ThomasBirkmaier/ReqSeq-archive#276), else against the version `prepare` read. No walk and no memo: one pass over the element's own records; never inherited.
- `prepare(elements, { own: true })` (the filter) also reads the versions of the elements with a counted validation record, in the same single batch; the child walk below the elements stays on verification records, so a child with only validation records is never read for a parent (S4 of the plan review). `element.get` of a need and an `evidence.status` page read no batch of their own (the version shown is used).
- Shown by `element.get`, `element.resolve` and `evidence.status` (`withEvidenceStatus`), and by the filter condition `validation` (`query/evidence.ts`), all from `verificationState`. `withEvidenceStatus` adds `validationReason` with an inconclusive one. The CLI shows it as its own bracket after the verification status, `[validation: inconclusive — <reason>]` with the reason on one line, cut at 120 characters.

Cost at N-036: O(records of the element) per element; the filter adds the validation-recorded elements to its one version batch.

## Verification degree

SR-037 (ThomasBirkmaier/ReqSeq-archive#49), `degree.ts` and `degree-text.ts`; the rules are ADR-0012 "Status rules", bullet "Verification degree", the open points spec question ThomasBirkmaier/ReqSeq-archive#592.

- `degreeOf(status, elements, view)`: pure and synchronous over `{ source, evaluate }` of a `WorkspaceStatus`; one pass. An element counts when its type is in `source.requirements`, its status is not in `source.invalid` (the status keys the metamodel marks invalid, `invalidStatuses`) and `evaluate(element, view)` gives a status. Returns `{ share?, total, counts }` (`$defs/verificationDegree`): the five counts in enum order, `share = (verified + indirect) / total`, left out when `total` is 0. The caller has run `prepare(elements, { own: true })` first; SR-126 calls it so after its own `prepare`.
- `countedIn(source, elements)`: the elements that pass the type and invalid test, in their order (what to prepare). `viewIdOf(view)`: `core` or the variant's UUID, as outputs name a view.
- `selectionDegree(workspace, elements, view)`: `verificationState`, `prepare(countedIn(...), { own: true })`, `degreeOf`. No second state and no evaluator of its own: the one of `evidence.status`, `element.get`, `element.resolve` and the filter. `evidence.degree` passes the selection's view (`Selected.views[0]`), else the core, and names a variant view in `names` (ThomasBirkmaier/ReqSeq-archive#588).
- `degreePercent(share)` and `degreeShareOf(value)` (`degree-text.ts`, no imports): the display rule of every access, one decimal rounded down (`64.2 %` for 9/14), and the shape a layout recognises a degree by (a number `share` next to an object `counts`). Public as `@reqseq/core` and, for the app's renderer, `@reqseq/core/verification-degree`.
- `packageSummaryText(levels, degreeOutput)` (`degree-text.ts`, SR-112 AK3, AK4): the line under the title of a package page from `evidence.coverage` and the output of `evidence.degree`: coverage summed over the levels with `withEvidence` (the requirement types), then the degree with the view it is for (`summaryViewText`, exported: `core` as in the example of SR-112 AK3; a variant by its title from `names`, the title the app's modeline shows (`viewMark`); our own choice beyond that: its short ID when it has no title, the ID in `view` when `names` does not name it) and the count of each status that occurs, `Coverage 8 of 10 with evidence · Degree (core) 60 % (6 verified, 1 failed, 1 outdated, 2 open)`; undefined without a counted requirement.
- `minimumHeadText(met, expected, share)` (`degree-text.ts`, SR-153 AK1): the head of a matrix column with minima in the CLI and the app, `2 of 5 · 40 %`.

Cost at N-036: one pass over the selection and one evaluation per counted requirement (memoised per view); at most one version batch per state, none after a filter on `verification` or `validation` (`prepare` over the whole store) or an earlier degree; the output is O(1). E4 (ThomasBirkmaier/ReqSeq-archive#583) measures it cold and warm.

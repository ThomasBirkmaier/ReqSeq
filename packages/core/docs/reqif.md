# ReqIF block (`src/reqif/`)

ReqIF 1.2 import and export (SR-052..SR-059, SR-095; ADR-0013). So far the model, the parser, the writer, the XHTML conversion, the mapping files, the import of new elements with their origin and the repeated import of a delivery; the export and the other commands follow (#265, Lanes E and I).

## Model (`model.ts`)

`ReqifFile`: the header, datatypes (STRING, XHTML, INTEGER, REAL, DATE, BOOLEAN, ENUMERATION with its values, `KEY` and `OTHER-CONTENT`), spec types by category (`spec-object`, `spec-relation`, `specification`, `relation-group`) with their attribute definitions, SPEC-OBJECTs, SPEC-RELATIONs, SPECIFICATIONs with the nested SPEC-HIERARCHY, and `unread` (below). Every identifiable keeps IDENTIFIER, `LONG-NAME`, `LAST-CHANGE`, `DESC` and its line. References stay IDENTIFIERs; values stay the text of the file (numbers, dates, booleans as written), the import converts them. An XHTML value is the namespace-resolved node tree (`XhtmlElement`: local name, namespace, attributes, children in order with the text runs between them), never a re-escaped string. It keeps every element and attribute as given (`script`, `on…`, `javascript:` links too), so the conversion to Markdown and any rendering must allowlist.

## Parser (`parse.ts`)

`parseReqif(bytes, limits?)` gives `{ kind: "parsed", file, warnings }` or `{ kind: "refused", message, line }`; the commands turn a refusal into `reqif.invalid`. `limits` defaults to `REQIF_LIMITS`.

- The bytes stream through `streamXml` of `files/xml-scan.ts` (ADR-0012): UTF-8 only, no `<!DOCTYPE`, no entity but the five predefined ones and numeric references, well-formed only, so no file can make ReqSeq open a connection or read another file. No tree of the whole file is built: each item of DATATYPES, SPEC-TYPES, SPEC-OBJECTS, SPEC-RELATIONS and SPECIFICATIONS is read when it ends and its elements are dropped; inside THE-VALUE the XHTML elements become the model's nodes at once. Whatever the model does not read (TOOL-EXTENSIONS, unknown or foreign parts and children of the root, CORE-CONTENT and REQ-IF-CONTENT) is skipped without building anything and recorded once in `unread`. The walk is the scanner's iteration, so nesting depth is not limited, and namespace declarations are a stack per prefix, so deep nesting stays linear.
- Memory: `REQIF_LIMITS.bytes` (256 MiB) is refused before reading. While reading, the parser charges an estimate of what it keeps (open elements, attributes, text, model, unread entries; 64 bytes per object, 2 per character), and refuses the file above `REQIF_LIMITS.retained` (1 GiB) with "Reading the file would keep more than … bytes in memory". Measured on Node 22: a delivery of 50,000 SPEC-OBJECTs with XHTML and 200,000 SPEC-RELATIONs (114 to 161 MB) peaks at 260 to 300 MB of heap and is charged 0.4 to 0.5 GiB. The worst hostile files measured peak at about 1.1 GB, under the default heap (5 million XHTML elements with 4 attributes each, refused).
- Refused while reading: a prefix without declaration (element or attribute), a name that is not a qualified name (`:a`, `a:b:c`), an empty prefixed namespace (`xmlns:p=""`), a root that is not `REQ-IF` in the ReqIF namespace, a ReqIF element inside XHTML, a missing required part (`THE-HEADER`, `REQ-IF-HEADER`, `CORE-CONTENT`, `REQ-IF-CONTENT`, a `TYPE`, `DEFINITION`, `SOURCE`, `TARGET` or `OBJECT` reference, `THE-VALUE`) and an identifiable without IDENTIFIER, a part of the root or of REQ-IF-CONTENT met twice (ReqIF 1.2, 9.2.1 and 10.8.35), and an IDENTIFIER used twice (the header's included).
- `defaultValue` of an attribute definition is its `DEFAULT-VALUE` (ReqIF 1.2 §10.8.3), a value whose `definition` is that attribute's IDENTIFIER, whatever its DEFINITION says or whether it has one.
- Element names are resolved by their namespace declarations, never by the prefix: `reqif:SPEC-OBJECT` and an unprefixed one in the default namespace are the same, and XHTML may sit in a default namespace on its `div`. Attributes keep their name as written, as name and value pairs in a flat array. `MULTI-VALUED` is an `xsd:boolean` (`true` or `1`). Text runs that are only whitespace are dropped outside XHTML.
- `warnings`: one per reference to an IDENTIFIER the file does not define (datatype, spec type, attribute definition, enumeration value, relation end, hierarchy object), with the IDENTIFIER and line of the element that holds it; the model keeps the reference as written.
- `unread`: each element the reader did not look at, the topmost of each subtree, by local name, namespace and line: skipped parts (TOOL-EXTENSIONS, SPEC-RELATION-GROUPS, unknown or foreign parts), and inside the items read everything it does not use (ALTERNATIVE-ID, THE-ORIGINAL-VALUE, EDITABLE-ATTS, more than one value in DEFAULT-VALUE, a second VALUES, unknown or foreign children). An entry inside a SPEC-OBJECT, SPEC-RELATION or SPECIFICATION (its hierarchy included) has that `owner` (`kind`, `identifier`): it is a loss of that element and goes into the import's loss list as a `reqifLoss` with the same `kind` and `identifier` (SR-053 AK2; the import picks the code, `omitted-value` for a part of a value). An entry without owner belongs to no element (a type, a datatype, a part of the file); SR-053 AK2 asks for affected elements only.
- Datatype facets are kept as written (`maxLength`, `min`, `max`, `accuracy`), since the writer needs them (ReqIF 1.2 §10.8.25, §10.8.26, §10.8.28). Attributes the model does not read are left out on purpose and not listed: `IS-EDITABLE`, `IS-SIMPLIFIED`, `IS-TABLE-INTERNAL`, `xml:lang`.
- `.reqifz` archives are not read (SR-053).

The hand-written samples are in `toolchain/reqif/samples/` (its README). The nightly performance suite parses a generated delivery of 50,000 SPEC-OBJECTs and 200,000 SPEC-RELATIONs (118 MB; `test/perf/reqif-parse.test.ts`, N-036): 5.7 s and +193 MB of heap on the development container, recorded against 10 s.

## Writer (`write.ts`)

`writeReqif(file)` writes the model as ReqIF 1.2 and gives `{ kind: "written", chunks }` (the file as strings to write in order, never one string of the whole file) or `{ kind: "refused", problems }` (ADR-0013). It takes `ReqifWritable`, the model without line numbers and `unread`, so a parsed file and one the export builds are both accepted.

- XML declaration, UTF-8 without BOM, LF after the declaration and at the end, no indentation. Header fields in the schema's sequence (REQ-IF-VERSION always `1.0`, §9.2.3), then DATATYPES, SPEC-TYPES, SPEC-OBJECTS, SPEC-RELATIONS and SPECIFICATIONS, each written even when empty, items in model order. The same model gives the same bytes.
- Text escapes `& < >` and CR (`&#13;`), attribute values `& < "`, TAB, LF and CR, so `parse(write(m))` gives `m` back.
- The root declares the ReqIF namespace and `xmlns:xhtml`; XHTML is written with the prefix `xhtml:` and no whitespace of its own inside THE-VALUE. `xmlns` attributes of a value are dropped (the writer declares what it uses); `xml:` attributes are kept.
- Refused, with every problem named by the IDENTIFIER it belongs to: `missing-field` for a field the schema makes mandatory (header CREATION-TIME, REQ-IF-TOOL-ID, SOURCE-TOOL-ID, TITLE; LAST-CHANGE of every identifiable; MAX-LENGTH of STRING, MIN and MAX of INTEGER and REAL, ACCURACY of REAL; KEY and OTHER-CONTENT of an enumeration value; LONG-NAME of an attribute definition, §10.8.3, and of an enumeration value, §10.8.31), `invalid-character` for a character XML 1.0 cannot carry (C0 controls but TAB, LF and CR, U+FFFE, U+FFFF, lone surrogates) with its `field` (the IDENTIFIER of the attribute definition for a value, else the ReqIF name), `at` (`THE-VALUE`, `text in <xhtml:p>`, `title of <xhtml:p>`), code point and offset, `invalid-value` for an IDENTIFIER that is no NCName (`xsd:ID`) and a STRING value longer than its MAX-LENGTH in characters (code points), and `unsupported-content` for THE-VALUE that is not exactly one `div` or `p` (§10.8.45), `img` (images are written as `object`), an element outside the XHTML namespace, an attribute with another prefix or a malformed element or attribute name in a value. The content of a refused element is still checked, so every problem is named. Nothing is replaced or dropped silently.
- XHTML and SPEC-HIERARCHY nesting are walked without recursion, and the output is joined in chunks of 4,096 pieces. The nightly perf suite writes a model in the export's shape at N-036 (50,000 objects with title, about 1 KB of XHTML, `reqseq-markdown` and `reqseq-values`; 200,000 relations), checks it stays below `REQIF_LIMITS.bytes` and parses it back: 238 MiB of 256 MiB, written in about 4 s with about +400 MB of heap on the development container. The export at N-036 is thus close to the parser's limit (#530).

## XHTML and Markdown (`xhtml-markdown.ts`)

The conversion of an `ATTRIBUTE-VALUE-XHTML` and the text of an element (SR-095, ADR-0013); both directions walk without recursion of their own.

- `xhtmlToMarkdown(value)` gives `{ markdown, images, losses }`. Our node tree becomes hast, then `hast-util-to-mdast` and `mdast-util-to-markdown` with GFM write it in the editor's style: ATX headings, `-` bullets, `1.` lists, `*em*`, `**strong**`, `~~del~~`, fenced code, `---`, GFM tables (AK1). Only XHTML elements with a Markdown form are converted; `b`, `i` and `s` are read as `strong`, `em` and `del`, `span` and `div` as containers. A loss carries its `reqifLoss` code and a reason, once per code and reason, and keeps the text (AK3): `xhtml-style` for each `style`, `xhtml-element` for an element without Markdown form or outside the XHTML namespace and for a non-image `object`, `xhtml-rowspan` and `xhtml-colspan` for spans above 1 (the cells become simple cells), and `xhtml-cell-block` for a list, table, code block, quote, rule or heading in a cell. A cell is flattened at every depth into one line: `br`, paragraphs and `div`s end a line, written `<br>` without loss, and the blocks above keep their text as lines. `style="text-decoration:line-through"` (ReqIF 1.2 §10.8.20) becomes `~~`; every other declaration is `xhtml-style`. A `caption` becomes a paragraph before its table. An `img` without `src` or an `object` without `data` is `xhtml-element`, and emphasis of white space alone is dropped. Elements nested deeper than 256 keep only their text (`xhtml-element`), since the Markdown libraries recurse; wide values are walked without recursion or argument spreads.
- Images: an `object` with an image type (its `type`, else the extension of `data`) and an `img` become `![alt](data)`, the fallback text of the `object` as alt, and are listed in `images` as written. `prepareMarkdown(value)` converts once and gives `images`, `losses` and `markdown(link?)`: `link(image, at)` gives the link of each image in order, and an image it gives none for becomes its alt text (else its file name) as plain text, with no link. `xhtmlToMarkdown(value)` keeps every link as written.
- `markdownToXhtml(markdown, { image? })` gives `{ value, asWritten }`: `value` is one `div` with only the elements of the driver's XHTML modules and the attributes `href`, `title` and `align`: no `class` (§10.8.20), no `start` (not in the List module, so an ordered list counts from 1), no `id` (it would repeat across the values of one file). Images become `<object data type>`, `data` through `image` (the export's link rewrite). HTML in the text stays text, since the editor interprets none; only `<br>` is a line break, as in a table cell. `thead` and `tbody` are dropped (not in Basic Tables), keeping their rows. Task boxes are written as `[ ]` and `[x]`, footnotes as written (`[^1]` and a paragraph `[^1]: …`), with no heading, back link or `id`. A text nested too deeply for the libraries (about 3,000 `>`) is written as one `pre` with the text as typed and `asWritten: true`, so the export can name it.

## Import (`import.ts`, `repeat.ts`, `xhtml-text.ts`, `delivery.ts`; `commands/reqif/import.ts`, `commands/reqif/analyze.ts`)

`reqif.import` (SR-053) reads the file (`readDelivery`: a regular file only, at most `REQIF_LIMITS.bytes` counted while reading, so a file growing meanwhile is refused too: `reqif.invalid`; unreadable or no file: `file.faulty`), parses it (`reqif.invalid`), reads the saved mapping `mapping` (`readMappingFile`, SR-054 AK2; a file without mapping, SR-052, is not read yet: `input.invalid`), plans everything in memory and only then writes. The own metamodel is only read (SR-054 AK3).

`reqif.analyze` (SR-055 AK1) runs the same phases up to the plan and writes nothing: `unmapped` is the list `reqif.import` refuses with (`reqif.unmapped`); otherwise `new` lists each object the import would create and `losses` its losses, both without the planned UUIDs. Without `mapping` it plans with an empty one named `source` (else the header TITLE or IDENTIFIER), so every type and relation type is unmapped with the attributes of each type. For a repeated delivery it lists `changed`, `dropped` and `conflicts` with their UUIDs (below), and a loss of an existing element keeps its UUID; `problems` (left out when empty) has the `reqif.replaces-local` warnings and a `workspace.repository-missing` warning per repository not on this machine. The one-to-one mapping of a ReqSeq file waits for SR-052.

- An IDENTIFIER used twice (ReqIF 1.2 §10.8.32) is `reqif.invalid` from the parser, at the line of the second use; a reference the file does not define, which the parser only warns about, is `reqif.invalid` from the plan.
- `planImport(file, mapping, layout, metamodel, origin, images)` (async, as it reads the images) checks the mapping first: every SPEC-OBJECT-TYPE, attribute (an entry with `source-type` first; those of an unmapped type are listed with it, so one mapping of the list covers the type, SR-055 AK2), SPEC-RELATION-TYPE and enumeration value mapped to a choice property must be mapped or omitted, else `reqif.unmapped` with `details.unmapped` (SR-055 AK1). An attribute mapped to a key `element.create` refuses (`id`, `type`, `status`, the title key, a property the type does not have: `propertyKeyRefusal`; D-030), to an origin property (`ORIGIN_MEANINGS`: `source`, `source-identifier`, `import-date`, `delivery`, `import-version`, which only the import writes; SR-057 AK3, the refusal of `propertyKeyRefusal`) or to a property that cannot hold its datatype is `input.invalid` with `fields: ["mapping.attributes[i].property"]`.
- What a property holds: `title`, `text` and a text property every datatype as text (enumeration values by name, joined with `, ` unless `many`; a reference to a value the datatype does not define is an `omitted-value` loss); number INTEGER and REAL in their lexical form (xs:integer, xs:double; anything else, an empty value, a value that is not finite or an integer a number cannot hold exactly is an `omitted-value` loss); date DATE in the lexical form of xs:dateTime with a four-digit year, or its day alone (the day, white space around it collapsed; `24:00:00` is midnight of the next day; another time other than midnight is a `date-time` loss; anything else, an empty value or a day the calendar does not have is an `omitted-value` loss); choice ENUMERATION (through `values`; `omit-values` and a second value for a single choice are `omitted-value` losses). A `many` property gets a list.
- Markdown: in the text and a property with `markdown: true`, an XHTML value becomes Markdown (`prepareMarkdown`, SR-095 AK1, AK3: its losses with the attribute's name), and every other value gets its text escaped (`markdownText`: the characters `` \ ` * _ [ ] < > & | ~ `` and a line start `#`, `-`, `+`, `=`, `1.`, `1)`), so it renders as written. The title and other properties keep it plain: XHTML as `xhtmlText` (paragraphs, `br`, white space collapsed), each other element once an `xhtml-element` loss ("has no form in a plain text").
- Each SPEC-OBJECT of a mapped type becomes a new element: a new UUID, the initial status (`newElementBase` of the model), its title from LONG-NAME unless an attribute is mapped to `title`. An attribute the object has no value of gets its `DEFAULT-VALUE`, as if the object had it. Each SPEC-RELATION of a mapped kind becomes a relation `{ id, version }` of the source element; the version is the target's planned one (`plannedVersion`; relations do not count to a version, ADR-0005). The target folder is the mapping's `target`, else the source name made portable in the main repository (`file.folder-missing` when its repository is not on this machine); it is checked by `refuseUnlisted` before and after it is created, and the files go under the spelling found (#194).
- Origin (SR-057, `origin.ts`): each new element gets `source` (the mapping's source name), `source-identifier` (the IDENTIFIER of its SPEC-OBJECT), `import-date` (`importDate`: the day on this machine's local calendar, not UTC, so an import late in the evening carries the day the user sees), `delivery` (the input) and `import-version`, under the keys the metamodel gives these meanings (`originKeys`: one missing is `metamodel.meaning-unassigned`, SR-013 AK3; one whose property is not of kind text, or date for `import-date`, or has `many` is `input.invalid`, `reason: origin-kind`). `import-version` is the Importfassung of D-059: the element's planned version as written (`plannedVersion`, the fields D-057 counts), which `import-version` itself never counts to. A mapping that maps a SPEC-OBJECT-TYPE to a type without all five origin properties is refused with `input.invalid` at `mapping.types[i].type`, so every imported element has its origin. Every other command refuses to write an origin property with `input.invalid` and `details.reason: origin`: `element.create` (`properties`), `element.update` (`set`, `unset`), both through `propertyKeyRefusal`, and `element.bulkUpdate`.
- Losses (SR-053 AK2), in file order: `omitted-type` (object or relation), `omitted-attribute` (also for the values of a SPEC-RELATION or SPECIFICATION, which are not imported), `omitted-value`, `date-time`, the XHTML losses (`xhtml-style`, `xhtml-element`, `xhtml-rowspan`, `xhtml-colspan`, `xhtml-cell-block`), `image-missing`, `image-outside`, `relation-end-not-imported`, `relation-not-allowed` (the metamodel does not allow the kind between the two types; not written), `relation-duplicate` (a second SPEC-RELATION of the same kind between the same objects, imported once), and `hierarchy` for a SPECIFICATION with a SPEC-HIERARCHY (order and nesting are not imported); then an `omitted-value` for each `unread` entry with an owner ("`<ALTERNATIVE-ID>` on line 12 is not read"; on the source element of a relation), except for an object or relation whose type is omitted.
- Images (SR-095 AK2, `images.ts`): `imageReader(reqifFile, localPaths)` reads each image an XHTML value names once per `data` and `type` and call, one at a time. `data` is percent-decoded, a query or fragment dropped; it must be a relative path without scheme whose real path lies below the folder of the ReqIF file (no `..` segment; `..logo.png` is a name), and through API and MCP inside the repositories (`localPaths`, SR-142), else `image-outside`. A file that is not there, no regular file (opened without waiting, so a FIFO is refused at once), larger than `IMAGE_LIMIT_BYTES` (64 MiB), or whose extension and type are no image `element.addAttachment` takes, is `image-missing`. An image is opened once to hash it, without following a link as its last name, `fstat`ed on that handle, checked again for the real path after the open (same device and inode, still below the folder) and read only up to its size; the reader keeps the real path, identity, size and SHA-256 only. The copy opens it the same way while it is written (`imageContent`), never reads past that size, and is `file.changed-on-disk` when it is another file or its bytes changed. An image that is not copied becomes its alt text without a link, so the text never points outside the element. A copy goes into the element's image folder (the file name without `.md`, as `element.addAttachment` does) under the name `element.addAttachment` gives (`attachmentStem`; `ImageNames`: `-2`, `-3` for a name taken in any case, the same bytes once), and the Markdown links to it. `import-version` is the version the store computes (`plannedVersion`: `imageLinks` with the layout's ignore globs, the copies by their SHA-256, any other link looked up on disk). Images of a property do not count (ADR-0005, SR-127). The command checks every copy with `refuseUnlisted` before and after its folder is created, and writes the copies with the elements in one `createElementFiles` call; `files` lists the elements, then the copies. A folder created for the copies stays, empty, when the write fails (#530).
- Writing: `createElementFiles` (model, `new-files.ts`; the images first) through `createFilesAtomic` of the files block: every file as a temp file first, then each gets its name (a hard link, never replacing a file), each folder fsynced once; on a failure the call removes only the files it created whose bytes are unchanged and lists the others in `details.written` (D-045). All or nothing holds for errors, not for a crash (ADR-0013).
- Repeated delivery (SR-056, `repeat.ts`; assumptions of #575): `existingElements` takes every element of the workspace whose `source` is the mapping's source name; one whose `source-identifier` the file has is matched, the others are `dropped` (only listed: no status, no property, no write, AK3; an element whose IDENTIFIER is no text is not listed). Two elements with one IDENTIFIER of the file are `input.invalid` (`reason: origin-duplicate`, both files); one of a type the metamodel does not know is `element.read-only`; one whose type the mapping now changes is `input.invalid` at `mapping.types[i].type`; one without current version (`currentVersionsOf`) is `input.invalid` (`reason: no-version`). The matched files are read once with `readAllUnchanged`, and the images in each image folder are reserved (`ImageNames.reserve`), so the same bytes keep their name and nothing is copied again.
  - A matched object keeps its element, UUID, file and folder (new ones go to the target). Its planned file is the current one with the delivery's title, text, mapped properties (a mapped key without value is removed) and origin (`editElementFile`, only changed keys); unmapped properties and unknown keys stay. P is its version, I the stored `import-version` (missing: differs from both), C the current version. *changed*: P ≠ I (AK1, conflicts included); *conflict*: also C ≠ I and C ≠ P (#575/2). A local value of an unmapped property that counts makes P differ too (#575/5).
  - Update (changed, no conflict) and take: the planned file is written. Changed only locally (P = I ≠ C): nothing (#575/1). Neither: written only when it differs apart from `delivery` and `import-date` (#575/3). Whenever the delivery is written into an existing element (update, take, neither), a `reqif.replaces-local` warning names the title, the mapped properties that do not count and the relation kinds whose targets (UUID and repository) differ from the file, as the version cannot show a local edit of them (#575/4); a relation that only follows a target's new version is silent. With keep, or changed only locally, a SPEC-RELATION from that element is not written and not listed as a loss. Keep: only `import-version` (P), `delivery` and `import-date` (#575/6), so the same conflict does not come back.
  - Relations of mapped kinds: the items to elements of the source follow the delivery, every other item stays (`relationEdits`), so a relation to a dropped element goes. A relation carries P of a target the delivery is written into, else C, and names the target's repository when it lies in another one.
  - `reqif.import`: `take` and `keep` entries match a conflict's source IDENTIFIER first, else a reference to its element; the same conflict in both is `input.invalid` (`reason: take-and-keep`), an entry that names none a `reqif.choice-unused` warning. A conflict without choice is `reqif.conflict` with `details.conflicts`. While a repository of the workspace is not on this machine the import is refused (`file.folder-missing`, `details.repositories`, #575/7), and while the store cannot read an element file (an error at a file, SR-008) too (`file.faulty`, `details.files`, #575/8): an element of the source there could not be matched and would be created again. `reqif.analyze` warns of both. Every refusal of the plan, and the walk check of every new file and copy, comes before a folder is created; only the check again after a folder was created (a link put there meanwhile) can leave it empty (#530). Writes: the image copies of updated elements (`createFilesAtomic` per repository), the updated files (`writeElementFiles`, 16 at once), the new files (`createElementFiles`); a failing step undoes the earlier ones (`restoreElementFiles`, `removeCreatedFiles`: only files still as written) and `details.written` lists what it could not undo. `updated` lists the elements written from the delivery, `kept` the kept conflicts; `files` the updated files, their copies, then the new files.
- Not yet: the file without mapping (SR-052).

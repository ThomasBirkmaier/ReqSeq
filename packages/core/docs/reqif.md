# ReqIF block (`src/reqif/`)

ReqIF 1.2 import and export (SR-052..SR-059, SR-095; ADR-0013). So far the model, the parser, the mapping files and the import of new elements; the writer, the XHTML conversion and the other commands follow (#265, Lanes E and I).

## Model (`model.ts`)

`ReqifFile`: the header, datatypes (STRING, XHTML, INTEGER, REAL, DATE, BOOLEAN, ENUMERATION with its values, `KEY` and `OTHER-CONTENT`), spec types by category (`spec-object`, `spec-relation`, `specification`, `relation-group`) with their attribute definitions, SPEC-OBJECTs, SPEC-RELATIONs, SPECIFICATIONs with the nested SPEC-HIERARCHY, and `unread`: the elements the model leaves out (relation groups, tool extensions, unknown definitions), by name and line, for the loss list (SR-053 AK2). Every identifiable keeps IDENTIFIER, `LONG-NAME`, `LAST-CHANGE`, `DESC` and its line. References stay IDENTIFIERs; values stay the text of the file (numbers, dates, booleans as written), the import converts them. An XHTML value is the namespace-resolved node tree (`XhtmlElement`: local name, namespace, attributes, children in order with the text runs between them), never a re-escaped string. It keeps every element and attribute as given (`script`, `on…`, `javascript:` links too), so the conversion to Markdown and any rendering must allowlist.

## Parser (`parse.ts`)

`parseReqif(bytes, limits?)` gives `{ kind: "parsed", file }` or `{ kind: "refused", message, line }`; the commands turn a refusal into `reqif.invalid`. `limits` defaults to `REQIF_LIMITS`.

- The bytes stream through `streamXml` of `files/xml-scan.ts` (ADR-0012): UTF-8 only, no `<!DOCTYPE`, no entity but the five predefined ones and numeric references, well-formed only, so no file can make ReqSeq open a connection or read another file. No tree of the whole file is built: each item of DATATYPES, SPEC-TYPES, SPEC-OBJECTS, SPEC-RELATIONS and SPECIFICATIONS is read when it ends and its elements are dropped; inside THE-VALUE the XHTML elements become the model's nodes at once. Whatever the model does not read (TOOL-EXTENSIONS, unknown or foreign parts and children of the root, CORE-CONTENT and REQ-IF-CONTENT) is skipped without building anything and recorded once in `unread`. The walk is the scanner's iteration, so nesting depth is not limited, and namespace declarations are a stack per prefix, so deep nesting stays linear.
- Memory: `REQIF_LIMITS.bytes` (256 MiB) is refused before reading. While reading, the parser charges an estimate of what it keeps (open elements, attributes, text, model, unread entries; 64 bytes per object, 2 per character), and refuses the file above `REQIF_LIMITS.retained` (1 GiB) with "Reading the file would keep more than … bytes in memory". Measured on Node 22: a delivery of 50,000 SPEC-OBJECTs with XHTML and 200,000 SPEC-RELATIONs (114 to 161 MB) peaks at 260 to 300 MB of heap and is charged 0.4 to 0.5 GiB. The worst hostile files measured peak at about 1.1 GB, under the default heap (5 million XHTML elements with 4 attributes each, refused).
- Refused while reading: a prefix without declaration (element or attribute), a name that is not a qualified name (`:a`, `a:b:c`), an empty prefixed namespace (`xmlns:p=""`), a root that is not `REQ-IF` in the ReqIF namespace, a ReqIF element inside XHTML, a missing required part (`THE-HEADER`, `REQ-IF-HEADER`, `CORE-CONTENT`, `REQ-IF-CONTENT`, a `TYPE`, `DEFINITION`, `SOURCE`, `TARGET` or `OBJECT` reference, `THE-VALUE`) and an identifiable without IDENTIFIER.
- Element names are resolved by their namespace declarations, never by the prefix: `reqif:SPEC-OBJECT` and an unprefixed one in the default namespace are the same, and XHTML may sit in a default namespace on its `div`. Attributes keep their name as written, as name and value pairs in a flat array. `MULTI-VALUED` is an `xsd:boolean` (`true` or `1`). Text runs that are only whitespace are dropped outside XHTML.
- `unread` holds, by name and line, each skipped element and the unknown children of the items read. Part 1b of #265 refuses a repeated part, records what is still dropped (a second VALUES, THE-ORIGINAL-VALUE, defaults, facets) and gives each entry its owner, as the loss list needs; it also refuses an IDENTIFIER used twice and warns about dangling references. Until then a reference to an IDENTIFIER the file does not define is kept as written.
- `.reqifz` archives are not read (SR-053).

The hand-written samples and the nightly parse at N-036 follow in part 1b.

## Import (`import.ts`, `xhtml-text.ts`; `commands/reqif/import.ts`)

`reqif.import` (SR-053) reads the file (a regular file only, at most `REQIF_LIMITS.bytes` counted while reading, so a file growing meanwhile is refused too: `reqif.invalid`; unreadable or no file: `file.faulty`), parses it (`reqif.invalid`), reads the saved mapping `mapping` (`readMappingFile`, SR-054 AK2; a file without mapping, SR-052, is not read yet: `input.invalid`), plans everything in memory and only then writes. The own metamodel is only read (SR-054 AK3).

- An IDENTIFIER used twice (datatypes, enumeration values, types, attribute definitions, objects, relations, specifications; ReqIF 1.2 §10.8.32) is `reqif.invalid` at the line of the second use, as is a reference the file does not define.
- `planImport(file, mapping, layout, metamodel)` checks the mapping first: every SPEC-OBJECT-TYPE, attribute of a mapped type (an entry with `source-type` first), SPEC-RELATION-TYPE and enumeration value mapped to a choice property must be mapped or omitted, else `reqif.unmapped` with `details.unmapped` (SR-055 AK1). An attribute mapped to a key `element.create` refuses (`id`, `type`, `status`, the title key, a property the type does not have: `propertyKeyRefusal`; D-030) or to a property that cannot hold its datatype is `input.invalid` with `fields: ["mapping.attributes[i].property"]`.
- What a property holds: `title`, `text` and a text property every datatype as text (enumeration values by name, joined with `, ` unless `many`; a reference to a value the datatype does not define is an `omitted-value` loss); number INTEGER and REAL in their lexical form (xs:integer, xs:double; anything else, an empty value, a value that is not finite or an integer a number cannot hold exactly is an `omitted-value` loss); date DATE (the day; a time other than midnight is a `date-time` loss); choice ENUMERATION (through `values`; `omit-values` and a second value for a single choice are `omitted-value` losses). A `many` property gets a list.
- Markdown: the text and a property with `markdown: true` get their text escaped (`markdownText`: the characters `` \ ` * _ [ ] < > & | ~ `` and a line start `#`, `-`, `+`, `=`, `1.`, `1)`), so it renders as written; the title and other properties keep it plain.
- Each SPEC-OBJECT of a mapped type becomes a new element: a new UUID, the initial status (`newElementBase` of the model), its title from LONG-NAME unless an attribute is mapped to `title`. Each SPEC-RELATION of a mapped kind becomes a relation `{ id, version }` of the source element; the version is the target's planned one (`plannedVersion`; relations do not count to a version, ADR-0005). The target folder is the mapping's `target`, else the source name made portable in the main repository (`file.folder-missing` when its repository is not on this machine); it is checked by `refuseUnlisted` before and after it is created, and the files go under the spelling found (#194).
- Losses (SR-053 AK2), in file order: `omitted-type` (object or relation), `omitted-attribute` (also for the values of a SPEC-RELATION or SPECIFICATION, which are not imported), `omitted-value`, `date-time`, `xhtml-element`, `relation-end-not-imported`, `relation-not-allowed` (the metamodel does not allow the kind between the two types; not written), `relation-duplicate` (a second SPEC-RELATION of the same kind between the same objects, imported once), and `hierarchy` for a SPECIFICATION with a SPEC-HIERARCHY (order and nesting are not imported).
- XHTML: until the conversion of SR-095, `xhtmlText` gives the text (paragraphs, `br`, white space collapsed) and names every element other than `div`, `p` and `br` once as an `xhtml-element` loss; SR-095 replaces it behind the same call. Images (`object`) are not read yet.
- Writing: `createElementFiles` (model, `new-files.ts`) through `createFilesAtomic` of the files block: every file as a temp file first, then each gets its name (a hard link, never replacing a file), each folder fsynced once; on a failure the call removes only the files it created whose bytes are unchanged and lists the others in `details.written` (D-045). All or nothing holds for errors, not for a crash (ADR-0013).
- Not yet: the origin properties and import version (SR-057), so a repeated import creates new elements; updating elements of an earlier delivery and `take`/`keep` (SR-056; the lists change nothing yet); the file without mapping (SR-052); `type-without-origin`; and the parser's `unread` entries, `DEFAULT-VALUE` among them, as losses (#530, after #547).

# Variants block (`src/variants/`)

Part of the [`@reqseq/core` README](../README.md).

Validity and views of the core and the variants (SR-040, SR-041, SR-043, D-020).

- `validityOf(metamodel)`: the property with the meaning `validity` as a relation key (`relationKey`: key, label, `many`), undefined when none has it or it holds no relations. Then nothing has a validity and everything applies everywhere; the stage-5 view commands must call `requireMeaning` first and report `metamodel.meaning-unassigned` instead (SR-013 AK3).
- `validityEntries(validity, element)`: the entries with their paths. Absent, `null` and `[]` give none. Under a key with `many` only a list has entries (`[key, i]`); one value there gives none, and the value-kind check reports it (SR-085). Without `many` the one value is the entry (`[key]`). It is `relationItems` of `src/model/relation-keys.ts`, the same reading as the missing-target check (SR-089).
- `validityTarget(entry, source)`: the one cheap predicate that view and hint share. An entry for which `hasId` holds (a mapping, not a list, with a text `id`; `src/model/relation-keys.ts`) names that UUID in the repository it names, or in the source's own when it names none (D-058); a `repository` that is not text, a free name or any other value names nothing (D-020). Other keys are SR-085's.
- `appliesIn(validity, element, view)`, with `View = { kind: "core" } | { kind: "variant", variant }`: without entries the element applies in the core and every variant (SR-040 AK1); with entries only in the variants they name, never in the core (SR-040 AK2, SR-043 AK9). Pure: no store lookup, no schema validation. Replacement and exclusion (SR-041, SR-042) are the view rule's.
- Stage 5 contracts (catalog, `data-export.schema.json`, `problem-codes.yaml`), built by the stage's SR PRs: a variant's view is the core requirements it neither excludes nor replaces, plus those valid for it, and every element whose type has no validity property (SR-043, `$defs/view`); the filter condition `validFor` stays validity only. `variant.diff` gives `added`, `replaced` (one row per core requirement and replacement), `excluded`, `names`, `problems` and `incomplete`; elements give `replacedBy` and `excludedBy` for a core requirement (SR-046 AK3) and one `verification` entry per view they are in (SR-047 AK3). Refusals: `variant.diff` and `variant.exclude` of no variant (`not-a-variant`), `variant.exclude` adding an exclusion of no core requirement (`not-core`; `undo` removes any entry), `evidence.record` for a variant that excludes or replaces the requirement (`excluded-in-variant`, `replaced-in-variant`). Hints: `variant.target-not-core` (a replacement or exclusion of no core requirement, SR-041 AK8, SR-042 AK7), `variant.core-changed` (SR-045, confirmable, `hints.md`), `variant.nested` (SR-039, below).
- `isCoreRequirement(context, element)` (`core.ts`): the type has the validity property among its effective properties and the element no validity entry (absent, `null`, `[]`); a need, a package or a validity of another shape is none. The one predicate for the targets of replacements and exclusions.
- `viewRuleOf({ workspace, store, metamodel }, view)` (`view-rule.ts`): the rule of a view (`ViewRule`): `includes`, `replacedBy`, `excludes`, `addedOf`, `replacedOf`, `excludedOf`. The core view is `appliesIn`; a variant's view is `appliesIn` less the core requirements the variant excludes or a replacement valid in it replaces. Rule items are the items of the relation kinds with the meaning `replacement` (only from sources with a validity entry, SR-041 AK6) or `exclusion` (only from variants), read by meaning; an item acts only when its target resolves (`resolveTarget`) to one core requirement. Exclusion wins: a replacement of an excluded target does not count, its source is added (SR-042 AK5). The status is not read (SR-041 AK9), nothing cascades (SR-041 AK5). The index (`viewRuleIndexOf`, `viewRuleIndexState`) is one pass over the store per store and metamodel, synchronous and without other state; the rule of a variant is built from it once. Used by the selection (`selection.view`) and the `variant` filter of `hint.list`; trace and evidence follow (A4a-2). A variant in a repository that is not here is `ref.unknown`; a target there acts in no view, and the selection is `incomplete` (SR-006 AK2).
- `targetNotCoreProblemsState`, `targetNotCoreFindingsOf(context, record)` (`target-not-core.ts`): one `variant.target-not-core` warning at the line of each rule item whose target resolves to one element that is no core requirement (SR-041 AK8), for `workspace.check`, `hint.list` and `element.get`; missing, ambiguous and absent targets are other checks.
- `variantTypes(metamodel)`, `variantsOf(store, metamodel)`: the types with the meaning `variant` (own or inherited) and their elements, in store order.
- `supersededValidityFindingsOf(context, record)`: the same hints for one element, for `element.get` (one filter over the store for the superseded variants, then only the entries of `record`).
- `supersededValidityFindings(context)`, `supersededValidityProblemsState` (depends on the element store, the metamodel and the short IDs), for `workspace.check` (SR-019): one hint `variant.superseded-in-validity`, severity `warning`, per entry whose `validityTarget` resolves (`resolveTarget`) to one element of a variant type with an invalid status (D-044), with `repository`, `file`, `line`, `elementId` and `targetId`. So every requirement with an entry that names a superseded variant (`validityTarget`) gets it (SR-040 AK3); a requirement with an empty validity applies in that view too but gets none. Missing and ambiguous targets are other checks. N-036: one pass collects the UUIDs of superseded variants and the check ends without any; only entries naming one are looked up.
- Nested variants (`nested.ts`, SR-039, D-020): a variant builds only on the core, so a variant (a type with the meaning `variant` that has the validity property) with validity entries (`validityEntries`; every entry, also one that names no variant, spec question #253) is nested. Only the validity decides: a relation between variants is allowed; in the standard model the type Variant has no validity, so a `validity` key written there by hand is an unknown property (SR-016) and refuses nothing. The short IDs for the message are read only when a variant is written. `nestedVariantCheck(workspace, command)` is the `WriteCheck` that `element.create`, `element.update` and `element.bulkUpdate` pass to the model's write path: it sees each variant as it would be written and refuses with the error `variant.nested` (`details.elements`), before anything is written; a bulk preview lists the hints instead. `nestedVariantsState` (in `FINDING_STATES` and `HINT_STATES`, for `workspace.check` and `hint.list`) and `nestedVariantFindingsOf` (`element.get`) give one hint `variant.nested`, severity `warning`, per entry of a file written by hand, at the line of the entry, with `targetId` when it resolves. N-036: one pass over the variants. Nothing against a metamodel that is not valid.

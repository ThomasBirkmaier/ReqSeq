# Evidence block: records (`src/evidence/`)

Part of the [`@reqseq/core` README](../README.md). It covers the readers, `evidence.record` and `evidence.enrichJunit`; the status rules are in [evidence-status.md](evidence-status.md), the views in [evidence-views.md](evidence-views.md).

The evidence records (Datensätze) of a workspace as an in-memory list, indexed by element, with the test cases they form (ADR-0012 "Block and state"). Producers (the Markdown and JUnit readers, `evidence.record`, `evidence.enrichJunit`) write or read records; consumers (status, coverage, degree, list, chain, matrix, export) only read them. The block imports the model, workspace and variants blocks, never `commands`; it never computes or writes the `status` of an element (D-030).

## Model

- `EvidenceRecord` (`record.ts`) is `data-export.schema.json#/$defs/evidenceRecord`: the fields of a record (`evidence-record.schema.json`), plus where it lies (`source`: `markdown` | `junit`, `repository`, `file`, `line`: of the `<testcase>`, 1 for a Markdown record), the JUnit `className`, and `baselines` (only `evidence.list` fills it, SR-032 AK2). The readers always set the location fields; records injected through `evidenceRecordsState` may leave them out.
- `evidenceSource` (`evidence-source.ts`, #821): where the evidence (Beleg, SR-032 AK1) is, as a person reads it, the one rule every adapter prints. `evidenceSourceOf(record)` is the `evidence` when given and not empty, else `<repository>/<file>` (`<file>` without a repository) and `:<line>` when `line` is given (`:1` for a Markdown record), else none. `withEvidenceSource(record)` and `testCaseWithEvidenceSource(test)` return copies with the field and never change a record of the index; they are applied where records leave core: `evidence.list` (`records`, the executions and `last` of `testCases`), `trace.chain` (`evidence`, `validationRecords`), `trace.matrix` (`last`), `trace.affected` (`records`), `baseline.get` (`later`, `validationLater`) and `evidence.record` (`record`). The index stores no location, so only the records of an answer are copied (N-036).
- `SkippedTestCase`: a JUnit test case marked `<skipped>` that names elements. It gives no record (ADR-0012) and is kept so the test case is listed without execution (SR-033 AK3).
- `testCaseKey(name, className)`, `testCaseKeyOf(record)`: the identity of a test case, JUnit `classname` + `name`, or the `test-case` of a Markdown record alone, as `JSON.stringify([className ?? null, name])` so no name can pass for another class and name. Records with the same key are one test case across files; each `<testcase>` and each Markdown record is one execution (a JUnit file that holds a test case twice gives two).
- `TestCase` is `$defs/testCase`: a test case seen from one element (ThomasBirkmaier/ReqSeq-archive#535). `executions` holds that element's records only, newest first, `last` is `executions[0]`, `elements` lists every element the test case names; a test case with only skipped appearances has `executed: false` and `executions: []`.

## Folders

`evidenceFiles(layout)` (`folders.ts`): every `*.md` and `*.xml` file below each `evidence` location of the workspace file, in any repository of the workspace, through `listFiles` of the model block (the walk of the element store with a start folder and an extension list: no `.git` or `node_modules`, no nested repository, the `ignore` globs, links never followed, `.MD`/`.XML` a `file.skipped` warning). Result `{ files: { repository, file, absolute, ext }[], incomplete, problems }`:

- a location in a repository that is not on this machine sets `incomplete` (SR-006 AK2, SR-036 AK3);
- a location whose repository the workspace file does not list is left out (the layout reports it);
- the location folder itself follows the walk rules: one that is or lies below a link, in `.git` or `node_modules`, matched by an `ignore` glob, in another repository of the workspace (name that repository in the location) or in a nested Git repository is `file.skipped` (warning); one that does not exist (or is a file) is `evidence.folder-missing` (info); one that cannot be looked at (`EACCES`) is `file.unreadable` (error). An `ignore` glob that keeps the store out of an evidence folder hides its records too;
- a file or walk problem two locations both reach is listed once.

`evidenceProblemsState` (`match.ts`, below) shows the problems in `workspace.check`.

## State

- `evidenceReadState` (`state.ts`, depends on `workspaceLayoutState`): `readEvidence(layout, readers)`: the files of `evidenceFiles`, each given with its bytes to the reader of its extension, 16 at a time; `{ records, skipped, problems, incomplete }`. A file without a reader is not read; one that cannot be read is `file.unreadable`.
- `EVIDENCE_READERS`: one `EvidenceReader` (`{ extension, read(file, bytes) }`) per extension: `MARKDOWN_READER` (`md`, SR-028) and the JUnit reader (`xml`, SR-093). A reader reads nothing else and gives nothing for a file that is no record of its kind.
- `evidenceRecordsState` (depends on `evidenceReadState`): the records alone, an array. It is the seam through which tests and consumers get records without files (ThomasBirkmaier/ReqSeq-archive#127 option 1): `workspace.replace(evidenceRecordsState, current, Promise.resolve(records))`. Skipped test cases are injected by replacing `evidenceReadState` first (replacing it gives `evidenceRecordsState` the records of the new read, its `carry`). A replace of `evidenceRecordsState` itself resets the index and the status. The check of SR-025 AK4 (`hints/evidence.ts`) reads it.

## Index

`evidenceIndex(records, skipped)` (`by-element.ts`), and `evidenceIndexState` (from `evidenceRecordsState` and the `skipped` of `evidenceReadState`). Pure: matching against the store (unknown elements, current versions) belongs to the consumers.

- `byElement`: the records of each element, newest first (`newestFirst`: `date` as an instant, an unreadable date the oldest, then repository, file, line; `sortNewestFirst` parses each date once).
- `testCases`: every test case by key (`TestCaseEntry`: name, class name, the elements it names, all its records newest first), ordered by class name, then name.
- `testCasesOf(id)`: the test cases that name the element, each seen from it (`TestCase`), from the records per element each entry keeps (`recordsOf`), so a call costs the test cases of the element and their executions, never the records of other elements; built once per element and kept.
- `positionOf(record)`: the position of a record in the records the index was built from (`evidenceRecordsState` order), -1 for another record; a map over all records built on first use and kept. The outdated hint of one element uses it (SR-025 AK4, [hints block](hints.md)).
- `hasVerificationRecord(index, id, view, independent)`: at least one verification record in the view (`holdsIn` of `holds.ts`: core: a record without variant; a variant: a record for it, SR-047, and one without variant when `independent`, the element's repository is marked `variant-independent`, SR-173). The one definition of "has evidence" ("ohne Nachweis", SR-069 AK3; the `no-evidence` gap, SR-022 AK3; coverage, SR-036) for the filter, the chain and the coverage (ThomasBirkmaier/ReqSeq-archive#535). The chain asks it only for a requirement its view holds; one outside the view is `not-in-view` (#674). Version and result do not count (spec question ThomasBirkmaier/ReqSeq-archive#527).

## Markdown reader

SR-028 (ThomasBirkmaier/ReqSeq-archive#40). `readMarkdownRecord(file, bytes)` (`markdown.ts`), registered as `MARKDOWN_READER` for `md`: one record per Markdown file whose frontmatter has the key `reqseq-record` (`RECORD_KEY`), checked against `evidence-record.schema.json` (`fileSchemaValidator`).

- The bytes are parsed as an element file is (`parseFileBytes`: strict UTF-8, BOM, CRLF, conflict markers, YAML 1.2). A file that does not parse gives the problem of the files block (`file.invalid-yaml`, `file.conflict-markers`, `file.unreadable`, with the repository) and no record.
- A file without frontmatter, or whose frontmatter is no mapping with `reqseq-record`, is no record (a README in an evidence folder): nothing, not even its YAML warnings. A record keeps its YAML warnings (`file.yaml-warning`).
- A key the format does not know: warning `evidence.invalid-record` naming the key, at its line; the record counts without it (spec question ThomasBirkmaier/ReqSeq-archive#533 Q1, assumption: as D-012 does for unknown properties of elements).
- Any other violation (a required key missing, a wrong value, `reqseq-record` other than 1): error `evidence.invalid-record` per violation, at the line of its key (1 for a missing key); the file gives no record, and the warnings on unknown keys say so. A validation record with `variant` is such a violation (the schema's `variant: false` for `kind: validation`; SR-038 AK4, D-007), at the line of `variant`, with the reason in the message (`VALIDATION_VARIANT_REASON`); it counts for no status, no hint names it and `evidence.list` does not list it. So is an `inconclusive` record without `reason` (`INCONCLUSIVE_REASON_REQUIRED`, SR-172 AK1, #807 Q1) and an `inconclusive` verification record (`INCONCLUSIVE_VALIDATION_ONLY`, #807 Q2), each at the line of `result`.
- A `reason` on a passed or failed record (the schema's `else: reason: false`): warning `evidence.invalid-record` at the line of `result` (`REASON_INCONCLUSIVE_ONLY`); the record counts without it (#807 Q4).
- The lines of the keys come from `keyLinesOf` of the model block (one pass over the frontmatter, also for thousands of keys); the problems of a file are in line order.
- `criteria` (D-072, SR-028 AK4, #960): the acceptance criteria the record holds for, whole numbers from 1, each once (anything else is an error at the line of `criteria`); absent, the record holds for all. On a validation record it is a warning at its line, whatever its value (`CRITERIA_VERIFICATION_ONLY`, SR-030 AK3), and the record counts without it.
- The record: the frontmatter without `reqseq-record` (`reason` only with `inconclusive`, `criteria` ascending and only on a verification), `test-case` as `testCase`, `source: markdown`, the repository and file, `line: 1`. A record with criteria registers the line of `criteria` for each number (`withCriterionLines`, read by `criterionLineOf`, `record.ts`), so the check below names it.

## Findings

`evidenceProblemsState` (`match.ts`; depends on the layout, the element store, `evidenceReadState` and `evidenceRecordsState`) is the evidence entry of `FINDING_STATES` in `workspace.check`, after the cycles and before the outdated evidence (SR-025 AK4):

- the problems of `evidenceReadState` (walk and readers), without those the element store reports for the same code, repository, file and line: the store reads every Markdown file of every available repository, evidence folders included, so a record with broken YAML shows once;
- `recordElementProblems(records, store, layout)` over the records of `evidenceRecordsState` (injected ones too), in their order: `evidence.unknown-element` (warning, SR-028 AK3) for a UUID the store does not have, with a note naming the repositories that are not on this machine; `evidence.ambiguous-element` (warning) for a UUID with several copies (SR-088). Both carry the record's repository, file and line and the UUID as `targetId`, never as `elementId`: they are about the record, not confirmable and not in `hint.list` (spec question ThomasBirkmaier/ReqSeq-archive#533 Q2, assumption).
- `recordKindProblems(records, store, metamodel)`: `evidence.kind-mismatch` (warning, #628) for a verification record whose element (one copy) is of a type without the meaning `requirement`, and for a validation record whose element is of a type with neither the meaning `need` nor `requirement` (D-012, SR-038 AK5), so a JUnit test case naming a need or a hand-written validation of a decision no longer passes silently; the same place and `targetId`; nothing while the metamodel is not valid. `evidence.enrichJunit` gives the same warning in its own output (step 5b, #843).

- `noViewProblems(context, records)` (`no-view.ts`): `evidence.counts-in-no-view` (warning, SR-047 AK5) for a verification record that counts in no view: its view (its variant, else the core) does not hold its requirement (`recordOutOfView` of `in-variant.ts`: `outOfView`, plus SR-173 AK1: a record of the core of an element of a repository marked `variant-independent` counts in each variant whose view holds it; the variants are listed once per call, `recordViewContext`). The message names the requirement and the view by short ID with the text of `outOfView`, replacing requirements included, the place is the record's, with `targetId` and `targetRepository`. Not while another record of the same execution (`executionOf` of `holds.ts`) counts, since CI writes the core and one variant per test case (SR-093 AK5, SR-029 AK11). Only for a requirement with one copy and a variant with one copy of a variant type, while the metamodel is valid; a validation record counts per element, in no view.

- `evidence.unknown-criterion` (warning, SR-028 AK5, #960) for a record whose `criteria` name a number larger than the acceptance criteria of the version it names: the values of the property with the meaning `acceptance-criteria` (`acceptanceCriteriaKeyOf`, `criteriaCount`, `model/acceptance-criteria.ts`; a type without it has none). One per record, naming every such number, at the line of the first (`criterionLineOf`), with `targetId` and `targetRepository`; only for an element with one copy and a known current version, while the metamodel is valid. `criteriaTargets` splits the records into those of the current version (either normal form), checked here against the element file, and those of an older one, checked per call by `olderCriterionProblems(workspace)` in `workspace.check` against the values at the commit that started that version (`versionValues`, `model/version-date.ts`, the walk of the version dates); without Git, or when Git does not have the version, such a record is not checked. A warning, as `evidence.unknown-element`: the record stays readable, only that number counts for nothing (assumption of the plan of #960).

Only the kind, criterion and view checks need the metamodel, so the other findings show while it is not valid. The state also depends on `currentVersionsState`, which it reads only when a record has criteria.

## JUnit reader

SR-093 (ThomasBirkmaier/ReqSeq-archive#105). `readJunitRecords(location, bytes)` (`junit.ts`), registered as `JUNIT_READER` for `xml`: the records of an enriched JUnit XML file, read with the XML scanner and the JUnit model (`files/xml-scan.ts`, `evidence/junit-model.ts`, E2, ADR-0012 "JUnit XML"). It reads the bytes only, never the element store: whether a UUID names an element of the workspace is the consumers' question (`evidence.unknown-element`, SR-028).

- A test case is enriched when it has a `reqseq:version` property. Its `reqseq:element` properties (UUIDs, any case, kept in lower case) name the requirements, and the n-th `reqseq:version` is the version of the n-th `reqseq:element`; `reqseq:item` and `reqseq:date` are required, `reqseq:variant` is optional and repeatable (`Enrichment.views`, SR-093 AK5): each value a variant UUID (any case, kept in lower case) or `core` (any case), each view once in the order of its first property; absent, the core. It gives one record per view and element, views outer (a repeated element with the same version once, with two different versions `evidence.invalid-record`; SR-033 AK2), the record for the core without `variant`, all with the same place, name, item, date, result and criteria: kind `verification`, method `test`, result `failed` with `<failure>` or `<error>`, else `passed`, `testCase` the JUnit `name`, `className` the `classname` (left out when empty), `source: junit`, the repository, file and line of the `<testcase>`.
- A test case that names no requirement (no `reqseq:element` property, no short ID or UUID token in its name) is passed over without a problem (AK2). A pytest parameter list (`test_add[1-2]`) or an identifier in brackets (`[SR-036]`) is no reference the reader can tell without the store, so it is passed over too.
- A test case that names a requirement but has no `reqseq:version` gives no record. The file gets one `evidence.not-enriched` warning with the number of such test cases and the line of the first (spec question ThomasBirkmaier/ReqSeq-archive#529 Q3), not one per test case, so an unenriched CI file of thousands of test cases gives one line. A test case enrich left out because every requirement it names applies in none of the given views carries one `reqseq:not-in-view` per given view (SR-029 AK12; `notInViewOf`, values as for `reqseq:variant`): it gives no record and no warning, its hand-written `reqseq:element` and `reqseq:criterion` ignored (SR-093 AK6). A mark value that is neither a UUID nor `core` is `evidence.invalid-record` at the line of the test case, and so is a mark on an enriched test case (a check of `enrichmentOf`, which enrich's read-back shares). Marks are looked at only where `namesElement` holds (SR-093 AK2).
- An enriched test case marked `<skipped>` gives no record, so it never counts as passed (AK3); it is one `SkippedTestCase`, a test case without execution (SR-033 AK3), whatever views it names.
- Several views (SR-093 AK5): each record counts only in its view (`holdsIn`), the core's also in every variant of a `variant-independent` repository (SR-173). There both hold, so where a view's records are listed (`listedRecords` and `testCasesIn` of `views.ts`, the later records of `baseline.ts`) `withoutShadowedCore` (`holds.ts`) leaves out a record without variant of the same repository, file, line, test case (name and class name), date and element (place alone is not enough: pytest writes a whole file on line 1) as one for the variant; the status is the same with either. The index orders such records by variant, none first (`newestFirst`), and `evidenceProblemsState` and `olderCriterionProblems` give each finding once per code, place, target and message (`distinctFindings`, `match.ts`). Without a view, `evidence.list`, `evidence.outdated` and `trace.affected` name the execution once per view.
- `reqseq:criterion` (`CRITERION_PROPERTY`, D-072, AK4, #960; `criteriaOf`): `<element UUID>:<n>`, `n` matching `[1-9][0-9]*`, one property per pair, read on enriched test cases only. Each element's record gets the numbers that name it, ascending, each once, with the line of the property that names each first (`withCriterionLines`); an element no property names holds for all its criteria. A value of another form, or whose UUID is no `reqseq:element` of the test case, is `evidence.invalid-record` at the line of that property, and the test case gives no record. A kept test case whose criterion `criteriaOf` refuses is `evidence.invalid-record`, left unchanged and not counted; enrich writes the criteria of a test case it enriches itself (step 5c).
- An enriched test case whose properties do not fit gives no record and an `evidence.invalid-record` error with its line: a `reqseq:element` that is no UUID (a short ID left by hand: enrich writes the UUID, ThomasBirkmaier/ReqSeq-archive#529 Q4), element and version counts that differ, an element given twice with different versions, a malformed version, item or date, a variant that is neither a UUID nor `core` (an empty one too), or item or date given twice with different values. A file the scanner refuses is `evidence.invalid-record` with the scanner's line; XML whose root is not `testsuites`/`testsuite` gives nothing.
- Problems of a file come by line. `evidenceProblemsState` (SR-028, "Findings" above) shows them in `workspace.check`.
- Cost: linear in the file; the JUnit model is most of it (a 29 MB file with 50,000 enriched test cases reads in a few seconds). Memory is the larger risk: the model holds about 17 times the file (an 18 MB file, 313 MB heap), and `readEvidence` reads 16 files at a time, so many large CI files at once can need several GB. E4 (ThomasBirkmaier/ReqSeq-archive#583, `test/perf/evidence-heap.test.ts`) measures it: 178 JUnit files of 247 MB (16 of them about 14 MB each, read first in one batch; 587,000 records) and 18,900 Markdown records read in about 32 s and added about 0.9 GB of heap in use and 1.1 GB of resident memory (one shared machine, indicative). The readers run one file after the other, so one model lives at a time. The concurrency for `xml` stays 16.

## Writing records

`evidence.record` (SR-030) and `evidence.enrichJunit` (SR-029).

### Enriching JUnit XML

SR-029 (ThomasBirkmaier/ReqSeq-archive#41). `evidence.enrichJunit` (`enrich.ts`, ADR-0012 "Enriching"): `enrichJunitBytes(bytes, options)` is pure (the resolver and the current versions are injected; it reads and writes no file); `enrichJunitFile(workspace, input)` reads, resolves against the store, writes and resets the evidence state. Per test case:

1. **References**: each `reqseq:element` property on its own, in file order (a repeated one gets its own version), then the name tokens (`elementRefsOf`), each resolved with `resolveRef`. A property that names no element or more than one is reported, whatever its form; an empty one too. A name token of the form of a short ID or UUID is reported the same way; one glued to a word as pytest writes a parameter (`test_get[<UUID>]`, `glued`, #358) only when it is a short ID with a type prefix of the metamodel (`reportable`); any other name token (`[SR-036]`, `test_add[1-2]`) counts only when it names exactly one element. Elements a property names already are not added again.
1a. **Name pattern** (AK5, `name-pattern.ts`): with `namePattern`, `parseNamePattern` checks the template before any file is read (`input.invalid`, `reason: "name-pattern"`, one sentence per rule) and `nameMatcher` compiles it once per call with the type prefixes of the metamodel. Its matches follow the bracket tokens in `elementRefsOf` as `shortId` tokens (`<PREFIX>-<id in lower case>`) with the `matched` text, so an unknown or ambiguous one is reported as in step 2, its message naming the matched text (`"SR-ffffff" (read as "sr_ffffff_ak1" by the name pattern)`). The text never reaches `RegExp`. `{prefix}` tries the longest fitting prefix first, then shorter ones; `{id}` takes 6 to 32 hex digits, the longest first down to 6 until the rest fits, and its run ends at the start of a camel case word; `{ak}` takes the whole digit run, 1 to 9 digits, given as written in the match's `ak` (step 5c); literal text is ASCII case-insensitive. A match starts and ends at a word boundary, is looked for outside `[...]` only, and the next one starts after it. Ambiguous on purpose, and documented in the guide: a prefix that is the start of another next to the ID (`de123456` gives DE-123456), hex letters right after the ID (`sr_c67baaface`), identifiers with fewer than six digits (`sr_029`, counted without reference) and a criterion number of ten or more digits (no match).
1b. **Count** (AK4): a test case whose plan is `none` (no property, no token that names one element) counts in `withoutReference`; kept (step 3), reported (step 2), refused (step 5a) and left out or marked (step 5a, AK11, AK12) test cases do not. It adds no problem.
2. **Reported references**: the test case stays unchanged; `unknown` gets `{ testCase, className?, line, ref }` and `problems` an error `evidence.unknown-element` or `evidence.ambiguous-element` (`Test case "<name>" (line <n>): …`, the candidates for an ambiguous one, and a note when a repository is not on this machine). The other test cases are enriched and the file is written (spec question ThomasBirkmaier/ReqSeq-archive#529 Q1); the errors make the CLI exit with 1.
3. **Already enriched** (a `reqseq:version` property): never changed, so the version stays the one tested (D-026, spec question ThomasBirkmaier/ReqSeq-archive#529 Q5, assumption "keep"). It counts in `testCases`; a kept version that is no longer current gives `evidence.outdated` (warning), a UUID the workspace does not have (or has twice) `evidence.unknown-element` (`evidence.ambiguous-element`, warning), and one the reader rejects `evidence.invalid-record` (error).
4. **Versions**: `currentVersionsOf` for the elements named only (a fresh CLI process reads only their files). An element without one gives `file.faulty` (error, `elementId`); the test case stays unchanged.
5. **Values**: every `reqseq:element` becomes the UUID in place; one `reqseq:version` per element, in the same order; `reqseq:item` the input; `reqseq:date` the input, else an existing valid one, else the `timestamp` of the nearest suite when it has a time zone (spec question ThomasBirkmaier/ReqSeq-archive#529 Q2), else the time of the call. Existing `reqseq:item` and `reqseq:date` are replaced in place (at `valueAt`, or the whole property when it has no value), never written twice.
5a. **Views** (SR-029 AK6 to AK9, AK11; `variantPlanOf`, `fitOf`): each `reqseq:variant` of a test case to be enriched is resolved through `resolveView`: a variant by UUID, short ID or identifier, or `core` (any case); any other refusal is `evidence.invalid-record`. Several values may name several views, each counted once. The input `variant` (one or more, through `resolveView`, each view once in the order first given; `core` is taken here, unlike at `evidence.record`, which refuses it; follow-up of #464) gives the views of every enriched test case: one whose own views are not all among them is `evidence.invalid-record` (AK8, a subset check; a hand-written `core` fits when the core is given, or when nothing is given). Each view of the test case (the given ones, else its own) must hold each named element by `recordOutOfView` (`in-variant.ts`, shared with `evidence.record`: the view rule, and for the core SR-173 AK1, so an element of a type without the validity property is in every view, SR-043 AK10; SR-040, SR-047 AK4): not valid there, excluded or replaced is `evidence.invalid-record` with the same text as the refusal of `evidence.record` for a variant, per view (AK9). In each case the test case stays unchanged and the CLI exits 1. Otherwise a `reqseq:variant` that names a variant by short ID or identifier becomes its UUID in place (AK7; a `core` stays as written), and each given view the test case does not name yet is added after the versions, in the order given (AK6); the core alone adds nothing, so with one given variant and no `core` the output is as before. The core is checked like a variant, also the core of a test case with no view at all (SR-047 AK5). With `skipNotInView` (only with `variant`; without it `input.invalid`, `reason: "skip-without-views"`) an element that applies in none of the given views is left out instead (AK11): it gets no `reqseq:element`, `reqseq:version` or `reqseq:criterion`, a hand-written `reqseq:element` or `reqseq:criterion` of it is removed (with its line when it stands on one of its own), and `notInView` counts it once per test case; a test case with no element left gets no requirement but one `reqseq:not-in-view` per given view, in the order given (AK12, `markSplices`), and counts nowhere else: marks that name the same views (any order or case, `viewOf`) are left as they are; otherwise the marks in place get the given views in order, extra ones are removed and missing ones follow the last mark. Every test case that is enriched loses all its marks (`drop`), with or without given views; reported, refused and `none` test cases keep theirs. Without the option AK9 refuses the test case and leaves it, marks included, unchanged; the others are still enriched. An element that applies in some of the given views is enriched: the reader gives a record for each view, and the status counts it only where the element applies. Without the option AK9 holds. A kept test case (step 3) is never changed, but it is `evidence.invalid-record` (and not counted) when one of its views (`Enrichment.views`, SR-093 AK5) is not among the given ones, or it names an element that does not count in one of its views (with `skipNotInView`: in none of them; such a test case is still `evidence.invalid-record` and the CLI exits 1, since the option leaves out elements only of test cases it enriches, and an enriched test case is not changed); a variant the workspace does not have is not checked; the core is, also that of a test case without `reqseq:variant`. One that gives its `reqseq:variant` by short ID gets the reader's error plus the UUID to write (not for `core`, which the reader reads). The read-back takes exactly the views written, in any order. `variantResolverOf` looks up each distinct value once.
5b. **Kind** (#843, `notRequirement`): an enriched or kept test case that names an element of a type without the meaning `requirement` (a need, a use case) gives `evidence.kind-mismatch` (warning) per such element, with the line, `targetId` and `targetRepository`, as `workspace.check` gives it for the record afterwards (`recordKindProblems`): the record counts for no status (D-012). The test case is enriched all the same. The metamodel is valid here, since a write is refused while it is not.
5c. **Criteria** (SR-029 AK10, D-072, #961; `criteriaPlanOf`): `criterionRefsOf` (`junit-model.ts`) gives every reference of the name with its criterion: `[<ref>/AK<n>]` (`AK` in any case) and each name pattern match with `{ak}`, n as `[1-9][0-9]*`; another suffix (`/slow`) and a match without `{ak}` name the whole requirement. A suffix `AK` alone or before a digit that is no such number (`AK0`, `AK02`, `AK`, `AK2a`), or `{ak}` that is none (`0`, `03`), is `malformed`: for an element of the test case it is `evidence.invalid-record` and the test case stays unchanged, since enriched without it, it would hold for all criteria (D-072). For each that names an enriched element, a `reqseq:criterion` `<UUID>:<n>` is appended after the new properties, each pair once, unless a property names it already or the name also names that element without a criterion (`[SR-x] [SR-x/AK2]`: all of them). A hand-written `reqseq:criterion` `<ref>:<n>` (short ID, UUID or identifier, split at the last colon, n as `[1-9][0-9]*`) is kept and its value replaced in place by `<UUID>:<n>` unless the reference is that UUID already; one that is malformed or names no element of the test case (unknown, ambiguous or another one) is `evidence.invalid-record`, and the test case stays unchanged. The read-back compares the criteria per element, independent of the order of the properties (`criteriaText`).
6. **Where**: a new element right after the last `reqseq:element`, a new mark right after the last mark, the rest at `propertiesAt` (`insertionOf`). In a block on lines each new property goes on a line of its own with the indentation and line ending of the property before it; otherwise inline, and a new `<properties>` block goes on the line of the `<testcase>` start tag (pytest's one-line files stay one line). Every other byte stays.
7. **Escaping**: attributes escape `& < >`, the quote, tab, line feed and carriage return (as `&#9; &#10; &#13;`, so they survive attribute normalisation); element text escapes `& < >` and carriage return. The catalog refuses an item with white space at either end or with control characters other than tab, line feed and carriage return, which XML 1.0 cannot hold.
8. **Read back** (ADR-0007 pattern, `checkReadBack`): every splice lies inside the test case it enriches, so the bytes outside the changed test cases must be byte for byte those read (the other test cases among them), and each enriched `<testcase>` element, scanned on its own (`readsBackAs`), must be one test case with the same name, class name and outcome and exactly the intended elements, versions, item, date and views by the reader's checks (`enrichmentOf`); one whose marks this call wrote (AK12, `LeftOutIntended`) must have the same name, class name and outcome, one mark per given view and no other, and its other properties as read (so no version). No model of the whole result is built (S1 of the PR review). Any difference is `internal`, nothing written. The output is built with one `Buffer.concat` of slices.
9. **Files**: `file` and `output` are local paths (ADR-0009). A missing input or one that is not a regular file is `input.invalid` (base name only), one the scanner refuses `file.faulty`, XML whose root is no JUnit root `input.invalid`. The file written (input or `output`) must not lie in a `.git` folder: its real folder is checked, case-insensitively (D-036). It is written with `writeFileAtomic(dirname, basename, bytes, snapshot, { kind: "xml" })`: in place only while its bytes are those read and still scan; an existing `output` only when it is a JUnit file (`readFileSnapshot`, its own snapshot), else `file.faulty`; a missing `output` is created; a missing folder is `file.folder-missing`. Nothing to change: the input is not rewritten (`files: []`); a given `output` is still written (the input bytes), unless it holds exactly these bytes already (`files: []`, its time kept).
10. **Paths**: `files` and the problems' `file` are relative to the workspace root (the folder of the main repository) with `/` when the file lies below it or in another repository of the workspace (as `workspacePath`; the layout gives the repository folders as real paths), else absolute (a file outside the repositories reaches the command only from the command line or the app, SR-142); the same on every access. After a write `evidenceReadState` is reset, so app, API and MCP see an enriched file in an evidence folder at once (E3 adds outside changes).

Cost (S5 of the plan review, S1 and S4 of the PR review; measured on one machine, Node 22 with its default heap of about 2.2 GB): pytest-style files whose test cases each name a requirement: 42 MB with 250,000 test cases in about 23 s with a peak of about 1.4 GB resident memory; 77 MB with 450,000 in about 57 s and 1.8 GB; 102 MB with 600,000 in about 83 s and 2.0 GB, close to the limit. The scanner model of the file as read is most of it (it holds about 17 times the file); the read-back builds no second model of the whole result: it compares the bytes outside the enriched test cases with the file as read and scans each enriched test case on its own. Memory grows with the number of test cases and properties, not with the bytes, so the practical ceiling on a default heap is stated in test cases: about 600,000 for a first enrich. Enriching makes a one-line pytest file about three times bigger (34.6 MB with 250,000 test cases becomes 103 MB, 83 MB with 600,000 becomes 247 MB), and an enrich run again on an enriched file needs the model of that bigger file: 250,000 enriched test cases (103 MB) took 14 s and 1.5 GB (nothing to change, `files: []`), 600,000 (247 MB) ran out of memory after 27 s. The ceiling for an enriched file read again lies in between, about 400,000 test cases (an estimate, to be measured in E4), so a CI step that enriches a file near the first ceiling must not enrich it again. For a larger file raise the heap, e.g. `NODE_OPTIONS=--max-old-space-size=8192`. Beyond the ceiling the process stops with an out-of-memory error before anything is written (the input stays unchanged, no temporary file is left). No streaming yet. E4 (ThomasBirkmaier/ReqSeq-archive#583, `test/perf/evidence-enrich.test.ts`) measures one 50 MB pytest file (528,642 test cases, 198 MB written) in a workspace of 50,000 elements: about 50 s; the call added about 1.1 GB of heap in use and 1.5 GB of resident memory (indicative). The same file runs 50,000 test cases named `sr_<id>_ak1_…` through `{prefix}_{id}_ak{ak}`, plus two names of about 200 KB built against the matcher (hex runs over 32 digits, near matches): 3.3 s and 425 MB of heap, about 67 µs per test case against about 72 µs in the run without a pattern on the same machine (38 s for the 50 MB file that time), so the matcher adds nothing measurable. Its cost is linear in the name: per start of a match at most (prefixes that fit) × 27 tries, each as long as the pattern (at most 100 characters).

### Recording a record

SR-030 (ThomasBirkmaier/ReqSeq-archive#42). `evidence.record` (`write-record.ts`, ADR-0012 "Recording in the tool"): `recordEvidence(workspace, input, deps)` writes one manual record as a new Markdown file; `renderRecordFile(fields)` is pure. Every refusal (rules 1 to 6) comes before a folder is created, so a refused call leaves nothing behind (D-036, D-045).

1. **Element**: `resolveRef` (`ref.unknown`, `ref.ambiguous`; an element with copies, SR-088, cannot get a record, as there is no `repository`/`file` input, ThomasBirkmaier/ReqSeq-archive#255). D-012: `verification` only for an element whose type has the meaning `requirement`, `validation` for `need` or `requirement`; anything else `input.invalid` (`reason: "D-012"`). Its file and status are never written (D-030).
2. **ID and version** (AK1): the UUID and `currentVersionsOf` (one file read in a fresh process, N-036); no current version is `file.faulty` with `elementId`. Neither is an input.
3. **Fields**: as given; `variant` through `resolveView` (a variant element, else `input.invalid`; `core` names none and is `input.invalid` with `reason: "core-is-no-variant"`, #464) whose view holds the element by the view rule (`viewRuleOf`, as the views decide it: an element of a type without the validity property is in every view, SR-043 AK10). Otherwise the record would count nowhere, and the refusal says why: the element does not apply in the variant (SR-040), `not-valid-in-variant`, or the variant leaves the core requirement out: `excluded-in-variant`, or `replaced-in-variant` with the replacing requirements in the message and their UUIDs in `details.replacedBy` (SR-047 AK4). Each of the three names the element and the variant by short ID in the message and gives the variant's UUID in `details.variant`, for a verification record. Without `variant`, a verification record of an element the core does not hold (and, for a repository marked `variant-independent`, no variant either, SR-173 AK1; `recordOutOfView`) would count in no view and is `input.invalid` with `reason: "counts-in-no-view"` and no `details.variant` (SR-047 AK5). A validation record with a variant is `input.invalid` with `reason: "validation-with-variant"` and the variant's UUID in `details.variant`, before any of these (SR-038 AK4: a validation names only the item under test, D-007). `date` defaults to the time of the call, UTC, whole seconds. The frontmatter is checked against `evidence-record.schema.json` (`recordViolations`): a verification without `method` or `item` is `input.invalid` with `details.errors` naming the input field (`test-case` as `testCase`), so the CLI shows `--item`; so is an `inconclusive` record without `reason` (SR-172 AK1), a `reason` with another result (both naming `reason`) and an `inconclusive` verification (naming `result`). A blank `reason` or one with control characters is refused by the input schema. `evidence` is written as given and never opened. `criteria` (SR-030 AK4, D-072): whole numbers from 1, each once (input schema), written in ascending order; absent, the record holds for every criterion. On a validation record it is `input.invalid` with `reason: "validation-with-criteria"` (a validation counts per element, SR-030 AK3), unlike the reader, which only warns.
4. **Folder** (AK2): `folder` relative to the workspace root with `/`, at or below an evidence location of the workspace file, compared segment by segment after normalising (`evidence2` and `evidence/../requirements` are not below `evidence`); the most specific location holds it. Default: the first location whose repository is on this machine. No location, a folder below none, or a location in a repository that is not on this machine: `input.invalid`. The full target passes `refuseUnlisted` (the rules of every new ReqSeq file) before and again after a missing folder is created (the location itself included).
5. **Name**: `<day>-<short id>-<method>.md`, `validation` for a validation record, and `<day>-<short id>-<variant short id>-<method>.md` for a record of a variant (#647, the short ID as shown at the write, whatever form `variant` was given in), `<day>` the first ten characters of `date`; a taken name (`clashKey`: NFC, any case) gets `-2`, `-3`, .... Created with `writeFileAtomic(…, null)`, which never replaces; a create that fails with `file.changed-on-disk` (the file appeared meanwhile) takes the next name, three names at most.
6. **Bytes and read back**: `---`, the frontmatter in schema order (`renderYamlDocument`), `---`, LF, no BOM, empty body. Before anything is created the bytes must give exactly the intended record and no problem through `readMarkdownRecord`, else `internal`; so values that look like other YAML (`yes`, a date, `: #`, line breaks) stay text.
7. **Output**: `files` (`workspacePath`), `record` as the reader gives it (`source: markdown`, repository, file, line 1, the line of `criteria` registered for the check), `problems`: empty, or the `evidence.unknown-criterion` warning `workspace.check` gives for a number the current version does not have (`unknownCriterionProblem` of `match.ts` with the count of the element file, SR-028 AK5); the record is written all the same.
8. **State** (S12, S1 of the plan review): a built `evidenceReadState` is replaced with the record inserted at its walk position (`withRecord`: location order of the workspace file, then path; an `evidence.folder-missing` above the file is dropped), and the new value is registered with the record (`registerInsertion`, `state.ts`), so the states built on the read carry the one record over instead of being built again (#278): the records are the new read's; the index is `evidenceIndexWith(index, record, records, skipped)` (`by-element.ts`), equal to `evidenceIndex` of the new records: the element's list gets the record at its `newestFirst` place (a copy; on a full tie after the records before it in the walk), a test case it names is built again (or added in its order) with the test cases of its elements, every other list and test case is kept, and `positionOf` counts in the new records, so every record after the inserted one moves by one (review N2 of ThomasBirkmaier/ReqSeq-archive#708); the keys of `byElement` may come in another order (only `get` and `has` read it). The status (`verificationState`, [evidence-status.md](evidence-status.md)) is carried with the carried index, taken inside the hook (review B5 of the ThomasBirkmaier/ReqSeq-archive#698 plan): a new status source (its records changed, review S1 of ThomasBirkmaier/ReqSeq-archive#714), the versions kept, and the walks and results of the element's UUID and its ancestors dropped, so a first record for a variant reaches its parent. Any other replace of the read (no registered record), and a record written while `evidenceRecordsState` holds records put in place through the seam of ThomasBirkmaier/ReqSeq-archive#127 (the index is of those), resets the index and the status. Cost at N-036: the carry adds about 40 to 55 ms to each `evidence.record` (the copy of the status caches, as over a store change, and the new index), paid at once; the open right after it takes about 30 to 140 ms instead of about 240 to 290 ms. For k records written between two opens (a batch through MCP) that is about k × 45 ms against one rebuild of about 700 ms at the next open, even at about 15 records; a cheaper copy is follow-up #284. The next `element.get` reads no evidence file and builds no index. A read that runs is reset; an unbuilt one stays unbuilt. The element store is not changed: the record is a non-element file. The watcher leaves the carried read alone for this file while it holds the bytes written (`ownEvidenceWrite`, #785); a record, a JUnit file or a folder changed outside an evidence location resets the read. When two `evidence.record` calls run at once, both start from the same read; the second replace then fails and resets the read, so the next read finds both files (#308).

The deps (`render`, `write`, `now`) are seams for the tests only (a faulty render, a name taken meanwhile, the time).

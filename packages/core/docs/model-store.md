# Model block: store, watcher, short IDs, current versions (`src/model/`)

Part of the [`@reqseq/core` README](../README.md); the model block is split into [store](model-store.md), [checks](model-checks.md), [writing](model-write.md) and [findings](model-findings.md).

`elementStoreState` (async Workspace state, depends on `workspaceLayoutState`) holds every element of the workspace, found by its frontmatter in whatever folder it lies (SR-003, D-056), with `loadElements(layout)`:

- Each available repository in the order of the workspace file (a missing one is skipped, SR-004 AK3), one folder walk each (`listMarkdownFiles`), no process spawned (N-036). Every `*.md` file counts, in any folder, hidden ones too. Left out: `.git` and `node_modules`; the `excludes` of the layout (repositories of the workspace nested in this one are read once, under their own name); folders below the repository root that hold a `.git` entry (a nested repository that is not in the workspace; spec question #145 b); paths matching an `ignore` glob of the workspace file. Links are never followed: a linked folder is skipped, a linked `*.md` file is a `file.skipped` warning (e.g. `CLAUDE.md` linked to `AGENTS.md`), and so is a Markdown file whose extension is not lower-case `.md` (`.MD`). A folder that cannot be listed is a `file.unreadable` error (`.` for the repository root). `listFiles(repository, ignored, start, kind)` is the same walk from a folder of the repository and for other extensions; the evidence block lists the `*.md` and `*.xml` files of the evidence folders with it.
- `ignore` globs (`ignoreMatcher`, `compileGlob` in `src/model/ignore.ts`, for the watcher too): compiled once per pattern, the same on every OS. Relative to each repository and anchored at its root; `*` any characters within one name, `?` one code point after NFC, `**` as a whole name any number of names; everything else literal; case-sensitive; patterns and paths compared in Unicode NFC, so `Übersicht/**` names that folder whether it is stored composed or decomposed (NFD, as HFS+ stores it and `readdir` then gives it; #218); wildcards match names starting with `.`; `x/**` matches `x` itself, so the folder is not even listed. Use it for folders of other tools whose Markdown frontmatter has `id` and `type` but is no element, for example documentation sites (Docusaurus, Hugo): `ignore: ["website/**"]`; otherwise each such file is an `element.invalid` error.
- Each file is read with `readElementFile` (32 at a time) and classified at once, so no parsed YAML `Document` is held for more than one file. A file is an element when its frontmatter is a mapping with `id` and `type` (ADR-0004; spec question #145, option 1). Every other Markdown file is listed in `nonElements` and never written (SR-003 AK2). A type the metamodel does not know is still an element (SR-016 AK3). An `id` that is not a UUID or a `type` that is not a non-empty string is an `element.invalid` error on its line (without a line when the key is written as an alias); that file is not loaded.
- `ElementStore`: `elements` (by repository, then path in code-unit order), `byId` (UUID to every record with it, so a copied file shows as two records; reporting that is SR-088), `nonElements`, `problems`. Every problem names its `repository`; `file` is relative to it. An `ElementRecord` is small plain data (ADR-0008): `id`, `type`, `repository`, `file`, `data` (the frontmatter values), `eol`, `closingEol`, `bom` and the `snapshot` for `writeFileAtomic`. The raw frontmatter and the Markdown text are not kept: read them with `readElementFile(repository folder, record.file)` when needed (text display, version, edit; the write checks the snapshot anyway). A lazy text cache (LRU, ADR-0008) comes with the commands that need it.
- Relations name their target by UUID, so moving a file to another folder keeps every relation to it (SR-003 AK3): look the target up with `resolveTarget(store, sourceRepository, target)` in the repository it names (relation targets below).
- Kept until `workspace.reset(elementStoreState)` or a reset of the layout. The store also keeps, per repository, what each file contributed (`repositories`), so `updateElements(store, layout, changes)` can update it file by file: list again, drop gone files (also one deleted while it is read), read new and changed ones, keep a record whose snapshot (SHA-256, size, mtime) is unchanged; the result equals a full `loadElements`, or is `undefined` when nothing changed. Change the store only through `applyStoreChange(workspace, (store) => ...)`: one queue per workspace, compare and set with `Workspace.replace`, a retry on the newer store when it was replaced meanwhile, nothing when it was never read or was reset. Versions and indexes come with their SRs (SR-091).
- Inline references in properties (SR-127): besides `references` (the text) an `ElementRecord` has `propertyReferences`, the links in the string values of the frontmatter with their key, list position and line (`propertyReferences` in `src/model/references.ts`; not scanned unless the frontmatter holds `reqseq:`, N-036). `referencesOf(element, metamodel)` keeps those of the properties the metamodel marks `markdown` (`markdownKeysOf`, built once per metamodel object) in front of the text's, so the incoming index (`incoming.ts`), the missing-target check, the outdated check and the neighbourhood read one list.
- Model cache (`src/model/model-cache.ts`, ADR-0008, SR-082): for a workspace with a cache folder, `elementStoreState` loads through `loadThroughCache`. `model.json` holds a header (format, `codeFingerprint()`: product version, core's dependency versions and code, written by core's build to `dist/code-fingerprint.json`; canonical root; start time of the load that wrote it) and, per repository (name and canonical folder), what each file that parsed contributed, with the inode and change time of the file. A cache that is not JSON, has another format (5 since SR-127, which added `propertyReferences`), code or root, or an entry of the wrong shape is discarded whole. After the walk each file with an entry is `lstat`ed (blocking, 2,000 per turn of the event loop); the entry is reused when size, mtime, inode and change time match and the mtime is more than `RACY_MS` (2 s) older than the start of the load that wrote the cache; a file whose change time is less than `RACY_MS` older than that start is not written at all (inode and change time are taken at the write). `loadThroughCache` takes the clock as its last parameter (tests). Everything else is read as usual (`ReadOptions.reuse` of `loadElements`). The cache is written again in the background when `STALE_FILES` (1,000) or `STALE_SHARE` (1 %) of the files are out of date (one save after the other per workspace; `close` waits; a failed write is ignored). Only values JSON gives back exactly are cached (no `Date`, `Uint8Array`, `Set`, `Map`, non-finite numbers, `-0` or cycles); such entries, files without a snapshot and a cache folder inside a repository (also one that does not exist yet and lies there through a symbolic link) are never cached. `warmWorkspace(workspace)` (public, `src/runtime/warm.ts`) loads metamodel, store, short IDs and the incoming relation index (`warmModel`), then starts the search index in the background (`warmSearchIndex`) and never rejects; `serve api` awaits it before it listens.
- Consistency: the store, and the states built on it (short IDs, findings), may be swapped while a command runs (the watcher). A command that needs one consistent view reads `elementStoreState` once and derives the rest from that object (`buildShortIds(store.byId, metamodel)`, `duplicateIdFindings(store)`, `valueKindFindings(store, metamodel)`) instead of reading several states one after the other. A state built on the store (a search index, SR-068) depends on `elementStoreState`, so a swap resets it.
- Watcher (`src/model/watch.ts`, `src/model/watch-tree.ts`, SR-007, ADR-0008): `watchWorkspace(workspace)` (public) starts one watcher per workspace as a workspace state; closing the workspace stops it. The CLI starts it for `reqseq serve api` and `reqseq mcp`. macOS and Windows: `fs.watch` with `recursive` per repository; Linux: one plain watch per folder (`FolderTree`; Node's recursive watch on Linux loses files replaced by a rename and costs one inotify watch per file). It batches events (100 ms debounce, at most 1 s), resets the layout on a change of the workspace or local file, resets the metamodel on a change in its folder, and updates the store with `updateElements` through `applyStoreChange`. Event paths are compared with the walk's paths in Unicode NFC, so FSEvents may spell a name in another normal form than `readdir` (#225). The layout gives an existing metamodel folder as its real path (`fs.realpath`: links resolved, the name as stored), so on macOS a folder typed in another letter case or normal form matches the events; events are compared with it in NFC and lower case (a safety net; a twin folder on Linux costs an extra reset). An event at the folder or a folder above it, or in a missing one, reads the layout again and compares it, so a metamodel folder that is renamed, moved, deleted or appears is noticed (#231). A metamodel folder reached through a link out of its repository is not watched. A folder watch belongs to one folder (`dev:ino`): a folder deleted and created again, replaced or emptied by a checkout is watched anew. Folders it cannot watch (`ENOSPC`) are `workspace.not-watched` warnings in `workspace.status` (`watcherProblems`), once per repository and folder; only processes with a watcher report them. `ready` resolves once the folders are watched, `settled()` once no batch or folder walk is left. `onChange(listener)` (public, #331) calls `listener` once per batch that changed the model, after the change is in place, with a `WorkspaceChange`: `scope` (`elements`, `metamodel` or `workspace`) and the UUIDs of the elements that came, changed or went (`model/watch-change.ts`); the app's core process forwards it to its windows. It is no catalog command (ADR-0008). `startWatcher(workspace, { watch, recursive, debounceMs, maxWaitMs })` is the same with an injected watch function, for tests; tests wait with `untilWatching` (testkit) for a probe change before the change they check.
- Agent activity (`src/model/activity.ts`, SR-117, ADR-0008, ADR-0009): the last element an agent read or changed through the API or the MCP server, for the app's mode „Agent folgen“ and `workspace.activity`. Recording: `invoke` passes each successful call whose `access` is one of `FOLLOWED_ACCESSES` (`api`, `mcp`; spec question #481) to `noteAccess`, which takes the states the command left in one step (`settledValue`: layout, store, metamodel, short IDs; nothing is read or built) and names the element: the subject of the catalog entry (`accessSubject`: the first required argument with `complete: "element"` whose input property is one `elementRef`; a `complete: "repository"` argument picks among several records the reference names), resolved after the run (a UUID through `store.byId`, any other reference only with short IDs of that store); for a `write-files` command without one that resolves, the one element whose file its `files` name (none when they name two). `recordAccess` hands it to the workspace's recorder (state `activity-recorder`), which writes `activity.json` (`schemas/activity.schema.json`: `version`, `process` = pid and 8 random hex digits new per recorder, `seq` from 1, the SHA-256 of the element's file, and the access) with `writeCacheFile`, only into `usableCacheFolder` (never inside a repository): the first write at once, then at most one per 100 ms with the latest access, one at a time, the timer `unref()`ed; a failed write is dropped silently (core has no logger); `workspace.close()` waits for noted accesses and writes the pending one. Recording never changes an output or an error. Watching (app's core process): `watchActivity(workspace, { onAccess, log, holdMs })` (public) watches the cache folder with one plain `fs.watch` (`persistent: false`, created with 0700), reads only `activity.json` (at most 4 KB, schema-checked, `version` 1; a file without a name in the event is read too), takes the file at start as baseline and reports each new `(process, seq)` once: at once when the store of the workspace is not built or holds the element's file with that hash, else after the watcher batch (`onChange`) that brings it, at the latest `holdMs` (`ACTIVITY_HOLD_MS`, 800 ms) after it was recorded (`access.at`; at most `holdMs` after it arrived, for a time in the future or one that does not parse); a newer access drops a held one, also one the file holds when the hold ends (the file is read once more then, since an event can come late or merged, macOS FSEvents, #304), and is held only for what is left of its own hold (#325). Counting from `access.at` puts the file event and the recorder's write delay inside the hold; the 200 ms to SR-117 AK1's 1 s are the margin for a late timer, the read at the end of the hold and the report to the windows. AK1 wins over waiting for the store: the workspace watcher batches changes for up to 1 s, and an event that arrives after the hold is over gets no hold, so a reported element can be one the store does not hold yet (a created one) or holds in an older state; the app's `element.get` then says the element is unknown or shows the older state (open in #325). `ready` resolves with undefined, or with why accesses cannot be seen (no usable cache folder, the watch could not start), which also goes to `log`; a watch error ends the watch. On macOS `fs.watch` starts its FSEvents stream asynchronously, so an access written in the first moments after `ready` can be missed until the next one (the app asks `workspace.activity` when the mode is turned on); tests make probe changes until the cache folder's watch reports one (#383). No polling, no socket (SR-117 AK6).

`shortIdState` (async Workspace state, depends on `elementStoreState` and `metamodelState`, `src/model/short-id.ts`) is what every display of an element ID uses (D-017, D-056, SR-084). Build it with `buildShortIds(store.byId, metamodel)` for tests:

- `of(element)`: `SR-46fb54`, the prefix of the element's type (`findType(...).prefix`; `UNKNOWN_TYPE_PREFIX` = `UNKNOWN` for a type the metamodel does not know, decision on #154), a dash and `tail(element.id)`.
- `tail(id)`: the last hex digits of the UUID without dashes, at least `SHORT_ID_MIN_LENGTH` (6), and one more than the UUID shares at its end with any other UUID of the workspace. Unique by the end of the UUID alone, whatever the type and repository (SR-084 AK2), so each displayed tail names one UUID. Missing repositories cannot be taken into account (D-056). For a UUID of no element (a target in a missing repository) it gives the tail that tells it apart from every element.
- `find(shortId)`: `{ kind: "found", element }`, `{ kind: "unknown" }` or `{ kind: "ambiguous", elements }`, used through `resolveRef` by every command that takes an `elementRef` (`element.get`, `element.resolve`, `element.update`, `element.setStatus`, `element.supersede`; SR-060 AK3 maps them to `ref.unknown` and `ref.ambiguous`). `resolveRef(store, shortIds, ref, copy)` narrows the elements `ref` names (a UUID several files share, SR-088, or a short ID shorter than the one shown) to those in `copy.repository` and/or `copy.file` (relative to the repository, as `details.candidates` give them; #255): one left is the element, several stay `ref.ambiguous` with them, none is `ref.unknown` with the elements `ref` names as `details.candidates`; `copy` never finds an element `ref` does not name. Only `element.get` and `element.resolve` pass a copy; writes refuse an ambiguous reference as before. Matches the elements whose UUID ends with the 6 to 32 digits (a displayed short ID, the 12 digits of the file name, or all 32) and whose type has the given prefix. A tail shorter than the displayed one is ambiguous unless the prefix leaves one element (a short ID another tool stored before the display grew, SR-060); files sharing a UUID (SR-088) are ambiguous; a wrong prefix or a malformed short ID is unknown, so a reference to a gone element is never retargeted to another element with the same tail.
- `identifierOf(element)`, `withIdentifier(value)` (#305, `src/model/identifier-index.ts`): the identifier of an element (the non-empty text under the property with the meaning `identifier`, `identifierKeyOf`) and the elements with an identifier, compared in any case, by repository and then file. Built with the short IDs in the same pass over the store and carried over a change of the store the same way (`updateIdentifierIndex`); `identifierField(shortIds, element)` gives the optional output field `identifier`. `resolveRef` (`src/model/resolve.ts`): a reference of the UUID form names only that UUID; any other names every element `find` gives for it and every element with it as identifier, so a short ID of one element that is the identifier of another, or an identifier two types share, is `ref.ambiguous` with all of them as candidates (short-ID matches first). `ref.unknown` says which forms were tried ("UUID", "short ID or identifier", "identifier"). Duplicates within a type: `duplicateIdentifierFindings`, `duplicateIdentifierProblemsState` (`src/model/identifiers.ts`; `element.duplicate-identifier`, warning, at the identifier key, the other files named; in `workspace.check`, `hint.list` and the hints of `element.get`; carried over a save by looking again at the elements that share an old or new identifier of a changed file). A property with the meaning on another kind than `text` or with `many` is `metamodel.invalid` (`meaningKindProblems`).
- `withTail(shortId)`: the elements whose UUID ends with the digits, whatever their type (none for a malformed short ID). Never a match: `element.resolve` names the one element it gives as `details.candidates` of `ref.unknown` ("prefix may be outdated; did you mean ...?"), for a reference from before a change of type or prefix (#275).
- One pass: UUIDs grouped by their last 6 digits, each group sorted by code units, neighbours compared; O(n log n), independent of file order. `of` and `find` take constant time on average. Nothing is read or written: file names keep their 12 digits (D-056, SR-084 AK3).

Current versions (`src/model/current-versions.ts`, ADR-0008 "Current versions", #259): `currentVersions(workspace)` gives the current version of every element of the store (`CurrentVersions`: `store`, `byRecord`, read one with `currentVersionOf(versions, record)`), for the checks that compare stored versions with it (SR-025 and later). Built on first use, once per store, in the calling thread (each file read again with `readElementBodySync`, no YAML parse while the bytes are those of the store's snapshot; 4 to 5 s at N-036 in local runs of the performance suite); not cached. An element whose file no longer holds it, whose images cannot be read or whose counted values have no normal form has an `unknown` entry with its reason, never a failed command; such entries are computed again on the next use. `currentVersionsState` is carried over watcher batches and ReqSeq's own writes (`recordWrites`) and reset with the metamodel or the layout; images are checked on use (`checkImages`, `imagesUnchanged` in `src/model/images.ts`), since the watcher does not report them. Use `versions.store` for everything else the command needs, so it sees one consistent store.

`currentVersionsIfBuilt(workspace)` gives the kept versions only when their build has ended, never waiting for one that runs. `currentVersionsOf(workspace, records)` gives the current versions of some records only, in their order: from the kept `currentVersionsState` when its build has ended, checking the images of these records only and computing the stale ones again (the state is not changed), or, when none is kept and the records are at least a quarter of the store, from `currentVersions(workspace)`, which builds and keeps it, otherwise computed from the files of these records only, without building the state (a page of a large workspace in a fresh CLI process reads only its own files). A version entry of a file that changed since the store read it (same UUID) carries the element as the file holds it now (`element`). List commands use it through `listElements(workspace, context, records)` (`src/model/list.ts`): each record as `element.get` shows it without text, hints and `readOnly` (`listedElement` in `src/model/view.ts`, which `elementView` builds on), as its file holds it now, with its current version. An element without one is listed without `version` (optional in the data-export schema) and with one `file.faulty` warning in its `problems`; it never fails the list. At N-036 a page of 200 elements costs about 30 to 60 ms; 42,000 listed elements about 5 s with kept versions. An output that gives elements elsewhere by UUID only names them in `names` (`common.schema.json#/$defs/elementName`, #588) with `namesOf(context, ids)` (the first element of each UUID in store order, UUIDs not in the store left out) or `namesOfRecords(context, records)` (`src/model/names.ts`): short ID, identifier and title from the store and the built short IDs, nothing read; `namesField` leaves an empty list out.

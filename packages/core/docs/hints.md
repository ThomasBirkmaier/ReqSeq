# Hints block (`src/hints/`)

Part of the [`@reqseq/core` README](../README.md).

Hints that someone settles by confirming them (D-042), and the list of all open hints (SR-026). Stage 2: outdated relations and inline references (SR-025), outdated evidence (SR-025 AK4), the list (`hint.list`), the hints at the element and confirming them (`hint.confirm`, SR-027). It imports the model, metamodel, workspace, variants and trace blocks, never `commands`.

- `outdatedRelationsState` (depends on the element store, the metamodel, the short IDs, `currentVersionsState` and `incomingState`), for `workspace.check`: one `OutdatedFinding` (`element`, `target`, `stored`, `current`, `problem`) per item of a relation kind or relation-valued property (validity, packages; ADR-0004) with a stored `version` of normal form 1, and per inline reference with one, whose target is `available` (`targetState`, `referenceTargetState`) and has a current version other than the stored one. Missing, ambiguous, inaccessible and unknown-repository targets are other findings; a target without a current version is left out. The problem: code `relation.outdated`, severity `warning` (with `failOn: warning` (#304) `ok` false, CLI exit code 1, ADR-0009), repository, file, line, `elementId` (source), `targetId`, `storedVersion`, `currentVersion`, `hintId`. Store order, then key and item order in the file, then the links in text order. Nothing against an invalid metamodel (#208, #220). The pass over the store runs in slices of 20 ms (`forEachSliced`, SR-082).
- Lines (`locateOutdated`): one rule for items and links: the line in the file as it is now when the file is unchanged since the store read it (SHA-256 of the snapshot), none when it changed. Item lines come from a scan of the frontmatter text (`textLineOf` on the lines of each source split once, `frontmatterLines`, in `model/item-lines.ts`: a top-level key at the start of a line and one flow mapping per item, as ReqSeq writes relations); only where the text is written in another layout is the YAML parsed (`findingLocator`). A link has its line from the store.
- Carried over a save or a watcher batch (`carryStoreUpdate`, #184): when every changed UUID keeps its repositories and types and the incoming index of the store before the change is there (the build makes it; the dependency on `incomingState` carries it first), only the changed files and the sources of relations and links to a changed UUID (`relationsById`, `referencesById`) are looked at again; the rest is kept. Otherwise (a new or deleted element, no index) it is built again.
- `datedProblems(workspace, findings)`: the problems with `storedDate` and `currentDate` (`versionDates`, one request per distinct target and version, one walk per target file) and both dates in the message (`: stored version from X, current version from Y`; `no date (not committed, or Git cannot tell)`). Per call, so a new commit never leaves old dates in a kept state. `workspace.check` calls `currentVersions` (image check) before the states and this after them.
- `outdatedFindingsOf(layout, element, context)`: the findings of one element, with lines, as the state has them.
- `outdatedOfShown(context, element)`: the outdated relations and links of one element shown (SR-026 AK3), by the same rules, before their lines are known (items carry their path, links their line). The current versions come from the state when its build has ended (`currentVersionsIfBuilt`), else only the targets' versions are read from their files (`currentVersionsOf`); a single element never waits for or starts the whole build, unless its targets are a quarter of the store (ADR-0008). `elementHints` (`element.ts`) is the `ElementHints` function `element.get`, `element.resolve`, `element.create` and `element.update` pass to the model: `supersededValidityFindingsOf` (SR-040 AK3), `nestedVariantFindingsOf` (SR-039 AK3), `targetNotCoreFindingsOf` (SR-041 AK8: its replacements and exclusions that name no core requirement), the element's cycle (`elementCycleFindings` in `trace/cycles.ts`: from the kept cycle state when built, else a walk up from the element), its outdated evidence (`elementEvidenceFindings`: from the kept state when built, else its records and its own current version), then these hints, so every hint `hint.list` lists for an element is shown at it (tested per element on the fixtures of every hint kind); with `versionDate` their messages and fields carry the dates (`datedProblems`), without it no git runs.
- `confirmHints(workspace, { hintIds, ref, target, kind })` (`confirm.ts`, command `hint.confirm`, SR-027, D-042): `ref` and `target` select the open hints with a hint ID about `ref` and pointing at `target` (both when both are given; the sources of `target` from the incoming index, `incomingTo`), `kind` narrows that selection; the selected IDs join `hintIds` as one set, each once, `confirmed` names the given ones first (#310). No `hintIds`, `ref` or `target`, or `kind` without `ref` or `target`, is `input.invalid`; a selection without an open hint to confirm is a `hint.not-found` warning. Each ID (`parseHintId`) names a source record of the store by repository, file and UUID; it is confirmed when the open outdated relations and references of that source (`outdatedOfShown`) have its canonical form (`hintIdOf` of the parsed ID; another spelling of a given ID is written once). A relation item gets its `version` scalar replaced with the target's current version (`set-scalar` of `editElementFile`; relation kinds and relation-valued properties, list or single), and through `writeElementFiles` the current titles of the same-repository targets of the file (`withCurrentTitles`, decision on #307); an inline reference only the value of its first `version=` parameter (the `n`-th link with that target, repository and stored version). A link in a Markdown property (SR-127) is rewritten inside the source text of its scalar (`set-scalar` with `source`, so plain stays plain and no other byte changes; a block scalar is replaced as one line, `replace-item` or `set`); its message names the property and the item (`placeOfReference`); `referencesOf(element, metamodel)` gives the references of the text and of the marked properties to every check. Items that share an ID are confirmed together. Each hint as if confirmed on its own: a hint whose target is a source this call writes gets that source's version after the write (the bytes are planned, the new versions computed with `elementVersion`, and only the sources with a hint on a target whose version changed are planned again, until none changes, at most one round per planned target and one more; a ring of inline references never settles (#281) and costs only its own files per round). One write per file; `assertElementWritable` and `readUnchanged` for every file before the first write, then `writeElementFiles`. A file the writer cannot change in place (a version held by a YAML alias or anchor) is not written: its IDs get `hint.not-confirmable` with the writer's reason, the other files are written. An ID of no confirmable hint is a problem `hint.not-confirmable` (error; only version hints, `relation.outdated` and `variant.core-changed`, can be confirmed, spec question #299), an ID that no open hint has `hint.not-found` (warning, exit code 0); both carry the ID as `hintId`, and the other IDs are still confirmed. Returns `confirmed` (in input order, then the selected IDs, each once), `files` and `problems`. Confirming a reference changes the source's text and so its version (ADR-0005; spec question #281).
- `listHints(workspace, input)` (`list.ts`, command `hint.list`, SR-026): a hint is a finding of severity `warning` that names an element (`isHint`; glossary "Hinweis": the element should be checked, it blocks nothing). The states of `HINT_STATES` (those of `FINDING_STATES` that can give warnings; duplicate UUIDs and missing targets give errors only), then the outdated relations, in the order of `workspace.check`; `currentVersions` checks the images first. Filters (`resolveHintFilter`, AND across filters, any of the values within one): `kind` (codes), `type` (`allowsType`: subtypes count, SR-012), `package` (the property with the meaning `packages` lists it; needs the meanings `packages` and `package`, `input.invalid` for another type; a `packages` property that holds no relations matches nothing), `variant` (`resolveView`, `viewRuleOf`: the elements the view of the variant holds; no validity applies in every variant unless the variant excludes or replaces it), `ref` (the element of the hint, by UUID and repository and file: the element's own, `elementRepository` and `elementFile`, where the problem names another file, as outdated evidence names its record file; else the problem's; when that names no record, the only record of the UUID). Only the outdated relations that pass get dates (`datedProblems`). Each hint names its element's short ID too (`elementShortId`, for display; #310), added by `invoke` as on the problems of every command (#315), so `hint.list` and `workspace.check` give equal hints. `incomplete` while a repository is not on this machine. Nothing against an invalid metamodel.
- Hint IDs (`hint-id.ts`, resolved by `hint.confirm`, SR-027): `relation.outdated/<repository>/<file>/<source>/<key>/<target>?version=<stored>[&repository=<name>]` for a relation item, `relation.outdated/<repository>/<file>/<source>/@text/<target>?version=<stored>[&repository=<name>]&n=<k>` for the k-th link in the text with that target, repository and version, and `relation.outdated/<repository>/<file>/<source>/@text:<key>/<target>?version=<stored>[&repository=<name>]&n=<k>` for the k-th such link in the values of the property `<key>` marked `markdown` (SR-127; a list is one text; the key follows a colon because a key can be `text`; `parseHintId` takes only a valid key). `variant.core-changed/<repository>/<file>/<source>/<key>/<target>?version=<stored>[&repository=<name>]` names the `replaces` item of a variant requirement onto a changed core requirement (SR-045), with the place rules of a relation item; it has no `@text` form. `CONFIRMABLE_CODES` are the two codes; the parsed `HintTarget` carries its `code`, so `hintIdOf` gives the ID back with it. Nothing raises `variant.core-changed` before SR-045 is built; until then `hint.confirm` of such an ID is `hint.not-found`. `<repository>` and `<file>` are the source's repository and file (percent-encoded), so two files with one UUID (SR-088) have different IDs. Items of one list with the same target, repository and stored version share an ID: confirming it confirms every such item. `hintIdOf`, `parseHintId` (form only; whether the relation still exists and is outdated is the caller's question).
- `outdatedEvidenceProblemsState` (from `evidenceRecordsState` of the [evidence block](evidence-records.md), empty until its readers are in, SR-028 #40): per element, kind and variant the newest record by date; one `evidence.outdated` (warning) when its version is not the current one (SR-025 AK4, tested at core level, #127 option 1). `repository`, `file` and `line` are the record's; `elementRepository` and `elementFile` name the element's own file (one copy of a shared UUID, SR-088). At one element shown (`elementEvidenceFindings`, SR-026 AK3) the hints come from that state when its build has ended, else from the element's own records alone: those of its UUID in the evidence index (`byElement`), put back into the order of `evidenceRecordsState` (`positionOf`) so that a tie of dates names the same record as the state (two locations whose repositories are not in name order). The element's current version is read only when it has records. Called only against a valid metamodel (`getElement`, the write path). Cost at N-036 (#698): the records of the element and one map lookup, instead of grouping all 81,904 records of the E4 workspace (about 170 ms per open); the first call builds the position map of the index once.
- Cost at 50,000 elements and 200,000 relations (`test/perf/outdated-relations.test.ts`, shared 4-core container): the current versions (4 to 5 s, #259) and one pass over the relations; with 500 targets changed after the commit (every relation and link to them outdated) the whole check took 8.7 s in process. Worst case, every relation and link outdated (300,009 findings): current versions 3.8 s, findings with lines 9.3 s, the dates of every stored and current version with Git 32 s (one walk per target file, every element a target); the CLI check of that workspace without Git (`[SR-020/AK1]`, no dates to walk for) took 36.6 s against SR-020's 60 s. With Git the worst case is above 60 s for the CLI (about 37 s + 32 s); capping the dates is spec question #287.

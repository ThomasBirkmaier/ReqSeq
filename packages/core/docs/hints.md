# Hints block (`src/hints/`)

Part of the [`@reqseq/core` README](../README.md).

Hints that someone settles by confirming them (D-042), and the list of all open hints (SR-026). Kinds: outdated relations and inline references (SR-025), outdated evidence (SR-025 AK4), the list (`hint.list`), the hints at the element and confirming them (`hint.confirm`, SR-027); a changed core requirement at its replacement (`variant.core-changed`, SR-045) and at a variant since its newest baseline (SR-103). It imports the model, metamodel, workspace, variants, trace and baselines blocks, never `commands` or `query`.

- `outdatedRelationsState` (depends on the element store, the metamodel, the short IDs, `currentVersionsState` and `incomingState`), for `workspace.check`: one `OutdatedFinding` (`element`, `target`, `stored`, `current`, `problem`) per item of a relation kind or relation-valued property (validity, packages; ADR-0004) with a stored `version` of a normal form the tool computes (n1, n2; `isKnownVersion`), and per inline reference with one, whose target is `available` (`targetState`, `referenceTargetState`) and has a current version other than the stored one, compared in the stored version's form (`sameVersion`, ADR-0005 "Normal form 2"); `currentVersion` is the form `hint.confirm` writes (`NORMAL_FORM`). Missing, ambiguous, inaccessible and unknown-repository targets are other findings; a target without a current version is left out. The problem: code `relation.outdated`, or `variant.core-changed` for an item of a relation kind with the meaning `replacement` from a source with a validity entry onto a core requirement (`isCoreChange`, `core-changed.ts`, SR-045: one hint at the replacement, not two, AK1; confirmed the same way, AK2; a superseded target keeps the usual hints, AK4, assumption: `relation.target-superseded`, and `relation.outdated` when its content changed too; no `relation.target-superseded` from a replacing requirement with an invalid status, SR-072 AK2), severity `warning` (with `failOn: warning` (ThomasBirkmaier/ReqSeq-archive#304) `ok` false, CLI exit code 1, ADR-0009), repository, file, line, `elementId` (source), `targetId`, `storedVersion`, `currentVersion`, `hintId`, and the place as data next to the ID (#222): `key` (the relation kind or property of the item, or the property marked `markdown` that holds the link; none for a link in the text) and `place` (`in`: `relation` or `text`, the `repository` the item or link names as written, and for `text` its `occurrence`), so that no access parses the ID. Store order, then key and item order in the file, then the links in text order. None from a source whose status the metamodel marks invalid (SR-025 AK5, D-044), so neither `relation.outdated` nor `variant.core-changed`; `outdatedAmong` (the `outdated` mark of trace.graph) and the `outdated` of the edges still compare its versions, so the relation stays visible in the chain. Nothing against an invalid metamodel (ThomasBirkmaier/ReqSeq-archive#208, ThomasBirkmaier/ReqSeq-archive#220). The pass over the store runs in slices of 20 ms (`forEachSliced`, SR-082).
- Lines (`locateOutdated`): one rule for items and links: the line in the file as it is now when the file is unchanged since the store read it (SHA-256 of the snapshot), none when it changed. Item lines come from a scan of the frontmatter text (`textLineOf` on the lines of each source split once, `frontmatterLines`, in `model/item-lines.ts`: a top-level key at the start of a line and one flow mapping per item, as ReqSeq writes relations); only where the text is written in another layout is the YAML parsed (`findingLocator`). A link has its line from the store.
- Carried over a save or a watcher batch (`carryStoreUpdate`, ThomasBirkmaier/ReqSeq-archive#184): when every changed UUID keeps its repositories and types and the incoming index of the store before the change is there (the build makes it; the dependency on `incomingState` carries it first), only the changed files and the sources of relations and links to a changed UUID (`relationsById`, `referencesById`) are looked at again (their records found by file, `contributionIn`); the rest is kept and the new findings are merged in by store order (repository order, then file path), without a pass over the store (#215). Otherwise (a new or deleted element, no index) it is built again.
- `datedProblems(workspace, findings)`: the problems with `storedDate`, `currentDate`, `storedCommit` and `currentCommit` (`versionStarts`, one request per distinct target and version, one walk per target file) and both dates with their commits in the message (`: stored version from X (1a2b3c4d5e6f), current version from Y (…)`, the commit's first 12 characters, #252). A missing date is `no date`, and its cause is said once at the end (`(the repository is a shallow clone)`; `undatedCause`, once per repository with a missing date); without both dates the message ends `: neither version has a date (...)` (#252). When only the stored version has no date and the metamodel folder has a commit newer than the start of the current version (`metamodelChange`, asked once per call and only then), the cause also names that commit: `(not committed, or Git cannot tell; the metamodel changed on Z (…), and older commits are read with today's metamodel)`, because a version at an older commit is computed with today's metamodel, so neither date tells when the version changed (#252, P-2-09). Per call, so a new commit never leaves old dates in a kept state. `workspace.check` calls `currentVersions` (image check) before the states and this after them.
- `outdatedFindingsOf(layout, element, context)`: the findings of one element, with lines, as the state has them.
- `outdatedOfShown(context, element)`: the outdated relations and links of one element shown (SR-026 AK3), by the same rules, before their lines are known (items carry their path, links their line). The current versions come from the state when its build has ended (`currentVersionsIfBuilt`), else only the targets' versions are read from their files (`currentVersionsOf`); a single element never waits for or starts the whole build, unless its targets are a quarter of the store (ADR-0008). `elementHints` (`element.ts`) is the `ElementHints` function `element.get`, `element.resolve`, `element.create` and `element.update` pass to the model: `supersededValidityFindingsOf` (SR-040 AK3), `nestedVariantFindingsOf` (SR-039 AK3), `targetNotCoreFindingsOf` (SR-041 AK8: its replacements and exclusions that name no core requirement), the element's cycle (`elementCycleFindings` in `trace/cycles.ts`: from the kept cycle state when built, else a walk up from the element), a requirement without a parent (`elementNoParentFindings` in `trace/no-parent.ts`, SR-022 AK6, the same rule on the element alone), its outdated evidence (`elementEvidenceFindings`: from the kept state when built, else its records and its own current version), then these hints, so every hint `hint.list` lists for an element is shown at it (tested per element on the fixtures of every hint kind); with `versionDate` their messages and fields carry the dates (`datedProblems`), without it no git runs.
- `confirmHints(workspace, { hintIds, ref, target, kind, all, expected })` (`confirm.ts`, command `hint.confirm`, SR-027, D-042): `ref` and `target` select the open hints with a hint ID about `ref` and pointing at `target` (both when both are given; the sources of `target` from the incoming index, `incomingTo`), `kind` narrows that selection; the selected IDs join `hintIds` as one set, each once, `confirmed` names the given ones first (ThomasBirkmaier/ReqSeq-archive#310). `all` (#644) selects the findings of `outdatedRelationsState` with a code of `kind` (the state hint.list reads, so at N-036 the current versions are built once and only the sources with a hint are planned; measured in `test/perf/outdated-relations.test.ts`); it needs `kind` and `expected` and goes with neither `ref` nor `target`; `kind` names only the confirmable codes (a since-baseline code gives its `hint.not-confirmable` refusal before the count, nothing written; another code is `input.invalid`), and the current versions are checked for changed images first, as hint.list does (`currentVersions`). `expected` (any selection) is the number of hints the call confirms, counted as hint.list counts them (a relation written twice is two hints with one ID); another number is `input.invalid` (`reason: count-changed`) before anything is written, so hints that came after the review are never confirmed unseen. No `hintIds`, `ref`, `target` or `all`, or `kind` without one of the selections, is `input.invalid`; a selection without an open hint to confirm is a `hint.not-found` warning. Each ID (`parseHintId`) names a source record of the store by repository, file and UUID; it is confirmed when the open outdated relations and references of that source (`outdatedOfShown`) have its canonical form (`hintIdOf` of the parsed ID; another spelling of a given ID is written once). A relation item gets its `version` scalar replaced with the target's current version (`set-scalar` of `editElementFile`; relation kinds and relation-valued properties, list or single), and through `writeElementFiles` the current titles of the same-repository targets of the file (`withCurrentTitles`, decision on ThomasBirkmaier/ReqSeq-archive#307); an inline reference only the value of its first `version=` parameter (the `n`-th link with that target, repository and stored version). A link in a Markdown property (SR-127) is rewritten inside the source text of its scalar (`set-scalar` with `source`, so plain stays plain and no other byte changes; a block scalar is replaced as one line, `replace-item` or `set`); its message names the property and the item (`placeOfReference`); `referencesOf(element, metamodel)` gives the references of the text and of the marked properties to every check. Items that share an ID are confirmed together. Each hint as if confirmed on its own: a hint whose target is a source this call writes gets that source's version after the write, which is its current version, since what a confirmation writes (relation `version` values and titles, `version=` parameters) is no part of the n2 version of its source (ADR-0005 "Normal form 2"); so one plan with the current versions settles chains and rings of references alike (#166, #1328). One write per file; `assertElementWritable` and `readUnchanged` for every file before the first write, then `writeElementFiles`. A file the writer cannot change in place (a version held by a YAML alias or anchor) is not written: its IDs get `hint.not-confirmable` with the writer's reason, the other files are written. An ID of no confirmable hint is a problem `hint.not-confirmable` (error; only version hints, `relation.outdated` and `variant.core-changed`, can be confirmed, spec question ThomasBirkmaier/ReqSeq-archive#299), an ID that no open hint has `hint.not-found` (warning, exit code 0); both carry the ID as `hintId`, and the other IDs are still confirmed. Returns `confirmed` (in input order, then the selected IDs, each once), `files` and `problems`. Confirming writes the target's version in normal form n2; it changes the source's text but not its n2 version (ADR-0005 "Normal form 2", #166), so references that name each other settle once each hint is confirmed. A link that stores n1 of the source becomes outdated once, as its n1 version changed.
- `listHints(workspace, input)` (`list.ts`, command `hint.list`, SR-026): a hint is a finding of severity `warning` that names an element (`isHint`; glossary "Hinweis": the element should be checked, it blocks nothing). The states of `HINT_STATES` (those of `FINDING_STATES` that can give warnings, the item limits of SR-171 and the relation limits of SR-152 among them; duplicate UUIDs and missing targets give errors only), then the since-baseline hints, then the outdated relations, in the order of `workspace.check`; `currentVersions` checks the images first. Filters (`resolveHintFilter`, AND across filters, any of the values within one): `kind` (codes), `type` (`allowsType`: subtypes count, SR-012), `package` (the property with the meaning `packages` lists it; needs the meanings `packages` and `package`, `input.invalid` for another type; a `packages` property that holds no relations matches nothing), `variant` (`resolveView`, `viewRuleOf`: the elements the view of the variant holds; no validity applies in every variant unless the variant excludes or replaces it; a since-baseline hint only for its own variant, and only that variant's are computed), `ref` (the element of the hint, by UUID and repository and file: the element's own, `elementRepository` and `elementFile`, where the problem names another file, as outdated evidence names its record file; else the problem's; when that names no record, the only record of the UUID). Since-baseline hints are computed only for the variants the filters can admit (`sinceBaselineVariants`): none when `kind` names neither code or `variant` is `core`, the variant of `variant` or the element of `ref` alone, every variant otherwise, each kept only when it passes `type` and `package`; so `ref` of a requirement or `type` without a variant type reads no baseline (N-036, SR-026 AK2, AK3). Pages as `trace.chain` (#146): every hint that passes is found and counted (`total`), and the output holds `limit` (default 200, at most 5,000) from `offset` (`hintsOf` with a `HintPage`). Only the outdated relations of the page get dates (`datedProblems`). With `ref` it takes the single-element path of `element.get` (#145, ADR-0008): `showElement` with `elementHints` (dated; the since-baseline hints only when `sinceBaselineVariants` admits the element), filtered the same way and put into the order of the check by code (`CHECK_ORDER`, `inCheckOrder`, stable; a code the check gives no hint with, such as the `file.faulty` warning of an element without a version, ThomasBirkmaier/ReqSeq-archive#276, is left out; `hints/list-ref.test.ts` checks that every hint code of `HINT_STATES` is in `CHECK_ORDER`), and pages as above, so it builds neither the incoming index nor the cycles or other hint states of the store, and skips the image check; per element it equals the whole list (`hints/list-ref.test.ts`). Each hint names its element's short ID too (`elementShortId`, for display; ThomasBirkmaier/ReqSeq-archive#310), added by `invoke` as on the problems of every command (ThomasBirkmaier/ReqSeq-archive#315), so `hint.list` and `workspace.check` give equal hints. `incomplete` while a repository is not on this machine. Nothing against an invalid metamodel.
- Since the newest baseline of a variant (`since-baseline.ts`, SR-103, D-042): `sinceBaselineProblems(context, variants?)` for `workspace.check`, `hint.list` and `hint.confirm` (every variant, or those given), `sinceBaselineFindingsOf` for `element.get` of a variant (`elementHints`). Not a state: a new baseline file changes them without a store change. A baseline of variant A stores a selection of exactly the key `view` naming A (`{ id, title }`, `{ id, repository }` by `resolveTarget` from the file's repository, a text by `resolveRef`); the newest is chosen by `newestBaselines` (baselines block: latest date and time, on a tie the last file, AK4); no stored selection is resolved and Git is not asked. For each core requirement (`isCoreRequirement`, found once per store) that A's view holds now (no variant rule removes it, `removersOf`, so excluded and replaced ones drop out, AK6) the baseline entry: a UUID with one copy in the store whose version the baseline lists is unchanged (`containsKey`), any other is looked up by the copy rule (`copyOf`, SR-088). Another version is `variant.core-changed-since-baseline` with `storedVersion` and `currentVersion` (AK1; a version that cannot be computed counts as changed, without `currentVersion`), no entry is `variant.core-new-since-baseline` with `currentVersion` only (AK7). At A's file, the line of `id`, `targetId` the core requirement, severity `warning`, no `hintId`. No baseline, no hint (AK3). `hint.confirm` refuses both with `hint.not-confirmable` naming the reason (AK5): for a `kind` with the code, an ID starting with it, and `ref` without `kind` naming a variant with such open hints (that variant alone is computed); the `hint.not-found` warning of an empty selection is then left out. `ref` of a variant still confirms its other open hints (its outdated relations, `variant.core-changed` of its replacements) in the same call, and the refusal makes it exit 1. `target` is not checked for them, since that would compute every variant. Kept per variant (`memoState`): the hits with the chosen `Baseline` object, store, metamodel and `currentVersionsState` value; a new or changed baseline file gives a new object. Over a store change the hits are carried (`carried`, `storeUpdate`) when every changed UUID keeps one copy in the same file, its rule items (with a replacement item also its validity, which names the variants it acts in) and whether it is a core requirement; then only the changed core requirements are looked at again. Kept or carried, the core requirements with images or without a version get their version again on each call (`currentVersionsOf`), so a changed image shows at once. Anything else is the full pass. Cost (N-036): the baseline headers (4 KiB each, kept by stamp), one full read of the newest baseline per variant (kept), then the carried hits or the full pass: the current versions of all core requirements (`currentVersionsOf`, the whole store), one pass per variant with one lookup each. Cold, the first call for a variant with a baseline waits for the versions build (4–5 s at N-036, ThomasBirkmaier/ReqSeq-archive#259), for example `element.get` of a variant in a new CLI process or in the app before its background build ends; a variant without a baseline returns before. Measured in `test/perf/since-baseline.test.ts` (in process, versions built).
- Hint IDs (`hint-id.ts`, resolved by `hint.confirm`, SR-027): `relation.outdated/<repository>/<file>/<source>/<key>/<target>?version=<stored>[&repository=<name>]` for a relation item, `relation.outdated/<repository>/<file>/<source>/@text/<target>?version=<stored>[&repository=<name>]&n=<k>` for the k-th link in the text with that target, repository and version, and `relation.outdated/<repository>/<file>/<source>/@text:<key>/<target>?version=<stored>[&repository=<name>]&n=<k>` for the k-th such link in the values of the property `<key>` marked `markdown` (SR-127; a list is one text; the key follows a colon because a key can be `text`; `parseHintId` takes only a valid key). `variant.core-changed/<repository>/<file>/<source>/<key>/<target>?version=<stored>[&repository=<name>]` names the `replaces` item of a variant requirement onto a changed core requirement (SR-045), with the place rules of a relation item; it has no `@text` form. `CONFIRMABLE_CODES` are the two codes; the parsed `HintTarget` carries its `code`, so `hintIdOf` gives the ID back with it. `<repository>` and `<file>` are the source's repository and file (percent-encoded), so two files with one UUID (SR-088) have different IDs. Items of one list with the same target, repository and stored version share an ID: confirming it confirms every such item. `hintIdOf`, `parseHintId` (form only; whether the relation still exists and is outdated is the caller's question). The ID is opaque to every access: the app and agents read `key` and `place` of the problem instead (#222).
- `outdatedEvidenceProblemsState` (from `evidenceRecordsState` of the [evidence block](evidence-records.md), empty until its readers are in, SR-028 ThomasBirkmaier/ReqSeq-archive#40): per element, kind and variant of its records whose status in that view is `outdated` (`verificationStatusOf` with the element's acceptance criteria, so also one criterion with records of older versions only beside verified ones, SR-031 AK8; `recordStatusOf` for validation), one `evidence.outdated` (warning) naming the newest record of an older version by date among the records that count in the view (`holdsIn`), with a record of the current version among them the outdated criteria and the newest record of one of them (SR-025 AK4, tested at core level, ThomasBirkmaier/ReqSeq-archive#127 option 1; the hint follows the status, #201). For an element of a repository the workspace file marks `variant-independent` (SR-173) a variant's status pools the records without variant, and its hint names the variant (#817 Q10); the state therefore also depends on `workspaceLayoutState`. `repository`, `file` and `line` are the record's; `elementRepository` and `elementFile` name the element's own file (one copy of a shared UUID, SR-088). At one element shown (`elementEvidenceFindings`, SR-026 AK3) the hints come from that state when its build has ended, else from the element's own records alone: those of its UUID in the evidence index (`byElement`), put back into the order of `evidenceRecordsState` (`positionOf`) so that a tie of dates names the same record as the state (two locations whose repositories are not in name order). The element's current version is read only when it has records. Called only against a valid metamodel (`getElement`, the write path). Cost at N-036 (ThomasBirkmaier/ReqSeq-archive#698): the records of the element and one map lookup, instead of grouping all 81,904 records of the E4 workspace (about 170 ms per open); the first call builds the position map of the index once.
- Cost at 50,000 elements and 200,000 relations (`test/perf/outdated-relations.test.ts`, shared 4-core container): the current versions (4 to 5 s, ThomasBirkmaier/ReqSeq-archive#259) and one pass over the relations; with 500 targets changed after the commit (every relation and link to them outdated) the whole check took 8.7 s in process. Worst case, every relation and link outdated (300,009 findings): current versions 3.8 s, findings with lines 9.3 s, the dates of every stored and current version with Git 32 s (one walk per target file, every element a target); the CLI check of that workspace without Git (`[SR-020/AK1]`, no dates to walk for) took 36.6 s against SR-020's 60 s. With Git the worst case is above 60 s for the CLI (about 37 s + 32 s); capping the dates is spec question ThomasBirkmaier/ReqSeq-archive#287.

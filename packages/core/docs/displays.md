# Displays block (`src/displays/`)

The display models that the web UI and the HTML export share (ADR-0019): one pure builder per display, which takes command outputs as they are and gives the rows, groups, order, bounds and words both sides render. Public as the subpath `@reqseq/core/displays` (`index.ts`). Its modules import only types, each other and the import-free modules of core (`graph/words.ts`, `model/criterion-items.ts`, `problem-titles.ts`, `hint-order.ts`, `query/fold.ts`, `type-order.ts`), so the bundle of the web UI's pages loads no `node:*` with it; the `no-restricted-imports` block on `packages/core/src/displays/**` in `eslint.config.js` enforces it.

- Words (`verification.ts`, `labels.ts`): `verificationLabel(cell, "long" | "short")`, the criteria count of the verification status of SR-031 AK5 ("open, 2 of 3 criteria, AK3 (k7f3) not verified"; short, for cells and badges, "open · 2 of 3"; the status alone without counted criteria), which the export's fields and list badges and the CLI's text output use; `relationGroupLabel` (an outgoing kind by its name, an incoming one by its `inverse-name`, else its name, as `trace.matrix` names an incoming column, a relation property by its name, the key where the metamodel names none, "Inline reference", incoming with "← "); `criterionStatuses(rows, count)`, the verification status of each acceptance criterion from the verification rows of `evidence.list` `display` in the view asked for, `open` for a criterion without a row (#2234, SR-031 AK5); `emptyValueLabel` ("–", SR-232 AK1); `boundNote` ("Only the nearest 100 are shown.", SR-232 AK5); `shownId` (SR-084 AK4, from `graph/words.ts`).
- `ElementRef` (`element-ref.ts`): an element as a row shows it and where it leads, by UUID and repository (no URL, ADR-0019 point 5), with `invalid` for a status the metamodel marks invalid (D-044).
- Open hints (`open-hints.ts`): `openHints(problems)` keeps the problems of `element.get` that `hint.list` gives for the element, in its order (`isHint`, `inCheckOrder` of `hint-order.ts`), for the hint section of the element page (SR-232 AK4; ADR-0019 point 9(c)). Every warning that names the element is one, the `file.faulty` warning of an element without a version among them; `metamodel.meaning-unassigned` names none and is no entry (#2231).
- `elementPageDisplay` (`element-page.ts`): of `element.get` (the export: the same shape from `listElements`), the verification cells in core's order, the relation groups (`relationGroupsOf`: outgoing first, then incoming; within each the kinds in the order of the metamodel, then kinds it does not know in the order they first appear; the targets of an outgoing relation property are left out, they are property values), the open hints (`hint.list` when given, else `openHints`) and `readOnly`. Option `relations`: `all` for every relation, `outgoing` for the export page (SR-232 AK1) and the web UI's element page; both pass the names of the metamodel.
- `elementProblemGroups` (`element-problems.ts`): the problems of `element.get` `element.problems` as the web UI's element page lists them (#2234): one group per severity and kind, errors first, then warnings, then info, each headed by the title of its kind (`problemTitle`; its code for a kind without one); within a severity the groups in the order their first problem appears, each group in the output's order.
- `overviewDisplay` (`overview.ts`): the type lines of the export's start page (SR-233 AK3) from `element.facets` `types`, each with its list as target. The counts follow the export's lists (ADR-0019 point 9(a)): it passes `typeCounts` of the elements of its lists (no invalid status, SR-231 AK1), which counts as `element.facets` does for `{ where: { invalid: false } }`, except that copies of a UUID several files share get no page and so are not counted by the export. The order of types is `inTypeOrder` of the root module `type-order.ts`, which `element.facets` and the export's lists use too. The web UI does not use it.
- `hintListDisplay` (`hint-list.ts`, SR-026): of the output of `hint.list` and the names of the variants by UUID, the total, the number of hints on the page, `incomplete`, and a group per entry of `kinds` in its order with its count and the title of its kind (`problemTitle`, SR-224 AK6, D-078; its code for a kind without one). Each group holds the hints of the page of its kind in the order of the output, each with its element (`shownId`, else its identifier, UUID or file), the element's title and name (`shownIdTitle`), the reason (`hintReason`: of a count its relation kind or property, target type, count and limit; of outdated evidence the view; of a relation to a resolved target its kind and that target; else the start of the message, `messageStart`, after the relation kind and the target where there are any), the message, and its `ElementTarget` (the element's own repository, not that of an evidence record). Nothing uses it yet (#2209).
- `neighbourhoodDisplay` (`neighbourhood.ts`): of the answers of `trace.neighbourhood` (parents: the up walk over the derivations; children: the down walk; incoming: one step down over every key), the parents level by level, topmost first, with the notes of the outdated links of shown elements to them; the children as a tree, depth first in walk order, repeated places as leaves, the element itself where a cycle leads back to it among them (SR-107 AK3), opened rows below (`open`: the keys the reader opened, or `all` for the export), drawn from the shown elements only; the incoming links per key in the order they first appear, derivations left out, a link of the element to itself kept (SR-107 AK5), and with option `withoutPackageMembers` (the key of the property with the meaning `packages`, set on the export's package page) the group of that property left out as a whole (SR-232 AK9); a link's source is looked up among the shown elements and the element itself. Option `bound` per part: the export's 100 parents and 100 children (SR-232 AK5); `more` when the walk reached more or the answer is one page of more. Built with a stack, not recursion: a chain can be thousands of levels deep.
- `listDisplay` (`list.ts`): of the rows of `element.list` (the export: the same shape from `listElements`) with their verification in the list's view (`rowVerification`; the core in the export) and their open hints, the columns, the filters with their values in the order of SR-075 AK1 and "–" last (the groups), and per row its cells, search text, facets and ranks (SR-233 AK1, AK5). Rows stay in the order given. The order of values is the caller's rule (`ListOrder`, the export's `listOrderOf`), asked once per distinct value, so the builder sorts once per column. Option `id`: `identifier` for the export (SR-233 AK1), or `shownId` (SR-084 AK4). A requirement outside the list's view shows "–" (SR-137 AK4). The web UI's lists do not use it. `relation-text.ts` names the other end of a relation (`relationText`, `nameOf`), as `html-export/links.ts` re-exports it.
- `packageDisplay` (`package.ts`): the elements of a package on its export page (SR-233 AK4), on the rows of the list display (`ListRowInput`, `rowId`, `rowCell` of `list.ts`): per element its identifier (option `id`, as `listDisplay`), title, status ("–" without one) and verification status in the row's view, the status alone ("–" for an element that is no requirement and for a requirement outside that view, SR-137 AK4), in the order given; the columns; and the package as target. Option `invalid`: `omit` for the export, whose pages hold no element with an invalid status (SR-231 AK1), or `keep`. Its members follow the rule of `element.list` `where.package` (D-040): `packageMembers` reads them from the relations of `element.list` (the property with the meaning `packages`, outgoing, in the repository the relation gives, D-058), for all packages in one pass over the rows; the export, which calls no command, takes its members from it. `isPackageType` tells whether an element of a type has a package page (the meaning package in `metamodel.get`); `targetKey` keys a package by UUID and repository. The web UI does not use it.
- Cost (N-036, SR-082): a builder works on one page's inputs; the export builds each model just before writing its page and keeps none. The relation groups sort once per page; the neighbourhood is linear in its answers.
- Tests: the builders' own tests (`*.test.ts` here); `html-export/display-input.test.ts` checks on one fixture that the export's batch and the commands give the same model (ADR-0019 point 2), that the start page shows the type lines of `element.facets`, and that `openHints` of `element.get` equals `hint.list`; `fixtures/displays/element-page.json` feeds `html-export/display-render.test.ts`, so the export shows every group and label of the model. For the neighbourhood: `html-export/neighbourhood-input.test.ts` checks on one fixture that the export's walks and `trace.neighbourhood` give the same model (ADR-0019 point 2), with an element that points at itself and a cycle back to it; `fixtures/displays/neighbourhood.json` feeds `html-export/neighbourhood-render.test.ts`, so the export shows every row and group of the model. `html-export/list-input.test.ts` checks that the export's batch and `element.list` with `hint.list` give the same list models, `html-export/list-render.test.ts` that the export shows each part of one. `html-export/package-input.test.ts` checks that the export's members and `element.list` `where.package` give the same package page models (a member only in a variant's view, a package in a package, a member with an invalid status, an entry in another repository, a package without members), `html-export/package-render.test.ts` that the export shows each part of one.

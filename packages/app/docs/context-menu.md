# Context menu

Part of the [`@reqseq/app` README](../README.md).

A right-click in an area of the sheet, on macOS also a click with Ctrl held, opens the app's own menu at the pointer (D-075, SR-194). It is no menu of the system: the window prevents every `contextmenu` and draws `ContextMenu.tsx` beside the minibuffer, in the tokens of the card (`.context-menu`). The menu brings no functions of its own. Each entry is an entry of the command prompt, under its name and with its key (`commands().items`, SR-109), shown only where it can run now; the last one, after a separator, is "All commands…" with the key of the command prompt, which opens the command prompt with an empty input (SR-133 orders it by fit to the shown view).

- **Places (`context-menu.ts`):** `MENU_PLACES` holds the fixed entries of each place, as action ids or `command:<name>`. A view marks a place with `data-menu="<place>"`; `placeAt` takes the nearest mark inside the area (`[data-area]`), and a press on no mark, or on a place whose block is still empty, gets the entries of `buffer` (AK6). Outside the areas there is no menu, except on the ID and the status of an element in the modeline (SR-196, below). A place works out its details from `MenuHit` (`place`, `target`, `point`); nothing parses `data-menu-*`. A unit test checks that every id is an action or a catalog command no action covers. Each block keeps its lines, so the SRs that fill a place touch only their own.
- **Opening (`use-context-menu.ts`):** the right press (and on macOS Ctrl+left, `opensMenu`) in an area is prevented, so Chromium selects no word and starts no drag; it focuses what it pressed, and in a text editor puts the caret at the pointer unless the press is inside the selection (`focusPressed`). The `contextmenu` that follows opens the menu 2 px right of and below the pointer, or left of and above it where the window has no room, measured before the first paint (`menuPosition`). A `contextmenu` without a press (the Menu key, Shift+F10) opens at the caret, the selected row or node, or the area's corner, with the first entry selected. An open prompt ends. On macOS the Ctrl+press and its click go nowhere else (not to a list, a link or a drag), and Blink sends the `contextmenu` itself.
- **Selection (AK5):** a right-click on a list row, a search hit, a row of the overview or the neighbourhood, an entry of a package page, a node of the graph or the metamodel, a target of the matrix or a cell of the matrix selects it in the same render that opens the menu (each view's `onContextMenu`). The element is the marked one of the context (`markedElement`): the matrix reports its selected target, or the row of its selected cell (`aria-selected` on the `gridcell`), and a package page its selected entry. The marks set so far are `element-entry` (rows, hits, nodes, the matrix's row heads), `matrix-target` (a connected element in a cell) and `matrix-cell`.
- **Running (AK2):** a click with the left button closes the menu and runs the entry with the id clicked, from the command prompt's entries built again from the latest context, after the same step a prompt takes first (`beforeCommand`: the input of the element is saved, the message goes). A choice in the menu is not recorded as a use of the command prompt.
- **Keys and focus:** the menu never takes the focus, so the editor, the list and the active area keep theirs. While it is open the window takes its keys first (`CONTEXT_MENU_KEYS`: Up/Down and Ctrl+P/N, Home/End, Enter/Space, Escape); any other key closes it and acts as without it.
- **Closing (AK4):** Escape; a press of the left or middle button outside it, which then acts as it would without the menu (as the command prompt in SR-134 AK3; the assumption of the PR); a right-click elsewhere, which opens that place's menu; a blur, a resize, a wheel outside, another shown buffer and an opening prompt. While it is open the mouse buttons Back and Forward do nothing.

## buffer

SR-194 AK6: "Go to element or buffer", "Search elements", "Close buffer", "Split window"; in a split window "Other window" and "Unsplit window" in place of "Split window".

## text

SR-195 (`text-menu.ts`), marked on the editor of the element's text (`Editor` with `menu="text"`), not on the boxes of properties: "Follow reference" first on a reference to an element (AK4); "Cut" and "Copy" with text selected, then always "Paste", "Bold", "Italic", "Inline code", "Link" and "Insert image" (AK1); in a table "Insert row", "Delete row", "Insert column", "Delete column" and "Align table" (AK5); on a heading with a section "Fold section", or "Unfold section" when it is folded (AK6). Each test reads the editor's state at its caret, which the right press has put at the pointer or kept in the selection it landed in (AK2, `focusPressed`); a press on a cell of a drawn table puts the caret in that cell (`pressedPosition`), since the drawing is one widget. "Follow reference" is shown on `reqseq:` references only: the app follows no other link (assumption, spec question #1176).

"Cut", "Copy" and "Paste" are actions of the command prompt too (`text-actions.ts`, `editor/clipboard.ts`), with the system's keys as their hint (`systemKey`: the window binds nothing to them, the field takes the key). They act on the field with the cursor, the text or a Markdown box, as the other text actions do. Cut and Copy ask the browser for its own cut or copy (`document.execCommand`) in the focused editor, within the click's or the Enter's activation, so CodeMirror gets the clipboard event of the key. Paste gives the editor the focus and asks main (`pasteText`, `reqseq:edit`), which pastes as the Edit menu does, after a left click or a bare Enter only (chosen in the menu by key, it takes Enter, not Space): the editor gets the paste event of Ctrl/Cmd+V, an image is copied as in SR-190 (`paste.ts`). The renderer never reads the clipboard.

## field, field-property, field-status, field-short-id

SR-196, marked on the fields (`FieldBox` with `menu`), not on the text, which is `text`. "Copy field" is first everywhere (AK1). `field`: the title and each group of relations. `field-property`: each property box, with "Add property" and "Clear property", and "List elements with this value" on a box with a value that lists elements (AK2): the element buffer marks such a box `data-listable` from the `element.facets` it asks for anyway (SR-132), so long free text never offers it (`field-menu.ts`). `field-status` has "Set status" (the catalog command, refs the shown element as in the prompt, AK3) and `field-short-id` "Show element ID and version" (AK4).

The element buffer shows no short ID and no status: the modeline does, as the ID field of SR-128 and the status after the type. So these two are the places (assumption, spec question #1179): `placeAt` takes them outside the areas, and nothing else of the modeline. `ModelineBar` draws them from `elementHead` (`modeline.ts`), the same structure the first part's text is joined from. They take the focus of a right press (`tabindex="-1"`): `cursorField` takes a field of the modeline with the focus as the field, and the element buffer keeps it as its last field (`modelineField`), so "Copy field" copies the ID or the status (which `copyable` has as a field) from the menu and from the prompt alike. When such a menu closes, the focus goes back to where it was before the press, else to the buffer of the active area, unless the entry moved it (a prompt). A right press on a field that takes no focus itself (a group of relations) focuses its first control, so the cursor is in the field pressed (`focusPressed`). Each entry then acts as from the command prompt with the cursor in that field.

## element-entry

SR-197 (`entry-menu.ts`), marked on a row of a list or a search, a row of the overview or the neighbourhood, an entry of a package page, a node of the graph and the head of a row of the matrix; a connected element in a cell of the matrix is `matrix-target`, which has the same entries first and what SR-199 adds after them (`ENTRY_MENU`). Everywhere in this order (AK1): "Show element", "Show graph", "Show neighbourhood", "Show affected elements", "Create relation", "Set status".

They act on the element of the entry, which the right-click selected (AK5 of SR-194): the context names it as `entry`. While the menu of an entry is open, it is the marked element (`menuContext`); in the command prompt, it is the marked one only where the buffer has no element of its own (a list, a search, the overview, the matrix), so there the prompt offers the same entries for the selected row (`promptEntry`). On an element, a package page, a neighbourhood or a graph the prompt's commands keep acting on the shown element, and the menu of an entry there acts on the entry. The first three are actions on `entry` (`ENTRY_ACTIONS`, last in `ACTIONS`, so the catalog command "Show graph" keeps the key of the action on the shown element): "Show element" opens it as Enter on the selected entry does, in the active area, which the right press made the area of the entry (AK2); "Show graph" and "Show neighbourhood" show its buffers, or switch to them when open. The other three are the catalog commands, whose element argument offers `entry` first (`firstOffered` in `catalog-commands.ts`); "Create relation" and "Set status" are not shown while the workspace is read-only.

In `App.tsx` the context is built once per render with the prompt's `entry`, and the context the commands read (`latest`) is `menuContext` of it, so the open menu's entries and the one clicked act on the entry. "All commands…" opens the prompt from the context without the menu's entry, so it lists what Ctrl/Cmd+Shift+P lists on that buffer, each name once (SR-194 AK3). The links of the relations in an element buffer are part of their field (`field`, SR-196) and no entry (assumption, spec question #1181).

## list

SR-198 (`list-menu.ts`), marked on the column of a list or a search (`ListView`: its heading, the line under it, the headings of its groups, the head of the folded section) and on the elements of a package page (`PackageMembers`: the whole section of the elements, with its heading), outside their rows, which are `element-entry`. By key (the Menu key, Shift+F10) with no row selected, the focused list buffer opens the menu of its column (`keyboardHit` takes the mark of a focused buffer's own content, `ownPlace`), while the mouse on the empty sheet around the column keeps the menu of `buffer`. In this order (AK1): "Filter list by type", "Filter list by status", "Filter list by text search", "Sort list", "Group list", or "Ungroup list" on a grouped list, and "Clear all list filters" on a filtered one. They are the list actions (`list-actions.ts`) and act on the shown list as from the command prompt; each is shown where the prompt offers it, so a search has no "Sort list" (SR-124 AK4) and a package page no "Group list". The prompt offers "Group list" on a grouped list too (to group by another value); the menu leaves it out there by the mark `data-grouped` the list sets on its column. "Clear all list filters" is offered on every filtered list, also with one step, beside "Clear list filter". The empty sheet beside and below the column is no part of the list and keeps the menu of `buffer` (SR-194 AK6; assumption, spec question #1183). The matrix has the places of SR-199 (below).

## graph, metamodel-graph

SR-199, marked on the sheet of the graph (`GraphView`, `MetamodelView`); a node of an element's graph is `element-entry`, and an edge or a type box of the metamodel gets the sheet's menu (assumption). `graph`: "Graph depth", "Also show relation kind" and "Show only relation kind" (AK1), the actions of the command prompt on the shown graph; "Also show relation kind" only where the prompt offers it (not while every kind and the evidence are shown). `metamodel-graph`: "Show metamodel as text" (AK2). The export as SVG and PNG that both AKs name is SR-151, which is not built yet: its entries follow it.

## matrix-cell, matrix-target

SR-199 (`matrix-menu.ts`). The matrix reports where its cursor or right-click stands with its marked element (`BufferData.spot`, `MatrixSpot`): the row, the kind and direction of the column, and on a connected element its other end. While the menu of a cell or a connected element is open, `menuContext` gives the catalog command its arguments (`ActionContext.given`, `matrixGiven`), and its entry starts the command with them given (`startCommand`), as if the prompt had asked them; Backspace asks a given one again. The prompt opened by keys gives none.

- `matrix-cell`, a cell outside its connected elements: "Create relation" (`relation.add`, AK3), with the row's element as the source of an outgoing column ("Derives from") or as the target of an incoming one ("Derived by"), and the column's kind, so the prompt asks only the other element. An element given so is not offered first again (the row as the source of its own incoming relation).
- `matrix-target`, a connected element: the entries of an element (SR-197), then "Remove relation" (`relation.remove`, AK4) with every argument given, so it runs at once: an outgoing relation from the row's file, an incoming one from the file of the other end, in the repository of the relation's target.

A column of a property of kind relation has no relation kind: its cells (`data-property-column`) offer neither entry (assumption).

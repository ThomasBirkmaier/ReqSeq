# Buffers and views

Part of the [`@reqseq/app` README](../README.md).

- **Start (SR-118):** the first buffer of a workspace is the overview, not the list of all elements. It has one line per element type with the number of its elements (`element.facets`, `types`: "System Requirement 117"), the types of the metamodel first, below them the perspectives (SR-118 AK6–AK8): at most ten from `perspective.list`, by name ignoring case (`shownPerspectives`), under a muted "Perspectives" (nothing of it without a perspective; a faulty file, which has no name to show, is left out), each with the `total` of `element.list` with the perspective in the window's view (the folded statuses count too); and below them the elements opened last, at most five, newest first, under a muted "Recent" (nothing of it before an element was opened). The type lines and the names of the perspectives show together; the counts follow, one `element.list` at a time (`countPerspective`: one row, `sort: []`, as the order does not change `total`), only while the overview is shown in the current revision (shown again, it asks only for those not counted yet), and each only once the window is idle and no other call to the core is pending (`call-turn.ts`, which counts the pending `invoke` calls of the bridge), so they do not delay the overview and a call of the user waits at most for the one count in flight. A perspective that `element.list` refuses shows "faulty file" (`file.faulty`) or "cannot be listed" instead of its count, core's message on hover. Enter or a click on a perspective line opens it through `openPerspective`, as "Open perspective" does (SR-118 AK7, SR-214 AK2): it counts as its use for the order of that prompt, and one that cannot be listed says core's message in the minibuffer. Enter or a click on a type line opens the list of the elements of exactly that type (`subtypes: false`, so the list is as long as the count says; it filters further like any list). The full list opens only on request: "List all elements" in the command prompt. Ctrl/Cmd+P works at once, with the overview as the only buffer. "Show overview" in the command prompt (offered when the overview is not shown) and closing the last buffer, also "Close all buffers", show it again; the lone overview cannot be closed. The counts are asked once per change of the workspace, not at every return to the overview. The recent elements are display state of the app, like the open buffers: only the UUID and the repository are kept, per workspace (its name and repositories), in the local storage of the app (Chromium, in the user data folder of the operating system), never in the files of the workspace (SR-118 AK5) and not through a catalog command (SR-080 AK1: "außer reiner Darstellung der App"). Each is read with `element.get` when the overview is shown; one that cannot be read is left out. The main process writes the storage to disk when the app quits.
- **Buffers:** the overview, the list of elements (`element.list`: filter, sort, derivation tree, pages of 200), a search result (`element.search`, pages of 50; each hit with its title marked where core says, `titleMarks`, and under it, for a hit in the text or a property, one line "text: …" or "<property name>: …" with core's snippet and its marked words heavier, across the row; when the line would hide its first marked word, the words before it are left out from a word start with "…" (`trimLead`; display only, the whole line is the tooltip, the option is named by ID, title and status and described by the snippet); none for a hit in the title or an ID only, SR-174) and one element (`element.get`: title, the text in the Markdown editor, the properties that are set as boxes below the text and the relations by kind, with a mark and the date of the stored version for outdated ones; the text and the text properties are edited in place, see below), its neighbourhood and its graph, and the metamodel of the workspace. Opening a buffer again shows the one that is open. A **result** buffer shows the output of a catalog command that no other buffer shows (SR-073 AK2, run from the command prompt with ThomasBirkmaier/ReqSeq-archive#85), laid out by its shape alone (`result.ts`): an element is a row that Enter or a click opens, with its status at the right edge as a list row has it when the output gives one (#276; the rows of "Show trace chain" too), also a UUID that the output names in `names` (ThomasBirkmaier/ReqSeq-archive#588, which itself is not shown; under a key the row keeps it: "variant: VAR-1"), a problem or hint is one line with its element (Enter opens it), a record of exactly two named UUIDs is one pair line, everything else is a quiet indented outline in greys, at most 2,000 lines; a top-level `total`, `view` and `incomplete` describe the answer and go to the modeline instead of the lines ("5 in all", "view: Coast" with the variant's title or "Core", "incomplete" only when true; #276). When the workspace changed, it asks the command again with the same input. It knows no command (ADR-0002), with one exception of layout: the output of `trace.chain` ("Show trace chain") has its `evidence` under the element rows it belongs to, not as a list of its own (SR-033, `chain-lines.ts`): under a requirement each test case "test case <class name> › <name>", " · not executed" for one with no execution (AK3), with one line per execution below it, newest first, "<date> · <result> · <item> · <Beleg>" (AK1), and each record without test case "record <date> · <method> · <result> · <item> · <Beleg>", a record of a variant with "variant <UUID>" at the end; the Beleg is core's `evidenceSource`, printed as text and never opened (#821). The evidence of an element goes under its row as a child, also when a cycle makes it a parent too. The validation records of the root (`validationRecords`, #646) go under the root row, each "validation <date> · <result> · <item> · <Beleg> · version <version>".
- **Quiet column (SR-148, D-062):** the list, a search result and the overview stand like the elements of a package page: in the centred column of an open element (72ch, `.column`), a buffer narrower than it gives them its full width without a sideways scroll; the matrix and the graph keep the full width. Above the rows of a list or a search result a heading says what it shows and how many, as the package page does, without a description: "All elements 14", the name of the type from the metamodel for a type line of the overview or a type value of SR-132 ("System Requirement 180", `FilterStep.heading`; the buffer's name stays "type: system-requirement"), else the labels of the steps ("type: need · status: draft"), or "Search: <text>" with the labels of its steps. The count says "incomplete" and the sort as the package page's heading does. Under the heading of a list stands the line of coverage and verification degree of its elements, as under the title of a package (`SummaryLine`, `evidence.coverage` and `evidence.degree` with the list's selection; asked once the first page stands, hidden when the list counts no requirement, kept while a new sort reads the rows again); a click or Enter on it opens the coverage of the list in a result buffer. A search result has no such line.
- **Verification in the rows (SR-137):** each row of a list, a package page or a search result shows right of its status what the element's node in the graph shows (SR-136, `NodeVerification`): a requirement's verification status (failed and outdated in the accent) and the progress ring of a requirement ("2 of 3") or need ("60 %"), nothing for an element without them. The rows come first: each page is asked again with `withVerification` once it stands (a list with `fields: ["identifier"]`), and the entries go into place by position. The ring's text is part of the row's name; its drawing is hidden. The view is the list's, so a ring equals the graph's when the graph is opened in that view. The validation status is not shown.
- **List query (#993, `list-query.ts`, `list-actions.ts`):** what a list asks `element.list` is one value, its query: the filter steps, the sort and the grouping. The list buffer has it, a package page has it for its elements (`memberQuery`: steps and sort), and a search result for its hits (`searchQueryOf`: steps and grouping, `withSearchQuery`; SR-124 AK4, SR-149 AK6). Every list action (filter, clear, sort, group, ungroup) acts on the shown list or package page and changes only the parts it sets (`withQuery`, `withMemberQuery`), so the other parts stay without each action carrying them. Each view says which parts it shows: a list all, the matrix and a package page the steps and the sort, a search the steps and the grouping (no sort: its hits keep the order of the search, question #1076). A search asks `element.search` with the steps as `selection` and `group`; the filters offer the values of its hits (`element.facets` over the steps and the search's own `text` condition; for a search in chosen fields over the steps with `search` and those fields, since the `text` condition searches every field, SR-216), and its heading and name add the step labels ("Search: wind · status: draft"). An action is offered only where its part is shown, and a list that moves into a view drops the parts it does not show; when that changes the rows, it starts from the first row. One rule says what a restart keeps (`keptQuery`: steps and sort). A new part of a query goes into `list-query.ts`, and the views and the restart rule decide on it there. "Filter by" and "Group by" offer the same properties (`choosableProperties`), each under the display name the metamodel gives it, as Type, Status and Package read; a choice value reads by its display name too, while the step and the grouping keep the key.
- **Grouped list (SR-149, `list-groups.ts`):** "Group list" (command prompt, no key; also on a search result, not in the matrix) asks "Group by" with Type, Status, Package (only when a property has the meaning `packages`) and each property of the listed elements whose values can be chosen, by its display name (`element.facets` over the list's selection, the rule `group` of `element.list` accepts; the property with the meaning `packages` is left out, Package groups by it). The list then asks `element.list` with `group` (a search `element.search` with `group`, its hits in the order of the search inside each group) and shows each group under a small muted heading with its name and count, styled like the groups of a package page, below the coverage line in `.column`: the display name of a type, status or choice, a package or target as "<ID> <title>", "(no value)" for the last group, which also counts the elements whose targets are not available. An element in several groups is a row in each; the rows are numbered and keyed by position, the pages go over the rows (`rows`), and a group of a later page shows once its rows are there. Choosing another grouping or "Ungroup list" shows the same list again from the first row with the same steps and sort (AK3); filtering and sorting keep the grouping. The matrix shows no groups: "Show traceability matrix" on a grouped list drops the grouping and starts from the first row. The grouping is display state on the list or search buffer (`ListBuffer.group`, `SearchBuffer.group`), named in the buffer's name ("· grouped by topic"); it is not kept after a restart and writes no file (AK5).
- **Perspective buffer (SR-214 AK1–AK4, SR-213 AK4, AK6–AK8, `perspective-actions.ts`, `perspective-recent.ts`):** Ctrl/Cmd+K V or "Open perspective" (command prompt) asks "Perspective" with the perspectives of `perspective.list`: the ones opened last first (`perspective-recent.ts`: names in the app's local storage per workspace, at most 50, never in the workspace; every opening by the user is recorded through `openPerspective`, a restore is not), then by name ignoring case; the prompt passes no `use` (SR-121 AK2). Faulty files follow as rows that cannot be chosen, with file and reason, and "incomplete: a repository is missing" when a repository with perspectives is missing; without any of these the minibuffer says "The workspace has no perspectives.". Enter asks `perspective.list` and `element.list` with `perspective` (one row) in the view of the window: an error, such as a missing saved filter (SR-213 AK6), is said and nothing opens; `perspective.group-unavailable` (AK7) is said and the buffer opens without the grouping. The buffer is a list buffer keyed `perspective:<name>` (folded with core's `fold`, `@reqseq/core/fold`) beside the plain list, which keeps its key: its first step is the perspective's selection, headed by its name, which "Clear list filter" and "Clear all list filters" never take back; its sort and grouping are as saved. It keeps what was saved when it opened (`PerspectiveOrigin.saved`) and asks `element.list` with that, not with the name, so a change of the file outside the app shows only when it is opened again; the app adds no sort of its own (`listSort`), so the order is that of `element.list` with the perspective (a stored sort, else that of its saved filter, else the workspace order). In the matrix it keeps its grouping without asking for it. Opening it again replaces the buffer with the perspective as saved, in list mode, with no row selected. "Save list as perspective" (SR-214 AK5, `SAVE_PERSPECTIVE`, command prompt only, not in the context menu) is offered on a list buffer that lists elements, not in the matrix, not in a read-only workspace (`perspective.save` refuses there); the hits of a search and a package page are no list buffer. It asks "Perspective name" with the perspective names of `perspective.list` as hits (when that call fails, its message is said and nothing is asked) (`preview`: Enter takes the typed name unless a hit is chosen), starting from the name of the buffer's perspective. It writes only through `perspective.save` (`perspectiveInput`): the conditions of the steps as `where` (`perspectiveWhere`: the perspective's own selection as stored when no step adds a condition, so saving it again under its name changes no line of it, SR-213 AK3; else under one `all`, none as `{ all: [] }`, a text step as its `text` condition, the perspective's stored `all` giving its parts first and a stored condition of another kind one part: the marks the condition of "Save perspective" takes from the shown list, SR-215 AK5), the saved filter of a step as `filter` by name, `group`, and the sort the list is shown in (`listSort`: the chosen one; none when none is chosen on a list with a saved filter or on a perspective buffer saved without a sort, so the order shown stays; else `DEFAULT_SORT`, so `element.list` with the perspective gives the app's order, SR-213 AK4); no `description`, which core keeps. It then reads `perspective.list` and replaces the list with the perspective's buffer as saved, at the same row (`open` with `replacing`): a plain list, or the buffer of another perspective saved under a new name, becomes the buffer of the saved one, and an open buffer of that perspective is replaced. The modeline says "modified" right after the name (SR-214 AK6, `perspectiveModified`) while the buffer has a step after the perspective's selection, or a sort or grouping other than saved; the matrix mode does not count (the buffer keeps its grouping there). Saving under its name or opening it again gives a buffer as saved, without it.
- **Folded statuses (SR-201, `fold-statuses.ts`, `fold-actions.ts`):** in a list, a search result and the elements of a package page, but not in a tree (sort Hierarchy, SR-075) or the matrix, the elements in folded statuses stand after the others under one row "▸ Folded statuses (<count>)", collapsed whenever the list opens. The list asks core twice: its selection with `not` the fold condition, and with only it (both in pages; the folded ones, grouped like the list, once every row in place is loaded). The section row is an option of the listbox: a click, Enter or Tab toggles it, Right opens and Left closes it; the heading and the modeline count every element. Without a choice every status the metamodel flags `invalid` folds; "Fold status in lists" (command prompt, no key) offers every status of the metamodel, the folded ones marked "folded", and choosing one folds it or puts its elements back in place in every list; "Fold invalid statuses in lists" (only after a choice) drops the choice. The choice is display state of the app for this user: one key in the app's local storage (`reqseq.fold-statuses.v1`), stored as a change of the default by status keys (those that fold besides the invalid ones, and invalid ones that stay in place), so another workspace folds its own invalid statuses; what folds is read from the metamodel of the open workspace, and nothing folds until it is read, the same for every workspace, kept after a restart, never in a file of the workspace and not a catalog command (AK4, SR-080 AK1).
- **Split window (SR-115 AK3):** "Split window" in the command prompt (no key) shows the shown buffer on the left, active, and beside it the preview of the element marked in it (SR-150 AK6), else the buffer used before, the overview beside a single buffer; "Other window" (Alt+O, SR-150 AK7) makes the other area active, as a click or a focus in it does, and "Unsplit window" leaves the active area alone. The modeline names the buffer of the active area, and the commands, Ctrl/Cmd+P and Alt+N/P act on it; choosing the buffer of the other area makes that area active, so a buffer is never in both. For an element and its graph side by side: the element, Ctrl/Cmd+Shift+G, then "Split window". An element left for the other area saves its input at once. The inactive area is a shade lighter: its text takes the muted grey, still WCAG AA (SR-150 AK8). The split is not kept after a restart.
- **Open to the right, Open to the left (SR-150):** both commands (no key) open the marked element, the selected row of a list, search, neighbourhood or of the elements opened last, or the selected node of a graph, in the area on that side. Without a split the window splits and the shown buffer stays active on the other side; in a split the inactive side shows it, while the active side opens it as Enter does. What these commands and Split window put into the inactive area is a preview (`Layout.preview` in `window-layout.ts`): it follows what the reader marks next in the active one; opening, reading again or switching areas moves nothing (`markToken`, `follow-mark.ts`). The next element, marked or opened with these commands, takes the place of one the preview brought in; one the reader had open, or one with unsaved input, stays open behind. Entering the preview (Alt+O, a click), opening another buffer there, the comparison of SR-044 and unsplitting end it: the area then stays as it is, so two elements can stand side by side. A relation at an element marks nothing yet (`markedElement` in `modeline.ts`).
- **Copy result (`result-copy.ts`):** the action "Copy result" (command prompt, no shortcut) puts the shown lines of the result buffer on the clipboard as one block (an output beyond 2,000 lines ends with its "more" line, a cut reason stays cut as shown), one line per shown line, indented by two spaces per level, a key with a colon, through the copy channel of SR-128; the modeline says "Copied result". It is offered on every result buffer with an output, whichever command opened it.
- **Hint list (SR-026 AK4, AK5, SR-122 AK4, `HintListView.tsx`, `hint-list.ts`):** the output of "List hints" (`hint.list`) shows in its result buffer as a list: the number of all hints that pass the filters (`total`, with "N listed" when the page holds fewer), then a heading per kind in the order of `kinds` with its label (the code, for a kind the app has no label for), its count of all its hints, its code after a label, and, while open, "N not listed" for its hints beyond the page; under it one row per hint of the page in the order of the output: the element's short ID with its identifier, its title (`elementTitle`), and a reason from the hint's fields (a count: relation kind or property, target type, count and limit; outdated evidence: "view: Core" or the variant by its short ID and identifier, as read for "Choose view"; a relation to a resolved target: its kind and that target; else the start of the message, after the relation kind and the target where there are any). The message is the row's title, shown on hover, and the modeline's last part for the marked row. Every heading is open when the list opens; a click on it, Tab on it (SR-193 AK1), or Enter or Space as on every fold head, folds and unfolds it; Right opens and Left closes it (SR-193 AK2), and Left on a row closes its group. Up and Down, Ctrl+N and Ctrl+P move the mark over headings and rows; Enter or a click on a row opens its element. Nothing is confirmed from the list. "Copy result" copies the output as other results.
- **Variant difference (SR-044 AK2):** "Show variant difference" (`variant.diff`, command prompt) opens a result buffer with the added, replaced and excluded requirements; a replaced one is a pair line "<core ID> <title> · replacement: <ID> <title>". Enter or a click on it shows the core requirement in the left area, active, and its replacement in the right one, each in a buffer of its own that is read-only (`readOnlyBuffer`: the editors take no input, the modeline says `read-only`, the name in the buffer list ends in "· read-only"), with their text and properties, the acceptance criteria among them. The command prompt does not offer a read-only element first to a write command (it can still be named), so a write never starts from that buffer by Enter alone. A pair line of any other output opens the same way; a row with more fields than the two is an outline. A UUID in two repositories (SR-088) opens in the repository that `names` gives first. The element's own buffer stays editable and apart, and a read-only buffer comes back read-only after a restart (SR-115 AK4).
- **Switch in motion (SR-212, `buffer-slide.ts`):** "Previous buffer" and "Next buffer" (Alt+P and Alt+N, the mouse buttons Back and Forward, ⌘[ and ⌘], a swipe macOS reports to the window (SR-163 AK4), a swipe of the wheel (SR-211, below), the commands) slide: the shown buffer leaves to the right and the new one comes from the left for Previous, the other way for Next, in 160 ms, eased like the card of the command line (`--card-ease`, SR-182). An area is a track of two layers (`BufferArea.tsx`), each over the whole area and moved by its own `translateX` in % of the area: `main` holds the live view, `side` (after it in the DOM, `contain: strict`, no pointer) what stands beside it. In the keydown, after the editor is left, the side gets a picture of the view that is left: a copy of its DOM, inert and hidden from assistive technology, without `data-buffer`, labels, roles, tab stops, editable text and popups, its ids and `url(#…)` references prefixed, its fields and scroll offsets as they were. React then unmounts the old view as before (saves on leaving, drafts and undo history are unchanged), and the new one is live at once with the focus, so input reaches only it (AK2). A buffer drawn in advance (below) slides at once; for any other the motion starts two frames after the new view reports that it is drawn: a view with its first `onData` with data, a list once its first rows show their verification and its line of coverage stands, a search result once its rows show their verification; a view whose read or layout fails reports it through `onDrawn`, so the motion starts over the error at once. A list keeps these per buffer (`list-drawn.ts`). After 1 s without a report the motion starts anyway (`DRAW_DEADLINE_MS`); a switch that reaches it is a bug. The motion then always runs. By the rationale of SR-212 the 200 ms bound only the motion: it starts once the new buffer is fully drawn, without a placeholder, and the time until then has no limit in SR-212. A key, a press of a mouse button (also Back and Forward), a swipe macOS reports to the window (`interrupt`, since it has no DOM event; also one that then switches nothing) or any other change of the active area's buffer or side ends it at once in its end state; a click during the motion lands where the live view stands at the press. A second switch before the first one moved slides from the picture the reader still sees. In a split window only the active area moves; a switch to the buffer of the other area moves nothing and makes that area active (AK1). Every other way to show a buffer (Ctrl+P, opening an element or a reference, closing, Follow agent, Alt+O, the preview, start) shows it at once (AK3), and with "reduce motion" in the system no picture is taken and nothing moves (AK4). `.area` clips (`overflow: clip`), so no focus or scroll into view can scroll it sideways while a layer stands beside it.
- **Swipe of the wheel (SR-211, `buffer-swipe.ts`, `use-wheel-swipe.ts`, `swipe-target.ts`):** a horizontal two-finger swipe on the trackpad or the horizontal mouse wheel runs "Previous buffer" (`deltaX` < 0, content pushed right) or "Next buffer" through `mouseButtonAction`, as the mouse buttons do; the buffer does not follow the fingers yet (#1611). One non-passive `wheel` listener on the sheet feeds `SwipeGesture`, pure state with the window's timers looked up at each call. Its numbers come from a measurement of a macOS trackpad (#1612): a *gesture* ends after a pause of 150 ms, a *segment* of it after 35 ms (the only longer gaps in a swipe are in its momentum, followed by at most 5 px); a segment its timer ended is joined again when its next event's `timeStamp` lies less than 35 ms after the last (a busy main thread), or, below the third, when it goes on its way with a step of at least 20 px (a wheel notch, an assumption). An event with Shift, Ctrl (a pinch), Meta or Alt is not read. The first event of a gesture, and the first with dX ≠ 0, ask the window whether the gesture is ignored: not cancelable, a button held, `bufferSwitchBlocked`, no workspace, no other buffer, the wheel event that closed a context menu (`closedBy` of `use-context-menu.ts`, whose capture listener closes it first), the pointer outside the active area, or under the pointer, up to the shown layer, content that scrolls sideways (`overflow-x` auto or scroll, wider than its box) and is not at its edge that way (`scrollsFirst`); an ignored gesture is never prevented. Until a segment has gone 8 px (`DECIDE_PX`) its events are prevented, as Chromium may send the rest of a scroll sequence without `cancelable`; then it is vertical when `|ΣdX| ≤ 1.5·|ΣdY|` (the measured diagonals reach 56 %) for the rest of the gesture, and the vertical distance held back is scrolled with `scrollBy` (a first event that decides scrolls itself), or it is the swipe: its events stay prevented, a running slide ends (SR-212 AK2) and `SwipeDraw.draw` draws the target. It switches when its distance in its way passes a third of the active area's width, at the end of the segment, or at once with reduced motion; the switch and `SwipeDraw.end` go into one commit (`flushSync`), so the drawn layer becomes the shown one without being drawn again. Afterwards the gesture is spent until its pause: every event is prevented and does nothing, a new segment decides only after 25 px, is released as vertical only by the ratio above, and becomes a new swipe only when it starts as a trackpad swipe starts (a first step under 20 px) and rises to twice that, to 12 px and past the last step of the swipe that switched; momentum after a pause only falls (3-9 px measured), so two quick swipes switch twice and the momentum of one never does. The swipe macOS reports to the window (SR-163 AK4) does not ask this gesture.
- **Drawn in advance (SR-212 AK5, `neighbours.ts`, `area-slot.ts`):** while a buffer is shown, the previous and the next buffer of the active area (SR-115 AK5, the walk's order) stand drawn hidden beside it, each in a layer of its own (`data-layer="neighbour"`: inert, `aria-hidden`, `visibility: hidden`, no pointer), when it is a neighbourhood or an element whose type is known and is not a package type, and not the buffer the other area of a split window shows. In a split window only the active area draws in advance, as only it switches with Previous and Next (SR-211 AK9; an assumption, #1637). Every other buffer (a list, a search result, the matrix, a package page, a graph, the metamodel, a result, the overview, a perspective, an element whose type is not known yet) is never read for it: it is drawn hidden only from its **record** (`area-record.ts`), the answers of reads (the commands of `RECORDED`, with `relation.options` the matrix asks per type of row; never a write or a failure) that its shown view got in the current generation of the workspace (`seen`) and view-bound call (the view of the window), kept per buffer key in the area (`AreaRecords`, at most `RECORD_MAX` answers; more is a miss). When the reader leaves such a buffer and it stays the previous or next buffer, its layer mounts again hidden as a fresh view, whose reads wait at the gate and take a turn in the queue like reads but are answered from the record and send nothing (`by: "record"`, `neighbours.ts`). A paged read (`element.list`, `element.search`, `trace.matrix`) is also answered from pages of the same input that cover the rows asked (`pageFrom`, only for a page with a `limit`: the parts with one entry per row concatenated, the matrix's `names` each once, the rest from the first page), so a list whose cursor stands past its first page, which a fresh view asks for in one page (`firstLimit`), is drawn too. A read the record cannot answer is a miss: nothing is sent, the layer is never reported ready and is dropped, and its record forgotten; so a buffer left before its reads answered (an answer after leaving is not recorded), or one whose input changed (another view, other folded statuses, SR-201), is not drawn in advance. The record also holds what the view shows besides its reads (`inputsOf` in `BufferArea.tsx`): the names of the types and relation kinds, the size of the area (a `ResizeObserver`; the graph and the metamodel lay out from it, and a split changes it), whether the core process stopped, and for the overview what the window read for it (`useOverview`, which reads only while an area shows the overview) with the elements opened last; any change of these drops it at the next commit, as any change of the workspace does, with no allowance for a save of leaving, as such a view cannot read once more. A buffer that left the side of the shown buffer (three buffers walked) loses its record (`AreaRecords.prune`) and is drawn in advance again only after it was shown. Being a fresh mount, such a view shows what a fresh view at the switch shows: the first-load position and per-mount state, the members of a package page (drawn for it: `useWhole`, `SlotState.whole`; their focus taken at the reveal when the page comes back), the outside-change marks of SR-116 set at the reveal (`useReveal` in `ListView`, `MatrixView` and `OverviewView`), and the layout of a graph or metamodel kept per output object (`layoutGraph`, `MetamodelView`), so dagre does not run again. A hidden list, matrix, graph or metamodel applies the state its answers give as a transition (`useHiddenUpdate`), which React renders in slices behind any input, so drawing a long list, matrix or graph never holds up a key pressed in the shown buffer (SR-082 AK3); a list counts as drawn once that state is committed. A switch to a buffer drawn from its record counts as drawn in advance only while leaving the shown buffer changes nothing (`AreaViews.clean`: no draft of it to save and no save of the window in flight, `WritesInFlight`, from sending until its `written`); otherwise the switch shows a fresh mount that reads, and the motion waits for its draw (`SlideController.prepare` with `clean`). The type of an element buffer comes from the reads the app makes anyway (`elementBufferOf` of a row, a hit or a read element, the names read at a restart, and each answer of the shown or hidden view, `typed`); it is not stored. A hidden view is always a fresh mount: the element just left unmounts (its save of leaving, SR-105 AK1, runs as before) and mounts again hidden, its first read after that save (`keep.ready()`); So a switch to it shows what a fresh view at the switch shows: its content, the first-load position, and the highlight of SR-116, which a hidden view sets only once shown (`useReveal`: the title of an element changed outside just now, the rows of a neighbourhood). A hidden view is never read again in the background: another view of the window (a new view-bound call, kept with the generation it read in, also for reads waiting at the gate) or a change of the workspace since it was mounted or last read (a change from outside or a save, also one that comes while its reads still wait at the gate) drops it from the buffers drawn in advance (`AreaViews.drop`, `useDropped` in `App.tsx`; a read it would make is not sent), so it counts as not drawn, and a switch to it reads and draws it. The save of leaving an element (SR-105 AK1) belongs to the switch it comes with: its change (the `written` answer to that write, counted as `switchSaves`) does not drop a hidden view that read before it, which reads once more instead; a view is dropped when more changes came than such saves. A write counts as one only once its answer came, which the core host posts just before its `written` on the window's channel, so another window's write takes no count (`countingWrites`); another workspace starts with none. An autosave that is still running when the reader switches is no save of leaving: its change drops the hidden views mounted or read before it, the element just left among them when it mounted first, until the next switch. The neighbours of the shown buffer are drawn in advance again after the next switch. **Swipe (SR-211 AK3, `swipe-draw.ts`):** `SwipeDraw.draw(key)`, which the swipe of the wheel calls once a segment is the swipe (below), unless the other area shows the target or motion is reduced, draws the buffer it would switch to beside the shown one (`by: "swipe"`), of any kind, also one dropped since the last switch (`undrop`), with reads that go as a shown buffer's (no gate, no queue) and into its record; it resolves `true` once the layer is ready (at once when it is drawn in advance already), `false` when the swipe ends first (`end`), another draw takes its place, the buffer is closed (`open`), or it is no longer drawn beside the shown one (`beside`; `withSwipe` never draws the other area's buffer). After `end` a layer that stays beside the shown buffer is drawn by the rules above, an other kind from the record its reads made. A hidden view takes no focus and gives no controls (not active), has no `data-buffer`, holds its actions (a rename, an element found gone) and its last message until it is shown, starts no save (autosave is held, and one that was never shown saves nothing when it goes), and reads neither the elements of a package page nor `element.facets` (asked once shown). What it loaded is kept under its key, so the modeline has it at once when it is shown; the modeline, the preview of the other area, the recent elements of the overview, the walk's order and the stored session read only the shown buffers. Its reads wait (`ReadGate`) until the buffer the active area shows reported that it is drawn (once since it was shown, or after `DRAW_DEADLINE_MS`) and while no slide runs and no prompt is open (the reader may be choosing the next buffer there), so none starts while the reader waits for a buffer (SR-082 AK3); a read already sent when the reader opens another buffer still runs, and the open waits for it (measured in `test/perf/neighbours.spec.ts`). The reads drawn in advance go one at a time, across all hidden layers (`ReadGate.turn`): the next only once the one before answered, and none is sent while a request of a shown buffer is in flight (`ReadGate.request`), which never waits; so at most one read drawn in advance is ahead of an open the reader asks for. A read that waited at the gate for a layer that went meanwhile is not sent. A hidden view is ready when it reported its drawing and none of its reads is pending, checked after the commit of each answer; the slide controller keeps it with the workspace's generation (`revision` plus the changes from outside), and a switch to a buffer ready in the current generation starts to slide in the commit that shows it. Otherwise (just after a switch or after the start, before its read answered) the motion waits for the draw as before. The shown layer stands first in the area, so a lookup in the document finds the shown view before a hidden one.
- **Buffers again after a restart (SR-115 AK4, `buffer-session.ts`):** the buffers open when the app was closed, or when the workspace was left for another, come back when the workspace opens again: the overview shows first (SR-118 AK1), the others are behind it, in their order of use (Ctrl/Cmd+P), which Alt+P and Alt+N walk too. A result comes back only for an implemented read command, and runs again when it is shown. A perspective buffer comes back as the perspective is saved, with its grouping, after one `perspective.list` and the check of opening; without the grouping when it can no longer be chosen, and the warning is said when the buffer is first shown. One whose saved filter is missing or faulty comes back and shows core's error, as a reload does; one that only a faulty file holds comes back with nothing saved and shows `file.faulty`: it lists nothing, offers no list action and gives no selection to a command (`listing`) until the perspective is opened again; one no file holds is left out. After "Close all buffers" only the overview comes back.

# Buffers and views

Part of the [`@reqseq/app` README](../README.md).

- **Without a workspace (SR-225 AK1–AK3, `start-commands.ts`, `StartView.tsx`):** while no workspace is open (at the start, in a folder without one, after an open failed) and no other buffer is shown, the sheet shows the start buffer: "Open workspace…" with the key of File > Open Workspace… as a side text, "Create workspace" and "Connect AI agent", one below the other in the middle, without a frame and subtle: the lines and the key in the pale `--faint`, the hovered or selected line in `--muted` on `--select` (how AK1's „heller als die Nebentexte“ is read); the modeline says "No workspace is open." A click, or Up/Down and Enter (Enter with no line selected runs the first), runs a line: "Open workspace…" has main show the menu's folder dialog (`openFolderDialog`, [bridge](bridge.md)), and the command line says so when main refused it; "Create workspace" (AK4–AK6, `create-workspace.ts`) has main give the folder (`chooseCreateFolder`, [bridge](bridge.md)): the folder without a workspace the window has open, else one chosen in the system folder dialog, which main opens itself, never a workspace above it, so a folder inside a workspace becomes a workspace of its own (as SR-014 AK1 and the CLI create one in any folder that is not one yet). The command prompt then asks only "Create workspace · name:", pre-filled with the folder's name, and Enter runs `workspace.init` with the path `.` and that name; the window opens the new workspace as after the command prompt's "Create workspace" (SR-226 AK2). An empty name stays in the step with "A name is needed", a refusal of core stays there with its message, and Escape or a cancelled dialog creates nothing; a chosen folder that is a workspace opens, and the command line says "Opened the existing workspace <name>". Main's answer, the open and the folder's status can come in any order, so the run waits for all three (`createRunner`). The command prompt's own "Create workspace" still asks path and name (SR-143); "Connect AI agent" runs the action as the modeline does (AK7). It is a buffer in the sense of D-062, but the window keeps it outside its list of buffers: it has no history, no session entry and no modeline parts, and it is gone as soon as a workspace opens, which shows its overview (AK3).
- **Start (SR-118):** the first buffer of a workspace is the overview, not the list of all elements. It has one line per element type with the number of its elements (`element.facets`, `types`: "System Requirement 117"), the types of the metamodel first, below them the perspectives (SR-118 AK6–AK8): at most ten from `perspective.list`, by name ignoring case (`shownPerspectives`), under a muted "Perspectives" (nothing of it without a perspective; a faulty file, which has no name to show, is left out), each with the `total` of `element.list` with the perspective in the window's view (the folded statuses count too); and below them the elements opened last, at most five, newest first, under a muted "Recent" (nothing of it before an element was opened). The type lines and the names of the perspectives show together; the counts follow, one `element.list` at a time (`countPerspective`: one row, `sort: []`, as the order does not change `total`), only while the overview is shown in the current revision (shown again, it asks only for those not counted yet), and each only once the window is idle and no other call to the core is pending (`call-turn.ts`, which counts the pending `invoke` calls of the bridge), so they do not delay the overview and a call of the user waits at most for the one count in flight. A perspective that `element.list` refuses shows "faulty file" (`file.faulty`) or "cannot be listed" instead of its count, core's message on hover. Enter or a click on a perspective line opens it through `openPerspective`, as "Open perspective" does (SR-118 AK7, SR-214 AK2): it counts as its use for the order of that prompt, and one that cannot be listed says core's message in the minibuffer. Enter or a click on a type line opens the list of the elements of exactly that type (`subtypes: false`, so the list is as long as the count says; it filters further like any list). The full list opens only on request: "List all elements" in the command prompt. Ctrl/Cmd+P works at once, with the overview as the only buffer. "Show overview" in the command prompt (offered when the overview is not shown) and closing the last buffer, also "Close all buffers", show it again; the lone overview cannot be closed. The counts are asked once per change of the workspace, not at every return to the overview. The recent elements are display state of the app, like the open buffers: only the UUID and the repository are kept, per workspace (its name and repositories), in the local storage of the app (Chromium, in the user data folder of the operating system), never in the files of the workspace (SR-118 AK5) and not through a catalog command (SR-080 AK1: "außer reiner Darstellung der App"). Each is read with `element.get` when the overview is shown; one that cannot be read is left out. The main process writes the storage to disk when the app quits.
- **Buffers:** the overview, the list of elements (`element.list`: filter, sort, derivation tree, pages of 200), a search result (`element.search`, pages of 50; each hit with its title marked where core says, `titleMarks`, and under it, for a hit in the text or a property, one line "text: …" or "<property name>: …" with core's snippet and its marked words heavier, across the row; a snippet in an acceptance criterion names its number and criterion key, "Acceptance Criteria AK3 (rqjp): …", the key heavier when only it was found there (SR-222 AK3, `snippetOf` in `rows.ts`); when the line would hide its first marked word, the words before it are left out from a word start with "…" (`trimLead`; display only, the whole line is the tooltip, the option is named by ID, title and status and described by the snippet); none for a hit in the title or an ID only, SR-174) and one element (`element.get`: title, the text in the Markdown editor, the properties that are set as boxes below the text and the relations by kind, with a mark and the date of the stored version for outdated ones; the text and the text properties are edited in place, see below), its neighbourhood and its graph, and the metamodel of the workspace. Opening a buffer again shows the one that is open. A **result** buffer, the output page, shows the output of a catalog command that no other buffer shows (SR-073 AK2, run from the command prompt with ThomasBirkmaier/ReqSeq-archive#85), laid out by its shape alone (`result.ts`, `ResultView.tsx`). Its answer (`answer`, SR-224 AK1) is the page's heading, above the listbox of the lines; when the output is `incomplete`, the line under it says "Incomplete" (SR-006 AK2), since the answer already says why. The buffer (`role="group"`) takes the focus and the keys and names the selected line as its active descendant. Then come the problems of the output's top-level problem lists, a heading "Errors", "Warnings" and "Info" each, in this order (SR-223 AK1): each problem one line with its element (Enter opens it), else its file and line, and its message; several problems of one kind and severity are one group line instead, where the first of them stands, folded at first, with the title of their kind (SR-224 AK6, `@reqseq/core/problem-titles`; its code where the app knows no title) and their count at the right edge (SR-223 AK3): Tab on it (SR-193 AK1) or a click on its triangle opens and closes it, Right opens and Left closes it, also from one of its lines; open, each of its problems follows one level in, with its element, else its file and line, and its message; Enter or a click elsewhere on it opens the list of the elements of its problems (`outputList`: one filter step named by the title of the kind, the condition `{ property: "id", op: "in" }` on their UUIDs, so every copy of a UUID in any repository is listed, SR-088, where `selection.ids` would refuse it as `ref.ambiguous`; further filters add to it, and as a list from the output of a command it offers neither "Save list as perspective" nor "Save list as saved filter", SR-214 AK5, SR-219 AK8), and a group whose problems name no element opens and closes instead; the kind, which is technical, shows under the group line only with "Show details", not at its problems; which groups are open belongs to the buffer (`ResultBuffer.unfolded`), and a buffer opened anew shows them folded. A list of problems further down keeps its place, ordered by severity, each line starting with its severity, without groups. A record of a list that names a problem kind by a `code` the catalog marks technical but is no problem, such as a count of hints per kind (`hintKinds` of "Show changes since baseline"), stands under the title of that kind (`kindLines`): with one other value that shows as it is (not normal, not technical, no number of elements) it is one line, the title with the value at the right edge as a group line has its count, otherwise an outline under the title; the code follows only with "Show details" (#2073). Every value stands under the title its field has in the catalog (`outputFields` of the command's entry, SR-224 AK3), never under its field name; a key of a map is data and stays as it is; a value equal to the normal value the catalog names for its field (`x-normal`, such as `ok: true` or empty `problems`) is left out (SR-223 AK7); so is a value the catalog marks technical (`x-technical`, resolved as `technical` in `outputFields`: a UUID, path, check value, commit, kind of a problem or duration, SR-224 AK3; `with-element` only while the problem names an element), except a UUID that `names` names, which is its element's row; a flag reads "yes" or "no". A text of several lines, such as the agent guide (SR-229 AK1), stands whole under its title across the column, its line breaks kept, in the monospace font (`ResultLine.block`, `.line.block`, #2141); the lines above the rows of a list from an output do the same. **Show details** (Ctrl+K D, ⌘K D on macOS; action `show-details`, SR-223 AK2) shows these values at their lines, as details in the second grey with the value in the monospace font (`ResultLine.detail`, `.line.detail`), a problem with its kind under its message and its technical values on lines under it (a `null` value is left out), and the same command hides them again; the echo says "Details shown" or "Details hidden". The state is `ResultBuffer.details`: it holds for that buffer while it is open, also when the same command opens it again (`withKept` in `buffers.ts`), and a closed buffer forgets it; it comes back with the buffers after a restart (SR-115 AK4, `details` of the stored result in `buffer-session.ts`). The selected line stays selected across the toggle (`keptCursor` of `result-copy.ts`: the same line by what it shows; none when it is a detail that is hidden again); the hint list keeps its rows, so its cursor stays. The fields come from the catalog the window read (`AreaViews.outputFields`), so the page knows no command. Below the problems an element is a row that Enter or a click opens, with its status at the right edge as a list row has it when the output gives one (#276; the rows of "Show trace chain" too), also a UUID that the output names in `names` (ThomasBirkmaier/ReqSeq-archive#588, which itself is not shown; under a field the row keeps its title: "Variant: VAR-1"), a record of exactly two named UUIDs is one pair line, everything else is a quiet outline in greys whose titles are indented by level while the values of all levels stand in one column, each record of a list after a small gap, at most 2,000 lines; a top-level `total`, `view` and `incomplete` describe the answer and go to the modeline instead of the lines ("5 in all", "view: Coast" with the variant's title or "Core", "incomplete" only when true; #276). When the workspace changed, it asks the command again with the same input. It knows no command (ADR-0002), with one exception of layout: the output of `trace.chain` ("Show trace chain") has its `evidence` under the element rows it belongs to, not as a list of its own (SR-033, `chain-lines.ts`): under a requirement each test case "test case <class name> › <name>", " · not executed" for one with no execution (AK3), with its executions below it as runs, newest first (`runs.ts`, SR-223 AK4): the executions of one date are one run, one row "<date> · <result>" while their results agree, followed by the views where the test case has an execution in a variant ("Core", then each variant by the title `names` gives, else its UUID: "· Core, Linux, macOS"); when a result differs, each view of the run has its own row, and a view whose own results differ a row per execution; the item under test and the Beleg stand under each row only with "Show details", one line "<view> · <item> · <Beleg>" per execution (AK1, SR-223 AK2); a test case in the output of any other command (`evidence.list`) shows the same way. Each record without test case is "record <date> · <method> · <result> · <item> · <Beleg>", a record of a variant with "variant <title>" at the end (its UUID when `names` does not name it); the Beleg is core's `evidenceSource`, printed as text and never opened (#821). The evidence of an element goes under its row as a child, also when a cycle makes it a parent too. The validation records of the root (`validationRecords`, #646) go under the root row, each "validation <date> · <result> · <item> · <Beleg> · version <version>".
- **Quiet column (SR-148, D-062):** the list, a search result, the overview and the output page stand like the elements of a package page: in the centred column of an open element (72ch, `.column`), a buffer narrower than it gives them its full width without a sideways scroll; the matrix and the graph keep the full width. Above the rows of a list or a search result a heading says what it shows and how many, as the package page does, without a description: "All elements 14", the name of the type from the metamodel for a type line of the overview or a type value of SR-132 ("System Requirement 180", `FilterStep.heading`; the buffer's name stays "type: system-requirement"), else the labels of the steps ("type: need · status: draft"), or "Search: <text>" with the labels of its steps. The count says "incomplete" and the sort as the package page's heading does. Under the heading of a list stands the line of coverage and verification degree of its elements, as under the title of a package (`SummaryLine`, `evidence.coverage` and `evidence.degree` with the list's selection; asked once the first page stands, hidden when the list counts no requirement, kept while a new sort reads the rows again); a click or Enter on it opens the coverage of the list in a result buffer. A search result has no such line.
- **Verification in the rows (SR-137):** each row of a list, a package page or a search result shows right of its status what the element's node in the graph shows (SR-136, `NodeVerification`): a requirement's verification status (failed and outdated in the accent) and the progress ring of a requirement ("2 of 3") or need ("60 %"), nothing for an element without them. The rows come first: each page is asked again with `withVerification` once it stands (a list with `fields: ["identifier"]`), and the entries go into place by position. The ring's text is part of the row's name; its drawing is hidden. The view is the list's, so a ring equals the graph's when the graph is opened in that view. The validation status is not shown.
- **List query (#993, `list-query.ts`, `list-actions.ts`):** what a list asks `element.list` is one value, its query: the filter steps, the sort and the grouping. The list buffer has it, a package page has it for its elements (`memberQuery`: steps and sort), and a search result for its hits (`searchQueryOf`: steps and grouping, `withSearchQuery`; SR-124 AK4, SR-149 AK6). Every list action (filter, clear, sort, group, ungroup) acts on the shown list or package page and changes only the parts it sets (`withQuery`, `withMemberQuery`), so the other parts stay without each action carrying them. Each view says which parts it shows: a list all, the matrix and a package page the steps and the sort, a search the steps and the grouping (no sort: its hits keep the order of the search, question #1076). A search asks `element.search` with the steps as `selection` and `group`; the filters offer the values of its hits (`element.facets` over the steps and the search's own `text` condition; for a search in chosen fields over the steps with `search` and those fields, since the `text` condition searches every field, SR-216), and its heading and name add the step labels ("Search: wind · status: draft"). An action is offered only where its part is shown, and a list that moves into a view drops the parts it does not show; when that changes the rows, it starts from the first row. One rule says what a restart keeps (`keptQuery`: steps and sort). A new part of a query goes into `list-query.ts`, and the views and the restart rule decide on it there. "Filter by" and "Group by" offer the same properties (`choosableProperties`), each under the display name the metamodel gives it, as Type, Status and Package read; a choice value reads by its display name too, while the step and the grouping keep the key.
- **Grouped list (SR-149, `list-groups.ts`):** "Group list" (command prompt, no key; also on a search result, not in the matrix) asks "Group by" with Type, Status, Package (only when a property has the meaning `packages`) and each property of the listed elements whose values can be chosen, by its display name (`element.facets` over the list's selection, the rule `group` of `element.list` accepts; the property with the meaning `packages` is left out, Package groups by it). The list then asks `element.list` with `group` (a search `element.search` with `group`, its hits in the order of the search inside each group) and shows each group under a small muted heading with its name and count, styled like the groups of a package page, below the coverage line in `.column`: the display name of a type, status or choice, a package or target as "<ID> <title>", "(no value)" for the last group, which also counts the elements whose targets are not available. An element in several groups is a row in each; the rows are numbered and keyed by position, the pages go over the rows (`rows`), and a group of a later page shows once its rows are there. Choosing another grouping or "Ungroup list" shows the same list again from the first row with the same steps and sort (AK3); filtering and sorting keep the grouping. The matrix shows no groups: "Show traceability matrix" on a grouped list drops the grouping and starts from the first row. The grouping is display state on the list or search buffer (`ListBuffer.group`, `SearchBuffer.group`), named in the buffer's name ("· grouped by topic"); it is not kept after a restart and writes no file (AK5).
- **Perspective buffer (SR-214 AK1–AK4, SR-213 AK4, AK6–AK8, `perspective-actions.ts`, `perspective-recent.ts`):** Ctrl/Cmd+K V or "Open perspective" (command prompt) asks "Perspective" with the perspectives of `perspective.list`: the ones opened last first (`perspective-recent.ts`: names in the app's local storage per workspace, at most 50, never in the workspace; every opening by the user is recorded through `openPerspective`, a restore is not), then by name ignoring case; the prompt passes no `use` (SR-121 AK2). Faulty files follow as rows that cannot be chosen, with file and reason, and "incomplete: a repository is missing" when a repository with perspectives is missing; without any of these the minibuffer says "The workspace has no perspectives.". Enter asks `perspective.list` and `element.list` with `perspective` (one row) in the view of the window: an error, such as a missing saved filter (SR-213 AK6), is said and nothing opens; `perspective.group-unavailable` (AK7) is said and the buffer opens without the grouping. The buffer is a list buffer keyed `perspective:<name>` (folded with core's `fold`, `@reqseq/core/fold`) beside the plain list, which keeps its key: its first step is the perspective's selection, headed by its name, which "Clear list filter" and "Clear all list filters" never take back; its sort and grouping are as saved. It keeps what was saved when it opened (`PerspectiveOrigin.saved`) and asks `element.list` with that, not with the name, so a change of the file outside the app shows only when it is opened again; the app adds no sort of its own (`listSort`), so the order is that of `element.list` with the perspective (a stored sort, else that of its saved filter, else the workspace order). In the matrix it keeps its grouping without asking for it. Opening it again replaces the buffer with the perspective as saved, in list mode, with no row selected. "Save list as perspective" (SR-214 AK5, `SAVE_PERSPECTIVE`, command prompt only, not in the context menu) is offered on a list buffer that lists elements, not in the matrix, not in a read-only workspace (`perspective.save` refuses there); the hits of a search and a package page are no list buffer. It asks "Perspective name" with the perspective names of `perspective.list` as hits (when that call fails, its message is said and nothing is asked) (`preview`: Enter takes the typed name unless a hit is chosen), starting from the name of the buffer's perspective. It writes only through `perspective.save` (`perspectiveInput`): the conditions of the steps as `where` (`perspectiveWhere`: the perspective's own selection as stored when no step adds a condition, so saving it again under its name changes no line of it, SR-213 AK3; else under one `all`, none as `{ all: [] }`, a text step as its `text` condition, the perspective's stored `all` giving its parts first and a stored condition of another kind one part), the saved filter of a step as `filter` by name, `group`, and the sort the list is shown in (`listSort`: the chosen one; none when none is chosen on a list with a saved filter or on a perspective buffer saved without a sort, so the order shown stays; else `DEFAULT_SORT`, so `element.list` with the perspective gives the app's order, SR-213 AK4); no `description`, which core keeps. It then reads `perspective.list` and replaces the list with the perspective's buffer as saved, at the same row (`open` with `replacing`): a plain list, or the buffer of another perspective saved under a new name, becomes the buffer of the saved one, and an open buffer of that perspective is replaced. "Save list as saved filter" (SR-219 AK8, AK9, `SAVE_SAVED_FILTER`, command prompt only) is offered where "Save list as perspective" is, except on a list whose selection names a saved filter (a saved filter step, or a perspective with `filter`). It asks "Saved filter name" with the names of `filter.list` as hits, and writes only through `filter.save` (`savedFilterInput`): the conditions of the steps in their order under one `all` (`shownMarks`, also for a perspective's own selection), and `sort` only when the list has one of its own (`ListBuffer.sort`: chosen with "Sort list", or saved with its perspective), not the `DEFAULT_SORT` that `listSort` shows otherwise; no grouping, no view, no `description`. The list stays as it is. The modeline says "modified" right after the name (SR-214 AK6, `perspectiveModified`) while the buffer has a step after the perspective's selection, or a sort or grouping other than saved; the matrix mode does not count (the buffer keeps its grouping there). Saving under its name or opening it again gives a buffer as saved, without it.
- **Renamed and deleted perspectives and saved filters (SR-218 AK4–AK6, `saved-file-actions.ts`, `buffers.ts`):** after "Rename perspective" succeeds, the buffer of the perspective takes the new name where it stands among the buffers (`perspective-renamed`): its key, the label and heading of its first step and its name, so the modeline, the heading, Ctrl/Cmd+K V and the name "Save list as perspective" proposes follow; its other steps, sort, grouping, mode and row stay, and so does "modified". A buffer of another perspective under the new name closes; in a split window the renamed buffer keeps its area (`window-layout.ts`). The order of use of the perspectives keeps its place under the new name (`perspective-recent.ts` `renamedPerspective`). After "Rename saved filter" the filter steps of lists and searches and the selection of perspective buffers that name the filter take the new name (`filter-renamed`), which changes no "modified". After "Delete perspective" its buffer closes as "Close buffer" closes it, so it does not come back at a restart. The overview reads the perspectives again after the write, as after any change.
- **Folded statuses (SR-201, `fold-statuses.ts`, `fold-actions.ts`):** in a list, a search result and the elements of a package page, but not in a tree (sort Hierarchy, SR-075) or the matrix, the elements in folded statuses stand after the others under one row "▸ Folded statuses (<count>)", collapsed whenever the list opens. The list asks core twice: its selection with `not` the fold condition, and with only it (both in pages; the folded ones, grouped like the list, once every row in place is loaded). The section row is an option of the listbox: a click, Enter or Tab toggles it, Right opens and Left closes it; the heading and the modeline count every element. Without a choice every status the metamodel flags `invalid` folds; "Fold status in lists" (command prompt, no key) offers every status of the metamodel, the folded ones marked "folded", and choosing one folds it or puts its elements back in place in every list; "Fold invalid statuses in lists" (only after a choice) drops the choice. The choice is display state of the app for this user: one key in the app's local storage (`reqseq.fold-statuses.v1`), stored as a change of the default by status keys (those that fold besides the invalid ones, and invalid ones that stay in place), so another workspace folds its own invalid statuses; what folds is read from the metamodel of the open workspace, and nothing folds until it is read, the same for every workspace, kept after a restart, never in a file of the workspace and not a catalog command (AK4, SR-080 AK1).
- **Split window (SR-115 AK3):** "Split window" in the command prompt (no key) shows the shown buffer on the left, active, and beside it the preview of the element marked in it (SR-150 AK6), else the buffer used before, the overview beside a single buffer; "Other pane" (Alt+O, SR-150 AK7) makes the other area active, as a click or a focus in it does, and "Unsplit window" leaves the active area alone. The modeline names the buffer of the active area, and the commands, Ctrl/Cmd+P and Alt+N/P act on it; choosing the buffer of the other area makes that area active, so a buffer is never in both. For an element and its graph side by side: the element, Ctrl/Cmd+Shift+G, then "Split window". An element left for the other area saves its input at once. The inactive area is a shade lighter: its text takes the muted grey, still WCAG AA (SR-150 AK8). The split is not kept after a restart.
- **Open to the right, Open to the left (SR-150):** both commands (no key) open the marked element, the selected row of a list, search, neighbourhood or of the elements opened last, or the selected node of a graph, in the area on that side. Without a split the window splits and the shown buffer stays active on the other side; in a split the inactive side shows it, while the active side opens it as Enter does. What these commands and Split window put into the inactive area is a preview (`Layout.preview` in `window-layout.ts`): it follows what the reader marks next in the active one; opening, reading again or switching areas moves nothing (`markToken`, `follow-mark.ts`). The next element, marked or opened with these commands, takes the place of one the preview brought in; one the reader had open, or one with unsaved input, stays open behind. Entering the preview (Alt+O, a click), opening another buffer there, the comparison of SR-044 and unsplitting end it: the area then stays as it is, so two elements can stand side by side. A relation at an element marks nothing yet (`markedElement` in `modeline.ts`).
- **Copy as JSON (SR-223 AK9, `result-copy.ts`):** the action "Copy as JSON" (`copy-as-json`, command prompt, no shortcut) puts the whole output of the result buffer on the clipboard as the CLI gives it with `--json` (`JSON.stringify` with two spaces and a line break, `null` for none), whatever the page shows of it, through the copy channel of SR-128; the modeline says "Copied output as JSON" (SR-128 AK2). It is offered on every result buffer with an output, the hint list too, whichever command opened it; it replaced "Copy result", which copied the shown lines. The context menu of a buffer offers neither (SR-194 AK6).
- **Next steps of an output (SR-226 AK5, `next-steps.ts`):** the next steps core names in an output (`next`, `#/$defs/nextStep`, such as those of "Create workspace", SR-226 AK2) are the last lines of its output page, under a heading with the title of their field ("Next steps"), never among its other lines (`ResultLine.step`, `.line.step`). Each names its command as the command prompt does (`appCommandEntry`: the action that covers it, else the catalog title) with its key at the right edge where it has one ("Ctrl+K E"); its known inputs are not shown. Enter or a click runs the entry of the command prompt for it (`runStep` in `App.tsx`, as a choice in the context menu runs one) with the known inputs given (`ActionContext.given`), so the prompt asks only the open ones, and Escape before the first goes back to the command prompt; an app action that covers the command (such as "Connect AI agent") takes no given inputs and asks all of its inputs itself. A step that names a workspace (`workspace`, such as the new one of "Create workspace") other than the open one, or while none is open, first opens that workspace as "Open workspace" does (`stepRunner`, `openWorkspaceAt`: as its entry of the recent workspaces, else as a typed folder path), and runs once it is open and its status and the catalog are read, only while that workspace is still the open one (another open or a stopped core process meanwhile runs nothing, and while one step waits another chosen step runs nothing); a workspace that does not open runs nothing, and the command line says why as the prompt "Workspace" says it. A step no entry runs in its own workspace says in the command line that it cannot run here (such as a write command in a read-only workspace). Which steps an output names is core's: the page shows them as they come.
- **Lists from outputs (SR-223 AK5, AK6, `output-list.ts`):** a number of elements in an output, a field the catalog marks `x-elements` with the lists it counts or `selection`, is a line of its own (`ResultLine.list`, `.line.count`: its value underlined in `--edge`) that Enter or a click opens as the list of exactly the elements the CLI, API and MCP give for it: of a read command a list whose one step is `selection.output` with the command, its input and `count` (the field and, per list it stands in, its entry by the fields of `x-key`), labelled "<buffer name> · <entry> · <title>"; of a write command, which never runs again, the UUIDs of the lists the catalog names in its own output (`outputList`). - **Swipe of the wheel (SR-211, `buffer-swipe.ts`, `use-wheel-swipe.ts`, `swipe-target.ts`):** a horizontal two-finger swipe on the trackpad or the horizontal mouse wheel runs "Previous buffer" (`deltaX` < 0, content pushed right) or "Next buffer" through `mouseButtonAction`, as the mouse buttons do, and the shown buffer follows the swipe (below). One non-passive `wheel` listener on the sheet feeds `SwipeGesture`, pure state with the window's timers looked up at each call. Its numbers come from a measurement of a macOS trackpad (#1612): a *gesture* ends after a pause of 150 ms, a *segment* of it after 35 ms (the only longer gaps in a swipe are in its momentum, followed by at most 5 px); a segment its timer ended is joined again when its next event's `timeStamp` lies less than 35 ms after the last (a busy main thread), or, below the third, when it goes on its way with a step of at least 20 px (a wheel notch, an assumption). A pause ends only once its time has passed and a frame has begun after the last event with no event in it (`requestAnimationFrame`, the second callback after the event, as the first may run in the event's own frame; at the time when that frame came already, else at the next frame): the window gets wheel events once per frame, before that frame's callbacks, so a slow frame (dragging over a matrix at 50,000 elements paints at about 22 frames a second) or a busy main thread never ends a swipe that goes on; with the time alone a swipe toward the matrix split (`test/perf/buffer-swipe.spec.ts`). A window that is not visible draws no frames, so there the time alone ends a pause, and a frame not come 300 ms after the time (`FRAME_WAIT_MS`; the longest gap between the events of a swipe on CI was 230 ms) ends it too. So a release can come up to one frame after the 35 ms pause (below about 57 frames a second, or after a slow frame), and without a frame at most 300 ms (`FRAME_WAIT_MS`) after it. An event with Shift, Ctrl (a pinch), Meta or Alt is not read. The first event of a gesture, and the first with dX ≠ 0, ask the window whether the gesture is ignored: not cancelable, a button held, `bufferSwitchBlocked`, no workspace, no other buffer, the wheel event that closed a context menu (`closedBy` of `use-context-menu.ts`, whose capture listener closes it first), the pointer outside the active area, or under the pointer, up to the shown layer, content that scrolls sideways (`overflow-x` auto or scroll, wider than its box) and is not at its edge that way (`scrollsFirst`); an ignored gesture is never prevented. Until a segment has gone 8 px (`DECIDE_PX`) its events are prevented, as Chromium may send the rest of a scroll sequence without `cancelable`; then it is vertical when `|ΣdX| ≤ 1.5·|ΣdY|` (the measured diagonals reach 56 %) for the rest of the gesture, and the vertical distance held back is scrolled with `scrollBy` (a first event that decides scrolls itself), or it is the swipe: its events stay prevented, a running slide ends (SR-212 AK2) and `SwipeDraw.draw` draws the target. With motion each event of the swipe calls `move` with its distance in its way (`max(0, ±ΣdX)`), and the end of the segment calls `release`: it switches when the drag stands past a third of the active area's width (without a drag, when the other area shows the target, by the distance), else the buffer springs back; with reduced motion it switches at once past a third. The switch and `SwipeDraw.end` go into one commit (`flushSync`), so the drawn layer becomes the shown one without being drawn again; the target's layer keeps `data-peek` through that commit and loses it right after (`unpeek`), so in the task of the switch everything it holds takes its style once, not hidden and shown again (#1787). The matrix renders its rows in a memoized component (`MatrixRows`), so that commit, which only shows its layer, does not render its cells again. **Drag (AK3, AK4, `swipe-drag.ts`):** `SwipeDrag` moves the shown layer by the shift in px (`translateX`, written at each event; style writes coalesce into one recalculation per frame) and the target's layer (found by `data-key`, a neighbour drawn in advance or the swipe's own layer) beside it at its edge, painted while it joins (`data-peek`: `visibility: inherit`, still inert and without pointer); the shift is clamped to 0..width, so a swipe back toward its start never shows the other neighbour. A target not drawn yet leaves the shown buffer standing; the distance at its draw is the baseline the shift counts from, so a swipe ended before it switches nothing. Only the active area's layers move; the modeline and the command prompt are outside the area and keep naming the old buffer. Past a third the drag hands its part of the width `p` to the switch (`handOff`, in the task of the switch: no frame between): the picture and the new view stand at `offsets(direction, p)` and slide on in `slideDuration(p)` (`SlideSpec.progress`); a target the drag showed (`peeked`) counts as drawn in advance whatever `AreaViews.clean` says and whatever generation it is ready in, as the reader saw it already. A third or less springs back to 0 in `120 ms · 3p` (`SPRING_MS`, at most 120 ms), nothing dispatched, the focus and selection untouched; a swipe that joins its segment again stops the spring-back and goes on. While a drag or its spring-back runs, the reads drawn in advance wait (`ReadGate.drag`); one of the swipe's target that waited there already goes once the swipe begins, as that layer then reads as a shown view (two quick swipes the same way: the second one's target was the outer neighbour, queued behind the first one's slide). A key, a press of a mouse button, the macOS swipe, another buffer shown in the area (Follow agent, an open), another active area, or the end of the target's draw (closed, no longer beside the shown one) end the drag at once without a switch (a modifier pressed alone does not, `modifier-keys.ts`) and abort the gesture (`abort`: spent), so the input acts on the buffer shown and the rest of the swipe does nothing; a key (not a modifier alone) or a press aborts the gesture also when no drag runs (without motion, or toward the other area: capture listeners of `use-wheel-swipe.ts`) (SR-211 AK12; for input that shows no other buffer an assumption, #1611). Afterwards the gesture is spent until its pause: every event is prevented and does nothing, a new segment decides only after 25 px, is released as vertical only by the ratio above, and becomes a new swipe only when it starts as a trackpad swipe starts (a first step under 20 px) and rises to twice that, to 12 px and past the last step before the pause; momentum after a pause only falls (3-9 px measured), so two quick swipes switch twice and the momentum of one never does. An ignored or vertical gesture is left to the browser in the segment it was decided in (AK6); after a pause, such a segment that rises as a new swipe does and is horizontal asks the window once more, so a swipe from the edge of a table just scrolled, or after a vertical fling, switches while that momentum still runs. The swipe macOS reports to the window (SR-163 AK4) does not ask this gesture.

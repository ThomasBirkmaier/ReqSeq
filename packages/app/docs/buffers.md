# Buffers and views

Part of the [`@reqseq/app` README](../README.md).

- **Start (SR-118):** the first buffer of a workspace is the overview, not the list of all elements. It has one line per element type with the number of its elements (`element.facets`, `types`: "System Requirement 117"), the types of the metamodel first, and below them the elements opened last, at most five, newest first, under a muted "Recent" (nothing of it before an element was opened). Enter or a click on a type line opens the list of the elements of exactly that type (`subtypes: false`, so the list is as long as the count says; it filters further like any list). The full list opens only on request: "List all elements" in the command prompt. Ctrl/Cmd+P works at once, with the overview as the only buffer. "Show overview" in the command prompt (offered when the overview is not shown) and closing the last buffer, also "Close all buffers", show it again; the lone overview cannot be closed. The counts are asked once per change of the workspace, not at every return to the overview. The recent elements are display state of the app, like the open buffers: only the UUID and the repository are kept, per workspace (its name and repositories), in the local storage of the app (Chromium, in the user data folder of the operating system), never in the files of the workspace (SR-118 AK5) and not through a catalog command (SR-080 AK1: "außer reiner Darstellung der App"). Each is read with `element.get` when the overview is shown; one that cannot be read is left out. The main process writes the storage to disk when the app quits.
- **Buffers:** the overview, the list of elements (`element.list`: filter, sort, derivation tree, pages of 200), a search result (`element.search`, pages of 50) and one element (`element.get`: title, the text in the Markdown editor, the properties that are set as boxes below the text and the relations by kind, with a mark and the date of the stored version for outdated ones; the text and the text properties are edited in place, see below), its neighbourhood and its graph, and the metamodel of the workspace. Opening a buffer again shows the one that is open. A **result** buffer shows the output of a catalog command that no other buffer shows (SR-073 AK2, run from the command prompt with #85), laid out by its shape alone (`result.ts`): an element is a row that Enter or a click opens, also a UUID that the output names in `names` (#588, which itself is not shown; under a key the row keeps it: "view: VAR-1"), a problem or hint is one line with its element (Enter opens it), a record of exactly two named UUIDs is one pair line, everything else is a quiet indented outline in greys, at most 2,000 lines; the modeline gives the `total` of the output. When the workspace changed, it asks the command again with the same input. It knows no command (ADR-0002).
- **Split window (SR-115 AK3):** "Split window" in the command prompt (no key) shows the buffer used before beside the shown one, the overview beside a single buffer; "Other window" makes the other area active, as a click or a focus in it does, and "Unsplit window" leaves the active area alone. The modeline names the buffer of the active area, and the commands, Ctrl/Cmd+P, Alt+N/P and Follow agent act on it; choosing the buffer of the other area makes that area active, so a buffer is never in both. For an element and its graph side by side: the element, Ctrl/Cmd+Shift+G, then "Split window". An element left for the other area saves its input at once. The split is not kept after a restart.
- **Open to the right, Open to the left (SR-150):** both commands (no key) open the marked element, the selected row of a list, search, neighbourhood or of the elements opened last, or the selected node of a graph, in the area on that side. Without a split the window splits and the shown buffer stays active on the other side; in a split the inactive side shows it, while the active side opens it as Enter does. In a split, an inactive area that shows an element follows what the reader marks next in the active one; opening, reading again or switching areas moves nothing (`markToken`). The element takes the place of one that following or these commands put there; one the reader opened, or one with unsaved input, stays open behind (`follow-mark.ts`). A list, the overview, a graph, a package page the reader put there and the read-only comparison of SR-044 stay; a package page that following or these commands brought in follows on, until the reader works in it. A relation at an element marks nothing yet (`window-layout.ts`, `markedElement` in `modeline.ts`).
- **Variant difference (SR-044 AK2):** "Show variant difference" (`variant.diff`, command prompt) opens a result buffer with the added, replaced and excluded requirements; a replaced one is a pair line "<core ID> <title> · replacement: <ID> <title>". Enter or a click on it shows the core requirement in the left area, active, and its replacement in the right one, each in a buffer of its own that is read-only (`readOnlyBuffer`: the editors take no input, the modeline says `read-only`, the name in the buffer list ends in "· read-only"), with their text and properties, the acceptance criteria among them. The command prompt does not offer a read-only element first to a write command (it can still be named), so a write never starts from that buffer by Enter alone. A pair line of any other output opens the same way; a row with more fields than the two is an outline. A UUID in two repositories (SR-088) opens in the repository that `names` gives first. The element's own buffer stays editable and apart, and a read-only buffer comes back read-only after a restart (SR-115 AK4).
- **Buffers again after a restart (SR-115 AK4, `buffer-session.ts`):** the buffers open when the app was closed, or when the workspace was left for another, come back when the workspace opens again: the overview shows first (SR-118 AK1), the others are behind it, in their order of use (Ctrl/Cmd+P) and of opening (Alt+N, Alt+P). They are kept per workspace in the app's local storage, never in the workspace, and only what rebuilds each buffer: the kind, UUID and repository of an element, the steps, sort and mode of a list, the text of a search, the input of a graph, the mode of the metamodel, the command and input of a result; no title, text, output or selected row. The names of the elements are read with one `element.list` after the overview shows (each with `element.get` when that fails because one is gone); an element that is gone is left out. A result comes back only for an implemented read command, and runs again when it is shown. After "Close all buffers" only the overview comes back.
- **Elements with a value (SR-132):** Ctrl/Cmd+Shift+Enter on an element ("List elements with this value") opens the list of every element of the workspace with the value at the cursor: the line with the caret in a text box (topic, one value of a list), the box of a choice, the focused target of a relation box (a package: its elements). The list is a list with one filter step (`topic: Timing`), the step "Filter list by property" or "by status" would add, so "Filter list by ..." narrows it further and "Clear list filter" takes the step back; it replaces an open list, as "List all elements" does. Elsewhere (the title, the text, a box with several values, a box of long free text) the minibuffer asks "Elements with" among the values that can be listed: the status, the type and the values of the boxes. Which values qualify is `element.facets` for the element, as for filtering (SR-124): long free text such as the rationale or the acceptance criteria is never offered. Ctrl/Cmd+click on a value of a box (a line of a text box, a choice, a target link) opens the list of that value the same way, before a link opens its target (#235); a click on the key of a box or on a box of long free text lists nothing and, unlike the key, never asks among the other values; the modeline stays a display only (D-062). Unsaved input is saved first. On macOS only Cmd is the modifier, for the key and the click.
- **Package page (SR-112):** an element whose type has the meaning `package` shows below its title, text, properties and relations the elements that name it (`element.list` with `where.package`). They sort and show as a tree with "Sort list" like any list. Down on the page goes into them, Escape and Up on the first row come back. Right under the title a muted line gives its coverage and verification degree (AK3, AK4, `PackageSummary.tsx`): `evidence.coverage` and `evidence.degree` with `selection.package`, formatted by core's `packageSummaryText`, "· incomplete: a repository is missing" when a repository was absent; a package without requirements has no line.
- **Variants and verification status of a requirement (SR-046, SR-047, `VariantLines.tsx`, `variant-lines.ts`):** the validity box names its variants by ID and title, like every relation box. Under the boxes, before the relation groups, a muted line says where a core requirement is replaced or excluded ("Replaced in Coast by SR-0000b1 Response time at most 20 ms · Excluded in Mountain", `replacedBy` and `excludedBy` of `element.get`), and a second its verification status per view ("Verification — Core: verified · Coast: open · Mountain: failed", `verification` of `element.get`: no row for a variant that excludes or replaces it). Variants and replacements are named by `names` and are links to their elements. On the page of a variant (a type with the meaning `variant`), one more muted line per hint since its newest baseline gives core's message as `element.get` and the CLI give it (SR-103: a core requirement it adopts that changed since then, with the version in the baseline and the current one, or that came into its view since then, with the current one; `variant.core-changed-since-baseline`, `variant.core-new-since-baseline`). They cannot be confirmed: they have no hint ID, so "Confirm hints" offers none of them, and confirming the variant shows core's refusal with its reason; a new baseline of the variant settles them. Since they depend on other files (core requirements, baseline files), the page of a variant is read again on every change from outside, its fields, lines and modeline count alike, not the lines alone. A baseline file written outside the app is no change the watcher reports (it watches elements, the metamodel and the workspace file), so the page shows it at its next read; a baseline made in the app ("Create baseline" on the list of all elements in the view of the variant) is read at once. A changed core requirement at its replacement (`variant.core-changed`, SR-045) marks the `replaces` row of the replacement like an outdated relation, and "List hints" with the variant lists it. Each line is there only when it has something to say. The lines come from the buffer's reads of the element; a save keeps them until the element is read again after it. A change from outside that names another element (a variant's exclusions, a replacing requirement, a record) reads a requirement again for the lines alone, as the parents line is read on every change, without touching the fields or their highlights.
- **Neighbourhood (SR-107):** on an element, the parents stand in one line above the title (`trace.neighbourhood`, `up`, derivations, all levels): the titles from the top need down to the direct parents, each a link to the parent; the line is there only when the element has parents, a parent whose link from the element is outdated says "link outdated" (with the hint's message as hover text), and it wraps. It is asked for together with the element, and the element (and the modeline with it) is shown with it, so the title and the fields never move down after they are shown (#542). A new editor parses its text for at most 50 ms more before its first paint, in steps from the end of the viewport, so an ordinary text (some hundred lines) is formatted from the start and a long one at least on its first screen; the rest follows in idle time. A key that needs the syntax tree (Enter in a list, Backspace on a marker, Follow reference, `/`) first parses past the top-level block around the caret (the whole list or table). Ctrl/Cmd+J (action "Show neighbourhood") opens the buffer "Neighbourhood: <ID> <title>": the parents line, the title, the children as an indented tree and below it the incoming relations and inline references grouped by kind ("← derives-from" is the tree itself; "← excludes", "← packages" for the members of a package, "← inline reference"), outdated ones marked "link outdated" with a hover text that names the direction ("SR-147 points to an older version of SR-076 (refines)"). The word names the link, not the element it stands next to: the same outdated relation is marked at the child in the neighbourhood of the parent and at the parent on the child (#513). The relation rows, the inline references and the matrix use the same word. The tree is `trace.neighbourhood` with `meanings: ["derivation"]` from the element; Right opens the row (the app asks again from the same element with one more level), Left closes it or goes to the parent row. A child that appears under more than one parent is shown under each and marked "repeated" from the second time (it is a leaf there). The order of siblings is the command's walk order; the app sorts nothing. Ctrl/Cmd+J on the neighbourhood goes back to the element (action "Show element"). Need to requirements: Ctrl+P, the need's ID or title, Enter, Ctrl+J (SR-119 AK2).
- **Traceability matrix (SR-125):** Ctrl/Cmd+T on a list (action "Show traceability matrix") shows it as a matrix, Ctrl/Cmd+T again ("Show as list") as rows. The matrix is a mode of the list buffer, not a buffer of its own: there is one list buffer, so the matrix replaces the list in place, and "Filter list by ...", "Clear list filter" and "Sort list" keep the mode; the modeline says "matrix". On a package page the same shortcut opens its members as a matrix (all system requirements of a package: Ctrl+P, the package's ID or title, Enter, Ctrl+T; from the overview with a type line and "Filter list by property": about 15 keys). One row per element of the list, in the order of the list (`trace.matrix` with the list's selection and sort), one column per relation kind and direction that occurs ("Derives from", "Derived by", ...), each cell the elements at the other end ("<ID> <title>", one per line). A row without a relation of a column shows "—" in the accent colour (a gap); above each column stands "<count> · <share> %": how many rows of the whole selection have such a relation. An outdated relation says "link outdated" and one to a target that is not there says "missing" (or its other state), as in the element. Up/Down select a row, Right/Left step through the row element and the relations of the row (the cursor is underlined), Enter or a click on a row element or a relation opens that element; an end that is not there opens nothing and the modeline says why. The columns, counts, gaps and marks are what `reqseq trace matrix` gives for the same input (SR-080, SR-125 AK6). Not yet: an entry from a search result or the neighbourhood.
- **Modeline:** a display, not a control (the ID of an element has the copy symbol of a field, and a copy is confirmed here for 3 s, SR-128). Left the parts of the shown buffer (a list: its filter, sort and count; an element: one part with the ID, the type by its name in the metamodel and the status, on a package page then the number of its elements as its heading gives it (SR-114 AK3), then `read-only`, "<n> outdated" and "<n> hints"), right the workspace and its marks. The counts of an element are its hints from `element.get` (SR-114 AK2): "outdated" counts those with the code `relation.outdated`, outdated relations and inline references alike, and "hints" the others, so an outdated one is not counted twice (assumption, the recommended answer to #478 Q5); each only when it is not 0. Values are the commands' output as it is.
- **View (SR-043 AK1, SR-041 AK1, `views.ts`):** "Choose view" (command prompt, no key) asks for "All elements", "Core" or a variant of the workspace ("<ID> <title>", the elements of the types with the meaning `variant`), the one shown marked "shown". The window then shows the chosen view: the list, a search, the overview's counts, a package page's coverage and degree, the filter values of a list, the neighbourhood, the graph, the matrix and the catalog's reads with a selection or a `view` (also from the command prompt, unless a `view` is given there) take it as `selection.view` or `view`, and core computes it. A write that takes the shown list's selection (`element.bulkUpdate`, `data.store`, `baseline.create`) takes it in the view too: it acts on the set the list shows; the list of all elements gives just the view (`baseline.create` of the view of a variant, SR-103). The offers of the prompts find all elements ("Go to", the element arguments of a command, relation targets, "Insert reference"), so a write can name an element outside the view, such as an excluded core requirement to take back (SR-042 AK6). An element itself (`element.get`) and a selection by `ids` (the values of one element, the names of buffers) are read in every view. The modeline says `view: <title>` while a view is shown. The view is display state: all elements at the start, never stored; another workspace shows all elements again.
- **Follow agent (SR-117):** Ctrl/Cmd+Shift+O (action "Follow agent", in the command prompt too) turns the mode „Agent folgen“ on, and again off ("Stop following agent"). While it is on, the window shows the element an agent read or changed last through the API or the MCP server of this copy (`agent-activity`, `use-follow.ts`, the rules in `follow.ts`): its open buffer, else its buffer opened after one `element.get`; turned on, at once the access `workspace.activity` gives (assumption Q3). The mode closes the buffer it opened for the access before (never one with a draft; once the user shows it himself or types in it, it is his), so an agent that reads 200 elements leaves one buffer; what the mode shows is no recent element of the overview. Unsaved input holds an access back (AK5): a draft in any buffer or an open prompt (spec question 2, assumption (b)); the latest access is shown once it is saved, discarded or the prompt is closed; an access only the prompt held is dropped when the user chose something in it, also a command or a sort in place (A3); Escape shows it. The modeline says `following agent`, and `following agent: waits for save` while a draft holds an access. The mode is display state: off at the start, never stored, no command of CLI, API or MCP (AK4); another workspace ends it, a restart of the core process keeps it and asks `workspace.activity` again. Own navigation keeps it on (A3).
- **Not shown unless asked:** UUID and version (action "Show element ID and version": the UUID and the date of the version, D-013, not the check value), empty properties, the shortcut of an action (only in the prompt).

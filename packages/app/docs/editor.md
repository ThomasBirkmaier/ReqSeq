# Editor (SR-065)

Part of the [`@reqseq/app` README](../README.md).

**Typography (SR-192):** the text stands in the centred column of the element, at most 72 characters wide (`72ch`, `.element .column`); in a narrower window the column takes the full width less a small margin, and the text wraps without a sideways scroll. A table wider than the column scrolls in its own box (`.cm-lr-table`), and the editor's content may shrink below it. Code, in the line and in blocks, stands in the face of fixed width (`--mono` in `styles.css`); all other text, tables and their source included, in the proportional face of the window.

The text of an element is Markdown source with a live preview (D-061, `src/renderer/editor/`, CodeMirror 6): headings, emphasis (`*em*`, `**strong**`, `~~strike~~`, `` `code` ``), bullet, ordered and task lists, tables, fenced and indented code blocks, quotes and links appear set, and the source shows only on the lines the cursor touches while the editor has the focus. A table shows its source while the cursor is in any of its rows (spec question ThomasBirkmaier/ReqSeq-archive#420). There is no preview pane, no toolbar and no Markdown rewriting: the preview only decorates, and the file holds exactly what is in the editor (core adds the final line break, ADR-0004). Nothing in the text is interpreted as HTML. An inline reference (a `reqseq:` link) opens its element on a click on its label (Ctrl/Cmd+click on a line that shows its source) and with Ctrl/Cmd+Enter when the cursor is on it (action "Follow reference"); an outdated one (a `relation.outdated` hint of `element.get`) is shown in the accent colour with the word "outdated" and the date of the version it stores ("outdated · version of 2026-03-04", D-013; "unknown date" when Git cannot tell), with the hint and both dates as its hover text (SR-110 AK2, ThomasBirkmaier/ReqSeq-archive#702). The element is opened without dates (no git, SR-082 AK3); only for an element with outdated hints the buffer asks `element.get` once more with `hintDates`, which dates these hints alone, and shows "outdated" until the answer is there. The relation rows and the parents line take the same mark from the hints of their item (ThomasBirkmaier/ReqSeq-archive#665). The app finds the hint of a link or item by the fields of the problem (`key`, `place`, `targetId`, `storedVersion`, #222), never by parsing its `hintId`. Other links are not followed, and a link in a table cell is not clickable yet.

**Folding and headings (SR-191, `editor/folding.ts`, `heading-actions.ts`):** a heading at the top level of the text and everything up to the next heading of the same or a higher level is a section (a `#` line in a list or quote is none). "Fold section" (command prompt, no key) folds the section the cursor is in, the innermost one, and puts the cursor at the end of its heading; the section shows as a muted "… 6 lines" after the heading. A toggle (▾, ▸ when folded) left of a heading with a section shows only while the pointer is over the heading; a click on it folds or unfolds. "Unfold section", a click on the hint, or the cursor moving into the fold (a click, "Go to heading") opens it again. "Go to heading" offers the headings of the text in their order, with their level (H1 to H6), with the fuzzy matching of the prompt, and puts the cursor at the start of the chosen one. Folding is display state of the editor: it writes nothing, works on an element that cannot be changed, and is gone when the buffer is shown again.

- **Keys:** Enter on the element puts the cursor at the end of the text; Escape comes back to the element; the input is saved without a save command (below), and Ctrl/Cmd+S saves at once; Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z undo and redo, in the text, in a text box and on a choice or relation box (below); Enter in a list continues it. After a prompt closes, the focus goes to the element (the article), not to the text, unless the action was "Edit text", or the prompt set the value of a property box or added a property: then it goes to that box.
- **Saving without a save command (SR-105, `autosave.ts`; what a save sends and says, `save-flow.ts`):** one second after the last change of the text or of a box, the buffer sends one `element.update` with everything that differs from the file; a cursor move is no input. At most one save of a buffer runs: input typed meanwhile waits for its answer and is saved one second after the last key, or at once when that second has passed. The save waits while input is still going on (an input method composing, the slash menu open, "Reference to element" waiting for its element; a prompt that replaces "Insert reference" cancels it as Escape does), so nothing half typed is written. It saves at once when the element is left (the holds do not count then: an open slash menu's `/` and its query are written as typed, since leaving is deliberate and nothing typed is lost) (another buffer shown, "Close buffer", "Close all buffers", another workspace, the window closed or the app quit) and when a prompt opens (binding review point 6: a command run from the prompt starts from the saved file). Assumption (ThomasBirkmaier/ReqSeq-archive#488): moving between the text and the boxes and the window losing focus are no leaving. A successful autosave says nothing, and the modeline `modified` goes away; a hint of core is said once while it stays the same. A save that fails leaves `not saved` in the modeline and says its reason once while it stays the same; the next input saves again, there is no retry loop. Nothing is saved over a change on disk, a deleted file or a read-only element (SR-106). "Save element" (Ctrl/Cmd+S) is a command and a key, not a button (AK3, assumption A1): it saves at once and says `Saved <name>`; pressed while a save writes, it waits for that write and saves what is left after it, and says `Saved <name>` also when that write left nothing (#563: it was dropped then and said nothing). The app has no save button and no save dialog (`[SR-105/AK3]`). A buffer shown again while the save of its leaving runs reads its element after that save, so its own write is no change on disk.
- **Closing the window (SR-105 AK1, `src/main/close.ts`):** closing the window is leaving the element, also when the app quits (Electron closes the window first). Main holds the first close and asks the window to save (`reqseq:save` with `{ id, closing: true }`); the window saves as before a switch (the shown buffer, the saves of buffers left just before, then every draft), but without the switching state, and main closes it when the answer is `saved`. Input that cannot be saved (a change on disk, a deleted file, a value core refuses) keeps the window open: the minibuffer says `<name> could not be saved (<why>): close the window again to discard the unsaved input`, and the next close discards it, unless input or an action came in between. No dialog (AK3). A window that does not answer within 2 s stays open: main tells it (`{ id, expired: true, closing: true }`), the minibuffer says so, and a close within 10 s goes through without asking, so a window that hangs can always be closed; a later close asks the window again. A close while a workspace switch saves waits for that save (no second write of the same drafts). An input method that is still composing, an open slash menu or a pending "Insert reference" do not hold the save (their text is written as typed).
- **Undo since the buffer was opened (SR-105 AK2, `buffer-memory.ts`, `value-history.ts`):** Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z (Ctrl+Y outside macOS) step through the states of the field with the cursor since its buffer was opened, also after the input was saved and after another buffer was shown (the app keeps the history of each editor, `EditorState.toJSON` with the history, per open buffer). A choice or relation box keeps the values it had (undo and redo on the focused box), and "Take the file" on such a box is a change it undoes. An undo or redo is input, so it is saved one second later. Closing the buffer, the buffers pushed out by the 30 kept, and another workspace drop the history. Assumption (ThomasBirkmaier/ReqSeq-archive#488, 2): per field, not one history across the element.
- **Unsaved text and boxes** are a draft the app keeps per buffer while another buffer is shown (the modeline says `modified`) until their save answered. "Close buffer" saves the input and closes; it asks once only when the input could not be saved (a change on disk, a deleted file, a value core refuses), and discards when repeated. Before another workspace opens ("Open workspace", File > Open Workspace), every draft is saved first (SR-131 AK3, `src/renderer/switch.ts`), the shown buffer last; the first that cannot be saved (core refuses a value, the element cannot be read, its file changed outside since the draft was typed on) stops the switch and keeps its draft. "Close all buffers" saves the unsaved text first and closes every buffer; only with text that could not be saved it asks in the minibuffer (Enter keeps the buffers with unsaved text, the second choice discards it). A draft keeps the text, the boxes with changes (the keys of a choice, one line per target of a relation with its id, repository and label separated by tabs, and the boxes that were added, whose base is the empty document), the file text and stored values they were typed on, and the bytes of that file (`fileSha256`). A file changed outside the app is read again when the watcher reports it (Changes from outside, above); a buffer that is not shown compares when it is shown again, by the same rule (below).
- **A crash of the window's page (#270, `src/main/renderer-gone.ts`, `src/renderer/draft-store.ts`):** the drafts are also kept in the window's session storage, one entry `reqseq.drafts.v1` written on every change of a draft, with the storage key of the workspace (`sessionKey`) and the buffer shown. Session storage lives outside the renderer process and goes with the window, so a draft a close let go never comes back at the next start. When the renderer ends other than by a clean exit (a crash, out of memory, killed), main loads the page again in the same window, without a dialog (SR-105 AK3), and logs one line; after 3 reloads within 60 s it stops, so a page that crashes at start does not loop. The page finds the workspace open in the core process and its buffers (SR-115 AK4); on its first status it takes the drafts kept for that workspace, shows the buffer it showed, and the minibuffer says `The window was loaded again; the unsaved input of <n> buffers is back` (a conflict found then says its own line). Each buffer compares its draft with its file as a buffer shown again does (below). A hang of the page (`unresponsive`) is not handled.
- **A file changed or deleted under the input (SR-106 AK2, AK3, SR-116 AK3; `outside-change.ts`; the buffer towards its file, `disk-state.ts`; the input and the file per field, `field-state.ts`):** a field without input follows the file, and input that the file now holds is no input any more. When the file's bytes are no longer those the input was typed on and input is left, nothing is saved: the editors keep the input, a quiet read-only block "On disk" under every field with input shows the file's value (the lines the input lacks in heavier weight), the modeline says `changed on disk`, the minibuffer says once `<name> changed on disk. Resolve with "Resolve change on disk"`, and Ctrl/Cmd+S says "Resolve the change on disk first". "Resolve change on disk" (command prompt, or Enter on a block) asks "Keep my input" (writes the fields with input on the file as it is now; an outside change of another field stays) or "Take the file" (the file's values into the editors; Ctrl/Cmd+Z brings the input back). Assumption until spec question ThomasBirkmaier/ReqSeq-archive#488 (1) is answered: any change of the file while there is input asks, not only a change of a field with input. A box with input whose property left the file stays, as an added box. A read that finds no element may be a file being written (a pull: removed in one batch, added in the next, and core does not know the element in between), so the buffer stays editable and asks once more after 2 s, longer than one batch of the watcher and the time core takes to apply a large one; an `added` asks at once, and a read that fails for another reason starts the count again. Ctrl/Cmd+S in that time writes nothing and says `<name> cannot be read now; it may have been deleted on disk`. A file that is still gone then is deleted: it leaves the content in the editors, read-only (Copy field works), the modeline says `deleted on disk`, the minibuffer `<name> was deleted on disk; its content stays here until you close the buffer`; nothing is written or created, and the buffer is editable again when the file is back. A buffer that was not shown when its file was deleted shows its draft in the same way when it is shown again: the draft keeps the element its buffer showed. A save that core refuses with `file.changed-on-disk` reads the element once: the bytes that were sent (core had not read the file yet) save again once, silently; other bytes follow the rule above.
- **Tasks (SR-185)** (`editor/tasks.ts`, the click in `editor/list-drag.ts`): a click (press and release) on the box of a task (☐, ☑) switches its marker in the file between `[ ]` and `[x]` (`[X]` counts as ticked), one undo step of its own; the caret and the focus stay where they are, and a read-only text does not change. With the caret on the line of a task (or a selection over several), "Toggle task" in the command prompt does the same, or says `No task on this line`.
- **Tables (SR-188)** (`editor/tables.ts`): with the caret in a table and no menu open at it, Tab and Shift+Tab select the next and the previous cell (over the delimiter row; an empty cell gets the caret after one space); a row with fewer cells than the header gets the missing cell Tab goes to; Tab after the last column of the last row adds an empty row (as wide per cell as a header framed by pipes) with the caret in its first cell, and Shift+Tab in the first cell stays there. Outside a table Tab keeps its meaning. In the command prompt, "Align table" writes every row as `| a | b |` with each column as wide as its widest cell, the delimiter dashes widened and the colons kept, and pads the content left, centred or right as the colons say; widths count characters as a reader does (grapheme clusters), so a wide character (CJK, emoji) lines up by characters, not on screen. Nothing aligns a table without this action. "Insert row" (below the caret's row; on the header or the delimiter row it becomes the first body row), "Insert column" (right of the caret's column, `---` in the delimiter row), "Delete row" (not the header) and "Delete column" (not the last one) change the table at the caret. Cells are split as GFM does, at each `|` no `\` escapes, also inside inline code. Each change is one undo step of its own. Off a table an action says `The cursor is not in a table`; "Delete row" on the header or the delimiter row says `The cursor is not in a table row below the header`, and "Delete column" in a table of one column `The cursor is not in a table with more than one column`.
- **Lists (SR-187)** (`editor/lists.ts`): in a list item, Tab indents the item with its sub-items (and the siblings a selection reaches) under the item before it, to that item's content column; Shift+Tab outdents it to the level of its parent item, so the items after it become its sub-items, as in an outliner. The first item and an item at the top level stay, and the key is taken all the same; the numbers of an ordered list are not rewritten by Tab; outside lists (and tables) Tab and Shift+Tab go on to the next or previous field as before, and the slash menu takes Tab while it is open. Alt+Up and Alt+Down (Option on macOS) move the item with its sub-items one place past its neighbour at the same level (at the end of its list it stays; what lies between, a blank line of a loose list, stays between; an ordered list numbered in sequence stays so), and outside lists the line or the selected lines. Each change is one undo step; the caret moves with its item. An item behind a quote mark or another mark on its line is left alone.
- **Dragging list items (SR-187 AK3)** (`editor/list-drag.ts`; plan and review on #1092): a drawn list mark (the bullet, the number of an ordered item, the box of a task; not on the line that shows its source) is a handle. A press and a move of 4 px drags the item with its sub-items; its lines are muted, and a grey rule shows the gap among its siblings nearest to the pointer, found from the line under it again on every move and scroll. Release drops it there, in one undo step; release at its own place or outside the window, Escape, the window losing the focus, and any change of the text meanwhile cancel. The page does not scroll by itself near its edges; the wheel scrolls during a drag, and the gap follows. A task box behind a quote or another mark is no handle, but a click on it still ticks it; a pointer on a blank line of a loose list aims at the gap there. Only the same list at the same level (assumption, spec question #1107); Tab and Shift+Tab change the level. The text between the items (line breaks, the blank lines of a loose list) stays at its places, and an ordered list numbered in sequence is numbered in sequence after it, the continuation lines of an item whose number changes width shifted with it (Alt+arrows do the same). A press and release without a move is a click: a task box toggles, a bullet or number puts the caret there. While a drag goes on autosave waits (`busy`). No HTML drag and drop: plain mouse events with window listeners while the button is held.
- **Text actions** (`src/renderer/text-actions.ts`): the actions of the command prompt that edit the text at its cursor (D-073). Each names an editing command of `editor/` and runs it on the field with the cursor, or the one it was in last (a Markdown box, else the text), with the selection it had before the prompt opened (`ElementControls.text`, `EditorHandle.run`), then gives that field the focus; in the title, or with the element locked (read-only, deleted or unreadable on disk, or changed on disk under the input), it says why instead. A click on a task box follows the editor's read-only state, like typing.
- **Formatting the selection (SR-186)** (`editor/format.ts`, `text-actions.ts`): "Bold", "Italic" and "Inline code" (command prompt; Ctrl/Cmd+B and Ctrl/Cmd+I for the first two) put `**`, `*` or `` ` `` around the selection and keep it on the text, around the word at the caret, or write an empty pair with the caret between them in white space. White space at the edges of a selection stays outside the marks; code with backticks gets a longer fence. The same format on formatted text (the selection inside it, or the whole node with its marks) takes its marks off, also `_x_`. "Link" asks for the address (prompt "Link address") and writes `[selection](address)`, or `[address](address)` at the caret; an address with white space or parentheses goes in `<…>`. Each is one undo step of its own. The editor with the focus takes the keys: the text and a Markdown property box format, the title and a plain box ignore them; from the command prompt the action formats the field with the cursor, or the one it was in last (a Markdown box, else the text), at the selection it had. On macOS the physical Ctrl+B stays the Emacs key.
- **Find and replace (SR-189)** (`editor/find.ts`, `find-actions.ts`): "Find in element" (Ctrl/Cmd+F) asks in the minibuffer; every hit of the typed text is marked in the text (the grey of a selection, the current one outlined) and the first one from the caret is current, while the minibuffer keeps the focus. The search is the text as typed, no pattern; it ignores case while it is all lower case (smart case, as Emacs). Enter goes to the next hit, Shift+Enter to the one before, both wrapping; the modeline says "2 of 5" or "no match". Escape (or a press outside) ends it: the marks go, and the text gets the focus with the caret at the start of the hit reached last. "Replace" asks for the search (the last one typed first) and then for the replacement in "Replace “…” with": each Enter replaces the current hit and goes to the next, Shift+Enter skips one, Escape ends as above. "Replace all" asks the same and replaces every hit at once; the modeline says "Replaced 3 hits". Each replace is one undo step. Always the text of the element, not a property box. Typing more searches again from the caret where the search began. Find also works in a read-only element; Replace and Replace all say why it takes no input. A search without hits opens no prompt for the replacement. The last search is kept while the window is open, for both areas.
- **Slash menu (SR-129)** (`slash-menu.ts`, `slash-entries.ts`): `/` typed at the start of a line or after white space, outside code, links and addresses, opens a menu at the caret with headings, normal text, lists, task list, quote, code block, table, link, reference to an element, image, math block, diagram, bold and italic (no underline: Markdown has none, D-015). More typing narrows it as the command line does (initials, letters in order, one slip); Down/Up, Tab and Ctrl+N/Ctrl+P choose, Enter takes the entry in one undo step, Escape closes the menu and the `/` stays as typed. "Reference to element" opens the prompt "Insert reference" (the search of "Go to") and writes `[title](reqseq:<uuid>)`. "Image" opens the prompt "Insert image" (below). The menu only edits the text; whether D-062 allows it is the spec question ThomasBirkmaier/ReqSeq-archive#453.
- **`[[` search (SR-066)** (`reference-search.ts`, `reference-pick.ts`): two `[` typed one after the other (not pasted, composed or brought back by undo; not after `\` or `!`, not a third `[`; not in code, links, addresses or HTML; not in the query of a `/` while its menu shows entries) open the prompt "Insert reference" of the slash menu: the same search over title and IDs of all elements. The pick replaces the `[[` with `[title](reqseq:<uuid>)` in one undo step (the short ID and the repository for a target in another repository); core adds the version when the text is saved. Escape leaves the `[[`; autosave waits while the prompt is open. The same works in a box of a property marked `markdown` (SR-127 AK2). A reference to another repository shows the title of its target off its source line when the target is here (D-058); the app keeps the titles for the workspace until another one opens or core restarts (`reference-titles.ts`; a failure other than "not here" is asked again), and a pick brings its title along.
- **Images (SR-097)** (`insert-image.ts`): "Insert image" (command prompt, and the slash menu's "Image") asks for the path of an image file, absolute or relative to the workspace root (typed text, no completion). `element.addAttachment` copies it into the folder named like the element file without `.md`, next to it, and the Markdown it returns (`![name](<folder>/<file>)`, relative to the element file) goes to the caret in one undo step, or in place of the `/` and its query; the text is saved as any input. A refused file (not an image, missing) is said in the minibuffer and nothing is written; Escape writes nothing. The command prompt does not list "Add attachment" separately (the action `covers` it).
- **Image preview (SR-184)** (`image-preview.ts`): an image whose destination is relative and stays inside the element's repository (resolved against the element file as core's version rule does: escapes removed, `?` and `#` dropped, percent-decoded; also `<…>` and reference images) is drawn from `reqseq-file:` (served by the core process, Security below) in place of its source off the lines that show their source, at most as wide as the text column, as a block when it is alone in its line. On a line that shows its source, the source stays and the image follows below the line. An address with a scheme (`https:`, `file:`), a `data:` address, a drive (`C:`), an absolute path or a path out of the repository is never loaded: the source stays with a grey note (`not shown: address on the network`, `not shown: data: address`, `not shown: outside the repository`). An image that does not load (missing, no readable image, a backslash or a trailing `/` in its path) keeps its source with `not shown: file missing or not an image`; it is asked again when the editor takes the focus. Assumption (#1100): another repository of the workspace counts as outside. An image over two lines or inside a table cell keeps its source (core's version rule reads images on one line; a table is drawn as one widget). The boxes of Markdown properties draw no images (ADR-0004, D-057).
- **Paste and drop as Markdown (SR-190)** (`paste.ts`): in the text (not in code or a formula, not read-only), a paste is decided in this order. Image files on the clipboard (a screenshot, a copied file) or dropped into the text are copied by `element.addAttachment` from their bytes (`content` and `name`; a name without an image extension gets one from the type, a screenshot is `image.png`), one after the other in their order (at most 20 MiB each), and once all answered their Markdown replaces the selection or goes where the drop was, one image per line, mapped through the edits made meanwhile, in one undo step; a refused image is said in the minibuffer, and an image copied after its buffer was left is said with its Markdown. No image is dropped into code. Files come first only when the clipboard has no HTML or the HTML is just one image, because spreadsheets put a picture of a copied table next to its HTML. A drop with a file that is no image inserts nothing and says `Only image files can be dropped into the text`. Plain text that is one absolute address (`http:`, `https:`, `mailto:`, `reqseq:`) over a selection makes each selected range `[text](address)` (`<address>` with a space or parentheses, brackets in the text escaped; a selection over two paragraphs pastes the address as it is). HTML from a browser or a word processor is read as an inert document (`DOMParser`) and written as Markdown with GitHub extensions by core (`@reqseq/core/pasted-markdown`, the conversion of the ReqIF import): headings, emphasis, strike-through, lists (also Word's list paragraphs), links, tables (a line end in a cell is a space), code and quotes, images on the network as Markdown images, which the preview does not load; other images become their alt text and the minibuffer says how many were left out; links other than `http:`, `https:`, `mailto:` and `reqseq:` become their text; `$` is escaped; block content pasted in the middle of a line gets blank lines around it. HTML without formatting and a code editor's copy (`white-space: pre`, or VS Code's `vscode-editor-data`) paste as plain text. Each paste is one undo step.
- **Formulas (SR-096)** (`math-syntax.ts`, `formula.ts`, `formula-preview.ts`): `$…$` in a line, a block between two lines that are only `$$`, and fenced `math` blocks appear set by the bundled KaTeX off the lines that show their source. With the cursor in a block formula its source shows with the set formula below it; with the caret inside a `$…$`, the set formula appears under the line. A formula with a syntax error keeps its source, and the error follows it in grey. No `/` menu and no `[[` search inside a formula.
- **Diagrams (SR-096)** (`diagram.ts`, `mermaid-renderer.ts`): fenced `mermaid` blocks appear drawn by the bundled Mermaid (loaded on the first diagram) off the lines that show their source, as an image of the SVG, in the greys of the colour scheme. With the cursor in a diagram its source shows with the drawing below it, drawn again after a pause that grows with the time the last drawing took (at least 300 ms), and at once when the cursor leaves it. A diagram with a syntax error, or over the bounds (50,000 characters, 500 statements in lines or between `;`, 500 edges of a flowchart), keeps its source, and the error follows it in grey.
- **Extension points** (`editor/plugins.ts`) for the following issues: parser extensions and preview rules (formulas and diagrams ThomasBirkmaier/ReqSeq-archive#108; images SR-184) and further CodeMirror extensions (the slash menu SR-129, the `[[` search SR-066). Property boxes use the same plugins (`TextBox.tsx`, ThomasBirkmaier/ReqSeq-archive#400).
- **Changes from outside (SR-116, SR-106):** when the CLI, the API, MCP, another editor or Git changes files while the app runs, the window follows without a word (D-062). A change of elements reads neither the metamodel nor the status: an element buffer asks for its element again only when a change since the one it saw last names it as changed or added, also when several came before the window drew (a file read while it is written counts as removed in one batch and added in the next), and its editors without input take the new text with the cursor kept at its place in the text (SR-106 AK1); a removal asks too, and only a read that still fails with `ref.unknown` 2 s later says the file is gone (below); the other views ask again on every change, and a list keeps its rows, selection and scroll until the answer is there (Enter opens a kept row meanwhile). A change of the metamodel or the workspace (also a pull of more than 1,000 elements) refreshes everything. An element changed or added outside and shown within 2 s of the change is highlighted briefly and quietly: a grey tint that fades and is gone after 2.5 s, within the 3 s of SR-116 AK2 (still, without fading, with reduced motion). In the element buffer it marks the fields whose shown value changed (the title when none did, or when the buffer opened just then), never one with input, and only when the file's bytes (`fileSha256`) differ from what the buffer showed, so the app's own save never flashes; in a list, the package page, the neighbourhood and the overview the row, in the matrix the row element. Graph nodes are not marked yet.

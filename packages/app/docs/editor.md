# Editor (SR-065)

Part of the [`@reqseq/app` README](../README.md).

The text of an element is Markdown source with a live preview (D-061, `src/renderer/editor/`, CodeMirror 6): headings, emphasis (`*em*`, `**strong**`, `~~strike~~`, `` `code` ``), bullet, ordered and task lists, tables, fenced and indented code blocks, quotes and links appear set, and the source shows only on the lines the cursor touches while the editor has the focus. A table shows its source while the cursor is in any of its rows (spec question #420). There is no preview pane, no toolbar and no Markdown rewriting: the preview only decorates, and the file holds exactly what is in the editor (core adds the final line break, ADR-0004). Nothing in the text is interpreted as HTML. An inline reference (a `logreq:` link) opens its element on a click on its label (Ctrl/Cmd+click on a line that shows its source) and with Ctrl/Cmd+Enter when the cursor is on it (action "Follow reference"); an outdated one (a `relation.outdated` hint of `element.get`) is shown in the accent colour with the word "outdated" and the date of the version it stores ("outdated · version of 2026-03-04", D-013; "unknown date" when Git cannot tell), with the hint and both dates as its hover text (SR-110 AK2, #702). The element is opened without dates (no git, SR-082 AK3); only for an element with outdated hints the buffer asks `element.get` once more with `hintDates`, which dates these hints alone, and shows "outdated" until the answer is there. The relation rows and the parents line take the same mark from the hints of their item (#665). Other links are not followed, and a link in a table cell is not clickable yet.

- **Keys:** Enter on the element puts the cursor at the end of the text; Escape comes back to the element; the input is saved without a save command (below), and Ctrl/Cmd+S saves at once; Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z undo and redo, in the text, in a text box and on a choice or relation box (below); Enter in a list continues it. After a prompt closes, the focus goes to the element (the article), not to the text, unless the action was "Edit text", or the prompt set the value of a property box or added a property: then it goes to that box.
- **Saving without a save command (SR-105, `autosave.ts`; what a save sends and says, `save-flow.ts`):** one second after the last change of the text or of a box, the buffer sends one `element.update` with everything that differs from the file; a cursor move is no input. At most one save of a buffer runs: input typed meanwhile waits for its answer and is saved one second after the last key, or at once when that second has passed. The save waits while input is still going on (an input method composing, the slash menu open, "Reference to element" waiting for its element; a prompt that replaces "Insert reference" cancels it as Escape does), so nothing half typed is written. It saves at once when the element is left (the holds do not count then: an open slash menu's `/` and its query are written as typed, since leaving is deliberate and nothing typed is lost) (another buffer shown, "Close buffer", "Close all buffers", another workspace, the window closed or the app quit) and when a prompt opens (binding review point 6: a command run from the prompt starts from the saved file). Assumption (#488): moving between the text and the boxes and the window losing focus are no leaving. A successful autosave says nothing, and the modeline `modified` goes away; a hint of core is said once while it stays the same. A save that fails leaves `not saved` in the modeline and says its reason once while it stays the same; the next input saves again, there is no retry loop. Nothing is saved over a change on disk, a deleted file or a read-only element (SR-106). "Save element" (Ctrl/Cmd+S) is a command and a key, not a button (AK3, assumption A1): it saves at once and says `Saved <name>`. The app has no save button and no save dialog (`[SR-105/AK3]`). A buffer shown again while the save of its leaving runs reads its element after that save, so its own write is no change on disk.
- **Closing the window (SR-105 AK1, `src/main/close.ts`):** closing the window is leaving the element, also when the app quits (Electron closes the window first). Main holds the first close and asks the window to save (`logreq:save` with `{ id, closing: true }`); the window saves as before a switch (the shown buffer, the saves of buffers left just before, then every draft), but without the switching state, and main closes it when the answer is `saved`. Input that cannot be saved (a change on disk, a deleted file, a value core refuses) keeps the window open: the minibuffer says `<name> could not be saved (<why>): close the window again to discard the unsaved input`, and the next close discards it, unless input or an action came in between. No dialog (AK3). A window that does not answer within 2 s stays open: main tells it (`{ id, expired: true, closing: true }`), the minibuffer says so, and a close within 10 s goes through without asking, so a window that hangs can always be closed; a later close asks the window again. A close while a workspace switch saves waits for that save (no second write of the same drafts). An input method that is still composing, an open slash menu or a pending "Insert reference" do not hold the save (their text is written as typed).
- **Undo since the buffer was opened (SR-105 AK2, `buffer-memory.ts`, `value-history.ts`):** Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z (Ctrl+Y outside macOS) step through the states of the field with the cursor since its buffer was opened, also after the input was saved and after another buffer was shown (the app keeps the history of each editor, `EditorState.toJSON` with the history, per open buffer). A choice or relation box keeps the values it had (undo and redo on the focused box), and "Take the file" on such a box is a change it undoes. An undo or redo is input, so it is saved one second later. Closing the buffer, the buffers pushed out by the 30 kept, and another workspace drop the history. Assumption (#488, 2): per field, not one history across the element.
- **Unsaved text and boxes** are a draft the app keeps per buffer while another buffer is shown (the modeline says `modified`) until their save answered. "Close buffer" saves the input and closes; it asks once only when the input could not be saved (a change on disk, a deleted file, a value core refuses), and discards when repeated. Before another workspace opens ("Open workspace", File > Open Workspace), every draft is saved first (SR-131 AK3, `src/renderer/switch.ts`), the shown buffer last; the first that cannot be saved (core refuses a value, the element cannot be read, its file changed outside since the draft was typed on) stops the switch and keeps its draft. "Close all buffers" saves the unsaved text first and closes every buffer; only with text that could not be saved it asks in the minibuffer (Enter keeps the buffers with unsaved text, the second choice discards it). A draft keeps the text, the boxes with changes (the keys of a choice, one line per target of a relation with its id, repository and label separated by tabs, and the boxes that were added, whose base is the empty document), the file text and stored values they were typed on, and the bytes of that file (`fileSha256`). A file changed outside the app is read again when the watcher reports it (Changes from outside, above); a buffer that is not shown compares when it is shown again, by the same rule (below).
- **A file changed or deleted under the input (SR-106 AK2, AK3, SR-116 AK3; `outside-change.ts`; the buffer towards its file, `disk-state.ts`; the input and the file per field, `field-state.ts`):** a field without input follows the file, and input that the file now holds is no input any more. When the file's bytes are no longer those the input was typed on and input is left, nothing is saved: the editors keep the input, a quiet read-only block "On disk" under every field with input shows the file's value (the lines the input lacks in heavier weight), the modeline says `changed on disk`, the minibuffer says once `<name> changed on disk. Resolve with "Resolve change on disk"`, and Ctrl/Cmd+S says "Resolve the change on disk first". "Resolve change on disk" (command prompt, or Enter on a block) asks "Keep my input" (writes the fields with input on the file as it is now; an outside change of another field stays) or "Take the file" (the file's values into the editors; Ctrl/Cmd+Z brings the input back). Assumption until spec question #488 (1) is answered: any change of the file while there is input asks, not only a change of a field with input. A box with input whose property left the file stays, as an added box. A read that finds no element may be a file being written (a pull: removed in one batch, added in the next, and core does not know the element in between), so the buffer stays editable and asks once more after 2 s, longer than one batch of the watcher and the time core takes to apply a large one; an `added` asks at once, and a read that fails for another reason starts the count again. Ctrl/Cmd+S in that time writes nothing and says `<name> cannot be read now; it may have been deleted on disk`. A file that is still gone then is deleted: it leaves the content in the editors, read-only (Copy field works), the modeline says `deleted on disk`, the minibuffer `<name> was deleted on disk; its content stays here until you close the buffer`; nothing is written or created, and the buffer is editable again when the file is back. A buffer that was not shown when its file was deleted shows its draft in the same way when it is shown again: the draft keeps the element its buffer showed. A save that core refuses with `file.changed-on-disk` reads the element once: the bytes that were sent (core had not read the file yet) save again once, silently; other bytes follow the rule above.
- **Slash menu (SR-129)** (`slash-menu.ts`, `slash-entries.ts`): `/` typed at the start of a line or after white space, outside code, links and addresses, opens a menu at the caret with headings, normal text, lists, task list, quote, code block, table, link, reference to an element, image, math block, diagram, bold and italic (no underline: Markdown has none, D-015). More typing narrows it as the command line does (initials, letters in order, one slip); Down/Up, Tab and Ctrl+N/Ctrl+P choose, Enter takes the entry in one undo step, Escape closes the menu and the `/` stays as typed. "Reference to element" opens the prompt "Insert reference" (the search of "Go to") and writes `[title](logreq:<uuid>)`. "Image" opens the prompt "Insert image" (below). The menu only edits the text; whether D-062 allows it is the spec question #453.
- **`[[` search (SR-066)** (`reference-search.ts`, `reference-pick.ts`): two `[` typed one after the other (not pasted, composed or brought back by undo; not after `\` or `!`, not a third `[`; not in code, links, addresses or HTML; not in the query of a `/` while its menu shows entries) open the prompt "Insert reference" of the slash menu: the same search over title and IDs of all elements. The pick replaces the `[[` with `[title](logreq:<uuid>)` in one undo step (the short ID and the repository for a target in another repository); core adds the version when the text is saved. Escape leaves the `[[`; autosave waits while the prompt is open. The same works in a box of a property marked `markdown` (SR-127 AK2). A reference to another repository shows the title of its target off its source line when the target is here (D-058); the app keeps the titles for the workspace until another one opens or core restarts (`reference-titles.ts`; a failure other than "not here" is asked again), and a pick brings its title along.
- **Images (SR-097)** (`insert-image.ts`): "Insert image" (command prompt, and the slash menu's "Image") asks for the path of an image file, absolute or relative to the workspace root (typed text, no completion). `element.addAttachment` copies it into the folder named like the element file without `.md`, next to it, and the Markdown it returns (`![name](<folder>/<file>)`, relative to the element file) goes to the caret in one undo step, or in place of the `/` and its query; the text is saved as any input. A refused file (not an image, missing) is said in the minibuffer and nothing is written; Escape writes nothing. The command prompt does not list "Add attachment" separately (the action `covers` it). Assumptions (#109): an image is inserted from a file only (no clipboard paste, no drop), and the live preview does not draw it, it shows the Markdown.
- **Formulas (SR-096)** (`math-syntax.ts`, `formula.ts`, `formula-preview.ts`): `$…$` in a line, a block between two lines that are only `$$`, and fenced `math` blocks appear set by the bundled KaTeX off the lines that show their source. With the cursor in a block formula its source shows with the set formula below it; with the caret inside a `$…$`, the set formula appears under the line. A formula with a syntax error keeps its source, and the error follows it in grey. No `/` menu and no `[[` search inside a formula.
- **Diagrams (SR-096)** (`diagram.ts`, `mermaid-renderer.ts`): fenced `mermaid` blocks appear drawn by the bundled Mermaid (loaded on the first diagram) off the lines that show their source, as an image of the SVG, in the greys of the colour scheme. With the cursor in a diagram its source shows with the drawing below it, drawn again after a pause that grows with the time the last drawing took (at least 300 ms), and at once when the cursor leaves it. A diagram with a syntax error, or over the bounds (50,000 characters, 500 statements in lines or between `;`, 500 edges of a flowchart), keeps its source, and the error follows it in grey.
- **Extension points** (`editor/plugins.ts`) for the following issues: parser extensions and preview rules (formulas and diagrams #108; images are not drawn yet, SR-097) and further CodeMirror extensions (the slash menu SR-129, the `[[` search SR-066). Property boxes use the same plugins (`TextBox.tsx`, #400).
- **Changes from outside (SR-116, SR-106):** when the CLI, the API, MCP, another editor or Git changes files while the app runs, the window follows without a word (D-062). A change of elements reads neither the metamodel nor the status: an element buffer asks for its element again only when a change since the one it saw last names it as changed or added, also when several came before the window drew (a file read while it is written counts as removed in one batch and added in the next), and its editors without input take the new text with the cursor kept at its place in the text (SR-106 AK1); a removal asks too, and only a read that still fails with `ref.unknown` 2 s later says the file is gone (below); the other views ask again on every change, and a list keeps its rows, selection and scroll until the answer is there (Enter opens a kept row meanwhile). A change of the metamodel or the workspace (also a pull of more than 1,000 elements) refreshes everything. An element changed or added outside and shown within 2 s of the change is highlighted briefly and quietly: a grey tint that fades and is gone after 2.5 s, within the 3 s of SR-116 AK2 (still, without fading, with reduced motion). In the element buffer it marks the fields whose shown value changed (the title when none did, or when the buffer opened just then), never one with input, and only when the file's bytes (`fileSha256`) differ from what the buffer showed, so the app's own save never flashes; in a list, the package page, the neighbourhood and the overview the row, in the matrix the row element. Graph nodes are not marked yet.

# SR-018: Metamodell in eigenem Repository unterstützen

Verification method: Demonstration. Record written by an agent (Claude Code) on 2026-10-24 for issue #30, branch `sr-018-metamodel-repository`. **Not confirmed.** A human confirms it at stage acceptance (D-050).

> Das Tool muss das Metamodell sowohl aus einem Ordner im Haupt-Repository als auch aus einem eigenen Repository lesen können.

## Setup

- Workspace: `fixtures/SR-018/own-repository/`, copied to a temporary folder. `system` is the main repository (workspace file, one element, and a decoy folder `metamodel/` that the workspace file does not name). `models` is the metamodel repository with the folder `model/` (`types.yaml`, `properties.yaml`, `statuses.yaml`). Both were made Git repositories with one commit each.
- Tool: the built CLI, `node packages/cli/dist/bin.js` (shown as `reqseq`), run in `system/`. Linux, Node 22, run as root inside a private mount namespace (`unshare -m`).
- No element command is implemented yet (stage 1 is in progress, open question #127 option 1). Writing is shown through the `files` block of the built core (`packages/core/dist/files/index.js`), which every write command goes through (architecture rule: `files` is the only module that writes to disk).

## AK1: metamodel in its own repository

> Gegeben eine Arbeitsbereichs-Datei nennt für das Metamodell ein eigenes Repository, wenn der Arbeitsbereich geöffnet wird, dann liest das Tool das Metamodell von dort.

Workspace file: `metamodel: { repository: models, path: model }`.

`reqseq workspace status --json` shows `"metamodel": { "repository": "models", "path": "model", "valid": true }`, `"readOnly": false` and no problems (full output under AK2, where the same command runs with `models` read-only). The automated test `[SR-018/AK1] reads the metamodel from the repository the workspace file names` checks that the types are those of `models/model/` (`need`, `system-requirement`) and not the decoy type of `system/metamodel/`.

Findings in metamodel files name the repository: `[SR-018/AK1] reports metamodel findings in the metamodel repository, with the file relative to it` expects `repository: models`, `file: model/statuses.yaml`, line 4 for faulty YAML; the CLI prints such a problem as `models:model/statuses.yaml:4`.

Result: the tool reads the metamodel from the repository the workspace file names.

## AK2: read-only metamodel repository

> Gegeben das Metamodell-Repository ist nur lesend zugänglich, wenn mit den Elementen gearbeitet wird, dann stehen alle Funktionen außer dem Ändern des Metamodells zur Verfügung.

**The typical case.** Rights are per repository and are enforced by the Git server (D-016, D-024; D-021: "Wer das Metamodell ändern darf, regeln die Rechte an diesem Repository"). So the usual read-only metamodel repository is a local clone that can be written, but whose pushes the server refuses. ReqSeq reads Git and never writes to it: no commit, no push (D-036, ADR-0006). It also does not need write access to the metamodel repository for any function: the metamodel is only read (SR-011), and the workspace is read-only only when the metamodel is missing or faulty (#141). So in this case AK2 holds by construction. A metamodel change made locally can still not reach the shared state, because the server refuses the push.

**Additional cases demonstrated here.** The local folder itself is read-only: a read-only file system, shown below, or a checkout without write permission (`EACCES`, automated test). The `models` repository was bind-mounted read-only, a real read-only file system:

```
$ mount --bind models models && mount -o remount,ro,bind models
$ touch ../models/model/new.yaml
touch: cannot touch '.../ws/models/model/new.yaml': Read-only file system
$ reqseq workspace status --json
{
  "name": "Weather station",
  "repositories": [
    { "name": "system", "available": true, "path": ".", "commit": "81fbe2ee…", "readOnly": false },
    { "name": "models", "available": true, "path": "../models", "commit": "edb28635…", "readOnly": true }
  ],
  "metamodel": { "repository": "models", "path": "model", "valid": true },
  "readOnly": false,
  "problems": []
}
exit 0
```

(JSON reformatted to one line per repository; commit IDs shortened.) The human output (`reqseq workspace status`) shows the same values and `No problems.`

Then a change of the metamodel and a change of an element were tried through the files block, still with `models` read-only:

```
$ node write-metamodel.mjs
metamodel change: {"code":"file.read-only","message":"Not written: the folder of model/types.yaml is not writable (EROFS)"}
element change in system: written
$ git -C ../system status --porcelain; git -C ../models status --porcelain
 M requirements/SR-6328cee88fb3.md
```

Observed:

- The metamodel is read and valid; the workspace is not read-only (`readOnly: false`), so `invoke` lets every write command run. Only the repository `models` is shown as `readOnly: true`.
- Changing the metamodel is refused cleanly with `file.read-only`; `models` has no change. Before this SR, `EROFS` ended as `internal`.
- An element in `system` is changed as usual.

Automated tests for the parts not demonstrated here: a checkout without write permission (`EACCES`) and `EROFS` in `workspace.status` (simulated, since tests may run as root); read and write stand-in commands passing the `invoke` guard while `models` is chmod read-only; a read-only metamodel file refused with `file.read-only` (`packages/core/src/metamodel/repository.test.ts`, `[SR-018/AK2] ...`).

Result: with a read-only metamodel repository every function stays available except changing the metamodel, which is refused with `file.read-only`.

## AK3: metamodel as a folder in the main repository

> Gegeben das Metamodell liegt als Ordner im Haupt-Repository, wenn der Arbeitsbereich geöffnet wird, dann arbeitet das Tool genauso.

The same `model/` folder was copied into `system/`, the repository `models` was removed, and the workspace file was changed to one repository with `metamodel: { repository: system, path: model }`.

```
$ reqseq workspace status --json
{
  "name": "Weather station",
  "repositories": [
    { "name": "system", "available": true, "path": ".", "commit": "04e08b0b…", "readOnly": false }
  ],
  "metamodel": { "repository": "system", "path": "model", "valid": true },
  "readOnly": false,
  "problems": []
}
exit 0
```

The test `[SR-018/AK3] works the same with the metamodel as a folder in the main repository` compares both layouts: the same files (relative to their repository), definitions, effective types, validity, problems and read-only state.

Result: the tool works the same with the metamodel as a folder in the main repository.

## Limits

- `repositories[].readOnly` asks the operating system about the repository folder itself (`access(W_OK)`). On Windows `access` never reports a folder as read-only, so `readOnly` is left out there (unknown, not "writable"); AK2 still holds, since a write is refused by the operating system and reported as `file.read-only`. Not demonstrated on Windows or macOS.
- Elements stored in a read-only metamodel repository cannot be changed either: their writes get the same `file.read-only` refusal. Elements in the other repositories are not affected.
- A metamodel repository that is missing locally makes the workspace read-only (open question #141, option 1 assumed); that is SR-011, not this record.
- Changing the metamodel has no catalog command in stage 1; people edit the YAML files (D-021). The refusal shown is the one every ReqSeq write into that repository gets.

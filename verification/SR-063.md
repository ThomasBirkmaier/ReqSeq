# SR-063: Anbindung ohne Programmierung ermöglichen

Verification method: Demonstration. Record written by an agent (Claude Code) on 2026-10-27 for issue #75, branch `sr-063-tool-guide`. **Not confirmed.** A human confirms it at stage acceptance (D-050); the demonstration of AK2 below needs a person and is still to be done.

> Das Tool muss sich an Test- und Auswertungswerkzeuge anbinden lassen, ohne dass dafür programmiert werden muss.

What was delivered: the guide `toolchain/junit/README.md` and its examples in `toolchain/junit/` (an example workspace with four requirements, Vitest tests with their configuration, pytest tests with `pytest.ini` and the JUnit file of a real pytest run), and the end-to-end tests `packages/cli/test/e2e/toolchain-junit.test.ts`. ReqSeq got no new function for it (D-054): the one call is `reqseq evidence enrich-junit` of SR-029.

## The reading (assumptions)

From spec question [#600](https://github.com/ThomasBirkmaier/ReqSeq-archive/issues/600):

- **Q1 „ohne eigenen Code“**: naming the requirement's ID in the test (in the test name, or one property line of the tool) is part of writing the test. „Eigener Code“ is code for the connection: a converter, script, plugin or reporter.
- **Q2 „ein Aufruf der Kommandozeile“**: one ReqSeq call per JUnit file. Keeping the enriched file (a commit, a pipeline artifact) is the pipeline's own step (D-007, D-008, D-036).
- **Q3 „mitgelieferte Beschreibung“**: `toolchain/junit/README.md`, which the delivery will include (ADR-0014).
- **Q4 AK2**: The product owner chooses the person at stage acceptance; one test tool of their choice; the hour runs from opening the guide until `reqseq evidence status` shows the status from their run.
- **Q5 evaluation tools**: the acceptance criteria name test tools only. Evaluation tools read the data of `reqseq data export` (SR-061) and later `data store` (SR-062), with their own D-054 examples; not part of this record.

## AK1: one command line call in the pipeline, no own code

> Gegeben ein Testwerkzeug, das JUnit-XML schreibt, wenn es angebunden wird, dann genügt ein Aufruf der Kommandozeile in der Pipeline, ohne eigenen Code.

### What was checked and how

The tests read the guide: each tested command block carries an invisible mark (`<!-- tested: pipeline-step -->` and others), and the test takes the line from there, so the guide is the source and a changed line is tested as it stands.

1. `[SR-063/AK1] a real Vitest run is connected by the one reqseq call of the guide, and its requirements get a status`: Vitest 5.0.5 runs the example `toolchain/junit/vitest` (from a copy in a temporary folder, offline, with the example's own configuration `reporters: ["default", "junit"]`; only the output path is moved). Then the one line of the guide's step 4 runs as written, with `BUILD=build-1` and the example workspace: exit 0, 4 test cases enriched, no unknown ID, the file written to `evidence/ci/results-build-1.xml`. `reqseq evidence status`: the three requirements named by passing tests are `verified` (one by a name token, one by Vitest's `annotate(..., "reqseq:element")`, one by its identifier `REQ-012`), the one named only by a skipped test is `open`. `reqseq workspace check` has no `evidence.*` finding. The example folder in the repository is unchanged afterwards, ignored files included.
2. `[SR-063/AK1] the JUnit file of a real pytest run is connected by the same call`: `toolchain/junit/pytest/results.xml`, written by pytest 9.1.1 (`pytest --junitxml=results.xml` in `toolchain/junit/pytest`, Python 3.13, 2026-10-27) and kept byte for byte, goes through the same line: exit 0, 2 test cases enriched (one by `record_property("reqseq:element", ...)`, one by a parameter ID), both requirements `verified`.
3. `[SR-063/AK1] the pipeline step of the guide is one reqseq call and the CI examples run exactly it`: the step block is exactly one line, `reqseq evidence enrich-junit ...`. The GitHub Actions and GitLab CI snippets of the guide parse as YAML, hold that line verbatim as a `run` value or a `script` entry, and no other `reqseq` line. The files of `toolchain/junit/` tracked by Git are on an allow-list: the guide, the example workspace, the test files, the tool configuration and the recorded JUnit file. A script, converter or plugin added later fails the test and has to be argued in review.
4. `[SR-063/AK1] a test case with a typo in its ID makes the pipeline step exit with 1 and name it`: the Vitest output with one short ID changed to an unknown one: the line exits with 1 and names the test case and the ID (the promise of step 4 of the guide; the details are SR-029 AK2's).
5. Inspection of `toolchain/junit/` by the agent: besides the guide and the example workspace it holds only test files (`vitest/login.test.js`, `pytest/test_login.py`), tool configuration (`vitest/vitest.config.mjs`: reporters and output file; `pytest/pytest.ini`: `junit_family = xunit1`) and the recorded `pytest/results.xml`. No converter, script or plugin.

### What these tests do not prove

- Only Vitest and pytest were run. For other tools (Jest, Maven, Gradle, CTest, Go) the guide says what their JUnit file must hold; they were not run.
- The CI snippets were not run on a CI server (none is reachable offline); only the ReqSeq line in them is tested. D-054's own example for the pipeline is a separate item and is not fulfilled by these snippets.
- pytest is not installed on the CI runners, so CI does not run pytest; it uses the recorded file. A later pytest that changes its JUnit layout is noticed only when someone records the file again (the guide says how).

### Result

With Vitest and with pytest, one `reqseq evidence enrich-junit` line after the test run connects the results to the requirements, and the statuses follow. No code was written for the connection; the tests name only the IDs. Not confirmed.

## AK2: a person who does not know the tool connects one within an hour

> Gegeben die mitgelieferte Beschreibung, wenn eine Person ohne Kenntnis des Tools sie befolgt, dann ist ein Werkzeug in höchstens einer Stunde angebunden.

### What the agent checked

1. `[SR-063/AK2] every reqseq command of the guide runs as written on the example workspace`: the blocks "Try it here" of the guide (Vitest, then pytest), line by line: every `reqseq` line runs as written and exits with 0, the `export` lines set the variables, and every other line (`mkdir`, `cp`, `cd`, the Vitest run) must be one the test knows exactly, so a changed line fails the test. The status after each block is the one the guide's text names, and the enrich lines of both blocks are the line of step 4.
2. A dry run of the guide by the agent: on 2026-10-27, in bash on Linux (Node 22, pnpm 10.28), with a fresh temporary home folder: the CLI as "What you need" said then (built checkout, an `alias`), then the blocks "Try it here" for Vitest and pytest copied out of the guide and run verbatim in one shell, then the untested line for a fresh pytest run (pytest 9.1.1 in a virtual environment) and the step 4 line with `BUILD=build-3`. Every command exited with 0; `evidence status` showed the statuses the guide names after each block (SR-a1c0de, SR-b2c0de, SR-c3c0de verified, SR-d4c0de open), `workspace check` had no problems, and the run took 11 seconds. What the dry run changed in the guide: the first draft ran Vitest with `cd toolchain/junit/vitest && pnpm exec vitest run`, but `pnpm exec` runs in the repository root and took the repository's own Vitest configuration; the guide now uses `pnpm exec vitest run --root toolchain/junit/vitest`. pytest leaves `.pytest_cache/` in the example folder, which `.gitignore` now ignores and the guide names. A second dry run on 2026-10-28, after the code review of #603: the CLI as "What you need" now says (`chmod +x` and a link on the `PATH`, here `~/.local/bin`, so that a script without the alias finds `reqseq` too), the two "Try it here" blocks verbatim, then two JUnit files in one build (`BUILD=build-5`: a Vitest run and a fresh pytest run), each with its own `--output` name as step 4 now says (`results-$BUILD-unit.xml`, `results-$BUILD-api.xml`). Both files were written and counted, all statuses as the guide names, `workspace check` without problems, 12 seconds. The review had found that the same `--output` twice keeps only the last file without a message (the guide said "once per file" only), that the folder of `--output` must exist (the CI snippets now run `mkdir -p`), and that an alias does not reach CI steps; the guide was fixed for all three, and the e2e test "two JUnit files of one build …" keeps the names working. The agent did not follow a clean-room protocol (it had read the plan and the code before), so this checks that the commands work, not that the guide is clear.

The agent knows ReqSeq; its time says nothing about AK2. The tests keep the commands of the guide working; they cannot show that a person understands the guide.

### Result

The guide's commands work as written, on Linux in bash. Whether a person who does not know ReqSeq connects a tool within an hour is open: the demonstration below. Not confirmed.

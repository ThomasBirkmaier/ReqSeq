## AK2: the delivery installs in a network without internet

### Linux evidence

- `[SR-078/AK-n50j] the linux delivery installs without network and its command line and MCP server run` and `[SR-078/AK-n50j] the CLI tarball installs without network and runs on Node` in `packages/cli/test/delivery/delivery.test.ts`, passed in the release workflow on `main@6542f58` (`spec/evidence/ci/delivery-ubuntu-24.04.xml`).
- They need a network namespace with loopback only (`assertOffline`), which macOS and Windows do not have, so there they skip with `NO_NAMESPACE`.

### Why it holds on macOS and Windows

- **The archive of each system is complete.** `[SR-249/AK-m4f9] the <system> delivery contains the command line, the MCP server, the web UI and Node, and no Electron` and `[SR-249/AK-m4f9] the launcher of the <system> delivery runs the command line and the MCP server on its Node` pass on `macos-26` and `windows-2025` (`delivery-macos-26.xml`, `delivery-windows-2025.xml`): the macOS and the Windows archive hold their own Node and every package the command line and the MCP server load, and the launcher runs them without an installed runtime.
- **The install steps fetch nothing.** The install guide (`docs/guide/how-to/install-reqseq.md`) has the same kind of steps on every system: unpack the archive, move it (`ReqSeq.app` to `/Applications` on macOS), and once after unpacking `xattr -dr com.apple.quarantine` on macOS or `Unblock-File` on Windows. Both only change a local file attribute. The Linux test runs the same steps that Linux has (unpack); no step on macOS or Windows downloads, and none runs a package manager.
- **The CLI tarball is one file for all systems.** `reqseq-cli-<version>.tgz` is the same tarball on every system, with its dependencies inside (`scripts/package/stage.mjs --pack`) and no install script in `packages/cli/package.json`. `npm install -g --offline` never asks the registry, on any system.
- **What runs after the install is the same code.** The command line and the MCP server are the same JavaScript on every system; that it opens no connection is SR-078 AK1, which `offline.test.ts` shows on all three systems with the network block of the tests.
- **Platform-dependent and not covered:** Git, which the guide asks to install beforehand (`xcode-select --install` on macOS, Git for Windows), is a prerequisite of the system, not a step of this installation; the Linux runner has Git preinstalled as well. Windows SmartScreen without `Unblock-File` warns about `ReqSeq.exe`; the warning and **Run anyway** also appear without network.

AK2 holds on macOS and Windows by this analysis.

## AK3: the web UI makes no connection to another machine

### Linux evidence

- `[SR-078/AK-wx9y] the server and its pages make no connection to another machine, also for an element that names one` in `packages/web/test/contract-content.spec.ts`, in Chromium, Firefox and WebKit (projects `contract-*` of `packages/web/test/playwright.config.ts`), passed on `main@a6730d6` (`spec/evidence/ci/web-ubuntu-24.04.xml`).
- The `web` job of CI runs only on `ubuntu-24.04` (`.github/workflows/ci.yml`).

### Why it holds on macOS and Windows

- **The recorders are not Linux tooling.** The pages' requests are refused and recorded by Playwright's `context.route` (`refuseRemote` in `packages/web/test/contract.ts`), the server's by the network block of the tests, a Node preload (`scripts/test-support/block-network.mjs`) that writes each attempt to `REQSEQ_NETWORK_LOG`. Both work in the process, the same way on every system. The `unshare -rn` around the job only adds a second wall; the assertions read the two recorders.
- **What is tested is the same on every system.** The server is `reqseq ui` of the built CLI, the same JavaScript of `packages/api` and `packages/core` on every system (ADR-0002, ADR-0020); the pages are one bundle (`packages/web`, vite build). The sources of `packages/web/src` and `packages/api/src` have one branch on the operating system, the label of the finder key (`⌘K` or `Ctrl+K`, `packages/web/src/areas/lists.ts`); nothing that loads or connects depends on it.
- **The browser engines are the named ones.** AK3 names Chromium, Firefox and WebKit, and the test runs all three. The engine's own background connections are not part of AK3 (it names the server and its pages).

AK3 holds on macOS and Windows by this analysis.

## What differs per system

- **The web engine:** WebKitGTK on Linux, WKWebView on macOS, WebView2 on Windows (ADR-0021). Each starts its own processes, writes its own data and may connect by itself.
- **The shell's own code** (`packages/shell/shell/src/`): `unix.rs` (process group, output filter, opener call) serves Linux and macOS; `windows.rs` (Job Object, handle list, output filter, `ShellExecuteW`) serves Windows only. `engine.rs` switches off the engine's own connections with one block per system. `host.rs` calls `gtk::init` on Linux only.
- **The recording:** the Linux tests record with `strace -f` and a network namespace. On Windows the e2e suite records with the audit of process creation (4688), the ETW provider Microsoft-Windows-Kernel-File through `logman`, firewall program rules with the audit of refused (5157) and permitted connections (5156) and the DNS client log (3006) (`packages/shell/e2e/record-windows.ts`, ADR-0021 Test seam). On macOS it records with `eslogger` (Endpoint Security), `tcpdump -k` on the `pktap` interface and a pf anchor (`packages/shell/e2e/record-macos.ts`, ADR-0021 Test seam).

## AK2: the token in no argument, output or file of the shell

- Linux: `[SR-252/AK-nhyc] the token is in no argument, no output of the shell and no file it writes` in `packages/shell/e2e/shell.test.ts` (`describe.runIf(linux)`, `strace`), passed on `main@a6730d6` (`spec/evidence/ci/shell-ubuntu-24.04.xml`).
- macOS: the shell's arguments to the server and the output filter are the Unix code that Linux runs, and the server's arguments are fixed before the server prints the token (`start.rs`, unit test `the_server_is_node_with_the_cli_and_ui_no_open_in_the_root` on all three systems). Not shown: the processes WKWebView starts and the files the system writes for the app (WKWebView's processes are not started by the shell as on Linux), which the Linux test covers for WebKitGTK.
- Windows: `[SR-252/AK-nhyc] the token is in no argument, no output of the shell and no file it writes (Windows)` in `packages/shell/e2e/shell.test.ts`. It runs `windows.rs` (output filter, start of the server) and records the command lines of the shell's whole process tree, WebView2's included, and the files the tree outside the server creates or writes, read back for the token as UTF-8 and UTF-16. Each write is named from the Create or NameCreate before it in the trace, of any process, since a file object is shared by every process with a handle to it. Controls: the trace lost no buffer or event, the engine's renderer is in the process tree, the server's opens of the workspace file and the engine's Write events in its data folder are in the record. Gaps: see below.
- macOS since #2465: `[SR-252/AK-nhyc] the token is in no argument, no output of the shell and no file it writes (macOS)` in `packages/shell/e2e/shell.test.ts`. It runs `unix.rs` and WKWebView and records the arguments of every program the shell's tree runs, and of every WebKit process that starts while the shell runs (launchd starts them through xpcproxy, whose exec names their arguments), and the files the tree outside the server and those WebKit processes create, rename to or open for writing, read back for the token as UTF-8 and UTF-16. Controls: Endpoint Security dropped no event, the stream has the shell's exit and a marker process after it, the controls' execs, the server's opens of the workspace file, a WebContent and a Networking process with their exec, and a file the engine wrote. No file is excepted as the engine's data folder; the test reads back every written file. Gaps: see below.

## AK6: only the server, the engine, the dialogs and the opener; no workspace file

## AK7: no connection to another machine, also none the engine makes by itself

- Linux: `[SR-252/AK-wfx8] showing pages and an element with a remote image and raw HTML connects to no other machine`, same file and run, which records the connections of WebKitGTK (DNS prefetching switched off in `engine.rs`).
- macOS since #2465: `[SR-252/AK-wfx8] showing pages and an element with a remote image and raw HTML connects to no other machine and looks up no name (macOS)` in the same file. The shell and its server run in the test group `reqseq-e2e`, and pf rules in the anchor `com.apple/reqseq-shell-e2e` refuse and count every connection of that group to an address other than loopback (IPv4 and IPv6). launchd starts WKWebView's processes outside that group, so their connections are recorded, not refused (#2479): pktap names the process of every packet, and for a lookup through mDNSResponder the process that asked. The test fails on any refused connection of the group after the controls, and on any packet of the shell's tree or of a WebKit process started during the session whose source or destination is not loopback, lookups included. Controls: outside the group the control's connection to `192.0.2.1` and its lookup are recorded with its process; in the group it is refused (`ECONNREFUSED`), counted by pf and its reset is recorded; the engine's packets to its server on loopback are recorded; tcpdump dropped no packet.
- Windows: `[SR-252/AK-wfx8] showing pages and an element with a remote image and raw HTML connects to no other machine and looks up no name (Windows)` in the same file refuses every connection of the shell, the server (a copy of `node.exe`) and `msedgewebview2.exe` to an address other than loopback, and records refusals (5157), permitted connections (5156) and name lookups (3006). The test fails on any refused connection of the tree, on any permitted one whose local or remote address is not loopback, and on any lookup; the permitted connections cover every process of the tree, also a child of the server that no program rule refuses. An event counts for the process that held its process ID at the event's time, so a process that had the ID before the shell is not counted. Controls: the control process's connection to `192.0.2.1` is refused and recorded with its program, its lookup is recorded, the engine's own connection to its server on `127.0.0.1` is in the 5156 record, the firewall profiles are on, and every engine program in the record is one the rules refuse. A name lookup of the tree counts as a connection (#2480); lookups go through the DNS client service, which no program rule refuses, so the test fails on any lookup in the DNS client log. The engine's own lookup of `wpad` (proxy auto-detection) is switched off with `--no-proxy-server` (#2482). Not covered on Windows: what services make on the engine's behalf besides lookups (the WinHTTP auto-proxy service), and IPv6, since the runner has only link-local IPv6.

## AK8: the window cannot open: exit code, English reason, no server

- Linux: `[SR-252/AK-ts68] on Ubuntu 24.04 without libwebkit2gtk-4.1-0 the shell ends with 1, names the package and the reason, and starts no server` (`packages/shell/test/delivery/no-engine.test.ts`) and `[SR-252/AK-ts68] on a machine where the window cannot open, the shell ends with a code other than 0, an English reason, and no server` (`packages/shell/test/delivery/shell.test.ts`, skipped on macOS and Windows: "a start without a display is tested on Linux"), passed on `main@6542f58` (`spec/evidence/ci/delivery-ubuntu-24.04.xml`). The first runs the Linux launcher, the second the `gtk::init` branch of `host.rs`; both exist on Linux only.
- macOS and Windows: a window that cannot open reaches the shell's rules through Tauri (an error of the builder, or `WindowFailed` from `setup`). The rule itself, an English reason and exit code 1 without a server, is shown by the unit test `a_window_that_cannot_open_starts_no_server` in `packages/shell/shell/src/run.rs`, which runs on all three systems but is no tagged evidence. Whether every failure of the engine comes back to the shell as an error is not shown on these systems, and ADR-0021 assumption A3 records the opposite for one Windows case: started with `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` set to an empty folder, the release `ReqSeq.exe` neither ended nor wrote to standard error within 60 s (#2407).
- Windows: `[SR-252/AK-ts68] with an empty WebView2 runtime folder the shell ends with 1, names the reason in English, and no server runs` in `packages/shell/e2e/shell.test.ts` starts the e2e build with `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` set to an empty folder: exit code 1, the reason of the builder error on standard error (not the fixed line of the panic hook, which a release build reaches by abort), no page, and no process left whose parent was the shell. Open in #2477: the release `ReqSeq.exe` under the same condition, and the shell that neither ends nor prints a reason with an unwritable user data folder or an engine process that cannot start.
- macOS (#2478): no condition was found that stops the window. WKWebView is part of macOS 26 (ADR-0021), so the engine cannot be missing as `libwebkit2gtk-4.1-0` can on Linux, and the e2e build started through `launchctl bsexec` as root or as the runner user still showed the page (probe of #2465, https://github.com/ThomasBirkmaier/ReqSeq/issues/2465#issuecomment-7106923320; the release `ReqSeq.app` was not started that way). The window code of `host.rs` is the same on macOS and Windows. A builder error of Tauri ends the shell in `host.rs` (`ends_with_failure`) before the server starts, which the Windows e2e test above runs; `WindowFailed` from `setup` reaches the rule of `run.rs` that the unit test `a_window_that_cannot_open_starts_no_server` shows on all three systems. Not shown: whether a failure of WKWebView comes back as one of these errors or, as in the Windows cases of #2477, as a hang. The analysis rests on the shared code and on no way to make the window fail.
- **Carries over** to macOS by this analysis (#2478). On Windows AK8 is not met for every way the window can fail (#2477).

## Gaps of the Windows recording

These hold for the Windows tests of AK2 and AK6 and are not shown by them:

- A file written and deleted before the test reads it back counts as gone, not as holding the token (the Linux test reads files back the same way).
- Paths are compared without their alternate data stream, so the token is looked for in the main stream of `file:stream`, not in the stream itself.
- Writes the Kernel-File provider does not log as Write events, such as writes through a mapped view, are not checked.
- A write to a file object created before the trace started has no name in the trace and is not read back; the test reports how many there were (0 or 1 in the runs of PR #2481).
- A program started through a broker (COM, WMI, a ShellExecute that explorer carries out) is not a descendant of the shell in the process creation events, so its arguments (AK2) and its start (AK6) are not checked.
- Paths on a network share (`\Device\Mup`) are not mapped to a drive and are not read back.

## Gaps of the macOS recording

These hold for the macOS tests of AK2, AK6 and AK7 and are not shown by them:

- `eslogger` records only the events of the shell, the server's copy of `node`, WebKit, xpcproxy, sudo and `env`, because without that selection Endpoint Security dropped events on the runner. A program of the tree outside the server that is none of these fails the AK6 test by its exec, but its own file events are not recorded.
- Every WebKit process that starts while the shell runs counts as the shell's, also one another app asked for; a WebKit process that started before the shell and serves it would not be counted.
- A process that launchd starts on the shell's behalf other than WebKit's (an XPC service of AppKit or of the system) is not in the shell's tree, so its arguments (AK2), its start (AK6) and its packets (AK7) are not checked.
- What system services do for the engine besides lookups through mDNSResponder (`trustd`, `nsurlsessiond`) is not attributed to the engine.
- Writes through a file opened before the recording, or through a mapped view, and a file written and deleted before the test reads it back, are not checked.
- IPv6 refusals: the runner has only link-local IPv6.

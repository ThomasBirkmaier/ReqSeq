# SR-010: Dateien ohne Tool lesbar halten

Verification method: Inspection. Record written by an agent (Claude Code) on 2026-11-05 for issue #17, branch `sr-010-readable-files-record`. Not confirmed yet: a human confirms it at stage acceptance (D-050).

> Die Dateien des Tools müssen in einem Texteditor ohne das Tool verständlich sein.

## AK1: title and text are plain text in an element file

> Gegeben eine Element-Datei, wenn sie in einem Texteditor geöffnet wird, dann stehen Titel und Text im Klartext darin.

### How and result

I opened `schemas/examples/element/SR-825b7146fb54.md` and an element of this repository's spec (`spec/need/N-c99900ac6b04.md`) as plain text.
- The title is a line `title: Show wind speed in large digits` in the YAML front matter.
- The text is the Markdown body below the closing `---`, as written ("The display shows the wind speed in large digits, readable from three metres.").
- The acceptance criteria are a YAML list of sentences.
- There is no encoding, escaping or binary part. An image is a separate file named by a relative Markdown link (`![Layout](SR-825b7146fb54/layout.png)`).

## AK2: every key of the standard model is a readable English word

> Gegeben das Standardmodell, wenn seine Schlüssel geprüft werden, dann sind alle Schlüssel lesbare englische Wörter, zum Beispiel status oder derives-from.

### How and result

I listed every `key` of `schemas/examples/metamodel/standard-model.yaml`, the standard model that `reqseq workspace init` writes:
- types: `need`, `use-case`, `system-requirement`, `decision`, `variant`, `package`;
- properties: `title`, `rationale`, `requirement-type`, `priority`, `validation-criteria`, `acceptance-criteria`, `validity`, `packages`, `emergent`, `verification-method`, `topic`, `source`, `source-identifier`, `import-date`, `delivery`, `import-version`, `statement`;
- choice values: `functional`, `performance`, `interface`, `constraint`, `quality`, `low`, `medium`, `high`, `test`, `inspection`, `analysis`, `demonstration`;
- relations: `refines`, `derives-from`, `based-on`, `supersedes`, `replaces`, `excludes`;
- statuses: `draft`, `approved`, `obsolete`.

All are English words or hyphenated English phrases, with no abbreviations or codes. The structural keys of an element file (`id`, `type`, `status`, `title`, `version`, `repository`) are English words too.

## AK3: a relation within the same repository has the target's title next to its ID

> Gegeben eine Beziehung innerhalb desselben Repositories, wenn die Datei gelesen wird, dann steht der Titel des Ziels neben seiner ID.

### How and result

- In the example element, `derives-from` holds `{ id: 878e…, version: n1:…, title: Wind speed visible at a glance }` for a target in the same repository, and only `{ id, version, repository: subsystem-sensor }` for one in another repository (D-058).
- I wrote a relation with the built CLI in a workspace made from the examples (`reqseq relation add SR-46fb54 refines SR-7b5503`). The file got `{ id: 323d…, version: n1:8a3770a29823fb93, title: Show wind speed in large digits and as a gauge }`.
- The stored titles follow their targets whenever ReqSeq writes the source file (`relation-titles.ts`, ADR-0004 "Stored titles"). `[SR-021/AK1] writes UUID, current version and title of a target in the same repository` (`packages/core/src/commands/relation/add.test.ts`) and `relation-titles.test.ts` test that.
- A title is only as current as the last write of the source file. A target renamed later shows its old title there until ReqSeq writes the source file again. The title does not count for the version (SR-091 AK2), so a rename gives no hint.

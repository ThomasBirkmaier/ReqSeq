# SR-020: Bestand schnell prüfen

Verification method: Test. An agent (Claude Code) wrote this record on 2026-10-24 for issue #32, branch `sr-020-fast-check`. It says what the test measures and where its result is recorded. **Not confirmed.** A human confirms it at stage acceptance (D-050).

> Gegeben ein Arbeitsbereich mit 50.000 Elementen und 200.000 Beziehungen auf einem Rechner mit 4 Kernen und 16 GB Speicher, wenn die Prüfung über die Kommandozeile läuft, dann ist sie nach höchstens 60 Sekunden fertig.

## Test

- AK1: `[SR-020/AK1] checks the workspace from the command line in at most 60 s` in `packages/cli/test/perf/workspace-check.test.ts`. It is part of the performance suite (`pnpm test:perf` after `pnpm build`, ADR-0011), which runs nightly and on pull requests labelled `perf`. The workflow runs it on `ubuntu-24.04` inside `unshare -rn`, so there is no network.
- Workspace: the generated workspace of `packages/testkit` (D-055, seed 36). It has 50,000 elements and 200,000 relations with valid versions, in four repositories, written to a new temporary folder.
- What is timed: one new process of the built CLI, `reqseq workspace check --json`, from spawn to exit. That includes Node start, reading every file, every finding state of stage 1 and the JSON output. The process gets an empty cache folder of its own and loads the network block (SR-077).
- Asserted: exit code 0, nothing on stderr, `{ ok: true, problems: [], checkedElements: 50000 }`, and a time of at most 60 s. The test is tagged, so it asserts its threshold (ADR-0011). The time is also recorded in `verification/performance.md` on the branch `perf-record` (#340).

## Machine

The perf job runs on the GitHub-hosted `ubuntu-24.04` runner and prints its cores and memory. For this private repository it has 2 cores and 7 GB (printed in run 40137117071), less than the 4 cores and 16 GB of AK1, so a pass there is conservative evidence for AK1 (ADR-0011); a failure on it would be measured again on the machine of AK1.
